# Qwen 로컬 창작 서비스 계획

**지금은 기존 모노레포에 독립 프로젝트를 두고, M5 Pro·통합 메모리 48GB에서 텍스트 기능부터 만드는 것을 권한다.** Qwen으로 페르소나 대화·소설·영상 대본을 만들고, 실제 영상 생성과 편집은 각각 전용 모델과 편집 도구가 맡는다. 카카오톡은 과거 대화 파일 가져오기와 채널 챗봇 연결을 나누어 설계한다. 개인 대화 분석은 로컬에서 시작하고, 외부 접속과 영상 공유가 필요해질 때 클라우드 웹·API·저장소·CDN을 추가한다. 이번 판단은 개인 개발과 소규모 비공개 사용을 출발점으로 하며, 유료 다중 사용자 서비스의 용량이나 비용을 확정한 것은 아니다.

2026년 11월 12일 확인한 공개 범용 Qwen 계열은 Qwen3.8이다. 이 장비의 품질 후보는 **Qwen3.8-27B 4bit**, 응답 속도 비교군은 **Qwen3.5-9B 4bit**로 잡는다. 27B 모델은 Apache-2.0이며 이미지·영상 입력을 이해한다. 모델마다 라이선스가 다르므로 계열 이름만 보고 사용 조건을 판단하면 안 된다. [Qwen 공식 모델 목록](https://huggingface.co/models?author=Qwen&sort=created), [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B), [Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B)

**1. 모델을 고르기 전에 알아야 할 개념**

모델은 입력을 받아 내용을 생성하고, 프로그램은 어떤 정보를 줄지, 답을 어디에 저장할지, 실패하면 어떻게 다시 실행할지를 결정한다. 같은 모델도 이 주변 설계에 따라 캐릭터 일관성과 소설 완성도가 달라진다.

| 개념               | 의미                                                       | 이번 작업에서의 판단 기준                                                                             |
| ------------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 파라미터·B         | 모델이 학습한 수치의 개수. 27B는 약 270억 개 규모          | 큰 모델은 메모리·계산량이 증가한다. 한국어 문체와 대화 품질이 그 비용만큼 나아지는지 비교한다.        |
| 양자화·4bit        | 가중치를 더 적은 비트로 표현해 크기와 메모리를 줄이는 방식 | 내 장비에서 큰 모델을 실행하기 위한 선택이다. 압축에 따른 품질 변화는 같은 문제로 비교한다.           |
| 토큰               | 모델이 텍스트를 나누어 처리하는 단위                       | 글자 수와 같지 않다. 한국어 소설 분량·입력 제한을 단순 글자 수로 환산하지 않는다.                     |
| 컨텍스트           | 한 번의 생성에서 모델이 참고하는 입력과 출력의 범위        | 길게 잡으면 더 많은 정보를 볼 수 있지만 시간·메모리 부담이 커진다. 큰 최대 사양을 그대로 켜지 않는다. |
| KV cache·실행 상태 | 생성 중 이전 계산을 재사용하기 위해 보관하는 정보          | 가중치 파일 크기 외에도 메모리를 차지한다. 대화 길이와 동시 요청이 늘 때 확인한다.                    |
| 추론               | 학습된 모델로 답을 생성하는 과정                           | 지금 만들 대부분의 기능이다. 처음부터 모델을 새로 학습할 필요는 없다.                                 |
| 런타임             | 모델을 읽고 GPU에서 실행하는 소프트웨어                    | MLX 계열·Ollama·llama.cpp 중 모델과 Mac 지원이 확인된 경로를 고른다.                                  |

48GB 통합 메모리는 macOS·브라우저·IDE·CPU·GPU가 공유하며, 전용 VRAM 48GB와 같은 조건이 아니다. 다운로드 파일이 18GB라고 실행 중에도 18GB만 쓰는 것은 아니다. Qwen3.8의 Ollama 목록에는 27B와 MLX 태그가 있고 다운로드 크기는 18GB로 표시되지만, 실제 메모리는 문맥 길이·입력 형태·동시성에 따라 달라진다. MLX-VLM 개발 문서에도 `mlx-community/Qwen3.8-27B-4bit` 실행 예제가 있다. **문서상 지원과 내 Mac에서의 속도는 별도로 확인해야 한다.** [Ollama Qwen3.8](https://ollama.com/library/qwen3.8), [MLX-VLM](https://github.com/Neywa-Labs/mlx-vlm)

첫 실험은 MLX-VLM의 27B 4bit 경로 하나로 시작한다. 설치·API 관리 편의가 더 중요하면 Ollama를 대안으로 비교하되, 처음부터 런타임과 모델을 여러 개 상주시킬 필요는 없다. 문맥 8K, 동시 생성 1개부터 시작하고 실제 메모리 압박과 swap을 보면서 늘린다. macOS와 개발 도구에 10–12GB 정도의 여유를 남기는 것을 초기 예산으로 잡되, 이는 실측 결과나 성능 보장이 아니다. 27B의 반응이 답답하면 같은 질문을 9B에 넣어 품질 차이와 기다리는 시간을 비교한다.

모델 선택에서는 첫 글자가 나오는 시간, 답변 완성 시간, 긴 대화의 품질, 메모리 압박을 측정한다. 소설은 설정 오류와 사람이 고치는 양도 본다. `temperature`는 답의 변화를 조절하는 설정이며 지식을 추가하지는 않는다. 작업별 설정을 고정해 비교한다.

**2. 페르소나와 기억은 프롬프트부터 만들고 학습은 나중에 판단한다**

원하는 성격의 챗봇을 만들 때는 세 가지 방법의 역할을 구분하면 선택이 쉬워진다.

| 방법                   | 모델에 영향을 주는 방식                               | 먼저 쓰기 좋은 문제                                        |
| ---------------------- | ----------------------------------------------------- | ---------------------------------------------------------- |
| 프롬프트·페르소나 카드 | 매번 행동 규칙과 예시를 알려준다                      | 말투, 존댓말, 농담 강도, 답변 길이, 피할 행동              |
| RAG                    | 질문과 관련 있는 저장 자료를 찾아 입력에 붙인다       | 과거에 확인한 사실, 작품 설정, 인물 관계, 필요한 대화 예시 |
| 파인튜닝·LoRA          | 예시로 모델의 가중치 또는 작은 추가 가중치를 학습한다 | 프롬프트로 계속 해결되지 않는 반복적인 형식·문체 문제      |

“짧게 말하고 먼저 공감한다”는 페르소나 카드에, “주인공은 왼손에 상처가 있다”는 검색할 작품 설정에 둔다. **대화를 읽히거나 RAG로 자료를 붙이는 것만으로 모델 가중치가 학습되지는 않는다.** LoRA는 작은 업데이트 행렬을 학습하지만 데이터 준비와 평가가 필요하며, 원문을 삭제해도 학습 결과에서 제거된 것은 아니다. [Hugging Face LoRA 설명](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora)

처음에는 페르소나 카드와 최근 대화 요약으로 시작하고, 필요한 사실을 자주 잊거나 자료가 커지면 RAG를 추가한다. 임베딩은 문장을 검색하기 좋은 숫자 표현으로 바꾼 것이며 익명화 장치는 아니다. 검색 범위는 사람·작품별로 분리하고, 답의 근거를 확인할 수 있게 한다.

카카오 대화에서는 **그 사람의 본질적 성격을 확정하기보다, 관찰한 말투와 상황별 대화 성향을 추출**하는 것이 현실적이다. “친한 상대에게 짧은 문장을 쓰고 농담을 자주 한다”는 근거를 표시할 수 있지만, 특정 대화방만 보고 고정된 성격이나 MBTI를 확정하는 것은 이 계획의 기능이 아니다. 답장이 늦다는 사실도 성격으로 바로 해석하지 않는다. 관계·주제·기간에 따라 행동이 달라질 수 있기 때문이다.

말 길이·존댓말 전환·질문·유머 예시를 근거 메시지와 함께 정리하고 당사자가 수정·저장하게 한다. AI 페르소나임을 표시하고, 말투 유사성과 사적인 사실의 재현 여부를 따로 평가한다. 원문 속 지시문은 분석 대상 데이터로 취급하고 시스템 명령이나 도구 실행 권한으로 승격하지 않는다.

**카카오톡 로그인이나 메시지 API로 개인 채팅방의 과거 대화를 읽을 수 있다고 전제하면 안 된다.** 카카오 공식 답변은 개인 간 수발신 내역의 외부 연동을 제공하지 않는다고 설명한다. 초기 입력은 동의를 받은 대화 내보내기 파일이나 예시 문장으로 만든다. 파일의 화자·기간·본문을 사용자가 확인한 뒤 분석하며, OS별 내보내기 형식은 실제 샘플로 검증한다. [카카오 공식 연동 답변](https://devtalk.kakao.com/t/topic/148362), [카카오톡 메시지 API](https://developers.kakao.com/docs/ko/kakaotalk-message/rest-api)

실시간 카카오 대화는 별도의 **카카오톡 채널 챗봇**으로 연결한다. 이는 개인 대화방 이력을 읽는 기능과 다르다. 현재 공식 안내의 일반 스킬 응답 제한은 5초, 콜백 URL은 5분 유효·1회 사용이므로 긴 영상·소설 작업은 접수 후 웹 결과 화면에서 확인하는 방식이 적합하다. [스킬 만들기](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/make_skill), [콜백 개발 가이드](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/ai_chatbot_callback_guide)

원문·요약·임베딩·프로필은 Mac 안에 두고, 당사자가 승인한 범위만 사용하는 정책을 권한다. 이는 모든 개인 사용에 전원 동의만이 유일한 법적 근거라는 뜻은 아니다. 외부 서비스 단계에서는 실제 처리 근거와 국외 이전을 검토한다. 원문 삭제가 검색 자료·프로필 삭제로 이어지게 만들며, 초기에는 원문 LoRA 학습을 하지 않는다. [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334803), [제21조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335641)

**3. 소설과 영상은 단계를 나눌수록 수정하기 쉬워진다**

소설은 한 번에 장편 전체를 생성하기보다 **설정집 → 시놉시스 → 회차 목표 → 장면 초안 → 검토 → 확정** 흐름으로 만든다. 설정집에는 세계관, 인물, 관계, 시간 순서, 문체를 둔다. 장면을 생성할 때 필요한 설정과 앞 장면의 요약만 전달한다. 사용자가 수정한 원문을 보존하고, 승인한 내용만 확정 설정에 반영한다. 모델이 임의로 만든 초안의 사실이 기존 설정을 덮어쓰면 이후 장면까지 오류가 전파되기 때문이다.

첫 소설은 인물 2–3명과 짧은 장면 몇 개로 시작한다. 이름·시점·시간 순서·인물 행동·반복 표현을 확인해 검색과 프롬프트의 문제를 먼저 고친 뒤 큰 모델이나 파인튜닝을 판단한다.

영상에서는 **영상 이해·영상 생성·영상 편집이 서로 다른 작업**이다. 영상 이해는 기존 장면을 보고 설명하거나 필요한 구간을 찾는 일이다. 영상 생성은 새 프레임을 만드는 일이고, 편집은 클립을 자르고 순서를 정하고 자막·음악을 합치는 일이다. Qwen3.8-27B의 영상 입력 지원은 그 모델 하나가 완성 영상을 출력한다는 뜻이 아니다. [Qwen3.8-27B 모델 카드](https://huggingface.co/Qwen/Qwen3.8-27B)

추천하는 영상 흐름은 다음과 같다.

```text
아이디어 → Qwen 대본·장면 목록 → 장면별 소스 준비 또는 영상 생성
       → 편집 가능한 타임라인 → 자막·음악·FFmpeg 렌더 → 미리보기·내보내기
```

Mac에서는 보유하거나 사용 권리가 있는 소스의 편집부터 완성한다. Qwen은 구간·순서·자막을 구조화된 데이터로 만들고, 프로그램이 검증한 편집 연산만 실행한다. 임의 셸 명령은 실행하지 않는다. 원본과 타임라인을 별도로 보관해 실패해도 편집 내용이 남게 한다.

실제 생성은 5–10초의 짧은 한 장면부터 검증한다. Wan2.2-TI2V-5B는 후보 중 하나이며 공식 저장소에 최소 24GB VRAM GPU와 offload를 사용하는 예제가 있다. 이는 NVIDIA 환경 기준이고 M5 Pro 48GB에서 같은 명령이나 속도가 보장된다는 근거가 아니다. **Mac에서의 생성 지원과 시간을 먼저 확인한 뒤, 부족하면 영상 작업만 클라우드 GPU에 맡기는 선택**이 합리적이다. 이 후보가 모든 최신 영상 모델 중 최상이라는 뜻은 아니다. [Wan2.2 공식 저장소](https://github.com/Wan-Video/Wan2.2)

영상 품질은 대본 준수·인물 일관성·움직임·자막 가독성으로 평가한다. 얼굴·목소리 복제는 최초 범위에서 제외하고 음성·음악의 사용 조건은 별도 확인한다. 텍스트와 영상의 동시 실행이 느리면 작업 시간이나 계산 장치를 나눈다.

**4. Cloud delivery는 웹 접속·계산·파일 전달을 나누어 이해하면 된다**

웹·API를 클라우드에 두면서 실제 답 생성은 Mac에서 할 수 있다. 혼자 Mac에서만 쓰는 단계에는 클라우드가 없어도 된다. 외부 접속을 추가할 때 어떤 정보가 어느 서버를 지나는지 그리면 비용과 개인정보 범위를 함께 판단할 수 있다.

| 구성         | 역할                                         | 도입 시점                                                     |
| ------------ | -------------------------------------------- | ------------------------------------------------------------- |
| 웹·API       | 화면 제공, 로그인, 요청 접수, 작업 상태 관리 | 다른 기기나 사용자의 외부 접속이 필요할 때                    |
| 워커         | 모델 실행과 영상 렌더처럼 실제 계산 수행     | 로컬 단계부터 필요. 텍스트는 Mac, 영상은 다른 GPU로 분리 가능 |
| 작업 큐      | 오래 걸리는 일의 순서·진행·재시도 관리       | 영상 생성과 중단 후 복구를 지원할 때                          |
| 객체 저장소  | 영상·이미지처럼 큰 파일 보관                 | 결과를 외부에서 내려받거나 공유할 때                          |
| CDN          | 이미 만든 파일을 시청자에게 전달             | 시청량과 전송량이 커질 때. 영상 생성 속도를 높이지는 않음     |
| 클라우드 GPU | 원격 GPU를 빌려 계산                         | Mac에서 영상이 미지원이거나 대기 시간이 목표에 미달할 때      |
| CI/CD        | 코드를 검사하고 배포하는 절차                | 반복 배포를 안정적으로 관리할 때. 모델 답변 품질 평가는 별도  |

첫 구조는 로컬 웹·API, 프로젝트 전용 DB와 파일 저장소, Mac의 Qwen 워커로 구성한다. 이후 하이브리드가 필요하면 클라우드 API가 요청을 접수하고 Mac 워커가 인증된 연결로 작업을 가져오게 한다. 추론 서버 포트를 인터넷에 그대로 열지 않는다. Mac이 잠들거나 네트워크가 끊기면 작업이 대기 중임을 표시하고, 다시 연결했을 때 완료된 작업을 중복 저장하지 않아야 한다.

```text
로컬 기본: 로컬 화면 → 로컬 API·작업 저장 → Mac Qwen / 편집 워커
외부 제공: 웹·카카오 채널 → 클라우드 API·작업 상태 → Mac 워커 또는 영상 GPU
영상 전달: 승인한 결과 파일 → 비공개 객체 저장소 → 필요해지면 CDN → 사용자
```

과거 카카오 원문 분석은 로컬 흐름에 남긴다. 외부 모드에서 신규 메시지가 카카오나 클라우드 API를 지나면 그 메시지는 이미 기기 밖에서 처리되는 것이다. 모델만 Mac에서 실행한다고 모든 데이터가 로컬에 머무는 것은 아니다. 검토한 최소 페르소나 설정이나 생성 결과를 동기화할지는 사용자가 별도로 선택하게 한다.

영상 공유는 짧은 MP4와 비공개 저장소로 시작한다. 접근을 허용할 때만 만료가 있는 링크를 발급하고, 시청 규모가 커지면 CloudFront를 붙인다. CloudFront의 서명 URL·쿠키와 S3 원본 접근 제한을 이용해 파일 접근을 통제할 수 있다. HLS처럼 여러 조각으로 재생하는 형식은 긴 영상·다양한 네트워크 품질이 실제 문제가 될 때 추가한다. [CloudFront 비공개 콘텐츠](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-overview.html), [서명 URL과 쿠키 선택](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-choosing-signed-urls-cookies.html)

비용은 장비·전력·생성 재시도·저장·전송을 합산해 작업 한 건 기준으로 비교한다. 측정과 이용 규모가 없으므로 월 비용이나 동시 사용자 수는 아직 확정하지 않는다. 노트북을 24시간 서버로 쓰면 절전·회선·발열도 서비스 가용성에 영향을 준다.

**5. 저장소는 기존 모노레포를 사용하고 실행 환경을 분리한다**

Python을 쓰거나 모델 파일이 크다는 이유로 코드 저장소를 나눌 필요는 없다. [루트 package.json](/Users/gimjingeon/Desktop/safedoc/side-project/package.json), [저장소 README](/Users/gimjingeon/Desktop/safedoc/side-project/README.md)

웹·API는 기존 Node 24·Yarn 4.17.0 규칙을 따르고, Python 의존성은 워커 내부에서 별도로 고정한다. 모델 가중치, 실제 카카오 원문, 임베딩, DB 덤프, 생성 영상은 Git에 넣지 않는다. 레포에는 모델 이름·revision·양자화·실행 버전·라이선스와 합성 평가 데이터만 기록한다. 실제 여러 프로젝트가 쓰게 된 코드만 공통 패키지로 올린다.

같은 레포에 있다는 것은 같은 서버·DB에 실행한다는 뜻이 아니다. AI 프로젝트의 DB·환경변수·파일 저장소·추론 프로세스는 다른 서비스와 분리한다. 현재 공유 EC2 문서는 작은 2GiB 시작 구성을 설명하므로 그 서버에 무거운 추론이나 영상 렌더까지 얹는 계획으로 잡지 않는다. 또한 현재 `Services`의 변경 경로와 서비스 선택에는 기존 두 서비스가 명시되어 있어 새 폴더를 만들기만 해서는 CI가 자동으로 포함되지 않는다. [배포 구조](/Users/gimjingeon/Desktop/safedoc/side-project/deploy/shared-instance/README.md), [Services workflow](/Users/gimjingeon/Desktop/safedoc/side-project/.github/workflows/services.yml:10), [서비스 선택](/Users/gimjingeon/Desktop/safedoc/side-project/deploy/shared-instance/scripts/service-ci.ts:6)

외부 협업자에게 AI 코드만 공개해야 하거나, 별도 팀·접근권한·라이선스 관리가 필요해지면 별도 레포가 더 적합해진다. 현재 확인된 요구에는 그런 경계가 없어서 모노레포의 기존 도구와 운영 지식을 재사용하는 편이 낫다. GPU와 배포를 독립시키는 설계는 처음부터 유지한다.

**6. 구현은 다음 단계의 완료 조건을 확인하며 진행한다**

전체 기간은 아직 정하지 않는다. 장비에서의 생성 속도와 작업 가능 시간이 확인되지 않았기 때문이다. 먼저 작은 결과를 끝까지 만들고 다음 기능을 추가한다.

| 단계                | 만들 것                                                   | 다음 단계로 넘어갈 기준                                                                            |
| ------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1. 모델 실험        | 27B 4bit 실행, 필요 시 9B 비교                            | 같은 한국어 대화·소설 문제로 응답 시간·메모리·수정량 기록. 원하는 문체가 비용에 맞는지 선택        |
| 2. 텍스트 MVP       | 편집 가능한 가상 페르소나, 채팅, 소설 설정집·장면 생성    | 대화와 작품이 분리 저장되고 재시작·저장 실패 후 초안 보존. 모르는 사실을 임의 확정하지 않는지 확인 |
| 3. 카카오 파일 분석 | 파일 가져오기, 화자 확인, 관찰 프로필 검토·수정           | 화자 오인·중복 가져오기·잘못된 형식 처리. 원문과 연결된 검색 자료·프로필 삭제 확인                 |
| 4. 영상 MVP         | 장면 계획, 타임라인 편집, FFmpeg 내보내기, 짧은 생성 장면 | 편집 실패 후 초안과 완료 장면 보존. 생성 시간·일관성을 보고 Mac 또는 클라우드 GPU 선택             |
| 5. Cloud delivery   | 외부 웹·API, 작업 상태, 파일 공유                         | 워커 절전·재접속·중복 재시도·링크 만료·타인 파일 접근 차단 확인                                    |
| 6. 카카오 채널      | 공식 스킬 요청과 결과 확인 연결                           | 플랫폼 응답 시간, 콜백 중복·만료, 워커 오프라인 상황 처리. 원문 로컬 모드와 데이터 흐름 구분       |

동일한 합성 질문·장면으로 말투 유지·설정 오류·사적인 원문 재현·사용자 수정량을 비교한다. 모델 revision·양자화·프롬프트·문맥 길이도 함께 기록한다. 앱의 일반 테스트는 가짜 추론기로 권한·저장·취소·재시도를 검증하고, 실제 모델 평가는 별도로 실행한다.

저장소 규칙에 따라 API 테스트는 API 앱, 웹 테스트는 웹 앱, Python 테스트는 워커 안에 둔다. 기존 `Services`, `Blog`, `Static analysis` 체계를 유지하면서 AI 프로젝트 검증을 명시적으로 연결한다. 실제 모델을 실행하지 않은 CI 성공을 한국어 창작 품질이나 GPU 안정성의 검증으로 보고하지 않는다. [저장소 작업 규칙](/Users/gimjingeon/Desktop/safedoc/side-project/AGENTS.md)

Amplitude는 기존 `ui_interaction` 패턴으로 클릭을 기록하고, 가져오기 성공·페르소나 저장·생성 성공/실패는 실제 상태 변경 후 한 번만 기록하도록 새 앱 카탈로그에 설계한다. 허용 속성은 기능 종류·입력 경로·모델 버전·처리시간 구간·오류 코드 정도로 제한한다. 대화·프롬프트·소설 본문·추론한 성격·실명·파일명·서명 URL은 보내지 않는다. 로컬 기본 모드에서는 키 없이 전송을 생략하며, 클릭만 했을 때 성공 이벤트가 없는지와 재시도 중복·금지 데이터 전송 여부를 검증한다. [기존 이벤트 카탈로그](/Users/gimjingeon/Desktop/safedoc/side-project/projects/game-feedback/apps/web/src/shared/analytics/analytics.catalog.ts), [관측 규칙](/Users/gimjingeon/Desktop/safedoc/side-project/projects/game-feedback/docs/observability.md:83)

원문 파인튜닝, 장편·고해상도 영상, 여러 GPU 운영, Kubernetes는 미룬다. 첫 실험에서는 **이 Mac에서 원하는 한국어 답과 문체를 감당할 시간 안에 얻는지** 확인한다. 부족하면 작은 모델·프롬프트·검색·추가 계산 자원 중 실제 병목에 맞게 선택한다.

이 계획의 근거는 공식 모델·런타임·카카오 문서와 현재 저장소 구조 확인이다. 모델 다운로드·실행, 한국어 품질 측정, 카카오 계정 연동, 클라우드 배포는 아직 수행하지 않았다. 구현 코드 변경·커밋·push·PR도 이번 범위에 포함하지 않았다.
