# 클래시 로얄 AI 플레이 계획

**Qwen 파인튜닝을 중심으로 진행하되, 첫 목표는 RoyaleGym 시뮬레이터에서 상태를 보고 합법 행동을 고르는 에이전트로 정한다.** M5 Pro·통합 메모리 48GB에서 `Qwen3-4B-Instruct-2507`의 MLX 4bit 모델을 QLoRA로 학습하고, 규칙 봇·학습 전 Qwen·학습 후 Qwen을 같은 조건에서 비교한다. Qwen으로 게임 정책을 학습하는 실험은 가능하지만, 파인튜닝하면 강해진다거나 LLM이 최적의 실시간 정책이라는 결론은 아직 없다.

실제 클래시 로얄 클라이언트의 자동 플레이는 기술적 가능성과 허용 여부가 다르다. Supercell은 봇·게임플레이 자동화 스크립트를 금지하고 계정 영구정지 사유로 안내하며, 친선전 예외도 확인되지 않았다. 따라서 이 계획의 실행 대상은 **별도 시뮬레이터**이고, 실제 게임 영상은 이후 입력 없는 분석에 사용한다. 공식 게임 자동 조작은 명시적으로 허용된 환경이 확보되어야 별도로 검토한다. [Supercell 정책](https://supercell.com/en/safe-and-fair-play/)

**1. 사용할 모델과 도구를 고정한다**

| 역할             | 첫 선택                                   | 선택 이유와 한계                                                      |
| ---------------- | ----------------------------------------- | --------------------------------------------------------------------- |
| 전투 환경        | RoyaleGym                                 | 관측·합법 행동·시뮬레이션·기록·뷰어 재사용. 실제 게임과 동일하지 않음 |
| 행동 모델        | Qwen3-4B-Instruct-2507                    | 작은 텍스트·non-thinking 모델로 상태→행동 학습 범위를 제한            |
| 양자화 가중치    | mlx-community/Qwen3-4B-Instruct-2507-4bit | Apple Silicon용 MLX 경로 사용. 실제 학습 메모리·속도는 측정 필요      |
| 학습·어댑터 평가 | MLX-LM                                    | JSONL 지도학습, LoRA/QLoRA, 어댑터 저장·재로딩 재사용                 |
| 직접 개발        | Python 상태 변환기·정책 어댑터·평가 도구  | 시뮬레이터와 Qwen의 데이터·실행 규격 연결                             |

선택한 원본 Qwen 모델과 MLX 변환 모델은 Apache-2.0으로 표시된다. “Qwen이 오픈소스이므로 모든 모델이 같은 조건”으로 판단하지 않고 정확한 모델·revision·라이선스를 기록한다. 공개 가중치의 사용 허락은 게임 자산·영상 이용권이나 공식 게임 자동화 허락과 별개다. [원본 모델](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [MLX 변환 모델](https://huggingface.co/mlx-community/Qwen3-4B-Instruct-2507-4bit)

이번에는 최신·대형 모델보다 **학습 경로를 작게 검증할 수 있는 4B**를 먼저 쓴다. 앞선 창작 계획의 27B는 추론 후보였으며, 27B 4bit를 실행할 수 있다는 사실만으로 같은 모델의 학습 메모리·시간이 감당된다고 볼 수 없다. MLX-LM은 양자화 모델의 QLoRA와 Qwen3 구현을 제공하지만 이 Mac에서의 학습 성공은 아직 확인하지 않았다. [MLX-LM 학습 문서](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md), [Qwen3 구현](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/qwen3.py)

용어는 간단히 구분하면 된다. **SFT는 좋은 상태→행동 예시를 따라 배우는 목표**, **QLoRA는 양자화한 기본 모델을 유지하면서 작은 어댑터를 학습하는 방법**이다. 두 가지를 함께 사용한다. 보상으로 시행착오를 개선하는 강화학습은 이번 첫 실험 뒤에 판단한다.

RoyaleGym은 Python 3.12·Apple Silicon 설치 경로를 안내하지만, 내장 학습기의 Mac 경로는 CPU이며 Apple GPU를 사용하지 않는다고 명시한다. 이것은 외부 Qwen을 MLX로 학습하는 경로와 별개다. **시뮬레이터 실행, RoyaleGym 내장 RL 학습, Qwen QLoRA 학습을 서로 다른 작업으로 측정**한다. [RoyaleGym 설치](https://royalegym.github.io/RoyaleGym/install/)

**2. 화면 대신 관측 가능한 상태를 입력한다**

```text
RoyaleGym의 플레이어 관측
→ 상태 JSON·합법 후보 변환
→ Qwen의 짧은 행동 JSON
→ 형식·합법성·시점 검사
→ 시뮬레이터 적용
→ 다음 관측·승패·지연 기록
```

첫 범위는 엔진이 지원하는 기본 카드로 구성한 **고정 덱 하나, 고정 레벨, 제한된 배치 후보**다. 어떤 덱을 쓸지는 설치 검증에서 카드 지원을 확인한 뒤 고정한다. 화면 인식·OCR·휴대폰 제어·여러 덱 일반화는 첫 완료 조건에 넣지 않는다.

입력에는 내 손패 슬롯, 내 엘릭서, 남은 시간, 보이는 양 팀 유닛·위치, 타워 상태, 지금까지 공개된 행동, 현재 합법 후보를 넣는다. 상대의 정확한 손패·숨은 엘릭서·미래 상태는 제외한다. 추정치를 추가한다면 관측 사실과 분리한다. 시뮬레이터 내부에 정답이 있다고 모두 넣으면 실제 플레이어보다 많은 정보를 본 모델을 학습하게 된다.

RoyaleGym은 player view, action mask, 행동 parser 확장점을 제공한다. 이를 그대로 긴 텍스트로 펼치기보다 다음처럼 작은 **자체 계약**으로 변환한다. 아래 이름은 RoyaleGym의 기본 API 규격이 아니라 구현할 제안이다. [관측 builder](https://royalegym.github.io/RoyaleGym/clash-royale/configuration-objects/observation-builders/), [행동 parser](https://royalegym.github.io/RoyaleGym/clash-royale/configuration-objects/action-parsers/)

| 계약               | 포함할 내용                                                      |
| ------------------ | ---------------------------------------------------------------- |
| `observation`      | `schema_version`, 관측 시각, 손패·엘릭서·타이머·유닛·타워        |
| `legal_candidates` | `wait`와 현재 허용된 카드 슬롯·타일 조합의 짧은 ID               |
| `action`           | 예: `{"action_id":"play_2_tile_18"}` 또는 `{"action_id":"wait"}` |
| `transition`       | 관측·원본 출력·검사 결과·실행 행동·다음 관측·경기 식별자         |

소수 배치 지점과 `wait`를 짧은 ID 메뉴로 주고 코드가 원래 좌표로 매핑한다. 동일 제한을 규칙 봇·기본 Qwen·학습 Qwen에 적용한다. 출력의 카드·엘릭서·배치 조건을 다시 검사하며 실패·오래된 관측이면 대기한다. 후보 제한으로 놓치는 전략은 후속 확장의 한계로 기록한다.

게임 제어 출력은 짧은 JSON만 사용한다. **한국어 설명은 경기 후 복기 또는 별도 요청으로 생성**하여 행동 결정의 지연에 더하지 않는다. 첫 Qwen은 텍스트 상태를 읽는 정책 모델이며 화면을 인식하는 모델이 아니다.

**3. 학습 전 기준선과 데이터부터 만든다**

무작위 합법 행동과 대기만 하는 봇으로 연결을 점검한 다음, 단순 방어·공격 규칙 봇과 학습 전 Qwen을 기록한다. 규칙 봇은 전문가가 아니라 최소 비교 기준이다. 동일 관측·행동 후보·상대·seed를 사용해야 파인튜닝으로 무엇이 달라졌는지 판단할 수 있다.

데이터는 관측 시점의 상태와 그때 선택한 행동의 짝으로 만든다. 초기에는 사람이 검토한 소량의 예제로 변환기를 검증하고, 수백~수천 판단 장면으로 첫 학습을 탐색한다. 이 수량은 작업 규모 제안이며 강한 에이전트에 충분하다는 근거가 아니다. 규칙 봇·합성 교사 출력은 형식과 기본 동작을 배우는 재료로 사용하고, 좋은 플레이의 정답으로 자동 취급하지 않는다. 승리한 경기에도 나쁜 행동이 있을 수 있다.

RoyaleImitate의 시범 기록·재구성 기능을 참고하되 **Qwen chat JSONL 변환기는 직접 작성**한다. 기존 artifact를 MLX에 그대로 넣는 호환은 전제하지 않는다. 시뮬레이터로 재구성한 상태와 실제 녹화 화면은 서로 다른 자료라는 점도 기록한다. [RoyaleGym 모방학습](https://royalegym.github.io/RoyaleGym/clash-royale/cloning-a-bot/)

학습·검증·최종 평가를 **경기 단위**로 분리한다. 인접 상태가 양쪽에 새지 않게 하고 teacher도 숨은 상대 정보·미래 결과를 보지 못하게 한다. 대기만 출력해 정답률을 높이지 않도록 공격·수비·대기의 분포와 학습 가중치를 확인한다. 테스트 데이터는 평가할 경기의 분포를 유지한다.

첫 평가는 고정 덱 안에서 다른 경기·seed·상대로 진행한다. 이를 통과하면 학습에 없던 상대 전략과 지원되는 다른 덱을 별도 평가한다. 처음부터 모든 덱·새 카드·실게임에 일반화했다고 보고하지 않는다.

**4. 작은 QLoRA 학습과 재로딩을 검증한다**

MLX-LM의 chat JSONL에 상태·후보를 입력, 행동 JSON을 assistant 정답으로 넣는다. `--mask-prompt`로 정답 출력 부분만 학습하는 경로를 사용하고, 실제 chat template에서 입력·정답 경계가 의도대로 처리되는지 샘플을 검사한다. 원본 모델과 tokenizer revision, 데이터 manifest, seed, 프롬프트·스키마 버전을 함께 고정한다. [MLX-LM 데이터와 학습 옵션](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)

첫 메모리 시험은 **배치 1, 문맥 1K–2K, rank 8, 마지막 4–8개 레이어**를 출발 후보로 둔다. 이는 측정된 최적값이 아니다. 입력이 잘리지 않는지 확인하고, 메모리 압박·swap·step 시간을 보고 문맥·레이어·배치를 조정한다. 필요하면 gradient checkpointing을 사용한다. 48GB 전체를 학습에 쓸 수 있다고 가정하지 않는다.

먼저 소량 데이터로 학습→어댑터 저장→프로세스 종료→재로딩→별도 검증 문제의 추론까지 끝낸다. 이 과정이 통과해야 긴 학습으로 확대한다. 학습 손실 감소만으로 게임 실력 향상을 선언하지 않는다. 첫 추론도 MLX-LM 안에서 유지하고, MLX 어댑터를 Ollama에 그대로 넣는 것은 지원된다고 가정하지 않는다.

**5. 성능은 합법성·승패·시간을 따로 비교한다**

| 지표             | 기록 방법과 의미                                                               |
| ---------------- | ------------------------------------------------------------------------------ |
| 원본 JSON 성공률 | 보정 전 출력이 바로 파싱되는 비율                                              |
| 원본 불법 행동률 | guard 적용 전 불가능한 행동을 고른 비율                                        |
| guard 결과       | 차단률·대기 대체율과 적용 후 불법 행동 여부. 보정이 모델 오류를 숨기지 않게 함 |
| 경기 성적        | 상대별 승·패·무, 경기 수와 95% 신뢰구간. 덱·레벨·엔진 버전 명시                |
| 결정 시간        | 상태 변환부터 행동 검사까지 p50/p95, 정한 deadline 초과율                      |
| 실행 비용        | 최대 메모리·swap·학습 step 시간·경기 처리량                                    |
| 전략 진단        | 카드 사용·엘릭서 낭비·타워 피해. 대기 편향이나 잘못된 보상 최적화 확인         |

먼저 소수 경기로 기능을 점검하고, 최종 비교의 경기 수는 측정한 처리량과 허용 시간을 보고 정한다. 예를 들어 상대별 100–300경기는 계획 후보일 뿐 검증 결과가 아니다. 규칙 봇·기본 Qwen·학습 Qwen에 같은 평가 조건을 적용하고, 승률 차이가 불확실하면 그대로 보고한다. 필요하면 작은 비언어 정책망도 같은 데이터로 비교하여 Qwen의 추가 비용이 실제 이득으로 이어지는지 판단한다.

**모델이 생각하는 동안 멈춘 시뮬레이터에서 이기는 것과 실시간으로 플레이하는 것은 다르다.** 초기에는 멈춤 방식으로 정책 품질을 비교해도 되지만, 다음 검증에서는 모델 처리 시간 동안 전투와 상대 행동을 진행시켜 지연·오래된 관측의 영향을 반영한다. RoyaleGym 예제의 500ms 간격은 출발 예제이며 M5의 성능이나 공식 게임 요구치가 아니다. 결정 예산은 실측 후 고정하고, 두 평가 방식의 결과를 섞지 않는다. [RoyaleGym quickstart](https://royalegym.github.io/RoyaleGym/quickstart/)

확대 조건은 “학습 완료”가 아니라, 보지 않은 경기에서 형식·합법성과 경기 성적이 기준선보다 나아지고 지연이 사용 목적에 맞는지다. 형식만 개선되면 데이터 품질·교사·후보 생성부터 바꾼다. 실력은 개선되지만 지연이 크면 작은 정책으로의 증류나 Qwen의 복기 역할 분리를 검토한다. 처음부터 LLM에 PPO·GRPO를 붙이지 않는다.

**6. 구현 순서와 저장소 범위**

| 단계           | 산출물                                     | 완료 조건                                                        |
| -------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| 1. 환경 검증   | 버전 고정 RoyaleGym·MLX 환경, 고정 덱 설정 | 짧은 경기가 정상 종료되고 관측·행동·seed 재현 확인               |
| 2. 기준선      | 규칙 봇·기본 Qwen adapter와 평가 로그      | 동일 관측 계약, 원본 불법 행동률·승패·지연 기록                  |
| 3. 데이터      | 검토된 상태→행동 JSONL·manifest            | 경기 단위 분리, 숨은 정보 누수·대기 분포·정답 형식 검사          |
| 4. QLoRA       | 작은 학습 어댑터·설정·체크포인트           | 저장·재로딩과 분리된 검증 데이터 추론 성공, 메모리·시간 기록     |
| 5. 비교 평가   | 학습 전후 표·경기 로그·판정                | guard 전후, 상대별 승률·신뢰구간, 멈춤/시간 진행 평가 분리       |
| 6. 선택적 영상 | 저장 영상→관측 추정·한국어 복기            | 사람 라벨과 상태 인식 비교. 실제 클라이언트 입력은 연결하지 않음 |

오픈소스는 **RoyaleGym 한 개부터 도입**한다. ClashRoyaleBuildABot은 화면 상태·규칙 기반 구조의 참고이며 README도 실제 Supercell 게임 사용을 금지한다고 안내한다. [RoyaleGym](https://github.com/RoyaleGym/RoyaleGym), [BuildABot](https://github.com/Pbatch/ClashRoyaleBuildABot), [KataCR](https://github.com/wty-yy/KataCR)

기존 모노레포에 창작 프로젝트와 별도인 **`projects/royale-lab`**을 둔다. `apps/agent`가 Python 의존성·상태 변환·학습·평가와 테스트를 소유하고, unit 테스트는 구현 옆에 둔다. 프로젝트에는 프롬프트·평가 설정·도구 버전·데이터 manifest·실험 기록만 남긴다. upstream 전체 소스, 모델 가중치, 원본 영상, 게임 자산, 큰 데이터셋은 Git에 넣지 않는다. 처음에는 upstream 뷰어와 로컬 로그를 쓰며 새 웹·DB·클라우드·CDN을 만들지 않는다.
