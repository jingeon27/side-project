# 카드 스펙, 라벨링과 지속 자가개선 계획

2026-11-20 대화에서 정한 방향을 기록한다. 학습과 평가의 대상은 **실제 클래시로얄 트로피 경기**이고, Counterpush는 이 계획에서 쓰지 않는다. 목표는 세 가지다.

1. **모든 카드의 스펙을 한 곳에서 확인할 수 있게 한다.** 수치, 형태, 만드는 오브젝트, 화면에서 보이는 모습, 검증 상태를 카드마다 정리한다.
2. **모든 카드를 라벨링한다.** 화면 인식이 모든 카드의 오브젝트, 효과, 손패 그림을 읽도록 정답을 만들고 오류를 잰다.
3. **자가개선을 계속 돌린다.** 실전 기록, 라벨링 대기열, 인식 재학습, 시뮬레이터 보정, 자가대국, 실전 평가가 사람이 지켜보지 않아도 이어지게 한다.

하지 않는 것: 사람이 행동 정답(좋은 수)을 라벨링하는 일. 좋은 수는 자가대국과 탐색이 만들고, 사람은 화면에 무엇이 있는지만 정한다.

## 2026-11-21 구현과 측정

고정표 145행 중 엔진이 지원하는 143장의 형태·수치·생성 관계와 별도 참조용 2행을 기록한다. `arena verify`는 143장의 양 진영 배치와 기사 어그로를 검사한다. 진화 44종의 주기 충전·사용, 히어로 18종과 액티브 챔피언 8종의 스킬 실행도 검증한다. 나머지 챔피언 등급 이벤트 카드 1종은 일반 배치와 스킬 미보유를 확인한다. `arena coverage`로 실전 기준 12개 덱, 기본 연습 덱 21개와 추가 형태 덱 20개에서 실제 배치·스킬·수읽기·최적화 참여를 확인한다. 기본 수치 재현과 특정 상호작용 검사의 범위는 각각 표시한다.

트로피전 원본 화면을 경기 단위로 나눠 저장하고 라벨 수정 이력을 유지한다. 감독이 완료된 경기의 자료를 수집하고 사람의 새 커버리지 라벨이 20장 쌓이면 인식을 재학습한다. 측정용 대기열은 인식 결과를 숨긴다. 기본 하루 배정은 측정 10장과 커버리지 10장이다. 독립 확인과 이틀 뒤 재판독도 제공한다. `perception-eval`은 측정 화면마다 검출기를 다시 실행하고 손패 후보 모델, 다음 카드와 엘릭서 판독을 비교한다. `status.json`의 파일럿 건수와 사람이 확인한 건수를 구분한다. 사람의 충분한 실전 표본, 카드별 실전 대조, 세 챔피언의 순위 비교, 일주일 운전 확인은 후속 측정이다. 명령과 어댑터 연결은 [프로젝트 README](../README.md)에 있다.

## 계획 작성 시점의 상태

- **실전 연결:** 트로피 경기는 맥에서 돌리는 실제 클래시로얄 화면을 368×652로 정규화해 읽는다. 화면 입력과 손패·엘릭서 인식은 저장소 밖 어댑터가 맡는다. 타워 체력은 `perception/macos/tower-text.swift`가 내 공주 타워 숫자만 읽는다.
- **트로피 기록:** `trajectory.json`은 판단 시점의 화면 파일 이름과 SHA-256, 일부 상태 특징만 남긴다. 프레임별 인식 원본 출력은 남지 않는다.
- **학습 경로:** 트로피 자기 행동 PPO와 16쌍/32판 실전 게이트(`contracts/trophy-learning.json`, `qualification.json`)가 있다. 자가대국은 RoyaleSim 0.1.53에서 돈다. 덱 풀은 12개 덱, 카드 61종이다. 자가개선 감독(`loop`)이 자가대국을 유지하고 새 시뮬레이터 챔피언을 트로피 실전 게이트에 넘긴다(8단계).
- **카드 정보:** `contracts/card-catalogue.json`에는 카드 143장과 필드 오브젝트 232종이 있다. 엔진 표(`cards-160635007-20261103.1`)에서 만든 정규화 특징만 있다. 다음 정보는 없다.
  - 원래 수치
  - 진화·히어로·챔피언 형태
  - 카드와 오브젝트의 연결
  - 화면 모습
  - 검증 상태

  `src/core/knowledge.ts`의 레벨 11 수치와 출처는 현재 덱 일부만 다룬다.

- **인식:** 검출기와 그림 분류기는 외부에서 받은 고정 버전이다. 이 프로젝트에서 학습한 인식 모델은 없다. 정답은 테스트 이미지 몇 장뿐이고, 정밀도·재현율이나 위치 오차를 재는 코드가 없다.
- **시뮬레이터:** 화면 오류율(`contracts/arena.json`의 `selfplay.perception`)은 가정값이다. 없는 유닛을 본 오탐과 다른 카드로 읽은 오류는 흉내 내지 않는다. `arena verify`는 엔진 안의 재현만 검사하고 `realClientParityVerified`는 `false`다. RoyaleSim의 수치표는 실제 클라이언트 버전을 기준으로 하므로, Counterpush보다 실제 클래시로얄과 맞추는 쪽이 대상이 일치한다.

## 0. Counterpush 정리 (완료, 2026-11-20)

코드 제거와 문서 정리를 마쳤다. 트로피 경로는 원래 Qwen을 쓰지 않았다.

- **지웠다:** `src/counterpush/**`(브라우저 조작, TS 손패·엘릭서·영웅 버튼 인식, 경기 기록기, Qwen 후보 학습 반복, 실전 비교), `src/qwen/**`, `src/arena/study.ts`, Python `clash_bot/qwen/**`(`action_prior`와 그 검사 제외), `clash_bot/arena/study/**`(Qwen 교사·내보내기), arena의 `export`·`curriculum`·`study` 명령과 세대마다 만들던 Qwen 자료, `contracts/model.json`, 손패 그림 참조(`assets/counterpush/hand-templates`)와 `ice-wizard-ability.png`, 대부분의 `test-fixtures/counterpush` 그림, Playwright 의존성, `counterpush`·`qwen:setup`·`test:integration`·`test:learning`·`test:learning:model` 명령. Qwen 모델과 LoRA 학습은 모두 없어졌다.
- **바꿨다:** 실행 환경은 `runtime:setup`이 `runtime.lock`(`core.lock`과 MLX·OpenCV·Pillow)으로 `.data/python/.venv`에 만든다. 예전 `.data/qwen/.venv`는 읽지 않으므로 이미 쓰던 컴퓨터는 한 번 실행해야 한다. `counterpush:setup`은 같은 모듈의 `perception:setup`으로 이름을 바꿨다. TS 이름은 `LIVE_DECK`, `LIVE_DECK_EVOLUTIONS`, `ActionOption`으로 바꿨다.
- **남겼다:** 공통 전투 규칙, 빠른 정책, 채택 검정(`qualification.json`), decision-v3 직렬화. Git 밖 화면 어댑터가 이름으로 실행하는 `clash_bot.qwen.action_prior`와 Python 인식 모듈(`vision_worker`, `trophy_vision`, `build_atlas`, `effects`, `setup`), 이들이 읽는 `assets/counterpush/*`, `.data/counterpush/detector`, `profiles/counterpush.json`(core 배치 검사도 읽는다). `contracts/arena.json`의 `liveDeck: "counterpush"`와 `combat-projection.json`의 `counterpushCalibrated`는 바꾸면 `rulesID`가 바뀌어 새 리그가 시작되므로 그대로 두었다.
- **옮기지 않았다:** 프레임과 인식 결과를 남기던 기록기(`src/counterpush/match/recorder.ts`)는 Counterpush 경기 루프에 묶여 있어 함께 지웠다. 트로피 기록은 3단계에서 새로 만든다.

후속 작업은 두 가지다.

1. 계약 키와 자산·데이터 경로의 `counterpush` 이름을 바꾼다. Git 밖 어댑터가 읽는 경로를 확인한 뒤 진행하고, 키 변경은 새 리그를 시작하므로 다른 `rulesID` 변경과 묶는다.
2. 인식 자산(스프라이트·배지·표식·아틀라스)은 Counterpush 화면에서 만든 것이다. 실제 클래시로얄 화면용으로 다시 만드는 일은 4~6단계에서 한다.

## 1. 모든 카드의 스펙

카드 스펙은 두 파일로 나눈다. 수치는 사람이 고치지 않는다.

**엔진 스펙(생성):** `arena catalogue`가 고정 엔진 표에서 카탈로그와 함께 만든다. 카드마다 다음을 담는다.

- 이름과 엔진 이름, 엘릭서, 종류(유닛·건물·주문), 배치 유형
- 형태별 수치: 일반, 진화, 히어로, 챔피언 중 있는 것. 체력, 피해, 공격 주기, 사거리, 이동 속도, 배치 시간, 대상(공중·지상·건물), 소환 수, 지속 시간, 범위
- 만드는 오브젝트 목록(오브젝트 232종의 ID), 사망·주기 생성 규칙
- 기준 레벨과 엔진 표 버전

**화면 스펙(사람이 관리):** 라벨링과 인식에 필요한 내용만 적는다.

- 라벨링할 오브젝트와 효과의 모양(예: 독 원, 무덤 영역, 통이 굴러가는 띠)
- 헷갈리는 묶음(비슷한 회색 손패, 같은 해골을 만드는 카드들)
- 확인한 참조 그림의 경로와 SHA-256

**검증 상태(자동 집계):** 카드마다 상태를 하나의 보고로 모은다.

- 엔진 재현 검사 통과 여부(`arena verify`의 카드별 결과)
- 실전 화면 대조 결과(7단계)
- 라벨 수(진영별)와 인식 정확도(5단계)

`card-status` 명령이 카드별로 이 세 가지를 출력한다. 검사로 다음을 확인한다.

- 카탈로그의 모든 카드에 엔진 스펙과 화면 스펙이 있다
- 모든 오브젝트가 어떤 카드의 생성 목록에 속한다
- 엔진 스펙이 고정 표와 해시로 일치한다

밸런스 패치로 표가 바뀌면 다시 생성한다. 바뀐 카드 목록은 재검증과 재라벨링 대상으로 넘긴다. 새 표는 지금처럼 자동 설치하지 않는다.

## 2. 라벨 형식

라벨 클래스는 카드가 아니라 **화면에 보이는 대상**이다. 해골은 해골, 해골 군대, 무덤, 마녀가 함께 만들기 때문이다.

- **필드 오브젝트:** 1단계 오브젝트 ID, 진영, 발 위치 한 점, 형태(일반·진화·히어로), 보이면 체력 구간(가득·절반 이상·절반 미만)
- **효과:** 주문 영역과 투사체의 종류, 진영, 중심점
- **손패:** 네 칸의 카드 ID와 상태(일반·진화·비활성), 다음 카드
- **엘릭서:** 0~10 정수
- **타워 체력:** 화면의 숫자

한 프레임에 보이는 것만 적고, 판단할 수 없으면 `unsure`로 남긴다. 경기 단위 라벨에는 상대가 카드를 낸 시점, 카드, 위치를 기록한다. 이 기록은 상대 플레이 미인식률과 7단계의 시뮬레이터 대조에 쓴다.

라벨은 프레임 SHA-256으로 원본과 연결해 `.data/trophy/labels/`에 둔다. 회귀 검사용으로 고른 20장 이내만 `test-fixtures`로 옮겨 커밋한다.

## 3. 실전 기록 보강

트로피 경기도 지운 Counterpush 기록기처럼 **모든 프레임과 프레임별 인식 결과**를 남긴다. 그래야 라벨과 비교하고 나중에 인식을 다시 돌릴 수 있다.

- 어댑터가 저장소 밖에 있으므로 프레임 저장과 인식 결과 기록을 저장소 쪽으로 옮길지, 어댑터에 추가할지 먼저 정한다.
- 인식 모델의 해시를 실험 지문에 넣는다. 지금 `src/trophy/fingerprint.ts`는 코드만 해시한다. 인식 가중치만 바뀌면 다른 인식으로 모은 자료가 한 실험에 섞인다.

## 4. 모든 카드의 화면 자료 모으기

내 경기만으로는 드문 카드가 거의 나오지 않는다. 출처를 섞는다.

| 출처                           | 장점                                           | 한계                                              |
| ------------------------------ | ---------------------------------------------- | ------------------------------------------------- |
| 내 트로피 경기                 | 실제 분포, 그대로 측정용                       | 드문 카드가 적음                                  |
| 게임 안 리플레이(전투 기록 등) | 다양한 카드와 양쪽 진영, 입력 없이 화면만 기록 | 리플레이 화면 요소가 다를 수 있음                 |
| 친선전·훈련 세션               | 낸 카드를 알고 있어 클래스 정답이 저절로 생김  | 해금한 카드만 가능, 두 번째 계정이 필요할 수 있음 |
| 공개 라벨 데이터셋             | 많은 카드를 빠르게 확보                        | 라이선스, 게임 버전, 클래스 체계를 확인해야 함    |

친선전·훈련 세션에서는 카드를 정해 양쪽 진영과 여러 위치에 내고, 추적기가 그 유닛을 따라가며 라벨 후보를 만든다. 사람은 확인만 한다.

**목표량**

- **측정 세트:** 내 트로피 경기에서 실제 분포대로 뽑고, 인식 결과를 보지 않고 라벨링한다. 오브젝트 약 1,000개, 손패 칸 약 600개, 엘릭서 값별 10장 이상이다. 누락률이 8% 근처일 때 1,000개면 95% 구간이 약 ±1.7%p다.
- **커버리지 세트:** 오브젝트 232종마다 확인된 표본 30개 이상, 진영별 10개 이상을 둔다. 인식 결과를 띄워 두고 고치는 방식으로 빠르게 단다. 클래스별 정확도와 재학습에 쓴다.
- 측정 세트와 커버리지 세트는 경기 단위로 나누고 섞지 않는다.
- 처음 20장의 실제 소요 시간을 재고 목표량을 다시 정한다. 며칠 뒤 15장을 다시 라벨링해 내 라벨의 일치도를 기록한다.

## 5. 도구

- `trophy label`: 라벨링 화면이다. 점 찍기, 오브젝트·카드 선택, 손패·엘릭서·타워 입력, `unsure`, 경기 단위 상대 플레이 기록을 지원한다. 브라우저 코드도 TypeScript로 쓴다.
- `trophy perception-eval`: 라벨이 있는 프레임에 **현재 코드와 가중치의 인식을 다시 실행**해 비교한다. 결과는 인식 해시별로 `.data/trophy/perception-eval/`에 남긴다. 픽셀과 타일의 변환은 인식이 쓰는 함수를 그대로 쓴다.
- `card-status`: 1단계의 카드별 스펙, 검증, 라벨 수, 정확도를 출력한다.
- **라벨 대기열:** 실전 경기가 끝날 때마다 사람이 볼 프레임을 골라 쌓는다. 우선순위는 다음 순서다. 하루 상한을 둔다.
  1. 아직 라벨이 없는 오브젝트
  2. 분류 확신이 낮은 대상
  3. 이웃 프레임에서 종류가 바뀐 대상
  4. 엘릭서 지출과 맞지 않는 엘릭서 값

측정 항목은 시뮬레이터 설정과 하나씩 맞춘다.

| 측정                                              | 시뮬레이터 값                 |
| ------------------------------------------------- | ----------------------------- |
| 라벨 오브젝트 중 같은 진영 인식이 1타일 안에 없음 | `missRate`                    |
| 짝지은 오브젝트를 모름으로 냄                     | `unknownRate`                 |
| 짝지은 오브젝트를 다른 종류로 냄, 혼동 쌍         | 추가 후보                     |
| 짝 없는 인식(오탐)                                | 추가 후보                     |
| 축별 위치 오차 분포                               | `jitterTiles`                 |
| 체력 막대가 보이는 대상의 체력 출력률과 구간 일치 | `healthSeenRate`              |
| 효과 누락과 오탐                                  | `effectMissRate`              |
| 경기 라벨의 상대 플레이 중 미인식                 | `playMissRate`                |
| 손패 칸, 엘릭서 값별 정확도                       | 실전 입력 오류(시뮬레이터 밖) |

## 6. 인식 개선

`perception-eval`과 `card-status`에서 판단에 영향이 큰 순서로 고친다.

1. 손패와 다음 카드: 실제 클래시로얄의 모든 카드 그림을 일반·진화·비활성 상태별로 확보한다
2. 엘릭서
3. 상대 플레이 미인식
4. 오브젝트 종류·누락·오탐
5. 효과와 체력

방법은 다음 순서로 시도한다.

1. 커버리지 세트로 분류기의 선형 머리를 다시 학습한다. 분류기가 384차원 특징을 함께 내므로 가볍게 할 수 있다.
2. 재현율이 문제면 검출기를 미세 조정한다.

새 인식은 측정 세트 전체가 나아지고, 정해 둔 폭 이상 나빠진 클래스가 없을 때만 채택한다.

## 7. 시뮬레이터 보정

- **화면 오류:** 인식을 채택한 뒤 측정 세트의 값으로 `selfplay.perception`을 바꾼다. 오탐과 종류 혼동이 의미 있는 수준이면 `noise.py`에 더한다. 이 값은 `rulesID`에 들어가 새 리그가 시작되므로 묶어서 바꾼다. 바꾼 값과 측정 파일을 `arena-learning.md`에 기록한다.
- **카드 범위:** 카드마다 `arena verify` 검사를 늘리고, 통과한 카드부터 덱 풀에 넣는다. 상대 덱은 실전에서 관측한 카드 분포를 따라 뽑아, 자가대국 상대가 실제 트로피 구간과 비슷해지게 한다.
- **실전 대조:** 경기 라벨을 단 경기를 RoyaleSim에서 같은 순서로 다시 실행한다. 공개된 사실만 확인 시점마다 비교한다: 유닛 위치, 사라진 시점, 내 공주 타워 체력. 결과는 카드별 차이 표로 남기고 1단계의 검증 상태에 반영한다.

## 8. 지속 자가개선 루프 (일부 구현, 2026-11-20)

하나의 감독 프로세스가 아래 작업을 돌린다. 지금의 실행 잠금, 상태 파일, 중단 후 재개 방식을 그대로 쓴다.

**지금 돌아가는 것:** `yarn workspace @side/clash-bot loop start [--background] [--keep-awake] | status | stop`(`src/loop/*`, `contracts/self-improvement.json`).

- 60초마다 점검한다. 자가대국(`arena start --hours 0 --games 4 --practice-games 56 --workers 4 --simulations 16 --depth 8 --pairs 32 --evaluate-every 4`)을 nice 10으로 유지하고, 자신이 시작한 실행이 실패하면 60·300·1800초 뒤 다시 시작한다. 6시간 안에 3번 실패하면 멈추고 마지막 오류를 남긴다. 자신이 시작한 실행이 정상 정지하면 사용자의 정지로 보고 다음 `loop start`까지 기다린다. 자신이 시작하지 않은 자가대국은 멈추지 않는다.
- 리그 챔피언(버전 0 초과)이 바뀌면 정책을 `.data/loop/simulation-champions/<sha>.json`으로 복사하고 트로피 인계 파일(`.data/trophy/learning/control/simulation-candidate.json`)을 쓴다. 트로피는 평가가 없고 학습 묶음이 빌 때 이를 가져와 기존 16쌍 실전 게이트로 비교한다. 통과하면 트로피 챔피언이 되고 PPO가 그 위에서 이어 학습하며, 탈락하면 학습 중이던 PPO 후보로 돌아간다.
- 24시간마다 `arena rules`를 실행해 엔진 갱신 여부와 오류를 사건으로 남긴다. 새 표는 자동으로 켜지 않는다. 바뀐 카드 목록은 사람이 `arena rules --stage-version`으로 준비할 때 만들어진다.
- 24시간마다 `.data/loop/reports/YYYY-MM-DD-HHmm.json`에 자가대국·트로피 상태, 감독 상태, 사건과 아직 자동화하지 않은 작업 목록(`notYetAutomated`)을 남긴다. 사건은 `.data/loop/events.jsonl`에 쌓인다.
- 감독은 실전 트로피 경기를 시작하지 않는다. 실전은 Git 밖 ADB 화면 어댑터가 `trophy serve`로 둔다.

**최초 계획의 대기 항목(2026-11-20):** 아래 표의 실전 기록과 대기열(3·5단계), 인식 재학습(6단계), 측정값 기반 시뮬레이터 오류율(7단계), 시뮬레이터와 실전 순위 확인. 보고서의 `notYetAutomated`가 이 네 가지(`real_screen_label_queue`, `perception_retraining`, `measured_simulator_perception_noise`, `simulator_and_real_ranking_check`)를 적는다. 매일 보고는 경기 수와 채택 결과를 담지만 라벨 대기열 크기, 카드별 커버리지, 순위 일치 여부는 아직 없다.

| 작업                   | 언제                             | 통과 조건과 되돌림                                                 |
| ---------------------- | -------------------------------- | ------------------------------------------------------------------ |
| 자가대국 학습          | 항상                             | 시뮬레이터 평가 게이트를 넘은 후보만 다음 단계로                   |
| 실전 평가              | 시뮬레이터 후보가 생기면         | 트로피 16쌍/32판 게이트. 떨어지면 챔피언 유지                      |
| 실전 기록과 대기열     | 실전 경기마다                    | 프레임·인식 결과 저장, 라벨 대기열 갱신                            |
| 인식 재학습            | 새 라벨이 정해 둔 수 이상 쌓이면 | 측정 세트 기준 채택. 나빠지면 이전 가중치 유지                     |
| 시뮬레이터 오류율 갱신 | 인식 채택 뒤 묶어서              | 새 리그 시작. 기존 챔피언 가중치는 초기값으로만 이음               |
| 패치 감시              | 매일                             | 표가 바뀌면 알림과 바뀐 카드 목록. 새 표 활성화는 사람이 확인한 뒤 |

- **사람이 하는 일:** 하루 정해 둔 시간만큼 라벨 대기열을 처리하고, 패치 활성화를 확인한다. 채택은 게이트가 자동으로 정한다.
- **매일 보고:** 경기 수, 채택과 탈락, 라벨 대기열 크기, 카드별 커버리지, 시뮬레이터 순위와 실전 순위의 일치 여부를 남긴다.
- **시뮬레이터 순위 확인:** 챔피언 버전 3개 이상의 시뮬레이터 순위와 실전 순위를 주기적으로 비교한다. 어긋나면 7단계의 실전 대조로 돌아가고, 그동안 자가대국 규모를 늘리지 않는다.
- **반복 검정:** 같은 후보를 여러 번 평가하면 우연히 통과할 수 있다. 지금의 유의수준 지출(`qualification.json`)을 계속 적용한다.

## 위험
