# Blog writer

`projects/blog`의 MDX 글을 작성하거나 고친다. 짧은 문장 수정은 해당 부분부터 처리하고, 새 글이나 큰 개정에만 필요한 근거를 넓혀 읽는다.

## 먼저 읽을 자료

- [프로젝트 지침](../../../AGENTS.md)과 대상 글의 현재 본문, 메타데이터, 언어별 SEO를 읽는다.
- 개인 스킬 `~/.agents/skills/blog-writing/SKILL.md`가 있으면 읽고 그 문체 피드백을 적용한다. 사용자가 새로 주는 수정 방향이 기존 예시보다 우선한다. 개인 스킬이 없는 환경에서도 현재 프로젝트 지침과 요청에 따라 글을 편집할 수 있다.
- 이관 글의 코드나 원본 자료를 바꿔야 할 때는 [이관 안내](../../../docs/migration.md)를 확인한다. 가져오기 스크립트로 편집본을 덮어쓰지 않는다.

## 독자가 얻을 것부터 정하기

새 글이나 큰 개정에서는 [독자 목적별 편집 기준](references/reader-needs.md)을 읽고, 대상 독자가 이미 아는 것과 지금 필요한 것, 글의 핵심 질문, 읽은 뒤 할 수 있거나 이해할 것을 짧게 정한다. 이 판단은 편집에 사용하고 본문에 기획 메모나 분류표를 삽입하지 않는다. 짧은 문장 교정에는 글 전체를 재분류하거나 재구성하지 않는다.

튜토리얼, 문제 해결 안내, 참조, 설명 가운데 중심 역할을 고른다. 기술명이나 독자의 경력만으로 유형을 정하지 않는다. 같은 Sentry 주제도 첫 실습, 특정 오류 해결, 설정 조회, 선택 이유 이해에 따라 필요한 글이 달라진다. 개발 경험담과 회고는 독자가 판단의 맥락을 이해하도록 설명의 기준을 활용하되, 경험을 매뉴얼로 바꾸거나 개인적인 회고를 억지로 분류하지 않는다.

네 유형을 모두 채우거나 사이트 분류와 메타데이터를 늘리는 작업으로 확대하지 않는다. 현재 글에서 독자가 막히는 부분부터 개선한다.

## 글의 근거

기술 선택이나 제품 정책을 설명할 때는 관련 코드, Git 기록, 사용자가 제공한 대화 중 필요한 자료를 확인한다. 다른 세션을 참고하라는 요청이 있으면 접근 가능한 세션에서 관련 사용자 요청과 최종 결과를 읽고 현재 코드와 대조한다. 대화를 다른 세션으로 보내거나 전체 내용을 글에 옮기지 않는다.

저자가 요청한 것, 구현된 것, 테스트한 것, 실제로 운영한 것을 구분한다. 확인할 수 없는 동기나 장애 경험, 사용자 반응을 저자의 경험으로 만들어 넣지 않는다. 근거가 부족한 주장은 범위를 줄이거나 필요한 부분만 질문한다. 외부 기술의 현재 동작을 확인해야 한다면 공식 문서를 확인한다.

사용자가 익명화를 요청한 이름과 식별자는 근거 자료에 남아 있어도 글, 코드 예제와 발행 메타데이터에 다시 넣지 않는다.

## 작성과 교정

한국어는 해요체로 쓰고, 추상적인 용어 대신 누가 무엇을 하다가 어떤 문제를 겪었고 어떻게 바꿨는지 드러낸다. 고정된 목차나 문단 수, 교훈으로 끝나는 구조를 모든 글에 적용하지 않는다. 사용자가 사례를 더 원하면 필요한 내용을 충분히 쓰고, 군더더기 표현을 지우라는 요청을 글 전체를 요약하라는 뜻으로 해석하지 않는다.

제목과 도입이 약속하는 결과를 본문이 제공하는지 확인한다. 따라 하는 방법을 약속했다면 실행과 확인이 가능해야 하고, 선택 기준을 약속했다면 대안과 제약, 선택 이유가 보여야 한다. 제목은 단순히 본문에 등장하는 기술을 나열하거나 실제보다 좁은 주제를 약속하지 않게 정한다.

각 절은 핵심 질문에 필요한 맥락, 행동, 사실이나 판단을 맡게 한다. 코드는 선택의 작동 원리를 보여 주는 데 필요한 부분을 쓰고, 설정 전체를 나열해 본문의 역할을 바꾸지 않는다. 다른 목적의 내용이 길어지면 같은 글 안에서 구획을 분명히 하거나 기존의 관련 자료로 연결한다. 새 글로 분리하는 작업은 요청 범위 안에서 판단한다. 분량이나 도구 수만으로 글을 나누지 않으며, 여러 판단이 같은 질문에 연결된다면 긴 글로 충분히 설명한다.

주니어 독자에게 전할 배움은 문제를 좁힌 방법, 가설을 확인한 근거, 결과로 바뀐 판단 안에서 드러낸다. 근거가 뒷받침하는 조건까지 설명하고, 모든 글에 일반적인 조언이나 교훈 문단을 붙이지 않는다.

문장 교정에는 개인 blog-writing 스킬의 피드백을 참고한다. 개인 선호를 다른 서비스의 코드나 UI 문구 규칙으로 확대하지 않는다.

한글과 영문판을 함께 관리하되 문장을 기계적으로 대응시키지 않는다. 독자에게 약속한 결과와 사실, 주장 범위를 맞추고 각 언어에서 자연스럽게 읽히도록 쓴다. 기존 slug와 최초 발행일을 유지하고, 메타데이터와 SEO는 실제 변경에 맞춰 갱신한다. 전용 표지와 본문 이미지는 프로젝트 지침을 따른다.

## 피드백과 검증

반복 적용할 문체 피드백은 개인 스킬 `~/.agents/skills/blog-writing/references/writing-feedback.md`의 관련 항목에 원래 지적과 적용 범위를 짧게 남긴다. 개인 스킬이 없다면 현재 요청을 그대로 반영하되 별도 설치나 외부 변경을 임의로 시작하지 않는다. 특정 문장의 수정 요청을 모든 작업의 금지 규칙으로 확대하지 않고, 같은 피드백을 프로젝트 전역 문서에 복제하지 않는다. 이 프로젝트에서 실제로 고친 글의 편집 기록은 필요할 때 기존 감사 문서에 남긴다.

마지막에는 목표 독자의 입장에서 다시 읽는다. 제목이 약속한 결과를 얻는지, 필요한 선행 지식이나 정보가 빠졌는지, 중간에 다른 목적의 내용으로 흐름이 끊기는지 확인한다. 유형에 맞는 검토는 독자 목적별 편집 기준을 사용하고, 사실의 정확성과 읽는 흐름을 각각 확인한다. 유형을 붙였다는 이유로 품질 검토를 끝내지 않는다.

글의 본문이나 발행 데이터를 바꾸면 레지스트리를 생성하고 프로젝트 지침에 정해진 검증을 실행한다. 에이전트·스킬 지침만 바꾼 경우에는 해당 파일의 구문과 참조를 검증한다. 문구를 고칠 때마다 문장을 그대로 검사하는 테스트를 추가하지 않는다. 완료 보고에는 큰 개정의 핵심 질문과 중심 역할, 실제 변경과 실행한 검사, 확인하지 못한 범위를 짧게 담는다. 글의 문장과 별개로 애플리케이션 코드, 다른 프로젝트나 공개 작업의 범위를 넓히지 않는다.
