# 블로그 문체와 편집 피드백

이 저장소의 `projects/blog` 글을 작성하거나 고칠 때 참고할 사용자 피드백이다. 블로그 문체에만 적용하며 일반 개발 작업이나 프로젝트 전역의 규칙으로 사용하지 않는다. 2026-10-29 대화에서 반복된 지적을 정리했다. 이후 새로 받은 피드백도 관련 항목에 보강한다. 대화 전체를 옮기거나 인증정보, 비공개 업무 내용을 기록하지 않는다.

## 날짜로 작성 기준을 설명하지 않기

사용자는 “2026년 10월 28일의 구현을 기준으로 썼어요” 같은 표현이 어색하다고 했다. 글의 도입이나 끝에 작성 시점을 설명하는 문장을 관성적으로 붙이지 않는다. 발행일과 수정일은 메타데이터로 관리한다.

문제의 발생 순서, 릴리스와 패치 버전, 기간별 결과를 이해하는 데 필요한 날짜는 본문에 남긴다. 과거 상태를 현재 사실로 바꾸지는 않는다. 예를 들어 “9월 28일 기준으로 아직 그대로예요”를 지울 때는 “당시 코드에 남아 있었어요”처럼 실제로 확인한 시점을 과거형으로 전달할 수 있다.

## 추상적인 말 대신 무엇을 했는지 쓰기

사용자는 “서버의 업무 규칙”이라는 표현을 지적했다. 그룹 가입을 승인하는지, 남의 글을 지울 수 있는지, 투표 기간인지 확인한다는 식으로 구체적인 행동을 쓴다. 기술 글에서 필요한 전문용어를 없애라는 뜻은 아니다. 용어만으로 설명을 대신하지 않는다.

## 회고를 질문 목록이나 다짐으로 끝내지 않기

“지금은 기능을 추가할 때 이런 질문도 같이 적어 보려고 해요” 뒤에 권한, 실패, 삭제, 돌아갈 곳을 나열한 결론이 AI가 쓴 문장 같다는 피드백을 받았다. “판단에 필요한 순간에 필요한 말을 보여 주고 싶어요”, “테스트로 확인해야 해요” 같은 일반론도 같은 지적에 포함됐다.

이미 본문에서 다룬 내용을 결론에서 다시 체크리스트로 만들지 않는다. 저자가 놓친 상황과 실제로 고친 내용을 짧게 돌아보거나, 내용이 끝나는 곳에서 글을 마친다. 모든 글에 교훈, 다음 계획, 사용자 모집 이야기를 덧붙이지 않는다. 목록 자체가 금지된 것은 아니며 비교나 절차가 필요하면 쓸 수 있다.

## 사례가 필요하면 길어져도 괜찮음

사용자는 기능을 만들 때 예외 상황도 처음부터 생각했어야 했다는 내용을 요청하며, 다른 작업 대화에서 어떤 상황과 정책을 고려했는지 넣어 달라고 했다. 글이 길어져도 괜찮다고 했다.

익명 이용 뒤의 기록, 그룹 가입 승인과 권한, 접수 마감 뒤 요청, 중복 전송처럼 구체적인 경우와 결정한 이유를 쓴다. 사례를 일반적인 제품 설계 원칙으로 바꾸거나 실제로 발생하지 않은 사고를 겪었다고 꾸미지 않는다.

## 구두점과 말투

기본은 자연스러운 해요체다. 나열에 가운데 점을 쓰거나 문장을 앰대시로 이어 붙이지 않는다. 문장을 나누거나 쉼표와 조사로 연결한다. 코드의 연산자, URL, 원문 인용, 제품 고유 이름은 문체 수정 때문에 바꾸지 않는다.

사용자는 앰대시와 가운데점, 아래아처럼 보이는 나열 기호가 겹치는 글과 화면을 고친 전후 예시를 원했다. 기호만 바꾸기보다 설명과 행동이 이어지도록 문장을 고친다. 재구성한 문구나 도해는 실제 초안이나 서비스 화면 캡처처럼 제시하지 않는다.

## 문단과 절의 흐름 이어가기

사용자는 AI 결과물 검토 글이 문단마다 끊긴다고 지적했고, 다듬은 글을 기준으로 최근 글에도 같은 피드백을 적용해 달라고 했다. 같은 역할 설명을 도입과 여러 절에서 반복하지 않는다. 관련된 문단은 묶고, 앞서 나온 경험이나 수정 요청이 다음 내용으로 이어지도록 순서를 다듬는다. 접속어를 덧붙이거나 문단 수를 줄이는 일만으로 처리하지 않는다.

이어 쓴다는 이유로 서로 다른 경험 사이에 관계를 만들어 넣지 않는다. 사용자는 인프라와 도구 설정을 더 맡기는 동안 글과 화면의 검수 기준도 구체화됐다는 문장을 특히 어색하다고 했다. 실제로 연결할 내용이 없으면 그런 문장을 빼고, 각 대목에서 누가 무엇을 했는지 쓴다.

사이드프로젝트의 역할을 설명할 때는 결과물을 직접 써 보고 피드백한 일, 코드 구조를 훑은 일, 에이전트가 맡은 세부 구현과 테스트를 구분한다. 업무에서 기존 코드베이스를 이해하고 diff로 구현을 판단한 경험과 섞지 않는다. 결과물의 수정 방향을 설명하는 대목은 피드백으로 쓴다.

## 작업 집계를 본문에 넣지 않기

사용자는 “파일 수와 호출부 수는 각 커밋 시점에 센 값이에요. 장애 건수의 변화는 측정하지 않았어요” 같은 수치 기록도 블로그에 어울리지 않는다고 했다. 몇 개 파일을 바꿨는지, 호출부가 몇 곳인지, 코드가 몇 줄 줄었는지와 그 집계 시점을 작업 보고처럼 본문에 나열하지 않는다. 무엇이 불편했고 어느 코드가 어떤 책임을 맡도록 바뀌었는지를 설명한다. 필요한 집계와 검증 기록은 PR이나 프로젝트의 편집 기록에서 관리한다.

“장애 건수 변화는 측정하지 않았다”처럼 글에서 주장하지 않은 성과 지표를 끌어와 부연하지 않는다. 측정하지 않은 개선을 주장하지 않고, 실제로 확인한 동작으로 문장을 마친다. 원인을 설명하는 실측 성능값, 오류의 영향, API 제한이나 설정값, 버전처럼 독자가 기술적 판단을 이해하는 데 필요한 숫자까지 일괄 삭제하라는 뜻은 아니다.

## 사실을 문체와 함께 확인하기

사용자가 직접 써보고 고쳐 달라고 한 것과 외부 사용자가 검증한 것은 구분한다. 계획, 구현, 로컬 확인, 실제 운영 결과를 섞지 않는다. 실제로 모집하거나 운영하지 않았다면 성공 사례로 쓰지 않는다.

문장이 딱딱하다는 이유로 필요한 한계까지 지우지는 않는다. 확인한 동작을 구체적으로 쓰고, 확인하지 않은 부분은 관련 주장 가까이에서 짧게 설명한다. 한글 본문을 고치면 영문판도 같은 사실과 어조로 맞춘다.
