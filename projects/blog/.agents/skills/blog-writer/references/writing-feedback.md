# 블로그 문체와 편집 피드백

이 저장소의 `projects/blog` 글을 작성하거나 고칠 때 참고할 사용자 피드백이다. 블로그 문체에만 적용하며 일반 개발 작업이나 프로젝트 전역의 규칙으로 사용하지 않는다. 2026-10-29 대화에서 반복된 지적을 정리했다. 이후 새로 받은 피드백도 관련 항목에 보강한다. 대화 전체를 옮기거나 인증정보, 비공개 업무 내용을 기록하지 않는다.

## 날짜로 작성 기준을 설명하지 않기

사용자는 “2026년 10월 28일의 구현을 기준으로 썼어요” 같은 표현이 어색하다고 했다. 글의 도입이나 끝에 작성 시점을 설명하는 문장을 관성적으로 붙이지 않는다. 발행일과 수정일은 메타데이터로 관리한다.

문제의 발생 순서, 릴리스와 패치 버전, 기간별 결과를 이해하는 데 필요한 날짜는 본문에 남긴다. 과거 상태를 현재 사실로 바꾸지는 않는다. 예를 들어 “9월 28일 기준으로 아직 그대로예요”를 지울 때는 “당시 코드에 남아 있었어요”처럼 실제로 확인한 시점을 과거형으로 전달할 수 있다.

## 추상적인 말 대신 무엇을 했는지 쓰기

사용자는 “서버의 업무 규칙”이라는 표현을 지적했다. 그룹 가입을 승인하는지, 남의 글을 지울 수 있는지, 투표 기간인지 확인한다는 식으로 구체적인 행동을 쓴다. 기술 글에서 필요한 전문용어를 없애라는 뜻은 아니다. 용어만으로 설명을 대신하지 않는다.

## 회고를 질문 목록이나 다짐으로 끝내지 않기

“지금은 기능을 추가할 때 이런 질문도 같이 적어 보려고 해요” 뒤에 권한, 실패, 삭제, 돌아갈 곳을 나열한 결론이 AI가 쓴 문장 같다는 피드백을 받았다. “판단에 필요한 순간에 필요한 말을 보여 주고 싶어요”, “테스트로 확인해야 해요” 같은 일반론도 같은 지적에 포함됐다.

이미 본문에서 다룬 내용을 결론에서 다시 체크리스트로 만들지 않는다. 저자가 놓친 상황과 실제로 고친 내용을 짧게 돌아보거나, 내용이 끝나는 곳에서 글을 마친다. 모든 글에 교훈, 다음 계획, 사용자 모집 이야기를 덧붙이지 않는다. 목록 자체가 금지된 것은 아니며 비교나 절차가 필요하면 쓸 수 있다.

## 사례가 필요하면 길어져도 괜찮음

사용자는 기능을 만들 때 예외 상황도 처음부터 생각했어야 했다는 내용을 요청하며, 다른 작업 대화에서 어떤 상황과 정책을 고려했는지 넣어 달라고 했다. 글이 길어져도 괜찮다고 했다.

익명 이용 뒤의 기록, 그룹 가입 승인과 권한, 접수 마감 뒤 요청, 중복 전송처럼 구체적인 경우와 결정한 이유를 쓴다. 사례를 일반적인 제품 설계 원칙으로 바꾸거나 실제로 발생하지 않은 사고를 겪었다고 꾸미지 않는다.

## 구두점과 말투

기본은 자연스러운 해요체다. 나열에 가운데 점을 쓰거나 문장을 앰대시로 이어 붙이지 않는다. 문장을 나누거나 쉼표와 조사로 연결한다. 코드의 연산자, URL, 원문 인용, 제품 고유 이름은 문체 수정 때문에 바꾸지 않는다.

사용자는 앰대시와 가운데점, 아래아처럼 보이는 나열 기호가 겹치는 글과 화면을 고친 전후 예시를 원했다. 기호만 바꾸기보다 설명과 행동이 이어지도록 문장을 고친다. 재구성한 문구나 도해는 실제 초안이나 서비스 화면 캡처처럼 제시하지 않는다.

## 문단과 절의 흐름 이어가기

사용자는 AI 결과물 검토 글이 문단마다 끊긴다고 지적했고, 다듬은 글을 기준으로 최근 글에도 같은 피드백을 적용해 달라고 했다. 같은 역할 설명을 도입과 여러 절에서 반복하지 않는다. 관련된 문단은 묶고, 앞서 나온 경험이나 수정 요청이 다음 내용으로 이어지도록 순서를 다듬는다. 접속어를 덧붙이거나 문단 수를 줄이는 일만으로 처리하지 않는다.

이어 쓴다는 이유로 서로 다른 경험 사이에 관계를 만들어 넣지 않는다. 사용자는 인프라와 도구 설정을 더 맡기는 동안 글과 화면의 검수 기준도 구체화됐다는 문장을 특히 어색하다고 했다. 실제로 연결할 내용이 없으면 그런 문장을 빼고, 각 대목에서 누가 무엇을 했는지 쓴다.

사용자는 무한 스크롤과 드롭다운 테스트 글(`scroll-and-dropdown-states`)도 문맥과 문단 구조가 많이 어색하다고 했다. 고칠 때 확인한 원인은 글을 쓰게 된 배경이 도입 다음 절에 따로 있던 것, Radix와 Base UI 테스트를 보게 된 이유가 그 문단들보다 뒤에 나온 것, 한 절이 마지막 페이지와 실패를 함께 다루면서 여러 절의 내용을 모은 표를 중간에 둔 것이었다. 배경과 문제는 도입에 모으고, 이유는 그 이유가 필요한 내용 앞에 두며, 한 절은 한 상황을 맡게 나눈다.

사이드프로젝트의 역할을 설명할 때는 결과물을 직접 써 보고 피드백한 일, 코드 구조를 훑은 일, 에이전트가 맡은 세부 구현과 테스트를 구분한다. 업무에서 기존 코드베이스를 이해하고 diff로 구현을 판단한 경험과 섞지 않는다. 결과물의 수정 방향을 설명하는 대목은 피드백으로 쓴다. 감사 문서의 항목과 저자가 따로 한 코드 수정도 구분한다. 사용자는 후속 과제 문서가 에이전트 감사로 나온 보고서이고, Knip 정리와 FSD pages 레이어 수정, API 책임 분리, presigned 업로드 전환은 감사 밖에서 진행한 작업이라고 바로잡았다. 회고에 에이전트 감사를 꼭 언급할 필요는 없다고도 했다.

## 문장과 단어의 연결을 교정하기

사용자는 디자인 TIL에서 “문장 이음새가 어색하지 않도록”, “문장과 단어가 어색하지 않게” 교정하고 이 기준도 스킬에 넣어 달라고 했다. 초고를 그대로 마무리하지 않고 문장 자체를 검토하는 단계가 필요하다.

문장 안에서는 주어와 서술어가 호응하는지, 동사에 맞는 목적어와 조사를 썼는지, 수식어가 의도한 대상을 꾸미는지 확인한다. 뜻이 통하더라도 단어끼리 자연스럽게 어울리는지 살핀다. 이 글에서는 “한 번에 얼마나 진행하는지”를 “수업 한 번에 몇 분이 걸리는지”로, “연습할 판단을 정해요”를 “다음 경기에서 고칠 점을 찾아요”로 고쳤다. 특정 단어를 금지하는 예시가 아니라 문맥에 맞는 구체적인 표현을 고르는 예시다. 본문뿐 아니라 요약, 제목, 사진 설명과 도해 안의 문구도 함께 본다.

인접한 두세 문장을 이어 읽으면서 주제가 갑자기 바뀌거나 같은 설명이 반복되는지 확인한다. “이것”, “그 차이”, “이 관계”가 무엇을 가리키는지 분명하게 하고, 새 용어는 앞서 설명한 문제나 예시와 연결한다. 정의문만 연달아 나열되어 끊기는 부분은 예시와 설명의 순서를 조정한다. 서로 독립된 내용은 문단을 나누되, 이음새를 만들려고 확인되지 않은 인과관계나 저자의 경험을 덧붙이지 않는다.

사용자는 Yarn Workspaces와 Turborepo 글의 문맥과 문장 구조가 이상하다고 했다(2026-11-10). 예제의 구성보다 오류가 먼저 나와 독자가 무엇이 깨졌는지 모른 채 읽었고, 처음 소개하지 않은 문서 앱이 표에 갑자기 나왔다. '이 저장소'가 예제 모노레포와 실제 사이드프로젝트 중 어느 쪽인지 흐렸고, 한 문단이 `node-modules`와 Plug'n'Play 설명을 오가다 다시 `node-modules`로 돌아왔다. "설치 범위를 좁히거나 … 알 수 있어요"처럼 앞뒤 절의 주어와 서술어가 맞지 않는 문장도 있었다. 배경과 구성원을 먼저 소개하고, 한 문단에서는 한 대상을 끝까지 설명하며, 예제와 실제 저장소를 이름으로 구분한다.

사용자는 글을 다 쓴 뒤 맥락과 문맥, 단어, 문장 구조를 한 번 더 확인해 어색하거나 AI가 쓴 것 같은 문장을 고쳐 달라고 했다(2026-11-11). 고친 부분만 따로 읽지 않고 앞뒤 문단과 이어 읽는다. 이때 고친 예는 한 문장 안에서 같은 말이 겹친 "UI는 … UI 컴포넌트의"와 "보려고 … 보려고", 연달아 같은 어미로 끝나던 "~게 됐어요", 문단 첫 문장을 끝에서 다시 요약하던 문장, 앞에 대상이 없던 "이 로더", 실제 동작과 맞지 않던 "PnP에서는 호이스팅 덕분에"였다.

한국어와 영어는 각 언어에서 자연스럽게 읽히도록 따로 교정한다. 번역투나 어색한 단어 조합을 고치면서 전문용어의 뜻, 주장 강도와 실제 경험의 범위는 보존한다. 문장을 매끄럽게 만든다는 이유로 글 전체를 줄이거나 예시와 필요한 한계를 삭제하지 않는다.

## 참고 목록 대신 본문에 링크 걸기

사용자는 “그냥 글에 링크만 걸면 되지 논문도 아닌데 아래에 참고글 링킹할 필요는 없어”라고 했다. 새 글에는 끝에 참고나 관련 글 목록을 붙이지 않고, 근거가 필요한 문장에 바로 링크를 건다. 요청 없이 기존 글의 참고 목록까지 일괄로 지우지는 않는다.

## 작업 집계를 본문에 넣지 않기

사용자는 “파일 수와 호출부 수는 각 커밋 시점에 센 값이에요. 장애 건수의 변화는 측정하지 않았어요” 같은 수치 기록도 블로그에 어울리지 않는다고 했다. 몇 개 파일을 바꿨는지, 호출부가 몇 곳인지, 코드가 몇 줄 줄었는지와 그 집계 시점을 작업 보고처럼 본문에 나열하지 않는다. 무엇이 불편했고 어느 코드가 어떤 책임을 맡도록 바뀌었는지를 설명한다. 필요한 집계와 검증 기록은 PR이나 프로젝트의 편집 기록에서 관리한다.

“장애 건수 변화는 측정하지 않았다”처럼 글에서 주장하지 않은 성과 지표를 끌어와 부연하지 않는다. 측정하지 않은 개선을 주장하지 않고, 실제로 확인한 동작으로 문장을 마친다. 원인을 설명하는 실측 성능값, 오류의 영향, API 제한이나 설정값, 버전처럼 독자가 기술적 판단을 이해하는 데 필요한 숫자까지 일괄 삭제하라는 뜻은 아니다.

## 사실을 문체와 함께 확인하기

사용자는 UI 테스트 글(`scroll-and-dropdown-states`)에서 개인적인 배경을 드러내는 설명을 빼 달라고 했다. 한글·영문 본문과 요약, 발행 메타데이터는 UI 테스트를 돌아본 경험과 실제 개선 내용을 중심으로 쓴다. PR 제목과 설명, 커밋 메시지도 글에서 바뀐 내용만 기술한다.

사용자는 같은 글에서 Base UI가 동작을 작은 테스트로 나눠 검증한다고 바로잡았다. 라이브러리 테스트를 소개할 때 특정 파일의 상태 기록 방식을 전체 테스트 구성으로 일반화하지 않는다. 기능별 묶음과 개별 동작 검사, 순서 자체를 확인하는 전환 검사를 구분한다. 이를 참고한 개선안은 실제로 반영하고 실행한 테스트와 구별해 쓴다.

사용자가 직접 써보고 고쳐 달라고 한 것과 외부 사용자가 검증한 것은 구분한다. 계획, 구현, 로컬 확인, 실제 운영 결과를 섞지 않는다. 실제로 모집하거나 운영하지 않았다면 성공 사례로 쓰지 않는다.

저자가 무엇을 몰랐거나 잊었는지는 저자가 직접 말한 것만 쓴다. 면접 회고 글에서 근거 문서에 비어 있던 선택 이유를 '스스로 물어보니 답하지 못했다'로 썼다가, 사용자가 그건 답할 수 있었다고 바로잡았다(2026-11-10). 문서의 빈칸은 글쓴이에게 전달되지 않은 정보일 뿐이고, 이음새를 만들려고 저자의 부족함을 원인으로 덧붙이지 않는다.

문장이 딱딱하다는 이유로 필요한 한계까지 지우지는 않는다. 확인한 동작을 구체적으로 쓰고, 확인하지 않은 부분은 관련 주장 가까이에서 짧게 설명한다. 한글 본문을 고치면 영문판도 같은 사실과 어조로 맞춘다.
