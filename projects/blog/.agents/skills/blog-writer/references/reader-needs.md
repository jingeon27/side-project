# 독자 목적별 편집 기준

Diátaxis의 독자 요구 구분을 이 블로그의 작성과 교정에 적용한다. 새 글이나 구조를 크게 고칠 때 필요한 유형의 기준을 읽는다. 아래 예시는 글을 고르는 기준이며 고정 목차나 필수 제목이 아니다.

## 중심 역할 고르기

독자에게 필요한 것이 직접 하는 행동인지, 사실이나 이유의 이해인지부터 본다. 이어서 새로 익히는 상황인지, 이미 아는 것을 실제 작업에 적용하는 상황인지 판단한다.

| 독자가 처한 상황                           | 중심 역할                     | 글이 제공할 결과                                        |
| ------------------------------------------ | ----------------------------- | ------------------------------------------------------- |
| 낯선 기능을 직접 해 보며 익히려 해요       | 튜토리얼 · Tutorial           | 작은 실습을 끝내며 동작과 개념에 익숙해져요             |
| 기본 사용법을 알고 특정 작업을 끝내려 해요 | 문제 해결 안내 · How-to guide | 자신의 상황에 맞게 절차를 적용하고 완료 여부를 확인해요 |
| 작업 중 정확한 값이나 동작을 찾아보려 해요 | 참조 · Reference              | 옵션, 제약, 입력과 출력에 관한 사실을 빠르게 찾아요     |
| 선택이나 현상의 이유를 이해하려 해요       | 설명 · Explanation            | 맥락과 대안, 인과관계를 연결해 판단을 이해해요          |

주니어도 특정 설정을 조회할 때는 참조가 필요하고, 숙련자도 처음 쓰는 도구를 익힐 때는 튜토리얼이 필요하다. 독자의 연차와 문서 유형을 같은 기준으로 취급하지 않는다.

## 튜토리얼: 작은 경험을 끝까지 따라가게 하기

- 만들거나 관찰할 결과와 필요한 환경을 먼저 드러낸다. 실습 경로를 선택해 주고, 학습 도중에 불필요한 대안 선택을 요구하지 않는다.
- 행동 뒤에 무엇이 나타나는지, 독자가 무엇을 눈여겨봐야 하는지 보여 준다. 중간에도 성공을 확인할 수 있어야 한다.
- 진행에 필요한 설명을 가까이 두고 긴 원리 설명과 옵션 목록은 별도의 자료로 연결한다. 코드를 복사하는 행위만으로 학습 결과를 대신하지 않는다.
- 안내한 시작 상태에서 끝까지 실행할 수 있는지 확인한다. 실행하지 못한 부분은 예상 결과와 실제 확인을 구분한다.

예: 작은 예제 앱에서 첫 Sentry 오류를 전송하고 이벤트를 찾아보는 실습. 독자가 얻을 것은 Sentry를 처음 다뤄 본 경험이다.

## 문제 해결 안내: 이미 가진 지식으로 작업을 끝내게 하기

- 해결할 문제와 적용 조건, 시작할 상태와 완료 상태를 명확히 한다. 도구의 기능 순서보다 독자의 작업 순서로 쓴다.
- 필요한 행동과 판단, 상황에 따른 분기, 실패했을 때 확인할 지점을 담는다. 기본 개념부터 다시 가르치거나 관련 기능을 전부 소개하지 않는다.
- 결과를 확인할 방법을 제공한다. 계정 권한, 버전 등 결과를 좌우하는 전제는 실행 전에 알 수 있게 쓴다.

예: 배포된 오류의 압축된 스택을 소스맵으로 확인하도록 릴리스 연결을 고치는 안내. Sentry 입문 전체를 다시 설명하지 않아도 된다.

## 참조: 필요한 사실을 찾아보게 하기

- 설명 대상의 버전과 범위를 고정하고 입력, 출력, 기본값, 허용 값, 제약과 예외 중 필요한 사실을 정확히 쓴다.
- 설정 이름이나 API 구조처럼 독자가 예상하는 기준으로 정보를 배치한다. 병렬 항목은 표나 일관된 목록으로 비교하기 쉽게 한다.
- 사실과 저자의 추천을 구분한다. 사례는 사용법을 식별할 만큼 제공하되 경험담이나 긴 선택 논거가 조회를 방해하지 않게 한다.

예: 특정 SDK 버전의 수집 옵션, 프로젝트에서 사용하는 값, 전송에 미치는 영향을 찾아보는 설정표. SDK 기본값과 이 프로젝트의 설정값을 구별한다.

## 설명: 맥락을 연결해 판단을 이해하게 하기

- 어떤 왜 질문에 답하는지 경계를 잡는다. 기술 선택과 장애 분석에서는 문제와 제약, 검토한 대안, 작동 원리와 결과를 필요한 순서로 연결한다.
- 대안을 검토했다는 사실과 나중에 가능한 대안을 소개하는 설명을 구분한다. 저자의 관점은 드러내되 확인하지 않은 동기나 실험을 덧붙이지 않는다.
- 코드, 로그, 테스트 결과는 판단을 뒷받침하는 근거로 쓴다. 코드가 보장하는 것과 테스트에서 확인한 것, 운영에서 관찰한 것을 구별한다.
- 결과와 한계를 통해 어떤 조건에서 같은 판단을 적용할 수 있는지 보여 준다. 설치 절차나 옵션 전체를 덧붙여 따라 하기 글로 흐르지 않게 한다.

예: 수집 범위를 줄인 이유와 전송 성공만으로 서버 저장을 확인했다고 볼 수 없었던 이유를 설명하는 Sentry 경험담. 사례를 따라가며 저자의 판단을 이해하게 한다.

## 여러 역할이 만날 때

설명형 경험담에 짧은 코드나 설정표가 필요한 경우도 있다. 그 부분이 중심 질문의 이해를 어떻게 돕는지 연결하고, 독자가 실행 모드와 이해 모드 사이를 반복해서 오가지 않게 배치한다. 독립적으로 수행할 긴 절차나 조회용 전체 목록은 기존 자료로 연결하거나 요청 범위 안에서 별도 구획으로 다룬다. 존재하지 않는 후속 글에 링크하지 않는다.

API와 캐시, DB 정합성, 관측이 한 문제의 원인과 결과로 이어진다면 같은 글에서 충분히 설명할 수 있다. 연결 없이 주제가 늘어나면 각 절이 핵심 질문에 답하는지부터 고친다. 길이만을 이유로 나누거나 제목을 포괄적인 말로 넓히는 것으로 해결하지 않는다.

유형에 맞춰 검토할 때는 튜토리얼의 학습 경로와 관찰 결과, 문제 해결 안내의 적용 조건과 완료 확인, 참조의 정확성과 검색 편의, 설명의 인과관계와 대안을 각각 살핀다. 실제 독자가 필요한 결과를 얻는지가 편집의 기준이다.
