In an interview, I was asked, "If you were testing a UI feature like a dropdown, how would you design the tests?" I said I would check that clicking outside the menu closes it, that clicking inside the menu area doesn't, and that clicking the trigger again closes it. I said whatever came to mind first. It wasn't a wrong answer, but I wasn't satisfied with it either.

Until then, I had left UI like dropdowns to Radix, shadcn/ui, and Base UI. I trusted them only because they were still being updated and had lots of downloads, and I never checked what they actually tested. Since I trusted the libraries, I didn't give unit-testing UI much thought. The unit tests I wrote at work were mostly about logic, and I checked screens with integration tests and E2E.

I did open tests when I read open-source code. But I read them to see how a feature was implemented and how to use it, not which cases were verified and how. The tests laid out many ways to use each feature.

## I had to define the dropdown first

Looking back, I only listed cases to check and never said why I picked those three. And before choosing cases, there was something to decide: what people call a dropdown isn't one kind of UI.

The [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/) split it into several patterns: a [menu button](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/) for choosing an action, a [listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) for choosing a value, a [combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) for narrowing options by typing, and a [disclosure](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/) for revealing a list of links. Each pattern needs different keyboard behavior and ARIA attributes. The design system in my side project also has a separate menu (`dropdown-menu`), custom select (`select`), and native select (`native-select`), and to a user all three are dropdowns.

Even for the same menu, libraries have different defaults. When you click a checkbox item, Base UI keeps the menu open (`closeOnClick` defaults to `false`), while Radix closes it. To keep a Radix menu open, you call `preventDefault()` in [`onSelect`](https://www.radix-ui.com/primitives/docs/components/dropdown-menu). Regular items close the menu in both libraries.

So to answer the question, I first had to decide what role the dropdown plays and which library it is built on. If the question didn't say, I should have stated my assumptions before starting. Instead, I went straight to cases.

## Rereading library tests as a verifier

In [my last article](/en/blog/testing-infinite-scroll-and-dropdown-states), I used Radix and Base UI tests as an answer key to fill out the tests for the infinite scroll and the more menu in Photo Contest. This time, I reread them to see what each library verifies rather than how to use it. Along the way, I wondered whether the many issues these libraries must have received over the years had left traces in their tests.

I traced the Radix menu test cases I cited in my last article back to their pull requests and issues.

| What the test checks | Pull request that added it | Original issue |
| --- | --- | --- |
| When the menu is closed, the trigger's `aria-controls` doesn't point to an element that isn't there | [#3922](https://github.com/radix-ui/primitives/pull/3922) (June 2026) | [#3013](https://github.com/radix-ui/primitives/issues/3013) (July 2024), [#3242](https://github.com/radix-ui/primitives/issues/3242) (November 2024) |
| When the window loses focus, submenus close too | [#3938](https://github.com/radix-ui/primitives/pull/3938) (June 2026) | [#3257](https://github.com/radix-ui/primitives/issues/3257) (November 2024) |
| A closing menu doesn't take focus when the pointer moves over it | [#4196](https://github.com/radix-ui/primitives/pull/4196) (October 2026) | [#4195](https://github.com/radix-ui/primitives/issues/4195) (October 2026) |

All three tests were added while fixing a reported issue. The `aria-controls` issue was opened in July 2024 and closed in June 2026. The title of the third issue notes that [#1266](https://github.com/radix-ui/primitives/issues/1266), which reported the same problem in March 2022, had been closed without a fix.

Base UI was no different. Its [menu tests](https://github.com/mui/base-ui/blob/v1.9.0/packages/react/src/menu/root/MenuRoot.test.tsx) contain a `See #5152` comment. [#5152](https://github.com/mui/base-ui/issues/5152) is a July 2026 issue reporting that multiple submenus broke when the mouse moved quickly. Five days later, [#5153](https://github.com/mui/base-ui/pull/5153) fixed it, and this test came in with the fix.

Not every test comes from an issue. Base UI's menu test history also has commits such as [#5269](https://github.com/mui/base-ui/pull/5269), "[menu] Expand test coverage," which added tests in bulk to widen coverage. If you follow a test line through blame to its pull request, and then to the issue linked from it, you can tell whether the test was designed up front or added while fixing a reported problem.

I had thought component tests were easy to write and easy to read, so designing them couldn't be that hard. But behind one test line was an issue that had stayed open for almost two years. There was a world I didn't know about, and I was embarrassed that I had thought it was easy.

[When I introduced tests](/en/blog/testing-standards), I decided to keep the expected behavior I defined up front in `*.spec` files and bugs found outside it in `*.test` files. The library tests added while fixing issues sat in the same place as my `*.test` files. Even widely used libraries didn't test these cases from the start, and a problem reported in 2022 became a test only in 2026. Not even the libraries had airtight tests from day one.

## Choosing cases by who interacts and in which state

When I choose cases, I look at two things.

The first is who decided the behavior. I trust behavior that the library decides and also tests. I check behavior myself when I couldn't find it in the library's tests but my screens depend on it, or when my own code decides it.

The second is who changes the state. I'll call these actors in this article. People use a menu with a pointer, a keyboard, or a screen reader, and developers who use the component change it through props such as `align` and `disabled`. The environment and time change the state too: the window losing focus, a transition still running, or the viewport size changing. Radix's [dropdown E2E tests](https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/e2e/dropdown-menu.spec.ts) are split the same way, with `when using pointer` and `When using keyboard` under `given submenu user`.

Pairing actors with the closed, opening, open, and closing states gives you cells to check. Here is where the issues above fall.

| State | Actor | What to check | Source |
| --- | --- | --- | --- |
| Open | Pointer user | Clicking outside closes it, clicking inside keeps it open, and clicking the trigger again closes it | My interview answer |
| Closed | Screen reader user | The trigger's `aria-controls` doesn't point to an element that isn't there | Radix #3013, #3242 |
| Open | Environment | Losing window focus closes submenus too | Radix #3257 |
| Closing | Pointer user | Moving over or clicking an item does nothing | Radix #4195 |
| Open | Developer using the component | Passing `align` opens the menu aligned to that side | A default my wrapper sets |

My interview answer covered only the first row. Every cell where an issue came in was outside it: a screen reader user meeting a closed menu, the environment changing the state through window focus, and the pointer passing over a menu that was closing.

## What needs a real browser

Radix and Base UI both test in real browsers. Radix runs its unit tests with Vitest and jsdom and keeps separate Playwright E2E tests. Its dropdown E2E tests include cases that need real positions and pointer movement, such as whether a submenu closes when the pointer moves away at a narrow viewport. Base UI runs the same tests in both jsdom and real browsers. In 1.9.0 its default `test` command runs in Chromium, and Vitest's [browser mode](https://github.com/mui/base-ui/blob/v1.9.0/vitest.shared.mts) can also run them in Firefox and WebKit. Tests that only make sense in a browser are marked with `it.skipIf(isJSDOM)`.

These libraries build browser behavior itself: focus movement, pointer events, positioning, and transitions. That has to be checked in real browsers, not with mocks. A product built on top of them doesn't need to check the same behavior again. But jsdom doesn't compute layout that my own code creates, so that part needs a browser.

At first, I wrote four browser tests for the shared menu: the gap from the trigger, the color of the destructive item, pointer input while closing, and the menu height when space runs out. Looking again with these criteria, the gap is just a number passed along while Base UI computes the position, the color is styling, and blocking the pointer while closing is also Base UI's job. What remains is fitting the menu height to the available space (`--available-height`) and scrolling inside it. That layout is the wrapper's decision, so it is the only thing I check in a browser: whether the menu stays on screen in a short viewport and whether I can scroll to the last item and choose it.

## Applying it to the shared menu

The shared [`DropdownMenu`](https://github.com/jingeon27/side-project/blob/ac05c293/packages/design-system/src/ui/dropdown-menu/DropdownMenu.tsx) in my side project wraps Base UI's Menu. Game Mate uses it for its conversation, comment, and profile menus and its editor toolbar, while the Photo Contest more menu from my last article is a separate menu that uses Base UI directly. The shared menu had two tests: opening it with the keyboard and closing it with Escape returns focus to the trigger, and choosing an item with Enter runs the action and closes the menu. Base UI already tests both, while nothing checked the alignment default or the height limit that the wrapper actually sets.

I added two things. Clicking a non-item area inside the menu keeps it open while clicking outside closes it, and the menu aligns to the start by default and to the end when `align="end"` is passed. Clicking inside the menu is Base UI's behavior, but I couldn't find a test covering it by name in Base UI's menu tests. My screens depend on it, so I added it myself.

I also deleted a test. At first I checked that a menu opened inside a card with hidden overflow is drawn outside the card. But when I removed the Portal from the wrapper, Base UI threw `<Menu.Portal> is missing`. Drawing the menu outside the card isn't the wrapper's choice but a structure the library enforces, so I deleted that test.

In Game Mate, I checked that closing a sheet opened from a menu item returns focus to the menu trigger. But the first version of the test still passed when I deliberately turned off the sheet's focus return. Right after the sheet opens, focus is still on the trigger and moves into the sheet a moment later, and the test was pressing Escape before that. Focus never left the trigger, so the test couldn't check whether it came back. I changed it to close the sheet only after confirming that focus had moved inside.

```tsx
await user.keyboard('{Enter}');
const sheet = await screen.findByRole('dialog', { name: 'Delete chat history' });
await waitFor(() => expect(sheet.contains(document.activeElement)).toBe(true));
await user.keyboard('{Escape}');

await waitFor(() => expect(screen.queryByRole('dialog')).toBeNull());
expect(document.activeElement).toBe(trigger);
```

After the change, turning off the sheet's focus return made the test fail. Turning off the menu's focus return instead still passed. It was the sheet, not the menu, that returned focus.

Of the three things I answered in the interview, clicking inside the menu without closing it wasn't in the Photo Contest menu tests or the shared menu tests. I added it to the shared menu tests this time.
