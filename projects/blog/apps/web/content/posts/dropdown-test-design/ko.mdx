_테스트 한 줄을 PR과 이슈까지 거슬러 가는 과정을 그린 도해예요. 실제 서비스 화면은 아니에요._

면접에서 "드롭다운 같은 UI 기능을 테스트한다면 어떻게 설계하겠냐"는 질문을 받았어요. 메뉴 바깥을 누르면 닫히는지, 메뉴 영역 안을 누르면 닫히지 않는지, 트리거를 다시 누르면 닫히는지 확인하겠다고 답했어요. 깊이 생각하지 않고 바로 떠오른 걸 말했어요. 틀린 답은 아니었지만 스스로도 만족스럽지 않았어요.

그동안 드롭다운 같은 UI는 Radix, shadcn/ui, Base UI에 맡겨 왔어요. 최근에도 꾸준히 업데이트되고 다운로드 수가 많다는 점만 보고 믿었고, 그 라이브러리가 무엇을 테스트하는지는 확인하지 않았어요. 라이브러리를 믿었으니 UI 단위 테스트도 깊게 신경 쓰지 않았어요. 실무에서 쓴 단위 테스트도 대부분 로직이었고, 화면은 통합 테스트와 E2E로 확인했어요.

오픈소스 코드를 읽을 때 테스트를 열기는 했어요. 다만 어떤 경우를 어떻게 검증하는지보다는 기능을 어떻게 구현했고 어떻게 쓰는지를 보려고 읽었어요. 테스트에는 다양한 사용법이 정리돼 있었거든요.

## 드롭다운의 스펙부터 정해야 했어요

돌아보니 저는 확인할 케이스만 말했고, 왜 그 세 가지인지는 말하지 않았어요. 그런데 케이스를 고르기 전에 정할 게 있었어요. 드롭다운이라고 부르는 UI가 한 종류가 아니에요.

[WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/)는 흔히 드롭다운이라고 부르는 UI를 여러 패턴으로 나눠요. 행동을 고르는 [메뉴 버튼](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/), 값을 고르는 [리스트박스](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/), 입력해서 후보를 거르는 [콤보박스](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), 링크 목록을 펼치는 [디스클로저](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)예요. 패턴마다 필요한 키보드 동작과 ARIA 속성이 달라요. 제 사이드프로젝트의 디자인 시스템에도 메뉴(`dropdown-menu`), 커스텀 셀렉트(`select`), 네이티브 셀렉트(`native-select`)가 따로 있는데, 사용자에게는 셋 다 드롭다운이에요.

같은 메뉴라도 라이브러리마다 기본 동작이 달라요. 체크박스 항목을 누르면 Base UI는 메뉴를 열어 두고(`closeOnClick` 기본값 `false`), Radix는 닫아요. Radix에서 메뉴를 열어 두려면 [`onSelect`](https://www.radix-ui.com/primitives/docs/components/dropdown-menu)에서 `preventDefault()`를 호출해야 해요. 일반 항목은 두 라이브러리 모두 누르면 닫혀요.

그래서 이 질문에 답하려면 어떤 역할의 드롭다운을 어떤 라이브러리로 만드는지부터 정해야 했어요. 질문에 그 범위가 없으면 가정을 먼저 말하고 시작했어야 했는데, 저는 바로 케이스로 넘어갔어요.

## 라이브러리 테스트를 검증하는 입장에서 다시 읽었어요

[지난 글](/ko/blog/무한-스크롤과-드롭다운-상태별로-테스트하기)에서는 Radix와 Base UI의 테스트를 답지 삼아 피식의 무한 스크롤과 더보기 메뉴 테스트를 보강했어요. 이번에는 사용법이 아니라 이 라이브러리가 무엇을 검증하는지를 보면서 다시 읽었어요. 읽다 보니, 라이브러리를 운영하면서 들어온 이슈가 많았을 텐데 테스트에 그 흔적이 남아 있지 않을까 싶었어요.

지난 글에서 인용한 Radix 메뉴 테스트의 케이스를 PR과 이슈까지 따라가 봤어요.

| 테스트가 확인하는 것 | 테스트를 추가한 PR | 원래 이슈 |
| --- | --- | --- |
| 메뉴가 닫혀 있으면 트리거의 `aria-controls`가 화면에 없는 요소를 가리키지 않아요 | [#3922](https://github.com/radix-ui/primitives/pull/3922) (2026년 6월) | [#3013](https://github.com/radix-ui/primitives/issues/3013) (2024년 7월), [#3242](https://github.com/radix-ui/primitives/issues/3242) (2024년 11월) |
| 창이 포커스를 잃으면 하위 메뉴까지 닫혀요 | [#3938](https://github.com/radix-ui/primitives/pull/3938) (2026년 6월) | [#3257](https://github.com/radix-ui/primitives/issues/3257) (2024년 11월) |
| 닫히는 중인 메뉴는 포인터가 지나가도 포커스를 가져가지 않아요 | [#4196](https://github.com/radix-ui/primitives/pull/4196) (2026년 10월) | [#4195](https://github.com/radix-ui/primitives/issues/4195) (2026년 10월) |

세 케이스 모두 이슈로 보고된 문제를 고치면서 들어온 테스트였어요. `aria-controls` 이슈는 2024년 7월에 열려 2026년 6월에 닫혔어요. 세 번째 이슈의 제목에는 2022년 3월에 같은 문제를 보고한 [#1266](https://github.com/radix-ui/primitives/issues/1266)이 수정 없이 닫혔었다고 적혀 있어요.

Base UI도 마찬가지였어요. [메뉴 테스트](https://github.com/mui/base-ui/blob/v1.9.0/packages/react/src/menu/root/MenuRoot.test.tsx)에 `See #5152`라는 주석이 있는데, [#5152](https://github.com/mui/base-ui/issues/5152)는 마우스를 빠르게 움직이면 여러 하위 메뉴가 깨진다는 2026년 7월의 이슈예요. 닷새 뒤 [#5153](https://github.com/mui/base-ui/pull/5153)에서 고쳐지면서 이 테스트가 같이 들어왔어요.

모든 테스트가 이슈에서 온 건 아니에요. Base UI의 메뉴 테스트 기록에는 [#5269](https://github.com/mui/base-ui/pull/5269) "[menu] Expand test coverage"처럼 커버리지를 넓히려고 한꺼번에 추가한 커밋도 있어요. 테스트 한 줄을 blame으로 PR까지, 다시 PR에 연결된 이슈까지 따라가면 처음부터 설계한 테스트인지, 보고된 문제를 고치면서 생긴 테스트인지 구분할 수 있어요.

컴포넌트 테스트는 쓰기도 읽기도 쉬워서 어렵지 않다고 생각해 왔어요. 그런데 테스트 한 줄 뒤에 2년 가까이 열려 있던 이슈가 있었어요. 제가 모르던 세계가 있었고, 쉽다고 생각했던 게 부끄러웠어요.

[테스트를 도입할 때](/ko/blog/테스트-코드를-도입하면서-세운-기준) 저는 처음 정한 기대 동작은 `*.spec`에, 그 밖에서 나온 버그는 `*.test`에 따로 두기로 했어요. 이슈를 고치면서 들어온 라이브러리 테스트는 제 `*.test`와 같은 자리에 있었어요. 많이 쓰이는 라이브러리도 처음부터 이 케이스들을 테스트하지는 않았고, 2022년에 보고된 문제는 2026년에야 테스트가 됐어요. 처음부터 빈틈없는 테스트는 라이브러리에도 없었던 거예요.

## 누가, 어떤 상태에서 조작하는지로 케이스를 골라요

케이스를 고를 때는 두 가지를 봐요.

첫째는 그 동작을 누가 정했는지예요. 라이브러리가 정하고 테스트까지 하는 동작은 믿어요. 라이브러리 테스트에서 근거를 찾지 못했는데 제 화면이 기대고 있는 동작, 그리고 제 코드가 직접 정한 동작은 제가 확인해요.

둘째는 누가 상태를 바꾸는지예요. 이 글에서는 이걸 액터라고 부를게요. 메뉴를 쓰는 사람은 포인터, 키보드, 스크린 리더로 조작하고, 컴포넌트를 가져다 쓰는 개발자는 `align`, `disabled` 같은 props로 조작해요. 창이 포커스를 잃거나, 전환 애니메이션이 도는 중이거나, 화면 크기가 바뀌는 것처럼 환경과 시간도 상태를 바꿔요. Radix의 [드롭다운 E2E](https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/e2e/dropdown-menu.spec.ts)도 `given submenu user` 아래를 `when using pointer`와 `When using keyboard`로 나눠 두었어요.

액터를 닫힘, 열리는 중, 열림, 닫히는 중이라는 상태와 짝지으면 확인할 칸이 생겨요. 앞에서 본 이슈를 그 칸에 놓아 봤어요.

| 상태 | 액터 | 확인할 것 | 근거 |
| --- | --- | --- | --- |
| 열림 | 포인터 사용자 | 바깥을 누르면 닫히고, 메뉴 안을 누르면 열려 있고, 트리거를 다시 누르면 닫혀요 | 면접에서 답한 칸 |
| 닫힘 | 스크린 리더 사용자 | 트리거의 `aria-controls`가 화면에 없는 요소를 가리키지 않아요 | Radix #3013, #3242 |
| 열림 | 환경 | 창이 포커스를 잃으면 하위 메뉴까지 닫혀요 | Radix #3257 |
| 닫히는 중 | 포인터 사용자 | 항목 위를 지나가거나 눌러도 반응하지 않아요 | Radix #4195 |
| 열림 | 컴포넌트를 쓰는 개발자 | `align`을 넘기면 그 쪽에 맞춰 열려요 | 제 래퍼가 정한 기본값 |

면접에서 답한 건 이 표의 첫 줄뿐이었어요. 이슈가 들어온 칸은 모두 그 바깥에 있었어요. 스크린 리더 사용자가 닫힌 메뉴를 만나는 칸, 창 포커스처럼 환경이 상태를 바꾸는 칸, 닫히는 중인 메뉴 위로 포인터가 지나가는 칸이었어요.

## 실제 브라우저에서 확인할 범위

Radix와 Base UI는 둘 다 실제 브라우저에서 테스트해요. Radix는 단위 테스트를 Vitest와 jsdom으로 돌리고, Playwright E2E를 따로 둬요. 드롭다운 E2E에는 좁은 화면에서 포인터를 치우면 하위 메뉴가 닫히는지처럼 실제 위치와 포인터 이동이 필요한 케이스가 있어요. Base UI는 같은 테스트를 jsdom과 실제 브라우저에서 모두 돌려요. 1.9.0에서는 기본 `test` 명령이 Chromium에서 실행되고, Vitest의 [브라우저 모드](https://github.com/mui/base-ui/blob/v1.9.0/vitest.shared.mts)로 Firefox와 WebKit에서도 돌릴 수 있어요. 브라우저에서만 의미가 있는 테스트에는 `it.skipIf(isJSDOM)`을 붙여요.

라이브러리는 포커스 이동, 포인터 이벤트, 위치 계산, 전환 애니메이션 같은 브라우저 동작 자체를 만들어요. 그러니 mock이 아니라 실제 브라우저에서 확인해야 해요. 그 위에서 서비스를 만드는 쪽은 같은 동작을 다시 확인할 필요가 없어요. 다만 제 코드가 직접 만든 레이아웃은 jsdom이 계산해 주지 않으니 브라우저에서 확인해야 해요.

처음에는 공용 메뉴에 브라우저 테스트를 네 개 썼어요. 트리거와의 간격, 위험한 항목의 색, 닫히는 동안의 포인터 입력, 공간이 부족할 때의 메뉴 높이였어요. 이 기준으로 다시 보니 간격은 숫자를 넘길 뿐 위치는 Base UI가 계산하고, 색은 스타일이고, 닫히는 동안 포인터를 막는 것도 Base UI였어요. 남은 건 메뉴 높이를 남은 공간(`--available-height`)에 맞추고 안에서 스크롤하게 한 부분이에요. 래퍼가 정한 레이아웃이라 이것만 브라우저에서 확인해요. 화면 높이를 줄여도 메뉴가 화면 안에 들어오는지, 스크롤해서 마지막 항목을 고를 수 있는지를 봐요.

## 공용 메뉴에 적용해 보니

사이드프로젝트의 공용 [`DropdownMenu`](https://github.com/jingeon27/side-project/blob/ac05c293/packages/design-system/src/ui/dropdown-menu/DropdownMenu.tsx)는 Base UI의 Menu를 감싼 래퍼예요. Game Mate의 대화, 댓글, 프로필 메뉴와 에디터 툴바에서 쓰고, 지난 글의 피식 더보기 메뉴는 Base UI를 직접 쓰는 별도 메뉴예요. 공용 메뉴에는 테스트가 두 개 있었어요. 키보드로 열었다가 Escape로 닫으면 트리거로 포커스가 돌아오는지, Enter로 항목을 고르면 동작을 실행하고 닫히는지였어요. 둘 다 Base UI가 이미 테스트하는 동작이었고, 정작 래퍼가 정한 정렬 기본값과 높이 제한은 어디에서도 확인하지 않고 있었어요.

여기에 두 가지를 더했어요. 메뉴 안에서 항목이 아닌 곳을 누르면 열려 있고 바깥을 누르면 닫히는지, 정렬을 넘기지 않으면 시작 쪽에, `align="end"`를 넘기면 끝 쪽에 맞춰 열리는지예요. 메뉴 안쪽을 누르는 경우는 Base UI가 정한 동작이지만, Base UI의 메뉴 테스트에서 이 경우를 다루는 테스트를 이름으로는 찾지 못했어요. 제 화면이 이 동작에 기대고 있어서 직접 넣었어요.

반대로 지운 테스트도 있어요. 처음에는 overflow를 숨긴 카드 안에서 열어도 메뉴가 카드 밖에 그려지는지 확인했어요. 그런데 래퍼에서 Portal을 빼 보니 Base UI가 `<Menu.Portal> is missing` 오류를 냈어요. 메뉴를 카드 밖에 그리는 건 래퍼의 선택이 아니라 라이브러리가 강제하는 구조여서 이 테스트는 지웠어요.

Game Mate에서는 메뉴 항목으로 연 시트를 닫으면 포커스가 메뉴 트리거로 돌아오는지 확인했어요. 그런데 처음 쓴 테스트는 시트의 포커스 복귀를 일부러 꺼도 통과했어요. 시트가 막 열렸을 때는 포커스가 아직 트리거에 있다가 조금 뒤에 시트 안으로 들어가는데, 테스트가 그 전에 Escape를 눌러 시트를 닫고 있었어요. 포커스가 트리거를 한 번도 떠나지 않았으니 복귀를 확인할 수 없었던 거예요. 포커스가 시트 안으로 들어간 걸 확인한 뒤에 닫도록 고쳤어요.

```tsx
await user.keyboard('{Enter}');
const sheet = await screen.findByRole('dialog', { name: '대화내역 삭제' });
await waitFor(() => expect(sheet.contains(document.activeElement)).toBe(true));
await user.keyboard('{Escape}');

await waitFor(() => expect(screen.queryByRole('dialog')).toBeNull());
expect(document.activeElement).toBe(trigger);
```

고친 뒤에는 시트의 포커스 복귀를 끄면 테스트가 실패했어요. 반대로 메뉴의 포커스 복귀를 꺼도 통과했고요. 포커스를 돌려주는 건 메뉴가 아니라 시트였어요.

면접에서 답한 세 가지 중 메뉴 안을 눌러도 닫히지 않는 경우는 피식 메뉴의 테스트에도, 공용 메뉴의 테스트에도 없었어요. 이번에 공용 메뉴의 테스트에 넣었어요.
