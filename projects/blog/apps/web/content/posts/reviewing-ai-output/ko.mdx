업무에서는 AI가 만든 변경분을 diff로 읽고, 기존 동작과 맞는 구현인지 판단했어요. 사이드프로젝트에서는 기능과 아키텍처 정도를 정한 뒤 구현과 테스트를 에이전트에게 맡겼어요. 나온 서비스를 직접 써 보면서 원하는 모습과 다른 부분을 설명하고, 다시 고친 결과를 확인했어요.

## 실서비스에서는 diff로 변경을 검토했어요

운영 중인 서비스에서는 버그로 사용자가 하려던 일이 막히지 않는지 먼저 봤어요. 잘 쓰던 기능이 갑자기 달라지거나 같은 문제가 반복되면 서비스와 만드는 사람에 대한 신뢰도 잃을 수 있어서, 변경된 구현을 이해하고 확인하는 일을 중요하게 생각했어요.

업무에서 다루던 전체 코드베이스와 기존 동작을 알고 있었어요. 그래서 AI가 만든 diff를 읽으면 어떤 동작을 바꿨는지, 기존 코드와 어떻게 이어지는지 이해할 수 있었어요. 변경된 코드를 보면서 잘된 구현인지, 잘못된 구현인지 판단했어요.

구현과 테스트는 에이전트가 진행했고, 저는 diff를 읽으며 고쳐야 할 부분과 추가로 확인할 조건을 피드백했어요. 에이전트가 검증한 결과를 보고 실제 화면에서도 동작을 확인했어요. 이 과정은 [「저는 코드를 읽어요」](/ko/blog/저는-코드를-읽어요)에 더 자세히 적었어요.

## 사이드프로젝트에서는 써 보면서 피드백했어요

피식과 Game Mate에서는 에이전트가 화면 배치와 세부 구현 순서를 정하도록 두었어요. 완성된 화면을 직접 써 보면서 요청한 기능이 있는지, 다음 행동을 찾을 수 있는지, 쓰기에 불편한 부분은 없는지 확인했어요. 주로 이렇게 결과물을 써 보고 피드백하는 블랙박스 방식으로 검토했어요.

피식의 첫 홈에는 그룹 목록이 먼저 나왔어요. 저는 들어오자마자 가입한 그룹의 사진을 보고 싶어서, 그룹 목록은 마이페이지로 옮기고 홈에는 사진을 보여 달라고 했어요. 긴 안내가 사진을 가리면 문구를 줄이게 했고, 스토리 기능이 없는데 붙어 있던 테두리는 지워 달라고 했어요.

처음 요청할 때 정하지 않았던 동작도 써 보면서 추가했어요. 익명으로 쓴 글은 회원가입 뒤에도 이어 볼 수 있게 하고, 가입 전에 로그아웃하면 어떻게 되는지 알려 달라고 했어요. 요청이 실패한 화면에서는 입력한 내용을 남기고 다시 시도할 수 있게 해 달라고 했고요. 수정한 결과를 다시 써 보고 빠진 동작이 있으면 설명했어요.

코드는 폴더와 모듈을 어떻게 나눴는지, 어떤 역할을 어디에 두었는지 훑어봤어요. 세부 구현과 테스트 작성, 실행은 에이전트가 담당했어요. 저는 에이전트의 검증 보고를 받고 결과물을 써 보며 수정할 부분을 요청했어요.

같은 구조 문제를 여러 번 고치게 되면 그 피드백을 skill이나 lint 규칙에 반영하게 했어요. 다음 작업에서도 같은 설명을 반복하는 일을 줄이고 싶었어요.

## 인프라와 도구 설정도 에이전트에게 맡겼어요

인프라 구성과 AWS CLI, 관측 도구의 연결과 설정도 에이전트에게 맡겼어요. 필요한 계정과 도구에 접근할 수 있도록 최대한 권한을 주고 직접 설정하게 했어요.

인프라는 Terraform으로 정의하는 IaC 방식으로 구성했어요. AWS 리소스를 코드로 만들고 설정하는 작업과 실제 적용까지 에이전트에게 맡겨, 제가 콘솔에서 직접 처리할 일을 최소화했어요.

설정을 마친 뒤에는 AWS CLI로 배포에 쓰는 인스턴스의 상태를 확인하게 했어요. Amplitude와 Sentry는 MCP로 연결하고, 실제 계정에서 어떤 행동이 이벤트로 남았는지와 어떤 오류가 기록됐는지 조회하게 했어요. 저는 설정과 조회 결과를 보고받고, 더 확인하거나 바꿀 부분을 다시 요청했어요.

## 글과 화면의 문구는 마지막까지 직접 읽어요

블로그 글은 제가 겪은 상황과 전달하고 싶은 내용을 먼저 설명하고 AI에게 초안을 맡겨요. 초안이 나오면 순서를 바꾸거나 빠진 내용을 보태고, 제 의도와 다른 문장은 다시 써 달라고 해요.

제가 하지 않은 일을 했다고 쓴 부분은 먼저 고쳐요. 이 글의 초안에도 사이드프로젝트의 세부 로직과 테스트를 제가 직접 검토한 것처럼 쓴 부분이 있었어요. 실제로는 결과물을 써 보고 코드 구조를 훑으며 피드백했고, 구현과 세부 테스트는 에이전트가 맡았다고 고쳤어요.

제가 어떤 동작을 바꿔 달라고 했는지 적으려던 글이 좋은 개발자의 태도를 설명하는 문장으로 바뀌기도 해요. 그럴 때는 실제로 불편했던 동작과 수정을 요청한 이유를 다시 적어 달라고 피드백해요.

같은 말이 반복되거나, 앰대시로 설명을 덧붙이거나, 나열 기호로 단어를 계속 이어 붙인 부분도 고쳐 달라고 해요. 길어진 문장은 나누고, 나열한 단어는 조사와 쉼표로 풀어 쓰게 했어요. 서로 관계없는 내용이 한 문장에 묶여 있으면 그 문장은 빼거나 따로 쓰게 했고요.

[Caperton Gillett](https://capertongillett.com/blog/its-not-a-surefire-hint-for-spotting-ai-writing-its-annoying/)도 반복되는 표현을 지적하며 “사람이 썼든 AI가 생성했든, 반복되는 표현과 부자연스럽게 꼬인 문장은 좋지 않은 글이다”라고 썼어요.

![앰대시와 가운데점으로 나열한 문장을 이유와 행동이 이어지는 문장으로 고친 전후 비교](/images/posts/reviewing-ai-output/01-prose-feedback.png)

_기호를 줄이고 문장을 이어 쓰는 피드백을 보여 주려고 재구성한 예시예요._

화면 문구는 실제 화면에 띄워 놓고 읽었어요. 피식 마이페이지에 있던 '브라우저 세션으로 유지돼요'라는 안내만으로는 로그아웃 뒤에 기록을 다시 볼 수 있는지 알기 어려웠어요. 로그아웃하면 익명 프로필과 기록에 다시 접근할 수 없다고 알리고, 계속 쓰려면 먼저 회원가입하라고 안내하게 했어요. 문구가 길어져 다른 내용을 가리지 않는지, 버튼 옆에서 읽었을 때 뜻이 분명한지도 봤어요.

![게시글과 프로필, 사진과 동영상을 기호로 나열한 화면 안내를 사용자가 할 행동으로 풀어 쓴 예시](/images/posts/reviewing-ai-output/02-interface-copy-feedback.png)

_화면 안내에서도 나열 기호를 조사로 풀어 쓰는 예시예요. 문구를 비교하기 위한 도해이며 실제 서비스 화면 캡처는 아니에요._

수정본을 받으면 처음부터 문장 하나씩 다시 읽어요. 제가 하려던 말이 빠졌거나 같은 내용이 되풀이되면 다시 피드백해요. 경험을 다 설명한 뒤에 불필요한 문단이 붙어 있으면 그 문단은 빼 달라고 해요.
