<Summary>

병원 리뷰를 여러 단계로 나눠 쓰는 폼을 전역 스토어에서 React Hook Form과 Zod로 옮기면서 시술 선택 UI도 다시 붙였어요. 시트를 닫으면 선택을 취소하고, 확인할 때만 폼에 넣도록 바꾼 과정이에요.

</Summary>

![별점 선택부터 내용 작성과 확인까지 이어지는 리뷰 폼을 그린 일러스트](/images/covers/review-form-funnel.png)

시술 선택 시트를 리뷰 폼에 처음 붙였을 때는 확인을 누르지 않고 닫아도 고른 시술이 폼에 남았어요. 시트를 닫는 것이 취소가 되려면 고르는 중인 값부터 폼과 나눠야 했어요. 배포 전에 고친 문제예요. 다만 이 시트에 오기까지 리뷰 작성 화면은 여러 번 바뀌었어요.

병원에 다녀온 사용자가 리뷰를 남기는 화면이에요. 사용자는 방문 인증용 영수증을 올리고, 시술과 결제 정보를 넣은 뒤, 별점과 사진, 리뷰 내용을 작성해요. 이렇게 입력을 한 화면에 늘어놓지 않고 단계별 화면으로 나눠 차례로 지나가게 하는 폼을 퍼널(funnel) 폼이라고 불러요. 깔때기를 지나듯 단계를 통과한다는 뜻이에요. 단계가 나뉘면 입력칸 말고도 정할 일이 생겨요. 앞 단계의 값을 어디에 보관할지, 어느 단계에서 어떤 값을 검사할지, 다음 단계로 언제 보낼지를 정해야 해요.

시작은 필드를 고치는 일이었어요. 필드 하나를 바꾸려면 값을 저장하는 액션부터 오류 문구, 다음 단계로 넘어가는 조건까지 따라가야 했어요. 각 입력 컴포넌트가 자기 필드 외에 전역 스토어를 바꾸고 검증하는 방법도 알고 있었거든요.

그래서 입력값을 React Hook Form(RHF)으로 옮기고 검증을 Zod에 모았어요. RHF는 폼의 값과 오류를 관리하는 라이브러리이고, Zod는 값의 조건을 스키마로 적어 실제 값을 검사하는 라이브러리예요. 단계 이동은 퍼널 훅에 남겼어요. 이 리팩터링이 먼저였고, 시술 선택 UI는 그 뒤로 두 번 더 바뀌었어요.

## 전역 스토어 두 개

기존에는 입력값과 현재 단계가 서로 다른 Zustand 스토어에 있었어요. Zustand는 컴포넌트 바깥에 스토어를 만들어 어느 컴포넌트에서든 읽고 바꾸게 해 주는 전역 상태 라이브러리예요. draft를 바꾸는 스토어와 step을 움직이는 스토어가 따로 있었고, step에 따라 입력 화면을 골라 그렸어요.

```tsx
type DraftStore = {
  draft: ReviewDraft;
  setField: <K extends keyof ReviewDraft>(
    key: K,
    value: ReviewDraft[K],) => void;
};

type StepStore = {
  step: number;
  moveForward: () => void;
  moveBack: () => void;
};
```

```tsx
switch (step) {
  case 1:
    return <ProofStep />;
  case 2:
    return <DetailsStep />;
  default:
    return <FeedbackStep />;
}
```

임시 저장은 별도 API가 하고 있었어요. 이 화면에서 작성 중인 값이나 현재 단계를 다른 화면이 쓸 필요는 없었어요. 이전 단계의 값을 보관하는 일도 페이지 안의 폼 인스턴스로 처리할 수 있었어요.

처음에는 전부 하나의 폼으로 합치려고 했어요. 그런데 단계마다 마운트되는 필드와 검증 시점이 달랐어요. 스키마 하나로 전체를 검사하면 사용자가 아직 입력하지 않은 다음 단계의 필드 때문에 지금 단계가 막혀요. 그래서 RHF는 값과 필드를 관리하고 Zod는 검증하며, @use-funnel/core를 감싼 공용 훅은 이동할 단계만 정하게 했어요. @use-funnel/core는 퍼널의 단계와 단계별 값(context), 이동 이력을 관리하는 라이브러리예요.

전체 값을 보관하는 폼과 각 단계의 폼을 뒀어요. 단계 폼이 통과하면 그 값을 전체 폼에 합쳐 다음 단계에 넘겨요. 대신 단계 사이에 값을 합치고 `reset`하는 연결이 남아요.

## `superRefine`은 따라오지 않았어요

각 단계에서는 그 단계의 값만 검사하고, 최종 제출에서는 전체 값을 다시 검사하는 구조가 이상적이에요. 단계별 스키마는 나눴지만 전체 스키마를 조립하는 쪽에는 문제가 남았어요. 단계별로 필요한 필드를 나눈 스키마는 아래와 같아요. 이름을 바꾸고 주요 필드와 추가 검증만 남겼어요.

```typescript
import { z } from 'zod';

export const ProofStepSchema = z.object({
  proofFiles: z.array(UploadSchema).min(1).max(5),
});

export const DetailsStepSchema = z
  .object({
    visibilityFlag: z.boolean(),
    items: z.array(ItemSchema).min(1).max(5),
    quoteFieldEnabled: z.boolean().optional(),
    quotedAmount: z.number().optional(),
    paidAmount: z.number().min(1),
    amountFlag: z.boolean().optional(),
    receivedBenefitInfo: z.boolean(),
    missingBenefitReason: z
      .object({
        value: z.enum(MISSING_INFO_REASONS),
        description: z.string(),
      })
      .optional()
      .nullable(),
  })
  .superRefine((data, ctx) => {
    if (data.quoteFieldEnabled && (!data.quotedAmount || data.quotedAmount <= 0)) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['quotedAmount'],
        message: '금액을 입력해 주세요.',
      });
    }

    if (!data.receivedBenefitInfo && !data.missingBenefitReason) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['missingBenefitReason'],
        message: '안내받지 못한 이유를 입력해 주세요.',
      });
    }
  });

export const FeedbackStepSchema = z.object({
  attachments: z.array(UploadSchema),
  ratings: z.array(
    z.object({
      criterion: z.enum(RATING_CRITERIA),
      score: z.number().min(0).max(2),
    }),
  ),
  body: z.string().min(50).max(500),
  wouldRecommend: z.boolean(),
});

export const SubmissionSchema = z
  .object({
    // 방문 인증 단계에서는 min(1)을 쓰지만 전체 스키마에서는 필수가 아니다.
    proofFiles: z.array(UploadSchema).max(5),
  })
  .extend(DetailsStepSchema._def.schema.shape)
  .extend(FeedbackStepSchema.shape);
```

두 번째 단계는 조건에 따라 견적 금액이나 혜택을 안내받지 못한 이유를 요구해요. 필드 하나만 봐서는 판단할 수 없는 조건이라, 객체 전체를 보고 오류를 더하는 `superRefine`을 `DetailsStepSchema`에 붙였어요. 그런데 이 스키마는 객체 스키마를 한 겹 감싼 ZodEffects가 되어 `.shape`(객체의 필드 정의)를 바로 꺼낼 수 없었어요.

전체 `SubmissionSchema`는 공개 API가 아닌 내부 속성 `_def.schema`로 안쪽 객체의 필드를 가져와요. 필드만 복사하므로 `superRefine`은 따라오지 않아요. 단계에서는 조건부 검증이 되지만, 전체 스키마에는 같은 규칙이 없는 상태예요. Zod 내부 구조에 기대는 코드도 여기에 남아 있어요.

`proofFiles`의 최소 개수가 다른 것은 별도 이유가 있어요. 방문 인증 단계에서는 증빙을 하나 이상 올려야 하지만 그 단계를 건너뛰는 경로도 있어요. 그래서 전체 스키마에는 `min(1)`을 넣지 않았어요.

## 금액 입력은 값과 변경 함수만 연결해요

전에는 입력 컴포넌트가 스토어 액션과 검증을 함께 알고 있었어요. 금액 입력을 줄이면 이런 모양이에요. 당시 코드를 옮긴 것은 아니고, 설명하려고 다시 적은 예시예요.

```tsx
// 줄인 예시예요. 훅과 함수 이름은 설명하려고 붙였어요.
function AmountField() {
  const paidAmount = useDraftStore((state) => state.draft.paidAmount);
  const setField = useDraftStore((state) => state.setField);
  const errorMessage = validatePaidAmount(paidAmount);

  return (
    <NumericInput
      value={paidAmount}
      errorMessage={errorMessage}
      onChange={(value) => setField('paidAmount', value)}
    />
  );
}
```

옮긴 뒤에는 값과 변경 함수만 폼에 이어요.

```tsx
function AmountField() {
  const { control } = useFormContext<DetailsStepValues>();

  return (
    <Controller
      control={control}
      name="paidAmount"
      render={({ field: { value, onChange } }) => (
        <NumericInput
          value={value}
          onChange={normalizeNumericInput(onChange)}
        />
      )}
    />
  );
}
```

`Controller`는 직접 만든 입력 컴포넌트를 RHF에 연결하는 컴포넌트예요. 여기서는 `NumericInput`의 value와 `onChange`를 RHF에 이어요. 금액 조건은 단계 스키마가 보므로, 입력 컴포넌트가 Zustand 액션을 부르거나 검증 함수를 따로 실행하지 않아요.

## 모바일에서 시술을 여러 개 고르려면

`items`는 시술을 1개에서 5개까지 담고 중복은 허용하지 않아요. 이 배열과 검증 조건은 유지한 채 선택 UI를 바꿨어요. 달라진 것은 고르는 도중의 값을 어디에 두느냐였어요.

시술 선택 UI는 두 번 바뀌었어요. 드롭다운 안 복수 선택은 2차 리팩터링에서, Bottom Sheet는 디자인 시스템 적용에서 구현했고, 폼 값이 바뀌는 시점을 '고르는 즉시'에서 '확인할 때'로 옮겼어요. 아래 그림은 세 시기의 코드를 바탕으로 다시 그렸고, 병원 이름과 시술 이름은 예시예요.

![시술 선택 UI는 두 번 바뀌었어요. 드롭다운 안 복수 선택은 2차 리팩터링에서, Bottom Sheet는 디자인 시스템 적용에서 구현했고, 폼 값이 바뀌는 시점을 '고르는 즉시'에서 '확인할 때'로 옮겼어요.](/images/posts/review-form-funnel/01.png)

처음에는 동료가 만든 키워드 자동완성 드롭다운을 썼어요. 입력칸을 누르면 아래로 목록이 열리고, 하나를 고르면 목록이 닫히며 검색어가 비워졌어요. 선택한 시술은 아래에 칩으로 쌓였어요. 처음 폼을 옮길 때는 이 UI를 `Controller`로 감싸는 데 그쳤어요.

직접 모바일에서 써 보니 시술마다 다시 누르고 검색해야 했어요. 키패드가 올라오면 아래로 펼친 목록을 가리고, 여러 개를 고를 수 있는데 하나를 고르면 목록이 바로 닫히고, 이미 고른 항목도 목록에서 구분되지 않았어요. 사용자 데이터로 확인한 것은 아니고 직접 써 보고 적은 판단이에요. 이 불편을 Jira에 적어 PO에게 공유했고, 기획과 디자인 담당자들은 이어진 리팩터링에 넣기로 했어요.

드롭다운은 남기되 그 안에서 복수 선택을 하고, 체크와 칩으로 고른 항목을 표시하며, 입력칸이 헤더 바로 아래로 오도록 스크롤하는 방향이었어요. 버튼에 붙어 뜨는 패널을 만드는 Radix Popover와 검색 가능한 목록을 만드는 cmdk로 구현해 운영에 반영했어요. 그때는 항목을 누르는 즉시 `useFieldArray`의 `append`와 `remove`가 폼을 바꿨어요. `useFieldArray`는 RHF에서 배열 모양의 필드를 다루는 훅이에요.

나중에 디자인 시스템 시안에서는 선택 UI가 Bottom Sheet로 바뀌었어요. 화면 아래에서 올라와 지금 화면 위를 덮는 패널이에요. 앞선 드롭다운 개선과는 다른 작업이었고, 동료가 만든 공용 시트를 리뷰 폼에 붙이는 것은 제가 맡았어요.

## 닫아도 선택이 남았어요

처음에는 드롭다운처럼 시트에서도 폼을 바로 바꿨어요. 그러면 확인하지 않고 닫아도 선택이 이미 반영돼요. 닫힌 뒤 원래 값으로 돌리는 처리를 덧대다가, 다음 날 시트가 임시 선택을 갖고 확인할 때만 넘기도록 바꿨어요. 이 두 방식은 모두 배포 전에 거친 구현이에요. 대신 임시 선택은 스키마가 보지 못하니, 개수 제한을 시트 안에서 따로 검사해야 했어요.

`ItemsField`와 `ItemPickerSheet`는 공개용 가명이에요. 필드가 시트를 열고 시트가 확인값을 넘기는 부분을 남기면 다음과 같아요.

```tsx
// FieldBox는 입력칸 모양의 상자(가명)다. 필드 이름도 가명이다.
// openBottomSheet·closeBottomSheet는 공용 시트의 전역 스토어를 여닫는 함수다.
function ItemsField() {
  const { control } = useFormContext<DetailsStepValues>();
  const { fields: items, replace, remove } = useFieldArray({ control, name: 'items' });

  const openPicker = () =>
    openBottomSheet({
      detent: 'content-height',
      fullContents: true,
      children: <ItemPickerSheet initialItems={items} onConfirm={replace} />,
    });

  return (
    <FieldBox onClick={openPicker}>
      {items.map(({ itemId, itemName }, index) => (
        <Tag key={itemId} text={itemName} onClose={() => remove(index)} />
      ))}
    </FieldBox>
  );
}

function ItemPickerSheet({ initialItems, onConfirm }: ItemPickerSheetProps) {
  const [draft, setDraft] = useState(initialItems);

  const toggle = (item: DetailsStepValues['items'][number]) => {
    if (draft.some(({ itemId }) => itemId === item.itemId)) {
      setDraft((prev) => prev.filter(({ itemId }) => itemId !== item.itemId));
      return;
    }
    if (draft.length >= 5) {
      toast.warning('시술은 최대 5개까지 선택 가능해요.');
      return;
    }
    setDraft((prev) => [...prev, item]);
  };

  return (
    <div>
      {/* 검색 입력, 체크 목록(행을 누르면 toggle), 고른 항목 요약과 초기화(setDraft([])) */}
      <Button
        onClick={() => {
          onConfirm(draft);
          closeBottomSheet();
        }}
      >
        확인
      </Button>
    </div>
  );
}
```

공용 시트는 `openBottomSheet`가 받은 요소를 전역 스토어에 넣고 앱 최상단 Provider에서 그려요. `FormProvider`의 자식으로 열리는 게 아니어서 시트 안에서는 `useFormContext`를 쓸 수 없어요. `useFormContext`는 자기 위쪽의 `FormProvider`에서 폼을 찾는 훅이거든요. 그래서 필드가 `useFieldArray`에서 읽은 `items`와 `replace`를 props로 넘겨요. `replace`는 필드 배열 전체를 넘긴 값으로 한 번에 바꾸는 함수예요.

시트는 열릴 때의 `items`로 `draft`를 만들어요. 행을 누를 때는 `draft`만 바뀌고, '확인'을 눌러야 `replace`가 폼 배열을 바꿔요. 딤(시트 뒤를 어둡게 덮는 영역)을 누르거나 아래로 끌어 닫으면 넘기는 값이 없어요. 닫힘 애니메이션 뒤 내용이 언마운트돼 `draft`도 사라지고, 다시 열면 현재 폼 값에서 새로 시작해요.

필드의 칩을 지우는 ×는 전파를 막아 시트를 열지 않고 `remove`만 실행해요. 필드에서 바로 지우는 동작과 시트 안에서 선택을 취소하는 동작을 구분한 거예요.

열 때, 고르는 동안, 확인할 때, 닫을 때를 나란히 놓으면 흐름이 더 잘 보여요. 시트는 열 때의 값으로 임시 선택을 만들고, 확인할 때만 `replace`로 필드에 넣어요. 닫으면 아무것도 넘기지 않아요.

## 5개 제한은 어느 값을 봐야 할까

규칙은 두 곳에 있어요. 시트는 임시 선택이 5개면 다음 선택을 토스트로 막아요. 같은 시술을 다시 누르면 빼므로 중복도 생기지 않아요. 스키마는 확인해서 폼에 들어온 `items`를 `min(1)`, `max(5)`와 중복 검사로 봐요. 중복 검사는 앞의 예제에서는 생략했어요. 이 필드에는 별도 오류 문구가 없어서 실패하면 '다음' 버튼만 꺼져요.

시트를 develop에 처음 합쳤을 때는 제한 조건이 `draft` 대신 `initialItems.length`를 보고 있었어요. 열 때 5개 미만이었다면 그 안에서 계속 고를 수 있고, 확인한 뒤에야 '다음'이 이유 없이 꺼질 수 있었어요. 다음 날 운영에 나가기 전에 `draft` 기준으로 고쳤어요. 지금 고르고 있는 개수를 세야 했는데 폼에 들어 있던 개수를 세고 있었던 거예요.

## 단계 폼도 확인한 뒤에 합쳐요

필드 안에서 임시 값을 따로 들고 있다가 확인할 때 합치는 이 모양은 단계 폼에서 한 단계 크기로 되풀이돼요. 해당 단계에서 바꾼 값을 검증한 다음에 전체 작성값에 합쳐요.

```tsx
// useSchemaForm·useStepFunnel·StepForm은 공용 폼 훅, 퍼널 훅, 단계 폼 래퍼의 공개용 가명이다.
// needsProof는 방문 인증 단계부터 시작하는 경우, isVisited는 예약이 방문 완료 상태인 경우다.
const form = useSchemaForm({
  schema: SubmissionSchema,
  defaultValues: savedDraft
    ? mapResponseToDraft(savedDraft.data)
    : emptyDraft,
});

const flow = useStepFunnel<Record<'proof' | 'details' | 'feedback', object>>({
  initial: {
    step: needsProof ? 'proof' : 'details',
    context: {},
  },
  id: 'public-example-flow',
});

const mergeAndReset = useCallback(
  (callback: (data: ReviewDraft) => void) =>
    <T extends Partial<ReviewDraft>>(stepValues?: T) => {
      const mergedDraft = {
        ...form.formState.defaultValues,
        ...stepValues,
      } as ReviewDraft;

      form.reset(mergedDraft);
      callback(mergedDraft);
    },
  [form],
);

const moveToStep = useCallback(
  (step: typeof flow.step) =>
    mergeAndReset(() => flow.history.replace(step)),
  [mergeAndReset, flow],
);

const confirmSubmission = mergeAndReset((data) =>
  openConfirmDialog({
    primaryAction: {
      text: '제출',
      onConfirm: () => submitDraft(data),
    },
  }),
);

return (
  <flow.Render
    proof={() => (
      <StepForm
        schema={ProofStepSchema}
        defaultValues={form.formState.defaultValues}
        onComplete={moveToStep('details')}
      >
        <ProofStep />
      </StepForm>
    )}
    details={() => (
      <StepForm
        schema={DetailsStepSchema}
        defaultValues={form.formState.defaultValues}
        onBack={needsProof ? moveToStep('proof') : undefined}
        onComplete={moveToStep('feedback')}
      >
        <DetailsStep />
      </StepForm>
    )}
    feedback={() => (
      <StepForm
        schema={FeedbackStepSchema}
        defaultValues={form.formState.defaultValues}
        onBack={moveToStep('details')}
        onComplete={confirmSubmission}
      >
        <FeedbackStep isVisited={isVisited} />
      </StepForm>
    )}
  />
);
```

`StepForm`은 각 단계에 `mode: 'all'`인 폼을 만들어요. `mode`는 검증을 언제 실행할지 정하는 옵션이고, `'all'`은 값이 바뀔 때와 입력칸에서 포커스가 빠질 때 모두 검증해요. 단계 스키마를 통과한 값은 상위 RHF의 `defaultValues`(폼의 초기값)에 합친 뒤 `reset`해서 다음 단계의 초기값으로 써요. `reset`은 넘긴 값으로 폼의 현재 값과 `defaultValues`를 함께 다시 정하는 함수예요.

퍼널은 `history.replace`로 이동할 단계만 바꿔요. `history.push`는 이력을 쌓으며 다음 단계의 context를 함께 넘기고, `replace`는 이력을 쌓지 않고 현재 단계를 덮어써요. 폼 값은 퍼널 context에 넣지 않고 `history.push`로 단계별 값을 쌓지도 않아요.

마지막 단계도 값을 합쳐 확인 대화상자와 API 요청에 넘겨요. 다만 여기서 `SubmissionSchema.parse`를 다시 실행하지는 않아요. 앞 단계에서 통과한 값이 계속 유효하다고 전제하므로, 최종 제출에서 모든 단계의 조건을 다시 검사하는 처리는 빠져 있어요.

## 수정 화면의 `defaultValues`

이미 쓴 리뷰를 고칠 때는 폼이 저장된 내용으로 채워져 있어야 해요. 수정할 리뷰가 있으면 `savedDraft`를 폼 값으로 바꿔 `defaultValues`에 넣어요. RHF는 이 값을 폼을 만들 때 캐시하므로, 빈 값으로 폼을 먼저 만든 뒤 응답만 늦게 받아서는 채워지지 않아요.

그래서 첫 렌더 전에 응답이 준비되도록 했어요. 서버 페이지가 예약과 리뷰를 미리 조회하고 `HydrationBoundary`로 캐시를 넘겨요. `prefetchQuery`가 서버에서 React Query 캐시를 채우고, `dehydrate`가 그 캐시를 브라우저로 보낼 수 있는 형태로 바꾸면, `HydrationBoundary`가 브라우저 쪽 캐시에 넣어 줘요. 클라이언트는 같은 옵션의 `useQueries`로 그 응답을 읽어요.

```tsx
// 컴포넌트, 쿼리 옵션, 경로 파라미터 이름은 공개용 가명이다.
// 서버 페이지. 예약 id와 리뷰 id가 모두 있는 경로이고, 다른 경로는 있는 id만 미리 요청한다.
async function ReviewEditorRoute({ params }: EditorRouteProps) {
  const { sourceId, draftId } = await params;
  const queryClient = getQueryClient();

  await Promise.all([
    queryClient.prefetchQuery(sourceByIdQuery(Number(sourceId))),
    queryClient.prefetchQuery(draftByIdQuery(Number(draftId))),
  ]);

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ReviewEditorPage />
    </HydrationBoundary>
  );
}

// 클라이언트 템플릿
function ReviewEditorPage() {
  const { sourceId, draftId } = useParams<EditorRouteParams>();
  const [{ data: sourceInfo }, { data: savedDraft }] = useQueries({
    queries: [
      sourceByIdQuery(toOptionalNumber(sourceId)),
      draftByIdQuery(toOptionalNumber(draftId)),
    ],
  });

  const form = useSchemaForm({
    schema: SubmissionSchema,
    defaultValues: savedDraft
      ? mapResponseToDraft(savedDraft.data)
      : emptyDraft,
  });

  // 퍼널과 단계 폼은 앞 절의 코드와 같다.
}
```

서버가 요청 완료를 기다리고 렌더링하므로, 조회에 성공했다면 클라이언트의 첫 렌더에는 수정할 데이터가 캐시에 있어요. 그 값으로 만든 수정용 입력이 처음 `defaultValues`가 돼요. 이 화면은 클라이언트에서 Suspense로 응답을 기다리는 방식은 아니에요.

조회에 실패하면 이야기가 달라져요. `prefetchQuery`는 실패를 호출부로 던지지 않고, 실패한 조회는 기본 `dehydrate` 결과에서도 빠져요. 그러면 첫 렌더의 `savedDraft`가 비어 있어 `emptyDraft`가 `defaultValues`가 되고, 나중에 클라이언트 조회가 성공해도 폼은 이 초기값을 유지해요. 이 예제는 그 경로를 처리하지 않아요. 수정에 꼭 필요한 데이터라면 서버에서 `fetchQuery`로 오류를 드러내거나, 조회 성공을 확인한 뒤에 폼을 렌더해야 해요. 자세한 동작은 [TanStack Query의 서버 렌더링 오류 처리](https://tanstack.com/query/latest/docs/framework/react/guides/ssr#error-handling)에 나와 있어요.

## 느낀 점

두 Zustand 스토어를 없앤 것보다 각 단계가 자기 필드와 검증만 알게 된 점이 더 쓸모 있었어요. 다만 단계 사이에 `defaultValues`를 합치고 `reset`하는 연결은 남았어요.

입력 타입에도 모호한 부분이 남아 있어요. 공개 여부가 불리언이라 API에 보낼 때 숨김과 공개 enum으로 바꿔요. 다른 요청 필드 변환을 제외하면 이 부분은 아래와 같아요.

```typescript
function toSubmissionRequest(form: ReviewDraft): SubmissionRequest {
  const { visibilityFlag, ...rest } = form;

  return {
    ...rest,
    visibilityFlag: visibilityFlag
      ? VISIBILITY.Hidden
      : VISIBILITY.Public,
  };
}
```

`true`가 공개인지 숨김인지 이 변환을 읽어야 알 수 있어요. 폼에서 `PUBLIC`이나 `HIDDEN`을 직접 쓰면 의미가 드러나겠지만, 현재는 이 불리언을 유지하고 있어요. 스토어를 폼으로 옮긴 것과 별개로 남은 해석이에요.

퍼널 쪽도 다시 볼 만해요. 퍼널 context는 비어 있고 `replace`로 화면만 바꾸고 있어요. 사진처럼 브라우저 객체가 들어간 값은 URL 직렬화만으로 이동 이력을 복원하기도 어려워요. 단계가 셋이라는 이유만으로 퍼널 라이브러리가 필요한 것은 아니고, 로컬 상태나 명시적인 리듀서가 더 단순한지도 비교해 봐야 해요. 값은 폼이 갖고 화면만 바꾸는 이 구조에 퍼널 라이브러리가 꼭 필요했을까요?
