리뷰 작성 화면에 필드 하나를 추가하려면 값, 오류 문구, 다음 단계로 넘어가는 조건을 여러 파일에서 함께 바꿔야 했어요. 화면은 세 단계로 이어져요.

1. 방문 인증을 위한 영수증 업로드
2. 시술과 결제 정보 입력
3. 별점, 사진, 리뷰 내용 작성

입력값과 현재 단계가 각각 다른 Zustand 스토어에 있었어요. 각 입력 컴포넌트도 검증과 스토어 액션을 함께 알고 있어서, 필드 하나를 바꿀 때 따라가야 할 곳이 많았어요.

입력값은 React Hook Form, 검증은 Zod, 단계 이동은 퍼널 훅으로 옮겼어요. 다만 전체 스키마에 2단계 추가 검증이 빠져 있고, 최종 제출 직전의 전체 검증도 남은 과제예요.

## 값과 단계를 전역 스토어 두 개가 나눠 들고 있었어요

기존 구조는 이랬어요.

```tsx

    key: K,

type StepStore = {

```

```tsx

  case 1:
    return <ProofStep />;

    return <DetailsStep />;

```

그런데 화면 전환과 작성 중인 값이 앱 전역에서 공유돼야 할 이유는 없었어요. 임시 저장은 별도 API가 담당하고 있었고, 화면 안에서 이전 단계 값을 보존하는 일은 RHF 폼 인스턴스 사이에서 처리할 수 있었어요.

## 하나의 큰 폼으로 합치려다 책임만 나눴어요

그럼 스토어를 걷어내고 무엇으로 나눠야 할까요? 처음에는 하나의 거대한 폼으로 합치려 했어요. 실제로는 단계마다 마운트되는 필드와 검증 시점이 달랐어요. 그래서 세 책임만 분리했어요.

입력값과 필드의 생명주기는 React Hook Form(RHF), 검증 규칙은 Zod, 단계 이동은 @use-funnel/core를 감싼 공용 퍼널 훅이 맡아요.

## 단계 스키마는 나눴지만 전체 스키마는 필드만 옮겨 담아요

각 단계에서는 해당 단계의 값만 검증하고, 최종 제출에서는 전체 값을 다시 검증하는 구조가 이상적이에요. 현재 구현은 단계별 스키마를 분리했지만, 전체 스키마를 조립하는 부분에는 기술 부채가 남아 있어요.

아래 코드는 현재 스키마에서 핵심 필드와 추가 검증만 추린 거예요. 사용자 정의 스키마와 필드 이름은 공개용 가명이에요.

```typescript
import { z } from 'zod';

export const ProofStepSchema = z.object({
  proofFiles: z.array(UploadSchema).min(1).max(5),
});

export const DetailsStepSchema = z
  .object({
    visibilityFlag: z.boolean(),
    items: z.array(ItemSchema).min(1).max(5),
    quoteFieldEnabled: z.boolean().optional(),
    quotedAmount: z.number().optional(),
    paidAmount: z.number().min(1),
    amountFlag: z.boolean().optional(),
    receivedBenefitInfo: z.boolean(),
    missingBenefitReason: z
      .object({
        value: z.enum(MISSING_INFO_REASONS),
        description: z.string(),
      })
      .optional()
      .nullable(),
  })
  .superRefine((data, ctx) => {
    if (data.quoteFieldEnabled && (!data.quotedAmount || data.quotedAmount <= 0)) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['quotedAmount'],
        message: '금액을 입력해 주세요.',
      });
    }

    if (!data.receivedBenefitInfo && !data.missingBenefitReason) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['missingBenefitReason'],
        message: '안내받지 못한 이유를 입력해 주세요.',
      });
    }
  });

export const FeedbackStepSchema = z.object({
  attachments: z.array(UploadSchema),
  ratings: z.array(
    z.object({
      criterion: z.enum(RATING_CRITERIA),
      score: z.number().min(0).max(2),
    }),
  ),
  body: z.string().min(50).max(500),
  wouldRecommend: z.boolean(),
});

export const SubmissionSchema = z
  .object({
    // 방문 인증 단계에서는 min(1)을 쓰지만 전체 스키마에서는 필수가 아니다.
    proofFiles: z.array(UploadSchema).max(5),
  })
  .extend(DetailsStepSchema._def.schema.shape)
  .extend(FeedbackStepSchema.shape);
```

두 번째 단계 스키마의 superRefine은 해당 단계 폼에서 실행돼요. 그런데 superRefine을 붙인 스키마는 객체 스키마를 한 겹 감싼 ZodEffects라서 .shape가 없어요. 그래서 전체 스키마는 공개 API가 아닌 내부 속성 \_def.schema로 안쪽 객체를 꺼내 필드 정의만 가져와요. 필드만 옮기는 방식이라 superRefine은 전체 스키마에 전달되지 않고, Zod의 내부 구조에 기대는 코드도 남아요. 단계별 검증은 동작하지만, 필드와 추가 검증을 함께 재사용하는 구조는 아직 완성되지 않았어요.

방문 인증 단계에서는 증빙 파일을 한 개 이상 요구해요. 다만 이 단계를 건너뛰는 흐름도 있어 전체 SubmissionSchema에는 min(1)을 두지 않았고, 현재 구현도 이 차이를 반영해요.

## 여러 개를 고르는 입력은 Controller로 잇는 것만으로 끝나지 않았어요

DetailsStepSchema의 items는 시술을 1개에서 5개까지 담는 배열이고, 사용자는 목록에서 여러 번 골라 이 배열을 채워요. 이 필드의 선택 UI는 두 번 바뀌었어요. 그동안 폼 값의 모양과 단계 스키마의 규칙(1~5개, 중복 없음)은 그대로였어요. 바뀐 것은 고르는 도중의 값을 누가 들고 있느냐였어요.

*시술 선택 UI는 두 번 바뀌었어요. 드롭다운 안 복수 선택은 2차 리팩터링에서, Bottom Sheet는 디자인 시스템 적용에서 구현했고, 폼 값이 바뀌는 시점을 '고르는 즉시'에서 '확인할 때'로 옮겼어요.*

처음 선택 UI는 동료가 만든 키워드 자동완성 드롭다운이었어요. 입력칸을 누르면 바로 아래로 시술 목록이 펼쳐지고, 하나를 고르면 목록이 닫히면서 입력칸이 비워졌어요. 고른 시술은 입력칸 아래에 칩으로 쌓였고요. 이 글의 구조를 잡은 1차 리팩터링에서는 이 드롭다운을 Controller로 감싸 폼에 연결만 하고 화면은 그대로 뒀어요.

그 뒤 모바일에서 이 화면을 써 보니, 여러 개를 골라야 하는 입력인데도 시술마다 입력칸을 다시 누르고 검색해야 했어요. 드롭다운 UI와 하나 고르면 닫히는 동작이 UX상 좋지 않다고 보고, 불편했던 점 세 가지를 Jira에 적어 PO에게 공유했어요.

- 키패드가 올라오면 아래로 펼친 목록이 가려져요.
- 여러 개를 고를 수 있는데 하나를 고르면 목록이 바로 닫혀요.
- 이미 고른 항목이 목록에서 구분되지 않아요.

사용자 데이터가 아니라 직접 써 보고 적은 판단이었어요. 기획·디자인 담당자들은 이를 곧 이어진 2차 리팩터링에 넣기로 하고 방향을 정했어요. 드롭다운은 유지하되 그 안에서 여러 개를 고르게 하고, 고른 항목에 체크와 칩을 붙이고, 입력칸을 누르면 헤더 바로 아래로 스크롤하는 방식이에요. 이를 Radix Popover와 cmdk로 직접 구현해 운영에 반영했어요. 이때도 폼 값은 고르는 즉시 useFieldArray의 append와 remove로 바뀌었어요.

운영에 반영된 그달 말, 디자인 시스템 시안에서 시술 선택 UI가 Bottom Sheet로 바뀌었어요. 디자인 시스템을 화면에 입히는 작업이라 2차 리팩터링과는 별개였어요. 공용 시트 컴포넌트는 동료가 만들었고, 리뷰 화면 적용은 직접 했어요. 운영에는 다음 달에 반영됐어요.

## 고르는 동안의 값은 시트가 갖게 했어요

처음에는 드롭다운 때처럼 시트 안에서 폼 값을 바로 고치게 붙였어요. 공용 시트는 열 때 전역 스토어에 넘긴 요소를 앱 최상단에서 그려요. 작업 기록에는 이 시트를 바깥에서 제어하지 못하는 문제가 있었다고만 남아 있어요. 고른 값이 곧바로 폼에 들어가면 시트를 닫아도 선택이 취소되지 않아요. 닫힌 뒤 원래 값으로 되돌리는 처리를 덧대 보다가 다음 날 방향을 바꿨어요. 고르는 동안의 값은 시트가 들고 있고, 폼에는 '확인'을 누를 때 한 번만 넣어요. 둘 다 배포 전, 같은 작업 안에서 있었던 일이에요.

현재 코드를 줄이면 다음과 같아요. 필드 컴포넌트(가명 ItemsField)와 선택 시트(가명 ItemPickerSheet)만 남겼어요.

```tsx
// FieldBox는 입력칸 모양의 상자(가명)다. 필드 이름도 가명이다.
// openBottomSheet·closeBottomSheet는 공용 시트의 전역 스토어를 여닫는 함수다.
function ItemsField() {
  const { control } = useFormContext<DetailsStepValues>();
  const { fields: items, replace, remove } = useFieldArray({ control, name: 'items' });

  const openPicker = () =>
    openBottomSheet({
      detent: 'content-height',
      fullContents: true,
      children: <ItemPickerSheet initialItems={items} onConfirm={replace} />,
    });

  return (
    <FieldBox onClick={openPicker}>
      {items.map(({ itemId, itemName }, index) => (
        <Tag key={itemId} text={itemName} onClose={() => remove(index)} />
      ))}
    </FieldBox>
  );
}

function ItemPickerSheet({ initialItems, onConfirm }: ItemPickerSheetProps) {
  const [draft, setDraft] = useState(initialItems);

  const toggle = (item: DetailsStepValues['items'][number]) => {
    if (draft.some(({ itemId }) => itemId === item.itemId)) {
      setDraft((prev) => prev.filter(({ itemId }) => itemId !== item.itemId));
      return;
    }
    if (draft.length >= 5) {
      toast.warning('시술은 최대 5개까지 선택 가능해요.');
      return;
    }
    setDraft((prev) => [...prev, item]);
  };

  return (
    <div>
      {/* 검색 입력, 체크 목록(행을 누르면 toggle), 고른 항목 요약과 초기화(setDraft([])) */}
      <Button
        onClick={() => {
          onConfirm(draft);
          closeBottomSheet();
        }}
      >
        확인
      </Button>
    </div>
  );
}
```

필드는 useFieldArray로 items, replace, remove를 받고, 누르면 openBottomSheet로 시트에 그릴 요소를 전역 스토어에 넘겨요. 공용 시트는 앱 최상단의 Provider에서 이 요소를 그리므로, 시트는 폼 Provider(FormProvider) 밖에 있어요. 그래서 시트는 useFormContext를 쓰지 않고, 열 때의 items와 replace를 props로 받아요.

그럼 시트를 그냥 닫으면 고른 값은 어떻게 될까요? 공용 시트는 닫힘 애니메이션이 끝나면 내용을 언마운트하므로, 시트는 열 때마다 새로 마운트되어 그 순간의 items로 임시 선택을 만들어요. 행을 누르면 임시 선택에 넣거나 빼고, '확인'을 눌러야 replace가 필드 배열을 임시 선택으로 한 번에 바꿔요. 딤을 누르거나 끌어내려 닫으면 스토어의 열림 상태만 꺼지고 넘어가는 값은 없어요. 시트가 언마운트되면서 임시 선택도 사라져요. 닫기가 곧 취소예요. 필드의 칩에 붙은 ×는 클릭이 필드로 번지지 않게 막혀 있어서, 시트를 열지 않고 remove로 바로 지워요.

![시트는 열 때의 값으로 임시 선택을 만들고, 확인할 때만 replace로 필드에 넣어요. 닫으면 아무것도 넘기지 않아요.](/images/posts/review-form-funnel/02.png)

*시트는 열 때의 값으로 임시 선택을 만들고, 확인할 때만 replace로 필드에 넣어요. 닫으면 아무것도 넘기지 않아요.*

## 같은 규칙을 두 곳에 두면 어느 값을 보는지부터 정해야 했어요

규칙은 두 곳에 있어요. 시트는 임시 선택이 5개면 6번째를 토스트로 막고, 같은 항목을 다시 누르면 빼므로 중복이 생기지 않아요. 단계 스키마는 확정된 items를 min(1), max(5), 그리고 앞에서 본 스키마 코드에서는 생략한 중복 검사로 봐요. 시술 선택 필드에는 오류 문구가 없어서 스키마의 결과는 '다음' 버튼이 꺼지는 것으로만 드러나요.

두 규칙이 보는 값이 다르다는 점이 한 번 실수로 이어졌어요. 시트를 처음 develop에 합쳤을 때 개수 제한이 draft가 아니라 열 때 받은 initialItems의 개수를 보고 있었어요. 그대로 나갔다면 열 때 고른 것이 5개보다 적은 경우 시트 안에서는 제한 없이 고를 수 있고, 확인한 뒤에야 '다음' 버튼이 이유 없이 꺼지는 구조였어요. 다음 날, 운영에 반영되기 전에 draft 기준으로 고쳤어요. 같은 규칙을 두 곳에 두면 각 규칙이 어느 값을 검사하는지부터 정해야 해요.

필드 하나 안에서 임시 값을 따로 들고 있다가 확인할 때 합치는 이 모양은 다음 절의 단계 폼에서 한 단계 크기로 되풀이돼요. 단계 폼도 자기 단계의 값을 따로 검증한 뒤에야 상위 폼에 합치거든요.

## 퍼널은 단계 이동만 맡고 검증한 값은 상위 폼에 합쳐요

```tsx
// useSchemaForm·useStepFunnel·StepForm은 공용 폼 훅, 퍼널 훅, 단계 폼 래퍼의 공개용 가명이다.
// needsProof는 방문 인증 단계부터 시작하는 경우, isVisited는 예약이 방문 완료 상태인 경우다.
const form = useSchemaForm({
  schema: SubmissionSchema,
  defaultValues: savedDraft
    ? mapResponseToDraft(savedDraft.data)
    : emptyDraft,
});

const flow = useStepFunnel<Record<'proof' | 'details' | 'feedback', object>>({
  initial: {
    step: needsProof ? 'proof' : 'details',
    context: {},
  },
  id: 'public-example-flow',
});

const mergeAndReset = useCallback(
  (callback: (data: ReviewDraft) => void) =>
    <T extends Partial<ReviewDraft>>(stepValues?: T) => {
      const mergedDraft = {
        ...form.formState.defaultValues,
        ...stepValues,
      } as ReviewDraft;

      form.reset(mergedDraft);
      callback(mergedDraft);
    },
  [form],
);

const moveToStep = useCallback(
  (step: typeof flow.step) =>
    mergeAndReset(() => flow.history.replace(step)),
  [mergeAndReset, flow],
);

const confirmSubmission = mergeAndReset((data) =>
  openConfirmDialog({
    primaryAction: {
      text: '제출',
      onConfirm: () => submitDraft(data),
    },
  }),
);

return (
  <flow.Render
    proof={() => (
      <StepForm
        schema={ProofStepSchema}
        defaultValues={form.formState.defaultValues}
        onComplete={moveToStep('details')}
      >
        <ProofStep />
      </StepForm>
    )}
    details={() => (
      <StepForm
        schema={DetailsStepSchema}
        defaultValues={form.formState.defaultValues}
        onBack={needsProof ? moveToStep('proof') : undefined}
        onComplete={moveToStep('feedback')}
      >
        <DetailsStep />
      </StepForm>
    )}
    feedback={() => (
      <StepForm
        schema={FeedbackStepSchema}
        defaultValues={form.formState.defaultValues}
        onBack={moveToStep('details')}
        onComplete={confirmSubmission}
      >
        <FeedbackStep isVisited={isVisited} />
      </StepForm>
    )}
  />
);
```

단계 폼 래퍼(가명 StepForm)는 단계마다 mode: 'all'인 폼 인스턴스를 만들고 해당 단계 스키마로 검증해요. 통과한 값은 상위 RHF 인스턴스의 defaultValues와 합친 뒤 reset해 다음 단계의 초기값으로 써요. 단계 이동은 퍼널의 history.replace로 표현해요. 퍼널 context에 폼 값을 넣거나 history.push로 단계별 스냅샷을 쌓지는 않아요.

세 번째 단계도 같은 방식으로 값을 합쳐 확인 대화상자와 API 요청에 전달해요. 이 경로에는 명시적인 SubmissionSchema.parse가 없어요. 앞 단계에서 검증한 값이 그대로 유지된다는 전제에 기대고 있어서, 최종 제출에서 전체 규칙을 확인하는 일은 남은 과제예요.

## 수정할 데이터는 폼을 만들기 전에 준비해 뒀어요

상위 폼은 savedDraft가 있으면 그 값으로 defaultValues를 만들어요. 그런데 React Hook Form의 defaultValues는 폼을 처음 만들 때 캐시돼요. 수정용 리뷰 데이터가 비동기로 늦게 도착하는 경우, 첫 렌더링에 빈 값을 넣고 끝내서는 안 돼요.

현재 화면은 서버 페이지에서 예약 정보와 리뷰 정보를 미리 요청하고, 채워진 캐시를 HydrationBoundary로 클라이언트에 넘겨요. 클라이언트 템플릿은 같은 쿼리 옵션으로 useQueries를 호출하므로 첫 렌더링부터 캐시에 든 응답을 읽어요.

```tsx
// 컴포넌트, 쿼리 옵션, 경로 파라미터 이름은 공개용 가명이다.
// 서버 페이지. 예약 id와 리뷰 id가 모두 있는 경로이고, 다른 경로는 있는 id만 미리 요청한다.
async function ReviewEditorRoute({ params }: EditorRouteProps) {
  const { sourceId, draftId } = await params;
  const queryClient = getQueryClient();

  await Promise.all([
    queryClient.prefetchQuery(sourceByIdQuery(Number(sourceId))),
    queryClient.prefetchQuery(draftByIdQuery(Number(draftId))),
  ]);

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ReviewEditorPage />
    </HydrationBoundary>
  );
}

// 클라이언트 템플릿
function ReviewEditorPage() {
  const { sourceId, draftId } = useParams<EditorRouteParams>();
  const [{ data: sourceInfo }, { data: savedDraft }] = useQueries({
    queries: [
      sourceByIdQuery(toOptionalNumber(sourceId)),
      draftByIdQuery(toOptionalNumber(draftId)),
    ],
  });

  const form = useSchemaForm({
    schema: SubmissionSchema,
    defaultValues: savedDraft
      ? mapResponseToDraft(savedDraft.data)
      : emptyDraft,
  });

  // 퍼널과 단계 폼은 앞 절의 코드와 같다.
}
```

서버 페이지가 두 요청이 끝날 때까지 기다린 뒤 렌더링하므로, 클라이언트 템플릿이 처음 렌더링될 때 수정용 데이터는 이미 캐시에 있어요. 그래서 응답을 폼 값으로 바꾸는 변환 함수가 만든 수정값이 첫 defaultValues에 들어가요. Suspense로 데이터를 기다리지도 않아요.

## 스토어는 사라졌지만 부채는 남았어요

바뀐 부분은 이래요.

- 리뷰 작성용 Zustand 스토어를 제거했어요.
- 컴포넌트에 흩어져 있던 조건부 검증을 단계별 스키마로 옮겼어요.
- 화면 전환과 폼 검증을 분리했어요.
- 각 단계가 자신에게 필요한 스키마로 제출 가능 여부를 판단해요.
- 시술 선택에서 고르는 도중의 값은 시트가 갖고, 확인할 때 replace로 한 번만 폼에 넣어요.

두 Zustand 스토어를 없앤 것보다 각 단계가 자기 필드와 검증만 알게 된 점이 더 유용했어요. 대신 단계마다 폼 인스턴스를 만들기 때문에 defaultValues를 합치고 reset하는 코드는 여전히 필요해요.

폼의 공개 여부도 현재는 의미가 드러나는 열거형 대신 불리언 값을 써요. 실제 요청을 만들 때는 다른 필드도 함께 가공하지만, 이 값의 변환만 추리면 다음과 같아요.

```typescript
function toSubmissionRequest(form: ReviewDraft): SubmissionRequest {
  const { visibilityFlag, ...rest } = form;

  return {
    ...rest,
    visibilityFlag: visibilityFlag
      ? VISIBILITY.Hidden
      : VISIBILITY.Public,
  };
}
```

현재 변환은 동작하지만 true가 숨김인지 공개인지 알려면 필드 이름과 변환 코드를 함께 봐야 해요. 폼 내부에서도 PUBLIC | HIDDEN 같은 값을 쓰면 해석하기 쉬워져요. 다만 이 방식은 현재 구현에는 반영되지 않은 후속 개선안이에요.

퍼널 라이브러리도 다시 볼 부분이에요. 이미지처럼 브라우저 객체를 포함한 값은 URL 직렬화만으로 이동 이력을 복원하기 어려워요. 3단계라는 이유만으로 퍼널 라이브러리가 필요한 것은 아니에요. 현재 구현처럼 context를 비워 두고 replace만 사용한다면 로컬 상태나 명시적인 리듀서가 더 단순한지도 비교할 필요가 있어요.

다시 손댄다면 먼저 단계의 추가 검증까지 합친 전체 스키마를 만들고, 마지막 제출이 모든 단계의 값을 다시 검사하는 테스트를 추가할 거예요.
