<Summary>

Moving a multi-step hospital review form from global stores to React Hook Form and Zod also meant reconnecting treatment selection. I changed the sheet to cancel on close and write selections to the form only after confirmation.

</Summary>

![An illustration of a review form moving from rating to writing and confirmation.](/images/covers/review-form-funnel.avif)

When I first connected the treatment sheet to the review form, closing it without confirming still left the chosen treatments in the form. Closing could mean cancelling only if the choices in progress lived apart from the form. I fixed that before release, but the review screen had already changed several times on the way to that sheet.

This is the screen where someone who visited a hospital leaves a review. They upload a receipt as proof of the visit, enter treatment and payment details, then add ratings, photos, and text. A form like this, split into screens the user passes through in order instead of laying every input out at once, is usually called a funnel form, after the way a funnel narrows people through stages. Splitting it creates decisions beyond the inputs themselves: where earlier values are kept, which values get checked in which step, and when the user may continue.

It started with changing a field, which meant following its storage action, error message, and next-step condition. Each input knew how to update global stores and run validation beyond its own field.

So I moved values to React Hook Form (RHF) and validation to Zod, and kept a funnel hook for navigation. RHF is a library that manages a form's values and errors. Zod writes the conditions on a value as a schema and checks real values against it. That refactoring came first. The treatment selection UI changed twice more after it.

## Two global stores

Input values and the current step lived in separate Zustand stores. Zustand is a global state library that creates a store outside your components, which any component can read and change. A draft store and a step store drove the screen, with `step` selecting the current view.

```tsx
type DraftStore = {
  draft: ReviewDraft;
  setField: <K extends keyof ReviewDraft>(
    key: K,
    value: ReviewDraft[K],) => void;
};

type StepStore = {
  step: number;
  moveForward: () => void;
  moveBack: () => void;
};
```

```tsx
switch (step) {
  case 1:
    return <ProofStep />;
  case 2:
    return <DetailsStep />;
  default:
    return <FeedbackStep />;
}
```

A separate API already handled saving drafts. Other screens did not need the ongoing values or current step, and page-local form instances could retain values between stages.

I first tried combining everything into one form. Different fields mounted and validation ran at different times in each stage. Checking everything against a single schema would also block the current step on fields from later steps the user had not reached. RHF therefore manages values and fields, Zod validates them, and a shared wrapper around @use-funnel/core changes the current step. @use-funnel/core is a library that tracks a funnel's steps, per-step values (its context), and navigation history.

A parent form retains the complete draft while each step has its own form. Passing a step merges those values into the parent before continuing. That leaves a connection between stages that merges values and calls `reset`.

## `superRefine` did not come along

Ideally each step checks only its own values and final submission checks everything again. The step schemas were separated, but a problem remained where the overall schema is assembled. The schemas below separate fields by step. This example uses renamed fields and keeps the main definitions and additional validation.

The schema examples and the `ZodEffects` explanation below use Zod 3. [Zod 4 stores refinements inside the schemas themselves](https://zod.dev/v4/changelog?id=drops-zodeffects), so the `_def.schema` access below cannot be used unchanged.

```typescript
import { z } from 'zod';

export const ProofStepSchema = z.object({
  proofFiles: z.array(UploadSchema).min(1).max(5),
});

export const DetailsStepSchema = z
  .object({
    visibilityFlag: z.boolean(),
    items: z.array(ItemSchema).min(1).max(5),
    quoteFieldEnabled: z.boolean().optional(),
    quotedAmount: z.number().optional(),
    paidAmount: z.number().min(1),
    amountFlag: z.boolean().optional(),
    receivedBenefitInfo: z.boolean(),
    missingBenefitReason: z
      .object({
        value: z.enum(MISSING_INFO_REASONS),
        description: z.string(),
      })
      .optional()
      .nullable(),
  })
  .superRefine((data, ctx) => {
    if (data.quoteFieldEnabled && (!data.quotedAmount || data.quotedAmount <= 0)) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['quotedAmount'],
        message: 'Enter an amount.',
      });
    }

    if (!data.receivedBenefitInfo && !data.missingBenefitReason) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['missingBenefitReason'],
        message: 'Explain why the amount was not provided.',
      });
    }
  });

export const FeedbackStepSchema = z.object({
  attachments: z.array(UploadSchema),
  ratings: z.array(
    z.object({
      criterion: z.enum(RATING_CRITERIA),
      score: z.number().min(0).max(2),
    }),
  ),
  body: z.string().min(50).max(500),
  wouldRecommend: z.boolean(),
});

export const SubmissionSchema = z
  .object({
    // Visit verification requires min(1), but the overall schema does not.
    proofFiles: z.array(UploadSchema).max(5),
  })
  .extend(DetailsStepSchema._def.schema.shape)
  .extend(FeedbackStepSchema.shape);
```

Step two conditionally requires a quoted amount or a reason benefit information was not received. No single field can decide those, so `DetailsStepSchema` uses `superRefine`, which looks at the whole object and adds errors. That refinement wraps the object in ZodEffects, without direct access to `.shape` (the object's field definitions).

`SubmissionSchema` reaches the inner object's fields through `_def.schema`, an internal property outside the public API. Copying fields does not copy `superRefine`. Conditional validation runs in the step but is absent from the overall schema, which also remains coupled to Zod internals.

The different minimum for `proofFiles` is intentional. The proof step requires at least one file, but some routes skip that step. The overall schema therefore omits `min(1)` for it.

## Connect amount inputs through values and changes

Inputs used to know about store actions and validation together. A shortened amount input looks like this. It is not the code from that time, only an example written to illustrate it.

```tsx
// A shortened example. The hook and function names are made up for this post.
function AmountField() {
  const paidAmount = useDraftStore((state) => state.draft.paidAmount);
  const setField = useDraftStore((state) => state.setField);
  const errorMessage = validatePaidAmount(paidAmount);

  return (
    <NumericInput
      value={paidAmount}
      errorMessage={errorMessage}
      onChange={(value) => setField('paidAmount', value)}
    />
  );
}
```

After the move, only the value and the change handler connect to the form.

```tsx
function AmountField() {
  const { control } = useFormContext<DetailsStepValues>();

  return (
    <Controller
      control={control}
      name="paidAmount"
      render={({ field: { value, onChange } }) => (
        <NumericInput
          value={value}
          onChange={normalizeNumericInput(onChange)}
        />
      )}
    />
  );
}
```

`Controller` connects a custom input component to RHF, here `NumericInput`'s value and `onChange`. The step schema checks amount conditions, so the input no longer calls Zustand actions or a separate validation function.

## Choosing several treatments on a phone

`items` holds one to five unique treatments. Its array shape and rules stayed the same while the selection UI changed. What moved was where the values in progress lived.

Treatment selection changed twice: multiple selection inside the dropdown came in the second refactoring, and Bottom Sheet came with the design system. Form updates moved from each selection to confirmation.

![Treatment selection changed twice: multiple selection inside the dropdown came in the second refactoring, and Bottom Sheet came with the design system. Form updates moved from each selection to confirmation.](/images/posts/review-form-funnel/01-en.avif)

The original UI was a colleague's autocomplete dropdown. Tapping the input opened a list below it, and choosing a treatment closed the list and cleared the search. Selections accumulated as chips below. The initial form migration only wrapped that UI in `Controller`.

Trying it on a phone myself meant reopening and searching for every treatment. The keyboard obscured the list, choosing one item closed the list even though several could be chosen, and selected items were not marked. This was my own judgment from using it, not something user data had confirmed. I recorded those problems in Jira and shared them with the PO, and planning and design included them in the next refactoring.

We retained a dropdown but supported multiple choices within it, marked selections with checks and chips, and scrolled the input just below the header. I built that and released it using Radix Popover, for a panel anchored to a button, and cmdk, for a searchable list. Each selection still changed the form immediately through `append` or `remove` from `useFieldArray`, the RHF hook for array-shaped fields.

Later design-system mockups replaced the selection UI with a Bottom Sheet, a panel that slides up from the bottom and covers the current screen. That was separate from the dropdown improvement. A colleague built the shared sheet, and I connected it to review writing.

## Closing did not cancel

I first connected the sheet like the dropdown, updating the form immediately. Closing without confirmation then kept the changes. I tried restoring old values after close, then changed direction the next day: the sheet keeps temporary choices and returns them only on confirmation. Both approaches came before release. The schema cannot see temporary choices, though, so the sheet had to check the count limit on its own.

`ItemsField` and `ItemPickerSheet` are publication aliases. Their opening and confirmation connection looks like this.

```tsx
// FieldBox is a public alias for an input-shaped container; field names are aliases too.
// openBottomSheet and closeBottomSheet control the shared sheet's global store.
function ItemsField() {
  const { control } = useFormContext<DetailsStepValues>();
  const { fields: items, replace, remove } = useFieldArray({ control, name: 'items' });

  const openPicker = () =>
    openBottomSheet({
      detent: 'content-height',
      fullContents: true,
      children: <ItemPickerSheet initialItems={items} onConfirm={replace} />,
    });

  return (
    <FieldBox onClick={openPicker}>
      {items.map(({ itemId, itemName }, index) => (
        <Tag key={itemId} text={itemName} onClose={() => remove(index)} />
      ))}
    </FieldBox>
  );
}

function ItemPickerSheet({ initialItems, onConfirm }: ItemPickerSheetProps) {
  const [draft, setDraft] = useState(initialItems);

  const toggle = (item: DetailsStepValues['items'][number]) => {
    if (draft.some(({ itemId }) => itemId === item.itemId)) {
      setDraft((prev) => prev.filter(({ itemId }) => itemId !== item.itemId));
      return;
    }
    if (draft.length >= 5) {
      toast.warning('You can select up to five treatments.');
      return;
    }
    setDraft((prev) => [...prev, item]);
  };

  return (
    <div>
      {/* Search input, checklist (click a row to toggle), selection summary, and reset (setDraft([])) */}
      <Button
        onClick={() => {
          onConfirm(draft);
          closeBottomSheet();
        }}
      >
        Confirm
      </Button>
    </div>
  );
}
```

`openBottomSheet` stores the supplied element globally, and an app-root Provider renders it. The sheet is not a `FormProvider` child, and `useFormContext` finds the form in a `FormProvider` above it, so the sheet cannot use that hook. The field passes `items` and `replace` from `useFieldArray` as props instead. `replace` swaps the whole field array for the value it receives.

The sheet creates `draft` from its opening-time `items`. Rows update `draft`, and only confirmation calls `replace` on the form array. Tapping the backdrop or dragging down returns no values. After the exit animation, content unmounts and discards `draft`, and reopening starts from the current form values.

The chip's × stops propagation and calls `remove` without opening the sheet. Removing directly in the field and cancelling choices inside the sheet are separate actions.

So the sheet starts with the opening values and passes its temporary selection to the field through `replace` only on confirmation. Closing passes nothing back.

![The sheet starts with the opening values and passes its temporary selection to the field through replace only on confirmation. Closing passes nothing back.](/images/posts/review-form-funnel/02-en.avif)

## Which count should the limit check?

The rule lives in two places. The sheet blocks another selection with a toast when `draft` has five items. Selecting an existing treatment removes it, preventing duplicates. The schema checks confirmed `items` using `min(1)`, `max(5)`, and a duplicate check omitted from the earlier example. This field has no separate error message, so a failure only disables Next.

When first merged into develop, the sheet checked `initialItems.length` instead of `draft`. Opening with fewer than five items could then allow unlimited choices and disable Next, with no explanation, only after confirmation. I changed it to `draft` the following day, before production. It had been counting what the form already held when it needed to count what was being chosen.

## Step forms also merge after checking

Holding temporary values and merging on confirmation repeats at the size of a whole step: step forms validate changes for that stage before merging them into the full draft.

```tsx
// useSchemaForm, useStepFunnel, and StepForm are public aliases for the shared form hook, funnel hook, and step wrapper.
// needsProof starts at visit verification; isVisited means the reservation has been marked visited.
const form = useSchemaForm({
  schema: SubmissionSchema,
  defaultValues: savedDraft
    ? mapResponseToDraft(savedDraft.data)
    : emptyDraft,
});

const flow = useStepFunnel<Record<'proof' | 'details' | 'feedback', object>>({
  initial: {
    step: needsProof ? 'proof' : 'details',
    context: {},
  },
  id: 'public-example-flow',
});

const mergeAndReset = useCallback(
  (callback: (data: ReviewDraft) => void) =>
    <T extends Partial<ReviewDraft>>(stepValues?: T) => {
      const mergedDraft = {
        ...form.formState.defaultValues,
        ...stepValues,
      } as ReviewDraft;

      form.reset(mergedDraft);
      callback(mergedDraft);
    },
  [form],
);

const moveToStep = useCallback(
  (step: typeof flow.step) =>
    mergeAndReset(() => flow.history.replace(step)),
  [mergeAndReset, flow],
);

const confirmSubmission = mergeAndReset((data) =>
  openConfirmDialog({
    primaryAction: {
      text: 'Submit',
      onConfirm: () => submitDraft(data),
    },
  }),
);

return (
  <flow.Render
    proof={() => (
      <StepForm
        schema={ProofStepSchema}
        defaultValues={form.formState.defaultValues}
        onComplete={moveToStep('details')}
      >
        <ProofStep />
      </StepForm>
    )}
    details={() => (
      <StepForm
        schema={DetailsStepSchema}
        defaultValues={form.formState.defaultValues}
        onBack={needsProof ? moveToStep('proof') : undefined}
        onComplete={moveToStep('feedback')}
      >
        <DetailsStep />
      </StepForm>
    )}
    feedback={() => (
      <StepForm
        schema={FeedbackStepSchema}
        defaultValues={form.formState.defaultValues}
        onBack={moveToStep('details')}
        onComplete={confirmSubmission}
      >
        <FeedbackStep isVisited={isVisited} />
      </StepForm>
    )}
  />
);
```

`StepForm` creates a `mode: 'all'` form for each stage. `mode` decides when validation runs, and `'all'` validates both when a value changes and when an input loses focus. Values passing its schema merge with the parent RHF `defaultValues` (the form's initial values), then `reset` supplies initial values for the next stage. `reset` sets both the form's current values and its `defaultValues` to what it receives.

The funnel's `history.replace` changes the visible step. `history.push` would add to the history and pass context to the next step, while `replace` overwrites the current step without adding to the history. Values do not enter funnel context, and `history.push` does not accumulate step snapshots.

The last stage merges values before confirmation and the API call too, but does not run `SubmissionSchema.parse` again. It assumes previously validated values remain valid. Final submission therefore lacks a fresh check of every step's conditions.

## `defaultValues` on the edit screen

Editing a review that already exists means the form has to open with the saved content. An existing `savedDraft` is converted into `defaultValues`. RHF caches those when creating the form, so starting with an empty form does not populate it merely because the response arrives later.

So the response had to be ready before the first render. The server page prefetches reservation and review data and transfers the cache through `HydrationBoundary`. `prefetchQuery` fills a React Query cache on the server, `dehydrate` turns that cache into a form that can be sent to the browser, and `HydrationBoundary` puts it in the browser's cache. The client reads it through `useQueries` with the same options.

```tsx
// Component, query-option, and route-parameter names are public aliases.
// Server page with both reservation and review IDs. Other routes prefetch only the available ID.
async function ReviewEditorRoute({ params }: EditorRouteProps) {
  const { sourceId, draftId } = await params;
  const queryClient = getQueryClient();

  await Promise.all([
    queryClient.prefetchQuery(sourceByIdQuery(Number(sourceId))),
    queryClient.prefetchQuery(draftByIdQuery(Number(draftId))),
  ]);

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ReviewEditorPage />
    </HydrationBoundary>
  );
}

// Client template
function ReviewEditorPage() {
  const { sourceId, draftId } = useParams<EditorRouteParams>();
  const [{ data: sourceInfo }, { data: savedDraft }] = useQueries({
    queries: [
      sourceByIdQuery(toOptionalNumber(sourceId)),
      draftByIdQuery(toOptionalNumber(draftId)),
    ],
  });

  const form = useSchemaForm({
    schema: SubmissionSchema,
    defaultValues: savedDraft
      ? mapResponseToDraft(savedDraft.data)
      : emptyDraft,
  });

  // The funnel and step forms are the same as in the previous section.
}
```

Because the server waits for the requests before rendering, edit data is cached on the client's first render as long as those requests succeed. The converted values become its initial `defaultValues`. This screen does not wait for the response through client Suspense.

A failed request changes that. `prefetchQuery` does not throw failures to its caller, and the default `dehydrate` leaves failed queries out. The first render then has no `savedDraft`, `emptyDraft` becomes `defaultValues`, and the form keeps those initial values even if a later client request succeeds. This example does not handle that path. Data the edit form cannot work without should either surface its error through `fetchQuery` on the server or be confirmed before the form renders. [TanStack Query's server rendering error handling](https://tanstack.com/query/latest/docs/framework/react/guides/ssr#error-handling) describes the behavior.

## Looking back

Getting each stage to know only its own fields and validation turned out more useful than removing the two Zustand stores. Merging `defaultValues` and calling `reset` between stages remains necessary, though.

The input types retain ambiguity too. Visibility is a boolean converted to the API's hidden/public enum. Omitting other request transformations, that conversion is:

```typescript
function toSubmissionRequest(form: ReviewDraft): SubmissionRequest {
  const { visibilityFlag, ...rest } = form;

  return {
    ...rest,
    visibilityFlag: visibilityFlag
      ? VISIBILITY.Hidden
      : VISIBILITY.Public,
  };
}
```

Understanding whether `true` means public or hidden requires reading this conversion. `PUBLIC` or `HIDDEN` within the form would expose its meaning directly, but the current form retains the boolean. Moving state out of a store did not resolve that interpretation.

The funnel deserves another look too. Its context is empty and `replace` only changes the screen. Values containing browser objects such as photos are also difficult to restore through URL serialization alone. Having three steps does not by itself call for a funnel library, and local state or an explicit reducer may turn out simpler, which I still need to compare. With the form holding the values and only the screen changing, did this structure really need a funnel library?
