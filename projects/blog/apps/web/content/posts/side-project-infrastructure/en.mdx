<Summary>

I dropped RDS while looking at deployment costs. I considered serverless options too, but decided to start with the web apps, APIs, and PostgreSQL on one small EC2 instance. That also meant working through storage, backups, and S3 permissions.

</Summary>

*An illustration of the two services, data storage, and backups.*

Game Mate and the photo community needed somewhere to run. The first plan was one EC2 instance for the apps and RDS for PostgreSQL. I wanted to keep the initial cost down, so I decided to take RDS out.

I did not settle on EC2 immediately. I asked about moving to Cloudflare and about coming back to EC2 after starting on a serverless platform. Deployment was unfamiliar territory, so whenever a product or setting came up that I did not understand, I asked about it and looked at the code.

## I considered moving to serverless

My first question was which Cloudflare product did the job of EC2. I looked into Workers and Containers, and checked whether R2 could handle the presigned uploads already in the apps.

“Moving to serverless” could mean very different amounts of work. A platform that ran the existing Docker images would mainly need deployment changes. Workers meant looking at the APIs again. Game Mate has chat SSE connections, and the photo service runs scheduled work inside its process. I would have to work out how those would run in the new environment.

I also wondered whether Hyperdrive could take care of the database. It turns out to [accelerate connections and queries to an existing database](https://developers.cloudflare.com/hyperdrive/). I would still need somewhere to run PostgreSQL.

I asked about the work involved in returning to EC2 too. Keeping the same containers and PostgreSQL is different from changing an API around a particular platform and then moving back.

In the end, I decided to start with a small EC2 instance and see how it went. The Node servers and Docker deployment were already there. Terraform, S3, and IAM were set up around AWS too. I chose to finish that work before adding another cloud.

Usage-based billing is another concern. A small service can still receive repeated requests that increase its bill. The [Workers documentation](https://developers.cloudflare.com/workers/platform/pricing/#custom-limits) recommends a per-invocation CPU limit for this kind of attack, but limiting each execution still leaves the cost of the total number of requests. If I revisit serverless, I also want to look at where to limit incoming traffic.

## Would one small instance be enough for the database too?

I changed PostgreSQL to run in a container on the same EC2 instance. If that server stops, both services and the database stop together. The initial cost is lower, but backups and recovery become my responsibility.

```text
One EC2 instance
  Caddy :443
    ├─ Game Mate Web ─ Game Mate API ─┐
    └─ Photo Web ─ Photo API ────────┤
                                    └─ PostgreSQL container
                                         ├─ game_feedback DB
                                         └─ photo_contest DB
Dedicated EBS volume  PostgreSQL data
Private media S3      Service-specific object prefixes
Separate backup S3    Database dumps before deployment
```

The blog stays on Vercel, outside this server. There is one PostgreSQL process, with separate databases and accounts for the two services. API runtime accounts and migration accounts are separate too.

The [t3.small configuration](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/variables.tf) starts with 2 GiB of memory and 2 GiB of swap. I checked the container limits as well: Caddy, PostgreSQL, and both services' web and API containers add up to roughly 3.1 GiB.

Those limits do not reserve that much memory in advance, but 2 GiB would not cover simultaneous heavy use. I documented moving to 4 GiB if swap use stays high or containers are killed by OOM. How far the small instance actually gets needs a load test.

The monthly estimate also needed more than the instance price. I included EBS, public IPv4, snapshots, and S3 storage, requests, and transfer. The estimate is still an estimate; I will need actual usage to compare it with the bill.

## Running the database meant preparing backups

I put database data on a separate encrypted EBS volume, mounted at `/srv/side-postgres`. A marker file identifies the volume. If it is missing, database startup stops, so a failed mount does not quietly create an empty database on the root disk.

The configuration takes a daily volume snapshot and keeps seven by default. Before a deployment migration, it runs `pg_dump` for that service and uploads the dump to a separate S3 backup bucket. If creating or uploading the dump fails, the migration stops too. The [deployment and backup scripts](https://github.com/jingeon27/side-project/tree/65c3d13a/deploy/shared-instance/scripts) follow that order.

I looked at rollback again as well. Starting the previous application image does not undo a migration that has already run. I kept checks for the previous app working with the changed schema and a separate procedure for restoring the database.

So far, this prepares the backup files. Restoring a snapshot volume and loading a dump into a fresh database on AWS are still on the list. This setup does not provide RDS-style point-in-time recovery either.

## I added S3 permissions, but CI still failed

I wanted one existing S3 media bucket with a folder for each project. The initial code assumed a separate bucket for each service, so I changed that first.

```text
media-bucket/
  game-feedback/
    production/...
    ci/...
  photo-contest/
    production/...
    ci/...
backup-bucket/
  postgres/...
```

Each production credential can only read and write under its service's `production/` prefix. Tests use run-specific paths under `ci/`. The console presents these as folders, but they are [prefixes in object names](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-prefixes.html). Different names do not enforce separate permissions by themselves.

The first IAM policy had `GetObject`, `PutObject`, and `DeleteObject`. CI also listed objects before uploading, and that permission was missing. This made me look again at bucket and object ARNs.

| Operation | Resource | Path restriction |
| --- | --- | --- |
| `GetObject`, `PutObject`, `DeleteObject` | `arn:aws:s3:::media-bucket/game-feedback/production/*` | Put the path in the object ARN |
| `ListBucket` | `arn:aws:s3:::media-bucket` | Add an `s3:prefix` condition |

An ARN ending in `.../game-feedback/` does not mean all files below it. The object pattern needs `*`. Listing needs permission on the bucket ARN, restricted by a prefix condition. The revised [IAM policy](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/iam.tf) has separate statements for the two operations.

Browser uploads had a CORS issue too. The test origin was not allowed on the bucket, which blocked the browser upload. I had to check IAM and CORS separately. [CORS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/cors.html) configures cross-origin browser access; IAM and signatures determine permission to use S3 objects.

I kept the backup bucket separate from media. The EC2 role can upload under `postgres/`, without permission to read or delete existing dumps.

## I looked into R2 too

Since R2 is S3-compatible, I asked whether it could handle the current upload flow. Both services use presigned POST policies with file size limits.

The [R2 documentation](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) supports GET, HEAD, PUT, and DELETE, but not HTML form POST uploads. That is the documented behavior as of October 28, 2026.

Moving would mean switching to PUT and checking the upload conditions and completion checks again. I kept S3 for now. If media transfer becomes a large expense, I will compare them again. Changing storage would not require moving off EC2 at the same time.

## Adding API domains did not mean changing the cookies

I chose to give the APIs their own hostnames. Each service has a web hostname and an `api.` hostname, with Caddy forwarding requests to the right containers.

Browsers still use same-origin `/api` or `/backend` paths, with the existing host-only session cookie on the web hostname. Photo service GraphQL mutations go through the web proxy so they still trigger Next cache invalidation.

Web traffic enters through Caddy on ports 80 and 443. Web and API containers have service-specific Docker networks. Only API, operations, and migration containers join the database networks. Caddy and the web containers have no need to connect directly to the database. The [proxy and network settings](https://github.com/jingeon27/side-project/tree/65c3d13a/deploy/shared-instance) are in the deployment directory.

## I also got mixed up about Terraform and CI permissions

After adding Terraform, I asked which AWS permissions I needed to run it. Signing into the console and authenticating local Terraform needed separate setup.

When CI failed on S3, I also wondered whether putting values in the deployment Environment would fix it. I had to check the S3 configuration for PR tests, environment files on the production server, and SSH deployment settings separately to understand what went where.

In this setup I run Terraform locally. GitHub Actions builds images and delivers deployment work to the server over SSH. It does not need infrastructure administrator credentials. It does need an SSH key and a working network path from the runner. My being able to connect through SSM does not provide that path.

The deployment Environment names were inconsistent too: `production` for one service and `photo-contest-production` for the other. After asking why, I aligned them as `game-feedback-production` and `photo-contest-production`.

Terraform creates resources and policies. Service keys are issued separately and placed in server environment files. It leaves the existing media bucket configuration alone and manages a separate backup bucket for database dumps. I recorded the initial server setup steps in the [Terraform guide](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/README.md).

## What I still need to check on the server

The [CloudWatch configuration](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/monitoring.tf) includes a reboot action after failed instance status checks and an alarm for low CPU credits. A stopped server cannot send application errors, so I needed a check outside the apps too. Email notifications require confirming the subscription after entering an address.

I still need to apply the infrastructure in the actual account and check that the volume attaches on first boot. Backup restoration and load testing remain as well. I want to look at memory, swap, container exits, and response times to find out whether the small instance is a workable starting point.
