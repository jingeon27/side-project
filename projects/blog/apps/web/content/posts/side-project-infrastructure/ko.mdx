*두 서비스와 데이터·백업 저장소를 그린 삽화예요.*

Game Mate와 사진 커뮤니티를 만들고 나니 어디에 올릴지 정해야 했어요. 처음 구성은 EC2 한 대에 앱을 두고 DB는 RDS로 분리하는 쪽이었어요. 그런데 초기 비용을 줄이고 싶어서 RDS부터 빼기로 했어요.

그렇다고 바로 EC2로 확정한 건 아니었어요. Cloudflare로 옮기는 건 어떨지, 서버리스로 시작했다가 나중에 다시 돌아올 수 있을지도 물어봤어요. 배포 쪽은 익숙하지 않아서 모르는 상품이나 설정이 나올 때마다 설명을 듣고 코드를 같이 봤어요.

## 서버리스로 옮길까도 생각했어요

Cloudflare에서 EC2 같은 역할을 하는 게 뭔지부터 궁금했어요. Workers와 Containers를 알아보고, R2에 지금 쓰는 presigned 업로드를 붙일 수 있는지도 확인했어요.

그런데 서버리스로 옮긴다는 말 안에서도 할 일이 꽤 달랐어요. Docker 이미지를 그대로 실행하는 곳으로 옮기면 배포 설정을 바꾸는 일이지만, Workers에 맞추려면 API부터 다시 봐야 했어요. Game Mate에는 채팅 SSE가 있고 사진 서비스에는 프로세스 안에서 도는 주기 작업이 있었어요. 이걸 옮긴 환경에서 어떻게 실행할지까지 생각해야 했어요.

Hyperdrive도 처음에는 DB를 대신해 주는 건가 싶었어요. 설명을 보니 [이미 있는 DB의 연결과 쿼리를 가속하는 서비스](https://developers.cloudflare.com/hyperdrive/)였어요. 결국 PostgreSQL을 둘 곳은 따로 필요했어요.

다시 EC2로 돌아올 때의 작업도 물어봤어요. 같은 컨테이너와 PostgreSQL을 쓰는 경우와, 특정 플랫폼에 맞춰 API를 바꾼 경우는 돌아오는 데 드는 수고도 달랐어요.

결국 일단 EC2 small에 넣고 지켜보기로 했어요. 이미 Node 서버와 Docker 배포 구성을 만들어 둔 상태였고, Terraform과 S3, IAM도 AWS 기준으로 준비하고 있었어요. 다른 클라우드를 더 붙이기보다는 이걸 먼저 마무리하기로 했어요.

사용량 과금도 신경 쓰여요. 작은 서비스라도 반복 호출이 많아지면 요금이 늘 수 있으니까요. [Workers 문서](https://developers.cloudflare.com/workers/platform/pricing/#custom-limits)도 이런 공격에 대비한 실행당 CPU 제한을 안내해요. 다만 한 번의 실행을 제한해도 전체 호출 수에 따른 비용은 남아요. 서버리스를 다시 검토하면 호출량을 어디서 제한할지도 같이 보려고 해요.

## small 한 대에 DB까지 넣으면 괜찮을까

RDS를 빼고 PostgreSQL도 같은 EC2의 컨테이너에서 실행하도록 바꿨어요. 서버가 멈추면 두 서비스와 DB가 같이 멈추는 구성이에요. 비용은 줄일 수 있지만 백업이나 복구는 제가 챙겨야 했어요.

```text
EC2 한 대
  Caddy :443
    ├─ Game Mate Web ─ Game Mate API ─┐
    └─ 사진 커뮤니티 Web ─ 사진 API ──┤
                                    └─ PostgreSQL 컨테이너
                                         ├─ game_feedback DB
                                         └─ photo_contest DB
별도 EBS 볼륨       PostgreSQL 데이터
비공개 미디어 S3    서비스별 파일 경로
별도 백업 S3        배포 전 DB 덤프
```

블로그는 이 서버에 넣지 않고 Vercel에 따로 두기로 했어요. PostgreSQL은 하나지만 서비스별 DB와 계정은 나눴고, API 실행 계정과 migration 계정도 따로 뒀어요.

[t3.small로 시작하는 설정](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/variables.tf)은 메모리 2GiB에 swap 2GiB예요. Caddy와 PostgreSQL, 두 서비스의 Web·API 컨테이너에 걸어 둔 메모리 한도를 합치면 약 3.1GiB라서 이 숫자도 확인했어요.

한도만큼 메모리를 미리 잡아 두는 건 아니지만, 동시에 많이 쓰면 2GiB로는 부족해요. swap을 계속 쓰거나 OOM으로 컨테이너가 죽으면 4GiB로 올리기로 했어요. 실제로 어느 정도까지 버티는지는 부하를 넣어 봐야 해요.

월 비용도 인스턴스 가격만 보면 안 됐어요. EBS와 공인 IPv4, 스냅샷, S3 저장·요청·전송 비용까지 같이 봤어요. 지금 계산한 금액은 예상치라 실제 청구액은 운영하면서 확인하려고 해요.

## DB를 직접 돌리기로 했으니 백업도 필요했어요

DB 데이터는 루트 디스크와 분리한 암호화 EBS 볼륨에 두기로 했어요. `/srv/side-postgres`에 마운트하고, 그 안에 볼륨을 확인할 표시 파일을 둬요. 표시 파일이 없으면 DB 시작을 멈추게 했어요. 마운트가 빠진 상태에서 루트 디스크에 빈 DB가 생기는 일을 막기 위해서예요.

볼륨 스냅샷은 매일 만들고 기본 7개를 남기도록 했어요. 배포할 때는 migration 직전에 해당 서비스 DB를 `pg_dump`로 떠서 별도의 S3 백업 버킷에 올려요. 덤프를 만들거나 올리는 데 실패하면 migration도 멈춰요. [배포·백업 스크립트](https://github.com/jingeon27/side-project/tree/65c3d13a/deploy/shared-instance/scripts)에 이 순서를 넣었어요.

롤백도 다시 봤어요. 이전 앱 이미지를 띄운다고 이미 적용한 migration까지 취소되는 건 아니었어요. 그래서 이전 앱이 변경된 스키마에서도 동작하는지 검사하고, DB를 복원하는 작업은 따로 다루도록 했어요.

다만 백업 파일을 남기는 것까지 준비한 거예요. 실제 AWS에서 스냅샷으로 볼륨을 복원하고 덤프를 새 DB에 넣어보는 작업은 아직 남아 있어요. RDS의 시점 복구처럼 쓸 수 있는 구성도 아니고요.

## S3 권한을 넣었는데도 CI가 실패했어요

미디어는 기존 S3 버킷 하나에서 프로젝트별로 폴더를 나눠 쓰고 싶었어요. 처음 코드는 버킷이 서비스마다 따로 있다고 가정하고 있어서, 이 부분부터 바꿨어요.

```text
media-bucket/
  game-feedback/
    production/...
    ci/...
  photo-contest/
    production/...
    ci/...
backup-bucket/
  postgres/...
```

운영 키는 자기 서비스의 `production/` 아래만 읽고 쓰게 했어요. 테스트는 `ci/` 아래에 실행별 경로를 만들어 사용해요. 콘솔에서는 폴더처럼 보이지만 실제로는 [객체 이름의 접두사](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-prefixes.html)라서, 이름을 나눴다고 권한까지 나뉘는 건 아니었어요.

처음 넣은 IAM 정책에는 `GetObject`, `PutObject`, `DeleteObject`가 있었어요. 그런데 CI는 업로드 전에 목록도 조회하고 있었고, 그 권한이 빠져 있었어요. 여기서 버킷 ARN과 객체 ARN의 차이를 다시 확인했어요.

| 작업 | Resource | 경로 제한 |
| --- | --- | --- |
| `GetObject`, `PutObject`, `DeleteObject` | `arn:aws:s3:::media-bucket/game-feedback/production/*` | 객체 ARN에 경로를 적어요 |
| `ListBucket` | `arn:aws:s3:::media-bucket` | `s3:prefix` 조건을 붙여요 |

`.../game-feedback/`만 적으면 그 안의 파일 전체를 가리키는 게 아니었어요. 파일에는 `*`까지 붙여야 했고, 목록 조회는 버킷 ARN에 권한을 준 뒤 접두사로 제한해야 했어요. 수정한 [IAM 정책](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/iam.tf)에는 두 항목이 따로 있어요.

브라우저 업로드에서는 CORS 문제도 있었어요. 테스트를 실행하는 origin이 버킷에 허용돼 있지 않아서 업로드가 막혔어요. 이때도 IAM과 CORS를 따로 봐야 했어요. [CORS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/cors.html)는 브라우저의 교차 출처 접근 설정이고, S3 파일을 사용할 권한은 IAM과 서명이 결정해요.

백업 버킷은 미디어와 분리했어요. EC2 역할에는 `postgres/` 아래에 덤프를 올리는 권한만 주고, 기존 덤프를 읽거나 삭제하는 권한은 주지 않았어요.

## R2도 알아봤어요

R2도 S3 호환이라고 해서 현재 업로드를 그대로 쓸 수 있는지 물어봤어요. 두 서비스는 presigned POST 정책에 크기 제한을 넣어서 파일을 올리고 있었어요.

[R2 공식 문서](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)에는 GET, HEAD, PUT, DELETE는 지원하지만 HTML 폼 방식의 POST는 지원하지 않는다고 나와 있어요.

옮기려면 PUT으로 바꾸고 업로드 조건과 완료 검사를 다시 확인해야 했어요. 우선은 S3를 유지하기로 했어요. 나중에 미디어 전송 비용이 많이 나오면 그때 다시 비교하려고 해요. 저장소를 바꾼다고 EC2까지 같이 옮길 필요는 없으니까요.

## API 도메인을 추가하면서 쿠키까지 바꾸지는 않았어요

웹과 별도로 API 도메인도 두기로 했어요. 각 서비스에 웹 호스트와 `api.` 호스트를 두고 Caddy가 해당 컨테이너로 요청을 넘겨요.

브라우저에서는 기존처럼 같은 출처의 `/api`나 `/backend`를 사용해요. 세션 쿠키도 웹 호스트의 host-only 쿠키를 유지했어요. 사진 서비스의 GraphQL 변경 요청은 웹 프록시를 거쳐서 Next 캐시를 갱신하는 처리도 그대로 타게 했어요.

웹 요청을 받는 포트는 Caddy의 80/443으로 모았어요. Web과 API는 서비스별 Docker 네트워크에 두고, DB 네트워크에는 API와 운영·migration 컨테이너만 연결했어요. Caddy나 Web이 DB에 직접 붙을 일은 없었어요. [프록시와 네트워크 설정](https://github.com/jingeon27/side-project/tree/65c3d13a/deploy/shared-instance)에 같이 들어 있어요.

## Terraform으로 인프라도 코드로 관리했어요

Terraform을 도입해 EC2와 네트워크, PostgreSQL 데이터용 EBS 볼륨, IAM 정책과 백업 버킷을 코드로 정의했어요. 콘솔에서 바꾼 설정을 따로 기억하는 대신, 인프라 구성과 변경 내역도 저장소에 남기는 IaC 방식으로 관리하기로 했어요.

처음에는 Lightsail도 고려했어요. 최종 배포 대상을 EC2로 정한 뒤에는 Lightsail용 단독 배포 구성과 남아 있던 스크립트, 문서 참조도 제거했어요. 선택한 배포 방식에 맞춰 관리할 구성을 정리했어요.

역할을 알아보기 어려운 변수명도 고쳤어요. 어떤 값을 어디에 쓰는지 이름에서 드러나도록 정리하고, 예제 파일과 안내서도 같은 이름으로 맞췄어요.

Terraform은 서버와 네트워크 같은 기반 환경을 관리하고, GitHub Actions는 이미지를 빌드해 기존 EC2에 SSH로 배포 작업을 전달하도록 나눴어요. 앱을 배포할 때는 그 서버 안의 컨테이너를 새 버전으로 교체해요.

기존 미디어 버킷은 Terraform 관리 대상에서 제외하고, DB 덤프를 받을 백업 버킷은 따로 관리해요. 처음 서버를 준비할 때 할 일은 [Terraform 안내서](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/README.md)에 적어 뒀어요.

## 실제 서버에서 봐야 할 것들

[CloudWatch 설정](https://github.com/jingeon27/side-project/blob/65c3d13a/deploy/shared-instance/terraform/monitoring.tf)에는 인스턴스 상태 검사 실패 시 재부팅과 CPU 크레딧 부족 알람을 넣었어요. 서버가 멈추면 앱에서 오류를 보낼 수도 없어서 서버 쪽 확인도 필요했어요. 알림 메일은 주소를 넣은 뒤 구독 확인까지 해야 해요.

아직 실제 계정에 인프라를 적용하고, 첫 부팅에 볼륨이 제대로 붙는지 확인하는 작업이 남아 있어요. 백업 복원과 부하 테스트도 해봐야 하고요. 그때 메모리와 swap, 컨테이너 종료, 응답 시간을 보고 small로 시작해도 괜찮을지 확인하려고 해요.
