Game Mate와 피식의 배포를 준비하면서 가장 먼저 줄이고 싶었던 건 고정 비용이었어요. 앱은 EC2 한 대에, PostgreSQL은 RDS에 두는 구성이었는데 DB까지 같은 서버에 넣으면 어떨까 생각했어요. 서비스마다 서버와 DB를 따로 마련하기보다, 사용자가 적은 동안에는 한 대를 함께 쓰는 쪽부터 검토했어요.

비교할 때는 가성비와 가용성, 유지보수 비용을 함께 봤어요. 같은 비용으로 필요한 기능을 얼마나 유지할 수 있는지, 한 곳이 멈췄을 때 어디까지 중단되는지, 배포와 변경 때마다 어떤 작업이 필요한지가 기준이었어요. 서버 요금만 낮추고 이전과 운영에 더 많은 일이 생긴다면 전체 비용을 줄였다고 보기 어려웠어요.

인프라를 구성하는 실제 작업은 에이전트에게 맡겼어요. AWS 리소스를 조회하고 Terraform을 작성해 적용하는 일부터 Docker와 Caddy의 배포 구성을 만드는 일까지 에이전트가 진행했어요. 저는 비용과 구성 방향을 정하고, 필요한 인증과 권한을 허용한 뒤 결과를 보고 추가로 확인할 부분을 요청했어요.

## CLI와 설정 파일로 인프라를 구성했어요

에이전트에게 작업을 맡기려면 설정을 명령으로 실행하고 결과도 확인할 수 있어야 했어요. AWS CLI는 리소스 상태와 적용 결과를 확인하는 데 쓰고, 반복해서 만들 기반 환경은 Terraform으로 정의했어요. EC2와 네트워크, PostgreSQL 데이터용 EBS, IAM 정책과 백업 버킷이 여기에 들어가요. [Terraform 구성](https://github.com/jingeon27/side-project/blob/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance/terraform/README.md)에 리소스와 적용 순서를 남겼어요.

서버 안에서 실행할 구성은 Docker와 Compose로 관리했어요. 서비스별 Web과 API, PostgreSQL, Caddy를 컨테이너로 나누고 이미지와 환경변수, 네트워크와 볼륨을 파일에 적었어요. Terraform의 첫 부팅 스크립트는 Docker와 Compose 설치, 데이터 볼륨 마운트와 swap 준비를 맡아요. 이후 앱을 배포할 때는 이 기반 환경 위에서 컨테이너를 교체해요.

Caddy는 도메인별로 요청을 알맞은 컨테이너에 보내고 HTTPS를 처리해요. 도메인과 외부 접근 조건을 맞추면 [인증서 발급과 갱신을 자동으로 처리](https://caddyserver.com/docs/automatic-https)할 수 있어서, 인증서를 따로 갱신하는 작업도 줄일 수 있었어요. 에이전트는 Caddyfile과 Compose 설정을 함께 다뤘고, 프록시 설정을 바꿀 때는 검증을 거쳐 다시 읽도록 스크립트에 넣었어요.

이렇게 기반 환경은 Terraform으로, 서버 안의 실행 구성은 Compose와 Caddyfile로 남겼어요. 기존 미디어 버킷은 Terraform이 새로 만드는 대상에서 빼고 별도 설정으로 관리했어요. 사람이 콘솔에서 하나씩 설정하는 일을 줄이되, 어느 도구가 어떤 설정을 관리하는지는 구분한 거예요.

반복되는 앱 배포는 GitHub Actions에 맡겼어요. main에 반영한 코드를 검증하고 이미지를 게시한 뒤, [SSM 터널 위의 SSH로 기존 EC2에 배포](https://github.com/jingeon27/side-project/blob/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance/README.md#외부-ssh를-열지-않는-ssm-cd)해요. GitHub는 OIDC로 AWS의 임시 자격 증명을 받고, 서비스 환경 파일은 GitHub Environment의 Secret에서 전달해요. 매번 서버에 들어가 명령을 입력하는 대신, 백업과 migration을 거쳐 컨테이너를 교체하는 순서를 스크립트로 실행하게 했어요.

## 두 서비스는 EC2를 공유하고 블로그는 분리했어요

한 대를 공유한다는 건 두 서비스를 하나의 앱으로 합친다는 뜻은 아니에요. Game Mate와 피식은 각각 Web과 API 컨테이너를 갖고, PostgreSQL 프로세스 하나 안에서 DB와 계정을 나눠 써요. API 실행 계정과 migration 계정도 따로 두었어요.

```text
EC2 한 대
├─ Caddy: 도메인별 HTTPS와 요청 전달
├─ Game Mate: Web + API → game_feedback DB
├─ 피식: Web + API → photo_contest DB
└─ PostgreSQL: 데이터는 별도 EBS 볼륨에 저장

미디어 S3: 서비스별 접두사로 파일 구분
백업 S3: 배포 전 DB 덤프 보관
Vercel: 블로그 별도 배포
```

앱의 Docker 네트워크도 서비스별로 나눴어요. 각 API는 자기 서비스의 내부 DB 네트워크로 PostgreSQL에 연결하고, Web과 Caddy는 DB 네트워크에 들어가지 않아요. 컨테이너마다 실제로 필요한 연결만 허용했어요.

블로그는 서비스 API나 PostgreSQL 없이 저장소의 MDX 글을 빌드해서 제공하는 구조예요. 그래서 Next.js 앱을 Vercel에 따로 배포했어요. 현재는 [main에 반영한 변경만 Git 연동으로 배포](https://github.com/jingeon27/side-project/blob/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/projects/blog/apps/web/vercel.ts)하도록 했어요. develop과 PR에서는 검증을 하고, 공개 블로그의 반영 시점은 main으로 맞췄어요.

이렇게 나누면 블로그의 빌드와 배포를 두 서비스의 컨테이너 교체와 따로 진행할 수 있어요. EC2 호스트가 멈추더라도 블로그가 같은 이유로 함께 중단되지는 않고요. EC2에서 관리할 컨테이너와 필요한 자원을 늘리지 않아도 된다는 점도 고려했어요.

EC2를 공유하면 서버와 DB를 서비스별로 따로 둘 때보다 고정 비용을 줄일 수 있지만, CPU와 메모리도 함께 써요. 한 서비스의 부하가 다른 서비스에 영향을 줄 수 있고, 호스트가 멈추면 두 서비스와 DB가 함께 멈춰요. 네트워크와 계정을 나누는 것만으로 이 장애 범위까지 나뉘지는 않아요. 초기 비용과 관리할 서버 수를 줄이는 대신, 이 공통 장애점을 받아들인 선택이에요.

[t3.small로 시작하는 설정](https://github.com/jingeon27/side-project/blob/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance/terraform/variables.tf)은 메모리 2GiB와 swap 2GiB를 사용해요. Caddy와 PostgreSQL, 두 서비스의 Web과 API 컨테이너 한도를 합하면 약 3.1GiB예요. 한도는 미리 예약한 메모리는 아니지만, 모두 상한에 가까워지면 물리 메모리로 감당할 수 없어요. swap을 계속 쓰거나 OOM으로 컨테이너가 죽으면 4GiB로 올리기로 했어요. 한 서비스만 계속 자원을 많이 쓰게 되면 그 서비스나 DB를 분리하는 것도 다음 선택지가 돼요.

비용을 비교할 때는 인스턴스 요금에 EBS와 공인 IPv4, 스냅샷, S3 저장과 요청, 전송 요금을 더해서 봤어요. RDS를 빼면 백업과 복구를 직접 챙겨야 하므로, 그 작업도 유지보수 비용에 포함했어요. Terraform과 스크립트로 반복 작업을 줄이고 백업과 복구 절차를 준비했지만, 이것이 서버 이중화나 무중단 운영을 대신하지는 않아요.

## Lightsail보다 EC2가 이번 구성에 맞았어요

Lightsail은 서버와 디스크, 전송량을 묶은 요금제로 시작하기 편해요. 간단한 서버 하나를 띄우는 데에는 충분히 검토할 만했어요. 다만 이번에는 서버를 만드는 것뿐 아니라 IAM 권한과 관리 접속, DB 볼륨과 백업까지 같은 구성 안에서 다루고 싶었어요.

배포와 관리에는 외부 SSH 포트를 열지 않는 SSM 접속 경로를 쓰고, DB 덤프는 EC2 인스턴스 역할로 S3에 올리도록 했어요. DB 데이터용 EBS와 일일 스냅샷 정책, 보안 그룹도 Terraform으로 함께 관리해요. Lightsail에서도 Systems Manager를 사용할 수 있지만 [하이브리드 활성화로 등록하는 절차](https://repost.aws/knowledge-center/add-lightsail-to-systems-manager)가 필요해요. 준비한 EC2 인스턴스 역할과 SSM 구성을 그대로 쓰는 편이 이번 작업에는 더 잘 맞았어요.

나중에 메모리나 네트워크 구성을 바꿀 때도 EC2 쪽에서 이어서 관리하기로 했어요. AWS의 [Lightsail에서 EC2로 이전하는 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-export-to-ec2.html)에서도 더 다양한 인스턴스와 세밀한 네트워크 구성을 EC2의 선택 이유로 설명해요. 이번에는 EC2의 역할과 SSM, EBS 구성을 유지해 플랫폼을 바꾸며 다시 확인할 설정을 줄이는 쪽을 택했어요. 월 요금과 함께 이후 변경에 드는 작업도 유지보수 비용으로 본 거예요. 사용하지 않을 Lightsail 설정과 스크립트는 지워 배포 경로를 EC2로 정리했어요.

## Lambda와 Workers는 API를 옮기는 작업까지 필요했어요

서버를 직접 관리하지 않는 Lambda와 Workers도 비교했어요. 여기서 걸린 건 API가 단순히 요청을 받고 응답만 하는 구조가 아니라는 점이었어요. Game Mate는 채팅 SSE 연결과 연결된 이용자 목록을 API 프로세스 안에서 관리하고, 피식은 같은 프로세스의 타이머로 정리 작업과 대회 종료 처리, 알림을 주기적으로 실행해요.

Lambda도 [응답 스트리밍을 지원](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)해요. 다만 HTTP 요청을 처리하는 실행에는 [최대 15분의 제한](https://docs.aws.amazon.com/lambda/latest/dg/web-functions-revisions-timeout.html)이 있어요. 채팅 연결의 종료와 재연결을 확인해야 하고, 여러 실행 환경으로 나뉠 때 어느 연결에 새 메시지를 전달할지도 별도로 풀어야 해요. 요청이 없는 동안에도 돌아야 하는 주기 작업은 API 프로세스의 타이머에서 분리해 실행 경로를 마련해야 하고요.

[Lambda의 컨테이너 이미지 지원](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html)도 Compose 구성을 통째로 올리는 방식과는 달라요. 이미지를 함수의 실행 방식에 맞춰야 하고 DB를 둘 곳과 연결 관리도 따로 정해야 해요. 서버 비용을 비교하는 일에 API와 작업 스케줄러를 옮기는 일까지 더해지는 셈이었어요.

Workers 역시 [Node HTTP 서버를 연결하는 기능](https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/)을 제공하고, [연결이 유지되는 동안 응답을 스트리밍](https://developers.cloudflare.com/workers/platform/limits/#duration)할 수 있어요. 다만 기존 Docker 이미지를 실행하는 [Cloudflare Containers](https://developers.cloudflare.com/containers/)와는 실행 환경이 달라요. API의 의존성과 진입점을 Workers에 맞춰 확인하고, 프로세스 안에 둔 연결 상태와 주기 작업을 어디서 관리할지 다시 정해야 했어요. 주기 작업을 옮긴다면 [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/) 같은 실행 방식도 함께 검토해야 해요.

Hyperdrive가 DB까지 대신해 주는지도 확인했어요. [기존 DB의 연결과 쿼리를 가속하는 서비스](https://developers.cloudflare.com/hyperdrive/)라서 PostgreSQL을 운영할 곳은 여전히 필요했어요. API의 실행 비용만 보고 비교하면 DB 비용과 이전 작업이 빠질 수 있었어요.

그래서 이번에는 Node 서버와 Docker, PostgreSQL을 유지하며 배포 구성을 완성하기로 했어요. 지금의 채팅과 주기 작업을 유지하면서 초기 고정 비용과 이전에 드는 작업을 함께 줄이는 쪽을 택한 거예요. 대신 DB를 직접 운영하는 데 필요한 저장소와 복구 절차를 배포 구성에 포함했어요.

## DB를 직접 돌리기로 했으니 백업도 필요했어요

DB 데이터는 루트 디스크와 분리한 암호화 EBS 볼륨에 두기로 했어요. `/srv/side-postgres`에 마운트하고, 그 안에 볼륨을 확인할 표시 파일을 둬요. 표시 파일이 없으면 DB 시작을 멈추게 했어요. 마운트가 빠진 상태에서 루트 디스크에 빈 DB가 생기는 일을 막기 위해서예요.

볼륨 스냅샷은 매일 만들고 기본 7개를 남기도록 했어요. 배포할 때는 migration 직전에 해당 서비스 DB를 `pg_dump`로 떠서 별도의 S3 백업 버킷에 올려요. 덤프를 만들거나 올리는 데 실패하면 migration도 멈춰요. [배포와 백업 스크립트](https://github.com/jingeon27/side-project/tree/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance/scripts)에 이 순서를 넣었어요.

복구는 앱 이미지를 되돌리는 것과 나눴어요. 이전 버전의 컨테이너를 띄워도 이미 적용한 migration은 남아요. 그래서 이전 앱이 바뀐 스키마에서 동작하는지 확인하는 절차와, DB를 백업으로 복원하는 절차를 따로 두었어요.

이 백업은 RDS처럼 특정 시점으로 되돌리는 방식은 아니에요. 스냅샷으로 볼륨을 복원하거나 덤프를 새 DB에 넣는 방식이에요. 실제 AWS에서 그 복원을 해 보는 단계는 아직 남아 있어요.

## S3 권한을 넣었는데도 CI가 실패했어요

미디어는 기존 S3 버킷 하나에서 프로젝트별로 폴더를 나눠 쓰고 싶었어요. 처음 코드는 버킷이 서비스마다 따로 있다고 가정하고 있어서, 에이전트에게 이 가정부터 바꾸도록 했어요.

```text
media-bucket/
  game-feedback/
    production/...
    ci/...
  photo-contest/
    production/...
    ci/...
backup-bucket/
  postgres/...
```

운영 키는 자기 서비스의 `production/` 아래만 읽고 쓰게 했어요. 테스트는 `ci/` 아래에 실행별 경로를 만들어 사용해요. 콘솔에서는 폴더처럼 보이지만 실제로는 [객체 이름의 접두사](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-prefixes.html)라서, 이름을 나눴다고 권한까지 나뉘는 건 아니었어요.

처음 IAM 정책에 GetObject, PutObject, DeleteObject를 넣었는데도 CI 업로드가 실패했어요. 업로드 전에 목록을 조회하고 있었기 때문이에요. 파일 하나를 다루는 권한과 버킷에서 이름을 찾는 권한은 Resource부터 달랐어요.

| 작업 | Resource | 경로 제한 |
| --- | --- | --- |
| `GetObject`, `PutObject`, `DeleteObject` | `arn:aws:s3:::media-bucket/game-feedback/production/*` | 객체 ARN에 경로를 적어요 |
| `ListBucket` | `arn:aws:s3:::media-bucket` | `s3:prefix` 조건을 붙여요 |

`.../game-feedback/`만 적으면 그 안의 파일 전체를 가리키는 게 아니었어요. 파일에는 `*`까지 붙여야 했고, 목록 조회는 버킷 ARN에 권한을 준 뒤 접두사로 제한해야 했어요. 수정한 [IAM 정책](https://github.com/jingeon27/side-project/blob/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance/terraform/iam.tf)에는 두 항목이 따로 있어요.

IAM을 고친 뒤에는 브라우저 업로드에서 CORS도 봐야 했어요. 테스트 origin이 허용되지 않아 막힌 경우였어요. [CORS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/cors.html)는 브라우저가 다른 출처로 접근할 수 있는지 정하고, 실제 객체를 사용할 권한은 IAM과 서명이 정해요. 둘 중 하나만 맞춰서는 업로드가 되지 않았어요.

백업 버킷은 미디어와 분리했어요. EC2 역할에는 `postgres/` 아래에 덤프를 올리는 권한만 주고, 기존 덤프를 읽거나 삭제하는 권한은 주지 않았어요.

## 미디어 저장소를 옮길 때 바꿔야 할 것도 봤어요

R2도 S3 호환이라고 해서 현재 업로드를 그대로 쓸 수 있는지 물어봤어요. 두 서비스는 presigned POST 정책에 크기 제한을 넣어서 파일을 올리고 있었어요.

[R2 공식 문서](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)에는 GET, HEAD, PUT, DELETE는 지원하지만 HTML 폼 방식의 POST는 지원하지 않는다고 나와 있어요.

S3 호환이라는 말만으로 지금 업로드를 그대로 옮길 수는 없었어요. PUT으로 바꾸려면 POST 정책에 넣었던 조건과 업로드 완료 검사를 다시 다뤄야 해요. 우선 S3를 유지하고, 미디어 전송 비용 때문에 저장소를 바꿀 필요가 생기면 그때 이 작업을 함께 비교하기로 했어요. 서버 실행 환경을 정하는 일과는 나눠서 판단했어요.

## API 도메인을 추가하면서 쿠키까지 바꾸지는 않았어요

웹과 별도로 API 도메인도 두기로 했어요. 각 서비스에 웹 호스트와 `api.` 호스트를 두고 Caddy가 해당 컨테이너로 요청을 넘겨요.

브라우저에서는 기존처럼 같은 출처의 `/api`나 `/backend`를 사용해요. 세션 쿠키도 웹 호스트의 host-only 쿠키를 유지했어요. 피식의 GraphQL 변경 요청은 웹 프록시를 거쳐서 Next 캐시를 갱신하는 처리도 그대로 타게 했어요.

웹 요청을 받는 포트는 Caddy의 80/443으로 모았어요. Web과 API는 서비스별 Docker 네트워크에 두고, DB 네트워크에는 API와 운영, migration 컨테이너만 연결했어요. Caddy나 Web이 DB에 직접 붙을 일은 없었어요. [프록시와 네트워크 설정](https://github.com/jingeon27/side-project/tree/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance)에 같이 들어 있어요.

## 실제 서버에서 봐야 할 것들

[CloudWatch 설정](https://github.com/jingeon27/side-project/blob/90d78ae201c9872a3823a0bd4c1244e05cc14e8e/deploy/shared-instance/terraform/monitoring.tf)에는 인스턴스 상태 검사 실패 시 재부팅과 CPU 크레딧 부족 알람을 넣었어요. 서버가 멈추면 앱에서 오류를 보낼 수도 없어서 서버 쪽 확인도 필요했어요. 알림 메일은 주소를 넣은 뒤 구독 확인까지 해야 해요.

기반 환경을 설정한 뒤에도 실제 서버에서 확인할 일이 남아요. 데이터 볼륨이 붙지 않았을 때 DB가 멈추는지, 백업으로 복원할 수 있는지는 별도로 확인해야 해요. 부하를 넣었을 때의 swap과 컨테이너 종료, 응답 시간도 small을 계속 쓸지 판단하는 데 필요해요. 에이전트가 설정과 실행을 맡아도, 패치와 자원 관리, 복구 확인에 드는 운영 작업은 계속 남아요.
