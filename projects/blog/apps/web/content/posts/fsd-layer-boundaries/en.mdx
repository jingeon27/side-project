Every new query hook reopened the entities-or-features discussion. The frontends of the benefits portal and the admin monorepo were both organized with FSD. The portal is where users find and apply for hospital programs; the monorepo holds the admin apps that hospitals and the operations team use.

FSD (Feature-Sliced Design) is a folder convention that divides frontend code into stacked layers by role. The standard layers stack as below, and a slice can only import from layers beneath its own.

```text
app       Code that starts the app, such as routing and providers
pages     Screens
widgets   Large UI blocks attached to several screens
features  The main interactions users perform
entities  Real-world concepts the product handles
shared    Common code that knows no domain
```

Inside a layer, code is divided into slices, folders named after a domain. Other slices may import only what a slice exposes, and that exposed surface is called its Public API. A slice's `index.ts` usually plays this role, and a file like it that gathers and re-exports other files is called a barrel.

The portal had entities, features, widgets, and pages; admin followed the same descriptions without pages. The names were familiar, but placing an actual file got different answers from different people, and I could not explain where a new file belonged either.

What follows is the move in the order it happened. Admin changes had merged into develop while the portal move was still on a separate branch.

## My rule: code that seemed reusable

I described entities as code that several features would probably reuse. Looking back, that was judging reusability by feel. It required predicting callers that did not exist yet, so classifications kept shifting. API types landed in entities, the hooks for the same query in features, and display UI in both entities and widgets.

Admin screens were murkier still: changing one save request also changed queries, forms, and buttons. Even with "domains are entities, user actions are features" memorized, the names alone did not tell me which code was domain and which was user action.

Placing filters got stuck too. Admin's filter widgets fetched their own options, so the code assembling them with lists had to sit above widgets, but features, which did that work, sat below them. With no layer able to compose filters and lists in one place, the composition ended up in app's `page.tsx`, along with the domain's filter-options arrays.

## Late August: dropping entities

This was not simply a failure to understand the definitions. The documentation describes entities as real-world concepts the product handles and features as the main interactions users perform, which is easy enough to follow. But both projects mostly fetched server-defined data and displayed it. Finding one query's API, schema, Query Options (an object bundling a TanStack Query key and request function), and UI across two layers was the more cumbersome part.

The official guidance does not require every layer and allows omitting entities when client business logic is thin. After reading that, I decided to try this arrangement.

```text
app → pages → widgets → features → shared
```

I chose based on whether the place for the next file could be explained in one sentence, more than on keeping every standard layer. Server-domain APIs, schemas, Query Options, state, and UI moved together into features. Taking on what entities used to do makes features here broader than the documentation describes. Pages went above widgets so self-fetching widgets and lists could be arranged without borrowing route files.

Pages hold a screen's JSX and interactions, and I set the expectation at the same time that a screen's composition should be readable directly from its JSX. Features keep logic that reads naturally as a procedure, such as call ordering and state transitions. I narrowed widgets to UI that attaches independently to several screens, and shared to code that knows no domain. Providers, SDK initialization, and routing went to app.

## August 31: moving day

I first emptied the existing features into pages, then moved entities into features. The reverse order collides on slice names. I merged overlapping barrel exports by hand.

```text
before
entities  Some APIs, models, and UI classified as domains
features  Some hooks, forms, and UI classified as user actions

after
features  APIs, models, schemas, and domain UI grouped by server domain
pages     Screen interactions and composition
```

While fixing module paths I searched only for aliased imports and missed one relative path. The final typecheck found it.

The same day turned up something typecheck could not find. In the Next.js App Router, files are Server Components by default. Hooks that use state work only in Client Components, and a `use client` directive at the top of a file marks the boundary between server and client. A barrel re-exports many modules, so a server file importing one thing from it can pull the other modules into the server module graph as well. The types still line up, so type checks say nothing.

In the portal, a moved slice's domain barrel exported a hook without `use client`. Typecheck and ESLint passed, and the whole E2E suite failed. React Hook Form modules needed the directive as well before the routes stopped returning 500.

Cross-page imports surfaced after the move too. Old features had been importing each other within their layer. Once those files lived in pages, the same imports became direct references between screens. I enabled `fsd/no-cross-page` as a warning and raised it to error after working out where each reference should go.

For parent screens importing child screens, such as program, search, and review writing under a detail page, I changed the folder nesting. What had been sibling slices in pages were grouped by how the route composed them, which made those imports internal to one slice.

I initially planned to move the remaining UI to widgets. Opening the remaining references, though, showed that review items and category lists directly rendered server DTOs (the data shapes a server returns), so they went to each domain's `features/{domain}/ui`. Maps, banners, and terms used by several screens followed the same criterion.

Custom ESLint rules had already been blocking wrong-direction layer imports and deep imports into another slice's internals before this work. Lint does not decide whether a component is a screen fragment or domain UI. Automating a call that takes reading the code would push people into stranger folders just to avoid false positives. I make that call from the code, then let rules check import direction and Public API use.

## September 2: a counterexample just over an hour later

Both projects had started out mirroring route paths as folders. That afternoon the portal even gained a rule: "collapse a dynamic segment into detail only when it must be told apart from a sibling screen." A dynamic segment is a path piece holding a URL value, such as `[id]`. Just over an hour later a counterexample appeared: adding a sibling screen later would make the existing folder name break the rule, and nobody renames a folder at that point. I ended up dropping the rule and defining one folder as one screen. Pieces that do not point to a screen, such as route groups and version strings, do not become folders, and one screen can serve several routes.

Admin, the same afternoon, matched pages one-to-one with URLs because people so often find screens by menu and URL. It then kept creating empty folders only to preserve the URL shape. Before the day ended, matching URLs became a default rather than a requirement, since the same finished screen can open at another URL and a lint rule would produce only false positives.

## The same day: a 633-second test run

Admin had separate ui, hooks, utils, and types workspace packages. All of it was shared code, chained as `ui → hooks → utils → types`, and callers imported each one separately.

That day I combined them as segments (folders grouped by purpose) inside one shared package. Cookies, environment values, and server-only code kept their own entrypoints, because a general barrel could pull browser-only or server-only dependencies into an Edge bundle, code that runs in the Edge runtime without the full set of Node.js APIs.

```text
packages/shared/src/
├── ui/
├── hooks/
├── utils/
└── types/

@app/shared          ← Public alias for the package name
@app/shared/cookie
@app/shared/env
@app/shared/server
```

Combining the Vitest configuration as well was my mistake. The combined configuration used jsdom, which imitates a browser DOM inside Node.js, so utils tests that had been running in node now ran in jsdom, and the local run took 633 seconds. HTTP client tests that build server authentication headers when there is no `document` failed too, because jsdom has one. Separating node and jsdom projects returned the run to eight seconds and restored passing tests. This only repaired the environment I had changed, and did not make anything faster than before.

## Type checks passed again

August 31 was not the end of it. After moving folders and barrels, typecheck, lint, and Vitest could all pass while the dev server or build failed. Counting August 31, I hit this kind of boundary error four times. The imports those checks followed were not the server graph Next.js built, and the checks and test coverage at the time could not see the difference.

On September 2, starting the dev server showed every route importing the top-level pages barrel returning 500. A review-options hook had reached `pages/index.ts` through `profile/index.ts` and entered the Server Component graph. Here is the idea in reduced form, with the hook and screen names made up for illustration.

```typescript
// pages/profile/index.ts
export { ProfilePage } from './ProfilePage';
export { useReviewOptions } from './useReviewOptions'; // A hook without 'use client'

// pages/index.ts
export { ProfilePage, useReviewOptions } from './profile';

// app/profile/page.tsx: a Server Component. Importing one screen still goes through the barrel.
import { ProfilePage } from '@/pages';
```

After I removed the hook from the barrel and added `use client`, the routes I reopened answered 200 or 307.

Widget cleanup the next day hit the same kind of problem. Reopening routes showed errors of that kind still there. I added `use client` where needed and limited the login barrel to its actual screens. I also went back over what belonged in widgets. Of seven slices, only global navigation and the chatbot attached independently to several screens. Single-screen pieces moved to pages, while chat and analytics SDK initialization moved to app. I briefly moved the chatbot to pages, then returned it to widgets that day because it was not a screen you open by URL.

In admin, the combined shared barrel was the problem. This one surfaced in `pnpm build` instead of the dev server, and all three apps broke while typecheck, lint, and Vitest passed. A route handler (a Next.js file that receives requests on the server) importing one value from shared pulled in the client UI graph, and the production build failed on modules without `use client`. Afterward I wrote a rule to run `pnpm build` after changing barrel exports or package structure. Opening routes on the dev server was something I did by hand on each portal commit, and I have not written it down as an exit condition.

The same week I separately built an E2E flow from hospital review submission to Back-Office rejection, running two dev servers together. It came out of fixing a bug in the rejection flow, so it was a different task from checking this move, and there is no record of rerunning it against the moved tree. [Another article](/en/blog/plan-gated-ai-workflow) covers it.

## September 4: @page and @common

Even with one folder per screen, I kept mixing up whether code inside was for the current screen or shared by child screens. A folder alone did not say whether it was this path's screen, a child path, or an attached segment. That day I added `@page` and `@common` to separate them.

```text
pages/catalog/search/
├── @page/            ← This screen's slice
│   ├── ui/
│   ├── model/
│   └── lib/
├── @common/          ← Code shared by child screens
├── keyword/@page/
│   ├── KeywordPage.tsx
│   └── ui/ model/ lib/
└── category/@page/
    ├── CategoryPage.tsx
    └── ui/
```

`@page` holds that screen's ui, model, and lib. `@common` holds code its child screens share. These names are examples of grouping screens rather than copied URLs. More widely shared domain code does not keep piling up in `@common`; it moves to features or another suitable lower layer, though having two callers is not by itself a reason to move it.

## Where I now look for a file

The first structure did not survive intact. Admin cut back folder depth that came from following URLs too faithfully, and the portal added the `@page` marker after abandoning route mirroring. Only moving the files for real turned up counterexamples that reading the documentation had not.

Portal lint treats layer direction, Public API, and cross-page references as errors. Admin still warns on the first two and has no cross-page check yet. The folders and checks have not reached the same level in both projects.

I look in features for server APIs, models, and domain UI, and in pages for what a screen draws together. That groups code changed together, instead of making me follow a URL-shaped tree or guess between entities and features. This codebase needed a structure that could explain where the next file goes more than it needed every standard layer.
