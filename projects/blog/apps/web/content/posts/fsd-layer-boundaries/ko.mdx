<Summary>

entities와 features를 나눌 기준이 모호해 파일을 둘 곳을 설명하기 어려웠어요. 실제 사용처를 보고 레이어와 참조 규칙을 다시 정했어요.

</Summary>

새 파일을 entity와 feature 중 어디에 둘지 매번 의견이 갈렸어요. 복지몰에는 entities, features, widgets, pages가 있었고, 관리자 서비스 모노레포도 pages를 뺀 같은 레이어 문서를 따르고 있었어요. 폴더와 설명은 갖춰져 있었지만, 실제 코드의 위치를 정하기에는 기준이 부족했어요.


## 처음 기준은 "재사용될 것 같은 도메인 코드"였어요

초기에 제가 쓴 기준은 "여러 feature에서 재사용될 것 같은 도메인 코드"였어요. 이런 코드를 entities에 뒀는데요. 지금 돌아보면 재사용 가능성을 느낌으로 판단한 셈이에요. 같은 도메인의 API 타입은 entities에 있고 조회 훅은 features에 있거나, 표시용 UI가 entities와 widgets에 나뉘는 일이 생겼어요.

관리자 서비스에서는 더 애매했어요. 조회와 변경, 폼, 화면 조합이 한 업무 안에서 같이 움직였어요. "도메인은 entity, 사용자 행동은 feature"라고 외워도 다음 파일을 어디에 둘지는 여전히 사람마다 달랐어요.

찾기 어려운 것만 문제는 아니었어요. 관리자 서비스의 필터 위젯은 스스로 조회를 해요. 그러니 widgets는 조회 계층 위에 있어야 하는데, 조합을 맡던 features가 widgets 아래였어요. 필터와 목록을 한자리에서 조합할 수 있는 레이어가 없으니 조합이 app의 라우트 파일로 밀렸고, 라우트 파일 하나가 202줄까지 커지면서 도메인 필터 옵션 배열이 page.tsx에 살고 있었어요.

## 그래서 entities를 빼고 pages를 widgets 위에 올렸어요

FSD 문서의 정의 자체가 문제라고 생각하지는 않아요. entities는 제품이 다루는 현실의 개념이고 features는 사용자가 수행하는 주요 상호작용이라는 설명은 이해하기 쉬워요. 다만 두 프로젝트는 서버가 정한 도메인을 프론트엔드에서 조회하고 보여주는 비중이 컸어요. 그 구조에서 API, 스키마, Query Options와 UI를 두 레이어로 나누자 얻는 것보다 찾는 비용이 더 컸어요.

공식 문서에도 모든 레이어를 쓸 필요는 없고, 클라이언트 쪽 비즈니스 로직이 얇으면 entities 없이 구성할 수 있다는 내용이 있어요. 그래서 8월 말에 레이어를 다음과 같이 줄였어요.

```text
app → pages → widgets → features → shared
```

entities를 없애고 한 칸씩 올렸어요. 서버 도메인의 API, 스키마, Query Options, 상태, UI는 features에, 한 화면의 조합은 pages에 둬요. pages를 widgets 위에 놓아 스스로 조회하는 위젯과 목록을 라우트 파일이 아니라 레이어 안에서 조합해요. 표준 레이어를 다 지키는지보다 다음 파일의 자리를 한 문장으로 설명할 수 있는지를 기준으로 골랐어요.

pages는 한 화면의 인터랙션과 조합을 담당해요. 화면 구성이 JSX에서 바로 읽혀야 한다는 기준도 함께 세웠어요. 호출 순서나 상태 전이처럼 절차로 쓰는 것이 자연스러운 도메인 로직은 features에 남겼어요. widgets에는 여러 화면에서 독립적으로 성립하는 UI 블록만 두고, 도메인을 모르는 코드는 shared로 보냈어요. 라우팅과 Provider, SDK 초기화는 app의 몫으로 정리했어요.

실제 이동은 8월 31일에 기존 features를 pages로 먼저 비우는 것부터 시작했어요. 그다음 entities를 features로 옮겼어요. 순서를 반대로 하면 같은 이름의 슬라이스가 충돌했기 때문이에요. 이름이 겹친 배럴 9곳은 기존 export를 직접 합쳤어요.

```text
before
entities  도메인이라고 판단한 일부 API·모델·UI
features  사용자 행동이라고 판단한 일부 훅·폼·UI

after
features  서버 도메인 단위의 API·모델·스키마·도메인 UI
pages     화면 단위의 인터랙션과 조합
```

핵심 이동 커밋 한 건 기준으로 복지몰은 853개 파일, 관리자 서비스 모노레포는 1,659개 파일이 걸렸어요. 모노레포에서 바꾼 모듈 경로는 1,489건, 패키지 참조는 437건이었어요. 별칭 import만 찾아 바꿨다가 상대 경로 하나를 놓쳤고, 마지막 typecheck에서야 발견했어요. 경로를 많이 바꾼다고 검색 결과만 믿고 끝내면 안 되는 이유가 바로 나왔어요.

## 옮긴 날 오후, page 간 import 62건이 드러났어요

옮긴 날 오후에 lint를 켜 보니 한 pages 슬라이스가 다른 pages 슬라이스의 파일을 가져오는 page 간 import가 62건 보고됐어요. 옛 features 슬라이스 22개가 pages로 합쳐지면서, 같은 레이어라 자유롭게 서로를 참조하던 import가 전부 page 간 결합으로 보이게 된 거예요. 처음부터 62건을 전부 error로 만들지는 않았어요. fsd/no-cross-page를 warning으로 켜고 위치를 하나씩 정리하기로 했어요.

62건 중 18건은 부모 라우트의 화면이 자식 라우트의 화면을 가져오던 것이었어요. 상세 화면 아래에 있는 프로그램, 검색, 리뷰 작성 화면이 pages/에서는 형제 슬라이스였거든요. 라우트 구성대로 중첩하자 이 참조는 슬라이스 내부 참조가 되어 사라졌고, 건수는 55에서 39, 다시 37로 줄었어요.

나머지는 계획이 바뀌었어요. 처음에는 "UI 블록은 widgets로 내린다"고 적었는데, 남은 참조를 열어 보니 리뷰 항목이나 카테고리 목록처럼 서버 DTO를 그대로 그리는 도메인 UI였어요. 기준을 "서버와 1:1인 도메인 UI는 features"로 바꾸고 아래로 내렸어요. 이틀 뒤인 9월 2일에는 지도, 배너, 약관처럼 두 화면이 함께 쓰던 마지막 10건도 각 도메인의 features/&#123;domain&#125;/ui로 내려 0건이 됐고, 그때 error로 올렸어요.

레이어 import 방향과 다른 슬라이스 내부를 직접 가져오는 deep import는 이 작업 전부터 custom ESLint 규칙이 이미 막고 있었어요. 반면 컴포넌트가 화면 조각인지 도메인 UI인지까지 lint가 추측하게 하지는 않았어요. 코드를 읽어야 판단할 수 있는 영역까지 자동화하면 오탐을 피하려고 더 이상한 폴더를 만들게 돼요. 합의가 끝난 의존 방향만 lint가 지키도록 했어요.

## 이틀 뒤, 라우트 미러링을 한 시간 만에 철회했어요

두 프로젝트 모두 처음엔 라우트 경로를 그대로 폴더로 옮겼어요. 복지몰은 9월 2일 오후에 "동적 세그먼트는 형제 화면과 구분이 필요할 때만 detail로 접는다"는 규칙까지 적었는데요. 한 시간 남짓 만에 반례가 나왔어요. 형제 라우트가 나중에 생기면 기존 폴더가 규칙 위반이 되는데, 아무도 이름을 안 바꿔요. 규칙을 없애고 pages를 화면 단위로 다시 규정했어요. 한 폴더가 한 화면이고, 라우트 그룹이나 버전 문자열처럼 화면을 가리키지 않는 조각은 폴더로 만들지 않아요. 하나의 화면을 여러 라우트에서 쓰는 것도 허용했어요.

관리자 서비스는 같은 날 오후에 메뉴와 URL로 화면을 찾는 일이 많다는 이유로 pages 경로를 URL과 1:1로 맞췄어요. 그런데 URL 모양을 지키기 위한 얇은 폴더가 계속 생겼어요. 그날 안에 URL 일치는 기본값으로만 남기고 강제하지 않기로 했어요. 같은 완성 화면을 다른 URL에서 열 수도 있어 lint로 걸면 오탐만 나기 때문이에요.

이 과정에서 복지몰의 widgets도 다시 봤어요. 슬라이스 7개 중 "여러 화면에 붙는 독립 UI 블록"이라는 정의에 맞는 것은 전역 내비게이션과 챗봇 둘뿐이었어요. 한 화면에서만 쓰던 조각은 그 화면의 pages 슬라이스로, 채팅 SDK나 분석 SDK 초기화처럼 UI 블록이 아닌 코드는 app으로 갔고, features로 간 것은 없었어요. 챗봇은 이동 당일에 pages로 올렸다가 라우트로 도달할 수 없는 것을 page라 부를 수 없다는 이유로 그날 widgets에 되돌린 적도 있어요.

## shared 네 패키지를 하나로 합치자 테스트가 633초로 늘었어요

관리자 서비스 모노레포의 ui, hooks, utils, types는 각각 별도 workspace 패키지였어요. 모두 shared 레이어인데 ui → hooks → utils → types 순서로 패키지끼리 의존했고, 사용하는 파일에는 import 네 줄이 반복됐어요.

9월 2일에 이들을 shared 패키지 하나로 합치고 내부 세그먼트로 바꿨어요. 다만 cookie와 환경 변수, 서버 전용 코드는 별도 entrypoint로 남겼어요. 공용 배럴을 그대로 쓰면 브라우저나 서버 의존성이 Edge 번들까지 들어올 수 있었기 때문이에요.

```text
packages/shared/src/
├── ui/
├── hooks/
├── utils/
└── types/

@app/shared          ← 패키지 이름은 공개용 가명이에요
@app/shared/cookie
@app/shared/env
@app/shared/server
```

패키지를 합치면서 vitest 설정도 하나로 합쳤는데, 그 설정이 jsdom이라 DOM을 쓰지 않던 utils의 테스트 파일 11개까지 jsdom에서 돌게 됐어요. 합친 직후 이 11개 파일이 633초가 걸렸고, document 유무로 서버 경로를 가르는 테스트 3건은 실패했어요. HTTP 클라이언트의 인증 헤더 테스트가 그중 하나였고요. 두 시간 남짓 뒤 node와 jsdom 프로젝트를 나누자 8초로 돌아왔고 3개도 통과했어요(로컬 단일 실행 기준). 합치기 전 utils는 원래 node에서 돌고 있었으니, 개선이 아니라 합치며 만든 퇴행을 되돌린 거예요.

## 정적 검사가 전부 지나간 경계 오류를 네 번 만났어요

typecheck와 ESLint, Vitest가 전부 성공한 뒤에도 서버, 클라이언트 경계 오류는 남아 있었어요. 당시 검사 설정과 테스트 범위로는 실제 Next.js 모듈 그래프에서 생기는 경계 오류까지 확인하지 못했어요.

첫 번째는 옮긴 날인 8월 31일이었어요. 복지몰에서 옮긴 슬라이스의 도메인 배럴에 'use client' 없는 훅이 실려 typecheck와 ESLint는 지나갔는데 E2E 전체가 실패했어요. 이어 React Hook Form을 쓰는 모듈 14개에도 같은 표시를 달고서야 라우트가 500에서 돌아왔고요.

두 번째는 9월 2일이었어요. dev 서버를 띄우자 최상위 pages 배럴을 import하는 라우트가 전부 500이었어요. 리뷰 옵션 훅이 슬라이스 배럴에 올라가면서 profile/index.ts → pages/index.ts를 타고 서버 컴포넌트 그래프에 들어간 것이 원인이었어요. 훅을 배럴에서 빼고 'use client'를 붙인 뒤 라우트 34개를 다시 열어 전부 200이나 307인 것을 확인했어요.

세 번째는 9월 3일 widgets를 정리하던 중이었어요. 라우트 28개를 다시 열어 같은 종류의 오류 4건을 잡았고, 'use client'를 달고 로그인 슬라이스 배럴은 화면 둘만 내보내도록 줄였어요.

네 번째는 관리자 서비스 모노레포였는데, 이쪽은 dev 서버가 아니라 pnpm build가 세 앱 모두 깨졌어요. 타입 검사와 lint, Vitest 테스트 1,319건이 모두 성공한 상태였는데요. 배럴을 하나로 합치면서 라우트 핸들러가 shared에서 무엇 하나만 가져와도 클라이언트 UI 그래프 전체가 서버 쪽으로 딸려왔고, 'use client'가 없는 모듈 22개가 걸렸어요. 그래서 배럴에 export를 더하거나 패키지를 합쳤으면 pnpm build를 한 번 돌린다는 항목을 관리자 서비스 규칙 문서에 넣었어요. dev 서버로 라우트를 여는 건 복지몰에서 커밋마다 손으로 했고, 아직 어느 문서에도 종료 조건으로 적지는 않았어요.

같은 주에 병원 관리자에서 등록한 검수 요청이 Back-Office에서 반려될 때까지 두 dev 서버를 함께 띄워 도는 횡단 E2E도 만들었어요. 다만 그건 반려 흐름의 버그를 고치다 나온 것이지 이 이동을 위한 것이 아니었고, 옮긴 트리에 대해 다시 돌린 기록도 없어요. 그 E2E 이야기는 [별도 글](/ko/blog/ai가-코드를-잘-짜기-시작했는데-제가-덜-바빠지지는-않았어요)에 적었어요.

## 화면 내부와 하위 화면의 공유 코드를 구분했어요

화면 단위로 옮기고 나서도 폴더만 보면 "이게 이 경로의 화면인지, 하위 경로인지, 부속 세그먼트인지"가 구분되지 않았어요. 9월 4일에 표식을 정했어요.

```text
pages/catalog/search/
├── @page/            ← 이 화면의 slice
│   ├── ui/
│   ├── model/
│   └── lib/
├── @common/          ← 하위 화면이 함께 쓰는 코드
├── keyword/@page/
│   ├── KeywordPage.tsx
│   └── ui/ model/ lib/
└── category/@page/
    ├── CategoryPage.tsx
    └── ui/
```

한 화면의 slice는 @page 안에서 구성하고, 하위 화면이 함께 쓰는 코드는 @common에 뒀어요. 위 폴더명은 설명용 예시예요. URL을 그대로 옮긴 구조가 아니라 화면별로 이름을 붙여 묶은 것이고, @page 안에서는 ui, model, lib처럼 역할을 나눴어요. 여러 화면에서 쓰는 도메인 코드까지 모두 @common에 두지는 않고, 공유 범위에 맞는 하위 레이어로 옮겼어요.

## 다음 작업에는 이 기준을 남겼어요

처음 세운 구조가 그대로 남은 것은 아니에요. 관리자 서비스에서는 URL을 너무 충실히 따라 생긴 폴더 깊이를 다시 줄였고, 복지몰에서는 라우트 미러링을 철회한 뒤 @page 표기를 추가했어요. 전체 파일을 실제로 옮겨 보고 나서야 문서만 읽을 때 보이지 않던 반례를 찾을 수 있었어요.

남긴 자리는 셋이에요. 복지몰 lint에는 레이어 import 방향, 슬라이스 Public API, page 간 참조 금지가 error로 남았어요(관리자 서비스는 앞의 둘이 아직 warning이고 page 간 참조 규칙은 없어요). 복지몰에서는 @page 내부의 화면 코드와 @common의 공유 코드를 구분했어요. 화면 밖에서도 쓰는 도메인 코드는 features에 두되, 단순히 사용처가 두 곳이라는 이유만으로 이동하지는 않아요. 검증 절차에는 배럴에 export를 더하거나 패키지를 합쳤으면 pnpm build를 한 번 돌린다는 항목을 추가했어요.

지금은 서버 도메인의 API와 모델, UI를 features에서 찾고 한 화면을 조합하는 코드를 pages에서 찾아요. 표준 레이어를 모두 유지하는 것보다 다음 파일을 어디서 찾아야 하는지 설명할 수 있는 구조가 이 코드베이스에는 더 필요했어요.
