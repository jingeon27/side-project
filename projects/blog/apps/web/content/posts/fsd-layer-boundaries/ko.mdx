<Summary>

폴더는 FSD 구조대로 나눴는데 새 파일을 어디에 둘지 저도 설명하지 못했어요. entities를 빼고 도메인 코드와 화면 조합을 다시 나누면서, 한 시간 남짓 뒤 반례가 나온 규칙과 633초 걸린 테스트, 타입 검사를 통과하고도 깨진 화면을 차례로 만났어요.

</Summary>

![레이어와 기능 모듈 사이의 import 방향을 표현한 일러스트](/images/covers/fsd-layer-boundaries.png)

새 조회 훅을 만들 때마다 entities인지 features인지 다시 이야기했어요. 회원 전용 서비스와 관리자 모노레포의 프론트엔드 폴더를 FSD로 나누고 있었거든요. 회원 전용 서비스는 사용자가 병원 프로그램을 찾아 신청하는 서비스이고, 관리자 모노레포는 병원과 운영팀이 쓰는 관리자 앱을 모은 저장소예요.

FSD(Feature-Sliced Design)는 프론트엔드 코드를 역할별 층으로 나누는 폴더 규칙이에요. 이 층을 레이어라고 불러요. 표준 레이어는 아래처럼 쌓이고, 슬라이스는 자기보다 아래 레이어만 가져올 수 있어요.

```text
app       라우팅, Provider처럼 앱을 띄우는 코드
pages     화면
widgets   여러 화면에 붙는 큰 UI 블록
features  사용자가 수행하는 주요 상호작용
entities  제품이 다루는 현실의 개념
shared    도메인을 모르는 공용 코드
```

레이어 안은 도메인 이름의 폴더인 슬라이스로 나눠요. 다른 슬라이스의 코드는 그 슬라이스가 공개한 것만 가져오는데, 이 공개 범위를 Public API라고 해요. 보통 슬라이스의 `index.ts`가 그 역할을 맡고, 이렇게 다른 파일을 모아 다시 내보내는 파일을 배럴이라고 불러요.

회원 전용 서비스에는 entities, features, widgets, pages가 있었고 관리자 모노레포는 pages를 뺀 같은 설명을 따랐어요. 이름은 익숙했지만 실제 파일을 놓으려면 사람마다 답이 달랐고, 저도 새 파일을 어디에 둘지 설명하지 못했어요.

아래는 그걸 고치려고 옮기면서 겪은 일을 일어난 순서대로 적은 거예요. 관리자 쪽 변경은 develop에 합쳤고, 회원 전용 서비스는 별도 브랜치에서 옮기던 과정이에요.

## "재사용될 것 같은 코드"라는 제 기준

저는 여러 feature에서 다시 쓸 것 같은 코드를 entities라고 설명했어요. 지금 돌아보면 재사용 가능성을 느낌으로 판단한 셈이에요. 아직 없는 사용처를 예상해야 하니 분류가 자꾸 달라졌어요. API 타입은 entities에, 같은 조회의 훅은 features에 있고 표시 UI도 entities와 widgets에 갈렸어요.

관리 화면에서는 더 애매했어요. 한 저장 요청을 고치면 조회와 폼, 버튼도 함께 바뀌었어요. "도메인은 entity, 사용자 행동은 feature"라고 외워도 어느 코드는 도메인이고 어느 코드는 사용자 행동인지 이름만으로는 잘 나눠지지 않았어요.

필터를 배치할 때도 막혔어요. 관리자의 필터 위젯은 옵션을 직접 조회해요. 그러니 이 위젯과 목록을 함께 조립하는 코드는 widgets 위에 있어야 하는데, 그 일을 맡던 features는 widgets 아래에 있어요. 필터와 목록을 한자리에서 조합할 레이어가 없으니 결국 app의 `page.tsx`에서 조합했고, 도메인의 필터 옵션 배열까지 그곳에 남았어요.

## 8월 말, entities를 빼기로 했어요

entities와 features의 정의를 몰라서 생긴 일만은 아니었어요. 문서의 설명대로 entities는 제품이 다루는 현실의 개념이고 features는 사용자가 수행하는 주요 상호작용이에요. 그 설명은 이해하기 쉬웠어요. 다만 두 프로젝트는 서버가 정한 데이터를 조회해 화면에 보여 주는 일이 많았어요. 하나의 조회에 쓰는 API와 스키마, Query Options(TanStack Query의 key와 조회 함수를 묶은 객체), UI를 두 레이어에서 찾는 일이 더 번거로웠어요.

공식 문서도 모든 레이어를 필수로 두지는 않아요. 클라이언트의 비즈니스 로직이 적으면 entities를 생략할 수 있다는 설명을 보고, 다음처럼 바꿔 보기로 했어요.

```text
app → pages → widgets → features → shared
```

표준 레이어를 다 지키는지보다 다음 파일의 자리를 한 문장으로 설명할 수 있는지를 기준으로 골랐어요. 서버 도메인별 API와 스키마, Query Options, 상태, UI는 features로 모았어요. entities가 하던 일까지 이어받으니 이 프로젝트의 features는 문서의 설명보다 넓어요. 화면을 조합하는 pages는 widgets 위에 뒀어요. 그래야 라우트 파일을 빌리지 않고도 데이터를 조회하는 위젯과 목록을 함께 배치할 수 있어요.

pages에서는 한 화면의 JSX와 상호작용을 읽어요. 화면 구성이 JSX에서 바로 읽혀야 한다는 기준도 이때 함께 세웠어요. 호출 순서와 상태 전이처럼 절차로 쓰는 것이 자연스러운 로직은 features에 남겨요. widgets는 여러 화면에 독립해서 붙는 UI, shared는 특정 도메인을 모르는 코드로 좁혔어요. Provider와 SDK 초기화, 라우팅은 app에 뒀어요.

## 8월 31일, 옮긴 날

먼저 기존 features를 pages로 비운 다음 entities를 features로 옮겼어요. 반대로 하면 같은 이름의 슬라이스가 부딪혀요. 겹치는 배럴의 export는 직접 합쳤어요.

```text
before
entities  도메인이라고 판단한 일부 API·모델·UI
features  사용자 행동이라고 판단한 일부 훅·폼·UI

after
features  서버 도메인 단위의 API·모델·스키마·도메인 UI
pages     화면 단위의 인터랙션과 조합
```

모듈 경로를 고칠 때는 별칭 import만 검색했다가 상대 경로 하나를 놓쳤어요. 마지막 typecheck가 그 참조를 찾아 줬어요.

타입 검사가 찾아 주지 못하는 일도 그날 나왔어요. Next.js App Router의 파일은 기본으로 서버 컴포넌트로 처리돼요. 상태를 쓰는 훅은 클라이언트 컴포넌트에서만 쓸 수 있고, 파일 맨 위의 `use client` 지시문이 서버와 클라이언트의 경계를 표시해요. 그런데 배럴은 여러 모듈을 다시 내보내는 파일이라, 서버 쪽 파일이 배럴에서 하나만 가져와도 나머지 모듈까지 서버 쪽 모듈 그래프에 들어올 수 있어요. 타입은 맞으니 타입 검사에는 걸리지 않아요.

회원 전용 서비스에서 옮긴 슬라이스의 도메인 배럴이 `use client` 없는 훅을 내보내면서 typecheck와 ESLint는 지나갔는데 E2E 전체가 실패했어요. React Hook Form을 쓰는 모듈에도 지시문을 붙여야 라우트의 500 응답이 사라졌어요.

옮기고 나니 page 간 import도 드러났어요. 기존 features끼리는 같은 레이어에서 서로 가져오고 있었는데, 그 파일들을 pages로 옮기자 서로 다른 화면을 직접 참조하는 코드가 됐어요. `fsd/no-cross-page`는 warning부터 켜고, 어디로 나눌지 정리한 뒤 error로 올렸어요.

상세 아래의 프로그램과 검색, 리뷰 작성처럼 부모 화면이 자식 화면을 가져오는 경우는 폴더 중첩을 바꿨어요. pages에서 형제 슬라이스였던 것을 라우트의 조합에 맞춰 묶으니 같은 슬라이스 안에서 가져올 수 있었어요.

처음에는 나머지 UI를 widgets로 내리려 했어요. 하지만 남은 참조를 열어 보니 리뷰 항목과 카테고리 목록은 서버 DTO(서버가 돌려주는 데이터 모양)를 그대로 그리는 도메인 UI였어요. 이런 것은 각 도메인의 `features/{domain}/ui`에 뒀어요. 지도와 배너, 약관처럼 여러 화면이 쓰는 코드도 그 기준으로 옮겼어요.

레이어 import 방향과 다른 슬라이스 내부를 직접 가져오는 deep import는 이 작업 전부터 custom ESLint 규칙이 막고 있었어요. 컴포넌트가 화면 조각인지 도메인 UI인지까지 lint가 정해 주지는 않아요. 코드를 읽어야 판단할 수 있는 영역까지 자동화하면 오탐을 피하려고 더 이상한 폴더를 만들게 돼요. 그 판단은 코드를 보고 하고, 정한 뒤의 import 방향과 Public API 사용을 검사하게 했어요.

## 9월 2일, 한 시간 남짓 뒤 나온 반례

두 프로젝트 모두 처음에는 라우트 경로를 그대로 폴더로 옮겼어요. 회원 전용 서비스는 이날 오후에 "동적 세그먼트는 형제 화면과 구분이 필요할 때만 detail로 접는다"는 규칙까지 적었어요. 동적 세그먼트는 `[id]`처럼 URL의 값이 들어가는 경로 조각이에요. 한 시간 남짓 뒤 반례가 나왔어요. 나중에 형제 화면이 추가되면 원래 폴더 이름이 규칙에 안 맞게 되는데, 그때 이름을 바꾸는 사람은 없어요. 결국 규칙을 없애고 한 폴더를 한 화면으로 봤어요. 라우트 그룹과 버전 문자열처럼 화면을 가리키지 않는 조각은 폴더로 만들지 않고, 같은 화면을 여러 라우트에서 여는 것도 허용했어요.

관리자 쪽은 같은 날 오후에 메뉴와 URL로 화면을 찾는 일이 많다는 이유로 pages 경로를 URL과 1:1로 맞췄어요. 그러자 URL을 지키기 위해 내용 없는 폴더를 계속 만들게 됐어요. 그날 안에 URL과 맞추는 것은 기본값으로만 두고 강제하지 않기로 했어요. 같은 완성 화면을 다른 URL에서 열 수도 있어서 lint로 걸면 오탐만 나기 때문이에요.

## 같은 날, 테스트 633초

관리자 모노레포에는 ui, hooks, utils, types가 별도 workspace 패키지였어요. 모두 shared 코드인데 `ui → hooks → utils → types`로 이어지고 사용하는 곳에서도 따로 import했어요.

이날 shared 패키지 하나 안의 세그먼트(목적별로 나눈 폴더)로 합쳤어요. cookie와 환경 변수, 서버 전용 코드의 entrypoint는 따로 뒀어요. 일반 배럴에 함께 올리면 브라우저나 서버 전용 의존성이 Edge 번들로 들어갈 수 있기 때문이에요. Edge 번들은 Node.js API를 모두 쓸 수는 없는 Edge 런타임에서 실행되는 코드예요.

```text
packages/shared/src/
├── ui/
├── hooks/
├── utils/
└── types/

@app/shared          ← 패키지 이름은 공개용 가명이에요
@app/shared/cookie
@app/shared/env
@app/shared/server
```

Vitest 설정까지 합친 것이 제 실수였어요. 합친 설정은 브라우저의 DOM을 Node.js에서 흉내 내는 jsdom 환경이었고, 원래 node에서 돌던 utils까지 jsdom에서 실행돼 로컬 테스트가 633초 걸렸어요. `document`가 없을 때 서버용 인증 헤더를 만드는 HTTP 클라이언트 테스트도 실패했고요. jsdom에는 `document`가 있으니까요. node와 jsdom 프로젝트를 나누니 8초로 돌아오고 테스트도 통과했어요. 합치면서 제가 바꿔 버린 실행 환경을 되돌린 것뿐이고, 원래보다 빨라진 건 아니에요.

## 타입 검사는 이번에도 지나갔어요

8월 31일의 일로 끝나지 않았어요. 폴더와 배럴을 옮긴 뒤에는 타입 검사와 lint, Vitest가 모두 통과해도 dev 서버나 빌드에서 실패했어요. 8월 31일을 포함해 같은 종류의 경계 오류를 네 번 만났어요. 검사들이 따라간 import와 Next.js가 만드는 서버 그래프가 같지 않았고, 당시 검사 설정과 테스트 범위로는 그 차이를 확인하지 못했어요.

9월 2일에는 dev 서버를 띄우자 최상위 pages 배럴을 import하는 라우트가 전부 500이었어요. 리뷰 옵션 훅이 `profile/index.ts`를 거쳐 `pages/index.ts`에 올라가면서 서버 컴포넌트 그래프에 들어간 것이 원인이었어요. 코드를 줄여 보면 이래요. 훅과 화면의 이름은 설명용으로 붙였어요.

```typescript
// pages/profile/index.ts
export { ProfilePage } from './ProfilePage';
export { useReviewOptions } from './useReviewOptions'; // 'use client'가 없는 훅

// pages/index.ts
export { ProfilePage, useReviewOptions } from './profile';

// app/profile/page.tsx: 서버 컴포넌트예요. 화면 하나만 가져와도 배럴을 거쳐요.
import { ProfilePage } from '@/pages';
```

훅을 배럴에서 빼고 `use client`를 붙인 뒤에는 다시 연 라우트들이 200이나 307로 응답했어요.

다음 날 widgets를 정리할 때도 비슷했어요. 라우트를 다시 열어 보니 같은 종류의 오류가 남아 있었어요. 필요한 모듈에 `use client`를 붙이고 로그인 배럴이 실제 화면만 내보내도록 줄였어요. widgets에 무엇을 남길지도 이때 다시 봤어요. 슬라이스 7개 중 여러 화면에 독립해서 붙는 것은 전역 내비게이션과 챗봇 둘뿐이었어요. 한 화면의 조각은 해당 pages로, 채팅과 분석 SDK 초기화는 app으로 옮겼어요. 챗봇은 한때 pages로 옮겼지만 URL로 여는 화면이 아니라서 그날 widgets로 되돌렸어요.

관리자 모노레포에서는 합친 shared 배럴이 문제였어요. 이쪽은 dev 서버에서 드러난 일이 아니었어요. `pnpm build`에서 세 앱이 모두 깨졌고, 타입 검사와 lint, Vitest는 모두 통과한 상태였어요. 라우트 핸들러(서버에서 요청을 받는 Next.js 파일)가 shared에서 값 하나를 가져오는데 클라이언트 UI 그래프까지 따라왔고, `use client` 없는 모듈에서 프로덕션 빌드가 깨졌어요. 이후 배럴 export나 패키지 구성을 바꾸면 `pnpm build`까지 실행하도록 규칙에 적었어요. dev 서버로 라우트를 여는 건 회원 전용 서비스에서 커밋마다 손으로 했고, 아직 문서에 종료 조건으로 적지는 않았어요.

병원 관리자의 검수 요청이 Back-Office의 반려까지 이어지는 흐름은 같은 주에 별도로 E2E를 만들었어요. 두 dev 서버를 함께 띄워 도는 테스트예요. 반려 흐름의 버그를 고치다 나온 테스트라 이 이동을 확인하는 작업과는 달랐고, 옮긴 트리에 대해 다시 돌린 기록도 없어요. 그 이야기는 [별도 글](/ko/blog/ai가-코드를-잘-짜기-시작했는데-제가-덜-바빠지지는-않았어요)에 있어요.

## 9월 4일, @page와 @common

화면별 폴더가 생겨도 그 안의 코드가 현재 화면용인지 하위 화면이 함께 쓰는 것인지 헷갈렸어요. 폴더만 봐서는 이 경로의 화면인지, 하위 경로인지, 부속 세그먼트인지 구분되지 않았어요. 이날 `@page`와 `@common`을 붙여 구분했어요.

```text
pages/catalog/search/
├── @page/            ← 이 화면의 slice
│   ├── ui/
│   ├── model/
│   └── lib/
├── @common/          ← 하위 화면이 함께 쓰는 코드
├── keyword/@page/
│   ├── KeywordPage.tsx
│   └── ui/ model/ lib/
└── category/@page/
    ├── CategoryPage.tsx
    └── ui/
```

`@page` 안에는 그 화면의 ui, model, lib를 두고, 하위 화면들이 함께 쓰는 코드는 `@common`에 뒀어요. 위 이름은 화면을 묶는 설명용 예시이고, URL을 그대로 옮긴 구조도 아니에요. 더 넓게 쓰는 도메인 코드는 `@common`에 계속 쌓지 않고 해당 features 등 하위 레이어로 옮겨요. 사용처가 두 곳이라는 이유만으로 옮기지는 않아요.

## 지금 파일을 찾는 곳

처음 세운 구조가 그대로 남은 것은 아니에요. 관리자 쪽에서는 URL을 너무 충실히 따라 생긴 폴더 깊이를 다시 줄였고, 회원 전용 서비스에서는 라우트 미러링을 철회한 뒤 `@page` 표기를 추가했어요. 파일을 실제로 옮겨 보고 나서야 문서만 읽을 때 보이지 않던 반례를 찾을 수 있었어요.

회원 전용 서비스에서는 레이어 방향과 Public API, page 간 참조가 lint error예요. 관리자 쪽은 앞의 두 규칙이 warning이고 page 간 참조 검사는 아직 없어요. 옮겨 둔 폴더와 검사가 똑같은 수준으로 적용된 것은 아니에요.

서버의 API와 모델, 도메인 UI가 궁금하면 features를 보고, 화면에서 무엇을 함께 그리는지는 pages를 봐요. URL을 닮은 폴더를 끝까지 따라가거나 entities와 features 중 어디일지 예상하는 대신, 실제로 함께 고치는 코드를 모아 둔 모양이에요. 표준 레이어를 모두 유지하는 것보다 다음 파일을 어디서 찾아야 하는지 설명할 수 있는 구조가 이 코드베이스에는 더 필요했어요.
