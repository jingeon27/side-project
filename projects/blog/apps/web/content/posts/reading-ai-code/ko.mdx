**이 글에서 다루는 것**

저저번 스프린트에서 코드 확인을 생략했는데, 핫픽스가 많이 발생했어요. 그 뒤 다시 diff를 읽고 있어요. 어떤 변경을 읽는지, 코드에서 무엇을 확인하는지, AI 덕분에 구조를 바꾸기 쉬워진 지금도 코드 확인이 필요한 이유를 적었어요.

![구현을 맡겨도, 무엇이 바뀌었는지는 직접 확인해요.](/images/posts/reading-ai-code/01.png)

*구현을 맡겨도, 무엇이 바뀌었는지는 직접 확인해요.*

“코드를 안 읽어요.”

요즘 이런 말을 종종 봤어요. 저도 궁금했어요. 에이전트가 구현하고 테스트가 성공했다면, 화면에서 동작만 확인해도 충분하지 않을까요?

그래서 저저번 스프린트에서는 코드를 읽지 않고 동작 검증을 중심으로 진행해 봤어요. 그런데 핫픽스가 많이 발생했어요. 동작만 확인하면 충분하다고 생각했던 검증 방식을 돌아보게 됐고, 그 뒤로 기능 개발과 리팩터링에서는 diff를 다시 읽고 있어요.

그렇다고 에이전트가 코드를 못 짠다는 뜻은 아니에요. 지금도 작은 기능이나 리팩터링을 맡기면, 제가 코드를 고치지 않아도 만족스러운 퀄리티로 나오는 경우가 있어요. 다만 **코드를 고치지 않는 것과 코드를 읽지 않는 것은 다른 일이었어요.**

## 기계적인 변경까지 한 줄씩 다시 읽지는 않아요

모든 변경을 같은 방식으로 읽지는 않아요. 포맷을 맞추거나 동작을 바꾸지 않는 lint 자동 수정을 적용할 때, 정해 둔 위치로 파일을 옮기고 import 경로만 바꿀 때는 기존 코드를 한 줄씩 다시 읽을 필요가 적어요. 변경 범위를 확인하고 그에 맞는 검증을 해요.

다만 작업 이름이 'lint 적용'이나 '폴더 이동'이라고 해서 전부 기계적인 변경은 아니에요. lint를 맞추면서 분기나 실행 순서를 바꿨다면 동작 변경이에요. 파일을 옮기며 서버·클라이언트 경계나 모듈 초기화 방식이 달라진 경우도 따로 봐야 해요.

리팩터링과 기능 개발은 diff를 읽어요. 입력을 어디서 받고, 상태를 누가 관리하며, 어떤 조건에서 요청하는지 알아야 하니까요. 매번 전체 저장소를 다시 읽는 것은 아니에요. 평소에 파악해 둔 흐름에서 무엇이 달라졌는지 보고, 필요하면 호출부와 연결된 코드까지 따라가요.

특히 리팩터링은 화면이 같아 보여도 데이터나 상태를 다루는 방식이 달라질 수 있어요. 초기값을 넣는 시점, 뒤로 갔을 때 남는 상태, 요청이 실패했을 때의 처리는 화면에서 정상적인 경로만 따라가 봐서는 확인하기 어려워요.

## 손댈 코드가 없는 결과도 나오기 시작했어요

처음부터 지금처럼 맡길 수 있었던 것은 아니에요. 약 반년 동안 [Compound Engineering](https://every.to/guides/compound-engineering) 방식을 참고하며, 결과가 제 의도와 어긋날 때마다 skill·AGENTS.md·lint를 보강했어요. 한 작업에서 바로잡은 기준을 다음 작업에도 적용하는 식이었어요.

폴더 위치나 import 방향처럼 코드만으로 판정할 수 있는 것은 lint에 넣었어요. 상태를 어디에 두고 어떤 추상화를 쓸지처럼 맥락이 필요한 기준은 skill과 AGENTS.md에 남겼어요. 기대 동작과 다시 발생하면 안 되는 오류는 테스트로 고정했고요.

지금 흐름은 이래요.

```text
티켓·plan 검토
→ 테스트 작성
→ 에이전트 구현·에이전트 코드 리뷰
→ 변경분 테스트·lint·typecheck
→ 제 diff 리뷰·dev 화면에서 동작 확인
→ 전체 CI(테스트·knip·lint)
→ QA 더블 체크 요청
```

앞의 네 단계까지 마친 결과를 읽어 보면 제가 고칠 부분이 없기도 해요. 특히 변경 범위가 작고 저장소 안에 비슷한 패턴이 있으면 잘 끝내는 편이에요. 모델 성능이 좋아진 데다, 저장소에도 제 기준을 계속 남겨 온 결과라고 느껴요.

테스트도 읽어요. 새 기능의 기대 동작은 BDD 형식의 \*.spec에 적고, 컴포넌트별로 필요한 조건이 빠지지 않았는지 봐요. 운영이나 QA에서 발견한 버그는 \*.test에 재현해요. 새 패턴으로 작성한 테스트는 제품 코드를 일부러 깨뜨렸을 때 실제로 실패하는지도 확인해요.

그렇게 기준을 쌓아도 엇나가는 부분은 남아요. 에이전트가 확률적 모델을 바탕으로 코드를 만드는 만큼, 저장소에 기준을 적어 뒀다고 항상 그 기준을 지키는 것은 아니에요. 에이전트 리뷰가 끝난 뒤에도 제가 요구사항과 코드를 대조해 봐요.

## 작은 변경과 큰 기능에서 고민이 달라요

작은 기능은 결과가 좋을수록 코드를 안 읽어도 될 것처럼 느껴져요. 그런데 이런 작업은 변경량도 작아서 읽는 데 시간이 많이 들지 않아요. 몇 개 파일을 보면서 요구사항에 맞는지, 기존 패턴에서 벗어나지 않았는지 확인하면 돼요.

오히려 읽는 시간이 부담스러운 건 큰 기능이에요. 화면과 상태, API, 기존 기능에 미치는 영향이 함께 늘어나니까요. 제가 맡긴 큰 기능이 한 번의 지시로 완전히 끝난 적은 없었어요. 에이전트가 완성됐다고 제출해도, 제가 읽어 보면 다시 작업해야 하는 부분이 남아 있었어요.

에이전트가 완성본을 제출하면 diff와 테스트를 읽고, 요구사항이나 저장소의 기준에 맞지 않는 부분을 짚어 반려해요. 수정된 결과를 받으면 다시 확인하고요. 큰 기능은 이 과정을 반복해요. 에이전트가 완료했다고 보고한 것과 제가 검토를 마친 것은 달라요.

복지몰의 Bottom Sheet을 compound 구조로 바꿀 때는 AI가 만든 코드와 기존 검토 과정을 믿고 작업을 마쳤어요. 하지만 헤더가 본문과 같은 스크롤 영역에 들어가 있어서, 본문을 스크롤하면 제목도 함께 올라갔어요. 이후 드래그 크래시를 해결하려고 라이브러리를 업그레이드하면서도 이 구조를 그대로 옮겼어요. diff를 읽고 시트 높이와 스냅 위치까지 확인했지만, 스크롤할 때 제목이 고정되는지는 놓쳤어요.

코드를 읽었는데도 화면의 잘못된 동작을 놓친 경험이었어요. 그 뒤로는 스크롤이나 드래그처럼 실제 화면에서 확인해야 하는 동작도 따로 챙기고, 같은 문제가 다시 생기면 알 수 있도록 브라우저 테스트를 남겨요. [자세한 수정 과정은 별도 글에 적었어요.](/ko/blog/sentry가-잡아-준-bottom-sheet-드래그-크래시-원인-경로가-사라진-버전으로-올리기까지)

## 화면을 눌러 보기 전에 코드에서 찾는 문제

코드를 읽으면서 컨벤션만 확인하는 것은 아니에요. 실행해 보기 전에 조건이나 데이터 흐름에서 문제를 찾을 때도 있어요.

임시 진료일을 추가할 때도 입력 화면뿐 아니라 예약 가능일을 판정하는 코드를 함께 바꿨어요. 평소 쉬는 요일이라도 병원이 임시 진료일로 정했다면 예약할 수 있어야 했거든요.

기존 휴무 판정 뒤에 새 조건만 붙이면 어떻게 될까요? 아래는 그 경우를 설명하려고 줄인 예제예요. 날짜 비교와 서버 응답 처리는 생략했고, 함수 이름은 공개용 가명이에요.

```typescript
if (isPastDate(day)) return false;
if (isWeeklyClosed(day)) return false;
if (hasTemporaryOpening(day)) return true;
return !isTemporarilyClosed(day);
```

조건은 다 들어 있지만 순서가 잘못됐어요.

요일 휴무에서 먼저 false를 반환하니, 쉬는 요일에 지정한 임시 진료일은 다음 조건까지 가지 못해요. 평소 진료하는 날만 눌러 보면 문제를 놓칠 수 있지만, 코드를 읽으면 임시 진료일 판정에 도달할 수 있는지부터 확인할 수 있어요.

```typescript
if (isPastDate(day)) return false;
if (hasTemporaryOpening(day)) return true;
if (isWeeklyClosed(day)) return false;
return !isTemporarilyClosed(day);
```

실제 구현도 오늘 이전 날짜를 먼저 막고, 임시 진료일을 요일 휴무와 임시 휴무보다 먼저 확인하도록 바꿨어요. 서버가 임시 진료와 임시 휴무를 같은 배열에 담아 보내기 때문에, 배열의 모든 항목을 휴무로 읽던 코드도 종류를 구분하도록 바꿨고요. type이 없는 옛 휴무 데이터는 계속 휴무로 처리했어요.

임시 진료일인데도 운영에서 예약이 막혔다는 이야기는 아니에요. 새 기능을 넣으며 기존 판정을 그대로 두면 생길 수 있던 문제예요. 휴무 요일을 임시 진료일로 열었을 때 선택할 수 있는지, 임시 휴무와 겹쳐도 열리는지, 지난 날짜는 계속 막히는지를 테스트로 남겼어요.

이런 부분은 새 조건이 있는지만 봐서는 놓치기 쉬워요. 기존 조건과 어떤 순서로 실행되는지, 기존 데이터의 뜻이 달라지지는 않는지도 봐야 해요. 코드를 읽으면 확인할 조건을 먼저 찾을 수 있고, 그 조건을 테스트와 화면에서 검증할 수 있어요. 제가 코드 읽기를 값싼 검증이라고 생각하는 이유예요.

## 읽는 시간을 구현 시간과 겹쳐 써요

큰 기능의 diff를 읽는 데는 시간이 걸려요. 하지만 에이전트가 구현이나 검증을 하는 동안 그 시간을 쓸 수 있어요.

에이전트가 다른 작업을 구현하거나 반려한 부분을 수정하는 동안, 이미 제출받은 diff를 읽거나 다음 변경과 연결되는 기존 코드를 따라가요. 구현이 끝날 때까지 기다리기만 하는 대신 코드와 비즈니스 맥락을 파악하는 데 시간을 써요.

지금 제 작업에서는 코드를 읽느라 업무 전체가 멈춘다는 느낌은 크지 않아요. 구현하는 시간과 읽는 시간을 겹쳐 쓸 수 있기 때문이라고 생각해요. 물론 작업이 더 커지거나 낯선 영역이 많아지면 제 검토가 병목이 될 수도 있어요.

변경 내용을 이해하고 설명할 수 있는지도 중요해요. 구현은 빨리 끝났는데 무엇이 바뀌었는지 모른다면, 제 입장에서는 아직 끝난 작업이 아니에요.

## 큰 구조 변경도 덜 부담스러워졌어요

AI 덕분에 쉬워진 건 새 기능 구현만이 아니에요. 폴더 구조를 다시 나누거나 공통 컴포넌트의 인터페이스를 바꾸면, 관련된 여러 파일과 사용처를 함께 고쳐야 해요. 방향을 정하는 것과 별개로 손이 많이 가는 일이에요.

이제는 변경 기준을 정해 에이전트에게 맡기고, 저는 제출된 결과가 그 기준에 맞는지 확인해요. 여러 파일에 같은 패턴을 적용하는 부담이 줄어서, 일부 코드만 손보는 데 그치지 않고 구조를 크게 바꾸기도 수월해졌어요.

덕분에 저장소를 제가 생각하는 이상적인 구조에 가깝게 유지하는 일도 쉬워졌다고 느껴요. 여기서 이상적이라는 것은 지금 제품의 요구에 맞고, 상태와 데이터의 책임이 분명하며, 변경한 부분을 읽고 검증하기 쉬운 구조예요. 구조를 바꾸는 방향은 제가 판단하고, 에이전트가 옮긴 결과는 다시 읽어 확인해요.

## 읽기 쉬운 구조를 유지하려는 이유

저는 코드 위생에 집착하는 편이에요. 미사용 코드를 찾으려고 knip을 쓰고, 반복해서 확인하는 기준은 lint와 skill에 남겨요. 같은 역할의 코드가 서로 다른 이름이나 위치에 있으면, 동작을 확인하기 전에 어디에 무엇이 있는지부터 찾아야 하니까요.

응집도와 결합도를 생각하고, 서로 다른 맥락을 나누고, 한 함수 안의 추상화 수준을 맞추려는 이유도 같아요. 상태를 누가 바꾸는지 찾으려고 여러 파일을 오가거나, 화면 동작과 데이터 변환이 한곳에 섞여 있으면 중요한 조건을 놓치기 쉬워요.

이름과 구조가 일관되면 에이전트가 참고할 패턴이 생기고, 저도 코드를 파악하기 쉬워져요. 그렇다고 익숙한 모양으로 만드는 데만 집중하지는 않아요. 이름은 비슷한데 역할이 다르거나 짧게 만들려고 중요한 분기를 숨겼다면 오히려 확인하기 어려워요. 코드를 읽으면서 각 부분의 역할과 실행 조건을 설명할 수 있는지 봐요.

코드 위생을 유지하려는 것은 보기 좋은 코드를 남기기 위해서만은 아니에요. 코드를 읽는 것도 검증 과정인 만큼, 적은 시간으로 내용을 파악하고 문제를 발견할 수 있게 하려는 거예요.

**지금의 검토 기준**

동작이 바뀌지 않는 기계적인 변경은 범위와 검증 결과를 중심으로 보고, 기능과 리팩터링은 변경된 제품 코드와 테스트를 읽어요. 큰 기능은 제출된 완성본을 검토하고 부족하면 반려해요. 테스트가 성공해도 코드 확인과 실제 화면 확인은 따로 해요.

처음에는 에이전트가 잘 짜면 읽을 필요도 없어질 것이라고 생각했어요. 지금은 만족스러운 구현이 나오면 제가 고치는 시간이 줄어드는 거라고 생각해요. 읽을 필요까지 없어지는 것은 아니고요.

AI 덕분에 빠르게 구현하면서 원하는 구조를 유지하기도 쉬워졌어요. 대신 어떤 구조가 맞는지, 이번 구현이 그 기준을 지켰는지는 제가 판단해야 해요. 그래서 저는 구현을 맡기되, 검증할 때는 코드를 읽어요.
