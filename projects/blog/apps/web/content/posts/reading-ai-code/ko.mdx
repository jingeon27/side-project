두 스프린트 전에는 에이전트가 만든 코드를 읽지 않고 화면 동작을 확인하는 데 집중해 봤어요. 화면에서 동작하면 충분할 거라고 생각했는데, 핫픽스가 많이 발생했어요. 화면에서 동작했다는 것은 제가 눌러 본 경로가 동작했다는 뜻이었을 뿐이에요.

그 뒤로 테스트를 두 가지로 나눠 생각해요. 제품이 어떻게 동작하는지 밖에서 확인하는 **블랙박스 테스트**와, 코드 안을 읽고 어떤 경로가 있는지 확인하는 **화이트박스 테스트**예요. 이 글은 제가 왜 블랙박스 테스트만으로는 검증을 끝냈다고 보지 않는지, 그리고 화이트박스 테스트를 하려고 코드를 어떻게 관리하는지에 대한 이야기예요.

## 블랙박스 테스트와 화이트박스 테스트

블랙박스 테스트는 내부 구조를 모른다고 보고 입력과 결과만으로 확인하는 방식이에요. 요구사항을 기준으로 화면을 눌러 보고, E2E 테스트로 사용자 흐름을 재현하고, QA가 시나리오대로 확인하는 것이 여기에 들어가요. 사용자가 실제로 겪는 동작을 그대로 확인할 수 있고, 구현 방식이 바뀌어도 테스트를 유지하기 쉬워요.

화이트박스 테스트는 코드 구조를 알고 확인할 경로를 정하는 방식이에요. 어떤 분기가 있고, 조건이 어떤 순서로 실행되며, 상태를 누가 바꾸는지 보고 그 경로가 의도대로 동작하는지 검증해요. 그래서 화이트박스 테스트는 코드를 읽고 이해하는 데서 시작해요.

| 구분 | 블랙박스 테스트 | 화이트박스 테스트 |
| --- | --- | --- |
| 기준 | 요구사항과 화면 동작 | 분기, 조건 순서, 상태와 데이터 흐름 |
| 하는 일 | 화면 확인, E2E, QA 시나리오 | diff·테스트 읽기, 경로별 테스트 작성 |
| 놓치기 쉬운 것 | 떠올리지 못한 입력과 내부 분기 | 코드로는 보이지 않는 실제 화면 동작 |

둘은 서로를 대신하지 않아요. 블랙박스 테스트는 제품이 사용자에게 어떻게 보이는지를 확인하고, 화이트박스 테스트는 그 동작이 왜 그렇게 되는지, 확인하지 않은 경로가 남아 있지 않은지를 확인해요.

제 작업 흐름에도 두 테스트가 함께 들어가 있어요.

```text
티켓·plan 검토
→ 테스트 작성
→ 에이전트 구현·에이전트 코드 리뷰
→ 변경분 테스트·lint·typecheck
→ 제 diff 리뷰·dev 화면에서 동작 확인
→ 전체 CI(테스트·knip·lint)
→ QA 더블 체크 요청
```

제 diff 리뷰가 화이트박스 테스트이고, dev 화면 확인과 QA 더블 체크가 블랙박스 테스트예요. 둘 중 하나만 통과했다고 작업을 끝내지 않아요.

## 블랙박스 테스트만으로는 검증됐다고 말하기 어려워요

블랙박스 테스트는 제가 떠올린 입력만 확인해요. 코드 안에 어떤 분기가 있는지 모르면 어떤 경우를 눌러 봐야 하는지도 알기 어려워요. 에이전트가 만든 코드는 제가 직접 쓰지 않았으니, 읽기 전에는 어떤 분기가 생겼는지 알 수 없어요.

리팩터링은 더 그래요. 화면이 같아 보여도 데이터나 상태를 다루는 방식이 달라질 수 있어요. 초기값을 넣는 시점, 뒤로 갔을 때 남는 상태, 요청이 실패했을 때의 처리는 정상 경로만 따라가 봐서는 확인하기 어려워요.

임시 진료일을 추가할 때가 그런 경우였어요. 입력 화면뿐 아니라 예약 가능일을 판정하는 코드도 바꿔야 했어요. 평소 쉬는 요일이라도 병원이 임시 진료일로 정했다면 예약할 수 있어야 했거든요.

기존 휴무 판정 뒤에 새 조건만 붙이면 어떻게 될까요? 아래는 그 경우를 설명하려고 줄인 예제예요. 날짜 비교와 서버 응답 처리는 생략했고, 함수 이름은 공개용 가명이에요.

```typescript
if (isPastDate(day)) return false;
if (isWeeklyClosed(day)) return false;
if (hasTemporaryOpening(day)) return true;
return !isTemporarilyClosed(day);
```

조건은 다 들어 있지만 순서가 잘못됐어요.

요일 휴무에서 먼저 false를 반환하니, 쉬는 요일에 지정한 임시 진료일은 다음 조건까지 가지 못해요. 평소 진료하는 날에 임시 진료일을 지정해 눌러 보는 블랙박스 테스트는 통과해요. 코드를 읽어야 임시 진료일 판정에 도달할 수 없는 경로가 있다는 것이 보여요.

```typescript
if (isPastDate(day)) return false;
if (hasTemporaryOpening(day)) return true;
if (isWeeklyClosed(day)) return false;
return !isTemporarilyClosed(day);
```

실제 구현도 오늘 이전 날짜를 먼저 막고, 임시 진료일을 요일 휴무와 임시 휴무보다 먼저 확인하도록 바꿨어요. 서버가 임시 진료와 임시 휴무를 같은 배열에 담아 보내기 때문에, 배열의 모든 항목을 휴무로 읽던 코드도 종류를 구분하도록 바꿨고요. type이 없는 옛 휴무 데이터는 계속 휴무로 처리했어요.

임시 진료일인데도 운영에서 예약이 막혔다는 이야기는 아니에요. 새 기능을 넣으며 기존 판정을 그대로 두면 생길 수 있던 문제예요. 코드에서 찾은 경로를 그대로 테스트로 남겼어요. 휴무 요일을 임시 진료일로 열었을 때 선택할 수 있는지, 임시 휴무와 겹쳐도 열리는지, 지난 날짜는 계속 막히는지예요.

새 조건이 있는지만 봐서는 이런 문제를 놓치기 쉬워요. 기존 조건과 어떤 순서로 실행되는지, 기존 데이터의 뜻이 달라지지는 않는지도 봐야 해요. 코드를 읽으면 확인할 경로를 먼저 찾을 수 있고, 그 경로를 테스트와 화면에서 검증할 수 있어요. 제가 화이트박스 테스트를 값싼 검증이라고 생각하는 이유예요.

## 화이트박스 테스트만으로도 부족했어요

반대 경우도 있었어요. 복지몰의 Bottom Sheet을 compound 구조로 바꿀 때는 AI가 만든 코드와 기존 검토 과정을 믿고 작업을 마쳤어요. 하지만 헤더가 본문과 같은 스크롤 영역에 들어가 있어서, 본문을 스크롤하면 제목도 함께 올라갔어요. 이후 드래그 크래시를 해결하려고 라이브러리를 업그레이드하면서도 이 구조를 그대로 옮겼어요. diff를 읽고 시트 높이와 스냅 위치까지 확인했지만, 스크롤할 때 제목이 고정되는지는 놓쳤어요.

코드를 읽었는데도 화면의 잘못된 동작을 놓친 경험이었어요. 스크롤이나 드래그처럼 브라우저와 라이브러리가 함께 만드는 동작은 코드만 봐서는 알기 어려워요. 그 뒤로는 이런 동작을 실제 화면에서 따로 확인하고, 같은 문제가 다시 생기면 알 수 있도록 브라우저 테스트를 남겨요. [자세한 수정 과정은 별도 글에 적었어요.](/ko/blog/sentry가-잡아-준-bottom-sheet-드래그-크래시-원인-경로가-사라진-버전으로-올리기까지)

그래서 테스트가 성공해도 코드 확인과 실제 화면 확인은 따로 해요. 화이트박스 테스트로 경로를 찾고, 블랙박스 테스트로 사용자가 겪는 동작을 확인해요.

## 에이전트와 일하면서 화이트박스 테스트를 하는 방식

모든 변경을 같은 깊이로 읽지는 않아요. 포맷을 맞추거나 동작을 바꾸지 않는 lint 자동 수정, 정해 둔 위치로 파일을 옮기고 import 경로만 바꾸는 작업은 변경 범위를 확인하고 그에 맞는 검증을 해요. 다만 이름이 'lint 적용'이나 '폴더 이동'이라고 해서 전부 기계적인 변경은 아니에요. lint를 맞추면서 분기나 실행 순서를 바꿨거나, 파일을 옮기며 서버·클라이언트 경계나 모듈 초기화 방식이 달라졌다면 동작 변경으로 보고 읽어요.

기능 개발과 리팩터링은 diff를 읽어요. 입력을 어디서 받고, 상태를 누가 관리하며, 어떤 조건에서 요청하는지 알아야 하니까요. 매번 전체 저장소를 다시 읽지는 않아요. 평소에 파악해 둔 흐름에서 무엇이 달라졌는지 보고, 필요하면 호출부와 연결된 코드까지 따라가요.

테스트도 읽어요. 새 기능의 기대 동작은 BDD 형식의 \*.spec에 적고, 컴포넌트별로 필요한 조건이 빠지지 않았는지 봐요. 운영이나 QA에서 발견한 버그는 \*.test에 재현해요. 새 패턴으로 작성한 테스트는 제품 코드를 일부러 깨뜨렸을 때 실제로 실패하는지도 확인해요. 테스트가 확인한다고 적은 경로를 정말 확인하는지까지 봐야 화이트박스 테스트라고 할 수 있어요.

큰 기능은 한 번에 끝난 적이 없어요. 화면과 상태, API, 기존 기능에 미치는 영향이 함께 늘어나니까요. 에이전트가 완성본을 제출하면 diff와 테스트를 읽고, 요구사항이나 저장소의 기준에 맞지 않는 부분을 짚어 반려해요. 수정된 결과를 받으면 다시 확인하고요. 에이전트가 완료했다고 보고한 것과 제가 검토를 마친 것은 달라요.

읽는 시간은 에이전트의 구현 시간과 겹쳐 써요. 에이전트가 다른 작업을 구현하거나 반려한 부분을 수정하는 동안, 이미 제출받은 diff를 읽거나 다음 변경과 연결되는 기존 코드를 따라가요. 그래서 코드를 읽느라 업무 전체가 멈춘다는 느낌은 크지 않아요.

약 반년 동안 [Compound Engineering](https://every.to/guides/compound-engineering) 방식을 참고하며, 결과가 제 의도와 어긋날 때마다 skill, AGENTS.md, lint를 보강했어요. 지금은 작은 기능이나 리팩터링을 읽어 보면 제가 고칠 부분이 없을 때도 있어요. 그래도 읽고 확인한 뒤에 그대로 써요. **코드를 고치지 않는 것과 코드를 읽지 않는 것은 다른 일이었어요.**

## 화이트박스 테스트를 하려면 코드를 관리해야 해요

화이트박스 테스트의 비용은 코드가 얼마나 읽기 쉬운지에 달려 있어요. 같은 역할의 코드가 서로 다른 이름이나 위치에 있으면, 동작을 확인하기 전에 어디에 무엇이 있는지부터 찾아야 해요. 상태를 누가 바꾸는지 찾으려고 여러 파일을 오가거나, 화면 동작과 데이터 변환이 한곳에 섞여 있으면 중요한 분기를 놓치기 쉬워요. 코드를 읽는 비용이 너무 커지면 결국 화면만 눌러 보는 블랙박스 테스트로 돌아가게 돼요.

그래서 저는 코드 위생에 집착하는 편이에요. 미사용 코드를 찾으려고 knip을 쓰고, 폴더 위치나 import 방향처럼 코드만으로 판정할 수 있는 기준은 lint에 넣어요. 상태를 어디에 두고 어떤 추상화를 쓸지처럼 맥락이 필요한 기준은 skill과 AGENTS.md에 남겨요. 응집도와 결합도를 생각하고, 서로 다른 맥락을 나누고, 한 함수 안의 추상화 수준을 맞추려는 이유도 같아요.

이름과 구조가 일관되면 에이전트가 참고할 패턴이 생기고, 저도 코드를 빨리 파악할 수 있어요. 그렇다고 익숙한 모양으로 만드는 데만 집중하지는 않아요. 이름은 비슷한데 역할이 다르거나, 짧게 만들려고 중요한 분기를 숨겼다면 오히려 확인하기 어려워요. 코드를 읽으면서 각 부분의 역할과 실행 조건을 설명할 수 있는지 봐요.

AI 덕분에 구조를 크게 바꾸기도 수월해졌어요. 폴더 구조를 다시 나누거나 공통 컴포넌트의 인터페이스를 바꿀 때, 변경 기준을 정해 맡기고 여러 사용처가 의도한 패턴으로 바뀌었는지 확인해요. 덕분에 제품의 요구에 맞춰 저장소를 계속 고치면서도, 상태와 데이터의 책임이 분명하고 바뀐 부분을 읽기 쉬운 쪽으로 유지할 수 있어요.

코드 위생은 보기 좋은 코드를 남기려고만 하는 일이 아니에요. 화이트박스 테스트를 적은 시간으로 할 수 있게 만드는 준비예요.

## 마치며

처음에는 에이전트가 잘 짜면 읽을 필요도 없어질 것이라고 생각했어요. 지금은 만족스러운 구현이 나오면 제가 고치는 시간이 줄어드는 거라고 생각해요. 읽을 필요까지 없어지는 것은 아니고요.

블랙박스 테스트는 제품이 사용자에게 어떻게 동작하는지 알려 주고, 화이트박스 테스트는 그 동작이 어떤 경로로 만들어지는지 알려 줘요. 두 가지를 모두 통과해야 검증된 제품이라고 말할 수 있다고 생각해요. 그래서 저는 구현을 맡기되, 검증할 때는 코드를 읽어요.
