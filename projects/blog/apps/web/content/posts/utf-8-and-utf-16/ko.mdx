<Summary>

한글 '가'가 UTF-8에서 `EA B0 80` 3바이트가 되는 과정을 비트 단위로 따라가며, UTF-8이 바이트마다 붙이는 표시 비트로 글자의 경계를 알리는 방식을 정리했어요. 같은 글자를 16비트 단위로 적는 UTF-16과 비교하고, 자바스크립트에서 `'😀'.length`가 2인 이유와 바이트, 코드 포인트, 화면의 글자를 각각 세는 방법도 살펴봤어요.

</Summary>

UTF-8로 저장한 파일에 `A가`라는 문자열을 쓰면 `41 EA B0 80` 4바이트가 들어가요. A는 1바이트이고 가는 3바이트예요. 바이트 사이에 구분 기호가 없는데도 읽는 쪽은 `41`에서 A를 끝내고 `EA B0 80`을 묶어 가로 읽어요. '가'가 왜 하필 3바이트인지, 읽는 쪽은 어디까지가 한 글자인지 어떻게 아는지 UTF-8의 규칙을 비트 단위로 따라가 봤어요.

## 유니코드가 번호를 정하고, UTF-8이 바이트로 적어요

파일에는 결국 바이트가 들어가요. 그래서 `A가`를 저장하려면 글자마다 어떤 번호를 붙일지, 그 번호를 어떤 바이트로 적을지 정해야 해요.

번호는 유니코드가 정해요. A는 `U+0041`, 가는 `U+AC00`이고, 이런 번호를 **코드 포인트**라고 해요. 코드 포인트를 바이트로 적는 방법은 UTF-8이나 UTF-16 같은 인코딩이 정하고요. UTF는 Unicode Transformation Format의 약자이고, UTF-8의 8은 글자를 적는 기본 단위가 8비트, 즉 1바이트라는 뜻이에요. 글자 하나가 이 단위를 몇 개 쓰는지는 코드 포인트에 따라 1개에서 4개까지 달라져요. 가에 `U+AC00`을 붙이는 건 유니코드의 일이고, `U+AC00`을 `EA B0 80`으로 적는 건 UTF-8의 일이에요.

## 첫 바이트의 앞자리가 몇 바이트를 읽을지 알려 줘요

`A가`의 첫 바이트 `41`을 2진수로 쓰면 `01000001`이에요. UTF-8에서는 맨 앞 비트가 0이면 그 바이트 하나로 글자가 끝나요. 읽는 쪽은 `41` 하나로 A를 얻고 다음 바이트로 넘어가요. 이 1바이트 형식은 U+0000~U+007F를 ASCII와 같은 바이트 값으로 적기 때문에, ASCII로 저장한 텍스트는 그대로 UTF-8로 읽을 수 있어요.

다음 바이트 `EA`는 `11101010`이고, 이번에는 `1110`으로 시작해요. UTF-8은 첫 바이트 맨 앞에 연속으로 나오는 1의 개수로 그 글자가 쓰는 바이트 수를 표시하고, 뒤따르는 0으로 표시가 끝났음을 알려요. `1110`에는 1이 세 개 있으니 이 바이트를 포함해 모두 3바이트를 읽으라는 뜻이에요. 그래서 읽는 쪽은 `EA`를 본 순간 뒤의 `B0`과 `80`도 같은 글자라는 걸 알아요. 뒤따르는 두 바이트는 모두 `10`으로 시작해요.

| 바이트의 앞자리 | 읽는 쪽의 판단 |
| --- | --- |
| `0` | 이 바이트 하나로 글자가 끝나요 |
| `110` | 여기서 시작해 모두 2바이트를 읽어요 |
| `1110` | 여기서 시작해 모두 3바이트를 읽어요 |
| `11110` | 여기서 시작해 모두 4바이트를 읽어요 |
| `10` | 앞에서 시작한 글자에 이어지는 바이트예요 |

`110`은 3비트짜리 표시이지만 가리키는 것은 2바이트이고, `1110`은 4비트짜리 표시이지만 가리키는 것은 3바이트예요. 바이트 수는 표시의 길이가 아니라 맨 앞에 이어진 1의 개수로 정해져요.

## 2바이트 형식에는 번호를 담을 자리가 11비트뿐이에요

가의 코드 포인트 `AC00`을 16진수 한 자리마다 4비트로 바꾸면 `1010 1100 0000 0000`이에요. 맨 앞 비트가 1이라서 이 번호를 적으려면 16비트가 모두 필요해요.

처음에는 2바이트면 16비트인데 왜 번호에는 11비트만 쓰는지 헷갈렸어요. 2바이트 형식도 16비트를 모두 읽지만, 그중 일부는 표시 비트예요. 1바이트에는 0이나 1을 적는 칸이 8개 있고, 2바이트 형식은 이 칸을 다음처럼 나눠 써요.

```text
첫째 바이트  110 xxxxx
둘째 바이트  10  xxxxxx
```

첫째 바이트에서 `110`이 3칸을 쓰니 5칸이 남고, 둘째 바이트에서 `10`이 2칸을 쓰니 6칸이 남아요. 번호를 적을 수 있는 칸은 5 + 6 = 11칸이에요. 같은 방식으로 세면 형식마다 담을 수 있는 번호의 크기가 나와요. [RFC 3629](https://www.rfc-editor.org/rfc/rfc3629)에 정의된 범위를 예시와 함께 정리했어요.

| 형식 | 바이트 패턴 | 번호를 담는 비트 | 코드 포인트 범위 | 예시 |
| --- | --- | --- | --- | --- |
| 1바이트 | `0xxxxxxx` | 7 | U+0000~U+007F | `A` → `41` |
| 2바이트 | `110xxxxx 10xxxxxx` | 5 + 6 = 11 | U+0080~U+07FF | `é` → `C3 A9` |
| 3바이트 | `1110xxxx 10xxxxxx 10xxxxxx` | 4 + 6 + 6 = 16 | U+0800~U+FFFF | `가` → `EA B0 80` |
| 4바이트 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` | 3 + 6 + 6 + 6 = 21 | U+10000~U+10FFFF | `😀` → `F0 9F 98 80` |

가의 번호는 16비트가 필요해서 11비트짜리 2바이트 형식에는 들어가지 않고, 16비트를 담는 3바이트 형식을 써요. 4바이트 형식에도 들어가긴 하지만 UTF-8은 번호가 들어가는 가장 짧은 형식만 올바른 표현으로 인정해요. 그래서 가는 언제나 3바이트예요.

이제 `1010110000000000`을 왼쪽부터 4비트, 6비트, 6비트로 잘라 각 바이트의 빈칸에 넣어요.

| 구분 | 첫째 바이트 | 둘째 바이트 | 셋째 바이트 |
| --- | --- | --- | --- |
| UTF-8이 붙이는 표시 | `1110` | `10` | `10` |
| `AC00`에서 가져온 비트 | `1010` | `110000` | `000000` |
| 실제로 저장되는 바이트 | `11101010` | `10110000` | `10000000` |
| 16진수 | `EA` | `B0` | `80` |

읽을 때는 거꾸로 하면 돼요. `EA B0 80`에서 표시 비트 `1110`, `10`, `10`을 떼고 남은 `1010`, `110000`, `000000`을 이어 붙이면 `AC00`이 돌아와요.

## 이어지는 바이트에는 모두 10을 붙여요

앞자리 표만 봤을 때는 가의 세 바이트가 `1110`, `110`, `10`으로 시작할 거라고 생각했어요. 표를 보면 남은 바이트 수를 하나씩 줄여 가며 표시할 것 같지만, 실제로 저장되는 바이트는 `11101010 10110000 10000000`이에요.

`110`은 새로운 2바이트 글자가 시작될 때 쓰는 표시예요. 둘째 바이트가 `110`으로 시작하면 읽는 쪽은 거기서 새 글자가 시작된다고 판단해요. 몇 바이트를 읽을지는 첫 바이트가 이미 정했으니, 뒤따르는 바이트는 자기가 이어지는 바이트라는 것만 알리면 돼요. 둘째 바이트 `10110000`에도 `110`이 보이지만, 이 바이트는 `10`과 `110000`으로 끊어 읽어요. 맨 앞의 `10`이 표시이고 뒤의 `110000`은 가의 번호를 이루는 데이터예요.

이어지는 바이트에 `10`을 쓰는 것도 바이트의 시작 모양으로 역할을 나누기 때문이에요. 0으로 시작하는 바이트는 A 같은 1바이트 글자이고, 11로 시작하는 바이트는 2~4바이트 글자의 첫 바이트예요. 남은 `10`을 이어지는 바이트에 쓰면 세 역할이 서로 겹치지 않아요. 가를 읽는 과정을 바이트마다 보면 다음과 같아요.

| 순서 | 실제 바이트 | 읽는 쪽이 아는 것 |
| --- | --- | --- |
| 첫째 | `1110 1010` (`EA`) | 이 바이트를 포함해 모두 3바이트예요. 두 개를 더 읽어요 |
| 둘째 | `10 110000` (`B0`) | 같은 글자가 이어져요. 한 개를 더 읽어요 |
| 셋째 | `10 000000` (`80`) | 같은 글자가 이어져요. 3바이트를 다 읽었어요 |

정리하고 나니 UTF-8의 모든 바이트는 맨 앞에 자기 역할을 알려 주는 비트를 갖고 있었어요. 1바이트로 끝나는 A도 맨 앞의 0이 표시예요. 표시가 데이터와 같은 바이트 안에 들어가서 번호를 담을 공간은 바이트 크기보다 작아지지만, 어느 바이트를 보더라도 글자의 시작인지 이어지는 부분인지 알 수 있어요. 바이트열 중간부터 읽게 되더라도 `10`으로 시작하는 바이트를 건너뛰면 다음 글자의 시작을 찾을 수 있고요.

## 글자가 청크 사이에서 나뉘어도 디코더가 기다려요

네트워크로 받는 데이터는 여러 청크로 나뉘어 도착할 수 있고, 청크의 경계가 글자의 경계와 맞는다는 보장은 없어요. 가의 `EA B0`이 한 청크로, `80`이 다음 청크로 올 수도 있어요. 청크마다 따로 문자열로 바꾸면 두 조각 모두 올바른 UTF-8이 아니어서 대체 문자 `�`로 바뀌어요.

스트리밍 디코더는 첫 바이트 `EA`를 보고 3바이트가 필요하다는 걸 알기 때문에, 모자란 바이트를 보관해 뒀다가 다음 청크에서 `80`을 받으면 가를 완성해요. 브라우저와 Node.js의 [`TextDecoder`](https://developer.mozilla.org/en-US/docs/Web/API/TextDecoder/decode)에서는 `stream: true` 옵션이 이 역할을 해요.

```js
const first = new Uint8Array([0xea, 0xb0]);
const second = new Uint8Array([0x80]);

// 청크마다 새 디코더로 바꾸면 글자가 깨져요
new TextDecoder().decode(first) + new TextDecoder().decode(second); // '��'

// 같은 디코더에 stream: true를 주면 모자란 바이트를 기다려요
const decoder = new TextDecoder();
decoder.decode(first, { stream: true }); // ''
decoder.decode(second, { stream: true }); // '가'
decoder.decode(); // 스트림이 끝나면 한 번 더 호출해 남은 바이트를 비워요
```

`fetch` 응답 본문처럼 `ReadableStream`으로 받는 데이터는 [`TextDecoderStream`](https://developer.mozilla.org/en-US/docs/Web/API/TextDecoderStream)에 `pipeThrough`로 연결해도 같은 처리를 해요.

## UTF-16은 16비트 칸을 하나나 두 개 써요

UTF-16은 16비트, 즉 2바이트를 한 칸으로 묶어 읽어요. 이 한 칸을 **코드 유닛**이라고 해요. 가의 번호 `AC00`은 16비트 한 칸에 그대로 들어가서 UTF-16에서는 2바이트예요. UTF-8에서는 표시 비트 때문에 3바이트가 필요했지만, UTF-16은 이 범위의 글자에 표시 비트를 붙이지 않아요. 반대로 A는 UTF-8에서 1바이트이지만 UTF-16에서는 `0041`로 2바이트를 써요.

😀의 번호 `1F600`은 17비트가 필요해서 한 칸에 들어가지 않아요. 이때 UTF-16은 두 칸을 짝지어 쓰고, 이 짝을 **서로게이트 쌍**이라고 해요. 번호에서 `10000`을 뺀 20비트를 앞뒤 10비트씩 나누고, 앞쪽은 `D800`에, 뒤쪽은 `DC00`에 더해요.

```text
1F600 - 10000 = 0F600
0F600 → 0000111101 1000000000 (앞 10비트, 뒤 10비트)
D800 + 03D = D83D
DC00 + 200 = DE00
```

`D800`부터 `DFFF`까지는 서로게이트 쌍에만 쓰도록 비워 둔 범위라서 어떤 글자에도 배정되지 않아요. 그래서 읽는 쪽은 첫 칸이 `D800`~`DBFF` 범위에 있으면 다음 칸까지 읽어 한 글자로 합쳐요. UTF-8이 바이트의 앞자리로 경계를 표시한다면, UTF-16은 예약해 둔 값의 범위로 표시하는 셈이에요. 계산 과정은 [유니코드 FAQ](https://www.unicode.org/faq/utf_bom.html)에도 정리돼 있어요.

## 자바스크립트의 length는 UTF-16 코드 유닛을 세요

자바스크립트 문자열은 [UTF-16 코드 유닛을 나열한 값](https://tc39.es/ecma262/#sec-ecmascript-language-types-string-type)이고, `length`는 그 코드 유닛의 개수예요. 가는 한 칸이라 `'가'.length`가 1이고, 😀는 서로게이트 쌍 두 칸이라 `'😀'.length`가 2예요.

```js
'가'.length; // 1
'😀'.length; // 2
'😀'.charCodeAt(0).toString(16); // 'd83d', 서로게이트 쌍의 앞 칸
'😀'.codePointAt(0).toString(16); // '1f600', 두 칸을 합친 코드 포인트
[...'😀'].length; // 1, 문자열을 순회하면 코드 포인트 단위로 나눠요
```

`charCodeAt`은 코드 유닛 하나를 그대로 돌려주고, `codePointAt`은 그 위치에서 시작하는 서로게이트 쌍을 합쳐 코드 포인트로 돌려줘요. 그래서 `length`를 기준으로 문자열을 자르면 서로게이트 쌍이 갈라질 수 있어요. `'😀'.slice(0, 1)`에는 짝을 잃은 앞 칸 `\uD83D`만 남고, 이 값을 UTF-8로 인코딩하면 대체 문자의 바이트인 `EF BF BD`가 나와요.

## 화면에서 보는 한 글자는 또 다른 단위예요

코드 포인트 하나가 화면의 글자 하나와 같다고 할 수도 없어요. 👩‍💻는 화면에서 한 글자로 보이지만 여성 `U+1F469`, 둘을 이어 주는 보이지 않는 문자 ZWJ `U+200D`, 노트북 `U+1F4BB` 세 코드 포인트로 이뤄져 있어요. 사용자가 한 글자로 인식하는 이런 단위를 [그래핌 클러스터](https://www.unicode.org/reports/tr29/)라고 해요.

같은 문자열이라도 무엇을 세느냐에 따라 길이가 달라져요.

| 문자열 | UTF-8 바이트 | UTF-16 코드 유닛 (`length`) | 코드 포인트 | 그래핌 클러스터 |
| --- | --- | --- | --- | --- |
| `A` | 1 | 1 | 1 | 1 |
| `가` | 3 | 1 | 1 | 1 |
| `😀` | 4 | 2 | 1 | 1 |
| `👩‍💻` | 11 | 5 | 3 | 1 |

전송할 데이터의 크기를 재려면 [`TextEncoder`](https://developer.mozilla.org/en-US/docs/Web/API/TextEncoder)로 UTF-8 바이트 수를 세고, 화면에서 보이는 글자 수를 세려면 [`Intl.Segmenter`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter)로 그래핌 클러스터를 나눠요.

```js
const text = '👩‍💻';

text.length; // 5
[...text].length; // 3
new TextEncoder().encode(text).length; // 11

const segmenter = new Intl.Segmenter('ko', { granularity: 'grapheme' });
[...segmenter.segment(text)].length; // 1
```
