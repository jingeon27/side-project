A hospital review can appear in a list and on its detail screen. Liking it changed only the component where the button was pressed. Each `ReviewItem` copied the server's like state and count into local `isLiked` and `likeCount` state, and the handler updated only that copy.

```tsx
function ReviewItem({ review }: { review: Review }) {
  const [isLiked, setIsLiked] = useState(review.like);
  const [likeCount, setLikeCount] = useState(review.likeCnt);

  const handleChange = async (checked: boolean) => {
    const previous = { isLiked, likeCount };

    setIsLiked(checked);
    setLikeCount((count) => count + (checked ? 1 : -1));

    try {
      await fetchReviewLike({
        reviewId: review.reviewId,
        feedbackType: checked ? 'LIKE' : 'UNLIKE',
      });
    } catch {
      setIsLiked(previous.isLiked);
      setLikeCount(previous.likeCount);
    }
  };

  return <LikeSwitch like={isLiked} likeCnt={likeCount} onChange={handleChange} />;
}
```

This code changes the screen without waiting for the response. Assuming a request will succeed and showing the result first is called an optimistic update. If the button waited for the response, it would sit unchanged for a network round trip after each press. The assumption can be wrong, so code to undo the change has to come with it. Here, `previous` holds the values to restore.

The button responded immediately, but the list and detail could disagree about the same review. `useState` reads its argument only on the first mount, so the copied value stays put even when a parent passes a new `review`. A failed request restored only the component's own state.

The review response was already in TanStack Query's cache. TanStack Query stores server responses by query key and re-renders the components subscribed to a key when its value changes. With screens subscribed to the cache instead of keeping copies, the like handler can update the relevant caches together and restore them together on failure. The examples use TanStack Query v5, which the project used.

## The sequence

Moving state into the cache does not remove the need for rollback. Requests that change server data go through `useMutation`: `onMutate` runs before the request is sent, `onError` runs on failure, and `onSettled` runs last after either outcome. TanStack Query does not save the previous value just because `onMutate` calls `setQueryData`. The value to restore has to be saved first, and that saved value is called a snapshot.

The work around the request runs in this order.

1. Cancel an ongoing refetch.
2. Save a snapshot of the cache before the change.
3. Update the cache optimistically.
4. Return the snapshot from `onMutate`.
5. Restore it in `onError` if the request fails.
6. Use `invalidateQueries` after success or failure to synchronize with the server.

The official optimistic-update example follows this flow too.

## Setup: query key scope

Updating only the cache for the current screen leaves the original problem in place. Lists differ by hospital and page size, and a detail uses another key. Passing the front part of a key to a cache lookup matches every cache starting with it, so a key hierarchy lets one prefix find every cached list.

```typescript
const reviewKeys = {
  all: ['review'] as const,
  infinite: ['review', 'infinite'] as const,
  detail: (reviewId: number) =>
    ['review', 'fetchReviewsById', reviewId] as const,
};
```

All these queries fall under `reviewKeys.infinite` despite their different parameters.

```text
['review', 'infinite', { hospitalId: 1, size: 3 }]
['review', 'infinite', { hospitalId: 1, size: 20 }]
['review', 'infinite', { hospitalId: 2, size: 10 }]
```

Using `reviewKeys.infinite` avoids fixing the handler to one `size`. The same update can reach every matching list already in the cache.

## Setup: a pure function for one review

One function updates a review for both list and detail, so the two cannot calculate the count differently. A pure function returns the same result for the same input and changes nothing outside itself. The cache has to be treated as immutable, so values passed to `setQueryData` are new objects rather than edited ones. The function returns the original object when the ID does not match or the like state is already correct. Applying the same state again does not change the count twice.

```tsx
import type { InfiniteData, QueryKey } from '@tanstack/react-query';

type Review = TReviewDTO;
type ReviewInfiniteData = InfiniteData<
  TGlobalListResponse<TReviewDTO[]>
>;
type ReviewDetailResponse = TGlobalResponse<TReviewDetailDTO>;

type ReviewLikeVariables = {
  reviewId: number;
  feedbackType: 'LIKE' | 'UNLIKE';
};

function updateReviewLike<T extends Review>(
  review: T,
  { reviewId, feedbackType }: ReviewLikeVariables,
): T {
  if (review.reviewId !== reviewId) return review;

  const nextLike = feedbackType === 'LIKE';

  // Reapplying the same state must not change the count twice.
  if (review.like === nextLike) return review;

  return {
    ...review,
    like: nextLike,
    likeCnt: Math.max(0, review.likeCnt + (nextLike ? 1 : -1)),
  };
}
```

An infinite list's cache holds its loaded pages in a `pages` array. Apply the function to the reviews on each page's `list`. Unchanged reviews and the rest of the response stay intact.

```typescript
function updateReviewList(
  oldData: ReviewInfiniteData | undefined,
  variables: ReviewLikeVariables,) {
  if (!oldData) return oldData;

  return {
    ...oldData,
    pages: oldData.pages.map((page) => ({
      ...page,
      data: {
        ...page.data,
        list: page.data.list.map((review) =>
          updateReviewLike(review, variables),
        ),
      },
    })),
  };
}
```

## useReviewLike

The six steps appear in this hook in order.

```tsx
type ReviewLikeContext = {
  listSnapshots: Array<[
    QueryKey,
    ReviewInfiniteData | undefined,
  ]>;
  detailKey: QueryKey;
  detailSnapshot: ReviewDetailResponse | undefined;
};

export function useReviewLike() {
  const queryClient = useQueryClient();

  const mutation = useMutation<
    void,
    Error,
    ReviewLikeVariables,
    ReviewLikeContext
  >({
    mutationKey: ['fetchReviewLike'],
    mutationFn: fetchReviewLike,

    onMutate: async (variables) => {
      const detailKey = reviewKeys.detail(variables.reviewId);

      // Prevent an in-flight refetch from overwriting the optimistic value.
      await Promise.all([
        queryClient.cancelQueries({ queryKey: reviewKeys.infinite }),
        queryClient.cancelQueries({ queryKey: detailKey }),
      ]);

      const listSnapshots =
        queryClient.getQueriesData<ReviewInfiniteData>({
          queryKey: reviewKeys.infinite,
        });

      const detailSnapshot =
        queryClient.getQueryData<ReviewDetailResponse>(detailKey);

      queryClient.setQueriesData<ReviewInfiniteData>(
        { queryKey: reviewKeys.infinite },
        (oldData) => updateReviewList(oldData, variables),
      );

      queryClient.setQueryData<ReviewDetailResponse>(
        detailKey,
        (oldData) => {
          if (!oldData) return oldData;

          return {
            ...oldData,
            data: updateReviewLike(oldData.data, variables),
          };
        },
      );

      return {
        listSnapshots,
        detailKey,
        detailSnapshot,
      };
    },

    onError: (error, _variables, context) => {
      context?.listSnapshots.forEach(([queryKey, oldData]) => {
        queryClient.setQueryData(queryKey, oldData);
      });

      if (context) {
        queryClient.setQueryData(
          context.detailKey,
          context.detailSnapshot,
        );
      }

      toast.warning(ServiceError.getMessage(error));
    },

    onSettled: () =>
      queryClient.invalidateQueries({ queryKey: reviewKeys.all }),
  });

  return {
    handleLike: mutation.mutate,
    isLikePending: mutation.isPending,
  };
}
```

The click handler does not need to await a result, so it uses `mutate`. `onError` handles the notice and rollback. With `mutateAsync`, the caller would also need to handle the rejected Promise separately.

### 1. Cancel refetches

`onMutate` starts with `cancelQueries`. An in-flight request that finishes late could overwrite the optimistic value, because a refetch started just before the click may carry the count from before the like. The result of a cancelled query does not enter the cache.

### 2. Save snapshots

Rollback needs the same scope as the update. `getQueriesData` saves the previous lists by key, and `getQueryData` saves the previous detail response. `getQueriesData` returns an array of `[queryKey, data]` pairs.

`getQueriesData({ queryKey: reviewKeys.infinite })` returns **queries that currently exist in the cache** under that prefix. It does not create new list caches or automatically synchronize screens that will be added later.

### 3. Update the caches

`setQueriesData` applies `updateReviewList` to the lists, and `setQueryData` applies `updateReviewLike` to the detail. List keys share one prefix, and the detail uses another key, so it is updated separately. When an updater returns `undefined`, `setQueryData` creates nothing, so a detail nobody has fetched yet does not gain a cache entry. Another cache displaying likes would also need to join this handler.

### 4. Return the snapshots

`onMutate` returns the list snapshots, the detail key, and the detail snapshot. That value arrives as `context` in `onError`. Variables inside `onMutate` are out of reach from `onError`, which is why they travel through the return value.

### 5. Restore on failure

On failure, `onError` puts each saved value back under its key. `toast.warning` shows the user the error message. `updateReviewLike` leaves a matching state alone and never goes below zero, so running it once more in the opposite direction cannot be counted on to reach the original value. Putting back the saved value avoids that.

### 6. Synchronize with the server

After either outcome, `onSettled` fetches the server state again. This reconciles the count calculated in the browser with the server's value. `invalidateQueries` marks the matching caches as outdated and refetches the queries screens are subscribed to. Returning its Promise keeps the mutation pending until that revalidation finishes.

## Repeated clicks need separate handling

The code so far handles one interaction at a time. If someone likes and unlikes repeatedly, the first request can finish last. Saving snapshots does not establish request order.

For this screen, disabling the button while its request is pending is the simplest approach.

```tsx
const { handleLike, isLikePending } = useReviewLike();

<LikeSwitch
  {...review}
  disabled={isLikePending}
  onChange={(checked) =>
    handleLike({
      reviewId: review.reviewId,
      feedbackType: checked ? 'LIKE' : 'UNLIKE',
    })
  }
/>
```

Because step 6 returns the Promise, the button stays disabled until the refetch finishes, and a like cannot be undone right away during that time.

If repeated interactions must be allowed, the design also needs to consider serializing requests by review ID, applying only the latest intention, and server-side idempotency. Cache snapshots alone do not solve that problem.

## How to verify

An icon changing quickly is only part of the behavior to check. With the same review in lists of different sizes and in a detail cache, they should change together before the response arrives. A failed request should return each cache to its own saved value.

An ongoing refetch must not overwrite that change midway. Applying the same like state again must not increase the count twice or make it negative. After revalidation, the displayed values should match the server.

Moving the value out of local state also changed the scope of a like action. The handler now updates the lists and detail showing that review in the same sequence.

```text
User input
  -> Cancel related refetches
  -> Save list and detail cache snapshots
  -> Update list and detail caches immediately
  -> Restore snapshots directly on request failure
  -> Revalidate server data after success or failure
```
