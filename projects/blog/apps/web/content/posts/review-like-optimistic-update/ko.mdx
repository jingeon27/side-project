<Summary>

같은 병원 리뷰가 목록과 상세에 함께 나오는데, 좋아요를 누르면 누른 쪽만 바뀌었어요. 좋아요 값을 TanStack Query 캐시로 옮겨 응답 전에 함께 바꾸고, 요청이 실패하면 저장해 둔 스냅샷으로 되돌렸어요. 그 구현을 여섯 단계로 나눠 v5 코드로 따라가요.

</Summary>

병원 리뷰는 목록에서도, 상세 화면에서도 볼 수 있어요. 좋아요를 누르면 버튼을 누른 쪽만 바뀌고 있었어요. 각 `ReviewItem`이 서버에서 받은 좋아요 상태와 개수를 `isLiked`, `likeCount` 로컬 상태로 복사해 두고 그 값만 수정했기 때문이에요.

```tsx
function ReviewItem({ review }: { review: Review }) {
  const [isLiked, setIsLiked] = useState(review.like);
  const [likeCount, setLikeCount] = useState(review.likeCnt);

  const handleChange = async (checked: boolean) => {
    const previous = { isLiked, likeCount };

    setIsLiked(checked);
    setLikeCount((count) => count + (checked ? 1 : -1));

    try {
      await fetchReviewLike({
        reviewId: review.reviewId,
        feedbackType: checked ? 'LIKE' : 'UNLIKE',
      });
    } catch {
      setIsLiked(previous.isLiked);
      setLikeCount(previous.likeCount);
    }
  };

  return <LikeSwitch like={isLiked} likeCnt={likeCount} onChange={handleChange} />;
}
```

이 코드는 응답을 기다리지 않고 화면부터 바꿔요. 요청이 성공할 것으로 가정하고 먼저 화면에 반영하는 방식을 낙관적 업데이트(optimistic update)라고 해요. 응답을 기다렸다가 바꾸면 누른 뒤 네트워크 왕복 시간만큼 버튼이 그대로 있어요. 가정이 틀릴 수 있으니 실패하면 되돌리는 코드가 함께 있어야 해요. 위 코드에서는 `previous`가 그 값을 들고 있어요.

버튼은 바로 반응했어요. 하지만 목록과 상세가 서로 다른 값을 들고 있어서 같은 리뷰도 화면에 따라 좋아요 수가 달라질 수 있었어요. `useState`의 인자는 처음 마운트할 때만 쓰이므로, 부모가 새 `review`를 넘겨도 복사해 둔 값은 그대로예요. 실패했을 때도 각 컴포넌트가 자기 상태만 되돌렸어요.

리뷰 응답은 이미 TanStack Query 캐시에 있었어요. TanStack Query는 서버 응답을 query key별로 저장하고, 그 key를 구독하는 컴포넌트를 값이 바뀔 때 다시 그려요. 화면이 복사본 대신 캐시를 구독하게 하면 관련 캐시를 함께 바꾸고 실패 시 함께 복구할 수 있어요. 아래 코드는 프로젝트에서 사용한 TanStack Query v5로 작성했어요.

## 전체 순서

캐시로 옮겨도 실패 처리는 남아요. 서버 값을 바꾸는 요청은 `useMutation`으로 다루는데, `onMutate`는 요청을 보내기 전에, `onError`는 실패했을 때, `onSettled`는 성공과 실패 모두의 마지막에 불려요. `onMutate`에서 `setQueryData`로 값을 바꿔도 TanStack Query가 이전 값을 따로 보관해 주지는 않아요. 돌려놓을 값은 먼저 저장해야 해요. 이 변경 전 값을 snapshot이라고 불러요.

요청 전후의 처리는 다음 순서로 묶어요.

1. 진행 중인 refetch를 취소해요.
2. 변경 전 캐시를 snapshot으로 저장해요.
3. 캐시를 낙관적으로 변경해요.
4. `onMutate`에서 snapshot을 반환해요.
5. 요청이 실패하면 `onError`에서 snapshot을 다시 넣어요.
6. 성공과 실패 모두 `invalidateQueries`로 서버 값과 다시 맞춰요.

공식 문서의 낙관적 갱신 예제도 이 흐름을 사용해요.

## 준비: query key 범위

좋아요를 누른 화면의 캐시만 바꾸면 처음 문제가 그대로 남아요. 목록은 병원과 페이지 크기에 따라 여러 개가 생기고, 상세는 다른 key를 써요. 캐시를 찾는 함수에 key의 앞부분만 넘기면 그 앞부분으로 시작하는 캐시가 모두 걸려요. 같은 종류의 목록을 한꺼번에 찾을 수 있도록 key를 계층으로 나눠요.

```typescript
const reviewKeys = {
  all: ['review'] as const,
  infinite: ['review', 'infinite'] as const,
  detail: (reviewId: number) =>
    ['review', 'fetchReviewsById', reviewId] as const,
};
```

다음 쿼리는 파라미터가 달라도 모두 `reviewKeys.infinite`에 포함돼요.

```text
['review', 'infinite', { hospitalId: 1, size: 3 }]
['review', 'infinite', { hospitalId: 1, size: 20 }]
['review', 'infinite', { hospitalId: 2, size: 10 }]
```

`reviewKeys.infinite`로 찾으면 `size`를 하나로 고정하지 않아도 돼요. 현재 캐시에 있는 목록 중 어떤 페이지 크기를 쓰든 같은 갱신 함수를 적용할 수 있어요.

## 준비: 리뷰 한 건을 바꾸는 순수 함수

목록과 상세에서 좋아요 수를 다르게 계산하지 않도록 함수를 하나 둬요. 순수 함수는 같은 입력에 같은 결과를 돌려주고 바깥 값을 바꾸지 않는 함수예요. 캐시는 불변으로 다뤄야 해서, `setQueryData`에 넘길 값도 기존 객체를 고치지 않고 새로 만들어요. 대상 ID가 아니거나 이미 같은 좋아요 상태라면 원래 객체를 그대로 돌려줘요. 같은 상태를 다시 적용해도 숫자가 중복으로 바뀌지 않아요.

```tsx
import type { InfiniteData, QueryKey } from '@tanstack/react-query';

type Review = TReviewDTO;
type ReviewInfiniteData = InfiniteData<
  TGlobalListResponse<TReviewDTO[]>
>;
type ReviewDetailResponse = TGlobalResponse<TReviewDetailDTO>;

type ReviewLikeVariables = {
  reviewId: number;
  feedbackType: 'LIKE' | 'UNLIKE';
};

function updateReviewLike<T extends Review>(
  review: T,
  { reviewId, feedbackType }: ReviewLikeVariables,
): T {
  if (review.reviewId !== reviewId) return review;

  const nextLike = feedbackType === 'LIKE';

  // 같은 상태를 다시 반영할 때 숫자가 중복으로 변하지 않게 한다.
  if (review.like === nextLike) return review;

  return {
    ...review,
    like: nextLike,
    likeCnt: Math.max(0, review.likeCnt + (nextLike ? 1 : -1)),
  };
}
```

무한 목록의 캐시는 불러온 페이지를 `pages` 배열에 담아요. 각 페이지의 `list`를 돌면서 이 함수를 적용해요. 바뀌지 않은 리뷰와 페이지 응답의 나머지 값은 그대로 남겨요.

```typescript
function updateReviewList(
  oldData: ReviewInfiniteData | undefined,
  variables: ReviewLikeVariables,) {
  if (!oldData) return oldData;

  return {
    ...oldData,
    pages: oldData.pages.map((page) => ({
      ...page,
      data: {
        ...page.data,
        list: page.data.list.map((review) =>
          updateReviewLike(review, variables),
        ),
      },
    })),
  };
}
```

## useReviewLike

여섯 단계가 이 훅에 순서대로 들어 있어요.

```tsx
type ReviewLikeContext = {
  listSnapshots: Array<[
    QueryKey,
    ReviewInfiniteData | undefined,
  ]>;
  detailKey: QueryKey;
  detailSnapshot: ReviewDetailResponse | undefined;
};

export function useReviewLike() {
  const queryClient = useQueryClient();

  const mutation = useMutation<
    void,
    Error,
    ReviewLikeVariables,
    ReviewLikeContext
  >({
    mutationKey: ['fetchReviewLike'],
    mutationFn: fetchReviewLike,

    onMutate: async (variables) => {
      const detailKey = reviewKeys.detail(variables.reviewId);

      // 이미 진행 중인 refetch가 낙관적 값을 덮지 않게 한다.
      await Promise.all([
        queryClient.cancelQueries({ queryKey: reviewKeys.infinite }),
        queryClient.cancelQueries({ queryKey: detailKey }),
      ]);

      const listSnapshots =
        queryClient.getQueriesData<ReviewInfiniteData>({
          queryKey: reviewKeys.infinite,
        });

      const detailSnapshot =
        queryClient.getQueryData<ReviewDetailResponse>(detailKey);

      queryClient.setQueriesData<ReviewInfiniteData>(
        { queryKey: reviewKeys.infinite },
        (oldData) => updateReviewList(oldData, variables),
      );

      queryClient.setQueryData<ReviewDetailResponse>(
        detailKey,
        (oldData) => {
          if (!oldData) return oldData;

          return {
            ...oldData,
            data: updateReviewLike(oldData.data, variables),
          };
        },
      );

      return {
        listSnapshots,
        detailKey,
        detailSnapshot,
      };
    },

    onError: (error, _variables, context) => {
      context?.listSnapshots.forEach(([queryKey, oldData]) => {
        queryClient.setQueryData(queryKey, oldData);
      });

      if (context) {
        queryClient.setQueryData(
          context.detailKey,
          context.detailSnapshot,
        );
      }

      toast.warning(ServiceError.getMessage(error));
    },

    onSettled: () =>
      queryClient.invalidateQueries({ queryKey: reviewKeys.all }),
  });

  return {
    handleLike: mutation.mutateAsync,
    isLikePending: mutation.isPending,
  };
}
```

### 1. refetch 취소

`onMutate`는 `cancelQueries`로 시작해요. 진행 중인 요청이 늦게 끝나면 방금 바꾼 값을 덮을 수 있어요. 좋아요를 누르기 직전에 시작한 재조회의 응답에는 좋아요 전 값이 들어 있을 수 있기 때문이에요. 취소한 조회의 결과는 캐시에 들어가지 않아요.

### 2. snapshot 저장

복구할 때도 목록과 상세를 같이 다뤄야 해요. `getQueriesData`로 이전 목록을 key별로, `getQueryData`로 이전 상세 응답을 저장해요. `getQueriesData`의 결과는 `[queryKey, data]` 쌍의 배열이에요.

`getQueriesData({ queryKey: reviewKeys.infinite })`는 해당 prefix로 **현재 캐시에 존재하는 쿼리**를 반환해요. 새로운 목록 캐시를 만들거나 앞으로 생길 화면까지 자동으로 동기화하지는 않아요.

### 3. 캐시 변경

`setQueriesData`로 목록들에 `updateReviewList`를 적용하고, `setQueryData`로 상세에 `updateReviewLike`를 적용해요. 목록 key는 같은 prefix를 쓰도록 맞췄고, 다른 key를 쓰는 상세는 별도로 갱신해요. 갱신 함수가 `undefined`를 돌려주면 `setQueryData`는 캐시를 만들지 않으므로, 아직 조회하지 않은 상세의 캐시가 새로 생기지 않아요. 나중에 좋아요를 표시하는 캐시가 더 생기면 그 캐시도 이 처리에 넣어야 해요.

### 4. snapshot 반환

`onMutate`는 목록 snapshot과 상세 key, 상세 snapshot을 함께 반환해요. 이 값이 `onError`의 `context`로 들어와요. `onMutate` 안의 변수는 `onError`에서 볼 수 없으니 반환값으로 넘겨요.

### 5. 실패 시 복구

요청이 실패하면 `onError`가 저장한 값을 각 key에 다시 넣어요. 사용자에게는 `toast.warning`으로 오류 메시지를 보여 줘요. `updateReviewLike`는 같은 상태면 값을 바꾸지 않고 0 아래로도 내리지 않으므로, 반대 방향으로 한 번 더 계산해서는 원래 값으로 돌아온다고 볼 수 없어요. 그래서 저장해 둔 값을 그대로 넣어요.

### 6. 서버 값과 다시 맞추기

성공과 실패 뒤에는 `onSettled`에서 서버 값을 다시 조회해요. 클라이언트에서 계산한 좋아요 수를 서버 값과 다시 맞추는 단계예요. `invalidateQueries`는 대상 캐시를 오래된 것으로 표시하고, 화면이 구독 중인 쿼리를 다시 조회해요. 여기서 `invalidateQueries`의 Promise를 반환하면 그 조회가 끝날 때까지 mutation의 pending 상태를 유지할 수 있어요.

## 연속 클릭은 별도 처리

여기까지는 한 번의 조작을 다룬 코드예요. 좋아요와 취소를 연달아 누르면 먼저 보낸 요청이 나중에 끝날 수도 있어요. snapshot을 저장하는 것만으로 요청 순서까지 정해지지는 않아요.

이 화면에서는 요청이 진행되는 동안 같은 버튼을 비활성화하는 방법이 가장 단순해요.

```tsx
const { handleLike, isLikePending } = useReviewLike();

<LikeSwitch
  {...review}
  disabled={isLikePending}
  onChange={(checked) =>
    handleLike({
      reviewId: review.reviewId,
      feedbackType: checked ? 'LIKE' : 'UNLIKE',
    })
  }
/>
```

6단계에서 Promise를 반환하므로 버튼은 재조회가 끝날 때까지 비활성화돼요. 그동안에는 좋아요를 바로 취소할 수 없어요.

연속 조작을 허용해야 한다면 review ID별 요청 직렬화, 마지막 의도만 반영하는 방식, 서버의 멱등성까지 함께 설계해야 해요. 캐시 snapshot만으로 해결되는 문제가 아니에요.

## 확인 방법

목록의 아이콘이 빨리 바뀌는 것만 보면 부족해요. `size`가 다른 목록과 상세에 같은 리뷰를 넣고, 응답이 오기 전에 함께 바뀌는지 봐요. 실패시키면 각각 저장해 둔 값으로 돌아와야 해요.

진행 중이던 refetch가 중간에 값을 덮는 경우와, 이미 좋아요인 리뷰에 같은 상태를 다시 적용하는 경우도 확인해요. 좋아요 수가 두 번 늘거나 음수가 되어서는 안 되고, 재조회가 끝나면 서버의 값과 일치해야 해요.

로컬 상태를 캐시로 옮기면서 좋아요 한 번에 바뀌는 범위도 달라졌어요. 버튼 하나의 상태를 고치는 대신, 그 리뷰를 보여 주는 목록과 상세를 같은 순서로 갱신해요.

```text
사용자 입력
  -> 관련 refetch 취소
  -> 목록과 상세 cache snapshot 저장
  -> 목록과 상세 cache 즉시 변경
  -> 요청 실패 시 snapshot 직접 복구
  -> 성공/실패 후 서버 데이터 재검증
```
