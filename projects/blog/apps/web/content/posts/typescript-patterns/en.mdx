Gathering field names in an enum does not guarantee the values attached to them. A caller can still pass a string as a `price` or combine incompatible props. I use `satisfies`, generics, and unions to catch those combinations where they are passed. With optional properties, I also look at which keys an object may omit, rather than only the type returned when reading them.

Each entry opens with a reduced example of the code without the pattern and what the type checker misses there.

## satisfies with as const

Some objects fill in a value for each of a fixed set of names, such as routes or labels. Annotating the variable widens the values to `string`, and `as const` alone checks nothing about the shape.

```typescript
type RouteName = 'home' | 'profile' | 'settings';

// Annotating the variable widens the values to string.
const TYPED_ROUTES: Record<RouteName, string> = {
  home: '/',
  profile: '/profile',
  settings: '/settings',
};

TYPED_ROUTES.profile === '/profil'; // The typo passes

// as const alone keeps the values but does not check the shape.
const CONST_ROUTES = {
  home: '/',
  profile: 'profile', // The missing slash passes
  // Leaving out settings passes too
} as const;
```

Use both together to check that required names are present while keeping each value as a concrete string. `as const` keeps a value as a literal type such as `'/profile'` rather than `string`. `satisfies` checks a value against a type without changing the value's own type. Below, `as const` keeps the literals, and `satisfies` checks the required keys and path format. `` `/${string}` `` is a type meaning a string that starts with a slash.

```typescript
type RouteName = 'home' | 'profile' | 'settings';

const ROUTES = {
  home: '/',
  profile: '/profile',
  settings: '/settings',
} as const satisfies Record<RouteName, `/${string}`>;

ROUTES.profile;
// Inferred as '/profile'.
```

Annotating the variable as `Record<RouteName, string>` can make `ROUTES.profile` read as the broader `string`. The combination keeps `'/profile'` while catching missing keys and invalid paths, and a typo such as `ROUTES.profile === '/profil'` becomes a compile error.

The same approach applies to objects that must be filled exhaustively, such as payment-method labels.

```typescript
const LABELS = {
  normal: 'Standard payment',
  coupon: 'Coupon payment',
  // A missing cancel entry causes a compile error
} as const satisfies Record<'normal' | 'coupon' | 'cancel', string>;
```

Asserting the same object with `as Record<'normal' | 'coupon' | 'cancel', string>` would let a missing `cancel` pass.

## A property set to undefined and a missing key

A new field added with `?` can be left out wherever objects are built, and the type checker will not say anything.

```typescript
interface CouponRequest {
  discountRate?: number;
}

// The type cannot say whether the rate was forgotten or left out on purpose.
function toCouponRequest(): CouponRequest {
  return {};
}
```

With `number | undefined` as the value type, the key must always exist, so the code above stops compiling, and a missing value has to be written out as `undefined`. Here are the two declarations side by side.

```typescript
interface Example {
  requiredKey: number | undefined;
  optionalKey?: number;
}

const a: Example = {
  requiredKey: undefined,
};
```

Both properties can read as `number | undefined`, but constructing the object carries different requirements.

- `requiredKey` must exist, and its value may be `undefined`.
- `optionalKey` may be omitted entirely.

`exactOptionalPropertyTypes` makes the distinction explicit. `optionalKey?: number` allows the key to be absent, which is different from allowing its value to be written as `undefined`. Assigning `undefined` requires adding it to the value type as well.

JSON introduces another distinction: `JSON.stringify` omits object properties whose values are `undefined`. Keeping a key in a JavaScript object does not mean it will appear in the request body. `JSON.stringify({ discountRate: undefined })` produces `{}`, while a `null` value keeps the key in the JSON.

## Connecting a value and its callback with a generic

If a select component declares each prop as `string`, a value that does not exist still passes, and the callback has no idea which values are possible.

```tsx
interface StringSelectProps {
  value: string;
  onValueChange: (value: string) => void;
}

<StringSelect
  value="points" // Passes even though no such payment method exists
  onValueChange={(method) => {
    // method is a string, so passing it on needs another assertion.
    pay(method as PaymentMethod);
  }}
/>;
```

A generic takes a type as a parameter. Using one `T` for both props creates the relationship that the two types must match.

```tsx
interface SelectProps<T extends string> {
  value: T;
  onValueChange: (value: T) => void;
}

function Select<T extends string>({ value, onValueChange }: SelectProps<T>) {
  return <button onClick={() => onValueChange(value)}>{value}</button>;
}
```

This `Select` passes its `value` to the callback. Supplying `PaymentMethod` at the call site gives both props the same union and keeps that set of payment methods visible inside the callback.

```tsx
type PaymentMethod = 'normal' | 'coupon';

<Select<PaymentMethod>
  value="coupon"
  onValueChange={(method) => {
    // method: 'normal' | 'coupon'
  }}
/>;
```

Here `'points'` as the `value` is a compile error, and `method` can go to a payment function without an assertion. If `value` is a variable of type `PaymentMethod`, `T` is inferred as that union without a type argument. Passing a literal directly, as in `value="coupon"`, narrows `T` to `'coupon'` alone, which is when you write the type argument as above.

A single generic expresses that relationship instead of declaring each prop independently as `string`.

## Mutually exclusive props with a never union

Use this when one component supports a value with a change callback, or just a `label`. Making every property optional would also permit a `label` and `value` together.

```tsx
type LooseProps<T extends string> = {
  value?: T;
  onValueChange?: (value: T) => void;
  label?: string;
};

<LooseField label="Invalid combination" value="active" />; // Passes
<LooseField value="active" />; // Passes without a callback
```

The implementation also has to recheck that `value` and `onValueChange` exist every time. Splitting the props into a plain union is still not enough: with the shape `{ value, onValueChange } | { label }`, passing `label` and `value` together passes as well. TypeScript does not treat a property as excess if any member of the union declares it.

So `never` marks the properties each mode rejects, and the union describes the allowed combinations. No value can be assigned to the `never` type.

```tsx
type ControlledProps<T extends string> = {
  value: T;
  onValueChange: (value: T) => void;
  label?: never;
};

type LabelOnlyProps = {
  label: string;
  value?: never;
  onValueChange?: never;
};

type Props<T extends string> = ControlledProps<T> | LabelOnlyProps;

function Field<T extends string>(props: Props<T>) {
  if ('label' in props) return <span>{props.label}</span>;
  return <button onClick={() => props.onValueChange(props.value)}>{props.value}</button>;
}
```

```tsx
<Field label="Read only" />;                         // Valid
<Field value="active" onValueChange={() => {}} />; // Valid
<Field label="Invalid combination" value="active" />;      // Compile error
```

An invalid combination fails where the component is called. The implementation can inspect the props and then read only the fields available for that mode. In the branch where `'label' in props` is false, `LabelOnlyProps` drops out, so `props.onValueChange` can be called directly.

`in` only checks whether the key exists, though. Passing `label={undefined}` explicitly passes the type check and takes the `<span>` branch. To rule that out as well, turn on the `exactOptionalPropertyTypes` option from earlier.

Function overloads can also separate call styles. For this component, a props union made it easier to see which fields the implementation could use.
