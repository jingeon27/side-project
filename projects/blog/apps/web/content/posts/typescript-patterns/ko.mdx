<Summary>

`satisfies`, optional property, 제네릭, 배타적인 props를 패턴마다 그것 없이 쓴 코드와 나란히 보여 줘요. 타입 검사를 그대로 통과하는 실수를 호출하는 자리에서 잡는 방법들이에요. 항목마다 독립적이라 필요한 것만 찾아 읽어도 돼요.

</Summary>

![타입에 맞는 입력을 호출부에서 구분하는 모습을 그린 일러스트](/images/covers/typescript-patterns.avif)

필드 이름을 enum으로 모아도 값의 타입까지 맞아지지는 않아요. `price`에 문자열을 넣거나 함께 쓰면 안 되는 props를 넘기는 실수는 따로 남아요. 이런 조합을 호출하는 자리에서 드러내려고 `satisfies`와 제네릭, 유니언을 쓰고, optional property는 읽는 값뿐 아니라 객체를 만들 때 생략할 수 있는 키도 함께 봐요.

항목마다 그 패턴 없이 쓴 코드를 줄인 예시로 먼저 두고, 타입 검사가 무엇을 놓치는지 적었어요.

## satisfies와 as const

경로나 문구처럼 정해진 이름마다 값을 채우는 객체가 있어요. 변수에 타입을 붙이면 값이 `string`으로 넓어지고, `as const`만 쓰면 모양을 검사하지 않아요.

```typescript
type RouteName = 'home' | 'profile' | 'settings';

// 변수에 타입을 붙이면 값이 string으로 넓어져요.
const TYPED_ROUTES: Record<RouteName, string> = {
  home: '/',
  profile: '/profile',
  settings: '/settings',
};

TYPED_ROUTES.profile === '/profil'; // 오타가 있어도 통과해요

// as const만 쓰면 값은 유지되지만 모양을 검사하지 않아요.
const CONST_ROUTES = {
  home: '/',
  profile: 'profile', // 슬래시를 빠뜨려도 통과해요
  // settings를 빠뜨려도 통과해요
} as const;
```

필요한 이름이 빠지지 않았는지 검사하면서 각 값을 구체적인 문자열로 쓰고 싶을 때 둘을 함께 써요. `as const`는 값을 `string` 대신 `'/profile'` 같은 리터럴 타입으로 남겨요. `satisfies`는 값의 타입을 바꾸지 않고 지정한 타입에 맞는지만 검사하는 문법이에요. 아래에서 `as const`가 리터럴 타입을 유지하고, `satisfies`가 필수 키와 경로 형식을 검사해요. `` `/${string}` ``은 슬래시로 시작하는 문자열을 뜻하는 타입이에요.

```typescript
type RouteName = 'home' | 'profile' | 'settings';

const ROUTES = {
  home: '/',
  profile: '/profile',
  settings: '/settings',
} as const satisfies Record<RouteName, `/${string}`>;

ROUTES.profile;
// '/profile'로 추론된다.
```

변수 타입을 `Record<RouteName, string>`으로 지정하면 `ROUTES.profile`도 넓은 `string`으로 읽힐 수 있어요. 두 문법을 함께 쓰면 `'/profile'`이라는 값을 유지한 채 빠진 키나 잘못된 경로를 찾을 수 있어요. `ROUTES.profile === '/profil'` 같은 오타도 컴파일 오류가 나요.

결제 수단별 문구처럼 빠짐없이 채워야 하는 객체에도 같은 방식을 적용해요.

```typescript
const LABELS = {
  normal: '일반 결제',
  coupon: '쿠폰 결제',
  // cancel 누락 시 컴파일 오류
} as const satisfies Record<'normal' | 'coupon' | 'cancel', string>;
```

같은 객체를 `as Record<'normal' | 'coupon' | 'cancel', string>`으로 단언하면 `cancel`을 빠뜨려도 통과해요.

## 값이 undefined인 프로퍼티와 키가 없는 프로퍼티

새 필드를 `?`로 추가하면 객체를 만드는 쪽에서 빠뜨려도 타입 검사가 알려 주지 않아요.

```typescript
interface CouponRequest {
  discountRate?: number;
}

// 할인율을 빠뜨렸는지 일부러 뺐는지 타입만으로는 알 수 없어요.
function toCouponRequest(): CouponRequest {
  return {};
}
```

값 타입을 `number | undefined`로 두면 키는 항상 있어야 해서 위 코드는 컴파일 오류가 나요. 아직 값이 없으면 `undefined`를 직접 적어야 하고요. 두 선언을 나란히 놓으면 이래요.

```typescript
interface Example {
  requiredKey: number | undefined;
  optionalKey?: number;
}

const a: Example = {
  requiredKey: undefined,
};
```

두 프로퍼티 모두 읽으면 `number | undefined`가 될 수 있어요. 객체를 만들 때의 조건은 달라요.

- `requiredKey`는 키가 있어야 하고, 값으로 `undefined`를 허용해요.
- `optionalKey`는 키 자체를 생략할 수 있어요.

이 차이는 `exactOptionalPropertyTypes`를 켰을 때 더 분명해져요. `optionalKey?: number`는 키를 빼도 된다는 뜻이고, 값을 `undefined`로 적어도 된다는 뜻은 아니에요. 직접 대입하려면 값 타입에도 `undefined`를 넣어야 해요.

요청 본문으로 보낼 때는 한 번 더 구분해요. `JSON.stringify`는 값이 `undefined`인 프로퍼티를 생략해요. 자바스크립트 객체에 키를 남겼더라도 JSON에 그대로 실리는 것은 아니에요. `JSON.stringify({ discountRate: undefined })`의 결과는 `{}`이고, 값이 `null`이면 키가 JSON에 남아요.

## 제네릭으로 value와 callback의 타입 연결

선택 컴포넌트의 prop을 각각 `string`으로 열어 두면, 없는 값을 넘겨도 통과하고 콜백 안에서는 어떤 값인지 알 수 없어요.

```tsx
interface StringSelectProps {
  value: string;
  onValueChange: (value: string) => void;
}

<StringSelect
  value="points" // 없는 결제 수단이어도 통과해요
  onValueChange={(method) => {
    // method는 string이라 결제 함수에 넘기려면 다시 단언해요.
    pay(method as PaymentMethod);
  }}
/>;
```

제네릭은 타입을 매개변수로 받는 문법이에요. `T` 하나를 두 prop에 함께 쓰면 두 타입이 같아야 한다는 관계가 생겨요.

```tsx
interface SelectProps<T extends string> {
  value: T;
  onValueChange: (value: T) => void;
}

function Select<T extends string>({ value, onValueChange }: SelectProps<T>) {
  return <button onClick={() => onValueChange(value)}>{value}</button>;
}
```

이 `Select`는 `value`로 받은 값을 콜백에도 그대로 넘겨요. 호출부에서 `PaymentMethod`를 지정하면 두 prop이 같은 유니언을 사용하고, 콜백 안에서도 결제 수단의 범위를 알 수 있어요.

```tsx
type PaymentMethod = 'normal' | 'coupon';

<Select<PaymentMethod>
  value="coupon"
  onValueChange={(method) => {
    // method: 'normal' | 'coupon'
  }}
/>;
```

여기서 `value`에 `'points'`를 넣으면 컴파일 오류가 나고, `method`는 단언 없이 결제 함수에 넘길 수 있어요. `value`가 `PaymentMethod` 타입의 변수라면 타입 인자를 적지 않아도 `T`가 그 유니언으로 추론돼요. `value="coupon"`처럼 리터럴을 바로 넘길 때는 `T`가 `'coupon'` 하나로 좁혀지므로 위처럼 타입 인자를 적어요.

두 prop을 각각 `string`으로 열어 두는 대신, 같은 타입을 써야 한다는 관계를 제네릭으로 표현해요.

## never 유니언으로 배타적인 props 표현

값과 변경 콜백을 받는 방식, `label`만 보여 주는 방식을 한 컴포넌트에서 지원할 때 써요. 아무 속성이나 선택적으로 받으면 `label`과 `value`가 동시에 들어올 수 있어요.

```tsx
type LooseProps<T extends string> = {
  value?: T;
  onValueChange?: (value: T) => void;
  label?: string;
};

<LooseField label="잘못된 조합" value="active" />; // 통과해요
<LooseField value="active" />; // 콜백이 없어도 통과해요
```

구현부도 `value`와 `onValueChange`가 있는지 매번 다시 확인해야 해요. 유니언으로 나누기만 해서는 부족해요. `{ value, onValueChange } | { label }` 모양에서도 `label`과 `value`를 함께 넘기면 통과해요. TypeScript는 유니언의 어느 한쪽에라도 있는 속성이면 남는 속성으로 보지 않기 때문이에요.

그래서 각 방식에서 받지 않을 속성을 `never`로 적어 허용할 조합을 나눠요. `never` 타입에는 어떤 값도 넣을 수 없어요.

```tsx
type ControlledProps<T extends string> = {
  value: T;
  onValueChange: (value: T) => void;
  label?: never;
};

type LabelOnlyProps = {
  label: string;
  value?: never;
  onValueChange?: never;
};

type Props<T extends string> = ControlledProps<T> | LabelOnlyProps;

function Field<T extends string>(props: Props<T>) {
  if ('label' in props) return <span>{props.label}</span>;
  return <button onClick={() => props.onValueChange(props.value)}>{props.value}</button>;
}
```

```tsx
<Field label="읽기 전용" />;                         // 가능
<Field value="active" onValueChange={() => {}} />; // 가능
<Field label="잘못된 조합" value="active" />;      // 컴파일 오류
```

호출부에 잘못된 조합을 넘기면 바로 타입 오류가 나요. 구현부도 props를 확인한 뒤 그 방식에 맞는 속성만 읽을 수 있어요. `'label' in props`가 거짓인 분기에서는 `LabelOnlyProps`가 빠지므로 `props.onValueChange`를 바로 호출해도 돼요.

다만 `in`은 키가 있는지만 봐요. `label={undefined}`를 명시해 넘기면 타입 검사를 통과하고 `<span>` 쪽으로 가요. 이 경우까지 막으려면 앞에서 본 `exactOptionalPropertyTypes`를 켜요.

함수 오버로드로 호출 방식을 나눌 수도 있어요. 이 컴포넌트에서는 props 유니언을 쓰면 구현부에서도 어떤 속성을 사용할 수 있는지 확인하기 편했어요.
