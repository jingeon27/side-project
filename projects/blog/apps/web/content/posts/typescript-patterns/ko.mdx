필드 이름이 맞아도 값 타입이 틀리거나, 함께 쓸 수 없는 props가 동시에 들어오는 코드를 종종 본다. 이런 조합을 타입 검사에서 걸러내려고 실무에서 반복해서 쓴 패턴 네 가지를 모았다.

## satisfies로 검사하면서 추론을 유지하기

satisfies는 값의 타입을 새로 만들어주는 문법이 아니다. **값이 지정한 타입을 만족하는지 검사하면서, 값 자체의 구체적인 추론을 유지한다.**

```typescript
type RouteName = 'home' | 'profile' | 'settings';

const ROUTES = {
  home: '/',
  profile: '/profile',
  settings: '/settings',
} as const satisfies Record<RouteName, `/${string}`>;

ROUTES.profile;
// '/profile'로 추론된다.
```

Record&lt;RouteName, string>으로 변수 타입을 직접 지정하면 값이 string으로 넓어질 수 있다. satisfies를 사용하면 key 누락과 잘못된 value를 검사하면서 literal 정보를 보존할 수 있다.

```typescript
const LABELS = {
  normal: '일반 결제',
  coupon: '쿠폰 결제',
  // cancel 누락 시 컴파일 오류
} as const satisfies Record<'normal' | 'coupon' | 'cancel', string>;
```

## T | undefined와 optional property는 다르다

```typescript
interface Example {
  requiredKey: number | undefined;
  optionalKey?: number;
}

const a: Example = {
  requiredKey: undefined,
};
```

두 값 모두 읽을 때는 number | undefined가 될 수 있지만 객체를 만들 때 의미가 다르다.

- requiredKey는 key가 반드시 있어야 하며 값으로 undefined를 허용한다.
- optionalKey는 key 자체를 생략할 수 있다.

exactOptionalPropertyTypes를 켜면 이 차이가 더 엄격해진다. optionalKey?: number에 undefined를 직접 대입하려면 number | undefined를 명시해야 한다.

## 제네릭으로 value와 callback의 타입을 연결하기

```tsx
interface SelectProps<T extends string> {
  value: T;
  onValueChange: (value: T) => void;
}

function Select<T extends string>({ value, onValueChange }: SelectProps<T>) {
  return <button onClick={() => onValueChange(value)}>{value}</button>;
}
```

사용하는 쪽에서 value가 구체적인 union이면 callback 인자도 같은 union으로 추론된다.

```tsx
type PaymentMethod = 'normal' | 'coupon';

<Select<PaymentMethod>
  value="coupon"
  onValueChange={(method) => {
    // method: 'normal' | 'coupon'
  }}
/>;
```

두 prop이 같은 타입이라는 관계를 각자 string으로 선언하지 않고 제네릭 하나로 표현한 것이다.

## 서로 배타적인 props를 union으로 표현하기

컴포넌트가 두 사용 방식 중 정확히 하나만 허용해야 한다면 never를 이용한 union이 명확하다.

```tsx
type ControlledProps<T extends string> = {
  value: T;
  onValueChange: (value: T) => void;
  label?: never;
};

type LabelOnlyProps = {
  label: string;
  value?: never;
  onValueChange?: never;
};

type Props<T extends string> = ControlledProps<T> | LabelOnlyProps;

function Field<T extends string>(props: Props<T>) {
  if ('label' in props) return <span>{props.label}</span>;
  return <button onClick={() => props.onValueChange(props.value)}>{props.value}</button>;
}
```

```tsx
<Field label="읽기 전용" />;                         // 가능
<Field value="active" onValueChange={() => {}} />; // 가능
<Field label="잘못된 조합" value="active" />;      // 컴파일 오류
```

함수 overload는 호출 시그니처를 설명할 때 유용하지만, React props의 가능한 상태를 모델링할 때는 discriminated union이나 never 기반 XOR가 구현부까지 안전하게 좁혀진다.

값의 구체적인 타입을 유지할 때는 satisfies를, prop 사이의 관계를 표현할 때는 제네릭이나 union을 사용한다. optional property를 정할 때는 값이 undefined일 수 있는지와 key를 생략할 수 있는지를 따로 확인한다.

참고: [TypeScript 4.9 satisfies](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html), [exactOptionalPropertyTypes](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html)
