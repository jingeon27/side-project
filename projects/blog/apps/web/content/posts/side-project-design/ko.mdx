<Summary>

사진 서비스에서 시작해 게임 피드백과 블로그까지 추가했어요. 여러 서비스를 만드는 동안 공통으로 둘 코드와 각 서비스의 범위를 어떻게 정했는지 돌아봤어요.

</Summary>

AI에 구현을 맡기면서 프런트엔드 밖의 작업도 직접 다뤄 보고 싶어졌어요. 백엔드와 데이터베이스, 디자인을 서비스에 필요한 수준까지 검토하고 구현하며 여러 아이디어를 만들어 보기로 했어요.

그래서 관심이 가는 아이디어들을 꺼내 놓고, 여러 서비스를 함께 기획하고 출시해 보기로 했어요. [사진 서비스](https://github.com/jingeon27/side-project/tree/develop/projects/photo-contest), [게임 피드백 서비스](https://github.com/jingeon27/side-project/tree/f0e64fcc40baf01ca50cc2add07416cf5203e5f9/projects/game-feedback), [개인 블로그](https://github.com/jingeon27/side-project/tree/develop/projects/blog)도 그렇게 진행하게 됐어요.

여러 서비스를 함께 작업하려면 새 프로젝트를 시작할 때마다 개발 환경을 다시 만드는 수고도 줄이고 싶었어요. [side-project 저장소](https://github.com/jingeon27/side-project) 안에서 서비스별로 나눠 관리하도록 모노레포를 구성했고, 처음에는 TypeScript 설정을 공유했어요. 이후 코딩 규칙과 디자인 시스템도 함께 관리하면서, 공통으로 쓸 부분과 각 서비스에 둘 부분을 정리해 갔어요.

## 처음에는 비공개 사진 대회였어요

처음 만들기 시작한 건 `photo-contest`였어요. 그룹을 만들고 친구를 초대해서 사진을 올린 뒤 투표하는 형태로 잡았어요. 제출 기간과 투표 기간을 나누고, 공동 우승이나 득표가 없는 경우도 처리했어요.

여러 서비스를 같은 저장소에서 만들더라도 테스트는 각 앱에서 관리하고 싶었어요. Vitest와 Playwright 설정을 앱 안에 두고, 해당 앱에서 필요한 테스트를 따로 실행할 수 있게 했어요.

루트에서는 Yarn workspace와 공통 설정을 관리하고, 프로젝트별 명령을 위임하게 했어요. 서비스는 `projects/<이름>` 안에 두고, 공용 설정은 `packages`로 나눴어요. 처음 공용 패키지는 TypeScript 설정이었어요.

```text
projects/
  photo-contest/
    apps/
      api/
      web/
packages/
  typescript-config/
```

여기서 시작해서 모바일 앱과 다른 서비스를 하나씩 추가했어요. API, 웹, 모바일 앱은 각각 자신의 테스트 설정과 실행 명령을 갖게 했어요.

## 홈 화면에서 바로 사진을 볼 수 있게 했어요

처음 실행한 홈은 그룹을 고르는 화면에 가까웠어요. 제가 원한 건 가입한 그룹의 사진을 최신순으로 모아 보는 화면이었어요. 그룹 목록은 마이페이지에서 확인하고, 홈에 들어오면 바로 사진이 보여야 했어요.

그다음에는 기간이 끝나면 닫히는 이벤트보다 계속 글을 올릴 수 있는 공간이 더 맞겠다고 생각했어요. 사진뿐 아니라 동영상과 합성 이미지도 올리고, 관리자가 게시물을 지우거나 이달의 인기 게시물을 볼 수 있게 범위를 바꿨어요. 기존 대회 중심 모델에 상시 게시물 모델을 추가한 이유예요.

디자인도 실행한 화면을 보면서 고쳤어요. 사진이 가려지는 배치를 바꾸고, 스토리 기능이 없는데 붙어 있던 테두리도 없앴어요. 데스크톱에서의 여백과 배치도 따로 확인했어요. 다른 서비스의 분위기를 참고하더라도 사진을 보는 흐름과 실제 기능에 맞는 화면이어야 했어요.

## 여러 프로젝트에서 쓸 코딩 규칙을 정리했어요

기능을 늘리면서 구현 방식도 정리했어요. 파일 업로드는 mutation으로 처리해 요청 상태와 실패 처리를 함께 관리했어요. 한 번만 쓰는 이벤트 핸들러는 사용하는 곳에서 읽을 수 있게 두고, 사진과 동영상을 고르는 UI처럼 맥락이 다른 부분은 컴포넌트로 나눴어요.

여러 프로젝트에 같은 기준을 적용할 수 있도록 [커스텀 ESLint 규칙](https://github.com/jingeon27/side-project/tree/develop/packages/config/eslint)을 공통 패키지로 옮겼어요. 규칙은 TypeScript로 작성하고 RuleTester와 fixture로 확인했어요. 규칙 파일과 프레임워크별 preset을 나눠 각 앱에서 필요한 설정을 조합하게 했어요.

게임 피드백을 추가하면서는 사진 서비스와 공통으로 사용할 [디자인 시스템](https://github.com/jingeon27/side-project/tree/f0e64fcc40baf01ca50cc2add07416cf5203e5f9/packages/design-system)도 작업했어요. 버튼과 입력, 모달 같은 UI는 함께 관리하고, 게임 정보나 피드 구성처럼 서비스에 속한 것은 각 앱에 남겼어요. 새 프로젝트를 붙이면서 공유할 이유가 생긴 부분부터 공통 패키지가 늘어났어요.

## develop과 기능 브랜치를 구분했어요

게임 피드백을 시작하면서 `main`을 기준으로 [develop](https://github.com/jingeon27/side-project/tree/develop)을 만들고, `feat/game-feedback`은 별도의 기능 브랜치로 뒀어요. 사진 서비스의 후속 작업도 PR의 기준 브랜치를 `develop`으로 맞췄어요.

사진 서비스를 수정하면서 게임 서비스와 블로그도 함께 작업했어요. 기능별 브랜치에서 구현하고 검증한 뒤 `develop`을 대상으로 PR을 만들었어요. 사진 피드와 로그인, 공통 린트 정리, 블로그 이관도 이 브랜치를 기준으로 합쳤어요.

블로그와 게임 서비스는 서로 다른 세션에서 진행하려고 worktree도 나눴어요. 각각의 작업 폴더에서 기능 브랜치를 유지하면서 작업할 수 있게 했어요.

## 첫 게임은 클래시로얄로 정했어요

B2C나 C2C 서비스를 해 보고 싶었어요. 제가 접근할 수 있는 커뮤니티에서 사용자를 모으고, 그 사람들이 서비스를 계속 쓰는지 확인하는 경험을 하고 싶었어요.

게임 피드백은 플레이하다 막힌 사람이 자신의 상황을 올리고, 다른 사람이 조언해 주는 서비스로 생각했어요. 클래시로얄은 초기 사용자를 찾아가기 수월할 것 같아서 먼저 골랐어요. 브롤스타즈나 롤로 넓힐 생각은 남겨 두되, 첫 게임부터 여러 개를 동시에 다루지는 않기로 했어요.

사진 평가와 게임 피드백은 각각 따로 운영하는 서비스로 봤어요. 둘 다 사람의 의견을 주고받는다는 공통점은 있지만, 이용하는 이유와 필요한 정보가 달라요. 같은 브랜드 아래에서 만들더라도 사용자 계정과 데이터를 당연히 합칠 이유는 없었어요.

게임 피드백에는 친추판매나 친선전 모집, 채팅 같은 기능도 붙이고 싶었어요. 게임과 게시판의 관계는 구분해서 클래시로얄 아래에 게시판을 두기로 했어요. 이후 게임코치와 자유게시판도 추가하고, 게임이 늘어도 같은 다섯 분류를 쓰는 구조로 정리했어요. 계정 거래는 위험 부담이 커서 빼기로 했어요.

친추판매에는 금액을 입력하고, 코칭에는 시간당 수강료와 월 수강료, 목표 점수까지의 총수강료를 구분하도록 했어요. 수강생이 코치를 구할 수도 있고 코치가 수강생을 모집할 수도 있어요. 금액과 모집 조건을 적고 채팅으로 연결하되, 플랫폼 안에서 결제를 처리하는 기능은 초기 범위에서 제외했어요.

## 피드백을 요청할 사람과 답변할 사람이 모두 필요했어요

게임 피드백에는 질문을 올릴 사람과 답변해 줄 사람이 모두 필요했어요. 인증과 게임 프로필 연동, 다국어, 캐시를 구현하면서도 첫 질문에 누가 답변해 줄지 함께 생각해야 했어요.

피드백을 원하는 사람이 글을 올렸는데 답변이 없으면 다시 들어올 이유도 줄어들어요. 질문을 등록한 사람이 답변을 받고 돌아와서 확인하는 데까지 이어져야 했어요.

그래서 먼저 확인할 흐름을 다음처럼 잡았어요.

```text
고민을 올린다
  → 다른 사람이 답변한다
  → 요청자에게 답변을 알린다
  → 요청자가 읽고 도움 여부를 표시한다
```

답변 알림과 `도움됨` 표시도 이때 중요해졌어요. 글과 답변을 저장하는 것까지는 생각했지만, 요청자가 답변이 달린 사실을 알고 실제로 확인하는 과정이 빠져 있었어요. 도움이 된 답변인지 확인할 수단이 있어야 처음 세운 가설도 살펴볼 수 있었어요.

지표는 도움됨으로 표시한 답변이 하나 이상 있는 요청 수를 우선 보기로 했어요. 같은 요청에 유용한 답변이 여러 개 달려도 요청 한 건으로 세어요. 첫 답변이 달리기까지 걸린 시간과 24시간 안에 답변을 받은 비율도 함께 보려고 해요.

먼저 답변해 줄 사람 5~10명을 찾아보고, 기존 커뮤니티에서 요청과 답변을 수동으로 연결해 볼 계획이에요. 아직 모집을 진행하지는 못했어요.

## REST로 캐시 모델을 직접 설계해 보고 싶었어요

사진 서비스에서는 GraphQL과 Apollo Client를 사용했고, 게임 피드백에서는 REST와 TanStack Query를 선택했어요. 게임 피드백의 목록과 상세 캐시를 나누고, 데이터를 수정한 뒤 어떤 조회를 갱신할지 직접 설계해 보고 싶었어요. REST로 그 관계를 정리하는 쪽이 제게 익숙했고, 이번 프로젝트에서 해 보고 싶은 작업과도 맞았어요.

브라우저의 서버 상태는 TanStack Query로 관리하기로 했어요. 피드 목록은 커서 기반 무한 스크롤로 조회하고, 글이나 답변을 작성하면 관련 조회를 갱신하는 방식이에요. 서버는 NestJS에 Express를 쓰기로 했어요.

Next.js 서버 캐시도 계획에 넣고 싶었어요. NestJS에서 데이터가 바뀌면 Next.js의 Route Handler를 호출해 관련 캐시를 무효화하는 흐름을 생각했어요. 이 부분을 검토하면서 캐시를 어디에 저장할지보다 변경 직후 화면이 무엇을 보여 줄지가 더 까다로웠어요.

답변을 등록한 사람이 예전 목록을 다시 받으면 등록에 실패했다고 생각할 수 있어요. 브라우저의 TanStack Query 캐시를 갱신해도 Next.js 서버 쪽에 오래된 결과가 남아 있다면 다시 조회한 화면이 예상과 달라져요. 다른 사람이 답변을 추가했을 때의 갱신도 따로 생각해야 해요.

서버 캐시를 설계하는 경험도 가져가고 싶어서 후속 개발 단계에 남겼어요. 우선 사용자 작성 콘텐츠에는 Next.js 데이터 캐시를 적용하지 않고, TanStack Query의 갱신과 재조회로 처리했어요. 서버 캐시를 추가할 때는 브라우저에 남은 값과 서버에서 다시 받는 값이 어떻게 갱신되는지 함께 확인하려고 해요.

지금 확인해야 할 동작은 구체적이에요. 작성 직후 본인의 글이 보여야 하고, 수정한 내용이 다시 예전 값으로 돌아오지 않아야 해요. 서버 캐시를 추가할 때도 이 동작을 기준으로 검증하려고 해요.

## 게임 프로필 조회와 계정 소유 확인을 나눴어요

게임 계정을 연결하는 화면은 Player Tag를 입력하고 프로필을 불러오는 흐름으로 잡았어요. 그런데 프로필을 불러오는 데 성공했다는 사실만으로 입력한 사람이 그 계정의 주인이라고 볼 수는 없었어요. 다른 사람의 태그를 넣을 수도 있기 때문이에요.

이 차이는 인증 표시를 설계할 때 중요했어요. 게임 데이터를 조회한 상태와 계정 소유권을 확인한 상태를 같은 의미로 보여 주면, 화면이 실제로 확인한 것보다 더 많은 신뢰를 주게 돼요.

연결한 게임 프로필은 우선 소유권 미확인 상태로 두고, 별도의 확인 절차를 검토하기로 했어요. 운영자가 확인하는 사용자 인증 표시도 게임 계정의 소유권 상태와 구분했어요. 어떤 자료를 보고 무엇을 확인했는지가 분명해져야 표시의 의미도 정할 수 있었어요.

초기에는 요청 시점의 덱과 게임 정보를 스냅샷으로 남기는 계획도 세웠어요. 작업하면서 게임 프로필은 사용자 계정에 등록하는 형태로 정리했고, 글쓰기 화면의 덱 첨부는 빼기로 했어요. 프로필 인증 요청은 사용자가 관리자와 1:1 채팅을 시작하는 흐름으로 잡았어요. 어떤 정보를 연결하고 무엇을 확인했다고 보여 줄지도 화면을 보며 계속 조정했어요.

## 다국어 메뉴와 서로 대화할 수 있는 서비스는 차이가 있었어요

게임 서비스는 처음부터 한국어, 영어, 일본어를 생각했어요. 언어별 경로와 UI 문구를 준비하고 게시글 번역도 제공하면 될 것 같았어요.

그런데 게시글만 번역하면 흐름이 중간에 끊겼어요. 한국어 질문을 일본어 사용자가 읽고 답변하더라도, 질문한 사람이 일본어 답변을 읽지 못할 수 있어요. 피드백을 주고받는 과정까지 생각하면 번역 범위에 답변도 들어가야 했어요.

언어별 라우팅은 초기에 잡되, 번역 기능과 각 언어권 운영은 따로 검증할 항목으로 남겼어요. `/en`이나 `/ja` 경로가 존재하는 것만으로 그 언어의 사용자가 서비스를 이용할 준비가 끝났다고 볼 수는 없었어요.

모바일은 WebView로 웹 화면을 함께 사용하는 형태로 만들었어요. 우선 웹에서 요청하고 답변을 확인하는 흐름을 다듬고, 앱 배포와 스토어 운영은 이후에 진행하려고 해요.

## 블로그는 DB 없이 운영하기로 했어요

블로그는 게임 서비스와 필요한 데이터의 성격이 달랐어요. 게임 서비스에는 여러 사용자가 계속 만드는 글과 답변이 있지만, 블로그의 작성자는 저 한 명이에요.

기존에는 저장소에 글을 두고 티스토리에도 올려 관리했어요. 이 과정이 번거로워서 개인 블로그를 만들기로 했어요. 글을 바꿀 때마다 다시 배포해야 한다는 점 때문에 DB와 관리자 에디터도 잠깐 고민했어요.

결국 Git과 MDX를 선택했어요. 익숙한 편집기에서 글을 고치고, 변경 내역을 남기면서 발행하고 싶었어요. Git에 push한 변경이 자동으로 배포되도록 운영하면 글을 고칠 때마다 직접 배포 명령을 실행하는 수고도 줄일 수 있겠다고 생각했어요.

한국어와 영어 본문은 각각의 MDX로 관리하고, 두 파일은 같은 콘텐츠 ID로 묶었어요. 제목과 slug, 검색 설명은 언어별 SEO JSON에 두고, 발행일과 태그 같은 공통 정보는 메타데이터로 분리했어요.

```text
content/posts/side-project-design/
  meta.json
  ko.mdx
  en.mdx

seo/
  ko.json
  en.json
```

번역을 쓰지 않은 글에 영문 주소만 만드는 일은 피하고 싶었어요. 실제 본문이 있는 언어만 목록과 사이트맵에 나오게 했어요. 제목을 고쳐도 주소는 유지하고, 주소를 바꿀 때는 리다이렉트를 명시하는 기준도 뒀어요.

소개 화면에는 연락처 정도만 남겼어요. 이력서와 프로젝트 소개까지 넣으면 글을 읽는 공간에서 제가 보여 주고 싶은 것이 다시 늘어날 것 같았어요. 블로그에서는 글을 쓰고 읽는 흐름에 집중하기로 했어요.

## 같은 저장소에서 서로의 데이터를 건드리지 않게 했어요

게임 서비스와 블로그를 서로 다른 세션에서 작업하려고 했어요. 기존 사진 서비스도 같은 저장소에 있어서, Git worktree로 작업 폴더와 브랜치를 나눴어요.

여기서 소스 폴더만 나누면 끝날 줄 알기 쉬웠어요. 실제로는 실행 포트, API 주소, 쿠키 이름, DB와 테스트 스키마도 각 프로젝트에 맞춰 정해야 했어요. 같은 PC에서 서버를 띄웠는데 다른 프로젝트의 API로 요청을 보내면, 폴더를 나눈 의미가 없어져요.

그래서 프로젝트마다 데이터와 실행 환경을 분리하는 기준을 문서에 넣었어요. 테스트는 사용 중인 개발 서버 대신 별도 포트와 임시 DB 스키마를 사용해요. 공통으로 관리할 이유가 확인된 설정이나 UI만 상위 패키지로 올리고, 서비스 데이터와 업무 로직은 각 프로젝트에 남겼어요.

지금은 기능을 만들고 직접 화면을 보면서 다듬는 중이에요. 다음에는 실제로 질문을 올릴 사람과 답변해 줄 사람을 찾아보려고 해요. 질문을 올린 사람이 답변을 받고 다시 들어와서 읽는지부터 확인해 보고 싶어요.
