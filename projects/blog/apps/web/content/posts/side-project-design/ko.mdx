사이드 프로젝트를 하면서 이번에는 직접 만든 서비스에 사람을 모으고, 그 사람들이 다시 돌아오는지까지 확인해 보고 싶었다. 프런트엔드에서 화면을 만드는 일에는 익숙하지만, 서버와 DB를 붙이고 운영하면서 제품 전체를 책임지는 경험도 하고 싶었다. 잘되면 계속 운영할 수 있는 부업으로 키워 보고 싶은 마음도 있었다.

처음부터 아이디어가 하나로 정해져 있지는 않았다. 사람을 연결하는 서비스를 생각하다가 게임 피드백으로 좁혀졌고, 별도로 사진을 평가하는 서비스도 만들기로 했다. 여기에 개인 블로그까지 같은 저장소에서 진행하게 됐다.

계획을 작성하는 동안 가장 많이 한 일은 기능을 추가하고 다시 빼는 일이었다. 기술 스택을 고르는 것보다, 무엇부터 확인할지 정하는 데 시간이 더 걸렸다.

## 첫 게임은 클래시로얄로 정했다

처음에는 B2C나 C2C 쪽이 나에게 더 맞겠다고 생각했다. 기업 고객을 찾아 영업하는 방식보다, 내가 접근할 수 있는 커뮤니티에서 사용자를 모아 보는 쪽을 해 보고 싶었다. 그렇다고 소비자 대상 서비스의 사용자 모집이 쉽다고 확인한 것은 아니다. 내가 시작하기 편한 쪽을 고른 것이다.

게임 피드백은 플레이하다 막힌 사람이 자신의 상황을 올리고, 다른 사람이 조언해 주는 서비스로 생각했다. 클래시로얄을 먼저 고른 이유도 초기 사용자를 찾아가기 수월할 것 같아서였다. 브롤스타즈나 롤로 넓힐 생각은 남겨 두되, 첫 게임부터 여러 개를 동시에 다루지는 않기로 했다.

사진 평가와 게임 피드백은 각각 따로 운영하는 서비스로 봤다. 둘 다 사람의 의견을 주고받는다는 공통점은 있지만, 이용하는 이유와 필요한 정보가 다르다. 같은 브랜드 아래에서 만들더라도 사용자 계정과 데이터를 당연히 합칠 이유는 없었다.

게임 피드백에는 친추판매나 친선전 모집, 채팅 같은 기능도 붙이고 싶었다. 다만 게임과 게시판의 관계는 구분해야 했다. 클래시로얄 아래에 피드백과 다른 게시판이 있는 구조로 잡았고, 계정 거래는 위험 부담이 커서 빼기로 했다. 플랫폼 안에서 결제를 처리하는 기능도 초기 범위에서 제외했다.

## 첫 답변이 달리는 시점이 계획의 맨 뒤에 있었다

초기 계획에는 인증, 게임 프로필 연동, 다국어, 캐시, 모바일 앱 같은 항목이 자세히 들어갔다. 정작 실제 사용자를 만나고 답변자를 모으는 일은 뒤쪽 단계에 있었다.

계획을 검토하면서 이 순서가 문제라는 지적을 받았다. 피드백을 원하는 사람이 글을 올려도 답변할 사람이 없으면 서비스가 이어지지 않는다. 서버 구조를 잘 나누고 앱까지 만들어도 첫 질문이 방치되는 문제는 그대로 남는다.

그래서 먼저 확인할 흐름을 다음처럼 잡았다.

```text
고민을 올린다
  → 다른 사람이 답변한다
  → 요청자에게 답변을 알린다
  → 요청자가 읽고 도움 여부를 표시한다
```

답변 알림과 `도움됨` 표시도 이때 중요해졌다. 글과 답변을 저장하는 것까지는 생각했지만, 요청자가 답변이 달린 사실을 알고 실제로 확인하는 과정이 빠져 있었다. 도움이 된 답변인지 확인할 수단이 있어야 처음 세운 가설도 살펴볼 수 있었다.

지표는 도움됨으로 표시한 답변이 하나 이상 있는 요청 수를 우선 보기로 했다. 같은 요청에 유용한 답변이 여러 개 달려도 요청 한 건으로 센다. 첫 답변이 달리기까지 걸린 시간과 24시간 안에 답변을 받은 비율도 함께 보려고 한다.

답변자 5~10명을 먼저 찾아보고, 기존 커뮤니티에서 수동으로 요청과 답변을 연결해 보자는 항목도 계획 앞에 뒀다. 아직 모집해서 검증한 결과는 없다. 지금 문서에 적혀 있는 숫자는 앞으로 확인할 목표다.

## REST를 고른 이유는 캐시 모델을 직접 잡아 보고 싶어서였다

API는 REST로 정했다. 목록과 상세의 캐시 범위를 나누고, 데이터를 수정한 뒤 어떤 조회를 갱신할지 직접 설계해 보고 싶었다. REST로 그 관계를 정리하는 쪽이 내게 익숙했고, 이번 프로젝트에서 해 보고 싶은 작업과도 맞았다.

브라우저의 서버 상태는 TanStack Query로 관리하기로 했다. 피드 목록은 커서 기반 무한 스크롤로 조회하고, 글이나 답변을 작성하면 관련 조회를 갱신하는 방식이다. 서버는 NestJS에 Express를 쓰기로 했다.

Next.js 서버 캐시도 계획에 넣고 싶었다. NestJS에서 데이터가 바뀌면 Next.js의 Route Handler를 호출해 관련 캐시를 무효화하는 흐름을 생각했다. 이 부분을 검토하면서 캐시를 어디에 저장할지보다 변경 직후 화면이 무엇을 보여 줄지가 더 까다로웠다.

답변을 등록한 사람이 예전 목록을 다시 받으면 등록에 실패했다고 생각할 수 있다. 브라우저의 TanStack Query 캐시를 갱신해도 Next.js 서버 쪽에 오래된 결과가 남아 있다면 다시 조회한 화면이 예상과 달라진다. 다른 사람이 답변을 추가했을 때의 갱신도 따로 생각해야 한다.

검토 과정에서는 초기 사용자 콘텐츠의 서버 캐시를 미루자는 의견도 있었다. 그래도 캐시 모델을 설계하는 경험을 가져가고 싶어서 후속 개발 단계에 남겼다. 현재 구현 문서에서는 사용자 작성 콘텐츠에 Next.js 데이터 캐시를 적용하지 않고, 우선 TanStack Query의 갱신과 재조회로 처리한다. 서버 캐시의 정합성을 확인하는 작업은 앞으로 남아 있다.

지금 확인해야 할 동작은 구체적이다. 작성 직후 본인의 글이 보여야 하고, 수정한 내용이 다시 예전 값으로 돌아오지 않아야 한다. 서버 캐시를 추가할 때도 이 동작을 기준으로 검증하려고 한다.

## 게임 프로필 조회와 계정 소유 확인을 나눴다

게임 계정을 연결하는 화면은 Player Tag를 입력하고 프로필을 불러오는 흐름으로 잡았다. 그런데 프로필을 불러오는 데 성공했다는 사실만으로 입력한 사람이 그 계정의 주인이라고 볼 수는 없었다. 다른 사람의 태그를 넣을 수도 있기 때문이다.

이 차이는 인증 표시를 설계할 때 중요했다. 게임 데이터를 조회한 상태와 계정 소유권을 확인한 상태를 같은 의미로 보여 주면, 화면이 실제로 확인한 것보다 더 많은 신뢰를 주게 된다.

연결한 게임 프로필은 우선 소유권 미확인 상태로 두고, 별도의 확인 절차를 검토하기로 했다. 운영자가 확인하는 사용자 인증 표시도 게임 계정의 소유권 상태와 구분했다. 어떤 자료를 보고 무엇을 확인했는지가 분명해져야 표시의 의미도 정할 수 있었다.

피드백 요청에는 글을 작성할 당시의 게임 정보를 보관하기로 했다. 사용자가 나중에 덱을 바꿔도 예전 답변이 어떤 덱을 보고 작성됐는지는 남아 있어야 했다. 현재 프로필과 요청 시점의 스냅샷을 나눈 이유다.

## 다국어 메뉴와 서로 대화할 수 있는 서비스는 차이가 있었다

게임 서비스는 처음부터 한국어, 영어, 일본어를 생각했다. 언어별 경로와 UI 문구를 준비하고 게시글 번역도 제공하면 될 것 같았다.

그런데 게시글만 번역하면 흐름이 중간에 끊겼다. 한국어 질문을 일본어 사용자가 읽고 답변하더라도, 질문한 사람이 일본어 답변을 읽지 못할 수 있다. 피드백을 주고받는 과정까지 생각하면 번역 범위에 답변도 들어가야 했다.

언어별 라우팅은 초기에 잡되, 번역 기능과 각 언어권 운영은 따로 검증할 항목으로 남겼다. `/en`이나 `/ja` 경로가 존재하는 것만으로 그 언어의 사용자가 서비스를 이용할 준비가 끝났다고 볼 수는 없었다.

모바일 앱도 같은 관점에서 순서를 다시 봤다. 웹에서 요청하고 답변을 확인하는 흐름을 먼저 검증하고, 앱 배포와 스토어 운영은 별도 작업으로 다루기로 했다. 이후 WebView 셸을 구현했지만, 로컬에서 앱 화면이 뜨는 것과 스토어에 출시해 운영하는 것은 각각 확인해야 한다.

## 블로그는 DB 없이 운영하기로 했다

블로그는 게임 서비스와 필요한 데이터의 성격이 달랐다. 게임 서비스에는 여러 사용자가 계속 만드는 글과 답변이 있지만, 블로그의 작성자는 나 한 명이다.

기존에는 저장소에 글을 두고 티스토리에도 올려 관리했다. 이 과정이 번거로워서 개인 블로그를 만들기로 했다. 글을 바꿀 때마다 다시 배포해야 한다는 점 때문에 DB와 관리자 에디터도 잠깐 고민했다.

결국 Git과 MDX를 선택했다. 지금 필요한 것은 익숙한 편집기에서 글을 고치고, 변경 내역을 남기고, 발행하는 흐름이었다. GitHub와 호스팅을 연결해 push 뒤 배포를 자동화하면 직접 배포 명령을 실행하는 수고도 줄일 수 있다. 현재 CI는 준비돼 있고, 실제 호스팅 연결과 도메인 설정은 별도로 진행할 일이다.

한국어와 영어 본문은 각각의 MDX로 관리하고, 두 파일은 같은 콘텐츠 ID로 묶었다. 제목과 slug, 검색 설명은 언어별 SEO JSON에 두고, 발행일과 태그 같은 공통 정보는 메타데이터로 분리했다.

```text
content/posts/side-project-design/
  meta.json
  ko.mdx
  en.mdx

seo/
  ko.json
  en.json
```

번역을 쓰지 않은 글에 영문 주소만 만드는 일은 피하고 싶었다. 실제 본문이 있는 언어만 목록과 사이트맵에 나오게 했다. 제목을 고쳐도 주소는 유지하고, 주소를 바꿀 때는 리다이렉트를 명시하는 기준도 뒀다.

소개 화면에는 연락처 정도만 남겼다. 이력서와 프로젝트 소개까지 넣으면 글을 읽는 공간에서 내가 보여 주고 싶은 것이 다시 늘어날 것 같았다. 블로그에서는 글을 쓰고 읽는 흐름에 집중하기로 했다.

## 같은 저장소에서 서로의 데이터를 건드리지 않게 했다

게임 서비스와 블로그를 서로 다른 세션에서 작업하려고 했다. 기존 사진 서비스도 같은 저장소에 있어서, Git worktree로 작업 폴더와 브랜치를 나눴다.

여기서 소스 폴더만 나누면 끝날 줄 알기 쉬웠다. 실제로는 실행 포트, API 주소, 쿠키 이름, DB와 테스트 스키마도 각 프로젝트에 맞춰 정해야 했다. 같은 PC에서 서버를 띄웠는데 다른 프로젝트의 API로 요청을 보내면, 폴더를 나눈 의미가 없어진다.

그래서 프로젝트마다 데이터와 실행 환경을 분리하는 기준을 문서에 넣었다. 테스트는 사용 중인 개발 서버 대신 별도 포트와 임시 DB 스키마를 사용한다. 공통으로 관리할 이유가 확인된 설정이나 UI만 상위 패키지로 올리고, 서비스 데이터와 업무 로직은 각 프로젝트에 남겼다.

완료 기록도 나눠서 남기기로 했다. 로컬 테스트가 통과한 것, 외부 API를 실제로 연결한 것, 배포한 것, 사용자가 써 본 것은 각각 확인한 사실이 다르다. 구현 문서에서 무엇까지 확인했는지 읽을 수 있어야 다음 작업을 이어 가기 편했다.

계획을 여러 번 고친 지금도 사용자 모집과 재방문에 대해서는 결과를 쓰지 못한다. 아직 확인해야 할 부분이기 때문이다. 다음에는 기능 목록을 더 늘리기 전에 실제로 올라온 요청과 첫 답변, 요청자가 돌아와 읽었는지를 기록해 보고 싶다.
