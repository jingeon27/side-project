피식과 Game Mate, 이 블로그를 만들 때는 필요한 기능과 아키텍처를 먼저 정하고 AI 에이전트에게 구현을 맡겼어요. 화면 배치와 세부 구현 순서는 에이전트가 정하도록 두었어요. 결과물이 나오면 직접 써 보고 원하는 모습과 다른 부분을 설명했어요. 코드는 전반적인 구조를 훑었고, 세부 구현과 테스트 작성, 실행은 에이전트가 맡았어요.

처음 만든 건 사진 커뮤니티 피식(`photo-contest`)이었어요. 한 방송인의 '영도 대회'라는 콘텐츠에서 아이디어를 얻었어요. 친한 사람끼리 그룹 안에서 재밌는 사진을 공유하고 투표할 수 있으면 좋겠다고 생각했어요.

처음에는 그룹에 친구를 초대하고 사진을 올린 뒤 투표하는 기능을 요청했어요. 나온 화면을 써 보니 사진보다 그룹 목록이 먼저 보였고, 사진 위에 긴 안내가 붙어 있었어요. 그런 부분을 하나씩 바꾸게 하면서 익명 기록이나 가입 승인처럼 처음에 정하지 않았던 동작도 다시 요청했어요.

## 피식 홈에서는 그룹 목록보다 사진을 먼저 보여 주고 싶었어요

첫 홈은 그룹을 고르는 화면에 가까웠어요. 저는 들어오자마자 가입한 그룹의 사진을 최신순으로 보고 싶었어요. 그룹 목록은 마이페이지로 옮기고 홈에는 사진을 보여 달라고 했어요.

대회가 끝나면 더 올릴 수 없는 것도 아쉬웠어요. 기간을 정하지 않고 계속 게시할 수 있게 하고, 동영상과 합성 이미지도 받도록 요청했어요. 관리자의 게시물 삭제와 이달의 인기 게시물도 추가했어요.

사진을 가리는 안내는 줄이고, 스토리 기능이 없는데 붙어 있던 테두리는 지워 달라고 했어요. 데스크톱에서도 띄워 보고 사진 크기와 여백, 배치를 다시 요청했어요.

공개 그룹의 대회 화면에서는 가입 직후 글쓰기 버튼이 나타나지 않는 문제도 있었어요. 페이지를 나갔다가 다시 들어오면 버튼이 보였어요. 가입한 화면에서 바로 글을 쓸 수 있게 해 달라고 했고, 가입 정보가 바뀌면 게시 권한도 갱신하도록 수정했어요.

시작 화면에는 로그인, 회원가입, '익명으로 시작하기'를 모았어요. 외부 계정을 연결하지 않고 이용할 수 있도록 소셜 로그인은 넣지 않았어요. 익명으로는 공개 그룹을 둘러보고, 비공개 그룹은 회원가입과 가입 승인을 거치도록 했어요.

## 익명으로 쓴 기록을 회원가입 뒤에도 이어가게 했어요

익명으로 글을 쓰고 그룹에 가입한 뒤 회원가입하면, 기존 활동을 그대로 이어갈 수 있게 해 달라고 했어요. 쓰던 익명 프로필을 계정으로 바꾸고 가입한 공개 그룹과 작성한 글을 유지하도록 했어요.

가입 전에 로그아웃하면 그 프로필과 기록에 다시 접근할 수 없어요. 이때 안내를 '기록이 삭제된다'고 쓰면 다른 사람에게 보이는 글까지 없어지는 것으로 오해할 수 있어요. 작성자가 자기 프로필로 다시 들어올 수 없다는 점을 설명하게 했어요.

마이페이지에 있던 '브라우저 세션으로 유지돼요'라는 문구도 바꾸게 했어요. 로그아웃 확인 창에는 기록에 다시 접근할 수 없다는 내용을 먼저 적고, 계속 쓰려면 회원가입하라고 안내하게 했어요.

## 초대 링크로 들어와도 비공개 그룹은 승인을 받게 했어요

피식에는 친구를 부를 수 있는 그룹 초대 링크가 있어요. 링크를 다른 사람에게 전달해도 비공개 글까지 볼 수 있어서는 안 됐어요. 공개 그룹은 가입 전에도 둘러볼 수 있지만, 비공개 그룹은 로그인과 가입 승인을 거치도록 정했어요. 이 조건은 서버에서도 확인하게 했어요.

관리 권한은 그룹장과 부관리자로 나눴어요. 부관리자는 일반 멤버만 내보낼 수 있게 하고, 그룹장은 다른 멤버에게 권한을 넘긴 뒤에 나가도록 했어요. 관리할 사람이 없는 그룹을 남기고 싶지는 않았어요.

그룹에서 나가거나 내보내져도 쓴 글과 댓글은 자동으로 지우지 않도록 했어요. 다른 멤버가 참여한 대화까지 함께 사라지는 건 원하지 않았어요. 비공개 그룹에 다시 들어올 때는 승인을 다시 받게 했어요.

## 대회 접수와 투표의 마감 시각을 정했어요

대회는 시작 전, 접수 중, 투표 중, 종료 후로 나눴어요. 접수 중에만 '대회에 참여하기' 버튼을 보여 주게 했지만, 이미 열어 둔 작성 화면에서 마감 뒤 제출하는 요청도 처리해야 했어요. 파일을 올리는 동안 접수가 끝날 수도 있어서 실제 저장 시각을 서버에서 확인하게 했어요.

접수 마감 시각에 도착한 요청은 투표 기간으로, 투표 마감 시각부터는 종료로 처리하도록 정했어요. 판단에는 각 기기의 시계가 아닌 서버 시간을 쓰게 했어요.

대회 투표는 회원가입한 계정당 한 표로 제한했어요. 본인 작품과 숨겨진 작품에는 투표할 수 없게 하고, 요청이 동시에 들어와도 DB에 표가 두 개 저장되지 않도록 구현과 검증을 맡겼어요. 익명 프로필은 새로 만들기 쉬워 투표에서 제외했어요. 회원가입한 사람이 여러 계정을 만드는 문제까지 막은 것은 아니에요.

좋아요는 대회 투표와 따로 두고, 대회 안에서 한 사람이 좋아요를 누를 수 있는 작품 수에도 한도를 뒀어요. 결과에서는 공동 1등과 득표가 전혀 없는 대회를 구분하게 했어요. 모두 0표인데 공동 우승으로 표시되면 이상해서, 최다 득표가 0보다 클 때만 우승자를 보여 주도록 했어요.

안내가 길어져 사진을 가리면 문구를 줄여 달라고 했어요. 화면에는 지금 할 수 있는 행동과 필요한 한도만 남기고, 서버에서는 정한 조건을 계속 확인하도록 했어요.

## 사진 선택 취소와 업로드 실패도 따로 다뤘어요

사진을 고르다 파일 선택 창을 닫았을 때는 기존 선택을 유지하게 했어요. 같은 파일을 다시 고르는 경우와 미리보기를 만들지 못한 경우도 확인하게 했어요. 동영상에는 파일 형식과 크기, 길이 제한도 정했어요.

업로드가 끝나기 전에 게시하거나, 올린 파일의 유효 시간이 지나거나, 그사이에 그룹에서 나갈 수도 있어요. 게시물을 저장할 때 파일이 준비됐는지와 작성 권한을 다시 확인하도록 요청했어요.

업로드만 다시 하면 되는데 작성한 글까지 사라지는 것은 원하지 않았어요. 어느 단계에서 실패했는지 알려 주고 입력한 내용은 남겨, 실패한 작업을 다시 시도할 수 있게 해 달라고 했어요.

## Game Mate는 친추판매와 코칭에서 시작했어요

제가 보던 클래시로얄 커뮤니티에서는 해외 사용자들이 트위터를, 국내 사용자들이 카카오톡과 디시인사이드, 네이버 카페를 이용하고 있었어요. 해외 랭커와 친구를 맺기는 쉽지 않았고, 게임을 가르쳐 줄 사람을 찾는 글도 종종 봤어요.

여러 플랫폼에 흩어진 친추판매와 코칭 모집을 한곳에서 찾고, 조건을 확인한 뒤 대화할 수 있게 만들고 싶었어요. 처음 사용자에게 다가갈 수 있는 곳도 제가 아는 클래시로얄 커뮤니티여서 이 게임부터 시작하기로 했어요. 브롤스타즈나 롤도 생각했지만 처음부터 여러 게임을 다루지는 않기로 했어요.

클래시로얄 아래에 친추판매와 게임코치 게시판을 두고 피드백, 친선전, 자유게시판도 함께 만들었어요. 게임이 늘면 같은 분류를 붙일 수 있게 했고, 계정 거래는 위험 부담이 커서 뺐어요.

친추판매에는 금액을, 코칭에는 시간당, 기간 단위, 목표 달성까지의 수강료를 입력하게 했어요. 수강생이 코치를 찾는 글과 코치가 수강생을 모집하는 글을 모두 올릴 수 있어요. 서비스 안에서는 조건을 보고 채팅으로 이야기하는 데까지 제공하고 결제는 넣지 않았어요.

금액을 비워 뒀을 때는 0원 대신 '수강료 협의'로 보여 달라고 했어요. 목표 달성형에는 목표 점수와 그때까지의 총수강료를 받도록 했어요. 화면의 '월 단위'는 '기간 단위'로, '목표 점수 달성'은 '목표 달성까지'로 바꾸게 했어요. 정해진 기간의 코칭인지, 목표를 이룰 때까지 받는 코칭인지 읽고 구분할 수 있어야 했어요.

금액 지급과 환불은 이용자 사이에서 정해요. 화면에서도 서비스가 결제를 처리하는 것처럼 보이지 않게 했어요. 피식과 Game Mate는 계정과 데이터도 나눴어요. 사진을 공유하는 서비스와 친추판매나 코칭을 찾는 서비스에 같은 계정이 필요하다고 보지는 않았어요.

## 피드백 게시판에는 답변 알림과 도움됨 표시를 넣었어요

피드백 게시판에서는 질문에 답해 줄 사람이 필요했어요. 게임 프로필을 연결하고 여러 언어로 글을 읽을 수 있어도, 질문에 답이 없으면 다시 들어올 이유가 없을 것 같았어요.

```text
고민을 올린다
  → 다른 사람이 답변한다
  → 요청자에게 답변을 알린다
  → 요청자가 읽고 도움 여부를 표시한다
```

답변을 놓치지 않도록 알림을 넣고, 읽은 뒤에는 `도움됨`을 표시할 수 있게 했어요. 이후에는 도움됨으로 표시된 답변이 하나라도 있는 요청이 얼마나 되는지 보려고 해요. 같은 요청에 유용한 답변이 여러 개 달려도 요청 한 건으로 세고, 첫 답변까지 걸린 시간과 24시간 안에 답변을 받은 비율도 함께 보려고 해요.

아직 답변해 줄 사람은 모집하지 못했어요. 먼저 5~10명과 기존 커뮤니티의 질문을 수동으로 연결해 보는 걸 생각하고 있어요.

## 채팅 재전송은 이미 저장한 메시지를 돌려주게 했어요

서버가 메시지를 저장한 뒤 응답을 받기 전에 연결이 끊기면, 보낸 사람의 화면에는 실패로 표시될 수 있어요. 이때 재전송으로 같은 메시지가 두 개 저장되지 않게 해 달라고 했어요.

같은 메시지를 다시 보낼 때는 같은 요청 식별자를 쓰고, 서버에 이미 저장된 메시지가 있으면 그 결과를 돌려주도록 했어요. 같은 식별자를 다른 대화나 다른 내용에 쓰는 요청은 거부하게 했어요.

읽음 표시는 클라이언트가 확인한 메시지까지만 적용하도록 했어요. 채팅방에 들어온 뒤 새 메시지가 도착할 수도 있어서 입장만으로 전부 읽음 처리하지 않게 했어요. 대화내역을 지울 때도 내 화면에서 지운 범위만 적용하고 상대방의 기록은 남기도록 했어요.

로그아웃 뒤 다른 계정으로 들어오는 경우에는 이전 계정의 목록이나 늦게 도착한 응답이 남지 않도록 요청했어요. 계정이 바뀌면 진행 중인 조회를 취소하고 이전 조회 결과를 비우게 했어요.

## 삭제와 차단 뒤에 남길 내용도 정했어요

댓글 하나를 지울 때 다른 사람이 남긴 답글까지 없어지는 건 원하지 않았어요. Game Mate에서는 원댓글을 지워도 다른 사람의 답글은 남기도록 했어요. 회원 탈퇴 때도 탈퇴한 사람의 본문과 개인정보를 정리하는 일과 다른 사람의 답변과 댓글을 보존하는 일을 구분하게 했어요. 운영자가 숨긴 글도 작성자가 자기 내용을 삭제할 수 있게 했고요.

차단 뒤에는 새 대화를 시작하거나 기존 대화에서 메시지를 보낼 수 없도록 했어요. 상대방이 먼저 요청하거나 화면을 거치지 않고 API를 호출해도 제한되도록 구현과 검증을 맡겼어요.

신고 버튼도 넣었지만, 접수한 내용을 확인하고 조치할 사람은 별도로 필요해요. 어떤 내용을 어느 기준으로 처리할지는 운영에서 정할 일이 남아 있어요.

## 게임 프로필 조회와 소유권 확인을 구분했어요

Player Tag로 게임 프로필을 불러오는 기능을 만들었어요. 다른 사람의 태그도 조회할 수 있으므로, 조회 성공만으로 본인 계정이라는 표시를 붙이지 않도록 했어요. 연결 직후에는 소유권 미확인으로 두고, 운영자가 확인한 사용자라는 표시도 게임 계정 소유권과 구분했어요.

처음에는 글을 쓸 때 덱과 게임 정보를 스냅샷으로 남기려고 했어요. 이후 게임 프로필을 사용자 계정에 등록하는 쪽으로 정하고 글쓰기 화면의 덱 첨부는 빼 달라고 했어요. 프로필 인증 요청은 관리자와 1:1 채팅으로 연결하게 했어요.

인증 뒤 대표 게임 태그를 바꾸면 기존 인증을 해제하고 다시 확인받게 했어요. 이전 태그로 받은 인증이 새 태그에 남아서는 안 됐어요. 게임 API가 응답하지 않거나 조회할 수 없는 태그를 입력한 경우도 따로 처리하게 했어요.

게임 프로필은 가입할 때 연결하지 않아도 돼요. 바로 연결할 사람은 태그를 조회하고, 나중에 할 사람은 닉네임과 필수 동의만으로 가입할 수 있게 했어요.

입력이 길어져 본문만 스크롤하고 가입 완료 버튼은 아래에 남도록 요청했어요. 높이가 짧은 화면에서도 입력과 버튼이 겹치지 않는지 확인했어요.

프로필 수정은 처음에 펼침 메뉴에서 Bottom Sheet로 바꿨다가, Game Mate에서는 별도 페이지로 옮겼어요. 여러 항목을 한곳에서 수정하고 마지막에 저장할 수 있게 해 달라고 했어요. 자기소개에 적은 웹 주소는 프로필에서 누를 수 있게 했어요.

모바일에서 올라오는 창에는 X 대신 취소와 저장을 나란히 두게 했어요. 본문을 스크롤한 뒤에도 마지막 입력칸과 버튼에 닿을 수 있어야 했어요.

![Game Mate의 게임 계정이 보이는 공개 프로필과 별도 프로필 수정 페이지](/images/posts/side-project-design/09-profile-pages.jpg)

_공개 프로필에는 연결한 게임 계정이 보이고, 수정은 별도 페이지에서 해요. 테스트 계정과 가짜 게임 API 응답으로 확인한 화면이에요._

버튼과 입력, 모달은 두 서비스가 함께 쓰는 [디자인 시스템](https://github.com/jingeon27/side-project/tree/65c3d13a/packages/design-system)으로 만들었어요. 피식에서는 사진을 크게 볼 수 있게, Game Mate에서는 게임과 작성자의 상황을 읽기 쉽게 배치와 여백을 각각 조정하게 했어요.

## 직접 연 링크에서도 돌아갈 곳을 보여 주게 했어요

게시물 링크를 직접 열거나 다른 사이트에서 들어오면 서비스 안에서 방문한 이전 화면이 없을 수 있어요. 브라우저 기록만 따라가서 서비스 밖으로 나가지 않도록 돌아갈 곳을 정해 달라고 했어요.

그룹의 대회 상세에서는 헤더에 그룹명과 대회명을 보여 주고, 뒤로 가면 그룹으로 돌아오게 했어요. 그룹의 게시물, 대회, 명예의 전당 탭은 상세에서 빼 달라고 했어요. 공개 프로필도 헤더에서 돌아갈 곳을 보여 주고 본문에는 프로필을 남기게 했어요.

로그인이 필요한 행동에는 먼저 이유를 알리고, 취소하면 현재 화면에 남도록 요청했어요. 로그인한 뒤에는 원래 보던 곳으로 돌아오게 했고요.

## 게시글을 번역하면 답변도 읽을 수 있어야 했어요

Game Mate는 한국어, 영어, 일본어를 생각하고 만들었어요. 처음에는 메뉴와 게시글의 번역을 요청했지만, 일본어로 번역된 한국어 질문에 일본어 답변이 달리면 질문한 사람이 못 읽을 수도 있었어요. 답변도 번역해야 한다고 다시 요청했어요.

언어별 경로는 만들었지만 번역 기능과 각 언어권 운영에는 아직 확인할 게 남아 있어요. 모바일은 웹 화면을 함께 쓰는 WebView로 만들었어요. 우선 웹에서 질문하고 답변을 확인하는 동작을 다듬고, 앱 배포와 스토어 운영은 그다음에 하려고 해요.

## 블로그 소개에서는 이력서를 빼 달라고 했어요

블로그 글은 원래 별도 저장소에서 관리했어요. 티스토리로 옮겨 발행하는 게 번거로웠고 직접 만드는 비용도 낮아져서 이 블로그를 만들기로 했어요.

에이전트는 제가 요청하지 않은 이력서까지 만들었어요. 그 부분은 빼고 소개 화면에는 연락처만 남겨 달라고 했어요. 한국어와 영어 글은 실제 번역이 있을 때만 해당 언어로 볼 수 있게 했고요.

다크 모드에서 언어를 바꿔 보다가 테마 초기화 스크립트의 렌더링 경고도 찾았어요. 주소로 바로 들어왔을 때와 사이트 안에서 이동했을 때를 비교하며 수정을 요청했어요.

## 코드에서는 구조를 훑고 피드백했어요

폴더와 모듈을 훑으면서 다른 기능의 내부 파일을 바로 가져오는 참조를 고쳐 달라고 했어요. 기능의 공개 진입점을 거치도록 요청하고, 화면 조합과 조회 코드를 어디에 둘지도 피드백했어요.

서버에서 받아 온 값은 Apollo나 TanStack Query가, 입력 중인 값은 폼이 맡도록 했어요. 라이브러리의 조회 훅을 호출해 그대로 돌려주는 래퍼는 줄이고, 요청과 캐시 갱신을 함께 정하는 옵션은 남기게 했어요. 이 피드백을 구현하고 세부 로직과 테스트를 확인하는 일은 에이전트가 맡았어요.

피식에서는 목록 조회가 실패한 뒤 다른 카테고리를 골라도 이전 오류가 남는 동작을 고치게 했어요. 필터는 계속 쓸 수 있게 두고, 그룹이나 대회, 카테고리가 바뀌면 그 목록의 오류를 초기화하도록 했어요.

같은 피드백을 반복하지 않도록 `AGENTS.md`와 작업별 스킬에 반영하게 했어요. import 경계나 중복 상태처럼 검사할 수 있는 부분은 ESLint로 확인하게 했고, 저는 바뀐 구조와 화면을 다시 봤어요.

API와 캐시를 고른 이유, 서버와 DB의 구성은 [두 사이드 프로젝트에서 기술을 선택한 기준](/ko/blog/두-사이드-프로젝트에서-기술을-선택한-기준)에 따로 적었어요.

## 검색과 공유 링크로 들어오는 경우도 확인하게 했어요

Game Mate 공개 글에는 제목과 설명, canonical, 공유 이미지와 구조화 데이터를 넣게 했어요. 자바스크립트 없이도 글과 댓글을 읽을 수 있는지 검증을 맡기고, 사이트맵에는 공개 글과 프로필을 담도록 했어요. 채팅과 설정 화면은 검색에서 제외했어요.

공개 게시글은 로그인 쿠키 없이 조회한 내용을 캐시하게 했어요. 로그인한 사람이 차단한 작성자의 내용은 따로 걸러, 개인별 조회 결과가 공용 캐시에 들어가지 않게 했어요.

글을 수정하거나 댓글을 남긴 뒤에는 관련 캐시도 갱신하게 했어요. API 저장은 성공했는데 캐시 갱신만 실패하면 DB에 대기 항목을 남겨 재시도하도록 했어요. 브라우저의 조회 결과도 함께 갱신하도록 구현과 검증을 요청했어요.

## Sentry에 남길 정보도 정했어요

배포 뒤 오류를 찾을 수 있도록 웹과 API에 Sentry를 연결하게 했어요. 서비스와 배포 버전을 구분하고, 입력 조건에 맞지 않는 요청과 예상하지 못한 서버 오류를 나눠 수집하도록 했어요.

사용자가 쓴 글이나 채팅까지 보내고 싶지는 않았어요. 요청 본문과 쿠키, 헤더는 제외하고, Prisma 조회 인자가 섞일 수 있는 오류 메시지는 종류와 코드, 호출 위치만 남기도록 요청했어요. 전송 내용과 수신 여부도 에이전트가 확인하고 결과를 보고하게 했어요.

배포 쪽 이야기는 [일단 EC2 한 대에 올려보기로 했어요](/ko/blog/사이드-프로젝트-인프라를-ec2-한-대로-시작하기로-한-이유)에 따로 적었어요.
