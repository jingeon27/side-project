<Summary>

I specified the features and architecture, then gave an AI agent as much freedom as possible to implement them. Trying the services and reading the code led me back to screen layouts, anonymous account recovery, group permissions, message retries, and other missing details.

</Summary>

![An illustration of revising wireframes, a photo feed, and a game conversation screen](/images/covers/side-project-design.png)

_An illustration of revising the screens._

I wanted to see what an AI agent would produce if I gave it as much autonomy as possible. I specified the features and the overall architecture, then left the remaining decisions and implementation to the agent.

That is how I started building the photo community, Game Mate, and my personal blog. Instead of prescribing each layout and interaction, I let the agent choose, then tried the result and read the code. When something felt wrong or was missing, I described the behavior I wanted and asked it to revise the implementation.

Having the requested features did not always produce a service I wanted to use. A screen meant for viewing photos opened with a group list, or long explanations covered the photos. Reading the code also meant revisiting mixed responsibilities and places where the same state had more than one owner.

I had left many product decisions unspecified too. How would someone return to anonymous posts after logging out? What if they opened a submission form before the deadline but sent it afterward? Reviewing the screens and code gave me concrete cases to decide, and the implementation changed with those decisions.

The first project was `photo-contest`. The idea came from a streamer's segment called a “Yeongdo contest.” It made me think it would be fun to have a service where close friends could share funny photos within their own group.

I started with inviting friends to a group, submitting photos, and voting. It had separate submission and voting periods, with rules for ties and contests without votes.

## I came to see photos and got a group list

The first home screen was mostly about choosing a group. I wanted the latest photos from my groups instead. I moved the group list to My Page and made photos the first thing on the home screen.

Once the home screen centered on photos, it felt limiting to stop posting when a contest ended. I added ongoing posts with no submission period and supported videos and edited images too. Administrator deletion and the month’s popular posts followed.

Running the screens brought up design changes. I changed layouts that covered photos and removed a story-style border when there was no story feature. I checked spacing and layout on desktop separately.

Joining a group needed more than a working Join button. On a public group's contest page, joining did not immediately show the button for publishing a post. I had to leave the page and return to see it. I changed the membership flow to refresh contest posting permissions as well. A feature could exist while still leaving the next action unavailable on the current screen.

The entry screen brings login, signup, and “Start anonymously” together. Anonymous sessions can browse public groups. Private groups require login and membership approval.

Anonymous access also shaped login. I left social login out so people could use the service without linking an external account.

## What happens to activity after an anonymous start?

Once people could enter anonymously, I had to consider what came afterward. Someone who had posted and joined groups would need a way back to that profile, whether on another device or after logging out.

Signing up while using an anonymous profile now converts that profile into an account, preserving public-group memberships and authored content. Creating an unrelated account would defeat the purpose for someone signing up to keep their activity.

Logging out before signing up means losing access to that anonymous profile and its history. Saying “your history will be deleted” would also be inaccurate. Removing posts that others can see and losing the ability to return as their author are different things.

I also replaced the My Page explanation about a “browser session.” A confirmation at logout explains the consequence first: the anonymous profile will no longer be accessible, and signing up is the way to keep using it. People should not need to know what a session is to understand why signup matters.

## An invitation must not bypass a private group's approval

Groups started with a link for inviting friends. Once I introduced public and private groups, knowing the link and having permission to read the posts had to become separate things.

Public groups can be browsed before joining. Private groups require an account and membership approval, including when someone arrives through an invitation. Forwarding a link should not expose private posts. I made the server check access as well as hiding content on the screen.

Inviting friends grew into managing members, which needed more than one administrator role. Moderators can remove ordinary members. An owner must transfer ownership before leaving, so the group is not left without someone able to manage it.

Removing a member also raised a question about their posts and comments. I kept leaving a group separate from erasing its past conversations. Leaving or being removed does not automatically delete that content, and returning to a private group requires approval again.

## When should the contest entry button disappear?

A contest has upcoming, submission, voting, and completed phases. I made “Enter the contest” appear only during submissions, but hiding a button was not enough. Someone could leave the form open and publish after the deadline. Submissions could also close during an upload, so the server needed to check the time again when saving the entry.

The exact deadline needed a definition too. A request arriving at the submission deadline belongs to voting, and one arriving at the voting deadline belongs to the completed phase. The server clock makes that decision rather than each device’s clock.

Being allowed to publish several entries does not mean being allowed several votes. Contest voting is limited to one vote per account, with no votes for one's own or hidden entries. The database also prevents duplicate votes when requests arrive together or someone presses the button twice. Anonymous profiles are easy to recreate, so contest voting requires a registered account. That alone does not solve the problem of one person creating several accounts.

I kept likes separate from contest votes and set a per-person limit on how many contest entries could receive a like. Results also needed to distinguish a tie for first place from a contest with no votes. Calling every zero-vote entry a joint winner was not what I wanted. A contest only has winners when its highest vote count is greater than zero.

As the rules accumulated, explanations began filling a screen meant for photos. I kept the server restrictions and shortened the visible guidance to the actions available now and the limits people need to know.

## What if someone cancels a selection or the upload fails?

Selecting and uploading a photo has intermediate states too. I checked whether cancelling the file picker preserves the existing selection, whether the same file can be selected again, and what appears when a preview fails. Supporting video also brought decisions about file types, sizes, and duration limits.

Storing a file and publishing a post are separate steps. Someone might submit before the upload finishes, the upload could expire, or the author could leave the group in the meantime. Publishing also needs checks that the file is ready and the author still has permission.

The screen after a failure is part of uploading too. If only the photo needs a retry, losing the written post would make the person start over. The form needs to explain which step failed and let the existing input carry on.

## Game Mate starts with Clash Royale

Game Mate grew out of watching Clash Royale communities. The overseas players I saw used Twitter, while Korean players used KakaoTalk, DC Inside, and Naver Cafe.

Getting added by top-ranked overseas players was difficult, and I often saw posts looking for someone to teach the game. People posted across several platforms and checked each one separately. I wanted a place for friend requests, coaching offers, and advice about getting stuck in a game.

The Clash Royale communities I knew were also where I could reach initial users, so I chose to start there rather than launch for several games at once.

I considered Brawl Stars and League of Legends too, but decided against supporting several games at the start. I made five boards under Clash Royale: feedback, friend-add sales, friendly matches, coaching, and general discussion. More games could use those boards later. I left account trading out because of the risk.

Friend-add sales have a price field. Coaching posts can list an hourly fee, a fee for a fixed period, or a total fee until a goal is reached. Either students or coaches can post. People can read the terms and talk through chat. I decided not to add payments inside the service.

A missing price needed a meaning too. Displaying an empty field as zero could imply that coaching was free, so it appears as “Fee negotiable.” Goal-based coaching asks for the target rating and the total fee until it is reached. “Fixed period” expresses the option better than “Monthly,” and “Until the goal is reached” makes the coaching arrangement clearer than “Target rating achieved.”

Even after people agree on terms in chat, payment and refunds remain between them. Suggesting that the service handles payments would promise something I had not built, so I kept it to finding people and talking.

I kept the photo service and Game Mate's accounts and data separate. Both involve other people's opinions, but that did not give people viewing photos and people asking for game advice a reason to share an account.

## Who would answer the first question?

I was adding game profiles and multiple languages, but the first question still needed someone to answer it. A question left unanswered gives its author little reason to come back.

```text
Someone posts a question
  → Another player replies
  → The requester receives a notification
  → The requester reads it and marks whether it helped
```

Saving a reply does not continue the conversation if its requester never sees it. Reply notifications bring them back, and the `Helpful` action lets them respond after reading.

First, I want to see how many requests receive at least one reply marked helpful. Several helpful replies on one request still count as one request. I also want to look at time to the first reply and the proportion answered within 24 hours.

I have not recruited people to answer yet. My plan is to start with five to ten people and manually connect them to questions in the communities I know.

## A failed send could still have reached the other person

Chat seemed complete once a message was saved and displayed to its recipient. But a connection could drop after saving, before the sender received a response. Their screen could show a failure even though the message had arrived. Retrying could then deliver it twice.

Retries of the same message now use the same request identifier. If the server has already saved it, it returns that result. Reusing the identifier for another conversation or different content is rejected. “Try again” should not quietly create another copy of the message.

Saving a message once and marking it read needed separate rules. More messages can arrive while someone is in a conversation, so entering it does not mark everything as read. The receipt advances only through the message the client has confirmed. Clearing history likewise affects my view while leaving the other person’s record intact.

I checked logging out and entering with another account as well. Changing the server's login state could still leave the previous account's fetched lists or a late response on screen. Switching accounts also needed to cancel active queries and clear their previous results.

## Deleting and blocking affect other people's screens

Deleting a post looks simple if I only consider its author. If other people have replied or commented, should their contributions disappear too? I did not want deleting a comment to erase someone else's reply.

In Game Mate, replies by other people remain when the original comment is deleted. Account withdrawal also separates clearing the departing author's content and personal information from preserving other people's answers and comments. Another case was allowing authors to delete their own content even after a moderator had hidden it.

Blocking started with a button on a profile, but it also needed to govern starting a new conversation and sending messages in an existing one. Chat restrictions apply when the other participant sends the request too, including direct API calls. Adding a report button was also separate from deciding who reviews reports and what action follows.

The API can enforce a block immediately. A report still needs someone to review its content and decide what to do. Adding the button leaves that operational work to handle.

## Looking up a game profile did not prove ownership

Connecting a game account starts with entering a Player Tag and loading the profile. But someone can enter another player's tag. A successful lookup should not produce an ownership verification label.

Connected profiles therefore start with ownership unverified. Administrator-managed user verification is separate from game-account ownership too. A successful tag lookup alone must not attach a verification badge.

The early plan included saving a snapshot of the deck and game information with each post. During implementation, I moved game profiles to the user account and removed deck attachments from the writing screen. Profile verification requests now start a one-to-one chat with an administrator.

Changing the primary game tag after verification was another case. A status checked for the previous tag should not automatically carry over to a new one, so changing the primary tag clears the existing verification and requires another review. An unavailable game API or a tag that cannot be looked up also needs handling separately from signup with a nickname alone.

## Things people do not have to do during signup

Connecting a game profile is optional at signup. People who want to connect immediately can look up their tag. Others can join with a nickname and the required agreements, then connect later.

As the form grew, I made the body scroll while keeping the completion button at the bottom. I checked short viewports to make sure the inputs and button did not overlap.

I also disliked editing a profile through an expandable section. I first changed it to an Edit Profile button that opened a Bottom Sheet. Later, I moved Game Mate's profile editor to a separate page so editing could happen in one place. Web addresses in the bio became clickable on the profile too.

Someone who stops editing needs to find that action in the editor too. For mobile sheets, I put Cancel beside Save rather than using an X. The body scrolls while the last field and buttons remain reachable on a small screen.

## Where should Back take someone?

Back navigation seems straightforward when I only consider clicking through screens in order. Someone opening a post directly or arriving from a shared link might have no previous screen inside the service. Following browser history alone could take them away from it.

For a contest opened inside a group, I asked for the header to show the group and contest names, with Back returning to the group. Keeping the group's Posts, Contests, and Hall of Fame tabs on the detail screen made the current location confusing. Public profiles also moved navigation into the header, leaving the body for the profile itself.

An action requiring login is another interruption. I made it explain why login is needed before leaving the screen. Cancelling keeps the current page, and completing login should return to what the person was viewing.

## If the post is translated, what about the reply?

I started Game Mate with Korean, English, and Japanese in mind. At first, translating menus and posts seemed enough.

But a Japanese-speaking player could read a translated Korean question and answer in Japanese. The person who asked might then be unable to read the reply. Replies needed translation too.

Language routes are in place, but translation features and running the service for each language still need work. The mobile app uses the web screens through a WebView. I want to refine asking and reading replies on the web first, then deal with app distribution and the stores.

## The blog's about page did not need my resume too

I originally kept my blog posts in a separate repository. Moving them over to Tistory to publish was cumbersome. Building a blog of my own had also become less expensive, so I decided to make one.

During implementation, the AI agent went beyond what I had asked for and built a resume too. I removed it and kept only contact information on the about page.

Korean and English editions only appear where an actual translation exists.

Switching languages exposed a warning from rendering the theme initialization script again. Merely checking the translated text would have missed it. I fixed it while trying language changes with dark mode selected and comparing direct URL entry with navigation inside the site.

## Specifying the architecture still left code to review

I reviewed the implementation alongside trying the screens. Organizing code into feature folders did not help much when one feature imported another's internal files directly. I still had to trace how far a change might reach. I routed those imports through each feature's public entry point and revisited where screen composition and data queries belonged.

I also looked at places where the same server data was managed separately. Apollo or TanStack Query would own fetched values, while forms would own input in progress. Copying query results into another state variable made it easy for a save to update the cache while the screen kept showing an older value.

Wrapping code did not always make it easier to read either. I reconsidered hooks that only called and returned a library query hook, and callbacks that only forwarded their arguments. I kept options that defined a request and its cache updates together, but reduced wrappers that added another call to follow without doing anything else.

An error boundary also needed more than a place in the component tree. In the photo service, a failed post-list query could leave its error visible after selecting another category. I kept the filter usable and reset the list's error when its group, contest, or category changed. Only checking a successfully loaded list would have missed that behavior.

Repeating the same review feedback in every request was tedious. I put recurring code conventions in `AGENTS.md` and task-specific skills, and used ESLint for checks such as import boundaries and duplicated state. Describing where code should belong still left me with the work of checking what had actually been written.

I wrote more about API and cache choices, server checks, and database behavior in [How I chose the technology for two side projects](/en/blog/choosing-the-stack-and-boundaries-for-two-side-projects).

## Many decisions came after I had built the feature

The agent filled in things I had not specified. Showing a group list on the home screen and adding a resume to the blog were choices it made along the way. Trying the services helped me decide which of those choices to keep and which to change.

Some details, such as anonymous account recovery and what happens when a group owner leaves, were mine to define more clearly at the start. Other problems only became apparent on screen, or while reading code that already ran. Reviewing what had been built and deciding what to change became as much a part of the work as asking for another feature.
