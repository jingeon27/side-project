<Summary>

병원 예약 폼에서 가족을 추가한 뒤 날짜를 고르면 날짜 선택이 추가하기 전 인원수대로 움직였어요. 같은 선택과 일시를 서버 응답 캐시와 전역 스토어, 컴포넌트 상태가 따로 들고 있던 구조에서 난 버그예요. 서버가 정하는 가족 목록과 사용자가 고른 값을 나누고, 작성 중인 값은 React Hook Form 한 곳에서 바꾸도록 고쳤어요.

</Summary>

![예약 대상과 공통 날짜를 폼 안에서 관리하는 모습을 그린 일러스트](/images/covers/reservation-form-state.avif)

예약 폼에서 가족을 추가한 뒤 날짜를 고르면, 날짜 선택은 추가하기 전 가족 수를 기준으로 움직였어요.

병원 진료를 예약하는 화면이에요. 사용자는 희망 날짜와 시간을 고르고, 본인과 등록해 둔 가족 중에서 진료받을 사람을 체크해 신청해요. 목록에 없는 가족은 이 화면에서 바로 추가할 수 있어요. 화면 아래에서 올라오는 시트에서 가족 인증을 마치면 서버의 가족 목록이 늘어나는데, 버그는 이 추가를 거친 다음에 나타났어요.

화면은 날짜와 시간, 예약 대상을 고르는 정도였는데 그 값을 바꾸는 곳은 흩어져 있었어요. 가족 목록은 React Query 캐시에 있었어요. React Query는 서버 응답을 브라우저에 보관해 다시 쓰고, 필요할 때 새로 조회해 주는 라이브러리예요. 여기서는 조회 결과에 사람마다 선택 여부와 희망 일시 칸을 붙여서, 작성 중인 값까지 캐시에 들어 있었어요. 예약 대상과 일시는 Zustand에도 저장했어요. Zustand는 컴포넌트 바깥에 스토어를 만들어 어느 컴포넌트에서든 읽고 바꾸게 해 주는 전역 상태 라이브러리예요. 방금 고른 날짜는 컴포넌트의 로컬 상태(`useState`)에도 있었어요.

세 곳은 수명도 달랐어요. 대상 목록은 조회한 뒤 10분 동안 다시 조회하지 않았고, 화면을 떠나도 그동안 캐시에 선택과 일시가 남았어요. 스토어는 전역이라 저절로 비워지지 않아서, 예약 페이지와 대상 컴포넌트가 화면에서 사라질 때 각각 비웠어요. 로컬 상태만 컴포넌트와 함께 사라졌어요.

세 곳을 나란히 그려 보면 같은 값이 칸마다 되풀이돼요. 선택 여부와 희망 일시가 캐시와 스토어에 사람마다 한 벌씩 있고, 희망 일시는 로컬 상태에도 흩어져 있어요.

![리팩터링 전 예약 화면의 상태 배치예요. 선택 여부와 희망 일시가 React Query 캐시와 Zustand 스토어에 사람마다 한 벌씩 있었고, 희망 일시는 컴포넌트 로컬 상태에도 흩어져 있었어요.](/images/posts/reservation-form-state/01.avif)

버그가 난 동작은 그림의 '가족 추가' 줄이에요. 가족을 추가하면 지금 목록의 ID를 백업하고, 가족 인증 시트가 끝나기를 기다렸다가 목록을 다시 받아요. 그런 뒤 선택과 일시를 복원하고, 백업에 없는 새 가족에게 날짜를 넣어요. 코드로 줄이면 이런 흐름이에요. 실제 코드를 옮긴 것은 아니고, 그림의 단계를 설명하려고 다시 적은 예시예요.

```typescript
// 줄인 예시예요. 함수 이름은 설명하려고 붙였어요.
async function addFamilyMember() {
  const before = readCachedList();
  rememberExistingIds(before.map(({ memberId }) => memberId));

  await waitForVerificationSheet();
  const fresh = await refetchList();

  writeCachedList(
    fresh.map((person) => {
      const previous = before.find(({ memberId }) => memberId === person.memberId);

      // 있던 사람은 조회 전 선택과 일시를 되살리고, 새 가족에게만 페이지에서 고른 일시를 넣어요.
      return previous
        ? { ...person, selected: previous.selected, schedule: previous.schedule }
        : { ...person, schedule: pageSchedule };
    }),
  );
}
```

여기까지는 캐시에서 일어나는 일이에요. 스토어에는 그 가족을 체크한 뒤에야 캐시의 일시를 복사해 넣었고, `applyScheduleToAll`은 스토어에 들어 있는 사람의 일시만 바꿨어요. 같은 사람의 일시라도 캐시 쪽과 스토어 쪽이 따로 움직일 수 있었던 거예요.

## `validateDraft`를 빠뜨리면

유효성에도 같은 구조가 있었어요. 신청 버튼을 켤지 정하는 `isValid`를 Zustand 스토어가 작성 중인 값과 함께 들고 있었어요.

```tsx
type BookingDraftStore = {
  form: Partial<BookingFormValues>;
  isValid: boolean;
  updateParticipant: (
    memberId: number,
    values: Partial<ParticipantDraft>,) => void;
  applyScheduleToAll: (date: string, time: string) => void;
};
```

`isValid`는 값에서 계산할 수 있는 결과인데 따로 저장해 두었으니, 값이 바뀔 때마다 누군가 다시 계산해 넣어야 했어요. 그래서 참여자나 일시를 바꾸는 액션은 끝에서 `validateDraft`를 다시 호출했어요.

```typescript
updateParticipant: (memberId, values) =>
  set((state) => {
    // 값 수정
    state.isValid = validateDraft(state.form);
  });
```

당시 액션은 모두 이 호출을 하고 있었지만 새 액션에서 빠뜨리기 쉬운 구조였어요. 빠뜨리면 값은 바뀌었는데 버튼은 이전 `isValid`를 볼 수 있어요. 가족을 추가하거나 삭제할 때는 캐시의 사람 목록과 스토어의 배열까지 맞춰야 했고요. 가족을 삭제할 때를 보면, 스토어에서는 서버에 요청하기 전에 먼저 빼고 캐시에서는 서버 삭제가 끝난 뒤에 뺐어요.

Zustand를 쓰는 것 자체가 버그의 원인은 아니었어요. 서버가 정하는 사람 목록에 작성 중인 선택과 일시를 섞어 두고, 그 값을 다시 스토어에 옮기면서 생긴 문제였어요.

## 사람 목록은 서버에서, 선택은 폼에서

값을 출처로 나눠 보면 두 종류예요. 가족 목록과 이름은 서버에 원본이 있어요. 브라우저가 가진 건 복사본이라 다시 조회하면 달라질 수 있어요. 어떤 사람을 골랐는지와 희망 일시는 제출하기 전까지 브라우저에만 있어요. 서버에 다시 물어도 받을 수 없는 값이에요. 앞의 흐름에서 목록을 다시 조회할 때마다 선택을 백업하고 되살려야 했던 것도 이 둘이 같은 캐시 항목에 들어 있었기 때문이에요.

저장할 위치를 바꾸는 것보다 같은 선택을 다시 맞춰 쓰지 않게 하는 것이 필요했어요. 서버가 준 이름과 가족 목록은 React Query로 읽어요. 사용자가 고른 사람과 일시는 React Hook Form에 쓰고, Zod가 그 값으로 제출 가능 여부를 계산해요. React Hook Form은 폼의 값과 오류, 유효성을 `useForm`이 만든 객체 한 곳에서 관리하는 라이브러리이고, Zod는 값의 조건을 스키마로 적어 실제 값과 비교하는 라이브러리예요. 아직 확인하지 않은 시트의 선택과 날짜 선택기의 표시값만 로컬 상태에 남겼어요.

한 값에는 주인을 하나만 둔 거예요. 대신 서버 목록이 바뀌면 동기화 훅이 폼 배열을 그 목록에 맞춰 줘야 해요. 리팩터링 뒤의 상태 배치를 같은 틀로 다시 그리면 다음과 같아요.

![리팩터링 뒤의 상태 배치를 같은 틀로 다시 그린 표예요. 작성값은 폼 한 곳에만 쓰고, 서버 목록이 바뀌면 동기화 훅이 폼 배열을 그 목록에 맞춰요.](/images/posts/reservation-form-state/02.avif)

날짜 선택기가 보여주는 값과 제출할 값도 구분했어요. 시트 안에서 고르는 동안에는 임시 값으로 두다가 확인하면 폼에 넣어요. 시트를 여닫는 동작은 오버레이 라이브러리가 맡아요.

예약 작성값을 다른 화면이 공유할 필요는 없어서 페이지에 `FormProvider`를 뒀어요. `FormProvider`로 감싸면 그 아래 컴포넌트는 props를 거치지 않고 `useFormContext`로 같은 폼을 받아요. 공용 훅 `useSchemaForm`이 `zodResolver`(Zod 스키마를 폼의 검증으로 잇는 어댑터)를 연결하고, `ParticipantSelector` 안의 동기화 훅이 서버 목록으로 빈 `participants` 배열을 채워요. 두 이름은 공개용 가명이에요.

```tsx
function BookingPage() {
  const methods = useSchemaForm({
    schema: BookingFormSchema,
    defaultValues: {
      participants: [],
    },
  });

  // handleScheduleSelect는 아래 '날짜 일괄 적용' 절에서 다룬다.

  return (
    <FormProvider {...methods}>
      <ScheduleSection onSelect={handleScheduleSelect} />
      <ParticipantSelector />
      <RequestNoteField />
      <TermsSection />
      <SubmitButton />
    </FormProvider>
  );
}
```

이렇게 만든 예약 신청 화면과 그 화면이 쓰는 폼 값을 함께 그렸어요. 실제 코드의 마크업과 문구를 바탕으로 다시 그렸고, 화면의 값은 예시예요. 시간까지 고르면 폼이 공통 일시를 모든 사람 칸에 옮겨 적고, 신청 버튼은 스키마 조건을 모두 채울 때 켜져요.

![리팩터링 뒤 예약 신청 화면과 그 화면이 쓰는 폼 값이에요. 시간까지 고르면 폼이 공통 일시를 모든 사람 칸에 옮겨 적고, 신청 버튼은 스키마 조건을 모두 채울 때 켜져요.](/images/posts/reservation-form-state/03.avif)

`participants` 배열 하나에도 서버가 정한 이름과 ID, 사용자가 바꾸는 선택 여부와 희망 일시가 같이 들어가요. 요청에는 선택하지 않은 사람도 `selected` 값을 달고 가요. 서버 목록을 다시 받더라도 이미 작성한 선택과 일시까지 덮어쓰지는 않도록 해야 했어요.

폼을 페이지 안에서 만들면서, 화면마다 전역 Zustand 스토어를 비우던 정리 코드는 지웠어요. 화면을 떠나면 작성 중이던 값도 폼과 함께 사라져요.

## 버튼은 왜 제때 켜질까

예약 폼의 조건은 다음처럼 옮겼어요.

```typescript
const ParticipantSchema = z.object({
  memberId: z.number(),
  selected: z.boolean(),
  name: z.string(),
  preferredDate: z.string({ message: '희망 날짜를 입력해 주세요.' }),
  preferredTime: z.string({ message: '희망 시간을 입력해 주세요.' }),
});

export const BookingFormSchema = z
  .object({
    requestNote: z.string().max(200, '최대 200자까지 입력할 수 있어요.').optional(),
    participants: z
      .array(ParticipantSchema)
      .min(1, '가족 예약이 최소 한 명 이상 있어야 합니다.')
      .default([]),
    preferredDate: z.string(),
    preferredTime: z.string(),
  })
  .superRefine((data, ctx) => {
    if (data.participants.some((participant) => participant.selected)) return;

    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      path: ['participants'],
      message: '최소 한 명은 예약 대상이어야 합니다.',
    });
  });
```

최소 한 명을 골라야 하고, 공통 `preferredDate`와 `preferredTime`이 있어야 신청할 수 있어요. `superRefine`은 필드 하나로 판단할 수 없는 조건을 스키마에 덧붙이는 메서드로, 여기서는 배열 전체를 보고 선택된 사람이 있는지 확인해요. 사람별 날짜와 시간은 문자열 여부만 검사해요. 날짜 선택기가 시간까지 골라 넘기기 전에는 공통 값이 준비되지 않아 제출이 막혀요.

버튼은 별도 `isValid` 상태 대신 `formState.isValid`를 읽어요. 액션마다 `validateDraft`를 부르던 일이 없어진 자리예요. 스키마에 오류 위치와 문구도 있지만, 이 화면은 아직 필드별 오류를 보여주지 않고 버튼을 끄는 방식만 써요.

다만 라이브러리로 옮겼다고 검증 시점까지 명확해진 것은 아니었어요. 버튼이 왜 제때 바뀌는지가 코드에 드러나 있지 않아요. `mode`는 `useForm`에서 유효성을 언제 검사할지 정하는 옵션이고 기본값은 제출 시점인데, `useSchemaForm`과 예약 폼은 `mode`를 지정하지 않아요. `setValue`는 코드에서 필드 값을 바꾸는 함수이고 `shouldValidate`를 넘기면 바꾼 뒤 검증까지 실행하는데, 날짜 핸들러는 이 옵션을 주지 않아요. 체크박스와 사람별 일시 변경은 `useFieldArray`의 `update`를 쓰고요. `useFieldArray`는 배열 모양의 필드를 다루는 훅으로, `update`나 `append`, `remove`처럼 배열을 바꾸는 함수를 돌려줘요.

React Hook Form 7.56 소스를 따라가 보니 답은 `participants` 배열에 있었어요. `isValid`를 구독하면 기본 제출 모드에서도 `register`나 `Controller`(입력 컴포넌트를 폼에 연결하는 방법들)에 연결된 입력 변경으로 유효성이 다시 계산돼요. 하지만 `shouldValidate` 없는 `setValue`만으로는 그렇지 않아요. 이 화면의 `setValue`는 `useFieldArray`가 관리하는 배열 전체를 바꾸고, `useFieldArray`가 그 변경 뒤 유효성을 계산하고 있었어요.

배열을 건드리지 않고 날짜만 `setValue`로 바꾸면 이 동작에 기대지 못해요. 스토어에서 `validateDraft`를 빠뜨렸을 때처럼, 값만 최신이고 버튼은 그대로인 문제가 다시 생길 수 있어요. `mode`를 호출부에서 정하거나 해당 `setValue`에 `shouldValidate`를 넘기는 수정은 아직 남아 있어요.

## `useSyncParticipants`가 맞추는 것

가족 목록을 다시 받아도 이미 고른 날짜는 지켜야 해요. 이전 구조에서 백업과 복원이 맡던 일이에요. `useBookingParticipants`가 회원 정보와 가족 쿼리를 합쳐 본인을 앞에 둔 목록을 만들고, 동기화 훅이 그 목록에 맞춰 폼 배열을 바꿔요. 회원 정보를 기다리는 동안에는 `null`이라 건드리지 않아요.

아래 코드의 `useWatch`는 지정한 필드를 구독해서, 값이 바뀌면 이 훅을 쓰는 컴포넌트를 다시 렌더링해요. `intersectionBy`와 `differenceBy`는 기준 값으로 두 배열의 교집합과 차집합을 구하는 유틸리티 함수예요.

```tsx
// 새 칸을 만드는 함수: 서버 값에 폼의 공통 희망 일시를 붙인다.
function useParticipantInitializer(control: Control<BookingFormValues>) {
  const preferredDate = useWatch({ control, name: 'preferredDate' }) ?? '';
  const preferredTime = useWatch({ control, name: 'preferredTime' }) ?? '';

  const initParticipant = useCallback(
    (override: Partial<Participant> = {}) =>
      <T extends { memberId: number; name: string }>(base: T) => ({
        ...base,
        preferredDate,
        preferredTime,
        ...override,
      }),
    [preferredDate, preferredTime],
  );

  return { initParticipant };
}

function useSyncParticipants() {
  const { control, setValue } = useFormContext<BookingFormValues>();
  const current = useWatch({ control, name: 'participants' });
  const serverParticipants = useBookingParticipants();
  const { initParticipant } = useParticipantInitializer(control);

  useEffect(() => {
    if (serverParticipants === null) return;

    // 처음: 서버 목록 전체로 채운다.
    if (current.length === 0) {
      setValue('participants', serverParticipants.map(initParticipant()));
      return;
    }
    // 서버 목록이 짧아졌다: 서버에 남은 사람만 남긴다.
    if (current.length > serverParticipants.length) {
      setValue(
        'participants',
        intersectionBy(current, serverParticipants, (p) => p.memberId),
      );
      return;
    }
    // 서버 목록이 길어졌다: 폼에 없는 사람을 선택한 채로 뒤에 붙인다.
    if (current.length < serverParticipants.length) {
      setValue('participants', [
        ...current,
        ...differenceBy(serverParticipants, current, (p) => p.memberId).map(
          initParticipant({ selected: true }),
        ),
      ]);
    }
  }, [serverParticipants, current, initParticipant, setValue]);
}
```

처음 채울 때는 서버 목록의 기본값을 써요. 본인은 선택된 상태, 기존 가족은 선택하지 않은 상태로 시작해요. 이후 추가된 가족은 `selected: true`로 붙여 바로 예약 대상이 돼요.

처음 봤던 장면은 여기서 달라져요. 새 사람의 일시는 `initParticipant`가 폼의 공통 `preferredDate`와 `preferredTime`에서 가져와요. 날짜를 고른 뒤 가족을 추가해도 새 칸에 같은 일시가 들어가요. 이미 있던 사람은 현재 폼 값을 남겨 개별 선택과 일시를 지켜요.

동기화 훅의 갈래는 처음 채우기, 추가, 삭제, 그리고 사람 수가 같을 때 그대로 두기까지 네 개예요. 길이로 무엇을 할지 고르고, 누구를 남기고 붙일지는 `memberId`로 정해요.

![서버 목록이 바뀔 때 동기화 훅이 폼 배열을 맞추는 네 갈래예요. 길이로 무엇을 할지 고르고, 누구를 남기고 붙일지는 memberId로 정해요. 새 칸에는 폼의 공통 희망 일시를 붙여요.](/images/posts/reservation-form-state/04.avif)

이 구현은 배열 길이가 달라졌을 때만 사람을 맞춰요. 인원수가 같은 채 `memberId`가 바뀌거나 이름만 바뀌면 그대로 둬요. 추가와 삭제에는 대응하지만 같은 길이의 교체나 서버 필드 갱신까지 동기화하는 코드는 아니에요.

## 날짜 일괄 적용

전에는 선택기에서 고른 일시가 페이지 상태로 올라가고, 대상 컴포넌트가 마지막 선택 일시와 비교한 뒤에야 캐시와 스토어의 일괄 적용을 시작했어요. 지금은 날짜 선택기가 시간까지 고른 뒤 날짜와 시간을 함께 넘겨요. 페이지 핸들러는 참여자들의 일시와 공통 일시를 폼에 적어요.

```typescript
const handleScheduleSelect = useCallback(
  ({ date, time }: { date: string; time: string }) => {
    const participants = methods.getValues('participants');

    // 날짜·시간 형식 변환은 생략
    methods.setValue(
      'participants',
      participants.map(initParticipant({ preferredDate: date, preferredTime: time })),
    );
    methods.setValue('preferredDate', date);
    methods.setValue('preferredTime', time);
  },
  [methods, initParticipant],
);
```

`initParticipant`에 새 일시를 덮어쓸 값으로 넘기니 선택 여부는 유지돼요. 날짜를 캐시와 스토어, 로컬 상태에 각각 쓰던 흐름이 이 폼 업데이트로 합쳐졌어요. 공통 시간을 고르면 사람 카드에 '변경'이 나타나고, 개인 시트에서 확인하면 `useFieldArray`의 `update`가 그 사람만 바꿔요. 공통 일시를 다시 고르면 개인별로 바꿨던 일시도 덮어써요.

`useFieldArray`는 예약 대상 목록 컴포넌트에만 두었어요. 페이지 핸들러와 동기화 훅은 `setValue`로 배열 전체를 바꾸고, `shouldDirty`나 `shouldValidate`를 지정하지 않아요. 앞서 설명한 버튼 갱신 경로가 여기에 걸려 있어요.

## 폼으로 옮겨도 남은 것

`ParticipantSelector`는 선택 UI를 조합하고, 가족 선택은 하위 컴포넌트가 맡아요. 서버 목록을 폼 배열에 반영하는 일은 동기화 훅으로 떼었어요. 날짜를 맞추려고 캐시와 스토어, 로컬 상태를 함께 바꾸던 코드를 이렇게 나누고 Zustand 스토어를 지웠어요. 가족을 추가할 때 공통 일시를 어디서 가져오는지는 이제 폼 안에서 찾을 수 있고, 새 사람에게 값을 넣으려고 선택을 백업하고 복원하는 과정도 거치지 않아요.

그래도 서버 목록과의 연결이 없어지지는 않았어요. 서버 목록과 작성 중인 값을 맞추는 코드는 React Hook Form에서도 필요하고, 그 코드는 앞에서 본 대로 길이가 달라질 때만 움직여요. 커스텀 입력은 `Controller`로 연결해야 해요. 이 폼은 `setValue`의 검증과 dirty 갱신을 명시하지 않아 필드 배열의 동작에 기대고 있어요.

동기화 로직의 자동화 테스트도 아직 없어요. 처음 봤던 버그가 이 코드에서 다시 생겨도 테스트가 먼저 알려 주지는 않아요.
