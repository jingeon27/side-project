병원이 등록하는 시술 상품인 프로그램의 입력을 두 관리자 앱에서 공유하면서, 코드가 확인해 주는 범위를 필드 이름 enum에서 값 타입, 변환 테스트까지 넓혔어요. Ant Design Form에서 값의 타입이 어디서 사라지는지와, 공용으로 둘 부분과 앱마다 남길 부분을 나눈 과정을 적었어요.

![공통 폼을 두 관리자 화면에서 각자의 설정으로 조합하는 모습을 그린 일러스트](/images/covers/typed-program-form.avif)

프로그램 입력을 고칠 때마다 병원 관리자와 Back-Office의 `FormItem`을 같이 찾아야 했어요.

프로그램은 병원이 사용자에게 내놓는 시술 상품이에요. 이름과 썸네일, 카테고리, 가격, 설명, 상세 이미지를 입력해서 만들어요. 병원 담당자는 병원 관리자 앱에서 프로그램을 등록하고 검수를 요청하고, 운영팀은 Back-Office에서 요청을 확인해 승인하거나 반려해요. 같은 프로그램을 다루니 입력 항목이 크게 겹쳐요.

두 앱은 Ant Design Form으로 만들었고, `FormItem`은 입력 하나를 폼에 연결해 둔 컴포넌트예요. 처음에는 이 `FormItem`이 앱마다 따로 있었어요. 추천 대상과 시술 장비, 주의사항은 하위 시술의 기본 템플릿 편집 화면에도 있었어요. 카테고리는 진료과, 시술, 하위 시술 세 단계로 고르는데, 하위 시술마다 이런 내용의 기본값을 템플릿으로 등록해 두고 프로그램에서 가져다 써요. 같은 입력을 여러 곳에서 따로 만들고 있었던 거예요. 하나를 고쳐도 다른 화면까지 함께 고쳤는지 다시 확인해야 했어요.

입력은 겹쳐도 제출하는 일은 달랐어요. 운영 메모와 노출 설정은 Back-Office에만, 요청자와 검수 요청 종류는 병원 관리자에만 필요했어요. 지금 폼 타입에 선언된 최상위 필드를 세어 보면 공통이 34개, Back-Office 전용이 13개, 병원 관리자 전용이 4개예요. 두 폼을 통째로 합치면 이 차이까지 공용 코드에 따라오게 됐어요.

같은 프로그램을 다뤄도 두 앱에 필요한 값은 조금씩 달라요. 그림의 입력값은 예시예요.

![같은 프로그램을 다뤄도 두 앱에 필요한 값은 조금씩 달라요. 그림의 입력값은 예시예요.](/images/posts/typed-program-form/01.avif)

그래서 같이 고쳐야 할 입력과 값의 타입은 공유하고, 검수와 제출은 각 앱에 남겼어요. 코드가 확인해 주는 범위는 필드 이름에서 값의 타입으로, 다시 변환 결과로 넓어졌고, 이 글은 그 순서를 따라가요. 무엇을 공유할지도 그 사이사이에 정해졌어요.

아래 코드는 설명에 필요한 부분만 옮겼어요. 병원을 가리키는 내부 식별자는 `partner`로 바꿨어요.

## 필드 이름 enum

Ant Design Form은 입력값을 `name`으로 찾아요. `<Form.Item name="price">`로 감싼 입력의 값은 폼의 `price` 자리에 들어가고, 다른 곳에서는 `form.getFieldValue('price')`로 읽어요. 이름은 실행 중에 쓰는 키일 뿐이라, 오타를 내면 없는 자리를 읽어 `undefined`를 받을 뿐 그 자리에서 오류가 나지 않아요.

처음 공용화할 때는 필드 이름을 enum으로 모았어요. 여러 곳에 흩어진 문자열을 맞추는 데는 도움이 됐고 오타도 줄었지만, `price`에 문자열을 쓰는 건 막지 못했어요. `getFieldValue`가 돌려준 값을 다룰 때도 이름만 맞고 값은 잘못 이해할 수 있었어요. 줄인 예시예요. 당시 코드를 옮긴 것은 아니고, 설명하려고 다시 적은 예시예요.

```tsx
// 줄인 예시예요. enum 이름은 설명하려고 붙였어요.
enum ProgramField {
  ProgramName = 'programName',
  Price = 'price',
}

const form = Form.useFormInstance();

const price = form.getFieldValue(ProgramField.Price); // any
price.toUpperCase(); // 타입 검사를 통과하고, 실행하면 오류가 나요.

form.setFieldValue(ProgramField.Price, '100000'); // 타입 검사를 통과해요.
```

값의 타입이 사라지는 자리는 Ant Design의 타입 정의에 보여요. `getFieldValue`의 반환 타입은 `any`이고 `setFieldValue`가 받는 값도 `any`예요. `Form.useForm<T>()`로 폼 값 타입을 넘기면 이름의 오타는 잡히지만, 이름과 값의 타입이 연결되지는 않아요. `Form.Item`은 제네릭을 따로 주지 않으면 폼 값 타입이 `any`라서 `name`에 어떤 문자열이든 들어가요. 이 내용은 Ant Design 5.29의 타입 정의로 확인했고, 당시 앱이 쓰던 버전과는 다를 수 있어요.

## 경로를 따라가는 값 타입

이름과 값을 잇는 일은 직접 해야 했어요. 지금 프로그램 공통 폼과 앱별 폼에서는 `createTypedForm<T>()`을 사용해요. 폼 값 타입을 한 번 전달하면 `Item`, `List`, `useForm`, `useFormInstance`, `useWatch`를 같은 타입 기준으로 쓸 수 있도록 만든 래퍼예요. 아래의 `IProgramFormCommon`이 두 앱이 공유하는 폼 값 타입이에요.

```tsx
// 공유 패키지
export const ProgramForm = createTypedForm<IProgramFormCommon>();

// Back-Office 앱: 공통 값에 운영·검수 전용 값을 더해요.
export interface IProgramInspectionClient extends IProgramFormCommon {
  memo?: string;
  hidePrice?: boolean | null;
  rejectReason?: string;
  // 나머지 앱 전용 필드 생략
}

export const ProgramInspectionForm =
  createTypedForm<IProgramInspectionClient>();
```

공유 입력은 `ProgramForm`으로 공통 필드만 읽고, Back-Office의 전용 입력은 `ProgramInspectionForm`으로 추가 필드까지 읽어요. 두 API가 쓰는 건 같은 Ant Design Form 컨텍스트예요. 컨테이너가 만든 폼 인스턴스를 `Form` 컴포넌트에 넘기면, 그 아래의 입력은 props 없이 `useFormInstance`로 같은 인스턴스를 받아요. 값이나 인스턴스를 복제하지 않고 접근할 수 있는 타입만 나눴어요. 공용과 앱 전용의 경계가 타입에서는 이렇게 보여요.

```typescript
const form = ProgramForm.useFormInstance();

const name = form.getFieldValue('programName'); // string
const price = form.getFieldValue('price');     // number

form.setFieldValue('price', 100000);
form.setFieldsValue({ programName: '프로그램명', price: 100000 });

// 아래 두 호출은 타입 검사에서 걸려요.
form.getFieldValue('programNmae');
form.setFieldValue('price', '100000');
```

앞의 enum 예시와 나란히 보면 차이가 보여요. `price`의 타입이 `number`로 나오니 `toUpperCase`를 부르는 코드도 타입 검사에서 걸리고, 문자열을 넣는 호출과 이름의 오타도 함께 걸려요.

`getFieldValue('price')`는 `number`를 돌려주고 `setFieldValue('price', ...)`도 그 타입만 받게 하고 싶었어요. `TFieldNamePath<T>`가 이름과 중첩 경로를 제한하고, `TPathValue<T, P>`가 고른 경로에 해당하는 값 타입을 찾도록 만들었어요. Ant Design Form에서 중첩된 값의 경로는 `['detail', 'title']`처럼 배열로 적어요.

```tsx
// TFieldNamePath<T>와 TDeepPartial<T>의 구현은 생략했어요.
type TPathValue<T, P> =
  P extends keyof T
    ? T[P]
    : P extends readonly [infer K, ...infer Rest]
      ? K extends keyof T
        ? Rest extends []
          ? T[K]
          : TPathValue<T[K], Rest>
        : never
      : never;

// 인스턴스에서 제공하는 메서드의 타입
interface ITypedFieldAccess<T> {
  getFieldValue: <P extends TFieldNamePath<T>>(
    name: P,) => TPathValue<T, P>;

  setFieldValue: <P extends TFieldNamePath<T>>(
    name: P,
    value: TPathValue<T, P> | undefined,) => void;
}
```

조건부 타입은 `A extends B ? C : D` 모양으로 조건에 따라 타입을 고르는 문법이고, `infer`는 그 조건 안에서 타입의 일부를 변수처럼 꺼내요. `infer`로 경로의 첫 항목과 나머지를 나눠서, 경로를 따라 값의 타입을 찾는 방식이에요. 폼 값 타입을 작게 만들어 풀어 보면 다음과 같아요.

```typescript
// 줄인 예시예요. 폼 값 타입은 설명하려고 만들었어요.
type Values = { price: number; detail: { title: string } };

type A = TPathValue<Values, 'price'>; // number
type B = TPathValue<Values, 'nope'>; // never

type C = TPathValue<Values, ['detail', 'title']>; // string
// 1. 'detail'이 Values의 키이고 나머지가 ['title']이니 TPathValue<Values['detail'], ['title']>로 다시 들어가요.
// 2. 'title'이 키이고 나머지가 없으니 Values['detail']['title']인 string으로 끝나요.
```

`getFieldValue`와 `setFieldValue`는 경로를 제네릭 `P`로 받아요. 호출할 때 넘긴 경로가 그대로 `P`로 추론되고, 거기서 반환 타입과 받을 값의 타입이 정해지니 호출하는 쪽에서 타입을 적을 일이 없어요. `setFieldsValue`는 중첩 객체 일부만 바꿀 수 있도록 `TDeepPartial<T>`를 받고, `useWatch`에는 아직 값이 등록되지 않은 경우를 고려해 `undefined`도 포함했어요.

Ant Design과 연결하는 데 필요한 타입 단언은 래퍼 안에 두었어요. 호출부에서는 반환값을 다시 단언하지 않고, 필드 이름과 값 타입이 연결된 API를 사용해요. 단언이 없어진 건 아니에요. 래퍼 한곳에 모였으니, 여기 타입이 틀리면 호출부의 검사도 같이 틀려져요.

공통 타입과 앱별 타입을 나누고, 읽고 쓰는 메서드도 그 타입을 따르도록 한 구조를 그리면 다음과 같아요.

## 같은 입력, 다른 조립

타입으로 정해지지 않는 차이도 있었어요. 하위 시술 템플릿 편집 화면과 프로그램 폼에는 같은 입력이 있어요. 추천 대상, 시술 특장점, 시술 장비, 시술 과정, 주의사항이에요.

시술 특장점에서 차이가 드러났어요. 템플릿 편집에서는 아이콘과 문구를 등록하지만, 프로그램에서는 가져온 아이콘은 그대로 두고 문구만 고쳐요. 공유 컴포넌트에 이 경우를 위한 옵션을 더하는 대신, `FormList`와 그 안에 놓을 입력을 분리했어요. 이렇게 한 이름 아래에 조각을 묶어 두고 쓰는 쪽이 조립하게 하는 방식을 compound 구조라고 불러요.

```typescript
// 하위 시술 템플릿 편집: 아이콘과 문구를 함께 입력해요.
<ProcedureHighlight.FormList>
  {({ field, index }) => (
    <>
      <ProcedureHighlight.Image field={field} />
      <ProcedureHighlight.Input field={field} index={index} />
    </>
  )}
</ProcedureHighlight.FormList>

// 프로그램 폼: 문구만 수정해요.
<ProcedureHighlight.FormList>
  {({ field, index }) => (
    <ProcedureHighlight.Input field={field} index={index} />
  )}
</ProcedureHighlight.FormList>
```

`FormList`가 토글과 목록을 맡고, 목록의 각 행에 어떤 입력을 넣을지는 호출하는 쪽이 정해요. 호출하는 쪽이 행 조립을 직접 써야 하는 대신 공유 컴포넌트의 옵션은 늘지 않아요. 입력 모양이 같은 추천 대상과 시술 과정은 그대로 공유했어요. 시술 장비와 주의사항은 기본 조립을 제공하면서 필요한 조각도 열어 두었고요.

템플릿 입력 일부는 기존 Ant Design Form을 그대로 써요. 입력을 조합하는 compound 구조를 쓴다고 모두 typed API가 되는 것은 아니에요. 어떤 필드를 읽고 쓰는지는 typed API가 제한하고, 아이콘과 문구 중 무엇을 보여 줄지는 입력을 조합하는 쪽이 정해요.

차이가 있는 입력만 조립을 다르게 하고, 나머지는 같은 구현을 사용해요.

![차이가 있는 입력만 조립을 다르게 하고, 나머지는 같은 구현을 사용해요.](/images/posts/typed-program-form/03.avif)

공통 입력은 검수 요청이나 승인 API를 몰라요. `onFinish`와 요청 버튼은 앱이 맡아요. 병원 관리자가 요청을 보내는 일과 Back-Office가 승인하는 일을 같은 컴포넌트에 넣지 않았어요.

## 입력칸이 모르는 서버의 모양

서버가 템플릿 항목을 종류별로 나누고 `orderNo`(순번)를 붙여 보내는 모양은 입력칸에 그대로 쓰기 불편했어요. 화면에서는 행을 추가하거나 지우고, 이미지는 업로드 컴포넌트의 파일 목록으로 편집해야 했어요. 추천 대상 하나를 세 모양으로 놓으면 차이가 보여요. 구조만 남겨 줄인 예시이고 값도 예시예요.

```typescript
// 줄인 예시예요. 추천 대상 섹션만 남겼고 값은 예시예요.

// 서버 응답: 종류별로 묶고 순번을 붙여요.
const response = {
  RECOMMENDED_TARGET: [
    { orderNo: 1, title: '앞니가 깨진 분' },
    { orderNo: 0, title: '충치가 생긴 분' },
  ],
};

// 폼 값: 순번 없이 배열 순서로 편집해요. 사용자가 빈 줄을 하나 더한 상태예요.
const formValues = {
  recommendedTarget: [
    { title: '충치가 생긴 분' },
    { title: '' },
    { title: '앞니가 깨진 분' },
  ],
};

// 요청 본문: 빈 줄을 거르고 남은 순서대로 순번을 다시 매겨요.
const request = {
  RECOMMENDED_TARGET: [
    { type: 'RECOMMENDED_TARGET', orderNo: 0, title: '충치가 생긴 분' },
    { type: 'RECOMMENDED_TARGET', orderNo: 1, title: '앞니가 깨진 분' },
  ],
};
```

그래서 응답을 폼 값으로 바꾸는 함수와, 폼 값을 요청 본문으로 바꾸는 함수를 따로 두었어요. 입력 컴포넌트는 편집에 필요한 모양만 다뤄요.

```text
API 응답 → 응답 변환 함수 → 폼 값 → 요청 변환 함수 → API 요청
                            ↑
                   FormItem은 이 모양만 다뤄요.
```

이렇게 바꾸면 입력 컴포넌트마다 응답과 요청 형식을 해석하지 않아도 돼요. 편집 중인 값은 폼 모양으로 유지하고, 서버와 만나는 곳에서만 변환해요.

저장된 이미지와 방금 올린 이미지도 같은 입력에서 다뤄요. `UploadFile`은 Ant Design 업로드 컴포넌트의 파일 목록 항목 타입으로, 업로드가 끝나면 서버 응답이 `response`에 들어가요. 저장된 에셋을 `UploadFile`로 바꿀 때 `response`에 원본을 넣어 두면, 업로드가 끝난 새 파일과 같은 자리에서 에셋을 읽을 수 있어요. 제출 코드에서 둘을 따로 분기할 필요가 없어져요.

지금 썸네일과 자체 제작 이미지의 폼 타입은 `UploadFile<TCommonAsset>`이에요. 업로드 응답에 제네릭을 지정해서 `response.id`를 읽는 부분까지 에셋 타입을 유지했어요.

```tsx
type TProgramClientImage = UploadFile<TCommonAsset>;

// 저장된 이미지도 업로드 컴포넌트가 사용하는 형태로 바꿔요.
function convertCommonAssetToUploadFile<T extends TImageFileInfo>(
  asset: T,
): UploadFile & { response: T } {
  return {
    uid: String(asset.id),
    name: asset.originalFileName || asset.fileName,
    status: 'done',
    url: asset.src,
    response: asset,
  };
}
```

요청을 만들 때도 폼 값을 그대로 펼치지 않아요. API에 필요한 필드를 골라 담고, 썸네일은 이미지 ID로, 날짜는 문자열로 바꿔요. 화면에서만 필요한 이전 가격이나 입력 모드는 요청에 섞이지 않아요. 나중에 더한 건강검진 구성도 같은 폼에서 편집하지만 별도 API가 저장하므로 프로그램 요청에서는 제외해요.

템플릿 목록의 변환에는 몇 가지 규칙이 있어요. 추천 대상 같은 섹션마다 제공 여부를 고르는 토글과 그 아래 항목 목록이 붙어 있어서, 토글 상태까지 변환에 들어가요.

- 응답은 `orderNo`로 정렬하고, 폼에서는 배열 순서로 편집해요.
- 제출할 때 제목만 사용하는 섹션은 빈 줄을 거른 뒤 순번을 다시 매겨요. 이미지가 있는 섹션은 같은 필터를 적용하지 않아요.
- 시술 전후 사진은 배열 인덱스가 아니라 `orderNo`로 짝을 찾아 한 행으로 합쳐요. 요청할 때는 같은 순번의 두 배열로 나눠요.
- `null`, `undefined`와 빈 배열은 구분해요. 응답에 섹션이 없으면 토글을 끄고, 빈 배열이면 토글은 켠 채 초기 입력 행을 보여줘요.
- 임시저장과 최종 요청에서 빈 섹션을 보내는 방식은 달라요. 임시저장은 편집 중인 빈 배열을 보낼 수 있고, 검수, 등록 요청은 비어 있는 섹션을 제외해요.

아래 그림은 공유할 입력의 모양과, 각 요청에서 보내야 하는 모양을 구분해 그렸어요. 코드를 줄였고 값은 예시예요.

![공유할 입력의 모양과, 각 요청에서 보내야 하는 모양을 구분했어요.](/images/posts/typed-program-form/04.avif)

## 변환 테스트

이 규칙들은 타입 검사가 확인해 주지 않아요. 변환은 처음에 테스트 없이 만들었어요. 입력 타입을 맞춘 뒤에도 요청 내용이 틀릴 수 있어서, 두 앱의 응답 변환과 프로그램 요청, 검수 요청, 임시저장에 각각 테스트를 붙였어요.

단순히 변환한 값이 있는지만 보지는 않아요. 응답 순서가 섞여 있을 때도 시술 전후 이미지가 맞는 순번으로 짝지어지는지, 이미지 객체에 ID가 빠졌을 때 별도 ID를 사용하는지, 지운 썸네일이 `null`로 요청되는지 같은 조건을 확인해요.

아래는 실제 변환 테스트를 줄인 예시예요. `createClientForm`은 나머지 기본값을 채우는 테스트 헬퍼예요.

```typescript
it('빈 제목을 거른 뒤 남은 순서대로 순번을 매긴다', () => {
  const form = createClientForm({
    isRecommended: PROGRAM_PROVIDED_TYPE.PlatformProvided,
    recommendedTarget: [
      { title: '' },
      { title: '30대' },
      { title: '40대' },
    ],
  });

  const result = getDetailImageInspection(form);
  const templates = result[PROGRAM_DETAIL_TEMPLATE_TYPE.PlatformTemplate].templates;

  expect(templates.RECOMMENDED_TARGET).toEqual([
    { type: 'RECOMMENDED_TARGET', orderNo: 0, title: '30대' },
    { type: 'RECOMMENDED_TARGET', orderNo: 1, title: '40대' },
  ]);
});
```

반대로 이미지가 있는 시술 특장점은 제목이 비어도 같은 방식으로 지우면 안 돼요. 그 차이도 테스트에 남겼어요. 임시저장은 빈 제목을 거른 결과가 빈 배열이어도 그대로 보내는 조건을 따로 확인하고요.

폼에서 typed API로 접근하는 이름과 값은 타입 검사로 확인하고, API에 어떤 모양으로 보내는지는 변환 테스트로 확인해요. 타입이 맞는 것과 요청 내용이 맞는 것을 같은 검증으로 취급하지 않았어요. 입력은 같은 인스턴스를 사용하고, 필드 접근과 제출 데이터의 검증은 각각 다른 곳에서 맡아요.

![입력은 같은 인스턴스를 사용해요. 필드 접근과 제출 데이터의 검증은 각각 다른 곳에서 맡아요.](/images/posts/typed-program-form/06.avif)

## 값을 언제 채우는가

타입도 변환 테스트도 값을 채우는 시점은 정해 주지 않아요. 처음 상세를 열 때는 저장된 프로그램을 불러오지만, 카테고리를 바꾸면 그 하위 시술의 기본 템플릿을 가져와야 해요. 이 둘을 구분하지 않으면 조회 응답이 사용자가 고친 값을 다시 덮을 수 있어요.

검수 상세 컨테이너에서는 필요한 조회가 끝나고 초기값을 만들 수 있을 때 폼을 그려요. 같은 드로어에서 다른 건으로 이동해 초기값이 바뀌면 `resetFields()`로 다시 채워요. 비동기 응답을 `initialValues`에 넘기는 것만으로 기존 인스턴스가 다시 초기화되지는 않기 때문이에요.

하위 시술 템플릿을 가져오는 동작은 `SyncTreatmentSub`가 맡아요. 폼에서 시술과 하위 시술 ID를 읽고, 둘 다 있을 때만 조회하도록 query options에 `skipToken`을 사용해요. `skipToken`은 TanStack Query에서 조회 함수 자리에 넣어 그 조회를 건너뛰게 하는 값이에요.

effect에서는 조회 응답뿐 아니라 필드가 touched 상태인지도 봐요. touched는 Ant Design Form이 필드마다 두는 상태로, 저장된 프로그램을 막 열었을 때는 꺼져 있고 카테고리를 바꿔 값이 달라지면 켜져요. 그래서 상세를 열 때는 응답이 와도 저장된 값을 덮지 않아요. 시술 ID만 확인하면 같은 시술 안에서 하위 항목을 바꾼 경우가 빠져서, 하위 시술 ID의 touched 상태도 함께 확인해요.

```typescript
const form = ProgramForm.useFormInstance();

const treatmentId =
  ProgramForm.useWatch(['treatmentId'], form) ||
  form.getFieldValue(['treatmentId']);
const treatmentSubId =
  ProgramForm.useWatch(['treatmentSubId'], form) ||
  form.getFieldValue(['treatmentSubId']);

const { data } = useQuery(
  treatmentSubDetailQueryOptions({ treatmentId, treatmentSubId }),
);

const isTouchedTreatmentId = form.isFieldsTouched(['treatmentId']);
const isTouchedTreatmentSubId = form.isFieldsTouched(['treatmentSubId']);

useEffect(() => {
  if (!data || !(isTouchedTreatmentId || isTouchedTreatmentSubId)) return;

  // 실제 구현은 추천 대상·특장점·장비·과정·주의사항을 갱신해요.
  const { recommendedTargets } = data.data;
  form.setFieldValue(
    'recommendedTarget',
    isEmpty(recommendedTargets)
      ? INITIAL_RECOMMENDED_TARGET
      : recommendedTargets?.map((title) => ({ title })),
  );
}, [data, form, isTouchedTreatmentId, isTouchedTreatmentSubId]);
```

기본 템플릿에서 가져오는 값은 다섯 섹션으로 한정했어요. 직접 입력하는 추가 혜택과 시술 전후 사진은 이 동기화에서 바꾸지 않아요. 조회 응답을 폼 값으로 바꾸는 일도 이 컴포넌트 안에서 처리해요. 입력 컴포넌트마다 조회와 값 갱신을 반복하지 않도록 한 거예요. 조회 조건, 적용 조건, 갱신할 필드를 한곳에서 확인할 수 있어요.

![조회 조건, 적용 조건, 갱신할 필드를 한곳에서 확인할 수 있도록 했어요.](/images/posts/typed-program-form/05.avif)

## typed form이 잡는 것과 못 잡는 것

프로그램 필드를 바꾸면 공유 타입과 `FormItem`을, API 형식이 바뀌면 변환 함수와 테스트를 찾아가요. 검수 요청과 승인 처리까지 입력 컴포넌트를 따라올 필요는 없어졌어요.

typed form이 잡는 것은 코드에서 넘기는 필드 경로와 값 타입이에요. `programNmae` 같은 오타나 `price`에 넘긴 문자열은 타입 검사에서 걸려요. 실제 서버 응답이나 비동기 조회 뒤 입력이 덮이는 문제는 그것만으로 잡히지 않아요. 기존 Ant Design Form을 그대로 쓰는 템플릿 입력에는 typed API가 닿지도 않고요. 변환 결과를 검사하는 테스트와 실제 조회, 편집, 제출 화면을 보는 일은 그래서 따로 남겼어요.
