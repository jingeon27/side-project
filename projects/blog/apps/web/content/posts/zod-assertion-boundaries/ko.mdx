<Summary>

TypeScript의 `as`는 값을 실제로 확인하지 않아서, 서버가 약속과 다른 값을 보내도 막아 주지 못해요. 이 단언을 걷어내다 보니 Zod로 바꾸지 않는 편이 맞는 곳도 있었고, 스키마를 둔 곳에서는 값이 틀렸을 때 누가 곤란해지는지에 따라 API 응답과 URL, 폼의 실패 처리를 다르게 정했어요.

</Summary>

TypeScript의 타입은 코드를 실행하기 전에만 있어요. 빌드가 끝나면 사라지기 때문에, 실행 중에 서버가 약속과 다른 값을 보내도 타입이 막아 주지는 못해요. `as`(타입 단언)는 이 타입 검사에 "이 값은 이 타입이 맞으니 믿어 달라"고 말하는 문법이에요. 값을 확인하는 코드가 생기는 건 아니에요.

```typescript
type Review = { id: number; author: { name: string } };

const review = response.data as Review; // 컴파일은 통과해요
review.author.name; // 서버가 author를 null로 보내면 여기서 런타임 오류가 나요
```

Zod는 이 확인을 실행 중에 해 주는 라이브러리예요. 값의 모양을 스키마로 적어 두면 실제 값을 스키마와 비교해 주고, TypeScript 타입도 스키마에서 뽑아 쓸 수 있어요.

운영 중인 서비스에서 타입 단언을 줄이는 작업을 시작했을 때 처음 세운 규칙은 단순했어요. `as`가 필요해지는 곳에 Zod 스키마를 두자는 것이었어요. 실제로 코드를 바꾸기 시작하자 이 규칙은 절반만 맞았어요.

같은 `as`도 이유가 달랐어요. 라이브러리 콜백 타입이 느슨해서 이미 알고 있는 값을 다시 단언하는 곳이 있었고, API나 URL에서 실제로 어떤 값이 올지 모르는 곳도 있었어요. 전자는 타입이 이어지는 길을 고치면 되는 문제였고, 후자는 실행 중에 확인해야 하는 문제였어요. 둘 다 Zod로 감싸면 필요 없는 검증만 늘어나요. 그래서 기준을 다시 정했어요.

> 타입 단언이 보이면 먼저 값의 출처를 찾아요. 코드 안에서 이미 검증된 값이면 타입 흐름을 고치고, 애플리케이션 밖에서 들어온 값이면 런타임 경계를 세워요.

스키마가 필요한 쪽도 실패했다고 모두 화면을 멈출 수는 없었어요. 실패 처리는 값이 틀렸을 때 어디서 누가 곤란해지는지에 따라 달라졌어요.

## Zod로 바꾸지 않은 단언

데이터 테이블의 셀 콜백이 그런 경우였어요. 표의 열을 정의할 때 `render` 콜백을 넘기면 표가 칸마다 이 함수를 불러요. 첫 번째 인자는 그 칸의 값이고, 두 번째 인자 `record`는 그 줄의 데이터 전체예요.

문제는 첫 번째 인자의 타입이 넓다는 점이었어요. 어떤 필드를 그리는 칸인지까지 타입으로 이어지지 않으니, 값을 쓰려면 `as`로 다시 좁히게 돼요. 줄여서 쓰면 이런 모양이에요.

```typescript
// 셀 값의 타입이 넓어서 as로 다시 좁혀요.
render: (status) => STATUS_LABEL[status as Status]
```

그런데 `record`는 데이터 소스의 행 타입을 유지하고 있었어요. 같은 값을 `record`에서 읽으면 단언이 필요 없어요.

```typescript
// 느슨한 셀 값을 다시 단언하지 않습니다.
render: (_, record) => STATUS_LABEL[record.status]
```

이 경우에는 Zod로 셀 값을 다시 검사하는 것보다 이미 타입이 보장된 `record.status`를 읽는 편이 맞았어요. 실행 중에 확인할 일이 늘지 않고, `status` 필드의 이름이나 타입이 바뀌면 컴파일러가 이 줄을 바로 알려 줘요.

공용 컴포넌트에 제네릭이 빠져 있으면 `record`까지 타입을 잃어요. 이런 곳은 컴포넌트가 타입을 이어 주도록 제네릭을 보강했어요. 이것도 줄인 예시예요.

```tsx
// 전: 행 타입이 any로 끊겨서 쓰는 쪽에서 다시 단언해요.
function DataTable({ rows, columns }: { rows: any[]; columns: Column<any>[] }) {}

// 후: 넘긴 rows에서 T를 추론해 columns의 record까지 이어져요.
function DataTable<T>({ rows, columns }: { rows: T[]; columns: Column<T>[] }) {}
```

null이 실제로 올 수 있는 값은 타입과 렌더링 분기를 고쳤어요.

반대로 코드 밖에서 오는 값은 타입 선언이 맞아도 실제 값이 다를 수 있어요. 이쪽은 코드 안의 타입만 연결해서 해결할 수 없었어요.

- 서버가 돌려주는 API 응답
- 사용자가 직접 수정하거나 오래된 링크에서 들어오는 URL 파라미터
- 사용자가 작성하는 폼 값
- 디코딩한 토큰, 스트림 이벤트와 외부 라이브러리 콜백 값

`jwtDecode<Claims>(token)`처럼 제네릭만 붙이는 것도 `as`와 다르지 않아요. 토큰을 풀어서 나온 값이 실제로 `Claims`인지 확인하지 않아요. 이런 자리가 Zod를 둘 경계였어요.

```typescript
const claimsSchema = z.object({ role: z.enum(ROLES) });

try {
  const { role } = claimsSchema.parse(jwtDecode(token));
  return ALLOWED_ROLES.includes(role);
} catch {
  return false;
}
```

`parse`는 값이 스키마와 다르면 예외를 던져요. 토큰처럼 잘못된 값일 때 false를 돌려주는 자리는 이 실패를 그 경로로 보냈어요. 이미 쓰고 있는 API 응답 전체를 같은 방식으로 막는 일은 더 조심스러웠어요.

## API 응답: 막으면 잘 쓰던 화면이 먼저 깨져요

API 응답에는 `axios.get<Review>()`처럼 제네릭으로 타입을 붙여 왔어요. 이것도 서버 응답이 실제로 그 타입인지 확인하지 않아요. 그래서 여기에도 스키마를 두려고 했는데, 틀리면 막는 방식으로는 넣을 수 없었어요.

여기서 곤란해지는 건 이미 잘 돌아가던 화면이에요. 운영 중인 화면에 검증을 뒤늦게 넣는 중이라 처음부터 스키마가 완전하다고 믿기 어려웠어요. Zod 객체는 선언하지 않은 키를 결과에서 제거해요.

```typescript
const reviewSchema = z.object({ id: z.number() });

// 스키마에 createdAt을 빠뜨리면 결과에서도 사라져요.
reviewSchema.parse({ id: 1, createdAt: '2026-01-01' }); // { id: 1 }
```

`result.data`로 바로 바꾸면 이렇게 프론트 스키마에 빠진 필드가 사라져, 그 값을 쓰던 화면이 깨질 수 있었어요.

목록 50건 중 한 건의 부가 필드가 어긋났다는 이유로 목록 전체를 내리는 것도 원하지 않았어요. 특정 필드에 기본값을 넣을 수도 있겠지만, 아직 그렇게 처리하기로 정한 건 아니에요.

그래서 API 응답에는 `safeParse`로 스키마와 맞는지 확인하는 함수를 뒀어요. `safeParse`는 `parse`와 달리 예외를 던지지 않고 성공 여부가 든 결과를 돌려줘요. 이름은 `parseApiResponse`지만 반환하는 것은 파싱 결과가 아니라 원본이에요.

```tsx
export function parseApiResponse<T>(schema: z.ZodType, response: AxiosResponse<T>): T {
  const result = schema.safeParse(response.data);

  if (!result.success) {
    reportOnce({
      code: 'RESPONSE_SCHEMA_MISMATCH',
      request: `${response.config.method} ${response.config.url}`,
      issues: result.error.issues,
    });
  }

  return response.data;
}
```

응답이 스키마와 다르면 어긋난 필드 경로를 기록해요. 성공하든 실패하든 `response.data`를 돌려주므로, 로그가 남아도 소비하는 화면의 값은 바뀌지 않아요.

로그에는 원인을 다시 찾을 수 있는 정보만 남겼어요.

- axios config에서 가져온 HTTP 메서드와 요청 경로
- 오류가 발생한 화면 경로와 앱 구분
- 어긋난 필드의 경로, 오류 코드, 메시지
- 로그 한 건이 지나치게 커지지 않도록 앞쪽 20개 이슈만 기록

로그의 요청 이름은 호출부에서 따로 쓰지 않고 Axios 응답의 실제 메서드와 경로에서 가져왔어요. API 주소가 바뀌어도 예전 이름으로 경고가 남지 않도록 했어요.

같은 요청의 같은 필드가 목록 항목마다 어긋나면 경고가 쏟아질 수 있어요. 그래서 세션당 한 번만 보내요. 그만큼 이 로그 건수는 오류가 일어난 총횟수보다 그 불일치를 만난 세션 수에 가까워요.

이 방식은 잘못된 응답을 발견해도 막지는 않아요. 반환 타입도 여전히 Axios 제네릭을 믿고 있어요. 그래서 기존 동작을 유지하며 계약 차이를 찾는 단계로 두었어요. 기존 응답에서 파싱 결과를 쓰려면 계약을 먼저 확인해야 해요. 새 API나 인증, 스트림 이벤트처럼 실패를 요청이나 이벤트 단위로 처리할 수 있는 곳은 처음부터 파싱 결과를 써요.

### 로그를 받은 다음

관측만 하는 검증은 로그를 보는 사람이 없으면 타입 단언과 크게 다르지 않아요. 그래서 로그를 수정 절차로 이었어요. `SCHEMA_MISMATCH`가 생기면 요청 경로와 앱에서 스키마를 찾고, OpenAPI(서버가 API 명세를 적어 둔 문서)와 실제 응답을 나란히 봤어요. 서버가 약속과 다르게 보낸 것인지, 프론트 스키마를 잘못 쓴 것인지부터 구분해야 고칠 쪽을 정할 수 있었어요.

```text
SCHEMA_MISMATCH 로그
  → 요청 경로와 앱으로 호출부·스키마 특정
  → OpenAPI 계약과 실제 응답 대조
  → 프론트 스키마 오류 / 서버 스펙 위반 / 판단 불가로 분류
  → 프론트 오류만 스키마와 파생 타입 수정
  → 계약 테스트와 뮤테이션 체크
  → 리뷰·검증 후 PR 반영
```

로그를 없애려고 스키마를 무조건 느슨하게 만들지는 않았어요. 실제 응답이 OpenAPI와 다르면 null과 undefined를 허용하는 `.nullish()`를 프론트 스키마에 추가해 조용히 통과시키지 않아요. 서버 스펙 위반으로 분류하고 프론트 수정은 멈춰요. 응답이 anyOf 형태의 유니언(두 모양 중 하나로 오는 응답)인데 프론트가 한쪽만 알고 있었다면 두 응답을 유니언으로 모델링하고 양쪽 계약 테스트를 추가했어요.

그 과정에서 페이징 없는 목록과 본문 없는 성공 응답도 응답을 감싸는 공통 틀인 봉투 스키마에 넣고 있다는 걸 찾았어요. 한 API가 두 형태의 성공 응답을 주는데 하나만 모델링한 경우도 있었고요. 서버가 틀린 게 아니라 프론트가 응답을 잘못 이해한 경고도 있었어요.

## URL: 값 하나 때문에 검색어까지 잃어요

URL이 틀렸을 때 곤란해지는 건 링크로 들어온 사람이에요. URL은 사용자가 고치거나 오래된 링크에서 그대로 가져올 수 있어요. status 하나를 모른다고 입력했던 검색어와 보고 있던 상세까지 사라지는 결과는 피하고 싶었어요.

처음에는 객체를 한 번 `safeParse`하고 실패하면 기본 조회 조건을 썼어요. 줄인 예시예요.

```typescript
// 필드 하나만 틀려도 전체가 기본값으로 돌아가요.
const parsed = searchParamsSchema.safeParse(query);
const params = parsed.success ? parsed.data : DEFAULT_PARAMS;
```

실제로 `?keyword=coupon&pageNumber=3&id=12&status=OLD`처럼 status만 틀린 주소로 들어와도 정상 검색어와 페이지, 상세 드로어 id까지 함께 초기화됐어요. 서로 독립적인 조건은 따로 복구해야 했어요.

그래서 개별 필드가 독립적으로 복구될 수 있는 스키마는 필드마다 fallback을 두었어요. `.catch(값)`은 그 필드의 검증이 실패하면 오류 대신 이 값을 쓰게 해요.

```typescript
const searchParamsSchema = z.object({
  pageNumber: z.coerce.number().int().positive().catch(1),
  status: z.enum(STATUSES).optional().catch(undefined),
  keyword: z.string().optional().catch(undefined),
  id: z.coerce.number().optional().catch(undefined),
});

const params = useTypedQueryParams({ schema: searchParamsSchema });
```

알 수 없는 상태값은 버리되 검색어와 상세 화면은 유지해요. 스키마 전체 fallback은 예상하지 못한 구조가 들어왔을 때의 마지막 안전망으로 남겼어요. 현재 URL을 다시 조립해 공유 링크나 탭 이동에 사용하는 화면은 `.passthrough()`를 명시해, 해당 화면의 스키마가 소유하지 않는 파라미터를 조용히 지우지 않도록 했어요.

필드의 `.catch`가 복구하면 객체 파싱은 성공하므로 불일치 로그가 남지 않아요. 오래된 링크 때문에 매번 경고가 쌓이지는 않지만, 어떤 잘못된 값이 얼마나 들어왔는지도 알 수 없어요. 유입을 추적해야 하는 파라미터는 `.catch`로 숨기지 않고 객체 파싱 실패로 기록해야 해요. 결제와 권한처럼 조용히 바꾸면 위험한 값에도 이 방식은 쓰지 않아요.

## 폼: 고칠 사람이 화면 앞에 있어요

폼에서는 입력한 사람이 직접 값을 고칠 수 있어요. 잘못된 값을 통과시키거나 다른 값으로 바꾸는 대신 그 필드에 이유를 보여 주고 제출을 멈췄어요.

사용자 서비스의 입력 폼은 React Hook Form과 `zodResolver`를 연결해 스키마를 입력 타입과 제출 조건의 단일 출처로 사용했어요. React Hook Form은 폼의 값과 오류를 관리하는 라이브러리이고, `zodResolver`는 제출할 때 Zod 스키마로 값을 검사하게 이어 줘요.

```tsx
function useZodForm<T extends ZodRawShape>(
  schema: ZodObject<T>,
  options?: Omit<UseFormProps<z.input<ZodObject<T>>, unknown, z.output<ZodObject<T>>>, 'resolver'>,
) {
  return useForm<z.input<ZodObject<T>>, unknown, z.output<ZodObject<T>>>({
    ...options,
    resolver: zodResolver(schema),
  });
}
```

이 코드는 Zod 4.6, React Hook Form 7.90, @hookform/resolvers 5.9 기준이에요. 스키마가 값을 변환하면 입력값과 제출값의 타입이 달라져서 `z.input`과 `z.output`을 나눠 넘겨요.

```typescript
// 입력창의 값은 문자열이지만 제출할 때는 숫자로 바꿔요.
const priceSchema = z.object({ price: z.string().transform(Number) });

type PriceInput = z.input<typeof priceSchema>; // { price: string }
type PriceOutput = z.output<typeof priceSchema>; // { price: number }
```

처음 공개한 예제는 `z.infer` 하나만 썼는데 이 버전에서는 컴파일되지 않아 고쳤어요. 당시 서비스가 쓰던 버전의 코드와는 다를 수 있어요.

예약이나 리뷰처럼 단계가 이어지는 폼은 단계별 스키마가 각 화면에서 필요한 입력을 검증하도록 나눴어요. 사용자가 아직 입력하지 않은 다음 단계의 필드 때문에 현재 단계가 막히지 않도록 하기 위해서였어요.

Ant Design으로 만든 운영 도구의 검색 폼은 이 입력 폼과 달라요. `createSearchFilter(schema)`는 `z.infer`로 필드 이름을 좁히고 URL을 읽을 때 스키마를 써요. Ant Design Form의 제출 검증 전체를 교체한 건 아니에요. 필드 이름은 타입 검사에서, 외부 URL 값은 런타임에서 다루도록 한 거예요.

## 경계별로 놓고 보면

같은 Zod라도 값이 틀렸을 때 곤란해지는 쪽에 따라 역할이 이렇게 갈려요.

| 경계 | 값이 틀리면 곤란한 쪽 | 실패 시 처리 | 쓰는 값 |
| --- | --- | --- | --- |
| 기존 API 응답 | 잘 돌아가던 화면. 스키마가 덜 쓰였을 수 있어요 | 기록 후 통과 | 원본 유지 |
| 신규 API, 인증, 스트림 | 그 요청이나 이벤트로 좁힐 수 있어요 | 요청, 이벤트 단위 실패 | 파싱 결과 |
| URL 조회 조건 | 링크로 들어온 사람. 정상 조건까지 잃을 수 있어요 | 필드별 fallback 또는 객체 fallback + 기록 | 파싱 결과 |
| 사용자 입력 폼 | 입력한 사람. 직접 고칠 수 있어요 | 제출 차단 + 필드 안내 | 파싱 결과 |
| 외부 라이브러리 값 | 값의 영향 범위에 따라 달라요 | 무시, fallback, 차단 | 상황에 따라 사용 |

검증 도구를 통일했다고 실패 동작까지 통일하지는 않았어요. “스키마가 어긋났다”는 사실과 “화면을 중단해야 한다”는 결정은 서로 다른 문제였기 때문이에요.

## 틀린 값을 넣어 보는 테스트

테스트에는 정상 응답뿐 아니라 스키마가 어긋난 뒤의 값도 넣었어요. 기존 API는 미선언 필드를 포함한 원본을 그대로 돌려주는지, 새 enum이 오면 실제 요청 메서드와 경로, 어긋난 필드가 로그에 남는지 확인해요. 본문 없는 성공과 페이징 없는 목록도 유효한 계약으로 다뤄요.

URL 테스트에서는 잘못된 enum 하나만 버리고 검색어와 페이지, 상세 id는 남는지 봐요. 폼 테스트는 틀린 값을 제출하지 않고 고칠 수 있는 오류를 보여 주는지 확인해요. 같은 불일치 로그가 세션당 한 번만 나가는 조건도 테스트에 넣었어요.

스키마를 고친 뒤에는 옛 정의로 잠시 되돌려 새 테스트가 실제로 실패하는지도 확인했어요. Mock 픽스처가 스키마와 함께 잘못 바뀌면 테스트가 계속 성공할 수 있기 때문이에요. API 응답 Mock은 가능한 곳부터 `satisfies`와 계약 테스트로 묶고, 실제 개발 서버에서 확인할 수 있는 계약은 Mock 성공만으로 끝내지 않았어요.

## 타입 가드, 고친 것과 남겨 둔 것

사용자 정의 타입 가드는 `value is T`라는 반환 타입으로 "이 함수가 true를 돌려주면 값을 T로 봐도 된다"고 컴파일러에게 약속하는 함수예요. 컴파일러는 함수 안에서 정말 그걸 확인하는지 보지 않아요. 그래서 다음과 같은 타입 가드는 가장 위험한 단언 중 하나였어요.

```typescript
function isCompletedPayment(value: unknown): value is CompletedPayment {
  return value != null;
}
```

이 함수는 값이 null이 아니라는 것만 확인해요. 그래도 true가 나오면 컴파일러는 `CompletedPayment`라고 받아들여요. 나중에 그 타입에 필드를 추가해도 이 확인은 바뀌지 않으니, 실제로 확인한 내용보다 훨씬 강한 타입을 주고 있었어요.

결제 완료인지 분류만 할 때는 스키마의 성공 여부를 boolean으로 돌려줬어요. 검사하지 않은 전체 타입까지 좁힌다고 선언하지는 않았어요.

```typescript
const completedPaymentSchema = z.object({
  method: z.literal('NORMAL'),
  status: z.literal('COMPLETED'),
});

function isCompletedPayment(value: unknown): boolean {
  return completedPaymentSchema.safeParse(value).success;
}
```

검증된 데이터가 실제로 필요한 자리에서는 `value is T`를 다시 손으로 선언하기보다 `safeParse` 결과의 `data`를 사용했어요.

```typescript
const result = completedPaymentSchema.safeParse(value);
if (!result.success) return;

useCompletedPayment(result.data);
```

UI 라이브러리가 문자열로 돌려주는 탭, 정렬 키처럼 모르는 값은 무시해도 되는 자리에는 `z.enum(...).optional().catch(undefined)`를 사용했어요. 반대로 코드 안에서 이미 타입이 좁혀진 행 데이터는 스키마로 다시 검사하지 않았어요. 좁히기의 근거가 런타임 값인지 기존 타입 흐름인지 먼저 구분했어요.

사용자 정의 타입 가드가 전부 사라진 건 아니에요. 검증 비용이 더 크거나 외부 라이브러리 타입을 보조하는 곳은 남겨 두고, 그 함수가 어떤 필드를 확인하는지 테스트로 남겼어요. OpenAPI와 프론트 스키마의 차이도 선언만으로 없어지지 않아서, 실제 서버 계약과 불일치 로그를 계속 대조해요.
