*글의 주제를 설명하려고 만든 일러스트예요. 실제 제품 화면이나 정확한 구성도는 아니에요.*

타입 단언을 줄이는 작업을 시작했을 때 처음 세운 규칙은 단순했어요. as가 필요해지는 곳에 Zod 스키마를 두자는 것이었는데요. 실제로 코드를 바꾸기 시작하자 이 규칙은 절반만 맞았어요.

컴포넌트 내부에서 이미 타입이 정해진 값을 라이브러리의 느슨한 콜백 타입 때문에 다시 단언하는 경우가 있었고, API 응답이나 URL처럼 런타임에 어떤 값이 들어올지 모르는 경우도 있었어요. 전자는 타입의 출처를 바로잡아야 했고, 후자는 런타임 검증이 필요했어요. 둘을 모두 Zod로 감싸면 불필요한 검증만 늘어나요.

그래서 기준을 다음처럼 다시 정했어요.

> 타입 단언이 보이면 먼저 값의 출처를 찾아요. 코드 안에서 이미 검증된 값이면 타입 흐름을 고치고, 애플리케이션 밖에서 들어온 값이면 런타임 경계를 세워요.

이 기준으로 API 응답, URL 조회 조건, 사용자 입력 폼, 타입 가드와 외부 라이브러리 콜백을 다시 살펴봤어요. 같은 Zod를 사용해도 실패 처리 방식은 모두 달랐어요.

## 모든 타입 단언을 Zod로 바꾸지는 않았어요

예를 들어 데이터 테이블의 셀 콜백은 첫 번째 인자를 넓은 타입으로 주지만, 두 번째 인자인 행 전체는 데이터 소스의 타입을 유지하고 있었어요.

```typescript
// 느슨한 셀 값을 다시 단언하지 않습니다.
render: (_, record) => STATUS_LABEL[record.status]
```

이 경우에는 Zod로 셀 값을 다시 검사하는 것보다 이미 타입이 보장된 record.status를 읽는 편이 맞았어요. 제네릭이 빠진 공용 컴포넌트는 제네릭을 보강하고, null이 실제로 올 수 있는 값은 타입과 렌더링 분기를 고쳤어요.

반대로 다음 값들은 코드 밖에서 들어오기 때문에 타입만 고쳐서는 안전해지지 않았어요.

- 서버가 돌려주는 API 응답
- 사용자가 직접 수정하거나 오래된 링크에서 들어오는 URL 파라미터
- 사용자가 작성하는 폼 값
- 디코딩한 토큰, 스트림 이벤트와 외부 라이브러리 콜백 값

jwtDecode&lt;Claims>(token)처럼 제네릭만 붙이면 디코딩 결과가 실제로 Claims인지 확인하지 않아요. 이런 자리가 Zod를 둘 경계였어요.

```typescript
const claimsSchema = z.object({ role: z.enum(ROLES) });

try {
  const { role } = claimsSchema.parse(jwtDecode(token));
  return ALLOWED_ROLES.includes(role);
} catch {
  return false;
}
```

손상된 값이 들어왔을 때 이미 실패 경로가 정의된 자리라면 parse로 강하게 막았어요. 하지만 운영 중인 API 응답 전체에는 같은 정책을 바로 적용할 수 없었어요.

## API 응답은 먼저 어긋난 필드를 기록했어요

타입 단언으로 믿고 넘기던 API 응답을 Zod 스키마로 확인하도록 바꿨어요. 다만 현재 이 계층은 파싱된 값을 반환하지 않아요.

```tsx
export function parseApiResponse<T>(schema: z.ZodType, response: AxiosResponse<T>): T {
  const result = schema.safeParse(response.data);

  if (!result.success) {
    reportOnce({
      code: 'RESPONSE_SCHEMA_MISMATCH',
      request: `${response.config.method} ${response.config.url}`,
      issues: result.error.issues,
    });
  }

  return response.data;
}
```

함수 이름은 parseApiResponse지만 스키마가 맞으면 아무 일도 하지 않고, 어긋나면 필드 경로를 기록한 뒤 원본 응답을 그대로 돌려줘요.

이렇게 시작한 이유가 있었어요. 이미 운영 중인 화면에 스키마를 뒤늦게 씌우는 마이그레이션이었는데요. Zod 객체는 기본적으로 선언하지 않은 키를 파싱 결과에서 제거해요. 처음부터 모든 응답 계약을 완벽히 옮겼다고 가정하고 result.data로 갈아끼우면, 스키마에 아직 적지 않은 필드가 사라져 정상 동작하던 화면을 깨뜨릴 수 있었어요.

목록 50건 중 한 건의 부가 필드가 어긋났다는 이유로 목록 전체를 내리는 것도 원하지 않았어요. 특정 필드에 기본값을 넣을 수도 있겠지만, 아직 그렇게 처리하기로 정한 건 아니에요.

대신 로그에는 원인을 다시 찾을 수 있는 정보만 남겼어요.

- axios config에서 가져온 HTTP 메서드와 요청 경로
- 오류가 발생한 화면 경로와 앱 구분
- 어긋난 필드의 경로, 오류 코드, 메시지
- 로그 한 건이 지나치게 커지지 않도록 앞쪽 20개 이슈만 기록

호출부에서 요청 이름을 문자열로 다시 적지 않았어요. 엔드포인트가 바뀌었는데 로그 이름만 예전 값으로 남는 문제를 피하려고 응답 객체가 가진 실제 요청 정보를 사용했어요. 동일한 요청과 필드에서 생긴 불일치는 세션당 한 번만 전송했어요. 목록 항목마다 같은 경고가 쌓여 다른 장애를 가리는 것을 막기 위해서였어요.

이 선택에는 분명한 한계가 있어요.

> 원본 값을 그대로 반환하는 API 경계는 계약 불일치를 발견하지만, 잘못된 값이 소비자에게 도달하는 것을 막지는 못해요.

따라서 이 단계만으로 “API 응답의 런타임 타입 안전성을 확보했다”고 말할 수는 없어요. 동작을 보존한 채 실제 계약의 어긋남을 수집하고, 확인된 스키마부터 강한 파싱으로 옮기기 위한 이행 단계예요. 새로 만드는 API나 인증, 스트림 이벤트처럼 실패 범위를 명확히 격리할 수 있는 경계에서는 처음부터 파싱 결과를 사용해요.

## 검증 로그를 보고 스키마를 고쳤어요

관측형 검증은 로그를 보는 사람이 없으면 타입 단언과 크게 다르지 않아요. 그래서 SCHEMA\_MISMATCH 로그를 발견하는 데서 끝내지 않고 수정 절차의 입력으로 연결했어요.

```text
SCHEMA_MISMATCH 로그
  → 요청 경로와 앱으로 호출부·스키마 특정
  → OpenAPI 계약과 실제 응답 대조
  → 프론트 스키마 오류 / 서버 스펙 위반 / 판단 불가로 분류
  → 프론트 오류만 스키마와 파생 타입 수정
  → 계약 테스트와 뮤테이션 체크
  → 리뷰·검증 후 PR 반영
```

로그를 없애려고 스키마를 무조건 느슨하게 만들지는 않았어요. 실제 응답이 OpenAPI와 다르면 프론트 스키마에 .nullish()를 추가해 조용히 통과시키지 않아요. 서버 스펙 위반으로 분류하고 프론트 수정은 멈춰요. 응답이 anyOf 형태의 유니언인데 프론트가 한쪽만 알고 있었다면 두 응답을 유니언으로 모델링하고 양쪽 계약 테스트를 추가했어요.

이 흐름에서 실제로 페이징이 없는 목록 응답, 본문이 없는 액션 응답, 한 API가 두 형태의 성공 응답을 돌려주는 경우를 기존 단일 봉투 스키마가 잘못 판정하고 있다는 사실을 찾았어요. 검증은 서버 오류만 찾는 장치가 아니었어요. 프론트가 서버 계약을 잘못 이해한 경우도 같은 방식으로 드러냈어요.

## URL은 잘못된 필드만 복구했어요

URL은 API 응답과 실패 조건이 달라요. 사용자가 직접 수정할 수 있고, 예전에 공유한 링크로 들어올 수도 있는데요. 잘못된 검색 조건 하나 때문에 화면 전체를 오류 상태로 보내는 것은 사용자가 이해하기 어려운 실패예요.

처음에는 객체 전체를 한 번 safeParse하고 실패하면 기본 조회 조건으로 돌아가게 했어요. 그런데 이 방식에도 문제가 있었어요. status 하나가 잘못됐다는 이유로 정상적인 검색어와 페이지, 상세 드로어의 id까지 모두 사라졌어요.

그래서 개별 필드가 독립적으로 복구될 수 있는 스키마는 필드마다 fallback을 두었어요.

```typescript
const searchParamsSchema = z.object({
  pageNumber: z.coerce.number().int().positive().catch(1),
  status: z.enum(STATUSES).optional().catch(undefined),
  keyword: z.string().optional().catch(undefined),
  id: z.coerce.number().optional().catch(undefined),
});

const params = useTypedQueryParams({ schema: searchParamsSchema });
```

알 수 없는 상태값은 버리되 검색어와 상세 화면은 유지해요. 스키마 전체 fallback은 예상하지 못한 구조가 들어왔을 때의 마지막 안전망으로 남겼는데요. 현재 URL을 다시 조립해 공유 링크나 탭 이동에 사용하는 화면은 .passthrough()를 명시해, 해당 화면의 스키마가 소유하지 않는 파라미터를 조용히 지우지 않도록 했어요.

여기에는 관측상의 차이도 있어요. 객체 전체의 safeParse가 실패하면 불일치 로그가 남지만, 필드에 붙인 .catch가 값을 복구하면 객체 파싱은 성공으로 끝나므로 현재 구현에서는 로그가 남지 않아요. 사용자의 오래된 링크를 오류로 계속 쌓지 않는 장점이 있는 반면, 잘못된 값의 유입 빈도를 알 수 없다는 비용도 있는데요. 반드시 추적해야 하는 파라미터에는 .catch를 쓰지 않고 객체 경계에서 실패를 기록해야 해요.

## 폼은 잘못된 필드를 보여 주고 제출을 막았어요

폼은 네 경계 중 사용자가 직접 값을 고칠 수 있는 자리예요. 따라서 잘못된 값을 원본 그대로 통과시키거나 기본값으로 바꾸지 않고, 해당 필드에 이유를 보여 주며 제출을 막았어요.

사용자 서비스의 입력 폼은 React Hook Form과 zodResolver를 연결해 스키마를 입력 타입과 제출 조건의 단일 출처로 사용했어요.

```tsx
function useZodForm<TSchema extends z.ZodType>({ schema, ...options }: Options<TSchema>) {
  return useForm<z.infer<TSchema>>({
    ...options,
    resolver: zodResolver(schema),
  });
}
```

예약이나 리뷰처럼 단계가 이어지는 폼은 단계별 스키마가 각 화면에서 필요한 입력을 검증하도록 나눴어요. 사용자가 아직 입력하지 않은 다음 단계의 필드 때문에 현재 단계가 막히지 않도록 하기 위해서였어요.

운영 도구의 검색 폼은 조금 달라요. Ant Design Form의 제출 검증 전체를 Zod로 교체한 것이 아니라, createSearchFilter(schema)가 필드명을 z.infer에서 좁히고 URL을 읽을 때 같은 스키마를 사용해요. 잘못된 필드명은 컴파일 단계에서 막고, 외부에서 들어온 URL 값은 런타임에서 복구하는 구조인데요. 같은 “폼”이라도 실제 경계가 사용자 입력인지 URL인지에 따라 Zod의 책임을 다르게 뒀어요.

## 타입을 좁힐 때는 검증 결과를 썼어요

다음과 같은 사용자 정의 타입 가드는 가장 위험한 단언 중 하나였어요.

```typescript
function isCompletedPayment(value: unknown): value is CompletedPayment {
  return value != null;
}
```

본문이 무엇을 확인하든 컴파일러는 true가 반환되면 CompletedPayment라고 믿어요. 타입에 필드가 추가돼도 술어는 그대로 통과할 수 있는데요. 타입을 바꿔도 확인 로직은 예전 상태로 남을 수 있었어요.

분류만 필요한 자리에서는 거짓 타입 좁히기를 제공하지 않고 스키마의 성공 여부를 반환했어요.

```typescript
const completedPaymentSchema = z.object({
  method: z.literal('NORMAL'),
  status: z.literal('COMPLETED'),
});

function isCompletedPayment(value: unknown): boolean {
  return completedPaymentSchema.safeParse(value).success;
}
```

검증된 데이터가 실제로 필요한 자리에서는 value is T를 다시 손으로 선언하기보다 safeParse 결과의 data를 사용했어요.

```typescript
const result = completedPaymentSchema.safeParse(value);
if (!result.success) return;

useCompletedPayment(result.data);
```

UI 라이브러리가 문자열로 돌려주는 탭, 정렬 키처럼 모르는 값은 무시해도 되는 자리에는 z.enum(...).optional().catch(undefined)를 사용했어요. 반대로 코드 안에서 이미 타입이 좁혀진 행 데이터는 스키마로 다시 검사하지 않았어요. 좁히기의 근거가 런타임 값인지 기존 타입 흐름인지 먼저 구분했어요.

## 실패 정책은 경계의 사용자에 따라 달라졌어요

정리하면 같은 Zod라도 역할이 이렇게 갈려요.

| 경계 | 검증 결과 사용 | 실패 시 처리 | 이유 |
| --- | --- | --- | --- |
| 기존 API 응답 | 원본 유지 | 기록 후 통과 | 검증 도입이 기존 화면을 먼저 깨뜨리지 않게 함 |
| 신규 API, 인증, 스트림 | 파싱 결과 사용 | 요청, 이벤트 단위 실패 | 실패 범위를 경계에서 닫을 수 있음 |
| URL 조회 조건 | 파싱 결과 사용 | 필드별 fallback 또는 객체 fallback + 기록 | 오래된 링크 때문에 정상 조건까지 잃지 않게 함 |
| 사용자 입력 폼 | 파싱 결과 사용 | 제출 차단 + 필드 안내 | 사용자가 직접 수정할 수 있음 |
| 외부 라이브러리 값 | 상황에 따라 사용 | 무시, fallback, 차단 | 해당 값의 영향 범위에 맞춤 |

검증 도구를 통일했다고 실패 동작까지 통일하지는 않았어요. “스키마가 어긋났다”는 사실과 “화면을 중단해야 한다”는 결정은 서로 다른 문제였기 때문이에요.

## 검증이 실패했을 때의 동작을 테스트했어요

스키마가 정상 값을 받는 테스트만으로는 이 구조의 목적을 확인할 수 없어요. 그래서 테스트는 각 경계가 실패했을 때 어떤 동작을 해야 하는지에 집중했어요.

- API 응답이 어긋나도 원본 객체와 미선언 필드가 유지되는가
- 로그가 호출부의 문자열이 아니라 실제 요청 메서드, 경로를 담는가
- 서버가 모르는 enum을 추가하면 정확한 필드 경로가 기록되는가
- 본문 없는 성공 응답과 페이징 없는 목록을 정상 계약으로 구분하는가
- 동일한 불일치는 세션당 한 번만 기록되는가
- URL의 enum 하나가 잘못돼도 검색어, 페이지, 상세 id는 유지되는가
- 폼의 잘못된 값은 제출되지 않고 사용자가 고칠 수 있는 오류로 보이는가

스키마를 고친 뒤에는 옛 정의로 잠시 되돌려 새 테스트가 실제로 실패하는지도 확인했어요. Mock 픽스처가 스키마와 함께 잘못 바뀌면 테스트가 계속 성공할 수 있기 때문인데요. API 응답 Mock은 가능한 곳부터 satisfies와 계약 테스트로 묶고, 실제 개발 서버에서 확인할 수 있는 계약은 Mock 성공만으로 끝내지 않았어요.

## 남은 한계

- 관측형 API 경계는 잘못된 값을 차단하지 않아요. 현재 반환 타입은 여전히 Axios 제네릭을 신뢰하므로, 확인된 계약부터 파싱 결과를 반환하는 방식으로 옮겨야 해요.
- 로그의 중복 제거 단위는 세션이에요. 같은 로그의 건수는 정확한 오류 발생 횟수라기보다 해당 불일치를 겪은 세션 수에 가까워요.
- 필드별 .catch는 화면을 살리지만 잘못된 값이 로그 없이 사라져요. 유입 빈도를 알아야 하거나 결제, 권한처럼 조용한 복구가 위험한 값에는 사용하지 않아요.
- 스키마를 단일 출처로 삼아도 OpenAPI와 프론트 스키마 사이의 차이는 자동으로 사라지지 않아요. 실서버 계약 테스트와 불일치 로그가 그 간격을 발견하는 역할을 해요.
- 모든 사용자 정의 타입 가드를 없애지는 않았어요. 검증 비용이 더 크거나 외부 라이브러리 타입을 보조하는 곳은 남겨 두되, 어떤 필드를 확인하는지 테스트로 고정했어요.
