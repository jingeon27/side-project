*client, server, edge의 이벤트를 전송하기 전에 민감 정보를 정화해요.*

복지몰의 프론트엔드 에러와 Web Vitals를 보려고 Sentry를 도입했어요. @sentry/nextjs를 설치하고 이벤트를 올리는 것 자체는 하루면 됐는데요. 운영할 수 있는 상태가 되기까지는 훨씬 많은 일이 필요했어요.

- client, server, edge 세 런타임 초기화
- 오류 이벤트, breadcrumb, transaction, span의 개인정보 제거
- Web Vitals 수집과 실제 전송을 검증하는 E2E
- 사내 Sentry를 조회하기 위한 MCP 연결
- 릴리스와 소스맵 artifact 업로드
- 사용자 영향에 따른 에러 레벨과 그룹핑 정책
- 의미 없는 수집 트래픽을 줄이는 전송 게이트와 잡음 표본 추출

설정을 추가한 뒤에는 실제 전송 결과를 확인했어요. Web Vitals가 envelope에 담기는지, 소스맵이 배포한 파일과 연결되는지, 민감 정보가 이벤트에 남지 않는지 봤어요. 옵션만으로 설명되지 않는 동작은 SDK 소스를 따라가며 확인했어요.

이 글은 Next.js 16과 @sentry/nextjs 10.70을 기준으로 썼어요.

## 세 런타임의 오류를 한곳으로 모았어요

Next.js에서는 브라우저, Node, Edge가 서로 다른 SDK 구현을 써요. 그래서 초기화 파일도 런타임별로 나눴어요.

```text
// sentry.client.ts
Sentry.init({
  dsn: SENTRY_DSN,
  enabled: IS_SENTRY_ENABLED,
  environment: SENTRY_ENVIRONMENT,
  integrations: [
    Sentry.browserTracingIntegration({
      idleTimeout: SENTRY_IDLE_TIMEOUT,
    }),
  ],
  tracesSampleRate: SENTRY_TRACES_SAMPLE_RATE,
});

// sentry.server.ts
Sentry.init({
  dsn: SENTRY_DSN,
  enabled: IS_SENTRY_ENABLED,
  environment: SENTRY_ENVIRONMENT,
  integrations: [
    Sentry.httpIntegration({
      disableIncomingRequestSpans: true,
      maxIncomingRequestBodySize: 'none',
    }),
  ],
});
```

브라우저는 instrumentation-client.ts에서 초기화하고, Node와 Edge는 instrumentation.ts의 register()에서 현재 런타임에 맞는 초기화 함수를 불러요. 라우터 이동이 시작된 시점부터 navigation transaction을 잡도록 captureRouterTransitionStart도 연결했어요.

서버 컴포넌트 렌더링, 라우트 핸들러, 서버 액션, proxy에서 난 오류는 Next.js의 onRequestError로 넘겼는데요. API 인터셉터에서 이미 수집한 오류라면 다시 보내지 않아요.

같은 오류가 인터셉터 → 에러 바운더리 → onRequestError를 지나며 서로 다른 이슈 세 개로 갈릴 수 있었거든요. captureError가 처리한 객체에는 열거되지 않는 심볼을 남기고, 상위 수집 지점은 그 표식을 보면 건너뛰어요. 잡음이라 올리지 않기로 거른 오류에도 같은 표식을 남겼어요. 표식이 없으면 걸러 낸 오류가 에러 바운더리에서 fatal로 되살아나요.

## 요청 정보의 자동 수집 범위를 확인했어요

요청 정보의 수집 범위를 확인하면서 sendDefaultPii: false가 적용되는 경로도 살펴봤어요. 이 글에서 확인한 SDK 버전에서는 이 설정만으로 event.request의 헤더와 쿠키를 모두 막지 못했어요. 인증 토큰 쿠키인 sessionToken과 renewalToken(공개용 가명)도 실릴 수 있는 구조였어요.

이 옵션은 헤더, 쿠키 수집을 false로 끄는 게 아니라, 제외할 이름을 담은 deny 목록 객체로 바꿔요. 그런데 이벤트에 요청 정보를 싣는 requestDataIntegration은 값이 false인지만 확인해서, 객체가 오면 켜진 것으로 보고 목록을 적용하지 않은 채 헤더와 쿠키를 그대로 실었어요. deny 목록으로 거르는 코드는 span 경로에만 있었고요.

요청 정보는 오류 원인을 찾는 데 도움이 되지만, 의료 정보를 다루는 서비스에서 인증 정보나 사용자가 입력한 내용을 함께 보낼 이유는 없었어요. 그래서 sendDefaultPii에 기대지 않고 dataCollection에 끌 항목을 전부 적었어요. 요청 헤더, 쿠키, 본문, 쿼리와 사용자 입력은 수집하지 않아요.

```typescript
export const SENTRY_DATA_COLLECTION = {
  userInfo: false,
  cookies: false,
  httpHeaders: { request: false, response: false },
  httpBodies: [],
  urlQueryParams: false,
  genAI: { inputs: false, outputs: false },
  databaseQueryData: false,
  graphQL: { document: false, variables: false },
  stackFrameVariables: false,
  frameContextLines: 5,
};
```

AI 입력과 출력도 닫았어요. 상담 기능의 프롬프트와 응답에는 사용자가 쓴 내용이 들어갈 수 있으니까요. GraphQL과 데이터베이스 계측은 지금 쓰지 않지만, 나중에 통합이 추가되더라도 닫힌 채로 시작하도록 명시했고요.

stackFrameVariables도 중요했어요. Node의 localVariablesIntegration은 예외 프레임의 지역 변수를 이슈에 붙여요. 오류가 난 함수의 지역 변수에 회원 정보나 토큰이 있으면 그대로 수집될 수 있었어요.

frameContextLines는 반대로 5줄을 유지했어요. 개인정보가 아니라 소스 노출의 문제였고, 보내는 곳도 같은 사내 Sentry라 원인 분석에 주는 가치가 더 크다고 봤어요. 다만 이 값이 붙는 Node 서버 쪽은 뒤에서 다룰 이유로 소스맵을 올리지 않아서, 지금은 minify된 줄이 실려요.

## 새 수집 키가 생기면 타입 검사가 깨지게 했어요

dataCollection 객체를 넘기면 적지 않은 키는 생략했을 때 닫히는 게 아니라 "전부 수집"으로 열려요. 처음에는 stackFrameVariables와 graphQL 같은 키가 빠져 있었는데요.

SDK의 타입을 그대로 붙이는 것만으로는 막을 수 없었어요. 원본 타입의 모든 필드가 optional이거든요.

```tsx
type TSentryDataCollection = NonNullable<NonNullable<Parameters<typeof init>[0]>['dataCollection']>;

type TClosedDataCollection = Required<Omit<TSentryDataCollection, 'queryParams'>> & {
  httpHeaders: Required<NonNullable<TSentryDataCollection['httpHeaders']>>;
  graphQL: Required<NonNullable<TSentryDataCollection['graphQL']>>;
  genAI: Required<NonNullable<TSentryDataCollection['genAI']>>;
};
```

optional을 걷어내면 SDK가 새 수집 항목을 추가하는 순간 타입 검사가 실패해요. 그때 새 항목을 수집할지 닫을지 정해야 다시 빌드할 수 있어요.

타입만으로는 값을 true로 잘못 적은 경우까지 잡지 못해요. 그래서 테스트에서 전체 객체를 toEqual로 비교해 키가 빠지거나 값이 열리는 경우를 함께 막았어요.

타입은 **새 키를 놓치는 경우**를, 테스트는 **열린 값을 넣는 경우**를 잡아요.

## breadcrumb은 dataCollection이 걸러 주지 않았어요

헤더와 쿠키를 막은 뒤에도 토큰이 나가는 경로가 하나 더 있었어요. 이번에는 오류 이벤트가 아니라 breadcrumb이었는데요.

dataCollection은 SDK가 자동으로 수집하는 request data에 적용돼요. breadcrumb은 그 바깥이에요. console breadcrumb에는 인자로 넘긴 값이 그대로 들어가는데, 코드베이스에 axios 오류 객체를 console.error로 넘기는 곳이 있었어요. 그 객체의 config.headers에 인증 정보가 들어 있었고요.

console breadcrumb은 통째로 버렸어요. 같은 오류는 이벤트로 따로 수집하니 console 인자를 다시 보낼 필요가 없었어요.

fetch, xhr, history breadcrumb은 URL의 쿼리와 해시를 지웠어요. Node의 http breadcrumb은 쿼리를 http.query라는 별도 키에도 넣어서 그 값도 삭제했고요.

```typescript
export function sanitizeBreadcrumb(breadcrumb: Breadcrumb): Breadcrumb | null {
  if (breadcrumb.category === 'console') return null;
  if (!breadcrumb.data) return breadcrumb;

  const data = { ...breadcrumb.data };

  ['url', 'from', 'to'].forEach((key) => {
    const value = data[key];

    if (typeof value === 'string') {
      data[key] = stripUrlParams(value);
    }
  });

  delete data['http.query'];
  delete data['url.query'];
  delete data['http.fragment'];

  return { ...breadcrumb, data };
}
```

여기서 한 가지가 더 드러났어요. **애플리케이션이 직접 context에 넣는 값은 자동 수집 차단 대상이 아니에요.**

- 화면 위치는 location.href가 아니라 pathname만 써요.
- API URL은 쿼리와 해시를 지워요.
- 숫자, UUID 경로는 :id로 접어 개인정보와 이슈 그룹 폭증을 함께 막아요.
- OAuth callback의 code, state, 검색 조건, 회원 식별자가 URL에 남지 않게 했어요.

## URL과 본문은 읽는 단계와 전송 직전 두 곳에서 닫았어요

수집 항목을 제한한 뒤에는 에이전트 코드리뷰와 SDK 소스 검토로 URL과 본문이 처리되는 경로를 더 확인했어요. 같은 요청 정보라도 필드와 통합에 따라 옵션이 적용되는 범위가 달랐어요.

- urlQueryParams: false가 끄는 건 event.request.query\_string 필드뿐이었어요. URL 본체는 SDK가 항상 싣게 돼 있어 쿼리를 단 채로 나갔어요.
- 브라우저에는 이 옵션을 적용하는 통합 자체가 없었어요. 기본 통합이 location.href 전체와 Referer를 모든 이벤트와 pageload transaction에 실었어요.
- httpBodies: \[\]로는 요청 본문이 막히지 않았어요. Node의 httpIntegration은 이 값과 상관없이 기본값 'medium'으로 들어오는 요청 본문을 읽어 스코프에 올리고, 요청 정보를 이벤트에 싣는 쪽은 스코프에 있는 본문을 그대로 붙였어요. 본인인증 콜백 같은 POST 본문이 이슈에 남을 수 있는 구조였어요.

그래서 자동 수집 설정과 별개로 읽는 단계와 전송 직전, 두 곳에서 다시 닫았어요. Node에서는 먼저 본문을 읽지 않도록 했어요.

```text
Sentry.httpIntegration({
  disableIncomingRequestSpans: true,
  maxIncomingRequestBodySize: 'none',
});
```

disableIncomingRequestSpans도 함께 넘겨야 했어요. 직접 넘긴 httpIntegration이 @sentry/nextjs가 기본으로 넣는 같은 이름의 Http 통합을 통째로 대체하는데, 그 기본 통합이 바로 이 값을 켜 둔 것이었거든요. 이 값을 빠뜨리면 Next.js와 Sentry가 같은 incoming request span을 두 번 만들어요.

읽는 단계에서 막은 뒤에도 전송 직전에 한 번 더 지웠어요.

```text
Sentry.init({
  beforeBreadcrumb: sanitizeBreadcrumb,
  beforeSend: sanitizeEvent,
  beforeSendTransaction: sanitizeEvent,
  beforeSendSpan: sanitizeSpan,
  dataCollection: SENTRY_DATA_COLLECTION,
});
```

민감 정보는 두 겹으로 닫아요. 읽는 단계에서는 dataCollection과 httpIntegration 옵션으로 수집을 막고, 전송 직전에는 beforeSend 계열 훅이 옵션으로 막히지 않는 URL, Referer, span 속성을 지우고, 옵션이 이미 막은 쿠키, 본문도 한 번 더 지워요. 옵션 한 줄이 바뀌거나 SDK가 새 경로를 열어도 토큰과 회원 정보가 곧바로 나가지 않게 하려는 거예요. 대신 정화 함수는 알고 있는 키만 지우기 때문에, SDK를 올릴 때마다 새 URL, span 속성을 다시 확인하는 비용을 받아들였어요.

sanitizeEvent는 다음을 처리해요.

- event.request.url의 쿼리, 해시 제거
- query\_string, cookies, data 삭제
- 대소문자와 관계없이 Referer의 쿼리 제거
- trace와 child span 속성 정리

URL은 한 가지 키로만 오지 않았어요.

```typescript
const URL_ATTRIBUTE_KEYS = ['url', 'url.full', 'http.url', 'http.target', 'http.request.header.referer'];

const QUERY_DATA_KEYS = ['http.query', 'url.query', 'http.fragment'];
```

특히 plain url이 마지막까지 남았어요. fetch, xhr 계측은 정리한 URL을 http.url이나 url.full에 넣으면서, 별도 url 속성에는 정리하지 않은 원본을 넣는데요. 이 앱의 API 호출은 axios(xhr)로 나가서, 쿼리가 붙은 호출은 전부 이 키에 원본 쿼리를 남겼어요.

처음에는 나머지 네 키만 닦고 있었어요. url을 목록에 넣기 전까지는 정화한 URL과 원본 URL이 같은 span에 나란히 실렸어요.

INP처럼 transaction에 속하지 않고 따로 전송되는 span은 beforeSendTransaction을 거치지 않아요. 그래서 같은 속성 정화를 beforeSendSpan에도 연결했어요.

## 정책과 배선은 테스트로 고정했어요

개인정보 정화 함수만 테스트해서는 부족했어요. 함수가 맞더라도 Sentry.init에 연결하지 않으면 원본이 그대로 나가니까요. 테스트를 세 층으로 나눴어요.

1. **정책 객체**: dataCollection의 모든 키와 값이 닫혀 있는지 전체 비교
2. **정화 함수**: URL, 본문, 쿠키, Referer, breadcrumb, span 속성 처리
3. **초기화 배선**: client, server, edge 모두에 정책과 훅이 실제로 전달되는지 확인

SDK가 수집 키를 추가하면 타입 검사가, 정책 값이나 배선이 바뀌면 단위 테스트가 먼저 깨지게 했어요. SDK가 새 URL, span 속성을 추가하는 경우는 이 테스트로 잡히지 않아서, SDK를 올릴 때 직접 확인해야 해요.

## Web Vitals는 실제 Sentry envelope까지 확인했어요

브라우저에서는 browserTracingIntegration이 LCP, CLS, TTFB, FCP를 pageload transaction의 measurement로 보내요. 프로덕션 trace는 20%를 수집하고, 전송을 확인하는 배포에서는 전부 수집해요.

처음에는 기본 idleTimeout 1초를 썼는데요. 실제 수집분을 보니 LCP가 없는 pageload transaction의 지속시간 p50은 728ms였고, LCP가 실린 쪽은 2.3초였어요. transaction이 지표보다 먼저 닫히는 경우가 있다고 판단해 대기 창을 3초로 늘렸어요.

```typescript
export const SENTRY_IDLE_TIMEOUT = 3_000;
```

이 값을 늘려도 기록되는 transaction duration이 3초 늘어나지는 않아요. SDK가 idle span의 종료 시각을 마지막 child span의 끝으로 다시 자르기 때문에, Web Vitals를 기다리는 시간과 전송 시점만 달라져요.

단위 테스트로는 browserTracingIntegration, 활성화 게이트, 샘플링을 모두 지난 payload가 실제로 나가는지 알 수 없었어요. 그래서 별도의 Playwright 실행 경로를 만들었어요.

```bash
npm run test:e2e:sentry
```

테스트에서는 Sentry의 envelope 요청을 page.route로 가로채고, 실제 서버에는 보내지 않은 채 transaction payload를 읽어요. pageload transaction에 fcp, lcp, ttfb measurement가 실렸는지 확인하는데요.

MSW 서비스 워커가 요청을 넘겨받으면 page.route가 envelope를 잡지 못해서, 이 E2E 컨텍스트에서는 서비스 워커도 막았어요. 응답을 주지 않으면 SDK가 재시도하므로 가짜 성공 응답까지 돌려줘요.

즉 이 테스트는 옵션 객체를 검사하는 게 아니에요.

```text
브라우저 진입
  → browserTracingIntegration
  → pageload transaction 종료
  → Sentry envelope 생성
  → measurement 포함 여부 확인
```

브라우저에서 envelope가 나가기까지의 경로를 검증해요. Sentry 서버가 그걸 저장하는지는 또 다른 문제였어요.

## INP는 앱이 보내도 서버가 저장하지 않았어요

여기에는 중요한 한계가 있었어요. 지금 SDK에서 INP는 pageload transaction의 measurement가 아니라 standalone span으로 전송돼요.

사내 Sentry 환경에서는 span ingestion이 꺼져 있어 dataset=spans가 비어 있었어요. 그래서 INP가 저장되지 않았고, Insights의 Web Vitals 화면도 비어 보였는데요. 지금은 Discover에서 transaction dataset과 transaction.op:pageload를 기준으로 LCP, CLS, TTFB, FCP를 확인해요.

지표를 수집하는 연결은 확인했지만, 제품별로 어떤 값부터 개선할지 판단하는 임계값과 알림 기준은 따로 정해야 해요. 수집 설정만으로 성능 개선 기준까지 마련된 것은 아니에요.

이 문제는 beforeSendSpan을 추가하거나 SDK 옵션을 바꾼다고 풀리지 않아요. 앱은 span을 보내고 있지만 지금 서버 설정에서 저장하지 않는 상태라, 서버의 span ingestion 설정을 따로 확인해야 해요.

그래서 지금 구성을 두고 "Core Web Vitals 전체를 운영하고 있다"고 말하지 않아요.

## 사내 Sentry를 에이전트가 조회하도록 MCP를 붙였어요

대시보드를 사람이 직접 열어 보는 것만으로는 코드 작업과 이슈 조사가 따로 놀았어요. 에이전트가 실제 이슈, transaction, 프로젝트 설정을 읽고 코드와 대조할 수 있도록 Sentry MCP를 저장소에 연결했어요.

@sentry/mcp-server를 stdio로 실행하고 사내 Sentry 주소를 --host로 넘겼어요.

```json
{
  "mcpServers": {
    "sentry": {
      "command": "npx",
      "args": ["-y", "@sentry/mcp-server@latest", "--host=sentry.example.com", "--disable-skills=seer"],
      "env": {
        "SENTRY_ACCESS_TOKEN": "${SENTRY_ACCESS_TOKEN}"
      }
    }
  }
}
```

사내 환경에서 쓸 수 없는 Seer 관련 도구는 껐어요. 토큰 값은 저장소에 넣지 않고 환경 변수 이름만 참조했어요.

여기서도 설정 파일이 맞는다고 끝나지 않았어요. Claude Code는 $&#123;SENTRY\_ACCESS\_TOKEN&#125;을 자기 프로세스 환경에서 치환해요. Bash 도구에만 적용되는 로컬 설정에 값을 넣으면 터미널의 curl은 성공하는데 MCP 호출만 인증에 실패했고, .env.local은 Claude Code가 아예 읽지 않았어요. 셸 시작 환경에 토큰을 두고 Claude Code를 다시 시작해야 반영됐어요.

MCP용 토큰과 소스맵 업로드용 토큰도 나눴어요.

- **MCP 토큰**: 이슈, 이벤트, 프로젝트를 조회하는 user auth token
- **빌드 토큰**: 릴리스와 소스맵 artifact를 올리는 org token

MCP 토큰에는 project:releases 권한이 없어 빌드 업로드에 다시 쓸 수 없었어요. 같은 Sentry 토큰처럼 보여도 목적과 권한이 달랐어요.

MCP를 붙인 뒤에는 코드만 보고 "수집될 것"이라고 추정하지 않고, 실제 transaction dataset과 이슈 payload를 확인하며 설정을 고칠 수 있었어요. INP가 앱에서 빠진 게 아니라 서버의 span 저장 단계에서 사라진다는 판단도 이 과정에서 가려냈어요.

## 릴리스와 소스맵은 빌드 결과로 확인했어요

minify된 스택을 원본 코드로 연결하려면 소스맵 artifact가 실제 Sentry 프로젝트에 올라가야 해요. withSentryConfig에 사내 Sentry 주소와 조직, 프로젝트, 빌드 토큰을 연결했어요.

```typescript
withSentryConfig(nextConfig, {
  sentryUrl: '<https://sentry.example.com/>',
  org: 'example',
  project: 'web',
  authToken: process.env.SENTRY_AUTH_TOKEN,
  telemetry: false,
  widenClientFileUpload: true,
  sourcemaps: {
    disable: !process.env.SENTRY_AUTH_TOKEN,
    deleteSourcemapsAfterUpload: true,
  },
  errorHandler: (error) => {
    console.warn('[sentry] 소스맵 업로드 실패:', error.message);
  },
});
```

도입하고 8일 동안은 이 설정이 있었는데도 소스맵이 한 번도 올라가지 않았어요. 배포 워크플로 세 개 어디에도 빌드 토큰이 없어서 sourcemaps.disable이 늘 참이었고, 그동안 쌓인 이슈의 스택은 전부 minify 상태였어요. 코드에 설정이 있다는 것과 배포 빌드에서 실행됐다는 건 다른 문제였어요.

Turbopack 빌드라서 처음에는 업로드가 동작하지 않는다고 생각했어요. 하지만 @sentry/nextjs 10.70은 Turbopack에서 production compile 이후 실행되는 훅으로 소스맵을 올려요. debug ID는 Next.js 16이 직접 만들고, Sentry는 그 ID를 기준으로 artifact bundle과 배포 파일을 연결해요.

토큰이 **있는지**만 확인해서는 부족했어요.

- 만료되거나 권한이 없는 토큰도 문자열은 있으니 업로드 단계에 들어가요.
- 업로드가 401로 실패해도 errorHandler가 경고만 남기면 빌드는 성공할 수 있어요.
- deleteSourcemapsAfterUpload: true는 업로드에 실패한 경우에도 로컬 산출물의 소스맵을 지울 수 있어요.

그러면 "Sentry에도 없고 배포 산출물에도 없는" 상태가 조용히 만들어질 수 있어요. 그래서 빌드 성공 여부가 아니라, sentry-cli로 릴리스 접근 권한을 확인하고 Sentry API에서 artifact bundle이 실제로 생겼는지를 따로 확인했어요.

서버 소스맵은 올리지 않기로 했어요. Turbopack은 .next/server에 소스맵을 항상 남기는데, 당시 빌드 기준으로 이 파일이 1,000개를 넘어 사내 Sentry가 업로드에 502를 냈고, 용량도 .next 199MB의 절반을 차지했어요. Sentry의 업로드보다 먼저 도는 빌드 훅에서 서버 소스맵을 지워 브라우저 소스맵만 올라가게 했더니, 같은 빌드에서 .next가 93MB로 줄었고 업로드도 502 없이 끝났어요. 대신 서버 쪽 스택은 minify된 채로 남아요.

릴리스 연결의 완료 조건은 next build가 성공한 게 아니라, 배포된 오류의 debug ID와 Sentry artifact가 실제로 맞물리는 거예요.

## 에러 레벨은 상태 코드가 아니라 사용자 영향으로 정했어요

여기까지가 무엇을 보내지 않을지와, 보낸 것이 실제로 닿는지를 확인한 일이었어요. 남은 건 모인 오류 중 무엇에 먼저 움직일지였어요.

이 기준의 출발점은 이전 회사에서 Sentry를 운영했던 경험과 우아한형제들의 [「선제적 장애 대응을 위한 Sentry 최적화 적용기」](https://techblog.woowahan.com/21604/)였어요. 이전 회사에서는 브라우저 확장 프로그램, Service Worker, 네트워크 환경에서 반복되는 오류와, 이미 비즈니스 흐름에서 처리한 API 오류를 ignoreErrors, denyUrls, beforeSend로 선별하고 개발, 테스트 실행의 이벤트가 전송되지 않게 관리했어요. 모든 오류를 모으는 것보다 사용자에게 영향을 주는 오류를 놓치지 않는 게 중요하다는 걸 이때 배웠어요.

우아한형제들의 글은 과도한 오류가 수집 한도를 소진해 정작 중요한 장애 로그가 누락된 경험에서 출발해, 서비스 영향도에 따른 레벨, 불필요한 오류 필터링, 알림과 담당 절차를 함께 설계해요. 구현을 그대로 가져오지는 않았어요. 두 경험의 문제의식을 이 앱의 Next.js 런타임, 개인정보, 배포 환경에 맞게 다시 해석했어요.

처음에는 4xx와 5xx만으로 심각도를 나누려 했어요. 그런데 같은 500이라도 사용자가 겪는 결과는 요청의 역할에 따라 달랐어요.

| 요청 | 5xx | 4xx |
| --- | --- | --- |
| GET: 화면을 채우는 호출 | fatal | error |
| 그 외: 사용자가 다시 시도할 수 있는 호출 | error | warning |

이 앱에서는 화면을 채우는 조회가 막힌 경우와 화면이 남아 있어 다시 시도할 수 있는 경우를 나누려고 이 기본 분류를 정했어요. 메서드만으로 영향을 모두 알 수는 없어서 핵심 동작이 막히거나 대체 흐름이 있는지는 별도로 봐요.

- fatal: 화면이 뜨지 않거나 핵심 조회 결과를 쓸 수 없는 경우
- error: 화면은 남아 있지만 사용자가 하려던 작업이 막힌 경우
- warning: 예상 가능한 실패이며 다시 시도하거나 대체 흐름으로 넘어갈 수 있는 경우

401도 전부 같은 방식으로 다루지 않았어요. 액세스 토큰 갱신으로 복구된 401은 보내지 않고, 토큰 갱신 요청 자체가 실패한 경우는 별도 fingerprint로 남겼는데요. 갱신 토큰이 수명대로 만료된 401은 돌아오는 사용자마다 나는 정상적인 세션 종료라 warning, 그 밖의 갱신 실패는 error로 나눴어요.

에러 레벨은 개발자가 느끼는 심각도가 아니라 사용자가 잃은 기능과 복구 가능성을 나타내도록 했어요.

## 회원 id 하나만 붙였어요

영향받은 사용자 수를 알아야 한 명의 특이 사례와 여러 명이 겪는 장애를 나눠 우선순위를 정할 수 있어요. 그래서 브라우저 이슈에 회원 id 하나만 붙였어요. 이름, 이메일, 전화번호는 넣지 않았고, IP는 dataCollection의 userInfo: false로 SDK 쪽에서 막았어요.

서버 렌더에는 사용자를 붙이지 않았어요. 요청 스코프와 캐시된 렌더의 수명이 어긋나면 다른 요청의 이슈에 이전 사용자의 id가 남을 수 있거든요.

컴포넌트가 SDK의 setUser를 직접 부르지도 않아요. 공용 setSentryUser가 전송 게이트와 싣는 사용자 필드를 함께 관리해요.

## 고칠 수 없는 잡음은 발생 지점에서 표본만 남겼어요

개인정보 경로를 막고 나니 위치 조회 실패가 이슈 목록 위쪽을 채웠어요. 권한 거부는 사용자의 선택이라 보내지 않고, 위치 소스 없음과 시간 초과는 기기, 주변 환경의 영향이 커서 10%만 남겼는데요. 완전히 끄면 급증해도 알아챌 방법이 없어서 표본은 남겼어요.

오류 코드가 없는 실패는 전부 남겼어요. 앱 브리지 reject나 navigator.geolocation 부재처럼 우리 코드가 깨졌다는 신호일 수 있거든요.

처음에는 위치 조회 실패를 ignoreErrors로 거르려 했어요. 하지만 무시 목록은 메시지가 맞으면 버리는 것밖에 못 해서, 코드 2, 3은 표본만 남기고 코드가 없는 실패는 전부 남기는 규칙을 표현할 수 없었어요. 그래서 원본의 code를 볼 수 있는 위치 조회 코드에서 표본 여부를 정하고, fingerprint에는 오류 코드를 넣었어요.

이슈 제목도 문제였어요. GeolocationPositionError는 Error도 Event도 아니어서 SDK가 스택 없는 synthetic 예외로 보내고, 목록에는 제목이 &lt;unknown>으로 떴어요. 읽히는 이름의 Error로 감싸고 원본은 cause로 붙였어요. fingerprint는 그대로 둬서 기존 이슈 그룹은 갈리지 않았어요.

## 전송 게이트로 의미 없는 트래픽을 줄였어요

이전 회사에서는 NODE\_ENV를 기준으로 개발, 테스트 이벤트를 뺐어요. 단순하고 효과적이었지만, 로컬에서 실제 전송을 검증하거나 프로덕션 빌드로 E2E를 돌리는 것처럼 환경 이름과 수집 목적이 어긋나는 경우를 세밀하게 표현하긴 어려웠어요.

이번에도 개발 중 콘솔로 이미 볼 수 있는 오류까지 보내면 수집 트래픽과 이슈 잡음만 늘어 실제 사용자 문제를 찾기 어렵다는 원칙은 그대로 뒀어요. 대신 실행 목적에 따라 전송 여부를 명시적으로 고르는 게이트를 만들었어요.

DSN이 있더라도 NEXT\_PUBLIC\_SENTRY\_ENABLED가 false면 SDK 전체가 꺼져요.

```typescript
export const IS_SENTRY_ENABLED = Boolean(SENTRY_DSN) && SENTRY_ENABLED !== 'false';
```

- 실제 사용자 오류를 수집하거나 전송 흐름을 확인해야 하는 배포에서는 켜요.
- 상시 수집할 가치가 적은 development 배포와 일반 로컬 실행은 기본으로 꺼요.
- dev, dev:mock, build:e2e는 기본값을 false로 두어 테스트, 개발 트래픽이 저장소를 쓰지 않게 해요.
- Sentry 전송 자체를 확인하는 E2E나 로컬 연동 점검에서는 명시적으로 true를 줘서 다시 켤 수 있어요.

환경 변수 하나로 가르기로 한 직후에는 로컬을 끄는 값을 git에 올라가지 않는 .env.local에 두게 했는데요. 그 줄이 없는 새 클론이나 worktree는 당시 true였던 .env.development를 읽어 development 이슈에 로컬 이벤트를 섞게 돼 있었어요. 그래서 같은 날 기본값을 실행 스크립트에 고정했어요. 이제 새 클론이나 worktree에서도 기본값은 꺼져 있고, 필요할 때만 의도적으로 켤 수 있어요.

## 이 체계가 먼저 알려 준 문제도 있었어요

Bottom Sheet를 드래그하다 놓으면 화면이 죽는 오류는 조사 당시 17명에게서 23건이 잡혔고(운영 배포 전까지 누적 57명 이상, 75건), 라이브러리 소스까지 따라가 원인 경로가 없는 버전으로 올렸어요.

응답 타입을 Zod 스키마에서 파생하며 null 허용 범위를 좁혔을 때는, 머지 전에 프로덕션 Sentry에 이미 쌓여 있던 스키마 불일치 33건과 대조해 서버가 실제로 null을 주는 자리를 찾아 되돌렸어요. dev 응답 12건에서는 전부 채워져 있던 필드가 프로덕션에서는 200건 중 27건이 null이었거든요. 그대로 배포했다면 화면은 멀쩡한 채 정상 응답마다 스키마 불일치 경고가 새로 쌓여 진짜 문제를 가렸을 거예요.

Sentry 워터폴을 보다가 메인 배너 링크가 뷰포트에 들어오는 것만으로 여러 라우트를 prefetch하는 것도 발견했어요. 해당 링크의 prefetch를 끄고 요청이 사라진 것은 확인했지만, Web Vitals가 얼마나 나아졌는지는 측정하지 않았어요. 성능 개선 수치가 아니라, 측정 환경이 불필요한 네트워크 작업을 찾게 해 준 사례로만 남겨요.
