After editing an applicant's memo, I searched the entire repository for strings to find the queries that needed updating. Only the first element of each query key came from an enum. Each call site appended its own detail ID and memo hierarchy. I moved these definitions together so the query function and invalidation scope could be found in the same place.

```text
enum CandidateQueryKey {
  Detail = 'CandidateDetail',
}

useQuery([CandidateQueryKey.Detail, 'detail', candidateId, 'memos'], fetchMemos);
```

There were four recurring problems.

- String order could differ between call sites.
- Finding a mutation's invalidation scope required searching the code.
- An API parameter change required separate changes to the query key and `queryFn`.
- Mutations wrapped API functions in lambdas that redeclared their argument types, leaving the same signature in two places.

> These examples use TanStack Query v4 and @lukemorales/query-key-factory 1.3.x. They are shortened versions of actual code with names changed. In v5, most APIs, including useQuery and invalidateQueries as well as useMutation, removed positional overloads and accept only objects. The invalidateQueries(queryKey) calls here use v4 syntax; v5 requires `{ queryKey }`. The mutation section includes both versions.

## Each caller defined the hierarchy after the enum

The issue was the hierarchy and parameters appended independently at each call site. Centralizing key creation does not necessarily require a library. A function returning both an array and a `queryFn` can also reduce scattered string combinations.

These were the options.

| Approach | Benefit | Remaining cost |
| --- | --- | --- |
| Enum plus arrays assembled at call sites | No extra dependency; arrays are directly readable | Hierarchy, argument order, and invalidation scopes must agree across callers |
| Custom key and query-options functions | Central definitions tailored to the product | Shared prefixes, child hierarchy generation, and types must be maintained manually |
| Query Key Factory | Consistent prefixes and child queries through _def and _ctx | Learning the definition syntax and maintaining a dependency and its use at call sites |

## Define the key and queryFn together

I chose Query Key Factory's hierarchy generation. The keys and query functions moved to a shared package consumed by several apps. Callers assembled fewer strings, but now needed to know the factory's return structure. A product with few queries and simple invalidation scopes could achieve the same purpose with custom functions.

```typescript
import { createQueryKeys } from '@lukemorales/query-key-factory';

export const candidateCollectionKeys = createQueryKeys('CandidateCollection', {
  list: (params?: CandidateListParams) => ({
    queryKey: [params],
    queryFn: () => candidateApi.getList(params),
  }),
  config: {
    queryKey: null,
    queryFn: candidateApi.getConfig,
  },
});
```

`list` creates both the key and `queryFn` from one argument. A parameter change is handled in that one definition.

Passing a method reference such as `candidateApi.getConfig` directly requires care. It must work without `this` binding and must not use its first argument. A `queryFn` receives `QueryFunctionContext` first, so a function with an optional argument would receive that context object there.

Expanding the factory's `_def` shows the invalidation scope.

```text
candidateCollectionKeys._def;
// ['CandidateCollection']

candidateCollectionKeys.list._def;
// ['CandidateCollection', 'list']

candidateCollectionKeys.list({ page: 1 }).queryKey;
// ['CandidateCollection', 'list', { page: 1 }]

candidateCollectionKeys.config.queryKey;
// ['CandidateCollection', 'config']
```

Fixed queries such as `config` and parameterized queries such as `list` have different definition shapes.

## Group detail subqueries with contextQueries

Applicant details had many queries sharing a `candidateId`, including memos, history, and messages.

```typescript
export const candidateDetailKeys = createQueryKeys('CandidateDetail', {
  detail: (candidateId: number) => ({
    queryKey: [candidateId],
    queryFn: () => candidateApi.getDetail(candidateId),
    contextQueries: {
      memos: {
        queryKey: null,
        queryFn: () => candidateApi.getMemos(candidateId),
      },
      histories: {
        queryKey: null,
        queryFn: () => candidateApi.getHistories(candidateId),
      },
    },
  }),
});
```

The same definition provides both the options passed to `useQuery` and the key used for invalidation.

```typescript
const detail = candidateDetailKeys.detail(candidateId);

useQuery(detail);
useQuery(detail._ctx.memos);

queryClient.invalidateQueries(detail.queryKey); // 상세·메모·이력 전부
queryClient.invalidateQueries(detail._ctx.memos.queryKey); // 메모만
```

These scopes overlap. `detail.queryKey` is `['CandidateDetail', 'detail', candidateId]`; `_ctx.memos.queryKey` appends `'memos'`. By default, `invalidateQueries` invalidates queries matching that prefix. Invalidating the detail therefore also invalidates memos and history. To target memos alone, pass `_ctx.memos.queryKey`.

The same principle lets `_def` invalidate everything under `list` rather than one specific ID.

```text
queryClient.invalidateQueries(candidateCollectionKeys.list._def);
```

## Grouping queries also broadens invalidation

Putting details and memos in one hierarchy makes related data easier to find and invalidate together. It also means `detail.queryKey` targets unchanged history. Active queries refetch in the background by default, while inactive ones are marked stale. They do not all issue a network request immediately. [TanStack Query invalidation behavior](https://tanstack.com/query/v4/docs/framework/react/guides/query-invalidation)

A change affecting the detail summary can use the detail scope. A memo-only change can use `_ctx.memos.queryKey`. To invalidate the detail itself while preserving its children:

```text
// TanStack Query v4에서도 객체 형식을 쓸 수 있어요.
queryClient.invalidateQueries({
  queryKey: detail.queryKey,
  exact: true,
});
```

Broad invalidation reduces the chance of forgetting related data but expands refetching. Narrow invalidation reduces requests but requires deciding which data the mutation affects. `contextQueries` provides a key hierarchy; it cannot decide whether editing a memo changes a summary or list. I therefore kept invalidation decisions close to each mutation.

## Pass the API function directly to a mutation

Previously, lambdas such as `(body: CreateReviewBody) => candidateReviewApi.create(body)` repeated the API argument type. When the mutation and API accept the same input, that intermediate lambda is unnecessary.

```typescript
// TanStack Query v4
const createReview = useMutation(candidateReviewApi.create, {
  onSuccess: (_review, { candidateId }) => {
    queryClient.invalidateQueries(
      candidateDetailKeys.detail(candidateId).queryKey,
    );
  },
});
```

TanStack Query v5 uses the object form, including `{ queryKey }` for invalidation.

```typescript
// TanStack Query v5
const createReview = useMutation({
  mutationFn: candidateReviewApi.create,
  onSuccess: (_review, { candidateId }) => {
    queryClient.invalidateQueries({
      queryKey: candidateDetailKeys.detail(candidateId).queryKey,
    });
  },
});
```

This removed a duplicated function signature. With a typed lambda, mutation variables are inferred from the lambda's annotation. Passing the API function directly infers variables from that function, including `candidateId` in `onSuccess`. Changing API parameters then produces type errors at incompatible `mutate()` calls. The API function must still work without `this` binding.

I centralized query functions and key hierarchy through the library, accepting that callers need `_def` and `_ctx`. Mutations remain outside the factory, with invalidation scopes nearby. Hierarchy generation is shared; deciding which data changes together remains with the mutation.

## Migration rules and the factory's limits

- Even callers needing only a key use the factory's `queryKey` or `_def`, rather than constructing arrays themselves.
- Parameter objects contain serializable values before entering query keys.
- I assess the migration by whether one definition owns a resource's key shape, rather than file counts or lines changed.

Inferred return types cannot ensure that every variable affecting a request appears in the key. If `queryFn` uses a new sort condition omitted from the key, different results share a cache. Changes to query inputs and keys still need to be reviewed together. [TanStack Query key guidelines](https://tanstack.com/query/v4/docs/framework/react/guides/query-keys)

Generated arrays must also be compared with the old arrays. Changing strings or their order can point callers at another cache; changing a prefix changes invalidation targets. These examples retain the arrays and move only their construction.

## Making the invalidation scope visible

The four initial problems changed as follows.

| Before | Change | After |
| --- | --- | --- |
| Callers could disagree on string order | The factory generates the array | Order is defined in one place |
| Invalidation scope required a search | _def and _ctx expose hierarchy | Code shows whether a memo edit refreshes the detail or only memos |
| API parameters required separate key and queryFn changes | One definition creates both | One place to edit |
| Mutation lambdas redeclared API input types | Pass the API function directly | Incompatible mutate() callers fail type checking after an API change |

Shorter call sites were a minor benefit. The memo key array above is identical to the old one, element for element. The practical gain was finding the query function and invalidation scope in the same hierarchy without searching for strings.

## Compare the built-in helper in v5

For a new v5 implementation, `queryOptions` is another option. It defines a query key, function, and inferred types together for reuse. It avoids a separate key-factory dependency, but key arrays and invalidation prefixes still need to be designed manually. It does not generate `_def` and `_ctx` hierarchies. [TanStack Query Query Options](https://tanstack.com/query/latest/docs/framework/react/guides/query-options)

The built-in helper may suffice for sharing definitions. If several apps need the same generated key hierarchy, the factory's conventions are worth comparing too.
