[Electron 수집 앱](/ko/blog/nestjs의-책임-분리를-참고해-electron-수집-앱을-나눈-기준)에 비밀번호가 걸린 파일을 내려받는 단계가 있었어요. 이 앱은 Puppeteer로 브라우저를 조작하는데, Puppeteer에서는 페이지가 주고받는 네트워크도 이벤트로 볼 수 있어요. `page.on('request', 콜백)`을 걸면 페이지가 요청을 보낼 때마다, `page.on('response', 콜백)`을 걸면 응답을 받을 때마다 콜백이 불려요.

이 단계에서는 페이지를 새로 불러온 뒤 네트워크 이벤트에서 정보를 꺼내야 했어요. request에서는 다음 API 호출에 쓸 헤더를 얻고, response에서는 내려받은 파일을 여는 데 필요한 값을 얻어요. 어느 한쪽만으로는 다음 작업으로 넘어갈 수 없었어요.

콜백은 이벤트가 생길 때마다 불리는 코드이고, 수집 코드는 값이 준비될 때까지 기다렸다가 다음 줄로 넘어가야 해요. 이 둘을 잇는 방법이 문제였어요. 처음 코드는 콜백이 외부 변수를 채우고, 그 변수를 1초마다 확인했어요.

```typescript
let result: PreInfo | undefined;

page.on('request', (request) => {
  result = readRequest(request);
});

await page.reload();

while (result === undefined) {
  await delay(1_000);
}
```

동작은 했지만 결과를 받는 것과 기다림을 끝내는 것이 떨어져 있어요. 원하는 이벤트가 오지 않으면 while문에서 계속 기다리고, 리스너를 떼는 코드가 없으니 함수를 다시 부를 때마다 이전에 등록한 리스너까지 남아요. request와 response가 같은 변수를 쓰면 뒤에 도착한 값이 앞의 값을 덮을 수도 있어요.

완료 조건을 `if (result)`로 둘 수도 없어요. 0이나 false, 빈 문자열도 유효한 결과일 수 있으니까요. 값을 받지 못한 상태는 `undefined`로 구분해요. 새로고침 뒤에 리스너를 등록하면 빠르게 지나간 이벤트를 놓칠 수 있으니 등록이 먼저예요.

## 이벤트가 오면 Promise를 끝내요

Promise는 `resolve`나 `reject`가 불릴 때 한 번 끝나는 값이에요. 이벤트 콜백 안에서 `resolve`를 부르면, 호출하는 쪽은 `await` 한 줄로 이벤트가 올 때까지 기다릴 수 있어요. while문과 외부 변수를 없애고 기다리는 일을 Promise 하나로 묶은 뒤, 성공과 실패, 시간 초과 어느 경로로 끝나든 리스너를 해제하도록 바꿨어요.

```tsx
import type { HTTPRequest, HTTPResponse, Page } from 'puppeteer';

type MaybePromise<T> = T | Promise<T>;

interface WaitForPreInfoOptions<T> {
  page: Page;
  timeoutMs?: number;
  onRequest?: (request: HTTPRequest) => MaybePromise<T | undefined>;
  onResponse?: (response: HTTPResponse) => MaybePromise<T | undefined>;
}

export function waitForPreInfo<T>({
  page,
  timeoutMs = 10_000,
  onRequest,
  onResponse,
}: WaitForPreInfoOptions<T>): Promise<T> {
  return new Promise<T>((resolve, reject) => {
    let settled = false;
    let timer: ReturnType<typeof setTimeout> | undefined;

    const cleanup = () => {
      if (timer) clearTimeout(timer);
      page.off('request', handleRequest);
      page.off('response', handleResponse);
    };

    const finish = (value: T) => {
      if (settled) return;
      settled = true;
      cleanup();
      resolve(value);
    };

    const fail = (error: unknown) => {
      if (settled) return;
      settled = true;
      cleanup();
      reject(error);
    };

    const consume = async (read: () => MaybePromise<T | undefined>) => {
      try {
        const value = await read();
        if (value !== undefined) finish(value);
      } catch (error) {
        fail(error);
      }
    };

    const handleRequest = (request: HTTPRequest) => {
      if (onRequest) void consume(() => onRequest(request));
    };

    const handleResponse = (response: HTTPResponse) => {
      if (onResponse) void consume(() => onResponse(response));
    };

    page.on('request', handleRequest);
    page.on('response', handleResponse);

    timer = setTimeout(() => {
      fail(new Error(`필요한 네트워크 정보를 ${timeoutMs}ms 안에 찾지 못했습니다.`));
    }, timeoutMs);

    void page.reload({ waitUntil: 'networkidle2' }).catch(fail);
  });
}
```

콜백이 `undefined`를 돌려주면 아직 기다려야 한다는 뜻이에요. 다른 값을 받으면 `finish`가 Promise를 완료하고 request와 response 리스너를 함께 해제해요. `page.off`에는 등록할 때 넘긴 함수를 그대로 줘야 하므로 `handleRequest`와 `handleResponse`를 변수로 뒀어요. 비동기 결과가 뒤늦게 더 도착해도 `settled`가 이미 끝난 Promise를 다시 처리하지 못하게 막아요.

콜백은 `consume` 안에서 호출해요. 처음 공개한 예제는 호출 결과를 넘기는 형태였어요.

```tsx
const consume = async (result: MaybePromise<T | undefined>) => {
  try {
    const value = await result;
    if (value !== undefined) finish(value);
  } catch (error) {
    fail(error);
  }
};

const handleRequest = (request: HTTPRequest) => {
  if (onRequest) void consume(onRequest(request));
};
```

`consume(onRequest(request))`에서는 `onRequest`가 `consume`보다 먼저 실행돼요. 콜백이 동기적으로 던진 예외가 `try`에 닿기 전에 이벤트를 보낸 쪽으로 빠져나가고, 리스너도 남은 채로 timeout까지 기다리게 되고요. 그래서 지금 코드처럼 호출할 함수를 넘기는 형태로 고쳤어요.

기다림에는 기본 10초의 제한을 뒀어요. 그 안에 결과가 없거나 reload가 실패하면 `fail`로 끝내요. 성공했을 때와 마찬가지로 타이머와 리스너를 정리하므로, 실패한 수집이 다음 수집에 리스너를 남기지 않아요.

`waitUntil: 'networkidle2'`는 열린 네트워크 연결이 2개 이하인 상태가 500ms 이어지면 새로고침이 끝났다고 보는 옵션이에요. 다만 이 함수가 기다리는 것은 콜백의 결과예요. 필요한 값을 먼저 찾으면 reload가 끝나기 전에도 Promise가 완료돼요.

## 먼저 온 값을 closure 안에 보관해요

request와 response를 받는 순서는 이 함수가 정할 수 없어요. 먼저 도착한 값을 보관하고, 나머지 값이 들어왔을 때 완성된 결과를 돌려주는 collector를 만들었어요. 값을 보관하는 자리는 closure예요. 안쪽 함수는 자기가 만들어진 자리의 변수를 기억해서, 바깥 함수가 끝난 뒤에도 그 변수를 읽고 쓸 수 있어요.

```typescript
interface SitePreInfo {
  headers: Record<string, string>;
  filePassword: string;
}

function createSitePreInfoCollector() {
  let headers: Record<string, string> | undefined;
  let filePassword: string | undefined;

  const getResult = (): SitePreInfo | undefined => {
    if (headers === undefined || filePassword === undefined) return undefined;
    return { headers, filePassword };
  };

  return {
    onRequest(request: HTTPRequest) {
      if (!request.url().includes('/target-api')) return undefined;
      headers = request.headers();
      return getResult();
    },

    async onResponse(response: HTTPResponse) {
      if (!response.url().includes('/file-info')) return undefined;
      const body = (await response.json()) as { password?: string };
      filePassword = body.password;
      return getResult();
    },
  };
}

const collector = createSitePreInfoCollector();
const preInfo = await waitForPreInfo({
  page,
  onRequest: collector.onRequest,
  onResponse: collector.onResponse,
});
```

`createSitePreInfoCollector`의 호출이 끝나도 돌려받은 두 콜백은 그 안의 `headers`와 `filePassword`를 공유해요. 페이지가 보내는 다른 요청도 모두 이 콜백을 지나가므로, URL 조건에 맞지 않는 이벤트에는 `undefined`를 돌려줘 계속 기다려요. 헤더가 먼저 오면 비밀번호를 기다리고, 비밀번호가 먼저 와도 헤더가 없으면 `getResult`는 `undefined`를 돌려줘요. 둘 다 모였을 때만 객체를 반환하니 `waitForPreInfo`도 그때 끝나요.

상태는 이 수집을 위해 만든 closure 안에만 있어요. 바깥에서 두 변수를 직접 고치지 않고 request와 response를 처리하는 함수만 넘겨요. `this`를 쓰지 않으니 `collector.onRequest`처럼 메서드를 떼어 넘겨도 동작해요. 다음 수집에는 새 collector를 만들어요. closure는 한 번의 수집이 모은 값을 들고 있고, Promise는 그 기다림을 끝내면서 리스너를 지워요.
