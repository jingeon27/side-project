*URL 변경, 쿠키 처리와 폼 초기화를 각 동작에 맞는 경로로 나눴어요.*

Next.js를 쓰면서 문제를 세 번 만났어요. 라우터 캐시, 프록시, 서버 액션에서 하나씩이었는데요. 원인은 제각각이었어요. 라우터 캐시와 서버 액션은 서버나 프레임워크에 맡기던 동작을 클라이언트로 옮겨 풀었고, 프록시는 matcher 범위를 고치고 버전을 묶었어요.

폼에서도 상태를 누가 관리하는지에 따라 다른 문제가 나왔어요. 주소를 조회 조건의 기준으로 삼자 작성 중인 검색값이 지워졌고, 복지몰에서는 7월부터 8월 초까지 프레임워크의 상태 보존 때문에 제출한 입력이 남았어요. 각 문제를 고친 과정과 아직 남은 비용을 적었어요.

## 조회 조건을 바꿔도 주소가 바뀌지 않았어요

스테이지 환경에서 Back-Office의 목록 화면 검색이 안 되는 문제가 있었어요. 조건을 고르고 검색을 눌러도 목록이 그대로였어요. 조건 없이 들어와서 검색하면 멀쩡했고, 조회 조건이 이미 주소에 붙은 채로 들어왔을 때만 그랬어요. 새로고침했거나 공유받은 링크로 들어온 경우요.

router.replace를 부르는데 주소창이 바뀌지 않았어요.

원인은 라우터 캐시였어요. 이 화면들은 서버 렌더에서 searchParams를 읽지 않아요. 목록은 전부 클라이언트가 조회하거든요. 그런데 캐시에 쓸 때 키로 삼는 값이 요청 URL의 검색 문자열이 아니라 서버가 실제 렌더에 사용한 검색 문자열이었어요. searchParams를 읽지 않는 라우트에서는 이 값이 항상 빈 문자열이에요. 그래서 /a?foo=bar로 들어온 요청이 파라미터 없는 /a가 찾아가는 슬롯에 캐시를 남겼어요. 이 엔트리에는 요청 URL이 그대로 저장돼 있어서, 나중에 router.replace('/a')가 이 슬롯을 맞히면 옛 검색 문자열이 주소창과 useSearchParams()에 되살아나요.

같은 증상이 업스트림에도 [#92187](https://github.com/vercel/next.js/issues/92187), [#91658](https://github.com/vercel/next.js/issues/91658)로 올라와 있어요. 위 설명은 수정 PR인 [#94144](https://github.com/vercel/next.js/pull/94144)에 적힌 내용이에요.

상세 Drawer가 닫히지 않던 문제는 처음에 닫기가 서버 왕복을 기다리느라 늦는 거라고 봤어요. 닫기를 전이(useTransition)로 감쌌는데 원인이 아니어서 같은 날 되돌렸고, 결국 검색과 같은 원인으로 판단했어요. 어떻게 들어왔는지에 따라 캐시에 남은 게 달랐거든요.

- 목록을 거쳐 상세를 연 경우: 직전에 있던 파라미터 없는 주소가 캐시에 있어서 정상으로 보였어요.
- 상세 주소로 바로 들어온 경우: 캐시에 남은 건 행 링크들이 미리 프리페치해 둔 ?id=… 주소뿐이라, 파라미터를 지워도 그 주소로 되돌아갔어요.

확인할 환경을 찾는 데 시간이 걸렸어요. localhost에서 dev로 띄웠을 때는 검색이 정상이라 실제 증상을 볼 수 없었어요.

같은 코드를 build한 뒤 start로 띄워 확인했어요. 그 환경에서는 Back-Office 목록 7개 중 6개에서 검색을 눌러도 주소가 바뀌지 않았어요. 업스트림 이슈에도 빌드 후 실행할 때만 재현된다는 설명이 있었어요.

고친 방법은 네이티브 history를 쓰는 것이었어요. 공용 훅에 두 함수를 두고 검색 제출, 초기화와 상세 닫기를 이쪽으로 옮겼어요.

```typescript
/**
 * 쿼리 파라미터만 바뀐 주소로 바꾼다.
 *
 * `router.replace` 를 쓰면 안 된다. 이 화면들은 서버 렌더에서 searchParams 를 읽지 않아
 * 라우터 캐시가 검색 문자열과 무관하게 재사용되고, 그 과정에서 캐시에 담긴 주소가 그대로 커밋된다.
 */
export function replaceUrl(url: string) {
  window.history.replaceState(null, '', url);
}

/** 뒤로가기로 되돌아갈 조건 변경(검색 등)은 엔트리를 남긴다. */
export function pushUrl(url: string) {
  window.history.pushState(null, '', url);
}
```

네이티브 history는 Next.js 라우터에 연결돼 있어서 usePathname과 useSearchParams가 바로 갱신돼요. 이 화면들은 어차피 서버에 다시 물어볼 게 없으니 이쪽이 맞았어요.

상세 닫기는 E2E로 고정했어요. 새로고침으로 복원한 Drawer에서 RSC 요청을 붙잡아 둔 채 닫기를 눌러서, 닫기가 서버 왕복에 매여 있으면 실패하게 했어요. 개발 서버에서 도는 테스트라 캐시 버그 자체를 잡지는 못하고, 닫기가 서버 왕복 없이 끝난다는 결정을 지키는 역할이에요. 수정 결과로 남은 확인은 이게 전부예요. 고친 뒤 같은 프로덕션 빌드로 여섯 목록을 다시 돌려 본 기록은 없어요.

### 이 해법은 목록을 클라이언트가 조회해서 성립해요

이 화면들은 클라이언트 컴포넌트가 주소를 읽어 조회 조건을 만들고, 그 조건으로 useQuery를 불러요. 주소가 바뀌면 쿼리 키가 바뀌고 **클라이언트가 스스로 다시 조회해요.** 그래서 "서버에 다시 묻지 않고 주소만 바꾼다"는 선택지가 열려 있었어요.

서버가 조회한 결과를 props로 내려 그리는 구조였다면 이 해법은 성립하지 않아요. 쿼리를 읽어 다시 조회하는 주체가 서버뿐이라, 목록을 새로 받으려면 서버 내비게이션을 시작하는 수밖에 없거든요. replaceState를 불러도 주소만 바뀌고 목록은 그대로예요.

### 그리고 이건 우회가 아니에요

버전이 올라가 라우터 캐시 버그가 고쳐지면 router.replace는 "동작은 해요". 그래도 돌아갈 이유가 없어요.

같은 경로에서 쿼리만 바꾸는데 라우터 내비게이션을 태우면, 캐시가 맞지 않는 순간 **서버가 RSC 페이로드를 다시 만들어 보내요.** 화면에서 실제로 바뀌는 건 목록 한 덩어리인데 사용자는 네트워크와 파싱 비용을, 서버는 렌더 비용을 다시 치러요. 검색, 필터, 탭처럼 연달아 누르는 자리에서는 이 왕복이 그대로 반복되고요.

History API는 그 왕복을 만들지 않아요. 주소만 바꾸고, 주소를 구독하는 쿼리가 필요한 데이터만 새로 받아요.

같은 경로에서 서버가 읽지 않는 조회 조건만 바꿀 때는 버전과 무관하게 History API로 주소를 바꿔요. 라우터 캐시 버그는 계기였을 뿐이라, 버그가 고쳐진 버전으로 올려도 router.replace로 되돌리지 않아요.

## 정작 고쳐진 버전으로는 올릴 수 없었어요

이 버그는 16.3.0에서 이미 고쳐졌어요. 릴리스 노트 Core Changes에 Bugfix: Incorrect search params stored in cache: #94144로 올라와 있고, 캐시에 쓸 때 요청 URL의 검색 문자열을 키로 쓰도록 바꾼 게 수정 내용이에요.

버전만 올리면 될 것 같았는데, 16.3에는 저희를 16.2.x로 내려오게 만든 문제가 있었어요. 관리자 서비스 모노레포는 8월 5일에 14.2에서 16.3으로 올렸다가 이틀 뒤 16.2.12로 내렸거든요.

16.3.0부터 Turbopack이 client reference manifest의 moduleLoading.crossOrigin을 null이 아니라 문자열 "none"으로 직렬화해요. 옵션 타입이 열거형으로 바뀌면서 기본값 None이 그대로 문자열이 돼서 나갔어요.

```text
16.2.12  "moduleLoading":{"prefix":"","crossOrigin":null}
16.3.0   "moduleLoading":{"prefix":"","crossOrigin":"none"}
```

React Flight는 이 값이 use-credentials가 아닌 문자열이면 전부 ""(anonymous)로 바꿔요. 그래서 설정 파일에 crossOrigin을 적은 적이 없어도 SSR에서 preinit되는 클라이언트 컴포넌트 청크의 &lt;script>에 crossorigin=""이 붙고, 브라우저는 그 청크를 CORS 모드로 받아와요.

- 이슈: [#96831](https://github.com/vercel/next.js/issues/96831)
- 수정: [#97164](https://github.com/vercel/next.js/pull/97164)

수정은 null로 되돌리는 게 아니라 CrossOrigin::None일 때 필드를 아예 직렬화하지 않는 방식이에요. 2026년 8월 12일에 canary에 머지돼 v16.3.1-canary.14에 들어갔는데요. 제가 확인한 안정 릴리스 v16.3.1까지는 들어 있지 않았어요. 그 태그의 매니페스트 소스를 열어 보면 생략 옵션이 붙어 있지 않아요. 16.3.0부터 16.3.1까지는 같은 증상을 그대로 안고 있는 셈이에요.

그 뒤 복지몰은 다른 이유로 16.3.x로 올렸어요. 9월에 16.3.6으로 올린 뒤의 빌드 산출물을 보니 매니페스트에 이 필드가 없었고, 미리 렌더된 HTML의 &lt;script>에도 crossorigin=""이 붙지 않았어요.

구분해야 할 게 하나 있어요. 업스트림 이슈가 다루는 상황은 cross-origin assetPrefix로 CDN을 쓰는 경우예요. 저희는 assetPrefix를 쓰지 않아요. cross-origin을 만든 건 프록시였어요.

병원 관리자에는 특정 경로로 들어온 요청을 다른 도메인이 받도록 강제하는 프록시가 있어요. Next.js 16에서 middleware가 이름을 바꾼 proxy예요. 그런데 matcher가 \_next 아래 번들 요청까지 잡고 있었어요. 그래서 그 도메인에서 불러온 JS 번들이 원래 도메인으로 리다이렉트됐고, 여기에 crossorigin=""이 겹치면서 CORS로 막혔어요. 번들이 리다이렉트되는 것 자체는 배포 환경에서는 버전과 상관없이 일어나던 일이에요. 14.2 시절 middleware에도 같은 matcher가 있었거든요. 로컬 모드에서는 프록시가 도메인 강제를 건너뛰어서 보이지 않았고요. 16.3이 그걸 드러냈을 뿐이에요.

근본 대응은 프록시 matcher에서 \_next 같은 정적 경로를 빼는 것이었어요. 도메인을 강제해야 하는 건 페이지 라우트뿐이에요. matcher를 고친 뒤로는 재현되지 않아요. cross-origin 리다이렉트가 없어지니 이슈의 조건 자체가 성립하지 않거든요.

그래도 관리자 서비스 모노레포는 당분간 16.2.x에 두기로 했어요. 같은 조건은 다른 앱의 다른 설정에서도 만들어질 수 있고, 업스트림 수정이 안정 릴리스에 담기기 전까지는 crossorigin=""이 아예 붙지 않는 버전에 있는 편이 비용이 적다고 봤어요.

여기서 버전 업그레이드와 URL 설계를 나눠 보게 됐어요. 버전은 올릴 때가 되면 올리면 되고, URL 설계는 버전이 올라가도 답이 바뀌지 않아요. 같은 경로의 쿼리 변경은 계속 History API로 둬요. **되돌릴 항목이 아니라 유지할 결정이에요.**

라우터가 조회 조건 변경을 알아야 하는 기능이 생기면 그때 다시 봐요. 그건 버전 문제가 아니라 요구사항 문제예요.

## 탭을 오래 열어 둔 사용자가 서버 액션에서 막혔어요

병원 관리자의 업데이트 공지 모달은 쿠키로 노출 여부를 정해요. 물려받은 구현에서 이 쿠키가 httpOnly, secure였고, 그래서 읽고 쓰는 일을 서버 액션이 하고 있었어요.

탭을 띄워 둔 채로 배포가 지나가면 그 탭에서 서버 액션 호출이 404가 났어요. 서버 액션 ID는 빌드 산출물에 묶여 있어서 새로 배포하면 대체로 ID도 새로 생겨요. [문서](https://nextjs.org/docs/app/guides/server-actions#deployment-considerations)에는 소스가 그대로여도 최대 14일 주기로 바뀐다고 돼 있어요. 오래된 탭이 들고 있는 ID는 새 빌드에 없어요. 사용자 입장에서는 아무것도 안 했는데 어느 순간부터 공지가 닫히지 않는 상황이었어요.

그날은 서버 액션이 실패하면 페이지를 새로 불러오는 핫픽스로 막았어요. 옛 번들로는 재시도해도 복구되지 않으니까요.

Next.js에 대응이 없는 건 아니에요. deploymentId를 설정해 두면 클라이언트와 서버의 배포 ID가 어긋날 때 하드 내비게이션으로 전환돼서 오래된 탭이 새 빌드로 올라와요. 문서는 여기에 롤링 배포와 "이 오류를 하드 실패가 아니라 재시도 경로로 노출하라"를 함께 권해요. 다만 어느 쪽도 오래된 ID를 살려 주지는 않아요. 저희가 고민한 건 쿠키를 읽고 쓰는 경로를 어디에 둘지였어요.

하나는 Route Handler로 옮기는 거예요. /api/... 경로는 빌드 ID에 묶이지 않으니 배포가 지나가도 404가 나지 않고, httpOnly도 그대로 유지할 수 있어요.

다른 하나는 클라이언트가 직접 읽고 쓰는 거예요. 쿠키에서 httpOnly를 벗겨요.

두 번째를 택했는데, 이유는 공지 쿠키가 아니라 토큰 쪽에 있었어요. 이틀 전에 액세스 토큰 쿠키를 이미 클라이언트로 내려 둔 상태였거든요. 요청 인터셉터가 모든 요청에서 이 토큰을 읽는데, 그때마다 서버 액션을 왕복하고 싶지 않았어요. 공지 쿠키도 같은 방식으로 맞췄어요. 아래에서는 두 토큰 쿠키를 공개용 가명인 sessionToken(액세스 토큰)과 renewalToken(리프레시 토큰)으로 불러요.

공지 쿠키만 떼어 놓고 보면 이 이유는 성립하지 않아요. 공지를 띄울지 말지는 요청마다 읽는 값이 아니니까요. Route Handler로 옮겼으면 httpOnly를 유지한 채 404만 없앨 수 있었어요. 두 쿠키를 같은 방식으로 다루려다 안 해도 될 노출을 같이 만들었어요. 부채로 적어 둬요.

서버 액션을 걷어낸 이유가 하나 더 있어요. 서버 액션 안에서 쿠키를 바꾸면 Next.js가 현재 라우트를 서버에서 다시 렌더해서, 그 RSC 페이로드를 액션 반환값과 같은 응답에 실어 보내요. 브라우저가 통째로 새로고침되는 건 아니고 UI가 언마운트되지도 않아요. 클라이언트 상태는 그대로 남아요. 그래도 공지 하나 닫는 데 서버 렌더가 한 번 더 붙어요. 이 비용은 측정하지 않아서 부하가 컸다고 쓰지는 않을게요. 없어도 되는 왕복이라고 봤을 뿐이에요.

토큰 쪽은 이렇게 바꿨어요.

- 서버 액션으로 읽어서 클라이언트가 Authorization 헤더에 싣던 흐름을 걷어내고, 재발급은 Route Handler가 맡는 BFF 방식으로 바꿨어요.
- renewalToken은 httpOnly로 남겨요. 브라우저가 재발급 요청에 알아서 실어 보내고, Route Handler가 그걸 읽어요.
- sessionToken이 없으면 로그아웃시키던 동작을, renewalToken으로 재발급을 한 번 시도하도록 바꿨어요. 이전 세션이 남긴 httpOnly sessionToken은 클라이언트가 읽을 수 없어서, 그대로 두면 배포 직후에 멀쩡한 세션이 전부 끊겨요.

마지막 항목에는 반대 방향의 함정이 있어요. 브라우저는 쿠키를 이름, 도메인, 경로로 구분해요. 이름이 같아도 도메인이나 경로가 다르면 옛 쿠키와 새 쿠키를 둘 다 들고 있고 요청에도 둘 다 실어 보내요. document.cookie로 직접 쓸 때 경로를 빼면 현재 문서의 경로가 기본값이라, 서버가 쓰던 경로와 다른 쿠키가 생기기 쉬워요. 그러면 클라이언트에는 새 값만 보이는데 서버는 옛 값을 집을 수 있어요. 이건 "sessionToken 없음"이 아니라 "오래된 sessionToken 있음"이라서 위의 폴백에 걸리지 않아요.

저희 코드는 여기에 걸리지 않았어요. 서버(Next.js의 cookies().set)도 클라이언트(js-cookie)도 경로를 지정하지 않으면 /로 채우고, 둘 다 도메인을 지정하지 않거든요. 걸린 건 다른 쪽이었어요. 브라우저는 스크립트가 httpOnly 쿠키를 덮어쓰는 걸 막아요. sessionToken은 재발급 Route Handler가 응답의 Set-Cookie로 다시 심어서 덮어쓸 수 있지만, 공지 쿠키는 이제 클라이언트만 써서 옛 쿠키를 읽지도 덮어쓰지도 못해요. 이름을 그대로 두면 배포 직전에 공지를 닫아 둔 사용자는 옛 쿠키가 만료될 때까지 하루 동안 공지를 닫을 수 없어요. 그래서 공지 쿠키는 이름을 새로 팠고, 하루짜리인 옛 쿠키는 따로 지우지 않았어요.

이 폴백은 마이그레이션용이에요. 이전 세션의 httpOnly 쿠키가 다 없어지면 되돌려요. 되돌릴 시점을 적어 두지 않으면 "sessionToken 없음"이 정상 경로로 굳어 버리고, 세션이 끝났는지를 renewalToken 만료만으로 판단하게 돼요.

### 클라이언트로 내리면서 늘어난 위험

sessionToken을 JavaScript가 읽게 하면 페이지 권한으로 실행되는 서드파티 태그와 의존성 코드도 접근할 수 있어요. XSS뿐 아니라 클라이언트 도구가 쿠키나 요청 헤더를 수집하는 경로도 확인해야 해요.

액세스 토큰의 수명을 줄이면 탈취된 토큰 하나를 재사용할 수 있는 시간은 줄어요. 다만 악성 스크립트가 계속 실행되고 재발급 응답까지 읽을 수 있다면 새 토큰도 가져갈 수 있어요. 짧은 만료시간만으로 실행 중인 XSS의 영향을 막을 수는 없어요.

HttpOnly는 renewalToken 값을 JavaScript가 직접 읽는 것을 막아요. 브라우저가 쿠키를 실어 보내는 요청까지 막지는 않으므로, 재발급 응답을 누가 읽을 수 있는지와 쿠키 값을 응답으로 돌려주는 경로가 있는지도 따로 봐야 해요.

아직 넣은 완화책은 없어요. 만료를 줄이는 일도, 재발급 경로에 제약을 거는 일도 하지 않았어요. 공지와 토큰 읽기에서 서버 액션을 걷어내서 배포와 무관하게 도는 경로를 얻었고, 대신 이 목록이 생겼어요.

## 주소를 기준으로 삼자 폼이 따라오지 않았어요

조회 조건을 주소에서 관리하기로 했다면 폼도 주소를 따라가야 해요. 처음에는 진입 시점의 주소로 폼을 한 번만 채웠어요.

```typescript
// 진입 시점의 주소가 폼의 초기값이다. 이후 주소 변경은 폼을 건드리지 않는다.
const [initialValues] = useState(() => ({ ...defaultValues, ...currentParams }));
```

목록은 주소를 매 렌더 읽는데 폼은 읽지 않아요. 그래서 뒤로가기를 누르면 목록만 이전 조건으로 돌아가고 검색바에는 방금 입력한 값이 남아 있어요. 화면에 보이는 조건과 목록이 어긋나는 거죠.

주소가 바뀌면 폼도 되돌리도록 고쳤어요. rc-field-form은 initialValues가 바뀌어도 이미 저장된 폼 값을 갱신하지 않아서 직접 초기화해야 해요.

```typescript
// currentParams 는 매 렌더 새 객체라, 내용이 달라졌을 때만 초기값을 다시 만든다.
const paramsKey = JSON.stringify(currentParams);
const initialValues = useMemo(() => ({ ...defaultValues, ...currentParams }), [paramsKey]);

useEffect(() => {
  form.resetFields();
}, [form, initialValues]);
```

아직 남은 문제가 있어요. 폼을 되돌리는 기준이 주소 파라미터 전체라는 점인데요. 조회 조건 스키마에는 페이지 번호와 상세 Drawer의 ID처럼 폼이 소유하지 않는 키도 들어 있어요.

그래서 검색어를 입력해 놓고 제출하기 전에 행을 눌러 Drawer를 열었다 닫으면, 주소의 id가 붙었다 빠지면서 입력하던 값이 사라져요. 페이지를 넘겨도 마찬가지고요. 폼이 주소를 따라가게 고칠 때부터 알던 동작이라, 커밋에는 폼이 주소를 따라가는 설계의 반대급부라고 적고 넘어갔어요. 지금은 트리거만 좁히면 피할 수 있는 비용으로 봐요. 로컬 테스트로 재현은 했는데, 그 테스트는 저장소에 남기지 않았어요.

고칠 방향은 트리거를 폼이 소유한 키로 좁히는 거예요. 초기화 쪽에서 이미 폼 키와 주소 전용 키를 구분하고 있으니 그 구분을 한 군데로 모으면 돼요. 아직 고치지는 않았어요.

## 프레임워크가 상태를 대신 남겨 줘서 폼이 비워지지 않았어요

관리 화면과 별개로 회원이 쓰는 복지몰에서는 반대 방향의 문제가 나왔어요. 6월에 사이트맵 생성 비용 때문에 Cache Components를 켰는데 라우트 상태 보존이 딸려 왔어요.

Next.js는 이동할 때 이전 페이지를 언마운트하지 않고 React의 &lt;Activity>로 감춰요. DOM이 display: none 상태로 문서에 남아 있어서 React 상태도 DOM 상태도 그대로 보존돼요. [문서](https://nextjs.org/docs/app/guides/preserving-ui-state)에 따르면 최근 라우트 3개까지 들고 있다가 그 뒤로는 오래된 것부터 버려요.

예약 신청과 상담 신청 폼이 제출하고 뒤로가기를 하면 입력값을 그대로 들고 있었어요.

폼마다 고치는 대신 공용 폼 훅 한 군데서 처리했어요. 이 앱의 입력 폼은 검색 필터 하나를 빼면 모두 이 훅을 지나거든요. 훅 이름 useSchemaForm은 공개용 가명이에요. 7월에는 화면이 다시 보이는 시점에 되돌리는 방식으로 먼저 막았고, 8월 5일에 아래처럼 바꿨어요.

```tsx
export function useSchemaForm({ schema, ...props }) {
  const form = useForm({ ...props, resolver: zodResolver(schema) });
  const { reset } = form;

  // Cache Components 는 떠난 라우트를 언마운트하지 않고 <Activity> 로 숨겨 입력값을 그대로 보존한다.
  // 폼은 들어올 때마다 새로 시작해야 하므로 화면이 숨겨질 때 초기값으로 되돌린다.
  useIsomorphicLayoutEffect(() => reset, [reset]);

  return form;
}
```

짧은 코드지만 정한 게 몇 가지 있어요.

cleanup 함수로 reset을 그대로 넘겼어요. Activity가 컴포넌트를 감출 때 React가 언마운트와 똑같이 cleanup을 실행하니까, 숨겨지는 시점이 곧 되돌릴 시점이에요.

layout effect로 붙인 건 타이밍 때문이에요. 다시 보이는 시점에 되돌리면 이전 입력이 한 프레임 보였다가 사라져요. 7월 방식에서 실제로 겪은 일이에요. useIsomorphicLayoutEffect는 브라우저에서는 useLayoutEffect로 동작하는 react-use 훅이에요.

되돌아갈 곳은 빈 폼이 아니라 마운트 시점의 defaultValues예요. 들어올 때 자동으로 정해지는 값이 있어서인데요. 예약 신청 화면은 진입하면 혜택이 가장 큰 쿠폰을 미리 골라 두는데, 초기화가 빈 폼으로 떨어지면 이 값까지 지워져요. 그래서 초기값을 서버 데이터에서 받는 폼은 데이터가 확정된 다음에 마운트해야 해요. 조회가 끝나기 전에는 화면을 그리지 않아요.

훅 단위 테스트로 고정해 둔 건 이래요.

- 입력한 값을 그대로 들고 있어요.
- 리렌더만으로는 입력이 지워지지 않아요.
- 화면이 정리되면 초기값으로 되돌아가요.
- 되돌아간 값은 빈 폼이 아니라 초기값이에요.

예약 신청 화면은 E2E로도 확인해요. 다른 화면에 갔다 돌아올 때, 앞으로가기로 돌아올 때, 접수한 뒤 다시 들어올 때 이전 입력이 남지 않는지, 그리고 최대 혜택 쿠폰이 다시 자동 적용돼 있는지를 봐요.

bfcacheId라는 API도 있어요. 키로 주면 되는 줄 알았는데 [문서](https://nextjs.org/docs/app/api-reference/functions/use-router#bfcacheid)를 보니 아니었어요.

> bfcacheId는 push나 replace로 세그먼트가 새로 만들어질 때 바뀌고, 뒤로가기, 앞으로가기와 router.refresh(), 검색 파라미터나 해시만 바뀌는 이동에서는 유지된다.

폼 페이지는 제출할 때 push로 떠나는 거지 새로 만들어지는 게 아니에요. 뒤로가기로 돌아오면 같은 세그먼트가 복원되니까 bfcacheId도 그대로고 키도 바뀌지 않아요. 제출하고 뒤로가기하는 이 시나리오에는 듣지 않는 거죠. 완료 화면에서 폼으로 push해서 다시 들어가는 흐름이라면 세그먼트가 새로 만들어져 키가 바뀌지만, 문서는 그 경우에도 새로 짜는 코드라면 명시적으로 리셋하거나 데이터에서 뽑은 key를 쓰라고 하고 bfcacheId는 마지막 수단으로 둬요.

## 우회를 걷어낼 조건

언제 걷어낼지 적어 두지 않으면 우회가 그대로 굳어요. 2026년 9월 28일 기준으로 네 항목 모두 아직 그대로예요.

- 매니페스트 수정이 담긴 안정 릴리스가 나오면 버전을 올려요. 16.3.6 산출물에서 필드가 빠진 걸 봤으니 조건은 채워졌지만, 16.2.x에 묶어 둔 관리자 서비스 모노레포는 아직 올리지 않았어요.
- 이전 세션의 httpOnly sessionToken이 다 없어지면 재발급 폴백을 되돌려요.
- 폼을 되돌리는 트리거를 폼이 소유한 키로 좁혀요.
- 공지 쿠키는 Route Handler로 옮겨 httpOnly를 되찾아요.

History API는 이 목록에 없어요. 라우터 캐시 버그 때문에 시작했지만, 같은 경로에서 서버가 읽지 않는 쿼리를 바꾸는 데 서버 왕복을 붙이지 않는다는 건 버그와 무관하게 맞는 선택이었어요. **버그가 계기였을 뿐 이유는 아니었던 셈이에요.**

CORS도 폼 초기화도 결정 하나가 잘못돼서가 아니라, 각각 맞는 결정 둘이 만나는 자리에서 어긋났어요. 이 작업으로 프레임워크 의존이 없어진 건 아니에요. 대신 어디까지가 프레임워크 몫이고 어디부터가 제 몫인지는 전보다 분명해졌어요.
