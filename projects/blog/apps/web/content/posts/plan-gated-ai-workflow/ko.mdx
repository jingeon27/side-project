![계획, 구현, 검증과 리뷰를 거쳐 확인한 기준을 다음 작업에 남겨요.](/images/covers/plan-gated-ai-workflow.avif)

에이전트가 성공했다고 보고한 E2E를 열어 봤어요. E2E는 실제 브라우저를 조작해 화면의 흐름을 끝까지 확인하는 테스트예요. 배너 등록 드로어에서 '업로드 중...' 문구가 사라지길 기다리는 줄이 있었는데, 저장소에는 그 문구를 보여주는 코드가 없었어요. 이 줄에 쓴 Playwright의 `toBeHidden()`은 찾는 요소가 아예 없어도 통과해요. 이미 없는 문구가 안 보인다는 이유로 통과한 것인지, 업로드를 정말 기다린 것인지 알 수 없었어요. 성공했다는 말을 그대로 믿었다면 그냥 지나갔을 일이에요.

코딩 에이전트는 저장소의 코드를 읽고 파일을 고치고 테스트 같은 명령까지 실행하는 AI 도구예요. 이 글에 나오는 저장소는 둘이에요. 하나는 병원이 프로그램을 등록하는 병원 관리자 앱과 운영 쪽에서 그 요청을 검수하는 Back-Office 앱이 들어 있는 관리자 모노레포이고, 다른 하나는 사용자가 병원 프로그램을 찾아 예약하는 회원 전용 서비스예요.

Claude 설정을 처음 저장소에 넣었을 때는 결과물을 어떻게 받아 볼지까지 정하지 않았어요. 그 무렵에는 코드가 나오는 속도만 빨라졌어요. 폼을 어디에 두고 Query Options를 어떻게 만드는지 같은 기본 기준은 문서에 있었지만, 작업마다 내리는 세부 판단은 코드와 제 머릿속에 흩어져 있어서 결과물은 제가 처음부터 끝까지 읽고 고쳤어요. 모델이 틀리는 문제보다 저장소에 제 기준이 충분히 적혀 있지 않은 문제가 더 컸어요.

그래서 push 명령에 리뷰어를 붙이고, 구현 전에 plan을 보여주고 기다리는 skill을 관리자 모노레포부터 회원 전용 서비스까지 들였어요. plan은 에이전트가 코드를 고치기 전에 쓰는 작업 계획이고, skill은 특정 작업을 할 때 에이전트가 읽도록 저장소에 적어 두는 지침 문서예요.

한 스프린트에서는 코드를 읽지 않고 화면 동작을 확인하는 데 집중했다가 핫픽스가 많았어요. 그 뒤로는 기능과 리팩터링의 코드와 테스트를 다시 읽어요.

지금은 티켓과 plan을 본 뒤 테스트와 구현을 맡기고, 변경분 검사 다음에 제가 diff와 화면을 봐요. CI를 거쳐 다른 사람이 stage 화면을 한 번 더 확인하는 QA 더블 체크까지 요청하면 한 작업이 끝나요. 아래 그림이 그 순서예요. plan 승인과 diff 리뷰, 화면 확인은 제가 판단하고, push 전에 통과해야 하는 검사 묶음인 push 게이트와 CI는 자동으로 검사해요. 어느 단계에서든 문제가 나오면 앞 단계로 돌아가요.

## 티켓

티켓을 받으면 먼저 코드로 해결할 문제인지, 기존 방식보다 나은 방법이 있는지 생각해요. 요구사항 논의에 참여한 티켓도 있지만, 모든 티켓의 스펙을 제가 정하거나 전부 확인한 것은 아니에요. plan을 읽다가 모호한 동작이나 백엔드 변경이 필요한 부분을 발견하기도 해요. 그런 부분은 담당자와 맞춘 뒤 구현하게 해요.

회원 전용 서비스는 디자이너 시안에 맞춰 작업하고, 다른 제품은 주로 와이어프레임을 보고 만들어요. 시안이 있으면 에이전트가 Figma를 읽게 해 주는 Figma MCP로 가져와 대조하지만 와이어프레임만으로 정할 수 없는 동작도 있어요. 글로벌 서비스의 파일 업로드 화면이 그랬어요. 인증 코드 입력을 언제까지 유지할지, 업로드 실패 뒤 무엇을 보여줄지를 따로 정해야 했어요.

## plan

에이전트는 관련 코드와 가까운 구현을 찾고 plan을 써요. 기존 패턴을 따라도 되는 부분과 요구사항 확인이 먼저인 부분, 완성된 화면과 데이터를 제가 봐야 하는 부분을 구분해요. 미리 정해 둔 버그 수정이나 스키마 불일치 대응은 재현과 검증부터 시작하고요.

완성된 diff에서 방향이 다르다는 걸 발견하면 구현을 버려야 해요. 그래서 티켓으로 브랜치를 만드는 skill이 plan을 낸 뒤에는 제 입력을 기다리게 했어요. 에이전트가 사용자 확인 없이 이어서 진행하는 auto mode에서도 마찬가지이고, 승인 전에는 구현하지 않아요.

템플릿에는 티켓 요약과 영향 범위, 작업 순서, 검토할 내용을 적어요. 저는 파일 목록보다 티켓을 어떤 동작으로 해석했는지를 먼저 봐요. 그 해석이 틀리면 파일 목록이 정확해도 소용이 없으니까요. 상태와 데이터를 어디에 두는지, 어떤 결과가 나오면 끝나는지는 템플릿에 없는 항목이라 제가 승인하면서 되물어요. 빠진 경우나 잘못 이해한 API가 있으면 다시 조사하게 해요. 제가 답할 때까지 그 세션은 멈춰 있지만, 수정된 plan을 보고 시작하면 아직 버릴 제품 코드는 없어요.

## 구현

맡기는 방식은 작업끼리 의존하는지에 따라 달라요. 독립적인 티켓은 Orca라는 도구에서 별도 worktree와 세션을 열어 진행해요. worktree는 한 저장소를 여러 폴더에 따로 체크아웃하는 Git 기능이라, 브랜치와 의존성이 폴더마다 달라서 한 세션이 건드려도 다른 세션은 그대로예요. 공용 API와 구조가 함께 바뀌는 리팩터링은 한 세션에서 맥락을 이어 가요. 어느 쪽이든 완성본을 받으면 제가 diff와 테스트를 읽고, 의도와 다른 부분은 이유를 설명해 다시 맡겨요. 구현 뒤의 리뷰는 plan에서 맞춘 영향 범위와 바꾸지 않을 동작을 실제 diff가 지키는지 확인하는 자리예요.

![독립적인 티켓은 세션을 나누고, 함께 바뀌는 구조는 같은 세션에서 완성본을 검토해요](/images/covers/ai-workflow-parallel.avif)

주의사항은 처음에 프롬프트 끝에 계속 붙였어요. 길어지면서 폼, Query, FSD처럼 작업에 따라 읽을 skill로 나눴어요. FSD는 코드를 레이어와 슬라이스로 나누는 폴더 구조 규칙이에요. 에러 처리는 관리자 서비스의 정책 문서에, 디자인 시스템은 회원 전용 서비스 skill에 뒀어요. 공통 기준은 세션을 열면 먼저 읽히는 `AGENTS.md`에 두고 필요한 설명을 찾아가게 했어요.

에이전트가 잘못 만든 코드를 고칠 때는 다음에도 같은 일이 생길지 봐요. import 방향이나 슬라이스 경계, 공용 정의 없이 직접 쓴 raw query key처럼 코드로 판정할 수 있으면 lint로 옮겼어요. 기존 위반을 고친 뒤 적용 범위를 넓혔고, 두 저장소의 규칙 심각도까지 똑같이 맞추지는 않았어요. 규칙의 개수보다 실제 호출부에서 작동하고 새 위반을 구별할 수 있는지를 봤어요. 컴포넌트가 화면 배치를 조합하는지, 도메인 데이터를 표현하는 UI인지는 사용처를 읽어야 해요. 이런 판단은 문서와 리뷰에 남겼어요.

아래 그림처럼 같은 지적은 판단의 성격에 맞는 자리에 남겨 다음 구현부터 맞게 나오게 해요. 그림 아래쪽의 `<Form key>` 함정이 실제로 옮겨 간 예예요. 관리자 서비스의 동의 모달 테스트를 쓰다가, `key`로 재초기화하게 바꾼 폼에 이전 값이 남는 걸 찾았어요. `useForm()`을 부르는 컴포넌트째 `key`를 주거나 `resetFields()`를 쓰도록 `AGENTS.md`에 적고, `key`와 `form`을 함께 준 폼을 잡는 lint 규칙 `form/no-key-reset`을 만들었어요. 저장소에 위반이 없는 걸 확인한 뒤 error로 켰어요.

![같은 지적은 판단의 성격에 맞는 자리에 남겨 다음 구현부터 맞게 나오게 해요](/images/posts/plan-gated-ai-workflow/03.avif)

[Compound Engineering](https://every.to/guides/compound-engineering)을 참고하면서 작업에서 얻은 판단을 다음 작업의 규칙으로 남기는 쪽으로 이 흐름을 보강했어요. 처음부터 갖춘 체계가 있었던 것은 아니에요. 반복해 고친 부분을 설명에 더했고, 모델 성능도 좋아지면서 제 코드 스타일에 가까운 결과가 나왔어요.

시안을 구현하면 같은 viewport에서 화면을 띄우고 스크린샷을 찍게 해요. 간격과 글꼴, 아이콘, 반응형 배치뿐 아니라 열렸을 때와 오류가 났을 때도 대조해요. 남은 차이를 목록으로 정리해 고친 뒤 다시 보고, 기능은 제가 직접 조작해요.

## 테스트

테스트는 구현보다 먼저 쓰게 하지만, 제가 읽는 건 완성본을 받은 뒤예요. 에이전트가 만든 테스트도 전부 읽어요. 함수와 스키마는 node, 폼과 컴포넌트는 jsdom이나 Browser Mode, 화면을 오가는 과정은 Playwright로 확인해요. jsdom은 브라우저 없이 DOM을 흉내 내는 환경이라 렌더링과 사용자 이벤트까지 볼 수 있어요. 레이아웃이나 좌표, 실제 브라우저 API가 필요하면 Vitest의 Browser Mode로 올려요. 관리자 서비스의 새 테스트는 dev API를 기본으로 쓰고, 직접 만들기 어려운 실패 상태만 요청을 가로채 가짜 응답을 주는 MSW로 재현해 `.mock` 파일로 구분해요.

테스트의 Mock이 모든 요청을 성공으로 처리해서 실제 서버의 400 응답을 숨긴 일도 있었어요. 이후에는 서버 제약을 어긴 요청을 Mock도 거절하게 바꿨어요. dev API에서 다른 제약이 나오면 폼과 Mock, 테스트를 함께 고치고 그 서버를 쓰는 테스트로 다시 확인해요.

도구를 골라도 테스트 내용이 틀리면 통과 결과를 믿을 수 없어요. 글머리의 업로드 테스트는 화면 문구 대신 실제 업로드 항목의 상태를 보도록 고쳤어요.

```typescript
// before: 저장소에 없는 화면 문구가 사라지길 기다린다
await expect(drawer.getByText('업로드 중...')).toBeHidden();

// after: 진행 중인 업로드 항목이 0개인지 본다
await expect(drawer.locator('.ant-upload-list-item-uploading')).toHaveCount(0);
```

고치기 전 줄은 문구를 찾지 못해도 통과하니 무엇을 기다리는지 코드만 봐서는 알 수 없었어요. 고친 줄은 진행 중인 항목을 직접 세요. 이 대기도 진행 중인 항목이 없다는 것만 뜻해요. 업로드가 시작하지 않았거나 실패해도 통과할 수 있어서, 올린 파일과 저장 결과를 함께 확인해야 해요.

QueryClient 설정도 앱과 같아야 했어요. QueryClient는 TanStack Query의 캐시와 기본 동작을 담는 객체예요. 앱과 다른 설정 때문에 초기 조회 실패가 Error Boundary에 도달하지 않던 테스트를 고치고, 데이터가 없는 첫 조회 실패와 기존 데이터가 있는 재조회 실패를 나눠 봤어요.

새 기능의 기대 동작은 BDD 형식의 `*.spec`, 운영과 QA에서 발견한 오류는 `*.test`에 적어요. 여기서 BDD 형식은 `it`에 기대 동작을 "해야 한다"로 끝나는 문장으로 쓰는 방식을 말해요. 테스트를 읽으면 입력과 행동, 기대한 결과가 보여야 해요. 리팩터링은 기존 동작을 먼저 테스트로 잡고 바꾸며, 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 그 테스트가 실패하는지 확인하도록 `AGENTS.md`에 남겼어요. plan에 적힌 성공 조건을 실제로 검사하는지도 같이 읽어요.

아래 그림이 이 기준이에요. 파일 이름으로 명세와 버그 재현을 나누고, 실행 환경은 Mock 없이 확인할 수 있는 자리부터 골라요.

![이름으로 명세와 버그 재현을 나누고, Mock 없이 확인할 수 있는 자리부터 골라요](/images/posts/plan-gated-ai-workflow/04.avif)

프로그램 검수는 병원 관리자와 Back-Office를 모두 지나가요. 병원 관리자가 등록하고 검수를 요청하면 Back-Office에서 검수중으로 바꾼 뒤 승인하거나 반려해요. 한쪽 앱의 렌더 테스트로는 덮이지 않아서 두 앱의 dev 서버를 3000과 3002에서 띄우고 dev API를 호출하는 별도 Playwright 설정을 뒀어요. 한쪽 앱의 E2E 설정에 넣으면 그 앱의 E2E가 매번 반대편 서버까지 띄우게 되거든요. localhost에서 쿠키 도메인이 겹치므로 병원 관리자 로그인은 다른 브라우저 context로 나눴어요. 이 E2E는 CI에 넣지 않고 스크립트로 따로 실행해요.

반려를 확인할 때도 '반려'라는 글자만 찾으면 안 됐어요. 드로어에 버튼으로 이미 있는 문구라 상태가 안 바뀌어도 찾을 수 있어요. 테스트가 입력한 반려 사유가 상세에 다시 나타나는지로 바꿨어요. 사유에 이번 회차의 프로그램 이름을 섞어서 옛 이력과도 구분해요. 그림 아래쪽의 왼쪽이 글자만 찾을 때, 오른쪽이 사유를 찾을 때예요.

![반려는 화면에 원래 있는 글자가 아니라 테스트가 입력한 사유로 확인해요](/images/posts/plan-gated-ai-workflow/05.avif)

## push

별도 worktree는 브랜치와 의존성이 다른 작업에 영향을 주지 않게 해줬지만, 각 세션이 전체 lint와 테스트를 동시에 시작하는 문제는 막지 못했어요. 모노레포의 패키지별 작업을 돌리는 Turbo가 모든 패키지를 캐시 없이 콜드로 돌리며 CPU를 점유했고, 검사가 겹친 실행은 exit 143으로 끝나기도 했어요. 143은 프로세스가 SIGTERM을 받아 종료됐을 때 흔히 나오는 코드예요. 그 코드만으로 CPU 경합이 원인이라고 단정할 수는 없었지만, 검사를 마치지 못하니 코드에 문제가 있는지 알 수 없었고 push도 판단할 수 없었어요.

처음 관리자 push 게이트는 전 패키지 `pnpm run lint`였어요. 이후에는 변경 파일의 ESLint와 해당 패키지의 타입 검사, 변경의 영향을 받는 테스트만 돌리는 `vitest --changed`를 먼저 보게 했어요. 타입 검사는 소비하는 쪽까지 영향을 보고, 쓰지 않는 코드를 찾는 Knip은 저장소 참조 그래프를 봐요. 관리자 CI는 lint와 단위 테스트를 돌리고 dev API 테스트와 E2E는 따로 확인해요. 회원 전용 서비스 CI는 lint와 타입 검사, Knip을 돌려요.

검사는 작업한 worktree에서 해요. 캐시를 쓰려고 메인 worktree에 잠깐 합치지는 않아요. 실패하면 원인에 따라 plan이나 구현, 테스트로 돌아가고, 완료 보고도 plan을 따랐다는 말보다 처음의 요구사항과 대조해요. plan도 에이전트가 만든 결과물이라 그 자체가 잘못될 수 있으니까요.

push를 지시하면 리뷰만 맡은 별도 에이전트가 `origin/develop...HEAD`, 그러니까 이 브랜치가 develop에서 갈라진 뒤 바꾼 내용을 읽고 항목마다 Critical, Warning, Nit과 확신도를 붙여요. Critical은 버그나 사용자 영향이 있는 문제, Warning은 동작은 정상이지만 컨벤션을 어긴 것, Nit은 스타일 선호예요. 확신이 낮은 항목도 빼지 않고 전부 보고해요.

처음에는 두 저장소 모두 리뷰를 먼저 돌렸어요. 리뷰가 ESLint나 타입 검사, 테스트보다 싸서, Critical이 있으면 오래 걸리는 검사를 시작하지 않으려는 순서였어요. 회원 전용 서비스는 그대로 두었고, 관리자는 차례로 돌리면 리뷰 시간만큼 push가 늦어져서 리뷰와 검사를 같이 시작해 둘 다 끝난 뒤 push하도록 바꿨어요. 대신 관리자에서는 Critical이 있는 변경에도 오래 걸리는 검사를 이미 시작한 상태예요.

관리자에서 한 화면의 마크업과 문구, 스타일만 바꿨다고 에이전트가 판단한 작업은 리뷰어와 테스트를 빼고 ESLint와 타입 검사, Knip을 돌려요. 분기나 데이터 흐름을 바꾸면 한 줄이어도 리뷰와 검사를 모두 거쳐요.

Critical은 에이전트가 고치고 다시 검사해요. 해결할 수 없거나 제 판단이 필요한 항목이 남으면 멈추고 제 확인을 받아요. Warning과 Nit은 보고하지만 그것만으로 막지는 않아요. 반면 lint나 타입 검사, 테스트 실패는 다음 단계로 넘어가지 못하게 했어요. 아래 그림이 이 게이트 전체예요.

![Critical은 에이전트가 수정하고 재검증하며, 남은 문제와 검증 실패가 있으면 멈춰요](/images/covers/ai-workflow-push-gate.avif)

에이전트의 리뷰도 그대로 적용하지는 않아요. plan에서 남겨 두기로 한 동작과 실제 지적의 재현 조건을 코드에서 확인해요. 설계를 함께 결정한 동료의 리뷰와는 다른 입력으로 다루고 있어요.

리뷰어가 반복하는 오탐은 예외로 설명했어요. Back-Office와 병원 관리자의 `src/app/api` route가 구조는 비슷하고 엔드포인트와 서비스명만 달라서 공통 핸들러 팩토리를 권하는 일이 반복됐어요. 각 앱의 백엔드와 응답 타입에 묶인 코드라 분리한 채로 두고, 그 추출을 다시 권하지 않도록 리뷰어 정의에 적었어요.

이 게이트를 지나면 제가 diff와 화면을 보고, CI와 QA 더블 체크로 넘어가요.

## 배포

PR을 각각 읽을 때는 괜찮아도 한데 모으면 같은 역할의 추상화가 겹치거나 이름과 FSD 경계가 어긋날 수 있어요. 배포 PR을 준비할 때 합쳐진 diff를 읽는 이유예요.

배포 뒤에도 불편한 패턴을 만나면 그 파일만 고치지 않고 저장소에서 같은 코드를 찾아 고쳐요. 회원 전용 서비스의 entities를 없애고 page 간 직접 참조를 막는 규칙도 이렇게 시작해 develop에 반영했어요. 관리자와 회원 전용 서비스의 구조를 전부 같게 만든 작업은 아니었어요. [FSD 레이어를 다시 나눈 과정은 따로 적었어요.](/ko/blog/fsd-폴더는-다-있었는데-새-파일을-어디에-둘지-설명하기-어려웠어요)

검사에서 뺐던 상담 채팅은 다시 lint와 테스트에 넣었고, 분리할 이유가 있던 API route에는 리뷰 예외를 남겼어요. 같은 지적이 돌아올 때마다 규칙을 더 세게 만들기보다, 실제 코드에 필요한 검사인지도 다시 보게 됐어요.
