I once opened an E2E an agent reported as successful. In the banner-creation drawer, it waited for “Uploading...” to disappear. That text existed nowhere in the repository. I could not establish whether the line actually waited for an upload. Trusting the success report would have let it pass unnoticed.

The first Claude configuration files gave the repository settings without a workflow. Later, I attached a reviewer to push and introduced ticket-branch skills that presented a plan and stopped, first in the admin monorepo and then in the benefits portal. Code generation initially became faster, but detailed decisions still lived across code and my memory. Documents covered basics such as forms and Query Options, while I read and corrected every result. My criteria were insufficiently recorded.

I still read the whole result. What changed is that there are more checks before and after that reading, added one inconvenience at a time.

## Review the ticket before giving it to AI

I first consider whether code can solve the ticket and whether a better approach exists than the current implementation. I sometimes participated in earlier requirements discussions, but did not define or verify every ticket's specification. Ambiguity or required backend work discovered during plan review goes to the relevant person.

The portal follows designer mockups; other products mostly use wireframes. I use Figma MCP where designs exist. For wireframes, I sometimes review UI during self-verification after agent implementation and tests. Global file uploads needed decisions beyond the wireframe, including how long to retain verification codes and what upload failures should show.

The agent then investigates code and patterns. In sessions I distinguish tasks with clear patterns that can proceed to a PR, tasks needing requirements clarification before implementation, and tasks needing human screen/data checks afterward. This is still a session convention, not a skill. Even direct-to-PR tasks have plan approval. Admin `/bugfix` instead proceeds from investigation and reproduction tests to a PR without a plan, stopping only for Critical review findings or failed checks. Both repositories' `/schema-fix` proceeds from operational mismatches through develop merge without a plan.

## Review the plan before the code

Finding a wrong direction in a completed diff means discarding implementation. The ticket-branch skill therefore presents a plan and waits for my input, even in auto mode, before implementation.

Its template has four sections: ticket summary, impact, work order, and review items. I inspect assumptions in the summary and unresolved review items. An accurate file list is useless if the intended behavior is misunderstood. I also ask who owns state/data and what result ends the task, although those are not template fields. Missing states or mistaken API assumptions trigger more investigation and a revised plan. No code exists yet, so changing direction discards only a document.

## Avoid making the same correction twice

Initially, each prompt accumulated cautions. I split them into task-specific skills for forms, Query, FSD, and the design system. Error handling remains an admin policy document; the design-system skill exists only in the portal. When an implementation misses the intent, I correct both code and the relevant skill or lint rule. Admin has 33 skills and the portal 36; AGENTS.md is the rule authority.

Code-decidable criteria moved into lint: reversed layer imports, imports into slice internals, and raw query keys. Progress differs by repository. Portal layer and raw-key rules are errors. Public API violations fell from 271 to 44, 17, then zero before becoming errors. Its subsequent rule is not to introduce lint as warnings, because warnings still exit zero. Admin enables outstanding rules as warnings until violations reach zero, although its three apps' layer/Public API rules remain warnings even after cleanup. Shared-package Public API also remains warning by choice. Five custom rules, including raw query keys, are errors.

Context-dependent judgments, such as whether a component is a screen fragment or domain UI, remain in documentation and review.

![Record each recurring correction where its kind of judgment belongs.](/images/posts/plan-gated-ai-workflow/03.png)

*Record each recurring correction where its kind of judgment belongs.*

Following [Compound Engineering](https://every.to/guides/compound-engineering), I carried task decisions into subsequent rules. This did not arrive as one finished process. Repeated corrections improved skills, and better models also produced more results fitting my style.

## Check the actual screen

For Figma work, agents open dev screens through claude-in-chrome MCP or Chrome CDP scripts and capture screenshots. Differences in spacing, fonts, colors, icons, responsive layout, and open/error states become a list. After fixes, the same viewport and state are captured again. I use no image-similarity score; completion means resolving the listed differences.

Functions also run against dev servers through screens and E2E. Admin integration mocks enforce actual server constraints because permissive mocks had hidden 400 responses. New dev-server constraints feed back into schemas, mocks, and existing tests. Contracts mocks cannot establish receive separate real-server tests.

## A passing test report still needs inspection

I once removed all tests and rebuilt them. Both repositories now aim to avoid mocks where practical. Single-file behavior uses Vitest with the lightest sufficient environment: node, then jsdom, then Browser Mode. Cross-screen flows use Playwright. New Back-Office and hospital-admin tests default to dev APIs; MSW tests get `.mock` names and a separate runner. Previously, real-server tests instead carried `.live`. Portal Vitest uses dev APIs only for queries with fully controllable inputs and outputs and mocks other server boundaries. Admin has 38 domain MSW handlers and the portal 13; portal handlers are for dev/E2E, not Vitest.

I read all AI-written tests. The upload wait from the opening example became:

```typescript
// before: 저장소에 없는 화면 문구가 사라지길 기다린다
await expect(drawer.getByText('업로드 중...')).toBeHidden();

// after: 진행 중인 업로드 항목이 0개인지 본다
await expect(drawer.locator('.ant-upload-list-item-uploading')).toHaveCount(0);
```

This wait alone does not prove upload success. No upload starting, or a failed upload, can also leave zero in-progress entries. The example changes what is awaited; completion still requires checking the file uploaded in this run and its saved result.

Tests must show inputs, actions, and expectations directly. BDD-style `*.spec` covers new requirements by component; `*.test` reproduces production/QA bugs. AGENTS.md requires tests before refactoring and mutation checks that deliberately break product code and confirm failure. New test patterns receive the same check. I read each line against the plan's success conditions and compare execution results with those conditions.

![Names distinguish specifications from bug reproduction, and testing starts where mocks are unnecessary.](/images/posts/plan-gated-ai-workflow/04.png)

*Names distinguish specifications from bug reproduction, and testing starts where mocks are unnecessary.*

Cross-app features use E2E spanning both apps. Hospital admin registers a program and requests review; Back-Office marks it under review, then rejects or approves. One app's render test cannot cover this. A separate Playwright configuration starts both dev servers on 3000 and 3002 against dev APIs. Because localhost shares cookie domains, hospital admin uses a separate browser context. Rejection is asserted through the reason entered by the test reappearing in details, not the word Reject already present on a button.

## Separate independent delegation from continuous joint editing

I run independent tickets as separate Orca sessions. Orca makes parallel sessions convenient and also permits direct code editing. Refactoring with continuous decisions is more comfortable in an IDE: I edit in VS Code and share change context with one agent session. The distinction is how continuously judgment must be shared, rather than task count alone.

Plans align impact, preserved behavior, exceptions, and review questions. Implementation review checks the actual diff against those criteria. Agent findings also need code evidence and reproduction conditions. I do not equate tool review with a colleague agreeing on a design.

![The need for continuous shared judgment determines parallel sessions versus joint editing.](/images/posts/plan-gated-ai-workflow/06.png)

*The need for continuous shared judgment determines parallel sessions versus joint editing.*

## Parallel sessions made verification a bottleneck

Even before Orca, nonoverlapping tickets used separate Git worktrees to isolate branches and dependencies. More sessions exposed another bottleneck: checks.

Simultaneous full lint and test runs made Turbo cold-run packages and consume the CPU. Some overlapping runs exited 143. That exit code alone does not prove CPU contention caused termination, but unfinished checks provided no result with which to judge code. The original admin push gate was one full `pnpm run lint`. Later I narrowed pre-push verification to changed-file ESLint, typechecking their packages, and related tests through `vitest --changed`.

Agents report changes and checks after implementation. I compare those reports against original requirements, not merely the plan: the plan is another agent-produced artifact and can be wrong.

The flow is ticket/plan review → tests → agent implementation/review → affected tests/lint/typecheck → my diff review/local screen → full CI (tests, knip, lint) → QA double check. Failures return to the relevant plan, implementation, or tests. Failed CI does not count as completion. Each task stays in its worktree instead of temporarily merging into the main one for cache reuse.

Affected verification does not mean passing a file list to every tool. Portal ESLint checks changed files and Vitest affected behavior, but typecheck and Knip inspect the whole app/reference graph. Admin typechecks affected packages and related tests, adding consumers explicitly when shared APIs change. Knip still analyzes the whole admin graph. Full lint/typecheck run in CI; dev-API and browser checks have separate paths and conditions.

## Treat review findings separately from failed checks

A separate push reviewer reads origin/develop...HEAD and reports every finding with Critical, Warning, or Nit severity and confidence. Both repositories initially reviewed before expensive checks, avoiding those checks if Critical would stop the change. Portal retains that order. Admin now runs review and checks concurrently, then decides after both finish to reduce push delay. For changes an agent identifies as markup, wording, or style within one screen, admin skips the reviewer/tests and runs ESLint, typecheck, and Knip. A single changed branch or data-flow line requires the full process.

Delegating a Critical fix is different from pushing with unresolved Critical findings. Both push skills require my confirmation for remaining Critical items. Warning and Nit are reported without stopping by themselves. Failed lint, typecheck, or tests independently stop progression.

![Critical review findings need my judgment; failed checks stop push without asking.](/images/posts/plan-gated-ai-workflow/07.png)

*Critical review findings need my judgment; failed checks stop push without asking.*

Repeated false positives become reviewer exceptions. Back-Office and hospital admin have similarly shaped src/app/api routes with different endpoints and service names. Review repeatedly suggested a common handler factory. Because each is tied to its app's backend and response types, I retained separation and documented an exception against recommending that extraction.

## Read the combined code before deployment

Before Stage deployment, I review the complete develop diff. This happens on the `/stage-deploy` path that gathers PRs into a separate deployment PR. `/full-deploy` moves through merges without a pause for this review. Code natural in one PR can reveal duplicate abstractions, inconsistent naming, or divided FSD boundaries when viewed together, prompting another refactor.

After deployment, troubling patterns can trigger a repository-wide search and changes to skills, lint, or shared implementations. Removing portal entities and reducing cross-page references from 62 to zero began here. That redesign reached develop, but the repositories still have different structures and rules. [The FSD article describes it.](/en/blog/fsd-layer-boundaries)

I place reviews where changing direction is cheapest: requirements and structure before code, individual behavior in dev screens/tests, and cross-task consistency in the combined pre-Stage diff. Lint owns mechanical decisions; documents and review retain context.

## Criteria carried forward

- **AGENTS.md:** test first for refactoring, mutation checks, and impact-based local verification just before push. Admin extends test first to bug fixes. A regression test exposed that `<Form key>` does not reinitialize its form, which became both a documented rule and lint.
- **Skills and reviewers:** ticket branches present a plan and wait; push follows review and affected checks, sequentially in portal and concurrently in admin. Test skills separate specifications and bugs; reviewers tag severity. Admin documents the API-route sharing exception. The three task categories remain session practice.
- **Lint and tests:** portal layer, Public API, cross-page, and raw-key rules are errors. Admin's three apps' layer/Public API and shared-package Public API remain warnings, while five custom rules are errors. Both repositories exclude chat from lint/test tracking while retaining typechecking.
