Moving an SPA prototype into a usable service meant adding SSR, SEO, multiple languages, form validation, and admin screens. I expected to build similar pages and forms repeatedly, so before giving the work to Claude Code, I wrote down the sequence from planning to verification.

These rules documented recurring decisions from reading a Jira task through planning, implementation, validation, code review, and committing. They were more specific than preferences such as “always use a hook.”

## Fix the workflow first

I put this sequence in the skill used for service development.

```text
Jira task와 acceptance criteria 확인
  -> 관련 route, API, 기존 pattern 탐색
  -> 변경 파일과 검증 방법을 plan으로 작성
  -> 작은 단위로 구현
  -> typecheck, lint, build, route smoke test
  -> diff 기반 code review
  -> 지적 반영 후 commit
```

The inputs and outputs of each stage mattered more than the name of a component-generation command.

- The plan lists routes to change, patterns to reuse, and loading, error, and empty states.
- Before implementation, find the closest example in the current codebase.
- Review checks scope, hydration, accessibility, and missing translations.
- Each commit contains one verified unit of work.

Separate skills covered recurring forms, queries, and drawers, using real codebase patterns and examples to avoid. Each new plan could focus on what differed in the Jira task instead of repeating the same instructions.

## Give rules conditions

Some early rules were too strong because I tried to stop recurring AI mistakes with short prohibitions. One was “do not pass a value as a prop if a hook can provide it.”

That can reduce prop drilling, but props also make a component's inputs explicit and allow pure tests. I revised it to:

> Do not pass values already owned by common providers, such as router, locale, or theme, through unrelated intermediate components. Pass parent-computed screen data and explicit component inputs as props.

```tsx
// 관계없는 component 두 개가 locale을 전달만 한다.
function Page() {
  const locale = useLocale();
  return <Section locale={locale} />;
}

function Section({ locale }: { locale: Locale }) {
  return <ProductCard locale={locale} />;
}

// 실제 소비 지점에서 app context를 읽는다.
function ProductCard() {
  const locale = useLocale();
  return <ProductName locale={locale} />;
}

// ProductName은 명시적인 입력을 받는 순수 UI로 남긴다.
function ProductName({ locale }: { locale: Locale }) {
  // ...
}
```

For viewport differences that affect presentation alone, prefer CSS media queries over JavaScript hooks. If the viewport changes fetching or behavior, make that decision explicit in client logic.

## A mount gate and Suspense solve different problems

The legacy code had a component that showed children only after mounting.

```typescript
function ClientOnly({ children }: { children: React.ReactNode }) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted ? children : null;
}
```

When I asked the AI to remove it, it moved the same code into a `useMounted` hook. The name changed; the first paint still remained empty.

But “the layout has Suspense, so remove every mount gate” is inaccurate too. Suspense handles fallback for work that suspends. It does not automatically fix access to `window` or viewport-based hydration mismatches.

I separated the rules by cause.

- Wrap the smallest subtree using a hook such as `useSearchParams`, which can switch static rendering to client rendering, in Suspense.
- Read browser APIs in event handlers or effects, and make the first server and client renders produce the same markup.
- Handle presentation differences with CSS media queries where possible.
- Use a client-only boundary for components that cannot support SSR, such as some external widgets.

```tsx
function SearchSection() {
  return (
    <Suspense fallback={<SearchSkeleton />}>
      <SearchResults />
    </Suspense>
  );
}
```

Before deciding whether to remove a gate, determine why the first render differs.

## When mutation state does not need another copy

After moving form submission to `useMutation`, some code still copied success state and the last submitted values into local state and a ref.

```typescript
const mutation = useMutation({ mutationFn: submitForm });

const submittedValues = mutation.variables;
const isComplete = mutation.isSuccess;
```

If only one submission can run at a time and the screen needs only the latest mutation's lifecycle, `variables` and `isSuccess` can be used directly. They do not need copies in `useState` and `useRef`.

That rule has exceptions too.

- Several submissions may run concurrently.
- A snapshot may need to survive long after success.
- The business state may be independent of resetting a mutation.

Those cases need domain state separate from mutation state. The aim is to avoid storing another copy of a value that already has an owner.

## Feed review findings back into the skill

After moving several routes, I reviewed the full diff. I fixed individual files and added only findings likely to recur to the skill.

For example:

- Await asynchronous page props according to the current Next.js version's types.
- Decide in the plan whether query prefetching needs SEO or can stream.
- Specify a Suspense gate or reset policy for asynchronous form initial values.
- Give icon buttons accessible names and tooltips.
- Check new message keys across every locale used by a multilingual route.

I did not turn every review comment into a permanent rule. Exceptions relevant to one screen or unlikely to recur stayed in code. Too many rules create conflicts and bury the criteria that matter.

## Completion criteria

I made the completion criteria explicit so that a fast-looking implementation would not be mistaken for a finished migration.

- Typecheck and lint pass for changed routes.
- The production build passes.
- Main routes pass desktop and mobile smoke tests.
- Server-rendered HTML and metadata are checked.
- Forms are checked for validation, submission, and errors.
- Missing locale keys are checked.
- The diff is reviewed and changes outside the task are removed.

I looked for fewer repeated review findings in the next task, rather than measuring only code generation speed. That also helped decide which findings belonged in the rules.

## Rules to carry into the next task

For this prototype, the useful work was fixing how a Jira task becomes a plan, how existing patterns are found, and how implementation passes through validation and review.

Rules need conditions and exceptions. Suspense, props, and mutation state each depend on context. I record decisions in a form the next task can reuse, then still check the result with a build and the actual screen. That is the AI collaboration process I settled on in this project.
