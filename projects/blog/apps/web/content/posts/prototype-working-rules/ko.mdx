검증용 SPA 프로토타입을 실사용 서비스로 옮기는 작업을 맡았다. 실제 운영 단계에서는 SSR, SEO, 다국어, 폼 검증, 관리자 화면과 배포 검증까지 필요했다. 정적 page와 form이 반복될 것이 분명했기 때문에 Claude Code에 화면 하나씩 설명하기 전에 작업 규칙부터 정리했다.

여기서 규칙은 "항상 hook을 써라" 같은 취향 목록이 아니었다. Jira task를 읽고 plan을 세우는 단계부터 구현, 검증, code review, commit까지 반복되는 판단을 문서화한 것이었다.

## 작업 흐름부터 고정하기

서비스 작업용 skill에는 다음 순서를 넣었다.

```text
Jira task와 acceptance criteria 확인
  -> 관련 route, API, 기존 pattern 탐색
  -> 변경 파일과 검증 방법을 plan으로 작성
  -> 작은 단위로 구현
  -> typecheck, lint, build, route smoke test
  -> diff 기반 code review
  -> 지적 반영 후 commit
```

component를 생성하는 command 이름보다 중요한 것은 각 단계의 입출력이었다.

- plan에는 바꿀 route, 재사용할 pattern, loading/error/empty state를 적는다.
- 구현 전에 현재 codebase에서 가장 가까운 예제를 찾는다.
- review에서는 task 범위를 벗어난 변경, hydration, 접근성, 번역 누락을 확인한다.
- commit은 검증을 통과한 한 작업 단위로 만든다.

form, query, drawer 같은 반복 구현은 별도 skill에 실제 codebase의 pattern과 금지 사례를 함께 적었다. 새로운 화면을 만들 때마다 설명을 다시 쓰지 않고, Jira task의 차이만 plan에 남기는 구조였다.

## 규칙은 blanket rule이 아니라 조건으로 쓴다

처음에는 AI가 반복해서 만든 문제를 짧게 막으려다 너무 강한 규칙을 만들기도 했다. 예를 들어 "hook으로 얻을 수 있는 값은 prop으로 넘기지 않는다"는 규칙이다.

이 문장은 prop drilling을 줄이는 데는 도움이 되지만 항상 맞지는 않는다. props는 component의 입력을 명시하고 순수하게 테스트할 수 있게 해준다. 수정한 규칙은 다음과 같다.

> router, locale, theme처럼 이미 공통 provider가 소유한 값을 관계없는 중간 component들이 전달만 하지 않는다. 반면 부모가 계산한 화면 데이터와 component의 명시적 입력은 props로 전달한다.

```tsx
// 관계없는 component 두 개가 locale을 전달만 한다.
function Page() {
  const locale = useLocale();
  return <Section locale={locale} />;
}

function Section({ locale }: { locale: Locale }) {
  return <ProductCard locale={locale} />;
}

// 실제 소비 지점에서 app context를 읽는다.
function ProductCard() {
  const locale = useLocale();
  return <ProductName locale={locale} />;
}

// ProductName은 명시적인 입력을 받는 순수 UI로 남긴다.
function ProductName({ locale }: { locale: Locale }) {
  // ...
}
```

viewport도 표시만 달라진다면 JavaScript hook보다 CSS media query를 우선한다. 하지만 viewport에 따라 fetch나 행동 자체가 달라진다면 그 결정은 별도 client logic으로 명시한다.

## mount gate와 Suspense는 같은 해결책이 아니다

레거시에는 mounted가 된 뒤에만 children을 보여주는 component가 있었다.

```typescript
function ClientOnly({ children }: { children: React.ReactNode }) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted ? children : null;
}
```

AI에게 제거를 요청했더니 같은 코드를 useMounted hook으로 옮겼다. 이름은 바뀌었지만 첫 paint를 비우는 동작은 그대로였다.

그렇다고 "layout에 Suspense가 있으니 모든 mount gate를 제거한다"도 정확하지 않다. Suspense는 suspend하는 작업의 fallback을 처리하지만 window 접근이나 viewport 기반 hydration mismatch를 자동으로 해결하지 않는다.

규칙을 원인별로 나눴다.

- useSearchParams처럼 정적 rendering을 client rendering으로 전환할 수 있는 hook은 사용하는 가장 작은 subtree를 Suspense로 감싼다.
- browser API는 event handler나 effect에서 읽고, 첫 server/client render가 같은 markup을 만들게 한다.
- 표시 차이는 가능한 CSS media query로 처리한다.
- 외부 widget처럼 SSR이 불가능한 component만 client-only boundary를 사용한다.

```tsx
function SearchSection() {
  return (
    <Suspense fallback={<SearchSkeleton />}>
      <SearchResults />
    </Suspense>
  );
}
```

핵심은 gate를 금지하는 것이 아니라 왜 첫 render가 달라지는지 먼저 분류하는 것이다.

## mutation state를 복제하지 않을 조건

폼 제출을 useMutation으로 옮긴 뒤에도 성공 여부와 마지막 제출 값을 local state와 ref에 다시 저장한 코드가 있었다.

```typescript
const mutation = useMutation({ mutationFn: submitForm });

const submittedValues = mutation.variables;
const isComplete = mutation.isSuccess;
```

한 번에 하나만 제출할 수 있고 마지막 mutation의 lifecycle만 화면에 필요하다면 variables와 isSuccess를 그대로 쓸 수 있다. 같은 값을 useState와 useRef에 복제하지 않아도 된다.

하지만 이것도 조건부 규칙이다.

- 여러 제출이 동시에 진행될 수 있다.
- 성공 이후에도 snapshot을 오래 보존해야 한다.
- mutation reset과 무관한 업무 상태다.

이 경우에는 mutation state와 별도의 domain state가 필요하다. "상태를 줄인다"가 목표가 아니라 source of truth가 이미 있는 값을 다시 저장하지 않는 것이 목표다.

## review 결과를 skill에 되돌려 넣기

몇 개 route를 옮긴 뒤 전체 diff를 다시 검토했다. 발견한 문제를 해당 파일만 고치는 데서 끝내지 않고, 반복될 가능성이 있는 항목만 skill에 반영했다.

예를 들어 다음 항목이 추가됐다.

- async page props는 현재 Next.js version의 타입에 맞춰 먼저 await한다.
- query prefetch는 SEO가 필요한지, streaming 가능한지 plan에서 정한다.
- form의 async initial value는 Suspense gate 또는 reset 정책을 명시한다.
- icon button에는 접근 가능한 이름과 tooltip을 둔다.
- 다국어 route는 새 문구의 모든 locale key를 함께 검증한다.

모든 review 지적을 영구 규칙으로 만들지는 않았다. 한 화면에만 해당하거나 앞으로 반복될 가능성이 낮은 예외는 code에서만 고쳤다. 규칙이 너무 많아지면 서로 충돌하고 중요한 기준이 묻히기 때문이다.

## 완료 기준

빠르게 끝났다는 인상만으로 실사용 전환을 설명하지 않기 위해 완료 조건을 명시했다.

- 변경 route의 typecheck와 lint 통과
- production build 통과
- 주요 route의 desktop/mobile smoke test
- server-rendered HTML과 metadata 확인
- form의 validation, submit, error path 확인
- locale별 누락 key 확인
- diff code review 후 task 밖 변경 제거

AI가 코드를 생성한 속도보다 같은 종류의 지적이 다음 작업에서 줄었는지를 봤다. 규칙으로 옮길 가치가 있는 것도 이 기준으로 골랐다.

## 마치며

프로토타입을 실사용 단계로 옮길 때 가장 효과가 컸던 것은 command를 많이 만든 일이 아니었다. Jira task를 plan으로 바꾸는 순서, codebase pattern을 찾는 기준, 구현 뒤 검증과 review를 거치는 흐름을 skill로 고정한 일이었다.

좋은 규칙은 짧고 강한 구호가 아니라 적용 조건과 예외를 함께 가진다. Suspense, props, mutation state도 항상 한쪽이 옳은 문제가 아니었다. 작업 중 발견한 판단을 다음 작업이 재사용할 수 있는 형태로 남기되, 실제 결과는 build와 화면 검증으로 다시 확인하는 것이 이 프로젝트에서 정리한 AI 협업 방식이다.
