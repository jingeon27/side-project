<Summary>

검증용 SPA를 Next.js 서비스로 옮기며 코딩 에이전트에 비슷한 구현을 여러 번 맡기는 동안, 그때마다 고치던 내용을 에이전트가 읽는 지침 문서인 skill에 적었어요. 그런데 짧고 강한 규칙은 멀쩡한 코드까지 바꾸게 할 수 있어서, 언제 쓰면 안 되는지까지 적어야 했어요.

</Summary>

반복되는 실수를 막으려고 skill에 “hook으로 얻을 수 있는 값은 prop으로 넘기지 않는다”고 적은 적이 있어요. skill은 코딩 에이전트가 작업할 때 읽도록 적어 두는 지침 문서예요. 에이전트는 여기 적힌 문장을 다음 구현에서 따르려고 하는데, 이 문장대로라면 명시적인 입력을 받는 UI까지 context에 묶일 수 있었어요.

마운트가 끝날 때까지 children을 숨기는 컴포넌트를 없애 달라고 했을 때는 에이전트가 같은 내용을 `useMounted` 훅으로 옮겼어요. 컴포넌트는 사라졌지만 첫 화면은 여전히 비어 있었어요.

둘 다 검증용 SPA를 Next.js 서비스로 옮기면서 겪은 일이에요. SPA는 브라우저에서 JavaScript로 화면을 그리는 앱이라 서버가 보내는 첫 HTML이 거의 비어 있어요. 실제로 쓸 서비스로 옮기는 일은 화면만 다시 만드는 것으로 끝나지 않았고, 서버에서 HTML을 만드는 SSR과 SEO, 다국어, 폼 검증, 관리자 화면을 붙여야 했어요. 비슷한 페이지와 폼이 이어질 작업이라 Claude Code에 매번 같은 설명을 반복하고 싶지 않아서 반복된 지적을 skill에 더해 갔는데, 쓰다 보니 규칙을 짧게 적는 것만으로는 부족했어요. 언제 그 규칙을 쓰면 안 되는지도 필요했어요.

## props를 없애라는 규칙

처음 문장이 어디서나 틀린 건 아니었어요. props로 값을 여러 단계 내리면 중간 컴포넌트는 자기가 쓰지도 않는 값을 전달만 하게 돼요. locale처럼 앱 전체가 함께 쓰는 값은 위쪽의 provider가 React context로 제공하니, 필요한 컴포넌트가 훅으로 직접 읽으면 이런 전달을 줄일 수 있어요.

하지만 props는 부모가 계산한 값을 전달하고, 컴포넌트가 무엇을 필요로 하는지 드러내는 방법이기도 해요. 입력이 드러나 있으면 그 컴포넌트만 떼어 테스트하기도 쉬워요. 그래서 공통 provider의 값을 중간에서 전달만 하는 경우로 규칙을 좁혔어요.

> router, locale, theme처럼 이미 공통 provider가 소유한 값을 관계없는 중간 component들이 전달만 하지 않는다. 반면 부모가 계산한 화면 데이터와 component의 명시적 입력은 props로 전달한다.

```tsx
// 관계없는 component 두 개가 locale을 전달만 한다.
function Page() {
  const locale = useLocale();
  return <Section locale={locale} />;
}

function Section({ locale }: { locale: Locale }) {
  return <ProductCard locale={locale} />;
}

// 실제 소비 지점에서 app context를 읽는다.
function ProductCard() {
  const locale = useLocale();
  return <ProductName locale={locale} />;
}

// ProductName은 명시적인 입력을 받는 순수 UI로 남긴다.
function ProductName({ locale }: { locale: Locale }) {
  // ...
}
```

위쪽의 `Page`와 `Section`이 규칙으로 없애려는 전달이고, 아래쪽이 규칙을 좁힌 뒤의 모양이에요. 이 예제에서는 `ProductCard`가 locale을 읽고 `ProductName`은 입력받은 locale로 그리기만 해요. `Section`이 대신 전달할 필요는 없지만, `ProductName`의 입력까지 없앨 필요도 없어요.

처음 문장을 그대로 따르면 `ProductName`도 locale을 직접 읽게 돼요. 줄인 예시예요.

```tsx
// 처음 규칙을 문자 그대로 따른 모양
function ProductName() {
  const locale = useLocale();
  // ...
}
```

겉으로는 입력이 없는 컴포넌트처럼 보이지만, 이제 provider가 있어야 그릴 수 있고 다른 locale로 그려 보려면 provider부터 감싸야 해요.

화면 너비에 따라서도 비슷하게 구분했어요. 배치나 표시만 달라지면 CSS media query를 쓰고, 너비에 따라 조회나 행동이 달라질 때만 클라이언트 로직으로 표현해요.

## useMounted로 옮겨도 비어 있는 첫 화면

기존 코드에는 마운트가 끝날 때까지 children을 숨기는 컴포넌트가 있었어요. 이런 코드를 여기서는 mount gate라고 부를게요.

```typescript
function ClientOnly({ children }: { children: React.ReactNode }) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted ? children : null;
}
```

`useEffect`는 서버에서 실행되지 않고, 브라우저에서도 첫 렌더가 끝난 뒤에 돌아요. 그래서 서버 HTML과 브라우저의 첫 렌더에서 `mounted`는 `false`이고, 이 컴포넌트 아래는 아무것도 그려지지 않아요. SSR과 SEO를 붙이려고 옮기는 서비스인데 이 아래는 서버 HTML이 비어 있는 셈이에요.

mount gate는 보통 hydration 문제를 피하려고 써요. hydration은 서버가 만든 HTML에 React가 브라우저에서 이벤트 핸들러를 연결하는 과정이에요. 이때 브라우저의 첫 렌더 결과가 서버 HTML과 다르면 hydration mismatch가 나요. 양쪽의 첫 렌더를 모두 비워 두면 다를 것이 없으니 mismatch는 사라지지만, 내용도 함께 사라져요.

이 코드를 없애 달라고 했더니 같은 내용이 `useMounted` 훅으로 옮겨 갔어요. 줄인 예시로 보면 이래요.

```typescript
function useMounted() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted;
}
```

첫 paint가 비어 있는 이유는 그대로 남았고, 바뀐 건 이름과 파일 위치뿐이었어요. 제가 원한 수정이 아니었어요.

그렇다고 layout에 Suspense가 있다는 이유로 mount gate를 모두 없앨 수도 없어요. Suspense는 아직 준비되지 않아 suspend한 하위 트리 대신 fallback을 보여 주는 경계예요. 기다릴 것이 있을 때 쓰는 장치라, window 접근이나 viewport에 따른 hydration mismatch를 해결해 주지는 않아요. 아래는 줄인 예시예요.

```tsx
// 서버에는 window가 없어서 DesktopNav를 그리고,
// 좁은 화면의 브라우저는 첫 렌더에서 MobileNav를 그려요.
const isMobile = typeof window !== 'undefined' && window.innerWidth < 768;

return isMobile ? <MobileNav /> : <DesktopNav />;
```

이 컴포넌트를 Suspense로 감싸도 서버와 브라우저의 첫 렌더는 여전히 달라요.

이후에는 규칙 하나로 줄이지 않고 원인을 구분해서 적었어요. `useSearchParams`처럼 정적 렌더링을 클라이언트 렌더링으로 전환할 수 있는 훅은 필요한 작은 subtree를 Suspense로 감싸요. Next.js에서 미리 렌더링하는 페이지는 요청이 오기 전이라 쿼리 문자열을 알 수 없어요. 그래서 이 훅을 쓰면 가장 가까운 Suspense 경계까지 브라우저에서 렌더링하고, 경계가 없으면 프로덕션 빌드가 실패해요. 작게 감싸면 그 바깥은 첫 HTML에 남아요.

```tsx
function SearchSection() {
  return (
    <Suspense fallback={<SearchSkeleton />}>
      <SearchResults />
    </Suspense>
  );
}
```

브라우저 API는 이벤트 핸들러나 effect에서 읽어 첫 서버 렌더와 클라이언트 렌더가 같은 마크업을 만들게 해요. 표시 차이는 CSS로 처리하고, 외부 위젯처럼 SSR을 할 수 없는 경우에만 client-only 경계를 남겨요.

## 제출 결과를 mutation 밖에 다시 저장한 코드

폼 제출을 TanStack Query의 `useMutation`으로 바꾸고도 성공 여부와 마지막 제출 값을 local state와 ref에 다시 저장한 코드가 있었어요. `useMutation`은 서버에 쓰는 요청과 그 진행 상태를 관리하는 훅이에요. 코드로 줄이면 다음과 같아요.

```typescript
const [isComplete, setIsComplete] = useState(false);
const lastValues = useRef<FormValues | null>(null);

const mutation = useMutation({
  mutationFn: submitForm,
  onSuccess: (_, variables) => {
    setIsComplete(true);
    lastValues.current = variables;
  },
});
```

화면에 필요한 값이 mutation에도 이미 있었어요.

```typescript
const mutation = useMutation({ mutationFn: submitForm });

const submittedValues = mutation.variables;
const isComplete = mutation.isSuccess;
```

한 번에 하나씩 제출하고 마지막 제출의 결과만 보여주는 화면이라면 마지막으로 보낸 입력값인 `variables`와 그 요청의 성공 여부인 `isSuccess`를 그대로 읽으면 돼요. 성공할 때 따로 상태를 쓰고 reset할 때 다시 맞출 필요가 없어요.

반대로 동시에 여러 제출을 다루거나, mutation을 reset한 뒤에도 제출 당시 값을 보관해야 한다면 별도 상태가 필요해요. `reset()`을 부르면 `variables`도 함께 비워지니까요. 성공 후 오래 남겨 둘 snapshot도 마찬가지예요. 그래서 상태를 만들지 말라고 적지 않고, 화면에서 필요한 동안 mutation이 이미 보관하는 값만 중복 저장하지 않도록 적었어요.

## 규칙보다 먼저 적은 작업 순서

이런 구현 규칙을 적기 전에 skill에 먼저 넣은 건 Jira task를 읽은 뒤 어떤 코드를 찾고 어디서 검토할지였어요. 계획부터 커밋까지의 순서를 이렇게 적었어요.

```text
Jira task와 acceptance criteria 확인
  -> 관련 route, API, 기존 pattern 탐색
  -> 변경 파일과 검증 방법을 plan으로 작성
  -> 작은 단위로 구현
  -> typecheck, lint, build, route smoke test
  -> diff 기반 code review
  -> 지적 반영 후 commit
```

plan은 에이전트가 구현 전에 쓰는 작업 계획이에요. 여기에 바꿀 route와 가까운 기존 구현을 적게 했어요. 로딩 중이거나 조회가 실패했을 때, 데이터가 없을 때 보여줄 화면도 여기서 정해요. 폼이나 drawer를 매번 다른 모양으로 만들지 않도록 구현 전에 참고할 코드를 찾게 한 거예요.

리뷰에서는 task 밖의 변경이 섞였는지와 hydration, 접근성, 번역 누락을 봐요. 검증을 통과한 작업 단위로 커밋하도록 했고요. 폼과 query처럼 자주 만드는 코드는 별도 skill에 예제와 피해야 할 구현을 함께 뒀어요. 각 작업의 plan에는 그 예제와 달라지는 부분을 설명하게 해서, 화면을 새로 만들 때마다 같은 설명을 다시 쓰지 않아도 됐어요.

작업을 끝내는 조건도 코드 생성과 나눠 뒀어요. 코드가 빨리 나왔다는 이유로 끝내지 않도록, 바뀐 route의 typecheck와 lint, production build에 더해 desktop과 mobile 화면을 열고, 서버 HTML과 metadata, 번역 key를 확인하도록 했어요. 폼의 입력 검증과 제출 실패도 보고, 마지막 diff에서 task 밖의 변경을 걷어내게 했고요. skill을 보강했다고 이 확인을 건너뛰지는 않았어요.

## skill에 남긴 지적

몇 개 route를 옮긴 뒤에는 변경 내용을 함께 읽었어요. 다시 나올 만한 내용은 skill에 더했어요. 이 Next.js 버전에서 Promise로 오는 async page props는 타입에 맞춰 먼저 await하고, query prefetch는 SEO에 필요한지 스트리밍해도 되는지를 plan에서 정하게 했어요. 늦게 도착하는 폼 초기값은 Suspense로 기다릴지 reset으로 채울지 적게 했고요. 아이콘 버튼의 접근 가능한 이름과 tooltip, 다국어 문구의 locale key 확인도 넣었어요.

한 화면에서만 필요한 수정은 그 코드에서 끝냈어요. 규칙이 너무 많아지면 서로 충돌하고 중요한 기준이 묻히기 때문이에요. 예외가 많은 문장을 모든 작업에 적용하면, 앞서 props 규칙에서 그랬듯 멀쩡한 입력까지 없애는 수정이 나올 수 있었어요.

규칙으로 옮길 만한지는 에이전트가 코드를 만든 속도보다 같은 종류의 지적이 다음 작업에서 줄었는지를 보고 골랐어요.
