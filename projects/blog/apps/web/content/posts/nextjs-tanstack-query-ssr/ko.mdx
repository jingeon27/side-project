> Next.js 15 App Router와 TanStack Query v5를 기준으로 한다.

App Router의 서버 prefetch와 브라우저 조회에 같은 QueryClient 생성 코드를 쓰면 인스턴스를 언제 만들고 재사용할지부터 정해야 한다. 요청 사이에 캐시가 섞이거나 렌더마다 사라지는 일을 막기 위해 두 환경의 수명을 나눴다.

- 서버 요청끼리는 캐시를 공유하면 안 된다.
- 브라우저에서는 렌더마다 QueryClient를 다시 만들면 안 된다.

## QueryClient 만들기

```typescript
// query-client.ts
import {
  QueryClient,
  defaultShouldDehydrateQuery,
  isServer,
} from '@tanstack/react-query';

function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        staleTime: 60_000,
      },
      dehydrate: {
        shouldDehydrateQuery: (query) =>
          defaultShouldDehydrateQuery(query) ||
          query.state.status === 'pending',
      },
    },
  });
}

let browserQueryClient: QueryClient | undefined;

export function getQueryClient() {
  if (isServer) {
    return makeQueryClient();
  }

  if (!browserQueryClient) {
    browserQueryClient = makeQueryClient();
  }

  return browserQueryClient;
}
```

기존 글의 typeof window !== undefined는 항상 참이었다. typeof의 결과는 문자열이므로 직접 검사하려면 typeof window === 'undefined'여야 한다. 여기서는 TanStack Query가 제공하는 isServer를 사용해 의도를 더 분명하게 했다.

서버에서는 요청마다 새 QueryClient를 만든다. 브라우저에서는 모듈 범위의 인스턴스를 재사용한다.

## Provider 연결하기

```tsx
'use client';

import { QueryClientProvider } from '@tanstack/react-query';

import { getQueryClient } from './query-client';

export function QueryProvider({ children }: { children: React.ReactNode }) {
  const queryClient = getQueryClient();

  return (
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  );
}
```

Provider가 Client Component여도 children으로 전달된 Server Component가 Client Component로 바뀌는 것은 아니다. layout에서 Provider로 감싸도 서버 컴포넌트 경계를 유지할 수 있다.

## queryOptions를 조회 계약으로 사용하기

```typescript
import { queryOptions } from '@tanstack/react-query';

export const categoryOptions = queryOptions({
  queryKey: ['categories'],
  queryFn: async () => {
    const response = await fetch(`${process.env.API_URL}/categories`);
    if (!response.ok) throw new Error('카테고리를 불러오지 못했습니다.');
    return (await response.json()) as Category[];
  },
});
```

같은 option을 서버 prefetch와 클라이언트 구독에 함께 사용하면 query key와 queryFn이 어긋날 가능성이 줄어든다.

## 서버에서 병렬로 prefetch하기

```tsx
import { dehydrate, HydrationBoundary } from '@tanstack/react-query';

export default async function HomePage() {
  const queryClient = getQueryClient();

  await Promise.all([
    queryClient.prefetchQuery(categoryOptions),
    queryClient.prefetchQuery(integrationOptions),
  ]);

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <HomePageView />
    </HydrationBoundary>
  );
}
```

두 조회가 서로 의존하지 않으므로 순서대로 await하지 않고 Promise.all로 묶는다. 완료된 query만 넘긴다면 기본 dehydration 정책으로도 충분하다. 위 QueryClient에서 pending query까지 포함한 이유는 일부 화면에서 prefetch를 기다리지 않고 Suspense로 streaming하는 선택지도 함께 지원하기 위해서다.

## 클라이언트에서 같은 query를 구독하기

```tsx
'use client';

import { useSuspenseQuery } from '@tanstack/react-query';

export function HomePageView() {
  const { data } = useSuspenseQuery(integrationOptions);
  return <IntegrationList items={data} />;
}
```

서버가 넘긴 dehydrated cache와 클라이언트의 query key가 같으므로 첫 렌더에서 같은 데이터를 사용한다. 이후 invalidate와 refetch도 TanStack Query의 캐시 흐름 안에서 동작한다.

## 선택 기준

- 초기 HTML에 데이터가 꼭 있어야 하거나 오류를 서버에서 처리해야 하면 await prefetchQuery를 사용한다.
- pending query를 streaming하려면 pending dehydration을 켜고 소비 컴포넌트를 Suspense 경계 안에서 useSuspenseQuery로 구독한다.
- 어떤 방식을 쓰든 서버 QueryClient는 요청별로, 브라우저 QueryClient는 한 번만 만든다.
