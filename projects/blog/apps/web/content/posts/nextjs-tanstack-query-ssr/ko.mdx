<Summary>

Next.js 서버 컴포넌트에서 미리 조회한 데이터를 브라우저의 TanStack Query 캐시가 이어 받도록 코드를 따라 읽었어요. `QueryClient`는 서버와 브라우저에서 수명을 다르게 만들고, 조회 옵션은 양쪽이 함께 쓰도록 연결했어요.

</Summary>

![서버와 브라우저의 별도 캐시 사이로 초기 데이터를 전달하는 모습을 그린 일러스트](/images/covers/nextjs-tanstack-query-ssr.avif)

> 예제는 Next.js 15 App Router와 TanStack Query v5를 사용해요.

TanStack Query는 API 응답을 브라우저 메모리에 캐시하고, 같은 key로 조회하는 컴포넌트에 나눠 주는 라이브러리예요. 이 캐시를 들고 있는 객체가 `QueryClient`예요. App Router에서 서버가 데이터를 미리 받아도, 화면에서 같은 데이터를 조회하는 코드는 클라이언트에 남아요. 서버가 받은 결과를 브라우저 캐시로 넘기지 못하면 브라우저가 같은 조회를 다시 해야 해요. 그래서 서버의 캐시를 어떻게 넘길지와 브라우저에서 그 캐시를 얼마나 오래 쓸지를 함께 정해야 해요.

먼저 정할 것은 `QueryClient`의 수명이에요. 가장 단순하게 쓰는 두 방법은 각각 한쪽 환경에서 문제가 돼요. 아래는 설명하려고 줄인 예시예요.

```typescript
// 줄인 예시: 모듈에 하나만 두면 서버에서는 모든 요청이 이 캐시를 함께 써요.
export const queryClient = new QueryClient();
```

```tsx
// 줄인 예시: 렌더마다 새로 만들면 브라우저에서 받아 둔 캐시를 잃어요.
export function QueryProvider({ children }: { children: React.ReactNode }) {
  const queryClient = new QueryClient();

  return <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>;
}
```

서버에서 인스턴스 하나를 계속 쓰면 한 요청에서 조회한 데이터가 다음 요청의 캐시에 남아요. 브라우저에서는 반대로, 렌더가 반복될 때마다 새로 만들면 받아 둔 캐시를 잃어요. 그래서 만드는 코드는 공유하되 인스턴스까지 공유하지는 않아요. 아래 코드는 `QueryClient`를 만드는 곳부터 화면에서 구독하는 곳까지 순서대로 이어져요.

## `getQueryClient`: 서버는 요청마다, 브라우저는 하나만

```typescript
// query-client.ts
import {
  QueryClient,
  defaultShouldDehydrateQuery,
  isServer,
} from '@tanstack/react-query';

function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        staleTime: 60_000,
      },
      dehydrate: {
        shouldDehydrateQuery: (query) =>
          defaultShouldDehydrateQuery(query) ||
          query.state.status === 'pending',
      },
    },
  });
}

let browserQueryClient: QueryClient | undefined;

export function getQueryClient() {
  if (isServer) {
    return makeQueryClient();
  }

  if (!browserQueryClient) {
    browserQueryClient = makeQueryClient();
  }

  return browserQueryClient;
}
```

`getQueryClient`는 서버에서 호출할 때마다 `makeQueryClient`로 새 인스턴스를 돌려줘요. 브라우저 쪽 인스턴스는 모듈에 보관해 Provider가 다시 렌더돼도 유지해요. `useState`에 보관하는 방법도 있지만, [TanStack Query 문서](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr)는 그 아래 코드가 suspend할 수 있는데 사이에 Suspense 경계가 없으면 쓰지 말라고 안내해요. 첫 렌더가 suspend되면 React가 만들어 둔 인스턴스를 버릴 수 있기 때문이에요.

`staleTime`은 받아 둔 데이터를 얼마 동안 새것으로 볼지 정하는 값이에요. 기본값 0으로 두면 서버가 방금 넘긴 데이터도 낡은 것으로 보여서, 브라우저가 화면을 띄우자마자 다시 조회해요. 같은 문서도 SSR에서는 0보다 크게 두라고 안내해요. `dehydrate` 설정은 뒤에서 다시 나와요.

서버 여부는 TanStack Query의 `isServer`로 구분해요. `typeof`로 직접 검사한다면 비교 대상도 문자열이어야 해요. 이 글의 처음 판에 있던 `typeof window !== undefined`는 항상 참이라 서버에서도 참이 돼요. `typeof`의 결과는 문자열이라 값 `undefined`와 같을 수 없거든요. 그래서 `typeof window === 'undefined'`처럼 비교해요.

## Provider에 브라우저 인스턴스 연결하기

```tsx
'use client';

import { QueryClientProvider } from '@tanstack/react-query';

import { getQueryClient } from './query-client';

export function QueryProvider({ children }: { children: React.ReactNode }) {
  const queryClient = getQueryClient();

  return (
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  );
}
```

`QueryClientProvider`는 React Context로 인스턴스를 내려 주는데, 서버 컴포넌트에서는 Context를 쓸 수 없어요. 그래서 Provider는 클라이언트 컴포넌트에 두고 `getQueryClient`가 돌려준 인스턴스를 넘겨요. layout이 이 Provider로 children을 감싸도, children으로 들어오는 서버 컴포넌트까지 클라이언트 컴포넌트가 되지는 않아요. 캐시를 구독하는 자리에 Provider를 두면서 서버 렌더링도 그대로 쓸 수 있어요.

## `queryOptions`로 같은 조회 가리키기

```typescript
import { queryOptions } from '@tanstack/react-query';

export const categoryOptions = queryOptions({
  queryKey: ['categories'],
  queryFn: async () => {
    const response = await fetch(`${process.env.NEXT_PUBLIC_API_URL}/categories`);
    if (!response.ok) throw new Error('카테고리를 불러오지 못했습니다.');
    return (await response.json()) as Category[];
  },
});
```

query key는 캐시에서 데이터를 찾는 이름이에요. 서버에서 prefetch할 때와 화면에서 구독할 때 query key를 따로 적으면, 같은 데이터를 요청하면서도 서로 다른 캐시를 볼 수 있어요. `queryOptions` 안에 key와 `queryFn`을 함께 두고 양쪽에서 가져다 써요. 카테고리 조회의 key나 요청 방식이 바뀌면 이 정의를 고쳐요.

이 `queryFn`은 서버와 브라우저에서 모두 실행돼요. 브라우저에서는 `NEXT_PUBLIC_`으로 시작하지 않는 환경변수를 읽을 수 없어서, 예제에서는 공개해도 되는 API 주소를 `NEXT_PUBLIC_API_URL`로 썼어요. 이 값은 `next build` 때 브라우저 코드에 들어가요. 서버에서만 쓰는 내부 주소가 따로 있다면 요청 함수를 환경별로 나눠야 해요.

## 서로 기다릴 이유가 없는 조회는 함께

```tsx
import { dehydrate, HydrationBoundary } from '@tanstack/react-query';

export default async function HomePage() {
  const queryClient = getQueryClient();

  await Promise.all([
    queryClient.prefetchQuery(categoryOptions),
    queryClient.prefetchQuery(integrationOptions),
  ]);

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <HomePageView />
    </HydrationBoundary>
  );
}
```

카테고리와 연동 목록은 서로의 결과가 필요하지 않아서 `Promise.all`로 함께 기다려요. `prefetchQuery`는 조회 결과를 `queryClient`의 캐시에 넣어요.

그런데 이 인스턴스는 Provider가 쓰는 인스턴스와 달라요. 서버에서는 `getQueryClient`를 부를 때마다 새로 만드니까요. 그래서 캐시를 직접 건네는 단계가 있어요. 조회가 끝나면 `dehydrate`로 캐시를 전달할 수 있는 값으로 꺼내 `HydrationBoundary`에 넘겨요. `HydrationBoundary`는 이 값을 Provider의 `QueryClient`에 채워요. 이제 하위 화면이 같은 key로 구독하면 서버가 받아 둔 데이터를 찾을 수 있어요.

이 예제처럼 완료된 조회만 보낼 때는 기본 dehydration 정책으로도 충분해요. 앞의 `QueryClient` 설정에서 pending 상태를 추가한 것은, prefetch가 끝나기를 기다리지 않고 Suspense로 스트리밍하는 화면도 지원하려는 설정이에요.

## 화면에서 구독하기

```tsx
'use client';

import { useSuspenseQuery } from '@tanstack/react-query';

export function HomePageView() {
  const { data } = useSuspenseQuery(integrationOptions);
  return <IntegrationList items={data} />;
}
```

`HomePageView`는 서버에서 썼던 `integrationOptions`로 `useSuspenseQuery`를 호출해요. 이 훅은 데이터가 아직 없으면 렌더를 멈추고 가장 가까운 Suspense 경계에 맡기므로, 컴포넌트 안에서는 `data`가 있다고 보고 쓸 수 있어요. key가 같으니 첫 렌더에서는 `HydrationBoundary`로 넘긴 데이터를 읽어요. 이후 invalidate나 refetch가 필요하면 브라우저의 `QueryClient`가 계속 처리해요. 서버가 한 번 조회했다는 이유로 별도의 상태에 데이터를 복사할 필요는 없어요.

지금까지의 흐름을 줄여서 적으면 이래요. `QueryClient`는 세 군데서 따로 만들어지고, 데이터는 `dehydrate`한 값으로 옮겨 다녀요.

```text
서버 컴포넌트 HomePage
  getQueryClient()          이 렌더만의 QueryClient
  await prefetchQuery(...)  캐시에 결과 저장
  dehydrate(queryClient)    전달할 수 있는 값으로 꺼냄
      │
      ▼
HTML을 만드는 서버 렌더
  Provider의 QueryClient를 새로 만들어 같은 값을 채움
  HomePageView가 그 데이터로 렌더됨
      │
      ▼
브라우저
  모듈에 보관한 QueryClient에 같은 값을 채움
  이후 invalidate와 refetch는 이 인스턴스가 처리
```

## 기다릴지 스트리밍할지는 조회마다 달라요

초기 HTML에 필요한 데이터는 위 예제처럼 `prefetchQuery`를 `await`해요. 다만 v5의 `prefetchQuery`는 실패를 호출부로 던지지 않으므로, 서버에서 오류를 받아 처리해야 하는 조회에는 `fetchQuery`를 써야 해요.

화면을 먼저 보내도 되는 조회는 pending dehydration을 켜고, 데이터를 쓰는 컴포넌트를 Suspense 안에 둘 수 있어요. 그 컴포넌트가 `useSuspenseQuery`로 구독하면 준비된 데이터를 이어서 받아요. `QueryClient`를 언제 만들지는 공통으로 정해도, 응답을 기다리는 방식까지 모든 화면에 같게 적용하지는 않아요.
