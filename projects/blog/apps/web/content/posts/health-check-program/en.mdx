Health checks originally sat outside Safedoc's program flow. Users viewed information on an external website and called to inquire. A partner asked to accept health-check reservations inside Safedoc, bringing them into the product.

I wrote this after the reservation feature officially launched. Users can now browse, apply, and pay through the benefits portal, while hospitals and operations manage programs and reservations in the admin services.

Safedoc needs to grow both partner hospitals and partner companies. Most users arrive through their companies. Too few hospitals make it hard to find a desired region or examination, while too few reservations reduce a hospital's reason to join. I cannot claim UI improvements solved that marketplace problem. My work made existing partners' health checks available for browsing and reservation within the portal.

The existing non-covered treatment program flow was established. Partners registered programs and requested review in hospital admin; operations checked regulations and service policy in Back-Office and approved them. Approved programs appeared in portal details, where users requested visits. I had originally built the hospital registration/review-request screens and Back-Office review screen.

Health checks could not simply reuse that flow. They might use corporate contract codes or require a deposit, and their configuration combined basic examinations with groups requiring a fixed number of choices. I clarified missing behavior and exceptions in the supplied specifications with the development lead and deputy lead.

The diagrams were redrawn from screens I checked directly. Code includes only the relevant parts.

## Restrict review by program rather than partner

Non-covered program review follows statuses. A partner requests registration, modification, or deletion, and hospital admin shows it as under review. Operations opens the review in Back-Office. Rejection leaves a reason in the partner's review history; approval creates the program and sets its visibility time.

Health checks bypass this review by specification. Operations registers their configuration directly in Back-Office, and hospitals only view it. Hospital admin therefore needs to block review entrypoints: the review-request menu, new/delete list actions, and request/delete-request detail actions. The detail form remains, with inputs locked.

I first applied this at partner level: block a partner with any health-check department. That also locked dermatology programs for a partner offering both. The restriction needed to apply to health-check programs, so I separated the decisions.

- Program details use the fetched program's department, without depending on the partner query.
- Menus and lists become read-only only for partners whose sole department is health checks. They have no programs requiring review.
- Mixed partners use the same form for new registration, old drafts, and rejected-request resubmission. Its category validation rejects health-check departments, including those already present in drafts or rejected requests. This avoided a one-off prop on the shared cascader and enforced the rule in one place.

Health-check detection was centralized too. Switching from department names to IDs had scattered six equality checks. I added `isHealthCheckDepartment` to the shared package, checked the department-list API for stable IDs across environments, and documented that next to the constant.

## Store one configuration and read it in four screens

A configuration contains required examinations and selection groups. Each group has a name, `pickCount`, and selectable items. Back-Office stores one configuration, read by four screens.

![Back-Office edits the configuration, hospital admin displays it locked, and the portal renders summary and selection views.](/images/posts/health-check-program/02.png)

*Back-Office edits the configuration, hospital admin displays it locked, and the portal renders summary and selection views.*

The central Back-Office rule is that an examination may appear in only one place. To avoid duplicates in one reservation, items already used by another group are disabled.

```typescript
/** owner 를 뺀 나머지 그룹이 이미 가져간 검사항목 id. 다른 그룹의 선택지는 잠근다. */
export function getItemIdsTakenByOtherGroups(values: CompositionValues, owner: 'included' | number): number[] {
  const fromIncluded = owner === 'included' ? [] : (values.includedItemIds ?? []);
  const fromGroups = (values.selectableGroups ?? []).flatMap((group, index) =>
    index === owner ? [] : (group?.itemIds ?? []),
  );
  return uniq([...fromIncluded, ...fromGroups]);
}
```

I also changed the operations preview. Its original table placed group and item names on one line and did not resemble portal content. I reused the portal's configuration section: basic examinations show their count, while selected examinations show categories and item chips by group. In the preview, View Items is visual only and groups stay expanded.

Changing a program's department away from health checks exposed save ordering. Program saving could succeed while clearing configuration failed. Reloaded details then disabled configuration fetching because the program was no longer a health check, and retries closed without clearing the remaining data. One save hook now remembers failed clearing and gives create/edit modals and details the same sequence. A test covers retrying it.

A configuration update was also rejected with `HEALTH_CHECK_ITEM_UNAVAILABLE`. The query response included an already deleted examination. I passed that response to the backend engineer instead of filtering it out and masking the problem in the UI.

## Split detail screens instead of adding conditions everywhere

A colleague originally built non-covered treatment details. I could add healthCheck conditions throughout that screen or split it into two views.

Health checks differ in three areas: no coupon query or coupon-adjusted price, an examination configuration section, and no phone consultation. Scattered branches would make both kinds of maintenance require reading both screens together.

![The detail page queries, records recently viewed programs, and chooses a screen. Each View assembles its own structure.](/images/posts/health-check-program/03.png)

*The detail page queries, records recently viewed programs, and chooses a screen. Each View assembles its own structure.*

I split on `programInfo.healthCheck`, the same value used to choose application forms.

```tsx
// 설명을 위해 줄이고 이름을 바꾼 코드예요. 페이지는 조회·최근 본 시술 저장·화면 선택만 해요.
function ProgramPage({ programId }: Props) {
  const { data: program } = useQuery(programDetailOptions(programId));
  useSaveRecentProgram(program);

  if (!program) return null;

  return program.programInfo.healthCheck ? (
    <HealthCheckProgramDetailView program={program} />
  ) : (
    <ProgramDetailView program={program} />
  );
}
```

Each View declares its full composition. They share existing sections, the top bar, logged-out and reservation buttons, post-authentication navigation, and event helpers. The price section accepts a slot below the price rather than rendering a coupon accordion itself. The treatment View supplies coupon pricing; the health-check View leaves it empty. Query-event shapes remain identical. Health checks fill coupon fields with the pre-discount price so analytics does not need separate interpretations.

Information, buttons, and queried data all differ, so separate Views make each structure readable. Application forms are split for the same reason. Health-check examinations, national screening eligibility, address, corporate codes, and withdrawal notices do not branch within the same form as treatment coupons and extra inquiries.

Hospital-detail program cards cannot use this flag because that list response does not include it. Cards detect health checks by department and omit phone consultation.

## Disable remaining chips after N choices

Each optional-examination group requires a fixed count, such as two imaging tests. The first request was to open the next group automatically when one became complete.

That would also advance while a user was replacing a previous choice: deselect one, select another, and the count is full again. The existing implementation also silently displaced the earliest choice when exceeding N, so users could miss a removed examination. I raised the forced-navigation problem and discussed the behavior again.

![Completing a group disables unselected chips. Selection confirmation becomes available only after all groups are complete.](/images/posts/health-check-program/04.png)

*Completing a group disables unselected chips. Selection confirmation becomes available only after all groups are complete.*

We chose to prevent excess selection in the UI. Full groups disable unselected chips; users deselect a choice before replacing it. The sheet does not advance on its own. Selection logic only adds and removes array entries.

```tsx
// 선택 로직은 넣고 빼기만 해요. 밀어내기와 pickCount 인자를 걷어냈어요.
export const toggleHealthCheckItem = (selected: number[], itemId: number) =>
  selected.includes(itemId) ? selected.filter((id) => id !== itemId) : [...selected, itemId];

// 넘치는 선택은 화면이 막아요(설명을 위해 줄인 코드예요).
const isFull = selected.length >= group.pickCount;
<Chip pressed={isSelected} disabled={isFull && !isSelected} onClick={() => onToggle(item.id)} />;
```

The design had no disabled-chip appearance. I requested one for the shared Chip and now use it in this sheet, its only current caller. Tests for displacing choices became tests for locking: full groups lock, incomplete groups remain selectable, and deselection unlocks them. Removing the lock code makes the tests fail.

## Design the return path from payment failures first

After completing the form and confirming the amount in a sheet, users proceed to payment. The backend contract changed during development. Previously, reservation creation came first and the payment screen created a separate order. Now one checkout call determines whether payment is needed. Corporate-funded and zero-cost applications finish there; only deposit reservations receive an order and open payment. Unpaid reservations are no longer left behind. I removed the old payment route, mocks, and E2E and rebuilt them for this flow.

![Each payment outcome has an explicit destination for the user.](/images/posts/health-check-program/05.png)

*Each payment outcome has an explicit destination for the user.*

On mobile, Toss Payments returns results only through redirects. The page reloads and memory state is lost. I store form values with the payment attempt's orderId in sessionStorage, restoring them once only when the attempt matches and current schema validation passes. Reading always deletes the saved value, valid or not, so a successful application's address and examination choices do not enter the next application.

Testing found a successful approval response whose status was REFUNDED. Only cards and simple payments were allowed, but the widget defaulted to quick bank transfer. Using it made the server immediately refund the payment and create no reservation. Available methods were controlled by payment-provider dashboard settings, not SDK options. On the frontend, I changed the result screen: instead of sending users to reservation history when nothing had been reserved or charged, it returns them to the application, restores input, and explains the reason, like a payment failure. Only an unknown outcome goes to the reservation list.

I also blocked duplicates. After checkout finished, waiting up to ten seconds for the SDK reopened the application button. Another click created another order. One mutation now spans order creation through opening payment and keeps the button locked. Repeated clicks before the confirmation sheet opens are blocked with the existing form-submission state instead of another flag.

## Test selection, saving, and payment

- Portal: Vitest covers group locking, the form schema requiring all three mandatory agreements, and storage/restoration/deletion of payment handoff values. E2E against the dev API checks the Toss test widget, restored input after payment failure, reservation-list navigation after approval-request failure, and corporate examination codes.
- Admin: specification tests check that a hospital offering both health checks and other departments can still register non-covered programs. Form tests exercise clearing the health-check configuration when switching departments. Dev-API E2E and contract tests verify that registration and reads connect to the server.
- Beyond tests, I manually ran non-covered program registration → review request → approval, treatment reservation, health-check registration, and health-check application → payment. This checked that existing flows remained usable alongside the new ones.
