<Summary>

AI 상담 화면에서 AI 답변과 상담사 메시지가 서로 다른 서버의 SSE로 왔어요. SSE는 서버가 HTTP 응답을 닫지 않고 메시지를 이어서 보내는 방식이에요. 화면에는 세션 SSE 하나만 연결하고, AI 스트림은 답을 생성하는 용도로만 남겼어요. 토큰 단위 표시를 포기한 대신 백엔드를 고치지 않고도 같은 답이 겹치지 않는 화면을 만들었어요.

</Summary>

## 두 서버의 메시지를 한 대화로 보여 줘야 했어요

서비스에 AI 상담 챗봇을 붙이는 일이었어요. 사용자는 대화창에서 AI에게 묻고, AI가 못 풀면 사람 상담사에게 넘어가요. 사용자에게는 이어지는 대화 하나인데, 화면은 백엔드 두 곳과 통신해야 했어요. 어느 쪽도 수정할 수 없었어요.

- **AI 챗 서비스**: 질문을 받으면 AI 답을 토큰 단위로 SSE로 보내요.
- **세션 백엔드**: 상담사 연결, 세션, 대화 히스토리를 맡아요. 상담사 메시지와 상태 변화를 SSE로 보내요.

SSE(Server-Sent Events)는 서버가 HTTP 응답을 닫지 않고 이벤트를 이어서 보내는 방식이에요. 응답 본문은 `data: ...` 줄이 계속 붙는 텍스트이고, 방향은 서버에서 브라우저 쪽뿐이에요. 토큰은 AI가 답을 만들면서 조금씩 내보내는 글자 조각이고요. 토큰을 받는 대로 화면에 붙이면 답이 타자 치듯 나타나요.

별개 서비스라 한쪽에 다른 쪽 응답까지 받아 달라고 할 수도 없었어요. 두 스트림을 한 대화처럼 보이게 만드는 일은 클라이언트에 남았어요. 토큰을 직접 쌓던 첫 구현에서 패널을 나누고 다시 합쳤고, 상태 관리도 `useReducer`와 자체 store를 거쳐 `@tanstack/ai`로 옮겼어요.

처음 만든 화면은 AI 챗 서비스만 연결했어요. `useMutation`으로 `POST /chat/stream`을 호출하고, SSE 응답을 직접 파싱해서 토큰이 올 때마다 `useState<Message[]>`의 메시지 끝에 붙였어요.

```tsx
// 초기: AI 응답 스트림을 직접 파싱해 화면에 흘림
async function* parseSSEStream(stream: ReadableStream<Uint8Array>) {
  const reader = stream.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';
    for (const line of lines) {
      const t = line.trim();
      if (t.startsWith('data: ')) yield JSON.parse(t.slice(6)) as StreamData;
    }
  }
}

// 토큰이 올 때마다 메시지 text에 이어 붙임
onData: (data) =>
  setMessages((prev) => updateMessage(prev, botMessageId, { text: current.text + data.content })),
```

네트워크에서 받는 조각은 줄 중간에서 끊길 수 있어요. 그래서 마지막 줄은 `buffer`에 남겼다가 다음 조각과 이어 붙이고, `data: `로 시작하는 줄만 JSON으로 읽어요. 브라우저의 `EventSource`는 GET 요청만 보낼 수 있어서 POST로 여는 이 스트림에는 쓸 수 없어요.

서버 히스토리에는 이런 안내가 있었어요.

> "무엇을 도와드릴까요? 상담사와 연결하려면 '상담원 연결'을 입력해 주세요."

AI 답변만 보여 주던 화면에 이 상담원 연결을 넣으려면 세션 백엔드의 SSE도 받아야 했어요. 세션 백엔드는 `start`로 세션을 열고 `subscribe`로 메시지와 상태를 구독하며, `message`와 `end`로 전송과 종료를 처리해요.

처음에는 서버가 나뉜 그대로 화면도 나눴어요. `AiChatPanel`은 AI 스트림을, `CounselingPanel`은 세션 SSE를 맡고 상담사 연결 버튼으로 전환했어요.

```typescript
// 상담사 연결이 '버튼'이던 시절: EventSource 로 세션 SSE 구독
const subscribeSse = useCallback((sid: string) => {
  const es = fetchCounselingSubscribe(sid);
  es.addEventListener('status', (e) => {
    const { status } = safeParse(e.data);
    if (status === 'counseling') append(createSystemMessage(GUIDE.accepted));
    if (status === 'ended') append(createSystemMessage(GUIDE.ended));
  });
  es.addEventListener('message', (e) => {
    const { message } = safeParse(e.data);
    if (message?.trim()) append(createCounselorMessage(message));
  });
}, []);
```

패널을 바꾸면 메시지 목록, 스크롤, 세션이 함께 갈라졌어요. 사용자에게는 이어지는 대화인데 코드에서는 다른 화면으로 넘어갔어요. `createUserMessage`, `createCounselorMessage`, `createSystemMessage`처럼 메시지를 만드는 함수와 타입도 출처마다 따로 생겼어요.

## 화면에 넣을 메시지는 세션 SSE에서만 받았어요

패널을 하나로 합치고 연결 버튼을 없앴어요. 서버 안내대로 "상담원 연결"을 입력하면 상담을 요청해요. 훅도 하나로 모았어요. 상담 연결을 기다리거나 상담 중이면 세션 백엔드로 보내고, 나머지 상태에서는 AI 챗 서비스로 보내요. 최상위 컴포넌트에서 패널을 고르던 분기는 없어졌어요.

이제 같은 목록에 두 종류의 답이 들어와요. 세션 SSE에는 AI 답과 상담사 답이 모두 들어오고, AI 챗 서비스는 AI 답만 보내요. 그러니 AI 답은 두 경로로 오고, 두 스트림을 다 그리면 같은 답이 겹칠 수 있어요. 지어낸 문장으로 보여 주면 이래요.

```text
AI 스트림: 배송은 + 내일 + 도착해요   (토큰을 이어 붙인 답)
세션 SSE : 배송은 내일 도착해요       (같은 답의 완성본)

둘 다 목록에 넣으면
  AI: 배송은 내일 도착해요
  AI: 배송은 내일 도착해요
```

둘을 합쳐 줄 서버가 없으니, 메시지가 겹치거나 순서가 어긋나지 않게 하려면 표시할 출처부터 정해야 했어요. 두 답을 모두 실어 나르는 세션 SSE만 화면에 연결했어요.

AI 스트림은 열어 두고 응답을 끝까지 읽되 화면에는 넣지 않아요. 답을 생성하게 하는 요청과 완성된 답을 받는 구독을 나눈 방식이에요.

```tsx
const response = await chatClient.post('/chat/stream', body, {
  adapter: 'fetch',
  responseType: 'stream',
  timeout: 30_000, // 30s 상한: 생성이 오래 걸릴 수 있어 넉넉히
});
const reader = (response.data as ReadableStream<Uint8Array>).getReader();
try {
  while (!(await reader.read()).done) {
    // 읽기만 하고 버린다. 표시는 세션 SSE가 담당한다.
  }
} finally {
  reader.releaseLock();
}
```

서버 내부는 볼 수 없어서 확증하지는 못했어요. 관찰한 동작으로는 AI 스트림을 최대 30초 동안 유지해야 생성이 진행되고 결과가 세션 SSE로 전달됐어요. 그래서 응답을 버리면서도 연결은 유지했어요.

이 결정으로 첫 구현에 있던 토큰 단위 표시를 포기했고, 질문마다 응답을 버리는 연결을 최대 30초까지 열어 둬야 했어요. 브라우저가 연결을 닫거나 타임아웃에 걸리면 생성도 영향을 받을 수 있어요. 그 대신 백엔드를 고치지 않아도 같은 답이 겹치지 않는 화면을 얻었어요. 표시할 메시지의 출처도 세션 SSE 하나로 줄었어요. 토큰 표시는 AI 서비스가 세션 SSE로 토큰도 보내게 되면 다시 붙일 수 있어요.

## 인증 헤더 때문에 EventSource를 쓰지 못했어요

세션 SSE를 붙일 때는 인증 헤더에서 막혔어요. 서버가 `Authorization: Bearer`를 요구했어요. 표준 `EventSource`는 커스텀 헤더를 보낼 수 없어서, fetch 기반인 [`@microsoft/fetch-event-source`](https://github.com/Azure/fetch-event-source)로 바꿨어요. 재연결 정책과 백그라운드 탭 연결(`openWhenHidden`)도 이 라이브러리로 처리했어요. 이 라이브러리는 기본으로 탭이 가려지면 연결을 닫기 때문에, 상담 메시지를 계속 받으려고 이 옵션을 켰어요. 의존성이 하나 늘고 재연결 간격도 직접 정해야 했지만, 서버가 요구하는 인증 헤더를 보낼 수 있었어요.

```typescript
export async function openSessionStream(sessionId, init) {
  const accessToken = await getCookie('accessToken');
  return fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
    signal: init.signal,
    openWhenHidden: true, // 백그라운드 탭에서도 상담 메시지 유지
    headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
    onmessage: (e) => init.onMessage(e.event, e.data),
    onerror: init.onError, // 지연(ms) 반환 시 재연결, throw 시 중단
  });
}
```

## 상태 전이와 연결 조건을 한곳으로 모았어요

상담 상태에 따라 전송할 서버와 구독 여부가 달라졌어요. 상태 값에는 클라이언트가 만든 것과 서버가 보낸 것이 섞여 있었어요.

```text
ai ──"상담원 연결"→ connecting ──(SSE: live)→ live ──(SSE: done)→ done
                                       └─(SSE: hold)→ hold
```

- `ai`: AI가 응답하는 상태예요. 클라이언트의 기본값이에요.
- `connecting`: AI 종료를 호출한 뒤 상담사 수락을 기다리는 상태예요. 클라이언트만 알아요.
- `live`, `hold`, `done`: 세션 SSE가 정하는 서버 상태예요.

클라이언트가 `connecting`으로 바꾼 사이에 서버가 `done`을 보내기도 해요. `useState`로 나눠 둔 값을 각자 바꾸다 보니 이런 순서를 다루기 어려워서 `useReducer`에 전이를 모았어요. `useReducer`는 어떤 일이 일어나면 상태가 어떻게 바뀌는지를 함수 하나에 적게 해 주는 React 훅이에요.

전이는 읽기 쉬워졌지만 연결은 여전히 effect 여러 곳에서 열고 닫았어요. 상태가 `live`여도 SSE가 닫혀 있을 수 있었어요. 그래서 연결 여부를 상태에서 계산하는 store를 만들었어요. 구독자가 있고, 세션이 있고, 종료되지 않았을 때만 연결해요.

`syncConnection()`은 이 세 값이 바뀔 때 연결을 맞춰요. React는 `useSyncExternalStore`로 스냅샷만 구독해요. `useSyncExternalStore`는 React 바깥에 있는 store를 `subscribe`와 `getSnapshot` 두 함수로 읽는 훅이라, 아래 `ChatStore`에 이 두 함수가 있어요. 재연결 중이거나 구독을 해제하는 중에 들어오는 이벤트는 이 조건만으로 해결되지는 않아요.

```tsx
export class ChatStore {
  private snapshot = ChatStore.initialSnapshot();
  private readonly listeners = new Set<Listener>();
  private readonly seen = new Set<number>(); // 메시지 id로 history와 SSE의 이중 표시 제거

  readonly subscribe = (listener: Listener) => {
    this.listeners.add(listener);
    this.syncConnection(); // 구독 시작: 필요하면 연결
    return () => {
      this.listeners.delete(listener);
      this.syncConnection(); // 구독 종료: 필요하면 해제
    };
  };
  readonly getSnapshot = () => this.snapshot;
}
```

AI 종료, 메시지 전송, AI 스트림 요청은 훅의 React Query에 두고, store에는 SSE 구독과 상태 전이를 남겼어요. 문서에 없는 메시지 형식도 store에서 받았어요. 단일 항목, 배열, `{messages: []}` 래퍼를 Zod `.catch()`로 읽어서 한 항목이 잘못돼도 나머지는 남겨요.

## 메시지 관리를 @tanstack/ai로 옮겼어요

자체 store로 동작은 연결했지만, `ChatStore`에는 메시지 누적, `seen`을 통한 ID 중복 제거, 구독 관리, 불변 스냅샷 갱신이 들어 있었어요. AI 메시지 라이브러리가 제공하는 기능을 직접 들고 있는 부분이었어요.

이후 토큰 스트리밍, tool call, 카드와 첨부가 있는 메시지도 지원할 계획이었어요. 메시지 형식을 늘리려면 텍스트 중심인 store를 다시 손봐야 해서 `@tanstack/ai`의 메시지 모델로 옮겼어요.

세션 SSE의 응답 형식은 [`useChat`](https://tanstack.com/ai/latest/docs/api/ai-react)이 받는 connection과 달랐어요. `useChat`은 이 라이브러리의 React 훅이고, connection은 그 훅이 메시지를 주고받는 통로예요. 서버 형식을 바꾸는 대신 `SubscribeConnectionAdapter`가 SSE를 읽어서 라이브러리에 넘기게 했어요. 링크한 문서는 최신 버전 기준이라 아래 코드와 이름이 다를 수 있어요.

```tsx
export function makeSessionConnection({ sessionId, onStatus }): SubscribeConnectionAdapter {
  return {
    async *subscribe() {
      const queue: StreamChunk[] = [];
      let notify = () => {};
      const controller = new AbortController();

      const accessToken = await getCookie('accessToken');
      fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
        signal: controller.signal,
        openWhenHidden: true, // 백그라운드 탭에서도 상담 메시지 유지
        headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
        onmessage: ({ event, data }) => {
          if (event === SseEvent.StatusChange) {
            const status = parseStatusEvent(safeParse(data));
            if (status) onStatus(status); // 서버 상태를 비즈니스 레이어로 전달
          } else {
            queue.push(...itemsToChunks(safeParse(data))); // 메시지를 표준 StreamChunk로 변환
          }
          notify();
        },
        onerror: () => 3000, // 3s 후 재연결
      }).catch(() => {});

      try {
        while (true) {
          if (queue.length === 0) await new Promise<void>((r) => (notify = r));
          yield* queue.splice(0); // 콜백의 push를 async generator의 pull로 연결
        }
      } finally {
        controller.abort(); // 소비 종료 시 SSE 닫기
      }
    },
    send: asyncNoop, // 전송은 이 채널에서 하지 않는다
  };
}
```

`subscribe`는 async generator예요. 값을 받는 쪽이 다음 값을 달라고 할 때마다 하나씩 내주는 함수인데, `fetchEventSource`는 반대로 메시지가 오면 콜백을 불러요. 이 둘을 잇느라 콜백은 메시지를 `queue`에 넣고 `notify`로 기다리는 쪽을 깨우고, generator는 큐가 비면 기다렸다가 쌓인 값을 내보내요. 상태 변화 이벤트는 큐에 넣지 않고 `onStatus`로 바로 넘겨요.

`send`는 비어 있어요. `useChat`의 connection은 보통 전송 뒤 응답 스트림을 돌려주지만, 여기서는 전송할 서버를 따로 고르고 수신은 세션 SSE로만 해요. 전송까지 어댑터에 넣으면 두 서버 중 어디로 보낼지 다시 처리해야 해서 구독만 남겼어요.

이 방식은 변환 어댑터를 직접 관리해야 하고, 서버나 라이브러리의 형식이 바뀌면 이 코드도 고쳐야 해요. 그 대신 서버 형식은 그대로 두고 메시지 누적과 구독 관리를 라이브러리에 넘길 수 있었어요.

옮긴 뒤에도 확인할 것은 남았어요. 위 코드는 두 채널을 잇는 구조를 보여 주려고 줄인 예제예요. 큐가 빈 채로 `await` 중이면 취소 신호가 와도 대기가 바로 풀리지 않을 수 있어서, 실제로는 취소를 SSE로 전달하고 큐도 깨워야 해요.

자체 store의 `seen`은 옮기지 않고 `useChat`의 `messageId` 누적에 맡겼는데, 히스토리와 SSE가 같은 ID를 보낼 때 하나로 합쳐지는지는 백엔드 재전송까지 포함해 더 봐야 해요. 대화 맨 위의 클라이언트 인사말도 서버 히스토리의 인사말과 겹칠 수 있어서, 히스토리가 비었을 때만 넣을지 확인할 부분이에요.

화면도 아직 텍스트 한 줄짜리 `Message`를 받아서, `UIMessage`를 변환할 때 `parts`의 카드, tool, 첨부가 버려져요. 이 형식을 보여 주려면 렌더러가 `parts`를 직접 그려야 해요.

### useChat의 초기화와 구독 시점을 맞췄어요

connection 형식을 맞췄는데도 히스토리가 안 보이고 실시간 메시지가 오지 않는 경우가 있었어요. 남은 문제는 시점이었어요.

`useChat`은 `initialMessages`를 mount할 때 한 번만 읽어요. 히스토리는 React Query로 비동기로 오니까 첫 렌더에는 비어 있었고, 나중에 도착해도 화면에 나오지 않았어요. 그래서 `useSuspenseQuery`로 히스토리가 준비된 뒤에 대화 컴포넌트를 mount하게 바꿨어요. `useSuspenseQuery`는 데이터가 준비될 때까지 그 컴포넌트의 렌더를 멈춰 두는 React Query 훅이에요. 조회가 끝날 때까지 대화 화면이 늦게 뜨지만, 첫 렌더부터 히스토리가 `initialMessages`에 들어가요.

실시간 메시지는 제 실수였어요. `live: true`를 넘기지 않으면 구독이 시작되지 않는데, 이걸 빠뜨려서 한동안 메시지가 들어오지 않았어요. `useChat({ connection, initialMessages, live: true })`로 바꿨어요.

패널을 닫으면 컴포넌트가 unmount되고 구독이 해제되면서, 어댑터의 `finally`가 `controller.abort()`로 SSE를 닫아요.

### 서버가 보낼 수 있는 상태를 타입으로 좁혔어요

처음에는 `connecting`을 서버 상태와 구분하려고 `serverStatus`와 `isConnecting`을 따로 뒀어요. 나중에는 상태 값을 하나로 두고, 서버에서 받을 수 있는 값의 타입을 `ServerStatus`로 좁혔어요.

```tsx
type ServerStatus = 'ai' | 'live' | 'hold' | 'done'; // SSE와 히스토리가 주는 상태
type ChatStatus = ServerStatus | 'connecting'; // 클라이언트 전용 상태를 더한 타입

const [status, setStatus] = useState<ChatStatus>(/* 히스토리 마지막 status ?? 'ai' */);
// onStatus는 ServerStatus만 받으므로 이 경로로 connecting을 넘기면 타입 오류가 난다
const connection = useMemo(() => makeSessionConnection({ sessionId, onStatus: setStatus }), [sessionId]);
```

`connecting`은 키워드 핸들러만 설정해요. 서버 이벤트를 받는 `onStatus`로 `connecting`을 넘기면 타입 오류가 나요.

## 회고

패널을 나눈 건 서버 구조를 화면에 그대로 옮긴 결정이었어요. 사용자는 대화 하나를 보고 있는데 코드만 둘로 갈라졌고, 다시 합치고 나서야 패널을 고르는 분기가 사라졌어요. 서버가 몇 개든 화면은 사용자가 보는 단위로 나눠야 한다는 걸 이때 배웠어요.

타입을 과하게 믿은 적도 있어요. `onStatus`를 `ServerStatus`로 좁히고 코드 주석에 SSE가 `connecting`을 덮을 수 없다고 적었어요. 이 글을 다시 검토하면서 틀렸다는 걸 알았어요. 타입이 막는 건 그 경로로 `connecting`이라는 값을 넘기는 일뿐이고, `live`나 `done`이 도착하면 지금의 `connecting`은 그대로 덮여요. 타입은 넘길 수 있는 값을 정할 뿐 이벤트가 도착하는 순서까지 정해 주지는 않았어요. 어떤 전이를 받아들일지는 아직 따로 정해야 해요.

대화 목록에 무엇을 넣을지도 겪고 나서 정했어요. 전송 실패를 에러 버블로 넣었더니 엉뚱한 응답 아래에 붙어서 세션이 끝날 때까지 남았어요. 실패 안내는 대화 내용과 성격이 달라서 공용 `toast.warning`으로 옮겼어요. 초기 상태를 `.at(-1)`로 읽으면 status 없는 메시지를 고를 수 있어서 `.findLast(i => i.status)`로 바꿨고, AI 종료 중에도 전송되던 문제는 그 호출을 `isPending`에 넣어 막았어요.
