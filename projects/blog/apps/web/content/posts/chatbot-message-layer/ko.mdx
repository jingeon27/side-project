답변 생성과 최종 메시지 수신이 서로 다른 SSE로 오던 화면을 연결했어요. 메시지가 중복되거나 순서가 어긋나지 않도록 역할을 나눴어요.

</Summary>

![두 SSE의 메시지가 어댑터를 거쳐 하나의 대화 화면으로 모이는 일러스트](/images/covers/chatbot-message-layer.png)

*글의 주제를 표현한 일러스트예요. 실제 서비스 화면은 아니에요.*

쇼핑몰에 AI 상담 챗봇을 붙였다. 프론트엔드 팀은 백엔드를 수정할 수 없었고, 서로 다른 두 서비스에 연결해야 했다.

- **AI 챗 서비스** — 질문을 보내면 AI 답을 토큰 단위로 스트리밍(SSE)해주는 백엔드.
- **세션 백엔드** — 상담사 연결, 세션 관리, 대화 히스토리를 담당하는 또 다른 백엔드. 상담사 메시지와 상태 변화를 SSE로 내려준다.

둘은 서로 다른 서비스였고, **둘 다 우리가 수정할 수 없었다.** 보통이라면 백엔드에 "두 채널을 합쳐서 한 번에 내려달라"고 부탁하면 된다. 그런데 합쳐줄 주체가 없었다 — 둘 다 우리 영역이 아니었고, 애초에 별개 서비스라 어느 한쪽에 "상대 응답도 병합해 달라"고 맡길 수도 없었다.

즉 "쇼핑몰에 AI 상담 챗봇 붙이기"는, 서로 다른 두 외부 백엔드의 스트리밍을 **클라이언트에서 하나의 대화 타임라인으로 봉합하는** 문제였다. 그 봉합을 다섯 번 갈아엎었고, 이 글은 그 기록이다.

> 순수 AI 토큰 스트리밍 → 상담사 버튼 패널 분리 → 키워드 통합 → useReducer 상태머신 → useSyncExternalStore 자체 store → @tanstack/ai 어댑터

## 시작은 평범한 AI 챗봇이었다

```text
src/modules/entities/chat/chatbot/
├─ api/chatbot.api.ts        # AI 챗 서비스 /chat/stream 호출 + SSE 파싱
├─ model/use-chat-stream.hook.ts
├─ model/use-chat-session.hook.ts
└─ ui/ (MessageBubble, TypingIndicator, MarkdownContent ...)
```

처음 요구사항은 단순했다. AI 챗 서비스에 질문을 던지고, 응답을 받아 보여준다. 이 API는 우리가 설계한 것도, 고칠 수 있는 것도 아니었다. POST /chat/stream이 답을 SSE로 흘려줬고, 우리는 그걸 직접 파싱해 토큰을 화면에 실시간 누적했다.

```tsx
// 초기 — AI 응답 스트림을 직접 파싱해 화면에 흘림
async function* parseSSEStream(stream: ReadableStream<Uint8Array>) {
  const reader = stream.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';
    for (const line of lines) {
      const t = line.trim();
      if (t.startsWith('data: ')) yield JSON.parse(t.slice(6)) as StreamData;
    }
  }
}

// 토큰이 올 때마다 메시지 text 에 이어붙임 (= 진짜 스트리밍 UI)
onData: (data) =>
  setMessages((prev) => updateMessage(prev, botMessageId, { text: current.text + data.content })),
```

처음에는 스트리밍 라이브러리 없이 useState&lt;Message\[\]>와 useMutation으로 받은 토큰을 화면에 쌓았다.

그리고 서버 히스토리가 내려주던 안내 문구엔 이미 한 줄이 있었다:

> "무엇을 도와드릴까요? 상담사와 연결하려면 '상담원 연결'을 입력해 주세요."

문제의 씨앗은 저 "상담원 연결"이었다.

## 상담사 연결 버튼을 추가했다

AI가 못 풀면 사람 상담사에게 넘겨야 했다. 그런데 상담사 응답은 AI 챗 서비스가 아니라 **전혀 다른 백엔드(세션 백엔드)**의 세션 SSE에서 왔다. start / subscribe / message / end로 세션을 열고 상담사 메시지, 상태 변화를 구독한다.

여기서 핵심: AI 답과 상담 답은 같은 API의 두 채널이 아니라, 클라가 각각 직접 호출하는 두 개의 별개 외부 백엔드였다. 둘을 합쳐주는 엔드포인트는 없었고, 합쳐달라고 부탁할 주체도 없었다.

첫 구현은 두 백엔드를 그대로 UI로 옮긴 것이었다. AiChatPanel(AI 스트림)과 CounselingPanel(세션 SSE)을 나누고, "상담사 연결" 버튼으로 모드를 전환했다.

```typescript
// 상담사 연결이 '버튼'이던 시절 — EventSource 로 세션 SSE 구독
const subscribeSse = useCallback((sid: string) => {
  const es = fetchCounselingSubscribe(sid);
  es.addEventListener('status', (e) => {
    const { status } = safeParse(e.data);
    if (status === 'counseling') append(createSystemMessage(GUIDE.accepted));
    if (status === 'ended') append(createSystemMessage(GUIDE.ended));
  });
  es.addEventListener('message', (e) => {
    const { message } = safeParse(e.data);
    if (message?.trim()) append(createCounselorMessage(message));
  });
}, []);
```

여기서부터 균열이 보였다. "AI로 대화하다 상담사로 넘어간다"는 건 모드 전환이 아니라 같은 타임라인의 연속인데, 패널을 둘로 쪼개니 전환 시점에 메시지 목록, 스크롤, 세션이 두 컴포넌트로 갈라졌다. 메시지 생성 함수도 채널별로 따로 놀았다 — createUserMessage, createCounselorMessage, createSystemMessage. 같은 "메시지"인데 출처마다 타입이 달랐다.

## 연결 키워드로 바꾸고 패널을 하나로 합쳤다

두 가지를 동시에 정리했다.

1. **연결 버튼 제거 → "상담원 연결" 키워드로 전환.** UI에서 '모드 버튼'이라는 상태를 없앴다.
2. **패널 통합.** 최상위 ai/counseling 분기를 지우고 단일 패널 + 단일 훅으로. 전송은 상태(status)로 라우팅만 한다 — 상담 연결 중/진행 중이면 세션 백엔드로, 그 외엔 AI 챗 서비스로.

UI는 하나가 됐다. 그 대가로 두 가지 골치가 따라왔다 — 표시 채널 문제와 상태 문제.

### AI 스트림은 연결만 유지하게 됐다

통합하면서 가장 큰 결정을 내렸다. **화면에 표시하는 채널을 세션 백엔드의 SSE 하나로 일원화한다.** 이유는 분명했다 — AI 답과 상담사 답이 한 타임라인에 섞여야 하는데, 두 출처를 다 실어 나르는 곳이 세션 SSE뿐이었다. AI 챗 서비스 스트림은 AI 답만 주고, 세션 SSE는 AI, 상담사 양쪽을 다 내려줬다.

문제는 합칠 방법이었다. 보통이라면 백엔드가 둘을 병합해 한 채널로 내려주면 된다. 그런데 두 백엔드 다 우리 영역이 아니었고, 애초에 서로 다른 서비스라 어느 쪽에도 병합을 맡길 수 없었다. 합칠 곳이 클라이언트밖에 없었다.

그 결과 AI 챗 서비스 스트림은 표시 역할을 잃었다. 한때 토큰을 화면에 흘리던 그 스트림이, 이제는 "생성을 끝까지 진행시키기 위해 연결만 유지하고 버리는" 펌프(drain-only)가 됐다.

```tsx
// 한때 화면에 흘리던 AI 스트림이 → drain-only(읽고 버림) 로 강등됨
const response = await chatClient.post('/chat/stream', body, {
  adapter: 'fetch',
  responseType: 'stream',
  timeout: 30_000, // 30s 상한 — 생성이 오래 걸릴 수 있어 넉넉히
});
const reader = (response.data as ReadableStream<Uint8Array>).getReader();
try {
  while (!(await reader.read()).done) {
    // 읽기만 하고 버린다. 표시는 세션 SSE 가 담당.
  }
} finally {
  reader.releaseLock();
}
```

스트리밍 응답을 읽고 화면에 표시하지 않는 이유는 두 백엔드를 수정할 수 없었기 때문이다. 내부를 볼 수 없어 확증하진 못했지만, 클라이언트가 AI 스트림을 최대 30초 동안 유지해야 서버 측 생성이 진행되고, 그 결과가 세션 백엔드에 쌓여 세션 SSE로 전달되는 구조로 보였다. 클라이언트에서는 연결을 유지하고 표시는 세션 SSE에 맡겼다. 다만 생성 수명이 브라우저 연결과 타임아웃에 묶이는 문제는 남았다.

## 인증 헤더 때문에 EventSource를 쓰지 못했다

표시를 세션 SSE로 모으자 인증 문제가 터졌다. 세션 SSE 엔드포인트는 Authorization: Bearer를 요구하는데, 브라우저 표준 EventSource는 커스텀 헤더를 못 보낸다. 그래서 @microsoft/fetch-event-source로 갈아탔다 — fetch 기반이라 Bearer를 붙일 수 있고, 재연결 정책과 백그라운드 탭 유지(openWhenHidden)도 제공한다.

```typescript
export async function openSessionStream(sessionId, init) {
  const accessToken = await getCookie('accessToken');
  return fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
    signal: init.signal,
    openWhenHidden: true, // 백그라운드 탭에서도 상담 메시지 유지
    headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
    onmessage: (e) => init.onMessage(e.event, e.data),
    onerror: init.onError, // 지연(ms) 반환 시 재연결, throw 시 중단
  });
}
```

작은 변경 같지만, "표준 브라우저 API가 외부 API의 인증 모델과 안 맞는다"는 건 남이 그린 API를 소비할 때 흔히 만나는 현실적 제약이다.

## 흩어진 상태 전이를 useReducer로 모았다

통합 패널의 status는 단순 플래그가 아니었다. 세션 백엔드의 흐름이 그대로 상태 전이로 박혀 있었다:

```text
ai ──"상담원 연결"→ connecting ──(SSE: live)→ live ──(SSE: done)→ done
                                       └─(SSE: hold)→ hold
```

- ai : AI가 응답하는 상태 (클라 기본값)
- connecting : AI 종료 호출 후 상담사 수락을 기다리는, 클라이언트만 아는 상태
- live/hold/done : 세션 SSE가 권위를 갖는 서버 상태

즉 클라가 만든 상태와 서버가 내려주는 상태가 한 변수에 섞인다. useState 몇 개로는 "connecting인데 SSE가 갑자기 done을 쐈을 때" 같은 경계에서 정합성이 깨졌다. 전이를 useReducer 상태머신 한곳에 모았다.

전이는 정리됐다. 그런데 effect 곳곳에서 SSE 연결을 열고 닫다 보니 "상태는 live인데 연결은 닫힘" 같은 불일치가 가능했다. 클라이언트와 서버 상태가 한 변수에 섞인 문제는 이후 @tanstack/ai로 옮기면서 타입을 나눠 처리했다.

## store가 SSE 연결을 관리하고 React는 스냅샷을 구독했다

> SSE 연결은 명령형으로 열고 닫을 게 아니라, 상태에서 파생되는 값이어야 한다. 연결 = (구독자 있음) ∧ (세션 있음) ∧ (종료 아님)

입력이 바뀌면 syncConnection()이 연결을 맞춰요. SSE를 열고 닫는 조건을 store 한곳으로 모으고, React는 useSyncExternalStore로 스냅샷을 구독하게 했어요. 재연결과 구독 해제 중에 이벤트가 들어오는 경우는 별도로 확인해야 해요.

```tsx
export class ChatStore {
  private snapshot = ChatStore.initialSnapshot();
  private readonly listeners = new Set<Listener>();
  private readonly seen = new Set<number>(); // 메시지 id 로 history+SSE 이중표시 제거

  readonly subscribe = (listener: Listener) => {
    this.listeners.add(listener);
    this.syncConnection(); // 구독 시작 → 필요하면 연결
    return () => {
      this.listeners.delete(listener);
      this.syncConnection(); // 구독 종료 → 필요하면 해제
    };
  };
  readonly getSnapshot = () => this.snapshot;
}
```

역할도 명확히 갈랐다 — 네트워크 호출(AI 종료 / 메시지 전송 / AI 스트림)은 훅의 React Query가, SSE 구독과 상태 전이는 store가. 또 하나의 외부 API 현실도 여기서 처리했다. 두 백엔드의 메시지 항목은 API 문서에 정의도 없는 제각각 페이로드였다(스키마를 우리가 정할 수 없었다). 그래서 단일 항목 / 배열 / &#123;messages:\[\]&#125; 래퍼를 zod .catch()로 전부 방어 파싱해, 한 항목이 깨져도 전체가 버려지지 않게 했다.

이 버전은 잘 돌았다. 그런데도 갈아엎었다.

## 메시지 관리를 @tanstack/ai로 옮겼다

ChatStore가 하는 일을 가만히 보면 — 메시지 누적, ID 기반 중복 제거(seen), 구독 생명주기, 스냅샷 불변 갱신. 전부 "구독되는 메시지 리스트 스토어"의 일반적인 일이고, AI 메시지 프레임워크가 이미 푸는 문제다.

이후에는 토큰 스트리밍과 tool call, 카드와 첨부를 포함한 메시지를 지원할 계획이었다. 이런 기능을 넣으려면 자체 store의 메시지 모델도 바꿔야 했다. useSyncExternalStore로 만든 store를 쓰던 시점에 라이브러리의 메시지 모델로 옮기기로 했다.

문제는 마지막 현실 — 세션 SSE는 라이브러리가 기대하는 표준 포맷이 아니었다. 외부에서 설계된 응답 포맷은 @tanstack/ai의 useChat이 기대하는 표준 connection 모양이 아니었고, 우리는 그 포맷을 바꿀 수 없었다. 그래서 세션 SSE를 표준 인터페이스 뒤에 감추는 어댑터를 만들었다: SubscribeConnectionAdapter.

```tsx
export function makeSessionConnection({ sessionId, onStatus }): SubscribeConnectionAdapter {
  return {
    async *subscribe() {
      const queue: StreamChunk[] = [];
      let notify = () => {};
      const controller = new AbortController();

      const accessToken = await getCookie('accessToken');
      fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
        signal: controller.signal,
        openWhenHidden: true,
        headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
        onmessage: ({ event, data }) => {
          if (event === SseEvent.StatusChange) {
            const status = parseStatusEvent(safeParse(data));
            if (status) onStatus(status); // 서버 상태 → 비즈니스 레이어 (ServerStatus 타입)
          } else {
            queue.push(...itemsToChunks(safeParse(data))); // 메시지 → 표준 StreamChunk
          }
          notify();
        },
        onerror: () => 3000, // 3s 후 재연결
      }).catch(() => {});

      try {
        while (true) {
          if (queue.length === 0) await new Promise<void>((r) => (notify = r));
          yield* queue.splice(0); // 콜백(push) → async generator(pull) 브리지
        }
      } finally {
        controller.abort(); // 소비 종료 시 SSE 닫기
      }
    },
    send: asyncNoop, // ← 전송은 이 채널이 아니다
  };
}
```

send가 빈 함수인 게 이 아키텍처의 정체를 드러낸다. 보통 Connection은 "보내면 응답 stream을 돌려준다"는 모델이지만, 우리는 두 백엔드 구조 탓에 송신 채널과 수신 채널이 분리돼 있다 — 전송은 출처별 라우팅(세션 백엔드 또는 AI 스트림), 표시는 세션 SSE 한 곳. 그래서 "send가 stream을 반환한다"는 추상화에 끼워 넣을 때 send 절반은 자연히 비게 된다.

### 라이브러리의 생명주기 가정에 mount를 맞추는 게 진짜 일이었다

어댑터만 만들면 끝일 줄 알았지만, 정작 시간을 많이 쓴 건 useChat의 가정이었다.

- useChat은 initialMessages를 mount 시 단 1회만 읽는다. 그런데 히스토리는 React Query로 비동기로 온다 → 첫 렌더엔 비어 있어서 히스토리가 안 떴다. 해결은 useSuspenseQuery로 히스토리가 준비된 뒤에 대화 컴포넌트를 mount(Suspense 게이팅)하는 것. 그러면 생성 시점의 initialMessages가 곧 히스토리가 된다.
- live: true를 안 넘기면 구독 자체가 안 일어난다. 이걸 빠뜨려서 한동안 실시간 메시지가 안 들어왔다. useChat(&#123; connection, initialMessages, live: true &#125;)로 해결.
- 패널을 닫으면 컴포넌트가 unmount → 구독 해제 → 어댑터의 finally에서 controller.abort()로 SSE가 닫힌다.

### 클라이언트와 서버의 상태 타입을 나눴다

클라이언트의 connecting과 서버 상태를 구분하기 위해 처음에는 serverStatus와 isConnecting을 따로 뒀다. 이후 상태 값은 하나로 유지하고 타입을 나누는 방식으로 바꿨다.

```tsx
type ServerStatus = 'ai' | 'live' | 'hold' | 'done';   // SSE/히스토리가 주는 권위 상태
type ChatStatus = ServerStatus | 'connecting';          // + 클라 전용 전이 상태

const [status, setStatus] = useState<ChatStatus>(/* 히스토리 마지막 status ?? 'ai' */);
// onStatus 가 ServerStatus 타입이라, SSE 는 connecting 을 타입상 절대 못 덮는다
const connection = useMemo(() => makeSessionConnection({ sessionId, onStatus: setStatus }), [sessionId]);
```

위 원본 예제의 주석은 타입이 보장하는 범위보다 강한 주장이에요. connecting은 키워드 핸들러에서 클라이언트가 직접 설정해요. onStatus는 ServerStatus만 받으므로 서버 이벤트 경로에서 connecting을 전달하는 호출은 타입 검사에서 걸려요. 다만 live나 done을 전달하면 현재 connecting은 바뀔 수 있어요. 상태 전이의 순서까지 타입이 보장하지는 않으므로, 허용할 전이는 별도로 확인해야 해요.

### 메시지 중복 제거는 추가 검증이 필요했다

ChatStore의 seen(메시지 id 중복 제거)은 어댑터로 포팅하지 않았다. 대신 메시지 누적, dedup, 생명주기를 useChat에 넘겼다. 다만 솔직히 — 이건 "라이브러리가 dedup해 줌이 검증됐다"가 아니라, 명시적 dedup을 제거하고 라이브러리의 messageId 기반 누적에 위임한 것이다. 히스토리(initialMessages)와 SSE가 같은 id를 쓸 때 라이브러리가 합쳐주는지는 백엔드 재전송 시나리오로 더 검증해야 할 빚으로 남았다.

## 전송 실패 처리를 고치고 남은 문제를 확인했다

리뷰를 거치며 마무리를 다듬었다.

- **전송 실패 피드백**: 처음엔 에러 메시지 버블을 직접 그렸는데, 실패가 무관한 응답 밑에 붙고 세션 내내 안 사라지는 문제가 있었다. 공용 토스트(toast.warning)로 바꿔 정리했다.
- **status 추론**: 초기값을 .at(-1)(마지막 항목)에서 뽑다가, 마지막에 status가 없는 항목이 오면 어긋났다 → .findLast(i => i.status)로 보정.
- **입력 잠금**: connecting(AI 종료 진행 중) 동안 입력이 안 막혀 전송과 레이스가 났다 → isPending에 그 호출을 합쳐 차단.
- **첫 안내 메시지**: 클라이언트 인사말을 대화 맨 위에 추가했다. 다만 서버 히스토리의 인사말과 중복될 수 있어 검증 대상으로 남겼다. 히스토리가 비어 있을 때만 노출하는 방법도 확인해야 한다.

남은 빚도 솔직히 적어둔다.

- **@tanstack/ai로 옮긴 값을 아직 다 못 뽑았다.** 지금은 라이브러리의 UIMessage를 자체 Message(텍스트 한 줄)로 역변환해 렌더하는데, 미래 기능(parts/tool/첨부)은 전부 UIMessage.parts에 실려 온다. 즉 베팅의 목적물을 렌더 직전에 버리는 셈이다. 다음 작업은 렌더러가 parts를 직접 분기하게 바꾸는 것 — 추상화는 "도입"이 아니라 "값을 뽑을 때" 완성되니까.
- **drain-only 펌프의 수명**이 브라우저 연결 + 30초 타임아웃에 종속된다는 점, **history↔SSE dedup 위임 검증** — 둘 다 백엔드를 볼 수 있게 되거나 부하 시나리오로 확인해야 한다.
- AI 챗 서비스가 세션 SSE로도 토큰을 내려주면, 처음에 제공하던 토큰 스트리밍을 라이브러리 위에서 다시 구현할 수 있다.

## 지금 남아 있는 작업

화면에 표시할 메시지는 세션 SSE에서 받고, 전송은 AI와 상담 상태에 따라 나누고 있어요. 두 채널의 역할을 정한 뒤에는 화면에서 메시지 출처를 따지는 코드가 줄었어요.

다만 메시지 ID가 재전송되는 경우와 빈 큐에서 구독을 끝내는 경우는 더 확인해야 해요. 위 어댑터 예제의 finally만으로는 진행 중인 await가 즉시 끝난다고 볼 수 없어요. 소비자의 취소 신호를 연결하고, 기다리는 큐를 깨우는 경로까지 있어야 연결 종료를 검증할 수 있어요. 예제는 두 채널을 연결하는 구조를 줄여 보여 준 코드예요.

다음에는 UIMessage.parts를 그대로 그리도록 바꾸고, 히스토리와 SSE에 같은 메시지가 들어오는 경우를 재현하려고 해요. 라이브러리로 옮긴 뒤에도 직접 확인해야 할 부분이 남아 있어요.
