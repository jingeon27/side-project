## One conversation, two servers

The job was adding an AI support chatbot to a service. A user asks the AI in a chat window, and when the AI cannot solve the problem, a human counselor takes over. To the user that is one continuing conversation, but the screen had to talk to two backends, and I could change neither of them.

- **AI chat service**: takes a question and streams the AI answer token by token over SSE.
- **Session backend**: handles counselor connections, sessions, and conversation history. It sends counselor messages and status changes over SSE.

SSE (Server-Sent Events) lets a server keep an HTTP response open and send events as they come. The response body is text made of a growing series of `data: ...` lines, and it flows one way, from the server to the browser. Tokens are the small pieces of text an AI emits while it builds an answer. Attach them to the screen as they arrive and the answer appears as if it were being typed.

These were separate services, so asking one to consume the other's output was not an option. Making the two streams look like one conversation fell to the client. I moved from accumulating tokens by hand to separate panels and back to one panel, then from `useReducer` through a custom store to `@tanstack/ai`.

The first screen connected only to the AI chat service. `useMutation` called `POST /chat/stream`, and I parsed the SSE response by hand, appending each token to a message in `useState<Message[]>`.

```tsx
// Initially: parse the AI response stream and render it directly
async function* parseSSEStream(stream: ReadableStream<Uint8Array>) {
  const reader = stream.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';
    for (const line of lines) {
      const t = line.trim();
      if (t.startsWith('data: ')) yield JSON.parse(t.slice(6)) as StreamData;
    }
  }
}

// Append each token to the message text
onData: (data) =>
  setMessages((prev) => updateMessage(prev, botMessageId, { text: current.text + data.content })),
```

Chunks off the network can break in the middle of a line, so the last line waits in `buffer` to join the next chunk, and only lines starting with `data: ` get read as JSON. The browser's `EventSource` can only send GET requests, so it cannot be used for a stream opened with POST.

The server's history already included this instruction:

> "How can I help? To connect to a counselor, enter 'connect to an agent'."

Adding that connection to a screen that only showed AI answers meant receiving the session backend's SSE too. Its `start` opens a session, `subscribe` delivers messages and statuses, and `message` and `end` send messages and close the session.

I first split the screen the way the servers were split. `AiChatPanel` handled the AI stream, `CounselingPanel` handled session SSE, and a button switched between them.

```typescript
// When connecting to an agent was a button: subscribe to session SSE with EventSource
const subscribeSse = useCallback((sid: string) => {
  const es = fetchCounselingSubscribe(sid);
  es.addEventListener('status', (e) => {
    const { status } = safeParse(e.data);
    if (status === 'counseling') append(createSystemMessage(GUIDE.accepted));
    if (status === 'ended') append(createSystemMessage(GUIDE.ended));
  });
  es.addEventListener('message', (e) => {
    const { message } = safeParse(e.data);
    if (message?.trim()) append(createCounselorMessage(message));
  });
}, []);
```

Switching panels also split the message list, scroll position, and session. The user saw one continuing conversation while the code moved to another screen. Message constructors and types separated by source as well: `createUserMessage`, `createCounselorMessage`, and `createSystemMessage`.

## Displaying messages from session SSE only

I merged the panels and removed the button. Entering the keyword from the server's instruction now requests a counselor. One hook handles sending: it goes to the session backend while connecting or counseling, and to the AI chat service otherwise. The branch in the top-level component that chose a panel went away.

Both kinds of answer now land in one list. Session SSE carries AI and counselor answers, while the AI chat service carries only AI answers. AI answers therefore arrive by two routes, and drawing both streams could show the same answer twice. A made-up sentence shows it.

```text
AI stream  : Your order + arrives + tomorrow   (an answer joined from tokens)
Session SSE: Your order arrives tomorrow       (the finished copy of that answer)

Put both in the list and you get
  AI: Your order arrives tomorrow
  AI: Your order arrives tomorrow
```

With no server to merge the two, keeping messages from doubling up or falling out of order meant choosing one source for display first. I connected the screen only to session SSE, which carries both kinds of answer.

The AI stream stays open and gets read to the end, but its response never reaches the screen. The request that triggers generation is now separate from the subscription that delivers the finished answer.

```tsx
const response = await chatClient.post('/chat/stream', body, {
  adapter: 'fetch',
  responseType: 'stream',
  timeout: 30_000, // Allow up to 30 seconds for generation
});
const reader = (response.data as ReadableStream<Uint8Array>).getReader();
try {
  while (!(await reader.read()).done) {
    // Read and discard. Session SSE owns display.
  }
} finally {
  reader.releaseLock();
}
```

I could not see inside the servers, so I never confirmed this. From the behavior I observed, generation only proceeded and reached session SSE while the AI stream stayed open, for up to 30 seconds. So the connection stayed open even though its response was discarded.

This decision gave up the token-by-token display from the first version and meant holding a connection open for up to 30 seconds per question just to throw its response away. A browser disconnect or timeout can also affect generation. What I got in exchange was a screen that does not show the same answer twice, with no backend changes. Displayed messages also came down to one source, session SSE. Token display could return if the AI service sends tokens over session SSE.

## Authentication headers ruled out EventSource

Attaching session SSE ran into the authentication header. The server required `Authorization: Bearer`, and standard `EventSource` cannot send custom headers. I switched to the fetch-based [`@microsoft/fetch-event-source`](https://github.com/Azure/fetch-event-source), which also handled the reconnection policy and background-tab behavior through `openWhenHidden`. By default this library closes the connection when a tab is hidden, so I turned the option on to keep receiving counseling messages. That added a dependency and left the reconnection delay for me to choose, but it could send the authentication header the server required.

```typescript
export async function openSessionStream(sessionId, init) {
  const accessToken = await getCookie('accessToken');
  return fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
    signal: init.signal,
    openWhenHidden: true, // Keep receiving chat messages in background tabs
    headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
    onmessage: (e) => init.onMessage(e.event, e.data),
    onerror: init.onError, // Return a delay in milliseconds to reconnect; throw to stop
  });
}
```

## Gathering transitions and connection rules in one place

Conversation status decided which server to send to and whether to subscribe. That status mixed values the client created with values the server sent.

```text
ai ──"Connect to an agent"→ connecting ──(SSE: live)→ live ──(SSE: done)→ done
                                       └─(SSE: hold)→ hold
```

- `ai`: the AI is answering. This is the client's default.
- `connecting`: the client has called AI end and is waiting for a counselor to accept. Only the client knows this state.
- `live`, `hold`, `done`: server states set by session SSE.

The server can send `done` while the client is in `connecting`. Separate `useState` values made that ordering hard to handle, so I gathered the transitions into `useReducer`, the React hook that lets one function describe how state changes when something happens.

Transitions became easier to read, but several effects still opened and closed the connection. Status could be `live` with SSE closed. So I built a store that derives the connection from state: it connects only when there is a subscriber, a session, and the conversation has not ended.

`syncConnection()` reconciles the connection whenever those three values change. React subscribes only to snapshots through `useSyncExternalStore`, a hook that reads a store living outside React through two functions, `subscribe` and `getSnapshot`. That is why `ChatStore` below has both. Events arriving during reconnection or unsubscribing are not solved by these conditions alone.

```tsx
export class ChatStore {
  private snapshot = ChatStore.initialSnapshot();
  private readonly listeners = new Set<Listener>();
  private readonly seen = new Set<number>(); // Deduplicate message IDs across history and SSE

  readonly subscribe = (listener: Listener) => {
    this.listeners.add(listener);
    this.syncConnection(); // Start subscribing: connect if needed
    return () => {
      this.listeners.delete(listener);
      this.syncConnection(); // End the subscription: disconnect if needed
    };
  };
  readonly getSnapshot = () => this.snapshot;
}
```

Ending AI, sending messages, and opening the AI stream stayed in the hook's React Query code. The store kept SSE subscriptions and transitions. It also accepted undocumented message shapes: single items, arrays, and `{ messages: [] }` wrappers. Zod `.catch()` let valid items survive a malformed one.

## Moving message management to @tanstack/ai

The custom store connected everything, but `ChatStore` was accumulating messages, deduplicating IDs with `seen`, managing subscriptions, and publishing immutable snapshots. AI message libraries already provide these.

We planned to support token streaming, tool calls, and messages with cards and attachments. Each new format would have meant reworking the text-oriented store, so I moved to the message model in `@tanstack/ai`.

Session SSE did not match the connection format [`useChat`](https://tanstack.com/ai/latest/docs/api/ai-react) accepts. `useChat` is the library's React hook, and a connection is the channel it uses to exchange messages. With the server format left as it was, `SubscribeConnectionAdapter` reads the SSE and hands it to the library. The linked docs describe the latest version, so names may differ from the code below.

```tsx
export function makeSessionConnection({ sessionId, onStatus }): SubscribeConnectionAdapter {
  return {
    async *subscribe() {
      const queue: StreamChunk[] = [];
      let notify = () => {};
      const controller = new AbortController();

      const accessToken = await getCookie('accessToken');
      fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
        signal: controller.signal,
        openWhenHidden: true, // Keep receiving chat messages in background tabs
        headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
        onmessage: ({ event, data }) => {
          if (event === SseEvent.StatusChange) {
            const status = parseStatusEvent(safeParse(data));
            if (status) onStatus(status); // Pass server status to the business layer
          } else {
            queue.push(...itemsToChunks(safeParse(data))); // Messages to standard StreamChunk values
          }
          notify();
        },
        onerror: () => 3000, // Reconnect after three seconds
      }).catch(() => {});

      try {
        while (true) {
          if (queue.length === 0) await new Promise<void>((r) => (notify = r));
          yield* queue.splice(0); // Bridge callback pushes to async-generator pulls
        }
      } finally {
        controller.abort(); // Close SSE when consumption ends
      }
    },
    send: asyncNoop, // Sending does not go through this channel
  };
}
```

`subscribe` is an async generator, a function that hands out one value each time its consumer asks for the next. `fetchEventSource` works the other way around and calls back when a message arrives. To bridge them, the callback puts messages in `queue` and wakes the waiting side with `notify`, while the generator waits when the queue is empty and then yields whatever has piled up. Status-change events skip the queue and go straight to `onStatus`.

`send` is empty. A connection usually returns a response stream after sending, but this app picks the sending server separately and receives only through session SSE. Putting sending in the adapter would have meant choosing between the two servers again, so the adapter only subscribes.

This approach leaves a conversion adapter to maintain, and a format change on the server or in the library means changing it. In exchange, the server format stayed as it was and message accumulation and subscription management moved to the library.

Some things still needed checking after the move. The code above is shortened to show how the two channels connect. With an empty queue awaiting input, a cancel signal may not release the wait right away, so a real version has to pass cancellation to SSE and wake the queue.

I left `seen` behind and relied on `messageId` accumulation in `useChat`, and whether identical IDs from history and SSE merge still needs a look, including backend retransmission. The client greeting at the top of the conversation can also duplicate the one in server history, and showing it only when history is empty remains to be checked.

The renderer also still takes a one-line `Message`, so converting `UIMessage` discards the cards, tools, and attachments in `parts`. Showing those formats requires the renderer to read `parts` directly.

### Matching useChat initialization and subscription timing

Even with the format matched, history could be missing and live messages could fail to arrive. What remained was timing.

`useChat` reads `initialMessages` once at mount. History arrived asynchronously through React Query, so the first render had none, and it did not appear when it arrived later. I used `useSuspenseQuery` to mount the conversation only after history was ready. `useSuspenseQuery` is a React Query hook that holds a component's render until its data is ready. The conversation appears later as a result, but `initialMessages` holds the history from the first render.

The live messages were my own mistake. Subscription never starts without `live: true`, and I had left it out, so messages stayed missing for a while. I changed the call to `useChat({ connection, initialMessages, live: true })`.

Closing the panel unmounts the component and unsubscribes, and the adapter's `finally` calls `controller.abort()` to close SSE.

### Narrowing the statuses a server can send

I first kept `serverStatus` and `isConnecting` separate to tell `connecting` apart from server states. Later I kept one status value and narrowed what the server can supply with `ServerStatus`.

```tsx
type ServerStatus = 'ai' | 'live' | 'hold' | 'done'; // Status from SSE and history
type ChatStatus = ServerStatus | 'connecting'; // Adds a client-only status

const [status, setStatus] = useState<ChatStatus>(/* Last history status ?? 'ai' */);
// onStatus accepts only ServerStatus, so passing connecting here fails type checking
const connection = useMemo(() => makeSessionConnection({ sessionId, onStatus: setStatus }), [sessionId]);
```

Only the keyword handler sets `connecting`. Passing it through `onStatus`, the path for server events, fails type checking.

## Looking back

Splitting the panels copied the server structure onto the screen. The user was reading one conversation while the code split in two, and the branch choosing a panel only went away once I merged them again. That taught me to divide a screen by what the user sees, however many servers sit behind it.

I also trusted types too far. I narrowed `onStatus` to `ServerStatus` and wrote in a code comment that SSE could not overwrite `connecting`. Reviewing this article later showed me that was wrong. The type only blocks passing the value `connecting` through that path. When `live` or `done` arrives, the current `connecting` still gets replaced. A type decides which values can be passed; it did not decide the order events arrive in. Which transitions to accept still needs its own rule.

What belongs in the conversation list was something I settled only after running into it. Send failures went in as error bubbles, attached under unrelated answers, and stayed for the whole session. Failure notices are a different kind of thing from conversation, so they moved to the shared `toast.warning`. Reading initial status with `.at(-1)` could pick a message without a status, so I switched to `.findLast(i => i.status)`. Sending that still worked while AI was ending got blocked by including that call in `isPending`.
