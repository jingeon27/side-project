<Summary>

AI answers and counselor messages came from separate services. To put both in one conversation, I separated where messages were sent from where they were displayed.

</Summary>

![An illustration of two SSE message streams passing through an adapter into one conversation](/images/covers/chatbot-message-layer.png)

*An illustration made for this article, rather than a screenshot of the service.*

The shopping service's AI support screen had one backend for questions and another for counseling sessions. The frontend had to connect to both, without changing either backend.

- **AI chat service:** streams AI answers token by token over SSE.
- **Session backend:** manages counselor connections, sessions, and history, sending counselor messages and status changes over SSE.

There was no shared backend owner who could combine the responses for us. Asking one independent service to consume the other's output was not an option.

The client had to make these streams look like one conversation. I moved from accumulating tokens directly to separate panels and back to one panel, then from useReducer through a custom store to @tanstack/ai.

> AI token streaming → separate counselor-button panel → keyword-based integration → useReducer state machine → useSyncExternalStore store → @tanstack/ai adapter

---

## Displaying tokens as they arrived

```text
src/modules/entities/chat/chatbot/
├─ api/chatbot.api.ts        # Calls the AI chat service /chat/stream and parses SSE
├─ model/use-chat-stream.hook.ts
├─ model/use-chat-session.hook.ts
└─ ui/ (MessageBubble, TypingIndicator, MarkdownContent ...)
```

The first screen sent a question to POST /chat/stream and rendered its SSE response. I parsed the response and appended each token to the current message. The API was already defined, so the frontend worked with the format it received.

```tsx
// Initially: parse the AI response stream and render it directly
async function* parseSSEStream(stream: ReadableStream<Uint8Array>) {
  const reader = stream.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';
    for (const line of lines) {
      const t = line.trim();
      if (t.startsWith('data: ')) yield JSON.parse(t.slice(6)) as StreamData;
    }
  }
}

// Append each token to the message text for a streaming UI
onData: (data) =>
  setMessages((prev) => updateMessage(prev, botMessageId, { text: current.text + data.content })),
```

useMutation made the request, and `useState<Message[]>` held the accumulating tokens. There was no streaming library in between.

The server's history already included an instruction:

> “How can I help? To connect to a counselor, enter 'connect to an agent'.”

Supporting that connection keyword meant receiving messages from another service too.

## Adding a counselor connection button

Counselor messages arrived through the session backend's SSE. Its start, subscribe, message, and end operations opened the session, received messages and statuses, sent messages, and ended it. The AI conversation had to continue through this session.

I initially divided the UI like the backends: AiChatPanel handled the AI stream, CounselingPanel handled session SSE, and a button switched between them.

```typescript
// When connecting to an agent was a button: subscribe to session SSE with EventSource
const subscribeSse = useCallback((sid: string) => {
  const es = fetchCounselingSubscribe(sid);
  es.addEventListener('status', (e) => {
    const { status } = safeParse(e.data);
    if (status === 'counseling') append(createSystemMessage(GUIDE.accepted));
    if (status === 'ended') append(createSystemMessage(GUIDE.ended));
  });
  es.addEventListener('message', (e) => {
    const { message } = safeParse(e.data);
    if (message?.trim()) append(createCounselorMessage(message));
  });
}, []);
```

Switching panels also split the message list, scroll position, and session. Code treated this as another screen, although the conversation continued for the user. Message constructors and types had separated by source too: createUserMessage, createCounselorMessage, and createSystemMessage.

## Combining the panels and using a connection keyword

I combined the panels and removed the connection button. Entering the keyword from the server's greeting now requested a counselor.

One hook handled the panel. Sending routes to the session backend while connecting or counseling and to the AI service otherwise. The top-level component no longer chooses an ai or counseling panel.

Both answers now needed to enter the same list. Rendering both streams could add the same answer twice, so I first chose which stream would supply displayed messages.

### Keep the AI stream connected without displaying it

Session SSE carried both AI and counselor answers; the AI service carried only AI answers. I made session SSE the sole source of displayed messages.

The AI stream stayed open and was read to completion without rendering its response. This drain-only arrangement kept the request that caused generation separate from the subscription delivering the finished answer.

```tsx
// The AI stream that once reached the UI becomes drain-only
const response = await chatClient.post('/chat/stream', body, {
  adapter: 'fetch',
  responseType: 'stream',
  timeout: 30_000, // Allow up to 30 seconds for generation
});
const reader = (response.data as ReadableStream<Uint8Array>).getReader();
try {
  while (!(await reader.read()).done) {
    // Read and discard. Session SSE owns display.
  }
} finally {
  reader.releaseLock();
}
```

I could not inspect the servers, but the behavior suggested that retaining the AI stream for up to 30 seconds allowed generation to proceed and its result to arrive through session SSE. The connection therefore stayed open even though its response was discarded. Browser disconnection and timeout can still affect generation in this arrangement.

## Authentication headers ruled out EventSource

Authentication blocked the first session-SSE integration. Its endpoint required Authorization: Bearer, which standard EventSource cannot attach. I used the fetch-based @microsoft/fetch-event-source to add the header and configure reconnection and background-tab behavior through openWhenHidden.

```typescript
export async function openSessionStream(sessionId, init) {
  const accessToken = await getCookie('accessToken');
  return fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
    signal: init.signal,
    openWhenHidden: true, // Keep receiving chat messages in background tabs
    headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
    onmessage: (e) => init.onMessage(e.event, e.data),
    onerror: init.onError, // Return a delay in milliseconds to reconnect; throw to stop
  });
}
```

## Gathering transitions in useReducer

Conversation state determined where to send and whether to subscribe. That state mixed values created by the client with values supplied by the server.

```text
ai ──"Connect to an agent"→ connecting ──(SSE: live)→ live ──(SSE: done)→ done
                                       └─(SSE: hold)→ hold
```

- ai: the client's default AI-response state
- connecting: client-only state after ending AI and while awaiting counselor acceptance
- live/hold/done: server-owned states from session SSE

The client sets connecting while waiting for a counselor, but the server may send done during that wait. Updating separate useState values made that order hard to handle, so I gathered transitions into useReducer.

Transitions became easier to read, while effects still opened and closed SSE independently. Status could be live with no open connection. I next gathered the connection conditions in one place.

## Letting the store own SSE while React subscribes to snapshots

> Connection = subscribers exist ∧ session exists ∧ session is not finished.

syncConnection() reconciles the connection when subscribers, session, or completion state change. React only subscribes to its snapshots through useSyncExternalStore. Events arriving during reconnection or unsubscribe still require handling beyond these conditions.

```tsx
export class ChatStore {
  private snapshot = ChatStore.initialSnapshot();
  private readonly listeners = new Set<Listener>();
  private readonly seen = new Set<number>(); // Deduplicate message IDs across history and SSE

  readonly subscribe = (listener: Listener) => {
    this.listeners.add(listener);
    this.syncConnection(); // Start subscribing; connect if needed
    return () => {
      this.listeners.delete(listener);
      this.syncConnection(); // End the subscription; disconnect if needed
    };
  };
  readonly getSnapshot = () => this.snapshot;
}
```

React Query in the hook kept the network actions: ending AI, sending, and opening the AI stream. The store kept SSE subscriptions and transitions. It also parsed undocumented message shapes: single items, arrays, and `{ messages: [] }` wrappers. Zod .catch() let valid items survive a malformed item.

The custom store connected the flow, but supporting more message formats would require changing it again.

## Moving message management to @tanstack/ai

ChatStore accumulated messages, deduplicated IDs with seen, managed subscriptions, and published immutable snapshots. These were functions available in AI message libraries.

We planned token streaming, tool calls, and messages containing cards and attachments. The text-oriented custom model would need to change, so I moved to @tanstack/ai's message model.

Session SSE still did not match the connection format useChat accepted. SubscribeConnectionAdapter reads the existing SSE format and passes it to the library without a server change.

```tsx
export function makeSessionConnection({ sessionId, onStatus }): SubscribeConnectionAdapter {
  return {
    async *subscribe() {
      const queue: StreamChunk[] = [];
      let notify = () => {};
      const controller = new AbortController();

      const accessToken = await getCookie('accessToken');
      fetchEventSource(`${SESSION_API_URL}/chat/sessions/${sessionId}/stream`, {
        signal: controller.signal,
        openWhenHidden: true,
        headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : undefined,
        onmessage: ({ event, data }) => {
          if (event === SseEvent.StatusChange) {
            const status = parseStatusEvent(safeParse(data));
            if (status) onStatus(status); // Server status to the business layer (ServerStatus)
          } else {
            queue.push(...itemsToChunks(safeParse(data))); // Messages to standard StreamChunk values
          }
          notify();
        },
        onerror: () => 3000, // Reconnect after three seconds
      }).catch(() => {});

      try {
        while (true) {
          if (queue.length === 0) await new Promise<void>((r) => (notify = r));
          yield* queue.splice(0); // Bridge callback pushes to async-generator pulls
        }
      } finally {
        controller.abort(); // Close SSE when consumption ends
      }
    },
    send: asyncNoop, // Sending is not this channel's responsibility
  };
}
```

Its send method is empty. A typical connection returns a response stream after sending, but this app chooses the sending service separately and receives only through session SSE. I kept subscription in the adapter rather than making it choose between the backends again.

### Matching useChat initialization and subscription timing

Matching the connection format was not enough. History could be missing or live messages could fail to arrive until I matched when useChat initializes and subscribes.

- It reads initialMessages only once at mount. Asynchronous history originally arrived after an empty first render. Gating the conversation with useSuspenseQuery mounts it only after history is ready, making initialMessages the actual history.
- Without `live: true`, subscription does not start. Omitting it caused missing live messages until I used `useChat({ connection, initialMessages, live: true })`.
- Closing the panel unmounts the component and unsubscribes. The adapter's finally calls controller.abort() to close SSE.

### Separating client and server status types

I first used serverStatus and isConnecting to distinguish the client's connecting state. Later I kept one state value and narrowed values accepted from the server with ServerStatus.

```tsx
type ServerStatus = 'ai' | 'live' | 'hold' | 'done';   // Authoritative state from SSE and history
type ChatStatus = ServerStatus | 'connecting';          // Adds a client-only transition state

const [status, setStatus] = useState<ChatStatus>(/* Last history status ?? 'ai' */);
// onStatus accepts ServerStatus, so SSE cannot set connecting
const connection = useMemo(() => makeSessionConnection({ sessionId, onStatus: setStatus }), [sessionId]);
```

The keyword handler sets connecting, while onStatus accepts only ServerStatus. Passing connecting through that server-event path therefore fails type checking. Despite the example comment, live or done can still replace the current connecting value. Accepted transition order needs separate handling.

### Message deduplication still needed verification

I left the old seen set behind and relied on useChat's messageId accumulation. The unresolved case is an identical ID arriving from history and SSE. Whether those messages merge needs checking with backend retransmission included.

## Keeping send failures out of the conversation

The original error bubbles appeared under unrelated answers and stayed for the whole session. I moved send failures to shared toast.warning because they were feedback about sending, not conversation messages.

Initial status could not simply come from the last item either. I replaced .at(-1) with .findLast(i => i.status) so a message without status would not reset it. Adding the AI-ending call to isPending also blocks sending during connecting. The client greeting at the top can still duplicate server history; showing it only for empty history remains to be checked.

The renderer still accepts a one-line Message even after the model migration.

Converting UIMessage into that type discards cards, tools, and attachments in parts before rendering. The renderer needs to read parts directly to use those message formats. If the AI service later supplies tokens through session SSE, token-by-token display can also return through this path.

---

Closing subscriptions needs more than the adapter's finally block. When the queue is empty and awaiting input, cancellation may not release that await immediately. It must reach SSE and wake the queue. The shortened example shows how the two channels connect; cancellation and retransmitted-ID behavior still need that additional checking.
