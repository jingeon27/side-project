병원이 쓰는 병원 관리자와 운영팀이 쓰는 Back-Office에는 시술 한 건의 결제를 타임라인으로 쌓아 보여 주는 결제 내역 화면이 있어요. 한 행이 결제 한 건이고, 점 색과 상태 태그, 날짜와 금액을 보여 줘요. 행을 펼치면 결제일과 미수잔금, 총 결제 예정 금액, 최종 결제금액 칸이 나오는데, 저장 전인 행에서는 이 칸들이 입력창이에요. 이 서비스는 취소도 별도 거래로 기록해요. 원래 결제를 고치는 대신 결제수단이 취소인 행을 더하는 구조예요.

여기에 쿠폰을 추가할 때는 쿠폰 타입과 상세 화면을 넣으면 될 줄 알았어요. 그런데 총 결제 예정 금액이 바뀌면 이미 고른 쿠폰을 풀어야 했고, 저장하기 전과 저장한 뒤에 보여줄 정보도 달랐어요. 결제수단에 쿠폰이라는 값만 더해서는 구분할 수 없는 경우들이었어요. 현장 결제 금액과 쿠폰 사용액도 같은 거래 안에서 보여줘야 했어요. 행의 결제수단뿐 아니라 상태, 저장 여부, 선택한 쿠폰과 할인 금액을 함께 보게 됐어요.

행을 펼쳤을 때 어떤 상세 컴포넌트를 그릴지 고르는 코드를 여기서는 렌더러라고 불러요. 쿠폰을 처음 넣은 6월 24일 오전에 렌더러의 갈래는 다섯 개의 if였어요. 그날 오후 그 if를 `match`로 옮겼을 때는 예전 순서가 그대로 남았어요. 상세를 컴포넌트로 나눠도 `id`와 상태가 섞여 있어서, 다음 날 오전 저장 여부를 먼저 보도록 다시 묶었어요. 문법을 바꾼 뒤에 어떤 순서로 판단할지도 바꿔야 했어요.

아래 그림의 위쪽이 렌더러가 바뀐 순서이고, 아래쪽 표는 쿠폰을 넣으며 손댄 자리예요. 커밋 기록과 실제 코드를 바탕으로 그렸어요.

## 쿠폰을 넣은 날의 if 다섯 개

서버에서 받는 결제 내역은 다음과 같은 구조예요. 예제에는 필요한 결제수단과 상태만 남겼어요. 실제 응답에는 결제수단 8종과 상태 6종이 있고, 그림에는 실제 이름을 썼어요.

```typescript
interface PaymentHistoryResponse {
  id?: number | null;
  method: 'NORMAL' | 'CANCEL' | 'COUPON';
  status: 'PROCESSING' | 'WAITING' | 'COMPLETED';
  paymentAmount: number;
  paymentDate?: string | null;
  memberCouponId?: number | null;
  couponName?: string | null;
}
```

`method`의 `NORMAL`은 병원에서 직접 받은 현장 결제이고, `CANCEL`은 취소, `COUPON`은 쿠폰 결제예요. 서버에 저장된 행에는 `id`가 있고, 화면이 폼에 붙인 저장 전 행에는 없어요.

6월 24일 오전에는 기존 렌더러 파일에 if를 더했어요. 그림의 첫 단계를 코드로 줄여 옮기면 다음과 같아요. 실제 코드를 그대로 옮긴 것은 아니에요.

```tsx
// 그림의 첫 단계를 줄인 예시예요. if 다섯 개에 갈래는 여섯이에요.
if (payment?.method === 'COUPON') {
  if (payment.status === 'COMPLETED') return <CompletedCouponDescriptions field={field} />;
  return <CouponDescriptions field={field} />;
}
if (payment?.id == null || payment.status === 'WAITING' || payment.status === 'PROCESSING') {
  return <WaitingDescriptions field={field} />;
}
if (payment.method === 'NORMAL' && payment.status === 'COMPLETED') {
  return <CompletedDescriptions field={field} />;
}
if (payment.method === 'CANCEL' && payment.status === 'COMPLETED') {
  return <CanceledDescriptions field={field} />;
}
return <WaitingDescriptions field={field} />;
```

쿠폰은 상태로 가르고, 나머지는 `id`와 상태를 섞어 가르고 있어요.

## 같은 날 오후, 순서는 그대로인 match

오후에는 상세 컴포넌트를 파일로 나누고 if를 ts-pattern의 `match`로 옮겼어요. `match(값)`은 값을 위에서부터 패턴과 비교해 처음 맞는 갈래의 함수를 실행하고, 그 반환값을 돌려줘요. `.with`는 객체 모양으로, `.when`은 boolean을 돌려주는 함수로 비교하고, `.otherwise`는 앞에서 걸리지 않은 나머지를 받아요.

이때는 if 순서를 그대로 옮겼어요. 완료된 쿠폰 전용 컴포넌트는 없애고 완료 상세가 연결된 쿠폰결제 행을 함께 그리게 됐지만, 판단 순서는 오전과 같았어요. 이것도 줄인 예시예요.

```tsx
// 그림의 둘째 단계를 줄인 예시예요. 문법은 바뀌었지만 순서는 if와 같아요.
match(payment)
  .with({ method: 'COUPON', id: P.optional(P.nullish) }, () => <CouponDescriptions field={field} />)
  .when(isUnsavedOrPending, () => <WaitingDescriptions field={field} />)
  .when(isCompletedNormalPayment, () => <CompletedDescriptions field={field} />)
  .when(isCanceledPayment, () => <CanceledDescriptions field={field} />)
  .otherwise(() => <WaitingDescriptions field={field} />);
```

둘째 갈래인 `isUnsavedOrPending`이 `id`와 상태를 한 조건으로 보고 있어요. 저장 여부를 묻는 건지 상태를 묻는 건지가 여전히 섞여 있는 거예요.

## 완료인데 저장 전인 행

어느 상세 화면을 보여줄지 정하려고 경우를 표로 적었어요.

| 저장 여부 | 결제수단 | 상태 | 화면 |
| --- | --- | --- | --- |
| 미저장 | 쿠폰 | 처리 중 | 쿠폰 선택과 예상 결제 금액 |
| 미저장 | 그 외 | 처리 중 | 일반 결제 입력 |
| 저장 | 현장 결제 | 완료 | 완료 정보와 연결된 쿠폰 |
| 저장 | 취소 | 완료 | 취소 정보 |
| 저장 | 그 외 | 대기/처리 중 | 일반 대기 정보 |

저장 여부를 먼저 봐야 했던 건 미저장 행의 상태가 그대로 있지 않기 때문이에요. 결제일을 고르면 상태가 완료로 바뀌지만, 서버에 저장한 것은 아니에요. 상태만 보고 완료 상세를 보여주면 아직 편집할 입력칸이 사라져요. 그래서 상세 화면은 `id`가 있는지부터 보게 했어요. 헤더와 점 색은 상태를 바로 따라가므로, 저장 직전에는 '결제완료' 태그 옆에 입력칸이 함께 보일 수 있어요.

노출 여부와 색상을 고르는 함수는 쿠폰을 넣기 전부터 있었어요. 색상 함수는 3월에 만들었고, 노출 조건 함수는 4월에 병원 관리자와 Back-Office가 쓰던 UI를 공용 패키지로 옮길 때 모아 둔 코드예요. 쿠폰의 노출 조건은 그 함수에 더하고 상세 컴포넌트를 고르는 순서를 바꿨어요.

아래 그림은 한 결제 내역 행을 두고 노출, 점 색, 헤더, 펼침, 상세 칸을 다섯 곳에서 따로 판단한다는 걸 보여 줘요. 표는 행의 저장 여부, 결제수단, 상태에 따라 각 자리가 내는 결과예요. 화면은 캡처 없이 코드의 antd 구성을 따라 단순화했고, 날짜와 금액은 예시예요.

## 저장 여부부터 묻는 match

다음 날 오전 다시 묶은 렌더러는 이 행을 이렇게 갈라요.

```tsx
import { P, match } from 'ts-pattern';

const isCanceledPayment = (payment: PaymentHistoryResponse | undefined) =>
  payment?.method === 'CANCEL' && payment.status === 'COMPLETED';

const isCompletedNormalPayment = (payment: PaymentHistoryResponse | undefined) =>
  payment?.method === 'NORMAL' && payment.status === 'COMPLETED';

function PaymentHistoryDescriptions({ field }: { field: FormListFieldData }) {
  const form = paymentForm.useFormInstance();
  const payment = paymentForm.useWatch(['payments', field.name], form);

  return (
    match(payment)
      // 미저장: 값이 없거나 id가 없다. 그 안에서 결제수단을 본다.
      .with(P.union(P.nullish, { id: P.optional(P.nullish) }), (unsaved) =>
        match(unsaved)
          .with({ method: 'COUPON' }, () => <CouponDescriptions field={field} />)
          .otherwise(() => <WaitingDescriptions field={field} />),
      )
      // 저장됨: 취소 → 완료 → 그 외
      .when(isCanceledPayment, () => <CanceledDescriptions field={field} />)
      .when(isCompletedNormalPayment, () => <CompletedDescriptions field={field} />)
      .otherwise(() => <WaitingDescriptions field={field} />)
  );
}
```

`paymentForm`은 antd Form에 결제 필드 타입을 입힌 래퍼의 가명이에요. `useFormInstance`와 `useWatch`는 antd API이고, `Form.List`가 주는 `field.name`은 결제 배열의 인덱스예요. `Form.List`는 antd에서 반복되는 입력을 배열로 다루는 컴포넌트이고, `useWatch`는 지정한 경로의 폼 값을 구독해요.

첫 갈래의 패턴도 풀어 볼게요. `P.union`은 안의 패턴 중 하나만 맞으면 통과해요. `P.nullish`는 null이나 undefined에 맞고, `P.optional`은 키가 아예 없어도 맞게 해 줘요. ts-pattern의 객체 패턴은 키가 있어야 맞기 때문에, `{ id: P.nullish }`만 쓰면 `id` 키 자체가 없는 행을 놓쳐요.

값이 없거나 `id`가 없으면 편집용 상세를 고르고, 그 안에서 쿠폰인지 구분해요. 저장된 행은 취소 완료, 현장 결제 완료를 차례로 보고 나머지는 대기 상세로 보내요. 예전에는 쿠폰 상태를 먼저 보다가 다른 분기에서 `id`와 상태를 섞어 봤는데, 이 순서로 바꾸니 행이 어느 컴포넌트에 도착하는지 따라갈 수 있었어요.

처음에는 모든 경우를 discriminated union으로 표현하려 했어요. discriminated union(판별 유니언)은 공통 필드의 값으로 어느 모양인지 가를 수 있는 유니언 타입이에요. 컴파일러가 그 필드를 보고 타입을 좁혀 주고, ts-pattern의 `.exhaustive()`와 함께 쓰면 빠진 경우를 컴파일 오류로 알려 줘요.

```typescript
// 판별 유니언을 설명하려고 만든 예시예요. 서버 응답은 이런 모양이 아니었어요.
type PaymentRow =
  | { saved: false; method: 'COUPON' | 'NORMAL' }
  | { saved: true; method: 'NORMAL'; status: 'COMPLETED' }
  | { saved: true; method: 'CANCEL'; status: 'COMPLETED' };

const detailFor = (row: PaymentRow) =>
  match(row)
    .with({ saved: false }, () => 'edit')
    .with({ saved: true, method: 'NORMAL' }, () => 'completed')
    .with({ saved: true, method: 'CANCEL' }, () => 'canceled')
    .exhaustive(); // 갈래를 하나 지우면 여기서 컴파일 오류가 나요.
```

하지만 서버 응답은 enum과 optional 필드를 가진 DTO였고 알 수 없는 값의 fallback도 필요했어요. 실제 응답을 다른 타입인 것처럼 단언하는 대신, 어떤 행을 보여주고 어느 상세 컴포넌트로 보낼지 정하는 코드를 모았어요.

그래서 여기서 ts-pattern이 새 결제수단의 누락까지 보장해 주지는 않아요. 입력이 완전한 판별 유니언이 아니고 `.otherwise()`가 있기 때문에 빠진 UI도 fallback으로 갈 수 있어요. API 응답을 클라이언트 유니언으로 파싱하고 `.exhaustive()`를 쓰는 변경까지 하지는 않았어요. 서버 계약과 기존 화면의 영향 범위를 생각해, 기존 서버 응답과 화면을 유지하면서 분기를 읽기 쉽게 모으는 데 그쳤어요.

## 타임라인에 올라가는 쿠폰 행

어떤 행을 타임라인에 올릴지는 상세를 고르기 전에 정해요. 이 조건은 4월에 JSX의 filter 콜백에서 함수 하나로 옮겨 두었으므로, 쿠폰 조건도 그 함수 안에 더했어요.

```typescript
const VISIBLE_STATUSES = ['COMPLETED', 'PROCESSING', 'WAITING'] as const;
// as const만 쓰면 includes의 인자가 'NORMAL' | 'CANCEL'로 좁혀져
// payment.method를 받지 못하므로, 원소 타입을 method 전체 union으로 선언한다.
const VISIBLE_METHODS: readonly PaymentHistoryResponse['method'][] = [
  'NORMAL',
  'CANCEL',
];

function isVisiblePayment(payment: PaymentHistoryResponse | undefined) {
  if (!payment) return false;

  const isVisibleOnsitePayment =
    VISIBLE_STATUSES.includes(payment.status) &&
    VISIBLE_METHODS.includes(payment.method);

  const isEditingCoupon =
    payment.method === 'COUPON' && payment.id == null;

  return isVisibleOnsitePayment || isEditingCoupon;
}
```

완료된 현장 결제가 저장된 쿠폰 사용액을 보여주므로, 저장된 쿠폰 행까지 노출하면 같은 거래가 나뉘어 보여요. 반면 저장 전 쿠폰 행은 선택 UI가 필요해서 남겨야 해요. `isEditingCoupon`이 `method`와 `id`를 함께 보는 이유예요.

쿠폰 조건을 처음 더한 6월 24일 오후에는 '처리 중' 상태를 봤어요. 다음 날 오전 상세 렌더러를 저장 여부부터 나누면서, 노출 조건도 `id`가 없는 쿠폰 행으로 맞췄어요. 편집 중이라는 뜻을 상태와 저장 여부로 서로 다르게 해석하지 않게 한 거예요.

## 화면에서만 쓰는 할인 금액

쿠폰을 고르는 동안에는 최종 금액을 미리 계산해야 해요. 이 계산에 쓰는 할인 금액은 서버의 결제 내역에 없어서 폼 전용 값으로 뒀어요.

```typescript
interface PaymentHistoryFormValue extends PaymentHistoryResponse {
  couponDiscountAmount?: number | null;
}
```

6월 23일에는 `couponDiscountAmount`를 응답 DTO에 같이 선언했다가, 다음 날 오후 폼 타입으로 옮겼어요. DTO는 서버와 주고받는 데이터의 모양을 적은 타입이에요. 서버가 보내는 필드와 화면에서 계산하려고 붙이는 필드를 구분한 거예요. 예약 확정 요청을 보낼 때도 폼 전체를 펼치지 않고 필요한 값을 골랐어요.

```typescript
// 확정 전 예약 상세의 결제 내역은 화면이 만든 쿠폰 행 하나뿐이다.
const couponPayment = payments.find(({ method }) => method === 'COUPON');
if (!couponPayment) return;

confirmReservation({
  reservationId,
  paymentAmount: couponPayment.paymentAmount,
  paymentDate: couponPayment.paymentDate,
  memberCouponId: couponPayment.memberCouponId,
  // 견적 금액·내원일·메모는 폼의 다른 칸에서 채운다.
});
```

쿠폰 예약은 병원 관리자의 예약 상세에서 확정해요. 확정 전 결제 내역에는 화면이 만든 쿠폰 행만 있어서, 이 화면의 폼 타입은 원소 하나짜리 튜플로 좁혀 뒀어요. 그 행에서 결제 금액과 날짜, `memberCouponId`를 꺼내면 할인 미리보기 값과 쿠폰명은 요청에 따라가지 않아요.

폼을 요청 DTO로 바꾸는 별도 함수까지 만들지는 않았어요. 편집용 필드가 많지 않고 요청을 만드는 코드가 보낼 값을 직접 고르고 있어서, 여기서 제외할 수 있었어요.

폼의 결제 내역 배열에는 서버가 저장한 행과 화면이 붙인 대기, 쿠폰 행이 함께 들어와요. 결제 내역 DTO에 없는 값은 쿠폰 할인 금액 하나이고, 확정 요청은 쿠폰 행에서 필요한 필드만 골라 만들어요. 아래 그림이 그 구조예요. 실제 코드를 바탕으로 줄여서 그렸어요.

![폼의 결제 내역 배열에는 서버가 저장한 행과 화면이 붙인 대기, 쿠폰 행이 함께 들어와요. 결제 내역 DTO에 없는 값은 쿠폰 할인 금액 하나이고, 확정 요청은 쿠폰 행에서 필요한 필드만 골라 만들어요.](/images/posts/payment-coupon-branches/01.avif)

저장된 쿠폰 결제는 타임라인에서 별도 행으로 보여주지 않아요. 같은 거래의 현장 결제 행이 `transactionId`로 연결된 쿠폰 행을 찾아 사용 금액을 함께 보여줘요.

## 금액을 바꾸면 풀리는 쿠폰

쓸 수 있는 쿠폰과 예상 할인액은 예약과 프로그램, 총 결제 예정 금액으로 조회해요. 금액이 바뀌면 같은 쿠폰의 할인액도 달라질 수 있어서, 금액을 고치면 적용된 쿠폰을 풀어야 했어요.

```tsx
function CouponDescriptions({ field }: { field: FormListFieldData }) {
  const { message } = App.useApp();
  const form = paymentForm.useFormInstance();
  const paymentAmount = paymentForm.useWatch(['payments', field.name, 'paymentAmount'], form);
  const memberCouponId = paymentForm.useWatch(['payments', field.name, 'memberCouponId'], form);
  const couponDiscountAmount =
    paymentForm.useWatch(['payments', field.name, 'couponDiscountAmount'], form) ?? 0;

  const finalAmount = (paymentAmount ?? 0) - couponDiscountAmount;

  // 금액은 Form.Item이 폼에 쓰고, 여기서는 적용된 쿠폰만 푼다.
  const handlePaymentAmountChange = () => {
    if (memberCouponId == null) return;

    form.setFields([
      { name: ['payments', field.name, 'memberCouponId'], value: null },
      { name: ['payments', field.name, 'couponName'], value: null },
      { name: ['payments', field.name, 'couponDiscountAmount'], value: 0 },
    ]);
    message.info('총 결제 예정 금액이 변경되어 적용된 쿠폰이 초기화되었습니다.');
  };

  return (
    <>
      <CouponSelector field={field} />
      <Form.Item name={[field.name, 'paymentAmount']} noStyle>
        <InputNumber onChange={handlePaymentAmountChange} />
      </Form.Item>
      <FinalAmount value={finalAmount} />
    </>
  );
}
```

편집 중인 값은 폼이 갖고 있으니, 상세 컴포넌트에는 `payment` 객체의 옛 값을 넘기지 않고 `field`를 넘겼어요. `useWatch`가 현재 폼 경로에서 금액과 쿠폰을 읽고, 금액이 바뀌면 `setFields`로 적용된 쿠폰을 풀어요. 일반 결제 상세나 타임라인이 이 계산을 알아야 할 이유는 없어요.

행을 펼쳐 두면 금액 라벨의 툴팁이 쿠폰 초기화를 미리 알려줘요. 실제로 금액을 바꾸면 쿠폰이 풀리면서 안내 메시지도 나와요. 해제와 툴팁은 6월 24일에 넣었고, 25일에 안내 메시지를 붙이면서 쿠폰이 있을 때만 풀도록 고쳤어요. 라벨은 7월 1일에 '현장 결제금액'에서 '총 결제 예정 금액'으로 바꿔, 쿠폰을 빼기 전의 금액이라는 뜻을 맞췄어요.

다른 쿠폰을 자동으로 고르지는 않아요. 사용자가 다시 선택하거나 모달의 '쿠폰 미사용'을 고를 수 있어요.

아래 그림은 확정 전 쿠폰 행에서 금액을 바꿀 때 일어나는 일과, 확정 뒤 완료 상세가 연결된 쿠폰결제 행을 찾아 같은 칸 순서로 그리는 모습이에요. 화면은 캡처 없이 코드를 따라 단순화했고, 쿠폰명과 날짜, 금액은 예시예요.

## 렌더러 밖에 남은 판단

쿠폰은 상세 화면에만 영향을 주지 않았어요. 결제 합계와 정산 상세, 예약 확정 요청도 같은 사용액을 다뤄야 했어요.

상세 컴포넌트를 고르는 순서는 바꿨지만, 한 행을 두고 노출과 점 색, 헤더, 펼침, 상세 칸을 따로 판단하는 구조는 그대로예요. 점 색과 헤더는 기존 fallback인 회색과 대기로 표시돼 따로 바꾸지 않았어요.

어떤 행이 어느 상세 컴포넌트로 가는지는 렌더러 한 파일에서 읽을 수 있게 됐지만, 새 결제수단이 생기면 렌더러도 고쳐야 해요. 그때 이 출력이 맞는지는 렌더러와 별개로 봐야 하고, 결제수단과 상태, 저장 여부를 조합한 자동화 테스트는 아직 없어요.
