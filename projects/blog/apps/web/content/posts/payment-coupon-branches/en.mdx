Hospital admin, used by hospitals, and Back-Office, used by the operations team, both have a payment history screen that stacks the payments for one treatment as a timeline. Each row is one payment, showing a colored dot, a status tag, a date, and an amount. Expanding a row reveals fields for the payment date, outstanding balance, total expected amount, and final amount, and on a row that has not been saved those fields are inputs. The service records cancellations as separate transactions rather than modifying the original payment, adding a row whose method is cancellation.

I expected coupon payments to need a new type and a detail view. Changing the total expected amount also had to clear an applied coupon, though, and the information shown before saving differed from the saved record. Adding a COUPON method could not distinguish those cases by itself. An on-site payment and its coupon usage also had to appear within the same transaction. I needed to consider status, saved state, selection, and discount amount as well as method.

I call the code that picks which detail component to draw for an expanded row the renderer. On the morning of June 24, when coupons first went in, the renderer had five if branches. Moving them to `match` that afternoon preserved the old condition order. Splitting details into components still left `id` and status mixed, so the following morning I grouped by saved state first. The decision order needed to change after the syntax did.

## Five ifs on the day coupons went in

The server returns a payment record shaped like this. The examples keep only the relevant methods and statuses; the actual response has 8 methods and 6 statuses, and the diagrams retain the actual names.

```typescript
interface PaymentHistoryResponse {
  id?: number | null;
  method: 'NORMAL' | 'CANCEL' | 'COUPON';
  status: 'PROCESSING' | 'WAITING' | 'COMPLETED';
  paymentAmount: number;
  paymentDate?: string | null;
  memberCouponId?: number | null;
  couponName?: string | null;
}
```

For `method`, `NORMAL` is an on-site payment taken at the hospital, `CANCEL` is a cancellation, and `COUPON` is a coupon payment. Rows saved on the server have an `id`. Unsaved rows the screen adds to the form do not.

On the morning of June 24, I added ifs to the existing renderer file. Here is that first stage, shortened. It is a reconstruction, not the code as written.

```tsx
// Shortened example of the first stage: five ifs and six outcomes.
if (payment?.method === 'COUPON') {
  if (payment.status === 'COMPLETED') return <CompletedCouponDescriptions field={field} />;
  return <CouponDescriptions field={field} />;
}
if (payment?.id == null || payment.status === 'WAITING' || payment.status === 'PROCESSING') {
  return <WaitingDescriptions field={field} />;
}
if (payment.method === 'NORMAL' && payment.status === 'COMPLETED') {
  return <CompletedDescriptions field={field} />;
}
if (payment.method === 'CANCEL' && payment.status === 'COMPLETED') {
  return <CanceledDescriptions field={field} />;
}
return <WaitingDescriptions field={field} />;
```

Coupons are split by status, while the others mix `id` and status.

## The same afternoon: a match in the same order

That afternoon I moved the detail components into their own files and the ifs into ts-pattern's `match`. `match(value)` compares a value against patterns from the top, runs the function of the first one that fits, and returns its result. `.with` compares by object shape, `.when` compares with a function returning a boolean, and `.otherwise` takes whatever is left.

I kept the if order as it was. The completed-coupon component went away, with completion details drawing the linked coupon-payment row instead, but the decision order matched the morning's. This is a shortened example too.

```tsx
// Shortened example of the second stage. New syntax, same order as the ifs.
match(payment)
  .with({ method: 'COUPON', id: P.optional(P.nullish) }, () => <CouponDescriptions field={field} />)
  .when(isUnsavedOrPending, () => <WaitingDescriptions field={field} />)
  .when(isCompletedNormalPayment, () => <CompletedDescriptions field={field} />)
  .when(isCanceledPayment, () => <CanceledDescriptions field={field} />)
  .otherwise(() => <WaitingDescriptions field={field} />);
```

The second branch, `isUnsavedOrPending`, treats `id` and status as one condition. Whether it is asking about saved state or status was still tangled.

## Complete, but not saved yet

I wrote out the cases before choosing detail components.

| Saved | Method | Status | View |
| --- | --- | --- | --- |
| No | Coupon | Processing | Coupon selection and expected amount |
| No | Other | Processing | Standard payment input |
| Yes | On-site | Complete | Completed details and linked coupon |
| Yes | Cancellation | Complete | Cancellation details |
| Yes | Other | Pending/processing | Standard pending details |

Saved state had to come first because an unsaved row's status does not stay put. Selecting a payment date changes status to complete before anything reaches the server. Choosing completed details by status alone would remove inputs that are still editable. Details therefore check `id` first. The header and dot color follow status immediately, so just before saving, a payment-complete tag can appear next to input fields.

Visibility and color helpers already existed. The color helper dates from March, and the visibility helper came from moving hospital admin and Back-Office UI into a shared package in April. I added coupon visibility there and changed the order used to select detail components.

As the diagram below shows, visibility, dot color, header, expansion, and details make five separate decisions for one payment row.

## A match that asks about saved state first

The renderer as regrouped the next morning splits those rows like this.

```tsx
import { P, match } from 'ts-pattern';

const isCanceledPayment = (payment: PaymentHistoryResponse | undefined) =>
  payment?.method === 'CANCEL' && payment.status === 'COMPLETED';

const isCompletedNormalPayment = (payment: PaymentHistoryResponse | undefined) =>
  payment?.method === 'NORMAL' && payment.status === 'COMPLETED';

function PaymentHistoryDescriptions({ field }: { field: FormListFieldData }) {
  const form = paymentForm.useFormInstance();
  const payment = paymentForm.useWatch(['payments', field.name], form);

  return (
    match(payment)
      // Unsaved: no value or no ID. Then inspect the payment method.
      .with(P.union(P.nullish, { id: P.optional(P.nullish) }), (unsaved) =>
        match(unsaved)
          .with({ method: 'COUPON' }, () => <CouponDescriptions field={field} />)
          .otherwise(() => <WaitingDescriptions field={field} />),
      )
      // Saved: cancellation, then completed, then the remaining cases
      .when(isCanceledPayment, () => <CanceledDescriptions field={field} />)
      .when(isCompletedNormalPayment, () => <CompletedDescriptions field={field} />)
      .otherwise(() => <WaitingDescriptions field={field} />)
  );
}
```

`paymentForm` is a publication alias for an antd Form wrapper with payment field types. `useFormInstance` and `useWatch` are antd APIs, and `field.name` from `Form.List` is the payment array index. `Form.List` is antd's component for repeated inputs held as an array, and `useWatch` subscribes to the form value at a given path.

The first branch's pattern needs a word too. `P.union` passes if any pattern inside it fits. `P.nullish` fits null or undefined, and `P.optional` also fits when the key is missing altogether. ts-pattern's object patterns require the key to exist, so `{ id: P.nullish }` alone would miss a row with no `id` key at all.

An absent value or `id` selects an editing view, which then distinguishes coupons. Saved rows check completed cancellations, then completed on-site payments, and otherwise use pending details. Earlier conditions looked at coupon status first and mixed `id` and status elsewhere. With this order I could follow which component a row ends up in.

I first tried to express every case as a discriminated union, a union type whose variants can be told apart by the value of a shared field. The compiler narrows the type from that field, and paired with ts-pattern's `.exhaustive()`, a missing case becomes a compile error.

```typescript
// Example made to explain discriminated unions. The server response was not shaped like this.
type PaymentRow =
  | { saved: false; method: 'COUPON' | 'NORMAL' }
  | { saved: true; method: 'NORMAL'; status: 'COMPLETED' }
  | { saved: true; method: 'CANCEL'; status: 'COMPLETED' };

const detailFor = (row: PaymentRow) =>
  match(row)
    .with({ saved: false }, () => 'edit')
    .with({ saved: true, method: 'NORMAL' }, () => 'completed')
    .with({ saved: true, method: 'CANCEL' }, () => 'canceled')
    .exhaustive(); // Removing a branch makes this line a compile error.
```

The server, however, returned one DTO with enums and optional fields, and unknown values needed a fallback. Instead of asserting the response into a different type, I gathered the code deciding which rows to show and which detail component to render.

That is why ts-pattern does not guarantee here that a new method gets a view. The input is not a full discriminated union and `.otherwise()` can send a missing UI to the fallback. Considering the server contract and how far the change would reach into existing screens, I did not extend it to parsing responses into a client union and using `.exhaustive()`. It stopped at keeping the server response and existing views while gathering the branches where they could be read.

## Which coupon rows reach the timeline

Which rows reach the timeline is decided before any detail component is chosen. In April this condition had already moved from a filter callback in JSX into one function, so the coupon condition went into that function too.

```typescript
const VISIBLE_STATUSES = ['COMPLETED', 'PROCESSING', 'WAITING'] as const;
// With only as const, includes accepts just 'NORMAL' | 'CANCEL',
// not payment.method. Give the elements the full method union type instead.
const VISIBLE_METHODS: readonly PaymentHistoryResponse['method'][] = [
  'NORMAL',
  'CANCEL',
];

function isVisiblePayment(payment: PaymentHistoryResponse | undefined) {
  if (!payment) return false;

  const isVisibleOnsitePayment =
    VISIBLE_STATUSES.includes(payment.status) &&
    VISIBLE_METHODS.includes(payment.method);

  const isEditingCoupon =
    payment.method === 'COUPON' && payment.id == null;

  return isVisibleOnsitePayment || isEditingCoupon;
}
```

A completed on-site payment already shows saved coupon usage, so showing the saved coupon row as well would split that transaction across rows. An unsaved coupon row must stay visible for selection, which is why `isEditingCoupon` checks both `method` and `id`.

When I first added the coupon condition on the afternoon of June 24, it checked processing status. The next morning, when I changed detail rendering to start with saved state, I aligned visibility with the absence of `id` too. Editing no longer meant one thing in visibility and another in detail selection.

## A discount that exists only on screen

While choosing a coupon, the form needs to preview the final amount. The discount behind that calculation is not part of the server's payment record, so I kept it as a form-only value.

```typescript
interface PaymentHistoryFormValue extends PaymentHistoryResponse {
  couponDiscountAmount?: number | null;
}
```

On June 23 I declared `couponDiscountAmount` on the response DTO, then moved it to the form type the next afternoon. A DTO is the type describing the data exchanged with the server. The move separates fields sent by the server from a value added for a screen calculation. The reservation confirmation request also selects its fields explicitly instead of spreading the whole form.

```typescript
// Before confirmation, reservation details contain only the coupon row created by the UI.
const couponPayment = payments.find(({ method }) => method === 'COUPON');
if (!couponPayment) return;

confirmReservation({
  reservationId,
  paymentAmount: couponPayment.paymentAmount,
  paymentDate: couponPayment.paymentDate,
  memberCouponId: couponPayment.memberCouponId,
  // Other form fields supply the quote, visit date, and memo.
});
```

Coupon reservations are confirmed from reservation details in hospital admin. Before confirmation, this form contains only the coupon row created by the screen, so its payment array is narrowed to a one-element tuple. Taking the amount, date, and `memberCouponId` from that row leaves the discount preview and coupon name out of the request.

I did not introduce a separate form-to-request mapper. There were few editing-only fields, and the request builder already picked the values to send, so it could exclude them there.

The form array contains server records and pending or coupon rows created by the screen. Only the coupon discount amount is absent from the payment DTO, and confirmation selects the required fields from the coupon row. The diagram below lays out that structure.

![The form array contains server records and pending or coupon rows created by the screen. Only the coupon discount amount is absent from the payment DTO; confirmation selects the required fields from the coupon row.](/images/posts/payment-coupon-branches/01-en.avif)

Saved coupon payments do not receive separate timeline rows. The on-site payment in the same transaction finds the linked coupon row through `transactionId` and shows its usage amount.

## Changing the amount clears the coupon

Available coupons and their expected discounts are looked up from the reservation, the program, and the total expected amount. A new amount can change the same coupon's discount, so editing the amount had to clear an applied coupon.

```tsx
function CouponDescriptions({ field }: { field: FormListFieldData }) {
  const { message } = App.useApp();
  const form = paymentForm.useFormInstance();
  const paymentAmount = paymentForm.useWatch(['payments', field.name, 'paymentAmount'], form);
  const memberCouponId = paymentForm.useWatch(['payments', field.name, 'memberCouponId'], form);
  const couponDiscountAmount =
    paymentForm.useWatch(['payments', field.name, 'couponDiscountAmount'], form) ?? 0;

  const finalAmount = (paymentAmount ?? 0) - couponDiscountAmount;

  // Form.Item writes the amount; this handler only clears the applied coupon.
  const handlePaymentAmountChange = () => {
    if (memberCouponId == null) return;

    form.setFields([
      { name: ['payments', field.name, 'memberCouponId'], value: null },
      { name: ['payments', field.name, 'couponName'], value: null },
      { name: ['payments', field.name, 'couponDiscountAmount'], value: 0 },
    ]);
    message.info('The expected total changed, so the applied coupon was cleared.');
  };

  return (
    <>
      <CouponSelector field={field} />
      <Form.Item name={[field.name, 'paymentAmount']} noStyle>
        <InputNumber onChange={handlePaymentAmountChange} />
      </Form.Item>
      <FinalAmount value={finalAmount} />
    </>
  );
}
```

The form owns the values being edited, so details receive `field` rather than an old snapshot of the `payment` object. `useWatch` reads the current amount and coupon from the form path, and `setFields` clears the applied coupon after an amount change. The ordinary payment details and timeline have no reason to know that calculation.

While a row is expanded, the amount label's tooltip warns that changing it clears the coupon. Actually changing the value clears the coupon and also shows a notice. Clearing and the tooltip went in on June 24, and on the 25th I added the notice and made clearing happen only when a coupon was applied. On July 1 the label changed from on-site payment amount to total expected payment amount, to describe the amount before subtracting a coupon.

The form does not automatically choose a replacement. Users can select another coupon or choose the modal's do-not-use option.

## Decisions still outside the renderer

Coupons affected more than detail views. Payment totals, settlement details, and reservation confirmation had to handle the same usage amount.

I changed the order for choosing detail components, but one row is still judged separately for visibility, dot color, header, expansion, and details. Dot color and header retained their existing gray and pending fallbacks.

Which component a row reaches can now be read in one renderer file, but a new payment method still means changing that renderer. Its other outputs need considering separately at that point, and automated tests do not yet cover the combinations of method, status, and saved state.
