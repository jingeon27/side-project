<Summary>

무한 스크롤에서 첫 조회, 추가 조회, 마지막 페이지, 두 종류의 오류 상태를 따로 만들어 확인했어요. 스크롤한 화면에서는 드롭다운이 열리는 위치와 바깥, 메뉴 항목, 더보기 아이콘을 눌렀을 때의 결과를 확인했어요. TanStack Query와 Radix, Base UI의 테스트를 답지 삼아, 상태가 바뀌는 순서와 키보드 조작, 메뉴가 닫히는 동안의 입력까지 확인했어요.

</Summary>

![기존 카드 아래에서 다음 페이지를 기다리는 스피너와, 화면 하단 더보기 아이콘 위로 열린 드롭다운을 나란히 그린 도해](/images/covers/scroll-and-dropdown-states.avif)

예전에는 테스트에서 코드가 특정 요구사항에 맞는지와 기본 동작만 확인하면 된다고 생각했어요. UI는 Base UI나 Radix, shadcn/ui처럼 이미 검증된 오픈소스를 신뢰하고 써 왔기 때문에, UI 테스트는 따로 고민하지 않았어요. 그러다 면접을 본 경험이 UI 테스트를 깊게 생각해 보는 계기가 됐어요. 로직은 입력과 결과로 확인할 경우가 어느 정도 정해지지만, UI는 메뉴 하나에도 따져 볼 경우가 훨씬 많았어요.

무한 스크롤과 드롭다운처럼 보편적인 UI도 마찬가지예요. 스크롤 끝에서 새 카드가 붙는 것만 확인하면, 응답을 기다리는 동안 기존 목록이 잠깐 사라져도 테스트는 통과할 수 있어요. 드롭다운은 메뉴가 열렸다는 사실만 확인하면 화면 아래로 잘려서 마지막 항목을 누를 수 없는 경우를 놓쳐요.

피식의 갤러리에는 이미 첫 게시물 24개에서 스크롤을 내려 다음 페이지를 읽는 [E2E 테스트](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/gallery-pagination.spec.ts)가 있었어요. 여기에 응답이 늦거나 실패했을 때와, 페이지 아래쪽에서 게시물의 더보기 메뉴를 눌렀을 때를 더했어요.

## 라이브러리 테스트를 답지로 봤어요

돌아보니 제가 믿고 쓰던 라이브러리의 테스트가 일종의 답지였어요. 그래서 TanStack Query와 Radix, shadcn/ui, Base UI가 테스트를 어떻게 구성했는지 살펴보고 피식에 적용해 봤어요.

TanStack Query의 [`useInfiniteQuery` 테스트](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx)는 렌더할 때마다 훅의 상태를 배열에 모아 두고, 첫 조회와 다음 페이지 조회가 어떤 순서로 상태를 바꾸는지 확인해요. 다음 페이지 요청이 실패해도 이미 받은 페이지가 남고 `isFetchNextPageError`가 켜지는지, `getNextPageParam`이 `undefined`를 돌려주면 `hasNextPage`가 `false`가 되는지도 따로 검사해요.

shadcn/ui는 드롭다운 하나를 Radix와 Base UI, React Aria 버전으로 나눠, 각 컴포넌트 위에 스타일을 입혀 제공해요. [Base UI 버전](https://github.com/shadcn-ui/ui/blob/8ab27715521cbd4f87ae6886cd989cbb678f6de7/apps/v4/registry/bases/base/ui/dropdown-menu.tsx)처럼 열고 닫기와 포커스 같은 동작은 아래에 깔린 컴포넌트가 맡아서, 저장소에는 드롭다운의 동작 테스트가 따로 없어요. 그래서 동작을 어떻게 검증하는지는 Radix와 Base UI의 테스트에서 찾았어요.

Radix의 [DropdownMenu 테스트](https://github.com/radix-ui/primitives/blob/fe02008f49834d7421427fe532e5b11f13c7bcac/packages/react/dropdown-menu/src/dropdown-menu.test.tsx)는 메뉴가 열리고 닫히는 것보다 그 주변을 더 많이 봐요. 닫혀 있을 때 `aria-controls`가 없는 요소를 가리키지 않는지, 창이 포커스를 잃으면 하위 메뉴까지 닫히는지, 메뉴가 닫히는 동안 포인터가 지나가도 항목이 포커스를 가져가지 않는지 같은 경우를 따로 확인해요.

피식의 더보기 메뉴는 Base UI로 만들어서 Base UI의 [메뉴 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/root/MenuRoot.test.tsx)도 열어 봤어요. 키보드로 열면 첫 항목에 포커스가 가는지, 닫힌 뒤 트리거로 포커스가 돌아오는지, 열린 메뉴에서 Tab을 누르면 메뉴가 닫히고 다음 요소로 포커스가 넘어가는지를 확인해요. 팝업의 [전환 상태 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/popup/MenuPopupTransitionState.test.tsx)는 TanStack Query처럼 상태가 바뀔 때마다 기록하고, CSS 전환을 10초로 늘려 메뉴가 열리는 도중의 상태를 확인해요. 이 테스트는 jsdom에서는 건너뛰고 실제 브라우저에서만 실행해요.

세 라이브러리 모두 마지막 결과 하나보다 상태가 바뀌는 지점을 따로 검사해요. 피식의 테스트도 응답을 기다리는 동안과 요청이 실패한 뒤, 마지막 페이지 이후처럼 상태가 바뀌는 지점을 나눠 확인해요. 아래에서는 이 상태별 테스트를 먼저 설명하고, 답지를 보고 새로 더한 테스트는 마지막 절에서 다뤄요.

## 응답 시점을 제어해 상태 만들기

상태별 테스트는 브라우저 테스트 페이지에서 실행해요. 이 페이지에 피식의 최신 게시물 목록과 게시물 카드, 더보기 메뉴를 띄우고, Playwright의 [`page.route`](https://playwright.dev/docs/mock)로 GraphQL 응답 시점을 제어해요. 목록 끝을 감지하는 `IntersectionObserver`와 다음 페이지를 붙이는 Apollo 캐시는 제품 코드를 그대로 써요. 기본 데이터는 첫 페이지 24개와 마지막 페이지 2개이고, 요청이 나갈 때마다 offset을 기록해서 첫 요청은 `offset: 0`, 추가 요청은 `offset: 24`로 남아요. 첫 조회는 서버가 아니라 브라우저에서 시작하기 때문에, 서버가 프리로드한 콘텐츠가 HTML에 포함되는지는 [별도의 E2E](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/access-layout.spec.ts#L32)에서 확인해요.

이렇게 만든 상태와 각 상태에서 확인한 내용은 다음과 같아요.

| 시점 | 화면에서 확인한 것 | 요청에서 확인한 것 |
| --- | --- | --- |
| 첫 응답을 기다릴 때 | 카드가 나오기 전 스켈레톤이 보이고, 응답 뒤 첫 24개가 나타나요 | `offset: 0` 한 번 |
| 스크롤 중 추가 응답을 기다릴 때 | 기존 카드와 목록 아래 스피너가 함께 보여요 | 끝을 다시 지나도 `offset: 24` 한 번 |
| 마지막 응답 뒤 | 마지막 페이지를 24개로 채운 테스트에서 총 48개가 보여요 | 문서 끝을 지나도록 스크롤해도 `[0, 24]` |
| 첫 조회가 실패했을 때 | 오류와 다시 시도 버튼이 보이고, 다시 시도하면 첫 페이지가 나타나요 | `[0, 0]` |
| 추가 조회가 실패했을 때 | 보던 카드 대신 목록 영역에 오류가 표시되고, 다시 시도하면 첫 페이지부터 읽어요 | 복구한 뒤 다시 내리면 `[0, 24, 0, 24]` |

첫 조회를 멈춰 두면 카드가 나오기 전에 스켈레톤을 볼 수 있어요. 추가 조회를 멈춰 두면 카드 24개 아래에 스피너가 붙어요. 아래 코드는 두 번째 경우를 줄인 예시예요. `openGallery`는 페이지를 열기 전에 응답 가로채기를 등록하고, 테스트에서 Promise를 풀 때까지 두 번째 응답을 보류해요.

```typescript
const response = Promise.withResolvers<'success'>();
const { feed, cards, offsets } = await openGallery(page, {
  responses: { 24: response.promise },
});

await expect(cards).toHaveCount(24);
await scrollPastEnd(page);
await expect(
  feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' }),
).toBeVisible();
await expect(cards).toHaveCount(24);
expect(offsets).toEqual([0, 24]);

response.resolve('success');
await expect(cards).toHaveCount(26);
```

전체 테스트에서는 응답을 풀기 전에 목록 위로 올라갔다가 다시 끝까지 내려요. 내려가기 전에 요청 감시를 걸어 `offset: 24`가 한 번만 나가는지 봐요. 응답이 도착하면 마지막 두 카드가 붙어 26개가 되고 스피너가 사라져요.

## 마지막 페이지까지 갔을 때

기본 데이터에서는 26개를 받은 뒤 요청이 멈춰요. 그런데 다음 페이지를 서버의 `nextOffset` 대신 카드 수로 계산하도록 임시로 바꿔 봐도 기존 테스트 네 개가 모두 통과했어요. 마지막 페이지가 2개뿐이어서 두 구현이 같은 지점에서 멈췄기 때문이에요.

그래서 마지막 페이지에도 카드 24개를 채우고 응답에 `nextOffset: null`을 넣은 테스트를 따로 만들었어요. 목록에 48개가 표시되면 [요청 감시](https://playwright.dev/docs/api/class-page#page-wait-for-request)를 먼저 시작한 뒤 문서 높이보다 더 큰 위치로 스크롤하고 휠을 한 번 더 움직여요. 1초 동안 새 조회가 없었고, 요청 목록은 `[0, 24]`였어요. 같은 데이터에서 카드 수로 계산한 코드는 `offset: 48`을 요청해 실패했어요.

## 요청이 실패했을 때

첫 페이지 실패와 추가 페이지 실패는 따로 만들었어요. 두 경우 모두 다시 시도하면 첫 페이지부터 새로 받아서, 복구한 뒤의 개수만 보면 두 오류를 구분하기 어려워요. 그래서 실패한 요청의 offset과, 다시 시도한 뒤 스크롤해서 다음 페이지를 이어 읽을 수 있는지까지 확인했어요.

추가 조회가 실패하면 이미 보던 카드 24개도 오류 화면으로 바뀌어요. 피식의 목록은 Apollo의 `QueryRef`로 읽는데, `useQueryRefHandlers`의 `fetchMore`가 실패하면 같은 `QueryRef`도 실패 상태가 되어 목록을 감싼 오류 경계로 넘어가기 때문이에요. TanStack Query는 다음 페이지가 실패해도 이미 받은 페이지를 남기지만, 이 테스트는 피식의 지금 동작을 고정한 것이에요. 보던 목록을 남기려면 추가 조회의 실패를 `QueryRef`와 분리하고, 목록 아래에 다시 시도 버튼을 따로 둬야 해요.

## 같은 응답을 MSW로 만들기

피식의 테스트는 `page.route`로 응답을 제어하지만, 같은 응답을 [MSW 3의 GraphQL 핸들러](https://mswjs.io/api/graphql/)로도 만들 수 있어요. `GalleryPosts`에서 `offset: 0`은 첫 카드 24개와 `nextOffset: 24`를, `offset: 24`는 나머지 24개와 `nextOffset: null`을 반환해요. 응답을 보류하거나 실패시킬 때는 해당 offset에 Promise를 넣어요.

```typescript
import { graphql } from 'msw/graphql';
import { HttpResponse } from 'msw/http';

import { GalleryPostsDocument, type GalleryPostsQuery } from '@/shared/api/generated';

type TResponse = 'success' | 'error';

function galleryHandler(
  endpoint: string,
  posts: GalleryPostsQuery['galleryPostsPage']['items'],
  responses: Partial<Record<number, Promise<TResponse>>> = {},
) {
  const pageSize = 24;

  return graphql.link(endpoint).query(GalleryPostsDocument, async ({ variables: { offset } }) => {
    if (offset !== 0 && offset !== pageSize) {
      return HttpResponse.json({ errors: [{ message: `Unexpected offset ${offset}` }] });
    }

    if ((await responses[offset]) === 'error') {
      return HttpResponse.json({ errors: [{ message: 'Gallery request failed' }] });
    }

    return HttpResponse.json({
      data: {
        galleryPostsPage: {
          __typename: 'GalleryPostPage',
          items: posts.slice(offset, offset + pageSize),
          nextOffset: offset === 0 ? pageSize : null,
        },
      },
    });
  });
}
```

`posts`에 서로 다른 카드 48개를 준비해요. 브라우저 테스트 페이지에서 [워커를 시작](https://mswjs.io/api/setup-worker/)한 뒤, 목록을 띄우기 전에 추가 응답을 보류하는 핸들러를 등록해요.

```typescript
import { setupWorker } from 'msw/browser';

const endpoint = new URL('/__test__/gallery', window.location.origin).href;
const worker = setupWorker(galleryHandler(endpoint, posts));
await worker.start();

const nextPage = Promise.withResolvers<'success'>();
worker.use(galleryHandler(endpoint, posts, { 24: nextPage.promise }));
```

스크롤해서 카드 24개와 스피너가 함께 보이면 `nextPage.resolve('success')`를 호출하고, 카드가 48개로 늘어나는지 확인해요. 첫 로딩을 검사할 때는 새 Promise를 `offset: 0`에 연결하고, 스켈레톤이 보인 뒤 응답을 풀어요.

요청을 실패시키려면 해당 offset의 응답을 `'error'`로 정해요. 아래는 추가 조회를 실패시키는 예시예요.

```typescript
worker.use(galleryHandler(endpoint, posts, { 24: Promise.resolve('error') }));
```

`24`를 `0`으로 바꾸면 첫 조회가 실패해요. 두 경우 모두 오류 화면을 확인한 뒤 `worker.resetHandlers()`를 호출하면 처음 등록한 성공 핸들러가 복원돼요. 그 상태에서 다시 시도 버튼을 눌러 첫 페이지가 돌아오는지 확인할 수 있어요.

## 스크롤한 위치에서 드롭다운 열기

게시물 목록에서 처음 화면에는 보이지 않는 여덟 번째 카드까지 내려가요. 더보기 아이콘을 화면 안에 둔 뒤, 아이콘 아래에 남는 공간을 두 가지로 나눠 [메뉴가 열리는 위치](https://base-ui.com/react/components/menu)를 비교했어요. 300px을 남기면 메뉴가 누른 아이콘 아래에 붙어요. 20px만 남기면 메뉴가 아이콘 위로 올라와서 수정과 삭제를 모두 볼 수 있어요. 열기 전후의 `scrollY`도 비교해서 메뉴를 열자마자 목록이 움직이지 않는지 확인했어요.

위로 열린 경우에는 팝업 하단 좌표가 아이콘 상단보다 작은지, 팝업의 왼쪽과 오른쪽이 뷰포트 안에 있는지 검사했어요. Playwright의 [뷰포트 단언](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport)에서 요소 전체가 보이는 비율을 정확히 `1`로 두니, 브라우저 계산 결과가 `0.99999988`일 때 실패했어요. 그래서 메뉴 항목이 화면에 들어오는지는 작은 오차를 허용하고, 팝업이 어디에 열렸는지는 좌표로 확인했어요.

## 메뉴를 연 뒤 어디를 누르는지 나누기

메뉴가 닫혔는지만 검사하면 배경 클릭과 삭제 항목 클릭을 같은 결과로 볼 수 있어요. 삭제 항목을 고른 경우에는 확인 대화상자가 열려야 하고, 배경을 누른 경우에는 그 대화상자가 없어야 해요. 그래서 누르는 곳마다 테스트를 따로 뒀어요.

각 테스트는 스크롤한 카드에서 메뉴를 연 상태로 시작해요. 카드 이름을 포함한 `테스트 사진 8 더보기`를 트리거와 메뉴의 접근성 이름으로 사용해요. 열린 메뉴를 그 이름으로 찾은 뒤 그 안에서 항목을 고르면, 스크롤한 목록에서 어느 카드의 메뉴를 눌렀는지도 확인할 수 있어요.

| 누르는 곳 | 확인한 결과 |
| --- | --- |
| 메뉴 바깥 배경 | 메뉴가 닫히고 아이콘의 `aria-expanded`가 `false`로 바뀌어요. 확인 대화상자나 추가 요청이 생기지 않아요 |
| 삭제 메뉴 항목 | 메뉴가 닫히고 삭제 확인 대화상자가 열려요. 확인 전에 삭제 요청이 나가지 않고, 취소하면 게시물이 남아요 |
| 메뉴를 연 더보기 아이콘 | 같은 아이콘을 다시 누르면 닫혀요. 한 번 더 누르면 메뉴가 다시 열려요 |

## 답지를 보고 더한 테스트

무한 스크롤 훅 테스트에서는 TanStack Query와 Base UI처럼 화면에 반영된 상태를 순서대로 모았어요. 다음 페이지를 요청하면 기존 목록을 그대로 둔 채 조회 중 상태가 되고, 응답이 오면 새 페이지가 붙으면서 조회 중 상태가 끝나야 해요. 그 사이에 목록이 로딩 화면으로 바뀌는 단계가 끼면 기록에서 바로 드러나요.

새로고침과 겹치는 경우도 같은 방식으로 기록해 보니 버그가 나왔어요. 다음 페이지를 받는 중에 새로고침이 먼저 끝나면, 그 뒤에 부른 다음 페이지 조회가 같은 offset으로 한 번 더 시작됐고 페이지 도착 콜백도 두 번 불렸어요. 최신 게시물 목록에서는 이 콜백이 분석 이벤트를 보내요. 이런 일이 생긴 건 훅이 진행 중인 요청을 하나만 기억해서, 새로고침이 끝나면서 아직 진행 중인 다음 페이지 요청의 기록까지 지웠기 때문이에요.

화면에서는 조회 중에 목록 끝 감시를 멈추기 때문에 바로 드러나지 않았어요. 하지만 콘테스트 피드처럼 사진 수가 바뀌면 자동으로 새로고침하는 목록에서는 두 요청이 겹칠 수 있어요. 그래서 진행 중인 요청을 모두 기록하고, 마지막 요청이 끝날 때까지 다음 페이지 조회를 막도록 [훅을 고쳤어요](https://github.com/jingeon27/side-project/commit/4830f074859ade4126f7d0a93c7bad9148bc9e92).

메뉴 테스트에는 Radix와 Base UI가 확인하는 주변 상태를 더했어요. 닫혀 있을 때는 더보기 아이콘에 `aria-controls`가 없고, 열렸을 때만 메뉴의 id를 가리켜요. 키보드로 열면 수정 항목에 포커스가 가고, 아래 화살표를 누르면 구분선을 건너 삭제 항목으로 가요. Escape로 메뉴를 닫거나 삭제 확인 대화상자를 닫으면 포커스가 더보기 아이콘으로 돌아와요. 키보드 테스트는 Desktop Safari에서도 실행해요.

메뉴가 닫히는 동안의 입력은 Base UI처럼 전환 시간을 늘려서 확인했어요. 메뉴의 전환을 2초로 늘리고 Escape를 누른 뒤, 메뉴가 닫히는 동안 삭제 항목 위로 포인터를 옮겨 눌러요. 항목은 강조되지 않고 확인 대화상자도 열리지 않아요. 일부러 닫히는 메뉴가 포인터 입력을 받도록 바꿔 보니 이 테스트가 실패했어요.

무한 스크롤과 메뉴가 [겹치는 경우](https://github.com/jingeon27/side-project/commit/49294bdff9abf8120bb67cfc06c6e61ef4d7188b)도 따로 확인했어요. 마지막 카드의 메뉴를 연 채로 다음 페이지가 도착하면 메뉴가 같은 좌표에 그대로 열려 있어요. 다음 페이지 요청이 실패하면 목록이 오류 화면으로 바뀌면서 메뉴가 사라지고, 메뉴가 걸어 둔 `body`의 스크롤 잠금도 풀려요. 다시 시도하면 첫 페이지가 돌아와요. 메뉴 없이 다음 페이지가 붙을 때도 보던 카드의 위치와 `scrollY`가 그대로인지 확인했어요.
