실무에서 작성한 단위 테스트는 주로 로직을 확인하는 코드였어요. 화면은 통합 테스트와 E2E로 확인해 왔고요. UI는 Radix와 Base UI, shadcn/ui로 많이 만들었어요. 사용하는 사람이 많고 다운로드 수도 높고, 보고된 이슈도 빨리 고쳐져서 믿고 썼어요. 정작 컴포넌트들이 어떤 테스트를 거치는지는 깊게 살펴보지 않았어요.

라이브러리 코드를 읽을 때도 구현과 타입 정의에 먼저 눈이 갔어요. 테스트 코드는 어떤 값을 넣고 어떻게 사용하는지 확인하려고 찾아보는 편이었고요.

실무에서 정했던 [테스트 파일 규칙](/ko/blog/테스트-코드를-도입하면서-세운-기준)도 돌아봤어요. 새 기능의 명세는 `*.spec.*`에 쓰고, 예상하지 못한 오류는 `*.test.*`에 재현해 같은 문제가 다시 생기지 않는지 확인했어요. 제 테스트 설계에 부족한 점이 있다고 생각해서, 뒤늦게 발견한 문제라도 테스트로 남기려고 정한 규칙이기도 했어요. 돌이켜 보면 문제를 찾은 뒤 테스트를 보태는 데 기대고 있었어요. 처음 명세를 쓸 때부터 어떤 상황을 확인할지 더 고민했어야 했어요.

무한 스크롤과 드롭다운처럼 자주 쓰는 UI에도 놓치기 쉬운 상황이 많아요. 목록 끝에 새 카드가 붙는지만 검사하면 응답을 기다리는 동안 기존 목록이 잠깐 사라져도 통과할 수 있어요. 메뉴가 열리는지만 보면 화면 아래로 잘려 마지막 항목을 누르지 못하는 경우를 놓칠 수 있고요.

피식의 갤러리에는 게시물 24개를 불러온 뒤 스크롤을 내려 다음 페이지를 읽는 [E2E 테스트](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/gallery-pagination.spec.ts)가 있었어요. 여기에 응답이 늦거나 실패하는 상황, 스크롤한 위치에서 더보기 메뉴를 여는 상황을 추가했어요.

## 라이브러리 테스트를 답지로 봤어요

TanStack Query와 Radix, Base UI의 테스트를 읽으면서 시작 상태와 조작, 기대하는 결과를 차례로 살펴봤어요. 살펴본 테스트 파일은 하나에 1,300줄에서 4,900줄 정도였어요. 참고할 테스트 몇 개를 고르기 전에, 파일 전체를 어떤 기준으로 나눴는지부터 봤어요.

### TanStack Query: 기능마다 상태가 바뀌는 순서를 기록해요

[`useInfiniteQuery` 테스트](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx)는 1,839줄짜리 파일이고, 테스트는 28개예요. 조회가 성공했을 때와 이전 페이지나 다음 페이지를 불러올 때를 나눠 검사해요. `select`, `placeholderData`, `initialData` 같은 옵션, 조회 종류에 따른 실패, 진행 중인 조회와 새 조회가 겹칠 때의 취소도 따로 확인해요. 다음 페이지가 있는지 나타내는 `hasNextPage`를 계산할 때도 여러 조건을 검사하고요.

많은 테스트가 렌더할 때마다 훅의 상태를 배열에 모아 두고, 기록된 순서가 기대한 순서와 같은지 비교해요. 마지막 결과만 보면 중간에 목록이 잠깐 비었다가 다시 채워져도 알아채기 어려워요. 상태를 차례로 기록하면 목록이 비었던 시점도 확인할 수 있어요. 실패도 조회 종류마다 나눠 검사해요. 다음 페이지 요청이 실패해도 이미 받은 페이지가 남고 `isFetchNextPageError`가 `true`가 되는지, 전체를 다시 조회하다 실패하면 어떤 상태가 되는지 확인해요. [각 테스트 전에는 새 QueryClient를 만들고 끝나면 캐시를 비워서](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx#L31-L46), 앞 테스트의 데이터 때문에 다음 테스트에서 첫 로딩을 건너뛰는 일도 막아요.

피식의 무한 스크롤 훅 테스트에서도 화면에 반영된 상태를 순서대로 기록했어요. 그 과정에서 새로고침과 추가 조회가 겹치면 같은 offset을 다시 요청하는 버그를 찾았어요. `hasNextPage`를 여러 조건으로 검사하는 테스트를 참고해, 마지막 페이지에서는 조회를 멈추는지 따로 확인했어요. 테스트마다 클라이언트도 새로 만들었고요. 다만 추가 조회가 실패해도 기존 페이지를 남기는 동작은 피식과 달랐어요. 피식에서 실패를 어떻게 처리하는지는 아래에서 설명할게요.

### Radix: 문제별 회귀 테스트와 부품별 계약 테스트, 조작 흐름은 E2E로 나눠요

드롭다운은 평소 사용하던 shadcn/ui부터 살펴봤어요. shadcn/ui는 드롭다운을 Radix와 Base UI, React Aria 버전으로 제공하는데, [Base UI 버전](https://github.com/shadcn-ui/ui/blob/8ab27715521cbd4f87ae6886cd989cbb678f6de7/apps/v4/registry/bases/base/ui/dropdown-menu.tsx)은 Base UI의 컴포넌트를 조합해 스타일을 입혀요. 열고 닫기나 포커스 처리를 검증하는 코드는 기반 라이브러리인 Radix와 Base UI에서 찾아봤어요.

Radix의 [DropdownMenu 단위 테스트](https://github.com/radix-ui/primitives/blob/fe02008f49834d7421427fe532e5b11f13c7bcac/packages/react/dropdown-menu/src/dropdown-menu.test.tsx)는 1,286줄이고, 크게 두 부분으로 나뉘어요. 앞부분에서는 문제마다 `describe`로 테스트를 묶어요. 닫힌 메뉴의 `aria-controls`, 창이 포커스를 잃었을 때의 동작, 메뉴 안 입력 요소의 Space와 Enter 처리, 닫히는 중의 포인터 이동, ref 안정성을 각각 검사해요. 나머지 약 1,000줄은 각 컴포넌트가 props를 올바르게 전달하는지 확인하는 계약 테스트예요. Trigger부터 SubContent까지 열세 개 컴포넌트를 같은 방식으로 검사해요. 컴포넌트가 직접 사용하지 않는 props를 렌더한 요소에 전달하는지, `asChild`를 쓰면 자식 요소에 전달하는지 확인하는 거예요.

앞부분의 테스트는 대부분 보고된 문제를 고치면서 추가됐어요. 커밋 기록을 보면 `aria-controls`([#3922](https://github.com/radix-ui/primitives/pull/3922)), 창 포커스([#3938](https://github.com/radix-ui/primitives/pull/3938)), ref 안정성([#3968](https://github.com/radix-ui/primitives/pull/3968)), 입력 요소의 키 처리([#3999](https://github.com/radix-ui/primitives/pull/3999)), 닫히는 중의 포인터 처리([#4196](https://github.com/radix-ui/primitives/pull/4196))를 고친 PR마다 테스트가 함께 추가됐어요. 컴포넌트별 계약 테스트는 2026년 7월에 한꺼번에 추가됐고요. `aria-controls` 문제([#3013](https://github.com/radix-ui/primitives/issues/3013))와 하위 메뉴 문제([#3257](https://github.com/radix-ui/primitives/issues/3257))는 2024년에 보고돼 2026년 6월에 고쳐졌어요. 닫히는 메뉴의 포인터 문제는 2022년 3월 [#1266](https://github.com/radix-ui/primitives/issues/1266)으로 처음 보고됐고, 수정된 시점은 2026년 10월이었어요.

메뉴를 실제로 조작하는 과정은 [Playwright E2E](https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/e2e/dropdown-menu.spec.ts)에서 확인해요. Storybook 스토리를 열고, 하위 메뉴를 포인터로 조작하는 경우와 키보드로 조작하는 경우를 나눠요. 좁은 화면, 오른쪽에서 왼쪽으로 쓰는 RTL 레이아웃, Dialog 안에 놓인 메뉴도 별도로 검사해요.

피식에서도 문제별 회귀 테스트와 실제 메뉴 조작을 확인하는 테스트를 구분했어요. 닫힌 메뉴의 트리거에서 `aria-controls`가 사라지는지, 닫히는 중인 메뉴가 포인터 입력을 받지 않는지 확인하는 테스트를 추가했어요. 피식의 더보기 메뉴에는 하위 메뉴가 없어서 창 포커스와 하위 메뉴를 다룬 테스트는 적용하지 않았어요. 컴포넌트별 props 전달은 라이브러리가 보장하는 동작이므로 피식에서 다시 검사하지 않았고요.

### Base UI: 상호작용과 prop별로 묶고, 브라우저가 필요한 테스트를 표시해요

Base UI의 [메뉴 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/root/MenuRoot.test.tsx)는 4,899줄이에요. 메뉴 열기, 키보드 탐색, 하위 메뉴, 포커스 관리, 스크롤 잠금, 마우스 조작을 `describe`로 나눠요. `modal`, `openOnHover`, `disabled` 같은 prop도 각각 묶어서 검사해요. 그 안에서는 동작마다 `it`을 따로 작성해요. 화살표 키로 강조된 항목을 옮기는 동작과 Home, End 키로 처음이나 끝으로 이동하는 동작을 따로 확인하는 식이에요. 한 동작의 테스트가 실패해도 다른 테스트는 독립적으로 실행돼요.

테스트는 jsdom과 실제 브라우저에서 실행해요. 그중 포인터를 올려 메뉴 열기, 스크롤 잠금, 마우스 조작, 메뉴 항목에서 대화상자 열기처럼 브라우저가 필요한 묶음에는 `describe.skipIf(isJSDOM)`을 붙여 jsdom에서 건너뛰어요. 팝업의 [전환 상태 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/popup/MenuPopupTransitionState.test.tsx)는 열기와 닫기, 닫히다가 다시 열기를 한 테스트에서 이어서 실행하며 상태를 기록해요. 앞선 전환이 다음 전환에 영향을 주므로 이 과정은 함께 확인하는 거예요. 중간 상태를 확인할 수 있도록 전환 시간을 10초로 늘리고, 검사가 끝나면 `getAnimations()`로 가져온 애니메이션에 `finish()`를 호출해 종료 시점을 정해요.

피식에서도 독립적으로 확인할 수 있는 조작은 테스트를 나누고, 앞뒤 상태를 이어서 봐야 하는 과정은 한 테스트에 뒀어요. 키보드 테스트는 Enter로 열기, 아래 화살표로 이동, Escape로 닫기로 나눴어요. 무한 스크롤도 목록 유지와 중복 요청 방지를 따로 검사하게 바꿨고요. 메뉴가 닫히는 동안의 입력은 Base UI처럼 전환 시간을 늘리고 종료 시점을 직접 제어해서 확인해요. 메뉴 항목에서 대화상자를 여는 경우와 스크롤 잠금도 확인했어요. 삭제 대화상자를 닫은 뒤 포커스가 더보기 아이콘으로 돌아오는지, 목록이 오류 화면으로 바뀌면 페이지를 다시 스크롤할 수 있는지 검사했어요.

## 무한 스크롤 테스트

피식의 갤러리는 offset을 기준으로 게시물을 24개씩 불러와요. 서버가 `nextOffset`을 `null`로 보내면 마지막 페이지예요. 목록 끝이 화면에 들어오면 다음 페이지를 요청하고, 받은 게시물은 기존 목록 뒤에 붙여요. 첫 조회와 추가 조회는 각각 실패할 수 있고, 콘테스트 피드처럼 목록이 자동으로 새로고침되는 화면도 있어요.

### 응답 시점을 제어해 상태 만들기

피식에서는 최신 게시물 목록과 게시물 카드, 더보기 메뉴를 테스트 전용 페이지에 띄워요. Playwright의 [`page.route`](https://playwright.dev/docs/mock)로 GraphQL 응답이 도착하는 시점을 제어하고, 목록 끝을 감지하는 `IntersectionObserver`와 다음 페이지를 붙이는 Apollo 캐시는 실제 구현을 사용해요.

기본 테스트 데이터는 첫 페이지에 24개, 마지막 페이지에 2개예요. 요청마다 offset을 기록하면 첫 조회는 `0`, 추가 조회는 `24`로 남아요. 테스트 페이지에서는 첫 조회를 브라우저에서 시작해요. 서버가 미리 받은 콘텐츠를 HTML에 포함하는지는 [별도의 E2E](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/access-layout.spec.ts#L32)에서 확인해요.

응답을 보류하거나 실패시켜 다음 상황을 확인했어요.

| 시점 | 화면에서 확인한 것 | 요청에서 확인한 것 |
| --- | --- | --- |
| 첫 응답을 기다릴 때 | 카드가 나오기 전 스켈레톤이 보이고, 응답 뒤 첫 24개가 나타나요 | `offset: 0` 한 번 |
| 스크롤 중 추가 응답을 기다릴 때 | 기존 카드와 목록 아래 스피너가 함께 보여요 | 끝을 다시 지나도 `offset: 24` 한 번 |
| 마지막 응답 뒤 | 마지막 페이지를 24개로 채운 테스트에서 총 48개가 보여요 | 문서 끝을 지나도록 스크롤해도 `[0, 24]` |
| 첫 조회가 실패했을 때 | 오류와 다시 시도 버튼이 보이고, 다시 시도하면 첫 페이지가 나타나요 | `[0, 0]` |
| 추가 조회가 실패했을 때 | 보던 카드 대신 목록 영역에 오류가 표시되고, 다시 시도하면 첫 페이지부터 읽어요 | 복구한 뒤 다시 내리면 `[0, 24, 0, 24]` |

피식의 Playwright 테스트는 테스트마다 새 페이지에서 앱과 Apollo 클라이언트를 시작해요. 응답을 제어할 Promise와 요청 기록도 매번 새로 만들어요.

첫 응답을 보내지 않고 기다리면 스켈레톤을 확인할 수 있어요. 추가 조회의 응답을 보류하면 기존 카드 아래에 스피너가 나타나고요. 처음에는 추가 조회 중 목록이 유지되는지, 중복 요청이 없는지, 응답 뒤에 카드가 붙는지를 한 테스트에서 검사했어요. 지금은 목록이 유지되다가 새 카드가 붙는 과정과 중복 요청을 막는 동작을 따로 검사해요. 첫 조회의 로딩 표시와 로딩 중 추가 요청 방지도 각각 확인하고요.

아래는 분리한 테스트를 간략히 옮긴 예시예요. [`openGallery`](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/test/browser/gallery.fixture.ts)는 페이지를 열기 전에 요청을 가로챌 핸들러를 등록해요. 지정한 offset의 첫 응답은 Promise가 완료될 때까지 보내지 않아요.

```typescript
test('추가 조회 중에는 기존 목록을 유지하고 응답 뒤 새 카드를 붙인다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards } = await openGallery(page, {
    responses: { 24: response.promise },
  });
  const loading = feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(loading).toBeVisible();
    await expect(cards.first()).toHaveAccessibleName('테스트 사진 1');
    await expect(cards).toHaveCount(24);
  } finally {
    response.resolve('success');
  }

  await expect(cards).toHaveCount(26);
  await expect(cards.last()).toHaveAccessibleName('테스트 사진 26');
  await expect(loading).toBeHidden();
});
```

로딩 표시를 확인한 뒤에 응답을 보내야 로딩 중인 화면까지 검사할 수 있어요. 카드 수와 첫 카드의 이름, 스피너를 함께 확인하는 이유는 추가 조회 중에도 기존 목록이 유지되는지 보려는 거예요. 이 검사들은 같은 과정에 속하므로 한 테스트에 뒀어요.

중복 요청을 검사할 때도 추가 조회의 응답을 보류해요. 그 상태에서 목록 위로 올라갔다가 다시 끝까지 내려요. `expectNoGalleryRequest`는 1초 동안 갤러리 요청을 감시해요. 그동안 새 요청이 없어야 통과해요.

```typescript
test('추가 조회가 끝나기 전 다시 내려도 같은 offset을 요청하지 않는다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards, offsets } = await openGallery(page, {
    responses: { 24: response.promise },
  });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(
      feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' }),
    ).toBeVisible();
    await cards.first().scrollIntoViewIfNeeded();

    const noRequest = expectNoGalleryRequest(page);
    await Promise.all([noRequest, scrollPastEnd(page)]);
    expect(offsets).toEqual([0, 24]);
  } finally {
    response.resolve('success');
  }
});
```

요청 감시는 두 번째 스크롤 전에 시작해요. 스크롤을 먼저 하면 그 순간 나간 요청을 놓칠 수 있어요. 테스트가 실패해도 응답이 보류된 채 남지 않도록 `finally`에서 응답을 보내요. 두 테스트를 나눠 두면 목록 유지에 문제가 생겨도 중복 요청을 막는지는 따로 확인할 수 있어요.

### 마지막 페이지까지 갔을 때

기본 데이터로는 카드 26개를 받은 뒤 조회가 멈췄어요. 그런데 다음 페이지를 서버의 `nextOffset` 대신 카드 수로 계산하도록 임시로 바꿔도 당시 테스트 네 개가 모두 통과했어요. 마지막 페이지가 2개뿐이어서 두 구현 모두 같은 지점에서 멈췄기 때문이에요.

그래서 마지막 페이지에도 카드 24개를 채우고 응답에 `nextOffset: null`을 넣은 테스트를 따로 만들었어요. 목록에 48개가 표시되면 [요청 감시](https://playwright.dev/docs/api/class-page#page-wait-for-request)를 시작해요. 그런 다음 문서 높이보다 큰 값으로 스크롤하고 휠을 한 번 더 움직여요. 1초 동안 새 조회가 없었고, 기록한 offset은 `[0, 24]`였어요. 같은 데이터에서 카드 수로 다음 offset을 계산하는 구현은 `offset: 48`을 요청해서 테스트에 걸렸어요.

이 테스트에서는 마지막 응답을 받은 뒤 다시 목록 끝으로 내려가요. 로딩 중이거나 목록 중간에 있을 때 새 요청이 없다고 해서 마지막 페이지에서 멈췄다고 볼 수는 없어요. 브라우저 테스트로 확인한 것은 다시 스크롤한 뒤 1초 동안 새 요청이 없었다는 점이에요. 서버가 알려 준 종료 조건을 따르는지는 훅 테스트에서도 따로 검사해요.

### 요청이 실패했을 때

첫 조회 실패와 추가 조회 실패는 따로 검사했어요. 어느 쪽이든 다시 시도하면 첫 페이지부터 받아서, 복구한 뒤의 카드 수만 보면 둘을 구분하기 어려워요. 먼저 어느 offset에서 실패했는지 확인하고, 다시 시도한 뒤에도 스크롤로 다음 페이지를 이어 읽을 수 있는지 봤어요.

추가 조회가 실패하면 이미 보던 카드 24개 대신 오류 화면이 나타나요. 목록을 읽는 Apollo의 `QueryRef`가 `fetchMore` 실패로 오류 상태가 되고, 목록을 감싼 오류 경계가 오류 화면을 보여 주기 때문이에요.

앞서 본 TanStack Query 테스트는 추가 조회에 실패해도 기존 페이지가 남는지 확인해요. 피식에서도 보던 목록을 남기려면 추가 조회 오류를 목록 전체의 실패와 구분하고, 목록 아래에서 다시 시도할 수 있게 바꿔야 해요. 라이브러리의 테스트를 참고하더라도 기대하는 결과는 제품의 동작에 맞춰 정해야 해요.

테스트를 시작하는 상태도 달라요. 첫 조회 실패는 카드가 없는 상태에서 시작하고, 추가 조회 실패는 카드 24개를 먼저 받은 뒤 스크롤해요. 두 경우 모두 오류가 보이는지 확인한 다음 다시 시도해요. 실패한 조회를 다시 불러오는 과정을 확인하므로 오류와 재시도는 한 테스트에서 검사해요.

재시도마저 실패하는 상황은 별도의 테스트로 추가할 수 있어요. 두 번 연속 실패하는 응답을 준비해 오류 화면과 다시 시도 버튼이 유지되는지 확인하는 거예요.

### 새로고침과 추가 조회가 겹칠 때

브라우저에서 화면을 확인한 뒤에는 훅의 조회 상태가 바뀌는 과정도 살펴봤어요. TanStack Query의 테스트를 참고해 화면에 반영된 상태를 순서대로 기록했어요. 추가 조회가 시작되면 기존 목록을 유지하면서 조회 중이라는 상태가 함께 나타나야 해요. 응답이 오면 새 페이지가 붙고 조회 중 상태가 끝나야 하고요. 그사이에 목록 전체가 로딩 화면으로 바뀌었다면 기록한 상태에서 찾을 수 있어요.

새로고침과 추가 조회가 겹치는 상황을 검사하다가 버그를 찾았어요. 다음 페이지를 받는 도중 새로고침이 먼저 끝나면, 추가 조회 함수를 다시 호출했을 때 같은 offset으로 요청이 한 번 더 나갔어요. 페이지를 받은 뒤 실행하는 콜백도 두 번 호출됐고요. 최신 게시물 목록은 이 콜백에서 분석 이벤트를 보내므로 이벤트도 중복될 수 있었어요.

당시 훅은 진행 중인 요청을 하나만 저장했어요. 새로고침이 끝나면 그 값을 비워서, 다음 페이지를 아직 받지 못했는데도 새 요청을 보낼 수 있는 상태가 됐어요.

추가 조회 중에는 목록 끝의 스크롤 감시를 멈추기 때문에 화면을 조작하는 것만으로는 이 문제가 바로 드러나지 않았어요. 하지만 사진 수가 바뀌면 자동으로 새로고침하는 콘테스트 피드에서는 두 요청이 겹칠 수 있어요. 처음에는 [진행 중인 요청을 모두 기록하도록 고쳤고](https://github.com/jingeon27/side-project/commit/4830f074859ade4126f7d0a93c7bad9148bc9e92), 이후에는 [Apollo ObservableQuery의 현재 조회 상태를 읽도록 바꿨어요](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/src/shared/api/infinite-query.hook.ts). 지금은 훅이 요청을 별도로 기록하지 않고, Apollo의 조회가 끝났는지 확인한 뒤 다음 페이지를 요청해요.

훅 테스트에서는 Apollo의 `queryDeduplication`을 꺼요. 같은 요청을 여러 번 호출해도 Apollo가 하나로 합쳐 보내면 네트워크 기록만으로는 중복 호출을 놓칠 수 있어요. 그래서 요청한 offset과 페이지를 받은 뒤 실행하는 콜백의 호출 횟수를 함께 확인해요. 스크롤했을 때 실제로 요청이 나가는지는 브라우저에서 검사하고, 요청이 겹칠 때 추가 호출을 막는지는 훅 테스트에서 확인해요.

### 같은 응답을 MSW로 만들기

지금까지는 `page.route`로 응답을 제어했어요. 같은 상황을 [MSW 3의 GraphQL 핸들러](https://mswjs.io/api/graphql/)로도 만들 수 있어요. 아래 예시는 카드 48개를 두 페이지로 나눠 반환해요. `offset: 0`에는 첫 24개와 `nextOffset: 24`를, `offset: 24`에는 나머지 24개와 `nextOffset: null`을 보내요. 특정 응답을 보류하거나 실패시키려면 해당 offset에 Promise를 넘겨요.

```typescript
import { graphql } from 'msw/graphql';
import { HttpResponse } from 'msw/http';

import { GalleryPostsDocument, type GalleryPostsQuery } from '@/shared/api/generated';

type TResponse = 'success' | 'error';

function galleryHandler(
  endpoint: string,
  posts: GalleryPostsQuery['galleryPostsPage']['items'],
  responses: Partial<Record<number, Promise<TResponse>>> = {},
) {
  const pageSize = 24;

  return graphql.link(endpoint).query(GalleryPostsDocument, async ({ variables: { offset, limit } }) => {
    if ((offset !== 0 && offset !== pageSize) || limit !== pageSize) {
      return HttpResponse.json({ errors: [{ message: 'Unexpected pagination variables' }] });
    }

    if ((await responses[offset]) === 'error') {
      return HttpResponse.json({ errors: [{ message: 'Gallery request failed' }] });
    }

    return HttpResponse.json({
      data: {
        galleryPostsPage: {
          __typename: 'GalleryPostPage',
          items: posts.slice(offset, offset + pageSize),
          nextOffset: offset === 0 ? pageSize : null,
        },
      },
    });
  });
}
```

`posts`에 서로 다른 카드 48개를 준비해요. 브라우저 테스트 페이지에서 [워커를 시작](https://mswjs.io/api/setup-worker/)한 뒤, 목록을 띄우기 전에 추가 응답을 보류하는 핸들러를 등록해요.

```typescript
import { setupWorker } from 'msw/browser';

const endpoint = new URL('/__test__/gallery', window.location.origin).href;
const worker = setupWorker(galleryHandler(endpoint, posts));
await worker.start();

const nextPage = Promise.withResolvers<'success'>();
worker.use(galleryHandler(endpoint, posts, { 24: nextPage.promise }));
```

스크롤한 뒤 카드 24개와 스피너가 함께 보이는지 확인해요. 그다음 `nextPage.resolve('success')`를 호출해 응답을 보내고, 카드가 48개로 늘어나는지 봐요. 첫 로딩을 검사할 때는 새 Promise를 `offset: 0`에 연결하고, 스켈레톤이 보인 뒤 응답을 보내요.

요청을 실패시키려면 해당 offset의 응답을 `'error'`로 정해요. 아래는 추가 조회를 실패시키는 예시예요.

```typescript
worker.use(galleryHandler(endpoint, posts, { 24: Promise.resolve('error') }));
```

`24`를 `0`으로 바꾸면 첫 조회가 실패해요. 두 경우 모두 오류 화면을 확인한 뒤 [`worker.resetHandlers()`](https://mswjs.io/api/setup-worker/reset-handlers/)를 호출하면 처음 등록한 성공 핸들러가 복원돼요. 그 상태에서 다시 시도 버튼을 눌러 첫 페이지가 돌아오는지 확인할 수 있어요.

테스트가 끝나면 핸들러뿐 아니라 클라이언트와 보류한 응답도 정리해야 해요. `resetHandlers()`는 Apollo 캐시나 보류 중인 Promise까지 초기화하지 않아요. 컴포넌트를 언마운트하고 보류한 응답을 마무리한 뒤, 다음 테스트에서는 새 Promise와 Apollo 클라이언트를 사용해요. 같은 테스트에서 다시 시도할 때는 기존 클라이언트를 유지해 실패한 조회가 복구되는지 확인하고요.

위 핸들러는 요청할 때마다 오류를 반환해요. 오류 화면만 확인하고 바로 재시도하면 같은 오류가 반복되므로, 재시도 전에 성공 응답으로 돌려놓아야 해요.

MSW를 써도 화면에서 확인할 동작은 같아요. 기존 카드가 남는지, 스피너와 오류가 언제 나타나는지는 그대로 검사해야 해요.

## 드롭다운 테스트

드롭다운은 어떤 라이브러리로 만드느냐에 따라 기본 동작이 달라요. 체크박스 항목을 누르면 Base UI는 메뉴를 열어 두고(`closeOnClick` 기본값 `false`), Radix는 닫아요.

흔히 드롭다운이라고 부르는 UI도 [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/)에서는 여러 패턴으로 나뉘어요. 작업을 선택하는 메뉴 버튼, 값을 선택하는 리스트박스, 글자를 입력해 선택지를 좁히는 콤보박스예요. 패턴마다 필요한 키보드 동작과 ARIA 속성도 달라요.

피식의 더보기 메뉴는 Base UI의 Menu로 만든 메뉴 버튼이에요. 항목을 고르면 메뉴가 닫혀요. 수정을 고르면 편집 시트가 열리고, 숨기기와 삭제는 확인 대화상자를 한 번 더 거쳐요. 목록을 스크롤한 상태에서 카드의 메뉴를 열 수 있고, 메뉴가 열려 있는 동안에는 페이지를 스크롤할 수 없어요. 마우스뿐 아니라 키보드로도 메뉴를 열고 항목을 고를 수 있어야 해요.

### 스크롤한 위치에서 드롭다운 열기

드롭다운은 먼저 스크롤 위치에 따라 어디에 열리는지 확인했어요. 처음 화면에는 보이지 않는 여덟 번째 카드까지 내려가, 더보기 아이콘 아래의 여유 공간을 바꿔 봤어요. 공간이 300px이면 [메뉴가 아이콘 아래에 열리고](https://base-ui.com/react/components/menu), 20px이면 위로 열려 수정과 삭제 항목이 모두 보여요. 열기 전후의 `scrollY`를 비교해 메뉴를 여는 순간 목록이 움직이지 않는지도 확인했어요.

위로 열린 메뉴는 팝업 하단이 아이콘 상단보다 위에 있는지, 팝업 양쪽 끝이 화면 안에 들어오는지 좌표로 검사했어요. 메뉴 항목이 화면 안에 보이는지는 Playwright의 [`toBeInViewport`](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport)로 확인했고요.

이때 항목이 화면에 보이는 비율을 정확히 `1`로 검사하니 브라우저가 `0.99999988`을 반환한 경우 실패했어요. 메뉴 위치가 틀어진 것이 아니라 계산 결과에 작은 오차가 있었어요. 그래서 보이는 비율에는 작은 오차를 허용하고, 메뉴가 열리는 방향은 좌표로 확인했어요.

위아래로 열리는 두 경우는 Base UI의 `it.each`처럼 남은 공간과 예상 방향을 짝지어 검사할 수 있어요. 각 조합이 별도의 테스트로 실행되면 한쪽이 실패해도 다른 쪽의 결과를 볼 수 있어요. 카드를 준비하고 스크롤 위치를 맞추는 코드는 도우미 함수로 빼고, 메뉴를 연 뒤 좌표를 비교하는 코드는 각 테스트에 남기면 무엇을 검사하는지 읽기 쉬워요.

### 메뉴를 연 뒤 어디를 누르는지 나누기

메뉴가 닫혔다는 결과만 보면 배경을 누른 것과 삭제 항목을 고른 것이 같아 보여요. 하지만 삭제를 고르면 확인 대화상자가 열려야 하고, 배경을 누르면 대화상자 없이 닫혀야 해요. 그래서 클릭하는 위치마다 테스트를 따로 뒀어요.

각 테스트에서는 같은 카드까지 스크롤한 뒤 메뉴를 열어요. 트리거와 메뉴에는 카드 이름을 포함한 `테스트 사진 8 더보기`라는 접근성 이름을 붙였어요. 이 이름으로 메뉴를 찾고 그 안에서 항목을 고르면, 어떤 카드의 메뉴를 조작하는지도 분명해져요.

| 누르는 곳 | 확인한 결과 |
| --- | --- |
| 메뉴 바깥 배경 | 메뉴가 닫히고 아이콘의 `aria-expanded`가 `false`로 바뀌어요. 확인 대화상자가 없고 목록 조회 기록도 그대로예요 |
| 삭제 메뉴 항목 | 메뉴가 닫히고 삭제 확인 대화상자가 열려요. 취소하면 대화상자가 사라지고 해당 게시물이 남아요 |
| 메뉴를 연 더보기 아이콘 | 같은 아이콘을 다시 누르면 닫혀요. 한 번 더 누르면 메뉴가 다시 열려요 |

여기서 기록하는 offset은 목록 조회에만 해당해요. 취소할 때 삭제 요청도 나가지 않는지 확인하려면 클릭 전에 삭제 mutation을 별도로 감시해야 해요. 삭제를 확정하는 테스트에서는 해당 게시물 id가 한 번만 전달되는지도 확인할 수 있어요. 카드가 화면에 남았다는 사실만으로 삭제 요청까지 없었다고 판단할 수는 없어요.

### 키보드 조작과 포커스 확인하기

키보드 조작은 Enter로 열기, 아래 화살표로 이동하기, Escape로 닫기를 각각 검사해요. 테스트마다 새 페이지에서 메뉴를 준비하므로 한 조작이 실패해도 다른 조작의 결과를 확인할 수 있어요. 이 테스트들은 Desktop Safari에서도 실행해요.

포커스와 함께 `aria-controls`도 확인해요. 메뉴가 닫혀 있을 때는 트리거에 이 속성이 없어요. 메뉴를 열면 해당 메뉴의 id가 속성값으로 들어가고, 다시 닫으면 사라져야 해요. 그래야 DOM에서 제거된 메뉴를 가리키는 값이 남지 않아요.

| 나눈 테스트 | 준비할 상태 | 확인할 결과 |
| --- | --- | --- |
| Enter로 열기 | 더보기 아이콘에 포커스 | 수정 항목에 포커스가 가요 |
| 아래 화살표로 이동 | 메뉴가 열리고 수정에 포커스 | 구분선을 건너 삭제로 가요 |
| Escape로 닫기 | 메뉴가 열리고 항목에 포커스 | 메뉴가 사라지고 더보기 아이콘으로 돌아와요 |
| 삭제 대화상자 취소 | 삭제를 골라 확인 대화상자가 열린 상태 | 게시물은 남고 더보기 아이콘으로 포커스가 돌아와요 |

Escape를 검사할 때도 메뉴를 열고 항목에 포커스가 있는 상태부터 준비해야 해요. 삭제 대화상자를 취소한 뒤 포커스가 돌아오는지 확인하려면 삭제를 선택하는 과정도 필요하고요. 이런 준비와 결과는 한 테스트에 두되, 메뉴의 위치나 다음 페이지 도착처럼 다른 조건은 별도로 검사하면 실패한 원인을 좁히기 쉬워요.

### 메뉴가 닫히는 동안의 입력 확인하기

메뉴는 닫히는 중에도 화면에 잠깐 남아 있을 수 있어요. 이때 포인터를 올리거나 클릭해도 메뉴 항목의 기능이 실행돼서는 안 돼요. 전환이 끝난 뒤에만 확인하면 닫히는 동안의 잘못된 동작을 놓칠 수 있어요.

피식의 테스트도 Base UI처럼 애니메이션을 끝내는 시점을 직접 정해요. 닫히는 시간을 10초로 늘리고 Escape를 누른 뒤, `data-ending-style`과 실행 중인 애니메이션이 있는지 확인해요. 이어서 `pause()`로 애니메이션을 멈춘 상태에서 포인터를 움직이고 삭제 항목을 눌러요. 애니메이션이 시작되기 전에도 `getAnimations()`는 빈 배열을 돌려줄 수 있으니, 시작됐는지부터 확인해야 해요.

포인터를 움직이고 클릭하는 동안 메뉴는 DOM에 남아 있어야 해요. 항목이 강조되거나 삭제 확인 대화상자가 열려서는 안 되고요. 검사를 마치면 `finish()`로 애니메이션을 끝내고 메뉴가 제거되는지 확인해요. 일부러 닫히는 메뉴가 포인터 입력을 받도록 바꾸면 이 테스트가 실패해요.

## 무한 스크롤과 드롭다운이 겹칠 때

마지막으로 목록 갱신과 메뉴 조작이 [겹치는 상황](https://github.com/jingeon27/side-project/commit/49294bdff9abf8120bb67cfc06c6e61ef4d7188b)을 확인했어요. 다음 페이지가 붙어도 보던 카드의 위치와 `scrollY`가 유지되는지 먼저 봤어요. 마지막 카드의 메뉴를 연 상태에서도 새 페이지가 도착한 뒤 메뉴가 같은 좌표에 열려 있는지 확인했고요.

다음 페이지 요청이 실패하면 목록이 오류 화면으로 바뀌면서 열린 메뉴도 사라져요. 이때 메뉴가 걸어 둔 `body`의 스크롤 잠금이 풀리는지 확인했어요. 다시 시도하면 첫 페이지가 돌아와 목록을 다시 읽을 수 있어요.
