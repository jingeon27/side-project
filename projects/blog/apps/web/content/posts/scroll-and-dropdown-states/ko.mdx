<Summary>

컴포넌트 단위 테스트를 충분히 고민하지 않았던 이유와, 면접을 계기로 라이브러리 테스트를 다시 읽은 경험을 적었어요. 피식의 무한 스크롤과 드롭다운을 검증하면서 놓친 상황을 찾아보고, 테스트를 어떻게 나눌지도 다시 생각해 봤어요.

</Summary>

![기존 카드 아래에서 다음 페이지를 기다리는 스피너와, 화면 하단 더보기 아이콘 위로 열린 드롭다운을 나란히 그린 도해](/images/covers/scroll-and-dropdown-states.avif)

실무에서는 단위 테스트로 주로 로직을 검증하고, 화면은 통합 테스트와 E2E로 확인해 왔어요. UI 컴포넌트는 Radix와 Base UI, shadcn/ui를 많이 사용했어요. 인기가 많고 다운로드 수도 높고, 보고된 이슈도 빨리 고쳐진다는 이유로 신뢰했어요. 정작 그 컴포넌트들이 어떤 테스트를 거치는지는 깊게 살펴보지 않았어요.

라이브러리 코드를 읽을 때도 구현과 타입 정의에 먼저 눈이 갔어요. 테스트 코드는 다양한 입력과 사용 예제가 있어서 기능의 사용법을 확인할 때 찾아봤고요. 그러다 면접에서 드롭다운 메뉴 설계에 관한 질문을 받았어요. 익숙하게 쓰던 UI인데 충분히 고민해 보지 않았다는 생각에 부끄러웠어요.

그 일을 계기로 실무에서 정했던 [테스트 파일 규칙](/ko/blog/테스트-코드를-도입하면서-세운-기준)도 돌아봤어요. 새 기능의 명세는 `*.spec.*`에 쓰고, 예상하지 못한 오류는 `*.test.*`에 재현해 다시 발생하지 않게 했어요. 제 테스트 설계 역량이 부족하니, 뒤늦게 발견한 문제라도 회귀 테스트로 보완하려고 정한 규칙이기도 했어요. 그런데 오류가 드러난 뒤 빈틈을 채우는 데 기대기보다, 처음 명세를 쓸 때 어떤 상황을 확인할지 더 고민했어야 했어요.

무한 스크롤과 드롭다운처럼 자주 쓰는 UI에도 놓치기 쉬운 상황이 많아요. 목록 끝에 새 카드가 붙는지만 검사하면 응답을 기다리는 동안 기존 목록이 잠깐 사라져도 통과할 수 있어요. 메뉴가 열리는지만 보면 화면 아래로 잘려 마지막 항목을 누르지 못하는 경우를 놓칠 수 있고요.

피식의 갤러리에는 게시물 24개를 불러온 뒤 스크롤을 내려 다음 페이지를 읽는 [E2E 테스트](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/gallery-pagination.spec.ts)가 있었어요. 여기에 응답이 늦거나 실패하는 상황, 스크롤한 위치에서 더보기 메뉴를 여는 상황을 추가했어요.

## 라이브러리 테스트를 답지로 봤어요

이번에는 TanStack Query와 Radix, Base UI의 테스트를 보면서 어떤 상태에서 시작하고, 무엇을 조작하며, 어떤 결과를 기대하는지 따라가 봤어요. 제가 떠올리지 못한 상황을 찾는 데 이 테스트들을 답지 삼았어요.

테스트에서는 라이브러리가 이슈를 해결해 온 맥락도 엿볼 수 있었어요. 어떤 입력이나 조작이 문제를 일으켰는지, 수정한 뒤에는 어떤 동작을 보장하려 했는지가 재현 코드와 기대값에 남아 있었어요.

TanStack Query의 [`useInfiniteQuery` 테스트](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx)는 렌더할 때마다 훅의 상태를 배열에 모아 두고, 첫 조회와 다음 페이지 조회가 어떤 순서로 상태를 바꾸는지 확인해요. 다음 페이지 요청이 실패해도 이미 받은 페이지가 남고 `isFetchNextPageError`가 켜지는지, `getNextPageParam`이 `undefined`를 돌려주면 `hasNextPage`가 `false`가 되는지도 따로 검사해요.

평소 사용하던 shadcn/ui도 살펴봤어요. 드롭다운을 Radix와 Base UI, React Aria 버전으로 제공하는데, [Base UI 버전](https://github.com/shadcn-ui/ui/blob/8ab27715521cbd4f87ae6886cd989cbb678f6de7/apps/v4/registry/bases/base/ui/dropdown-menu.tsx)에서는 Base UI의 컴포넌트를 조합해 스타일을 입혀요. 열고 닫기나 포커스 처리를 검증하는 코드는 기반 라이브러리인 Radix와 Base UI에서 찾아봤어요.

Radix의 [DropdownMenu 테스트](https://github.com/radix-ui/primitives/blob/fe02008f49834d7421427fe532e5b11f13c7bcac/packages/react/dropdown-menu/src/dropdown-menu.test.tsx)에는 메뉴를 여닫는 과정에서 놓치기 쉬운 동작이 담겨 있어요. 닫혀 있을 때 `aria-controls`가 사라진 요소를 가리키지 않는지, 창이 포커스를 잃으면 하위 메뉴도 닫히는지, 닫히는 메뉴 위로 포인터가 지나가도 항목이 포커스를 가져가지 않는지 확인해요.

피식의 더보기 메뉴에 사용하는 Base UI의 [메뉴 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/root/MenuRoot.test.tsx)에서는 테스트를 작게 나눈 방식이 눈에 들어왔어요. `describe`로 키보드 탐색과 포커스 관리 같은 주제를 묶고, 각 동작은 별도의 `it`으로 검사해요. Enter로 열면 첫 항목에 포커스가 가는지, 위쪽 화살표로 열면 마지막 항목에 가는지, 닫은 뒤에는 트리거로 돌아오는지를 따로 확인하는 식이에요. 그래서 앞의 조작이 실패해도 다른 동작의 테스트는 독립적으로 실행할 수 있어요.

팝업의 [전환 상태 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/popup/MenuPopupTransitionState.test.tsx)에서는 열기와 닫기, 닫히다가 다시 열기를 이어서 실행하며 상태를 기록해요. 앞선 전환이 다음 전환에 미치는 영향을 보려면 이 순서를 함께 확인해야 해요. 열림 상태를 외부에서 관리하는지, `keepMounted`를 사용하는지, 처음부터 열려 있는지, 포털을 어디에 붙이는지를 조합해 `it.each`로 반복하고요. 이 파일은 jsdom을 사용하는 환경에서는 건너뛰고 실제 브라우저에서 실행해요.

피식의 테스트도 이 구분을 기준으로 다시 살펴봤어요. 독립적으로 확인할 조작은 테스트를 나누고, 상태가 이어지는 과정은 함께 검사하도록 보완했어요. 아래에서는 그 과정과 아직 더 확인할 수 있는 부분을 함께 짚어 볼게요.

## 응답 시점을 제어해 상태 만들기

피식에서는 최신 게시물 목록과 게시물 카드, 더보기 메뉴를 테스트 전용 페이지에 띄워요. Playwright의 [`page.route`](https://playwright.dev/docs/mock)로 GraphQL 응답이 도착하는 시점을 제어하고, 목록 끝을 감지하는 `IntersectionObserver`와 다음 페이지를 붙이는 Apollo 캐시는 실제 구현을 사용해요.

기본 응답은 첫 페이지 24개와 마지막 페이지 2개예요. 요청마다 offset을 기록하면 첫 조회는 `0`, 추가 조회는 `24`로 남아요. 이 페이지의 첫 조회는 브라우저에서 시작해요. 서버가 미리 받은 콘텐츠를 HTML에 포함하는지는 [별도의 E2E](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/access-layout.spec.ts#L32)에서 확인해요.

응답을 보류하거나 실패시켜 다음 상황을 확인했어요.

| 시점 | 화면에서 확인한 것 | 요청에서 확인한 것 |
| --- | --- | --- |
| 첫 응답을 기다릴 때 | 카드가 나오기 전 스켈레톤이 보이고, 응답 뒤 첫 24개가 나타나요 | `offset: 0` 한 번 |
| 스크롤 중 추가 응답을 기다릴 때 | 기존 카드와 목록 아래 스피너가 함께 보여요 | 끝을 다시 지나도 `offset: 24` 한 번 |
| 마지막 응답 뒤 | 마지막 페이지를 24개로 채운 테스트에서 총 48개가 보여요 | 문서 끝을 지나도록 스크롤해도 `[0, 24]` |
| 첫 조회가 실패했을 때 | 오류와 다시 시도 버튼이 보이고, 다시 시도하면 첫 페이지가 나타나요 | `[0, 0]` |
| 추가 조회가 실패했을 때 | 보던 카드 대신 목록 영역에 오류가 표시되고, 다시 시도하면 첫 페이지부터 읽어요 | 복구한 뒤 다시 내리면 `[0, 24, 0, 24]` |

TanStack Query는 [각 테스트 전에 새 QueryClient를 만들고, 끝나면 캐시를 비워요](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx#L31-L46). 캐시를 공유하면 앞에서 받은 데이터 때문에 다음 테스트의 첫 로딩이 생략될 수 있어요. 피식의 Playwright 테스트도 테스트마다 새 페이지에서 앱과 Apollo 클라이언트를 시작해요. 응답을 제어할 Promise와 요청 기록도 매번 새로 만들어요.

첫 응답을 보류하면 스켈레톤을, 추가 응답을 보류하면 기존 카드 아래의 스피너를 확인할 수 있어요. 처음에는 추가 조회 중 목록 유지와 중복 요청 방지, 응답 뒤 카드 추가를 한 테스트에서 검사했어요. 지금은 목록이 유지되는 과정과 중복 요청을 막는 동작을 나눠 검사해요. 최초 로딩과 그동안 추가 요청을 막는 동작도 따로 확인하고요.

아래는 나눈 테스트를 줄인 예시예요. [`openGallery`](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/test/browser/gallery.fixture.ts)는 페이지를 열기 전에 응답 가로채기를 등록하고, 지정한 offset의 첫 응답을 Promise가 풀릴 때까지 보류해요.

```typescript
test('추가 조회 중에는 기존 목록을 유지하고 응답 뒤 새 카드를 붙인다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards } = await openGallery(page, {
    responses: { 24: response.promise },
  });
  const loading = feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(loading).toBeVisible();
    await expect(cards.first()).toHaveAccessibleName('테스트 사진 1');
    await expect(cards).toHaveCount(24);
  } finally {
    response.resolve('success');
  }

  await expect(cards).toHaveCount(26);
  await expect(cards.last()).toHaveAccessibleName('테스트 사진 26');
  await expect(loading).toBeHidden();
});
```

로딩 표시를 먼저 확인하고 응답을 풀어야, 요청이 끝난 화면만 보고 통과하는 일을 막을 수 있어요. 카드 수와 첫 카드의 이름, 스피너는 모두 추가 조회 중 목록이 유지되는지 확인하기 위한 단언이에요. 같은 동작을 설명하므로 한 테스트에 함께 둬도 괜찮아요.

중복 요청을 검사할 때도 추가 응답을 보류해요. 그 상태에서 목록 위로 올라갔다가 다시 끝까지 내려요. `expectNoGalleryRequest`는 갤러리 요청을 1초 동안 기다리며, 그동안 요청이 들어오지 않아야 통과하는 도우미예요.

```typescript
test('추가 조회가 끝나기 전 다시 내려도 같은 offset을 요청하지 않는다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards, offsets } = await openGallery(page, {
    responses: { 24: response.promise },
  });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(
      feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' }),
    ).toBeVisible();
    await cards.first().scrollIntoViewIfNeeded();

    const noRequest = expectNoGalleryRequest(page);
    await Promise.all([noRequest, scrollPastEnd(page)]);
    expect(offsets).toEqual([0, 24]);
  } finally {
    response.resolve('success');
  }
});
```

요청 감시는 두 번째 스크롤 전에 시작해요. 스크롤부터 하면 바로 나간 요청을 놓칠 수 있어요. `finally`에서는 테스트의 성공 여부와 관계없이 보류한 응답을 풀어요. 이렇게 두 테스트를 나누면 목록 유지에 문제가 생겨도 중복 요청을 막는 동작은 따로 확인할 수 있어요.

## 마지막 페이지까지 갔을 때

기본 데이터로는 카드 26개를 받은 뒤 조회가 멈췄어요. 그런데 다음 페이지를 서버의 `nextOffset` 대신 카드 수로 계산하도록 임시로 바꿔도 당시 테스트 네 개가 모두 통과했어요. 마지막 페이지가 2개뿐이어서 두 구현 모두 같은 지점에서 멈췄기 때문이에요.

그래서 마지막 페이지에도 카드 24개를 채우고 응답에 `nextOffset: null`을 넣은 테스트를 따로 만들었어요. 목록에 48개가 표시되면 [요청 감시](https://playwright.dev/docs/api/class-page#page-wait-for-request)를 먼저 시작한 뒤 문서 높이보다 더 큰 위치로 스크롤하고 휠을 한 번 더 움직여요. 1초 동안 새 조회가 없었고, 요청 목록은 `[0, 24]`였어요. 같은 데이터에서 카드 수로 계산한 코드는 `offset: 48`을 요청해 실패했어요.

이 테스트는 마지막 응답을 받은 뒤 다시 목록 끝으로 내려가 확인해요. 아직 로딩 중이거나 목록 중간에 있을 때 요청이 없다는 사실만으로는 조회가 끝났다고 볼 수 없어요. 브라우저 테스트에서 요청이 없음을 확인하는 범위는 이 1초 동안이에요. 서버가 알려 준 종료 조건을 따르는지는 훅 테스트에서도 따로 검사해요.

## 요청이 실패했을 때

첫 조회 실패와 추가 조회 실패는 따로 검사했어요. 어느 쪽이든 다시 시도하면 첫 페이지부터 받아서, 복구한 뒤의 카드 수만 보면 둘을 구분하기 어려워요. 먼저 어느 offset에서 실패했는지 확인하고, 다시 시도한 뒤에도 스크롤로 다음 페이지를 이어 읽을 수 있는지 봤어요.

추가 조회가 실패하면 이미 보던 카드 24개도 오류 화면으로 바뀌어요. 목록을 읽는 Apollo의 `QueryRef`가 `fetchMore` 실패와 함께 오류 상태가 되면서 목록을 감싼 오류 경계가 표시되기 때문이에요.

앞서 본 TanStack Query 테스트는 추가 조회에 실패해도 기존 페이지가 남는지 확인해요. 피식에서도 보던 목록을 남기려면 추가 조회 오류를 목록 전체의 실패와 구분하고, 목록 아래에서 다시 시도할 수 있게 바꿔야 해요. 라이브러리의 테스트를 참고하더라도 기대하는 결과는 제품의 동작에 맞춰 정해야 해요.

실패를 준비하는 과정도 달라요. 첫 조회 실패는 카드가 없는 상태에서 시작하고, 추가 조회 실패는 카드 24개를 먼저 받은 뒤 스크롤해요. 두 경우 모두 오류가 보이는지 확인한 다음 다시 시도해요. 실패한 조회가 복구되는 과정을 보는 것이므로 오류와 재시도는 한 테스트에 둬도 괜찮아요.

재시도마저 실패하는 상황은 별도의 테스트로 추가할 수 있어요. 두 번 연속 실패하는 응답을 준비해 오류 화면과 다시 시도 버튼이 유지되는지 확인하는 거예요.

## 새로고침과 추가 조회가 겹칠 때

브라우저 테스트로 화면을 확인한 뒤에는 훅이 조회 상태를 어떻게 바꾸는지도 살펴봤어요. TanStack Query의 테스트를 참고해 화면에 반영된 상태를 순서대로 모았어요. 추가 조회가 시작되면 기존 목록과 조회 중 상태가 함께 나타나고, 응답이 오면 새 페이지가 붙으면서 조회 중 상태가 끝나야 해요. 그 사이 목록 전체가 로딩 화면으로 바뀌는 순간이 있다면 기록에서 찾을 수 있어요.

새로고침과 추가 조회가 겹치는 상황을 검사하다가 버그를 찾았어요. 다음 페이지를 받는 도중 새로고침이 먼저 끝나면, 이후의 추가 조회 호출이 같은 offset을 다시 요청했고 페이지 도착 콜백도 두 번 실행됐어요. 최신 게시물 목록에서는 이 콜백으로 분석 이벤트를 보내기 때문에 이벤트도 중복될 수 있었어요.

당시 훅은 진행 중인 요청을 하나만 기억했어요. 새로고침이 끝나면 그 기록을 지웠고, 아직 다음 페이지 요청이 진행 중인데도 새 요청을 받을 수 있는 상태가 됐어요.

화면에서는 추가 조회 중 목록 끝 감시를 멈춰서 이 문제가 바로 드러나지 않았어요. 하지만 사진 수가 바뀔 때 자동으로 새로고침하는 콘테스트 피드에서는 두 요청이 겹칠 수 있어요. 처음에는 [진행 중인 요청을 모두 기록하도록 고쳤고](https://github.com/jingeon27/side-project/commit/4830f074859ade4126f7d0a93c7bad9148bc9e92), 이후에는 [Apollo ObservableQuery의 현재 조회 상태를 읽도록 바꿨어요](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/src/shared/api/infinite-query.hook.ts). 지금은 훅이 요청 기록을 따로 관리하지 않고, Apollo가 조회를 마쳤는지 확인해 다음 페이지 요청을 받아요.

훅 테스트에서는 Apollo의 `queryDeduplication`을 꺼요. 같은 요청을 여러 번 호출해도 Apollo가 하나로 합쳐 보내면 네트워크 기록만으로는 중복 호출을 놓칠 수 있어요. 요청한 offset과 페이지 도착 콜백의 실행 횟수를 함께 확인하는 이유예요. 실제 스크롤이 요청으로 이어지는지는 브라우저에서 확인하고, 이렇게 요청이 겹칠 때의 호출 제어는 훅에서 따로 검사해요.

## 같은 응답을 MSW로 만들기

지금까지는 `page.route`로 응답을 제어했어요. 같은 상황을 [MSW 3의 GraphQL 핸들러](https://mswjs.io/api/graphql/)로도 만들 수 있어요. 아래 예시는 카드 48개를 두 페이지로 나눠 반환해요. `offset: 0`에는 첫 24개와 `nextOffset: 24`를, `offset: 24`에는 나머지 24개와 `nextOffset: null`을 보내요. 특정 응답을 보류하거나 실패시키려면 해당 offset에 Promise를 넘겨요.

```typescript
import { graphql } from 'msw/graphql';
import { HttpResponse } from 'msw/http';

import { GalleryPostsDocument, type GalleryPostsQuery } from '@/shared/api/generated';

type TResponse = 'success' | 'error';

function galleryHandler(
  endpoint: string,
  posts: GalleryPostsQuery['galleryPostsPage']['items'],
  responses: Partial<Record<number, Promise<TResponse>>> = {},
) {
  const pageSize = 24;

  return graphql.link(endpoint).query(GalleryPostsDocument, async ({ variables: { offset, limit } }) => {
    if ((offset !== 0 && offset !== pageSize) || limit !== pageSize) {
      return HttpResponse.json({ errors: [{ message: 'Unexpected pagination variables' }] });
    }

    if ((await responses[offset]) === 'error') {
      return HttpResponse.json({ errors: [{ message: 'Gallery request failed' }] });
    }

    return HttpResponse.json({
      data: {
        galleryPostsPage: {
          __typename: 'GalleryPostPage',
          items: posts.slice(offset, offset + pageSize),
          nextOffset: offset === 0 ? pageSize : null,
        },
      },
    });
  });
}
```

`posts`에 서로 다른 카드 48개를 준비해요. 브라우저 테스트 페이지에서 [워커를 시작](https://mswjs.io/api/setup-worker/)한 뒤, 목록을 띄우기 전에 추가 응답을 보류하는 핸들러를 등록해요.

```typescript
import { setupWorker } from 'msw/browser';

const endpoint = new URL('/__test__/gallery', window.location.origin).href;
const worker = setupWorker(galleryHandler(endpoint, posts));
await worker.start();

const nextPage = Promise.withResolvers<'success'>();
worker.use(galleryHandler(endpoint, posts, { 24: nextPage.promise }));
```

스크롤해서 카드 24개와 스피너가 함께 보이면 `nextPage.resolve('success')`를 호출하고, 카드가 48개로 늘어나는지 확인해요. 첫 로딩을 검사할 때는 새 Promise를 `offset: 0`에 연결하고, 스켈레톤이 보인 뒤 응답을 풀어요.

요청을 실패시키려면 해당 offset의 응답을 `'error'`로 정해요. 아래는 추가 조회를 실패시키는 예시예요.

```typescript
worker.use(galleryHandler(endpoint, posts, { 24: Promise.resolve('error') }));
```

`24`를 `0`으로 바꾸면 첫 조회가 실패해요. 두 경우 모두 오류 화면을 확인한 뒤 [`worker.resetHandlers()`](https://mswjs.io/api/setup-worker/reset-handlers/)를 호출하면 처음 등록한 성공 핸들러가 복원돼요. 그 상태에서 다시 시도 버튼을 눌러 첫 페이지가 돌아오는지 확인할 수 있어요.

다음 테스트를 준비할 때는 핸들러와 클라이언트를 각각 정리해야 해요. `resetHandlers()`는 Apollo 캐시나 보류 중인 Promise까지 초기화하지 않아요. 컴포넌트를 언마운트하고 보류한 응답을 정리한 뒤, 다음 테스트에서는 새 Promise와 Apollo 클라이언트를 사용해요. 같은 테스트에서 다시 시도할 때는 기존 클라이언트를 유지해야 실패한 조회가 복구되는 과정을 볼 수 있고요.

위의 오류 핸들러는 교체하기 전까지 계속 실패해요. 따라서 오류 화면을 확인한 뒤 성공 핸들러를 복원하고, 그다음 다시 시도 버튼을 눌러야 해요.

MSW는 응답을 준비하는 방식을 바꿔 줘요. 기존 카드가 남는지, 스피너와 오류가 언제 나타나는지 확인하는 화면 검사는 그대로 필요해요.

## 스크롤한 위치에서 드롭다운 열기

드롭다운은 먼저 스크롤 위치에 따라 어디에 열리는지 확인했어요. 처음 화면에는 보이지 않는 여덟 번째 카드까지 내려가, 더보기 아이콘 아래의 여유 공간을 바꿔 봤어요. 공간이 300px이면 [메뉴가 아이콘 아래에 열리고](https://base-ui.com/react/components/menu), 20px이면 위로 열려 수정과 삭제 항목이 모두 보여요. 열기 전후의 `scrollY`를 비교해 메뉴를 여는 순간 목록이 움직이지 않는지도 확인했어요.

위로 열린 메뉴는 팝업 하단이 아이콘 상단보다 위에 있는지, 팝업 양쪽 끝이 화면 안에 들어오는지 좌표로 검사했어요. 메뉴 항목이 보이는지는 Playwright의 [뷰포트 단언](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport)으로 확인했고요.

이때 보이는 비율을 정확히 `1`로 두니 브라우저가 `0.99999988`을 반환하는 경우에 실패했어요. 위치를 잘못 잡은 문제가 아니라 작은 계산 오차였어요. 그래서 항목의 가시성에는 작은 오차를 허용하고, 메뉴가 열리는 방향은 좌표로 확인했어요.

두 위치를 검사하는 코드는 Base UI의 `it.each`처럼 남은 공간과 예상 방향을 데이터로 정리할 수 있어요. 이때 조합마다 별도의 테스트가 실행되도록 해야 한쪽이 실패해도 다른 쪽의 결과를 볼 수 있어요. 카드 준비와 스크롤 위치 맞추기는 도우미에 두고, 메뉴를 연 뒤의 좌표 비교는 각 테스트에 남겨 두면 무엇을 검증하는지 읽기 쉬워요.

## 메뉴를 연 뒤 어디를 누르는지 나누기

메뉴가 닫혔다는 결과만 보면 배경을 누른 것과 삭제 항목을 고른 것이 같아 보여요. 하지만 삭제를 고르면 확인 대화상자가 열려야 하고, 배경을 누르면 대화상자 없이 닫혀야 해요. 그래서 클릭하는 위치마다 테스트를 따로 뒀어요.

각 테스트에서는 같은 카드까지 스크롤한 뒤 메뉴를 열어요. 트리거와 메뉴에는 카드 이름을 포함한 `테스트 사진 8 더보기`라는 접근성 이름을 붙였어요. 이 이름으로 메뉴를 찾고 그 안에서 항목을 고르면, 어떤 카드의 메뉴를 조작하는지도 분명해져요.

| 누르는 곳 | 확인한 결과 |
| --- | --- |
| 메뉴 바깥 배경 | 메뉴가 닫히고 아이콘의 `aria-expanded`가 `false`로 바뀌어요. 확인 대화상자가 없고 목록 조회 기록도 그대로예요 |
| 삭제 메뉴 항목 | 메뉴가 닫히고 삭제 확인 대화상자가 열려요. 취소하면 대화상자가 사라지고 해당 게시물이 남아요 |
| 메뉴를 연 더보기 아이콘 | 같은 아이콘을 다시 누르면 닫혀요. 한 번 더 누르면 메뉴가 다시 열려요 |

여기서 기록하는 offset은 목록 조회에만 해당해요. 취소할 때 삭제 요청도 나가지 않는지 확인하려면 클릭 전에 삭제 mutation을 별도로 감시해야 해요. 삭제를 확정하는 테스트에서는 해당 게시물 id가 한 번만 전달되는지도 확인할 수 있어요. 카드가 화면에 남았다는 사실만으로 삭제 요청까지 없었다고 판단할 수는 없어요.

## 키보드 조작과 포커스 확인하기

키보드 조작도 Enter로 열기, 아래 화살표로 이동하기, Escape로 닫기를 각각의 테스트로 나눴어요. 테스트마다 새 페이지에서 메뉴를 준비하므로 한 조작이 실패해도 다른 조작의 결과를 확인할 수 있어요. 이 검사들은 Desktop Safari에서도 실행해요.

포커스와 함께 `aria-controls`도 확인해요. 닫힌 메뉴의 트리거에는 이 속성이 없고, 열리면 메뉴의 id를 가리켜요. 다시 닫았을 때 속성이 사라져야 이미 없어진 메뉴를 가리키지 않아요.

| 나눈 테스트 | 준비할 상태 | 확인할 결과 |
| --- | --- | --- |
| Enter로 열기 | 더보기 아이콘에 포커스 | 수정 항목에 포커스가 가요 |
| 아래 화살표로 이동 | 메뉴가 열리고 수정에 포커스 | 구분선을 건너 삭제로 가요 |
| Escape로 닫기 | 메뉴가 열리고 항목에 포커스 | 메뉴가 사라지고 더보기 아이콘으로 돌아와요 |
| 삭제 대화상자 취소 | 삭제를 골라 확인 대화상자가 열린 상태 | 게시물은 남고 더보기 아이콘으로 포커스가 돌아와요 |

Escape를 검사할 때도 메뉴를 열고 항목에 포커스가 있는 상태부터 준비해야 해요. 삭제 대화상자를 취소한 뒤 포커스가 돌아오는지 확인하려면 삭제를 선택하는 과정도 필요하고요. 이런 준비와 결과는 한 테스트에 두되, 메뉴의 위치나 다음 페이지 도착처럼 다른 조건은 별도로 검사하면 실패한 원인을 좁히기 쉬워요.

## 메뉴가 닫히는 동안의 입력 확인하기

메뉴는 닫히는 중에도 화면에 잠깐 남아 있을 수 있어요. 이때 포인터가 지나가거나 클릭해도 항목이 실행되지 않아야 해요. 전환이 끝난 뒤만 확인하면 이 짧은 구간을 놓칠 수 있어요.

Base UI의 팝업 전환 테스트에서는 종료 시점도 직접 제어해요. 전환을 10초로 늘려 중간 상태를 관찰할 시간을 확보하고, 필요한 검사가 끝나면 `getAnimations()`로 가져온 애니메이션에 `finish()`를 호출해요.

피식의 테스트도 종료 시점을 직접 제어하도록 바꿨어요. 닫힘 전환을 10초로 늘리고 Escape를 누른 뒤, `data-ending-style`과 실제 애니메이션이 나타났는지 확인해요. 이어서 `pause()`로 전환을 멈춰 두고 포인터를 움직여 삭제 항목을 눌러요. 애니메이션 시작 전에도 목록은 비어 있을 수 있으니 시작 여부부터 확인해야 해요.

입력을 검사하는 동안에는 메뉴가 DOM에 남아 있어야 하고, 항목이 강조되거나 삭제 확인 대화상자가 열려서는 안 돼요. 검사를 마치면 `finish()`로 전환을 끝내고 메뉴가 제거되는지 확인해요. 일부러 닫히는 메뉴가 포인터 입력을 받도록 바꾸면 이 테스트가 실패해요.

## 목록이 바뀔 때 열린 메뉴는 어떻게 될까

마지막으로 목록 갱신과 메뉴 조작이 [겹치는 상황](https://github.com/jingeon27/side-project/commit/49294bdff9abf8120bb67cfc06c6e61ef4d7188b)을 확인했어요. 다음 페이지가 붙어도 보던 카드의 위치와 `scrollY`가 유지되는지 먼저 봤어요. 마지막 카드의 메뉴를 연 상태에서도 새 페이지가 도착한 뒤 메뉴가 같은 좌표에 열려 있는지 확인했고요.

다음 페이지 요청이 실패하면 목록이 오류 화면으로 바뀌면서 열린 메뉴도 사라져요. 이때 메뉴가 걸어 둔 `body`의 스크롤 잠금이 풀리는지 확인했어요. 다시 시도하면 첫 페이지가 돌아와 목록을 다시 읽을 수 있어요.
