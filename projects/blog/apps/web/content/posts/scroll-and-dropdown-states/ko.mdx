<Summary>

컴포넌트 단위 테스트를 깊게 고민하지 않았던 이유와, 면접을 계기로 라이브러리 테스트를 다시 읽으며 놓친 경우를 찾아본 과정을 적었어요. 무한 스크롤의 로딩과 실패, 드롭다운의 위치와 포커스, 메뉴가 닫히는 동안의 입력을 피식에서 검증했어요.

</Summary>

![기존 카드 아래에서 다음 페이지를 기다리는 스피너와, 화면 하단 더보기 아이콘 위로 열린 드롭다운을 나란히 그린 도해](/images/covers/scroll-and-dropdown-states.avif)

실무에서는 단위 테스트를 주로 로직에 쓰고, 화면은 통합 테스트와 E2E로 확인해 왔어요. UI에는 Radix와 Base UI, shadcn/ui를 써 왔는데, 인기가 많고 다운로드 수도 높고 보고된 이슈가 빨리 고쳐진다는 점에서 신뢰했어요. 그 컴포넌트들이 어떤 테스트를 거치는지까지는 깊게 생각해 보지 않았어요.

라이브러리 코드를 읽을 때도 구현과 타입 정의를 주로 봤어요. 테스트에는 여러 입력과 사용 방식이 예제로 들어 있어서, 기능을 어떻게 쓰는지 확인할 때 찾아봤어요. 그러다 면접에서 드롭다운 메뉴 설계에 관한 질문을 받았어요. 익숙하게 쓰던 UI를 충분히 고민해 보지 않았다는 생각에 부끄러웠어요.

그 일을 계기로 실무에서 쓰던 테스트 파일 규칙도 다시 봤어요. 새 기능의 명세는 `*.spec.*`에 적고, 예상하지 못한 오류는 `*.test.*`에 재현해 막았어요. 제 테스트 설계 역량이 부족하다는 전제에서, 뒤늦게 찾은 문제라도 계속 재현해 보완하려고 정한 규칙이기도 했어요. 지금 돌아보면 오류가 드러난 뒤에야 빈틈을 채우는 방식에 기대고 있었어요. 처음 명세를 작성할 때 어떤 상황까지 검증할지 더 고민해야 했어요. [테스트 기준을 정리한 글](/ko/blog/테스트-코드를-도입하면서-세운-기준)

무한 스크롤과 드롭다운도 따져 보면 놓치기 쉬운 상황이 많아요. 목록 끝에 새 카드가 붙는 것만 확인하면, 응답을 기다리는 동안 기존 목록이 잠깐 사라져도 테스트는 통과할 수 있어요. 메뉴가 열렸다는 사실만 확인하면 화면 아래로 잘려서 마지막 항목을 누를 수 없는 경우를 놓쳐요.

피식의 갤러리에는 이미 첫 게시물 24개에서 스크롤을 내려 다음 페이지를 읽는 [E2E 테스트](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/gallery-pagination.spec.ts)가 있었어요. 여기에 응답이 늦거나 실패했을 때와, 페이지 아래쪽에서 게시물의 더보기 메뉴를 눌렀을 때를 더했어요.

## 라이브러리 테스트를 답지로 봤어요

이번에는 TanStack Query와 Radix, shadcn/ui, Base UI의 테스트를 열고, 어떤 상태에서 시작해 무엇을 조작하고 어디까지 확인하는지 따라가며 읽었어요. 제가 떠올리지 못한 경우를 찾는 데 이 테스트들을 답지 삼았어요.

테스트를 읽다 보니 라이브러리가 이슈를 해결해 온 맥락도 엿볼 수 있었어요. 어떤 입력이나 조작에서 문제가 생겼고 수정 후에는 무엇을 보장하려 했는지가 재현 코드와 단언에 남아 있었어요.

TanStack Query의 [`useInfiniteQuery` 테스트](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx)는 렌더할 때마다 훅의 상태를 배열에 모아 두고, 첫 조회와 다음 페이지 조회가 어떤 순서로 상태를 바꾸는지 확인해요. 다음 페이지 요청이 실패해도 이미 받은 페이지가 남고 `isFetchNextPageError`가 켜지는지, `getNextPageParam`이 `undefined`를 돌려주면 `hasNextPage`가 `false`가 되는지도 따로 검사해요.

shadcn/ui는 드롭다운 하나를 Radix와 Base UI, React Aria 버전으로 나눠, 각 컴포넌트 위에 스타일을 입혀 제공해요. [Base UI 버전](https://github.com/shadcn-ui/ui/blob/8ab27715521cbd4f87ae6886cd989cbb678f6de7/apps/v4/registry/bases/base/ui/dropdown-menu.tsx)처럼 열고 닫기와 포커스 같은 동작은 아래에 깔린 컴포넌트가 맡아서, 저장소에는 드롭다운의 동작 테스트가 따로 없어요. 그래서 동작을 어떻게 검증하는지는 Radix와 Base UI의 테스트에서 찾았어요.

Radix의 [DropdownMenu 테스트](https://github.com/radix-ui/primitives/blob/fe02008f49834d7421427fe532e5b11f13c7bcac/packages/react/dropdown-menu/src/dropdown-menu.test.tsx)는 메뉴가 열리고 닫히는 것보다 그 주변을 더 많이 봐요. 닫혀 있을 때 `aria-controls`가 없는 요소를 가리키지 않는지, 창이 포커스를 잃으면 하위 메뉴까지 닫히는지, 메뉴가 닫히는 동안 포인터가 지나가도 항목이 포커스를 가져가지 않는지 같은 경우를 따로 확인해요.

피식의 더보기 메뉴는 Base UI로 만들어서 Base UI의 [메뉴 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/root/MenuRoot.test.tsx)도 열어 봤어요. 눈에 들어온 건 테스트를 작게 나눈 방식이었어요. `describe`로 키보드 탐색과 포커스 관리 같은 주제를 묶고, 그 안에서는 Enter로 열 때 첫 항목에 포커스가 가는 경우, 위쪽 화살표로 열 때 마지막 항목에 가는 경우, 닫힌 뒤 트리거로 돌아오는 경우를 각각의 `it`으로 검사해요. 여러 조작을 한 번에 끝까지 해 보는 테스트만 있었다면 앞에서 실패한 조작 때문에 뒤의 동작은 확인하지 못했을 거예요.

팝업의 [전환 상태 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/popup/MenuPopupTransitionState.test.tsx)에서는 열기와 닫기, 닫히다가 다시 열기를 이어서 실행하며 상태를 기록해요. 여기서는 그 순서 자체가 검증 대상이에요. controlled 여부와 `keepMounted`, 처음부터 열린 상태인지, 포털을 어디에 붙이는지를 조합해 같은 검사를 `it.each`로 반복해요. 이 파일은 jsdom에서 건너뛰고 실제 브라우저에서 실행해요. 독립적인 조작은 작게 나누고, 앞 단계가 뒤 단계에 영향을 주는 전환은 필요한 순서를 한 테스트에서 따라가는 구성이었어요.

이 구성을 보고 피식의 테스트도 다시 살펴봤어요. 응답을 기다리는 동안과 실패한 뒤를 나누는 데서 더 나아가, 각 테스트가 어떤 동작 하나를 설명하는지도 봐야겠다고 생각했어요. 아래에는 지금 검증하는 내용과, 라이브러리 테스트를 참고해 더 나눌 수 있는 부분을 함께 적었어요.

## 응답 시점을 제어해 상태 만들기

상태별 테스트는 브라우저 테스트 페이지에서 실행해요. 이 페이지에 피식의 최신 게시물 목록과 게시물 카드, 더보기 메뉴를 띄우고, Playwright의 [`page.route`](https://playwright.dev/docs/mock)로 GraphQL 응답 시점을 제어해요. 목록 끝을 감지하는 `IntersectionObserver`와 다음 페이지를 붙이는 Apollo 캐시는 제품 코드를 그대로 써요. 기본 데이터는 첫 페이지 24개와 마지막 페이지 2개이고, 요청이 나갈 때마다 offset을 기록해서 첫 요청은 `offset: 0`, 추가 요청은 `offset: 24`로 남아요. 첫 조회는 서버가 아니라 브라우저에서 시작하기 때문에, 서버가 프리로드한 콘텐츠가 HTML에 포함되는지는 [별도의 E2E](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/access-layout.spec.ts#L32)에서 확인해요.

이렇게 만든 상태와 각 상태에서 확인한 내용은 다음과 같아요.

| 시점 | 화면에서 확인한 것 | 요청에서 확인한 것 |
| --- | --- | --- |
| 첫 응답을 기다릴 때 | 카드가 나오기 전 스켈레톤이 보이고, 응답 뒤 첫 24개가 나타나요 | `offset: 0` 한 번 |
| 스크롤 중 추가 응답을 기다릴 때 | 기존 카드와 목록 아래 스피너가 함께 보여요 | 끝을 다시 지나도 `offset: 24` 한 번 |
| 마지막 응답 뒤 | 마지막 페이지를 24개로 채운 테스트에서 총 48개가 보여요 | 문서 끝을 지나도록 스크롤해도 `[0, 24]` |
| 첫 조회가 실패했을 때 | 오류와 다시 시도 버튼이 보이고, 다시 시도하면 첫 페이지가 나타나요 | `[0, 0]` |
| 추가 조회가 실패했을 때 | 보던 카드 대신 목록 영역에 오류가 표시되고, 다시 시도하면 첫 페이지부터 읽어요 | 복구한 뒤 다시 내리면 `[0, 24, 0, 24]` |

TanStack Query는 [각 테스트 전에 새 QueryClient를 만들고, 끝나면 캐시를 비워요](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx#L31-L46). 앞 테스트에서 받은 데이터 때문에 다음 테스트의 첫 로딩이 생략되면, 시작 상태부터 달라지기 때문이에요. 피식의 Playwright 테스트는 테스트마다 새 페이지에서 앱과 Apollo 클라이언트를 만들고, 그 페이지에 응답 가로채기를 등록해요. 응답을 풀 Promise와 요청 기록도 테스트 안에서 새로 만들어요.

첫 조회를 멈춰 두면 카드가 나오기 전에 스켈레톤을 볼 수 있고, 추가 조회를 멈춰 두면 카드 24개 아래에 스피너가 붙어요. 현재 추가 조회 테스트에는 목록 유지와 중복 요청 방지, 응답 뒤 카드 추가가 함께 들어 있어요. Base UI의 구성을 참고하면 목록이 유지되는 과정과, 다시 스크롤했을 때 중복 요청을 막는 동작을 나눌 수 있어요. 아래는 기존 fixture를 사용해 나눈 작성 예시예요. [`openGallery`](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/test/browser/gallery.fixture.ts)는 페이지를 열기 전에 응답 가로채기를 등록하고, 지정한 offset의 첫 응답을 Promise가 풀릴 때까지 보류해요.

```typescript
test('추가 조회 중에는 기존 목록을 유지하고 응답 뒤 새 카드를 붙인다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards } = await openGallery(page, {
    responses: { 24: response.promise },
  });
  const loading = feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(loading).toBeVisible();
    await expect(cards.first()).toHaveAccessibleName('테스트 사진 1');
    await expect(cards).toHaveCount(24);
  } finally {
    response.resolve('success');
  }

  await expect(cards).toHaveCount(26);
  await expect(cards.last()).toHaveAccessibleName('테스트 사진 26');
  await expect(loading).toBeHidden();
});
```

로딩 표시가 나타난 것을 먼저 확인한 뒤 응답을 풀어요. 이렇게 해야 로딩을 거치지 않고 바로 끝난 화면을 보고도 통과하는 일을 막아요. 카드 수와 첫 카드의 이름, 스피너를 함께 확인하는 건 같은 동작을 설명하므로 한 테스트에 둬도 괜찮아요. 단언을 하나씩 쪼개는 것이 목적은 아니에요.

중복 요청은 별도의 테스트에서 같은 응답을 멈춘 채 목록 위로 갔다가 끝까지 다시 내려 확인할 수 있어요. `expectNoGalleryRequest`는 갤러리 요청을 1초 동안 기다리고, 그 시간이 지나도록 요청이 없어야 통과하는 기존 도우미예요.

```typescript
test('추가 조회가 끝나기 전 다시 내려도 같은 offset을 요청하지 않는다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards, offsets } = await openGallery(page, {
    responses: { 24: response.promise },
  });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(
      feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' }),
    ).toBeVisible();
    await cards.first().scrollIntoViewIfNeeded();

    const noRequest = expectNoGalleryRequest(page);
    await Promise.all([noRequest, scrollPastEnd(page)]);
    expect(offsets).toEqual([0, 24]);
  } finally {
    response.resolve('success');
  }
});
```

요청 감시는 두 번째 스크롤보다 먼저 시작해요. 스크롤한 뒤 감시를 걸면 바로 나간 요청을 놓칠 수 있어요. 테스트가 실패해도 `finally`에서 보류한 응답을 풀어 둬요. 두 테스트가 각각 새 페이지에서 시작하면, 목록 유지가 깨져도 중복 요청 방지는 따로 검사할 수 있어요.

## 마지막 페이지까지 갔을 때

기본 데이터에서는 26개를 받은 뒤 요청이 멈춰요. 그런데 다음 페이지를 서버의 `nextOffset` 대신 카드 수로 계산하도록 임시로 바꿔 봐도 기존 테스트 네 개가 모두 통과했어요. 마지막 페이지가 2개뿐이어서 두 구현이 같은 지점에서 멈췄기 때문이에요.

그래서 마지막 페이지에도 카드 24개를 채우고 응답에 `nextOffset: null`을 넣은 테스트를 따로 만들었어요. 목록에 48개가 표시되면 [요청 감시](https://playwright.dev/docs/api/class-page#page-wait-for-request)를 먼저 시작한 뒤 문서 높이보다 더 큰 위치로 스크롤하고 휠을 한 번 더 움직여요. 1초 동안 새 조회가 없었고, 요청 목록은 `[0, 24]`였어요. 같은 데이터에서 카드 수로 계산한 코드는 `offset: 48`을 요청해 실패했어요.

마지막 응답을 실제로 받은 뒤에도 다시 끝까지 내려 보았다는 점이 중요해요. 카드를 받기 전이나 목록 중간에서 요청이 없다는 사실만 확인하면, 더 읽을 수 없는 상태인지 판단할 수 없어요. 앞의 1초는 새 요청을 관찰한 범위예요. 서버가 준 종료 조건을 따르는지는 훅 테스트에서도 따로 확인해요.

## 요청이 실패했을 때

첫 페이지 실패와 추가 페이지 실패는 따로 만들었어요. 두 경우 모두 다시 시도하면 첫 페이지부터 새로 받아서, 복구한 뒤의 개수만 보면 두 오류를 구분하기 어려워요. 그래서 실패한 요청의 offset과, 다시 시도한 뒤 스크롤해서 다음 페이지를 이어 읽을 수 있는지까지 확인했어요.

추가 조회가 실패하면 이미 보던 카드 24개도 오류 화면으로 바뀌어요. 피식의 목록은 Apollo의 `QueryRef`로 읽는데, `fetchMore`가 실패하면 같은 `QueryRef`도 실패 상태가 되어 목록을 감싼 오류 경계로 넘어가기 때문이에요. TanStack Query는 다음 페이지가 실패해도 이미 받은 페이지를 남겨요. 피식에서 목록을 남기는 동작을 선택한다면, 추가 조회 오류를 목록 전체의 실패와 구분해 처리하고 목록 아래에서 다시 시도할 수 있게 바꿔야 해요. 라이브러리 테스트의 기대값도 제품이 정한 동작에 맞춰 가져와야 해요.

실패와 복구를 검사할 때는 오류가 먼저 보였는지 확인한 뒤 다시 시도해요. 첫 조회 실패에서는 카드가 없는 상태로 시작하고, 추가 조회 실패에서는 먼저 카드 24개를 받은 뒤 스크롤해요. 오류와 재시도를 한 테스트에 두는 것은 실패한 그 조회를 복구할 수 있는지 확인하기 위해서예요. 여기에 재시도마저 실패하는 경우를 더한다면, 별도 테스트에서 두 번 연속 실패하도록 응답을 준비하고 오류와 다시 시도 버튼이 남는지 확인할 수 있어요.

## 같은 응답을 MSW로 만들기

피식의 테스트는 `page.route`로 응답을 제어하지만, 같은 응답을 [MSW 3의 GraphQL 핸들러](https://mswjs.io/api/graphql/)로도 만들 수 있어요. `GalleryPosts`에서 `offset: 0`은 첫 카드 24개와 `nextOffset: 24`를, `offset: 24`는 나머지 24개와 `nextOffset: null`을 반환해요. 응답을 보류하거나 실패시킬 때는 해당 offset에 Promise를 넣어요.

```typescript
import { graphql } from 'msw/graphql';
import { HttpResponse } from 'msw/http';

import { GalleryPostsDocument, type GalleryPostsQuery } from '@/shared/api/generated';

type TResponse = 'success' | 'error';

function galleryHandler(
  endpoint: string,
  posts: GalleryPostsQuery['galleryPostsPage']['items'],
  responses: Partial<Record<number, Promise<TResponse>>> = {},
) {
  const pageSize = 24;

  return graphql.link(endpoint).query(GalleryPostsDocument, async ({ variables: { offset, limit } }) => {
    if ((offset !== 0 && offset !== pageSize) || limit !== pageSize) {
      return HttpResponse.json({ errors: [{ message: 'Unexpected pagination variables' }] });
    }

    if ((await responses[offset]) === 'error') {
      return HttpResponse.json({ errors: [{ message: 'Gallery request failed' }] });
    }

    return HttpResponse.json({
      data: {
        galleryPostsPage: {
          __typename: 'GalleryPostPage',
          items: posts.slice(offset, offset + pageSize),
          nextOffset: offset === 0 ? pageSize : null,
        },
      },
    });
  });
}
```

`posts`에 서로 다른 카드 48개를 준비해요. 브라우저 테스트 페이지에서 [워커를 시작](https://mswjs.io/api/setup-worker/)한 뒤, 목록을 띄우기 전에 추가 응답을 보류하는 핸들러를 등록해요.

```typescript
import { setupWorker } from 'msw/browser';

const endpoint = new URL('/__test__/gallery', window.location.origin).href;
const worker = setupWorker(galleryHandler(endpoint, posts));
await worker.start();

const nextPage = Promise.withResolvers<'success'>();
worker.use(galleryHandler(endpoint, posts, { 24: nextPage.promise }));
```

스크롤해서 카드 24개와 스피너가 함께 보이면 `nextPage.resolve('success')`를 호출하고, 카드가 48개로 늘어나는지 확인해요. 첫 로딩을 검사할 때는 새 Promise를 `offset: 0`에 연결하고, 스켈레톤이 보인 뒤 응답을 풀어요.

요청을 실패시키려면 해당 offset의 응답을 `'error'`로 정해요. 아래는 추가 조회를 실패시키는 예시예요.

```typescript
worker.use(galleryHandler(endpoint, posts, { 24: Promise.resolve('error') }));
```

`24`를 `0`으로 바꾸면 첫 조회가 실패해요. 두 경우 모두 오류 화면을 확인한 뒤 [`worker.resetHandlers()`](https://mswjs.io/api/setup-worker/reset-handlers/)를 호출하면 처음 등록한 성공 핸들러가 복원돼요. 그 상태에서 다시 시도 버튼을 눌러 첫 페이지가 돌아오는지 확인할 수 있어요.

다른 테스트를 시작할 때는 핸들러만 되돌려서는 부족해요. `resetHandlers()`는 Apollo 캐시나 보류 중인 Promise를 초기화하지 않아요. 컴포넌트를 언마운트하고 보류한 응답을 정리한 뒤, 다음 테스트에는 새 Promise와 새 Apollo 클라이언트를 준비해야 해요. 같은 테스트 안에서 재시도할 때는 기존 클라이언트를 유지해 실제 복구 과정을 확인하고요. 위 핸들러의 오류 응답은 교체하기 전까지 계속 실패하므로, 재시도 전에 성공 핸들러로 되돌리는 순서도 필요해요.

MSW가 응답했다고 해서 스피너나 오류 화면이 올바르다는 뜻은 아니에요. 응답을 만드는 부분만 바꾸고, 기존 카드가 남는지와 오류가 나타나는지 같은 화면 검사는 그대로 유지해요.

## 스크롤한 위치에서 드롭다운 열기

게시물 목록에서 처음 화면에는 보이지 않는 여덟 번째 카드까지 내려가요. 더보기 아이콘을 화면 안에 둔 뒤, 아이콘 아래에 남는 공간을 두 가지로 나눠 [메뉴가 열리는 위치](https://base-ui.com/react/components/menu)를 비교했어요. 300px을 남기면 메뉴가 누른 아이콘 아래에 붙어요. 20px만 남기면 메뉴가 아이콘 위로 올라와서 수정과 삭제를 모두 볼 수 있어요. 열기 전후의 `scrollY`도 비교해서 메뉴를 열자마자 목록이 움직이지 않는지 확인했어요.

위로 열린 경우에는 팝업 하단 좌표가 아이콘 상단보다 작은지, 팝업의 왼쪽과 오른쪽이 뷰포트 안에 있는지 검사했어요. Playwright의 [뷰포트 단언](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport)에서 요소 전체가 보이는 비율을 정확히 `1`로 두니, 브라우저 계산 결과가 `0.99999988`일 때 실패했어요. 그래서 메뉴 항목이 화면에 들어오는지는 작은 오차를 허용하고, 팝업이 어디에 열렸는지는 좌표로 확인했어요.

Base UI가 같은 검사를 옵션 조합마다 반복하는 것처럼, 두 위치도 남은 공간과 예상 방향을 데이터로 두고 각각의 테스트로 만들 수 있어요. 다만 두 위치를 한 테스트 안에서 연달아 열면 앞에서 실패한 순간 뒤의 검사는 실행되지 않아요. 위치 계산과 스크롤, 포커스는 실제 브라우저에서 확인하고, 카드 준비와 위치 맞추기만 도우미가 맡도록 두면 각 테스트에서 무엇을 비교하는지 읽기 쉬워요.

## 메뉴를 연 뒤 어디를 누르는지 나누기

메뉴가 닫혔는지만 검사하면 배경 클릭과 삭제 항목 클릭을 같은 결과로 볼 수 있어요. 삭제 항목을 고른 경우에는 확인 대화상자가 열려야 하고, 배경을 누른 경우에는 그 대화상자가 없어야 해요. 그래서 누르는 곳마다 테스트를 따로 뒀어요.

각 테스트는 스크롤한 카드에서 메뉴를 연 상태로 시작해요. 카드 이름을 포함한 `테스트 사진 8 더보기`를 트리거와 메뉴의 접근성 이름으로 사용해요. 열린 메뉴를 그 이름으로 찾은 뒤 그 안에서 항목을 고르면, 스크롤한 목록에서 어느 카드의 메뉴를 눌렀는지도 확인할 수 있어요.

| 누르는 곳 | 확인한 결과 |
| --- | --- |
| 메뉴 바깥 배경 | 메뉴가 닫히고 아이콘의 `aria-expanded`가 `false`로 바뀌어요. 확인 대화상자가 없고 목록 조회 기록도 그대로예요 |
| 삭제 메뉴 항목 | 메뉴가 닫히고 삭제 확인 대화상자가 열려요. 취소하면 대화상자가 사라지고 해당 게시물이 남아요 |
| 메뉴를 연 더보기 아이콘 | 같은 아이콘을 다시 누르면 닫혀요. 한 번 더 누르면 메뉴가 다시 열려요 |

여기서 기록하는 offset은 목록 조회에만 해당해요. 취소할 때 삭제 요청까지 나가지 않는지 검사하려면, 클릭하기 전부터 삭제 mutation을 별도로 감시해야 해요. 확인 버튼을 누르는 테스트에서는 해당 게시물 id가 한 번 전달되는지도 볼 수 있고요. 대화상자가 닫히거나 카드가 남았다는 화면만으로 서버에 보낸 요청까지 판단할 수는 없어요.

키보드 테스트는 더 나눌 여지가 있어요. 현재는 Enter로 열기, 화살표 이동, Escape로 닫기를 하나의 테스트에서 이어서 해요. 키보드 검사는 Desktop Safari에서도 실행해요. Base UI의 포커스 테스트를 참고하면 아래처럼 각 조작이 보장할 결과를 나눌 수 있어요. 단, Escape를 검사할 때도 메뉴를 열고 항목에 포커스가 있는 상태까지는 먼저 만들어야 해요.

| 별도로 둘 테스트 | 준비할 상태 | 확인할 결과 |
| --- | --- | --- |
| Enter로 열기 | 더보기 아이콘에 포커스 | 수정 항목에 포커스가 가요 |
| 아래 화살표로 이동 | 메뉴가 열리고 수정에 포커스 | 구분선을 건너 삭제로 가요 |
| Escape로 닫기 | 메뉴가 열리고 항목에 포커스 | 메뉴가 사라지고 더보기 아이콘으로 돌아와요 |
| 삭제 대화상자 취소 | 삭제를 골라 확인 대화상자가 열린 상태 | 게시물은 남고 더보기 아이콘으로 포커스가 돌아와요 |

삭제 항목 선택과 취소 후 복귀는 서로 이어지는 흐름이라 한 테스트에 둘 수 있어요. 대신 메뉴 위치나 추가 페이지 도착까지 그 테스트에 함께 넣지는 않아요. 실패한 테스트의 이름을 보고 어떤 동작이 깨졌는지 좁힐 수 있는 크기가 좋겠어요.

## 답지를 보고 더한 테스트

무한 스크롤 훅 테스트에서는 TanStack Query의 조회 상태 테스트를 참고해 화면에 반영된 상태를 순서대로 모았어요. 다음 페이지를 요청하면 기존 목록을 그대로 둔 채 조회 중 상태가 되고, 응답이 오면 새 페이지가 붙으면서 조회 중 상태가 끝나야 해요. 그 사이에 목록이 로딩 화면으로 바뀌는 단계가 끼면 기록에서 바로 드러나요. 이렇게 순서가 중요한 검사는 중간 상태를 이어서 기록하는 편이 맞아요.

새로고침과 겹치는 경우도 같은 방식으로 기록해 보니 버그가 나왔어요. 다음 페이지를 받는 중에 새로고침이 먼저 끝나면, 그 뒤에 부른 다음 페이지 조회가 같은 offset으로 한 번 더 시작됐고 페이지 도착 콜백도 두 번 불렸어요. 최신 게시물 목록에서는 이 콜백이 분석 이벤트를 보내요. 이런 일이 생긴 건 훅이 진행 중인 요청을 하나만 기억해서, 새로고침이 끝나면서 아직 진행 중인 다음 페이지 요청의 기록까지 지웠기 때문이에요.

화면에서는 조회 중에 목록 끝 감시를 멈추기 때문에 바로 드러나지 않았어요. 하지만 콘테스트 피드처럼 사진 수가 바뀌면 자동으로 새로고침하는 목록에서는 두 요청이 겹칠 수 있어요. 처음에는 [진행 중인 요청을 모두 기록하는 방식으로 고쳤고](https://github.com/jingeon27/side-project/commit/4830f074859ade4126f7d0a93c7bad9148bc9e92), 이후에는 [Apollo ObservableQuery의 현재 조회 상태를 확인하도록 바꿨어요](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/src/shared/api/infinite-query.hook.ts). 진행 중인 요청을 훅에서 따로 관리하지 않고, Apollo가 조회를 마쳤을 때만 다음 페이지를 요청해요.

훅 테스트에서는 Apollo의 `queryDeduplication`도 꺼요. 네트워크 요청이 하나였더라도 Apollo가 중복 호출을 합친 결과일 수 있기 때문이에요. 요청한 offset과 페이지 도착 콜백 횟수를 함께 확인해야 분석 이벤트까지 중복되는 일을 잡을 수 있어요. 이런 호출 제어는 훅에서 확인하고, 실제 스크롤이 요청을 일으키는지는 브라우저 테스트에서 확인해요.

메뉴 테스트에는 `aria-controls` 검사도 더했어요. 닫혀 있을 때는 더보기 아이콘에 이 속성이 없고, 열렸을 때만 메뉴의 id를 가리켜요. 다시 닫으면 속성이 없어지는 것까지 확인해, 이미 사라진 메뉴를 가리키지 않게 해요.

메뉴가 닫히는 동안의 입력은 Base UI처럼 전환 시간을 늘려서 확인했어요. 메뉴의 전환을 2초로 늘리고 Escape를 누른 뒤, 메뉴가 닫히는 동안 삭제 항목 위로 포인터를 옮겨 눌러요. 항목은 강조되지 않고 확인 대화상자도 열리지 않아요. 일부러 닫히는 메뉴가 포인터 입력을 받도록 바꿔 보니 이 테스트가 실패했어요.

이 방법도 Base UI에서 더 참고할 부분이 있어요. 팝업 전환 테스트는 전환을 10초로 늘려 중간 상태를 놓치지 않게 만들고, 필요한 검사가 끝나면 `getAnimations()`로 가져온 애니메이션에 `finish()`를 호출해요. 10초가 지나기를 기다리는 대신 테스트가 전환의 끝을 정하는 거예요. 피식의 테스트도 이렇게 바꾼다면 닫히는 전환이 실제로 시작됐는지 확인하고, 그동안 포인터 입력이 무시되는지 검사한 뒤 전환을 끝내 메뉴가 제거되는지 볼 수 있어요. 전환이 시작되기도 전에 애니메이션 목록이 비었다고 끝난 것으로 판단하지 않는 순서가 필요해요.

무한 스크롤과 메뉴가 [겹치는 경우](https://github.com/jingeon27/side-project/commit/49294bdff9abf8120bb67cfc06c6e61ef4d7188b)도 따로 확인했어요. 마지막 카드의 메뉴를 연 채로 다음 페이지가 도착하면 메뉴가 같은 좌표에 그대로 열려 있어요. 다음 페이지 요청이 실패하면 목록이 오류 화면으로 바뀌면서 메뉴가 사라지고, 메뉴가 걸어 둔 `body`의 스크롤 잠금도 풀려요. 다시 시도하면 첫 페이지가 돌아와요. 메뉴 없이 다음 페이지가 붙을 때도 보던 카드의 위치와 `scrollY`가 그대로인지 확인했어요.
