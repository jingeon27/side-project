![카드 아래에 뜬 로딩 스피너와 화면 하단의 더보기 아이콘 위로 열린 메뉴](/images/covers/scroll-and-dropdown-states.avif)

실무에서는 주로 로직을 단위 테스트로 검증하고, 화면은 통합 테스트와 E2E로 확인했어요. UI를 만들 때는 Radix, Base UI, shadcn/ui를 믿고 썼어요. 다운로드 수가 많고 이슈도 빨리 고쳐졌거든요.

라이브러리 코드를 열면 구현과 타입 정의부터 봤어요. 테스트는 사용 예제가 필요할 때 찾아봤고요.

새 기능의 명세는 `*.spec.*`에 쓰고, 뒤늦게 발견한 버그는 `*.test.*`에 재현한다는 [규칙을 뒀어요](/ko/blog/테스트-코드를-도입하면서-세운-기준). 제가 명세에서 놓친 경우라도 테스트로 남기고 싶었거든요. 돌이켜 보면 버그를 찾은 뒤 테스트를 보태는 데 많이 기대고 있었어요.

피식 갤러리의 [E2E 테스트](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/gallery-pagination.spec.ts)는 게시물 24개를 불러온 뒤 스크롤하면 다음 페이지가 붙는지 봤어요. 새 카드가 붙은 뒤에만 개수를 세면, 응답을 기다리는 동안 목록이 사라져도 테스트는 통과해요. 드롭다운도 마찬가지예요. 메뉴가 열려도 마지막 항목이 화면 밖에 잘리면 누를 수 없어요.

## 라이브러리 테스트를 답지로 봤어요

TanStack Query, Radix, Base UI가 어떤 동작을 따로 검사하고 어떤 동작을 한 테스트에 묶었는지 봤어요.

### TanStack Query: 기능마다 상태가 바뀌는 순서를 기록해요

1,839줄짜리 [`useInfiniteQuery` 테스트 파일](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx)에는 테스트가 28개 있어요. 첫 조회와 이전 페이지, 다음 페이지 조회를 나눠요. `select`, `placeholderData`, `initialData` 같은 옵션과 `hasNextPage`가 달라지는 조건, 요청이 겹칠 때의 취소도 따로 검사해요.

여러 테스트가 렌더할 때마다 훅의 상태를 배열에 넣고 순서까지 비교해요. 그래야 목록이 잠깐 비었다가 돌아와도 알 수 있어요. 다음 페이지 요청이 실패하면 이미 받은 페이지가 남고 `isFetchNextPageError`가 `true`인지 봐요. 전체를 다시 조회하다 실패하는 경우는 따로 다뤄요. 앞 테스트의 캐시 때문에 첫 로딩을 건너뛰지 않도록 [매번 새 QueryClient를 만들고 끝나면 캐시를 비워요](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx#L31-L46).

피식의 무한 스크롤 훅에서도 렌더할 때마다 목록과 로딩 상태를 기록했어요. 마지막 페이지에서 요청을 멈추는지는 따로 검사했고요.

### Radix: 문제별 회귀 테스트와 부품별 계약 테스트, 조작 흐름은 E2E로 나눠요

평소 쓰던 shadcn/ui에는 Radix, Base UI, React Aria로 만든 드롭다운이 있어요. [Base UI 버전](https://github.com/shadcn-ui/ui/blob/8ab27715521cbd4f87ae6886cd989cbb678f6de7/apps/v4/registry/bases/base/ui/dropdown-menu.tsx)을 열어 보니 Base UI 컴포넌트를 조합하고 스타일을 입히는 코드였어요. 메뉴를 열고 닫을 때 포커스가 어디로 가는지는 Radix와 Base UI의 테스트에서 찾아봤어요.

Radix의 [DropdownMenu 단위 테스트](https://github.com/radix-ui/primitives/blob/fe02008f49834d7421427fe532e5b11f13c7bcac/packages/react/dropdown-menu/src/dropdown-menu.test.tsx)는 1,286줄이에요. 앞부분은 버그마다 `describe`로 묶고, 나머지 약 1,000줄은 Trigger부터 SubContent까지 열세 컴포넌트에 같은 계약 테스트를 적용해요. 각 컴포넌트가 직접 쓰지 않는 props를 렌더한 요소에 넘기는지, `asChild`를 쓰면 자식 요소에 넘기는지 봐요.

테스트가 들어간 커밋을 따라가니 처음 올라온 버그 리포트도 읽을 수 있었어요. 2024년에는 [버튼의 `aria-controls`가 닫힌 메뉴를 가리키는 문제](https://github.com/radix-ui/primitives/issues/3013)와 [다른 탭에 다녀와도 하위 메뉴가 열려 있는 문제](https://github.com/radix-ui/primitives/issues/3257)가 보고됐어요. 2026년 6월에 [메뉴를 닫으면 속성을 지우고](https://github.com/radix-ui/primitives/pull/3922) [창이 포커스를 잃으면 메뉴를 닫도록](https://github.com/radix-ui/primitives/pull/3938) 고치면서 회귀 테스트가 들어갔어요. [닫히는 메뉴에 포인터를 올렸을 때 생긴 문제](https://github.com/radix-ui/primitives/issues/1266)는 2022년 3월에 보고돼 [2026년 10월에 고쳐졌어요](https://github.com/radix-ui/primitives/pull/4196).

[ref 안정성](https://github.com/radix-ui/primitives/pull/3968)과 [메뉴 안 입력 요소의 Space, Enter 처리](https://github.com/radix-ui/primitives/pull/3999)도 각각 수정한 PR에서 회귀 테스트를 추가했어요. 컴포넌트별 계약 테스트는 2026년 7월에 한꺼번에 들어갔고요.

[Playwright E2E](https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/e2e/dropdown-menu.spec.ts)에서는 Storybook을 열고 하위 메뉴를 포인터와 키보드로 각각 조작해요. 좁은 화면, 오른쪽에서 왼쪽으로 쓰는 RTL 레이아웃, Dialog 안의 메뉴도 따로 검사해요.

피식에서는 메뉴를 닫으면 더보기 버튼에서 `aria-controls`가 사라지는지, 닫히는 도중에 포인터를 올려도 항목이 반응하지 않는지 검사했어요. 하위 메뉴는 피식에 없고, props 전달은 라이브러리에서 이미 검사하고 있어요.

### Base UI: 상호작용과 prop별로 묶고, 브라우저가 필요한 테스트를 표시해요

Base UI의 [메뉴 테스트 파일](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/root/MenuRoot.test.tsx)은 4,899줄이지만 개별 테스트는 작아요. 메뉴 열기, 키보드 탐색, 포커스 관리 같은 상호작용과 `modal`, `openOnHover`, `disabled` 같은 prop을 `describe`로 묶어요. 키보드 탐색 안에서도 화살표로 한 칸 이동하는 동작과 Home, End로 처음이나 끝에 가는 동작을 별도의 `it`에서 검사해요.

jsdom과 브라우저 양쪽에서 실행하되, 스크롤 잠금이나 마우스 조작처럼 브라우저가 필요한 묶음에는 `describe.skipIf(isJSDOM)`을 붙여요. 팝업의 [전환 상태 테스트](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/popup/MenuPopupTransitionState.test.tsx)에서는 메뉴를 열고 닫다가 다시 여는 순서가 중요해요. 이 과정은 한 테스트에 두고, 전환을 10초로 늘려 중간 상태를 봐요. 검사가 끝나면 `getAnimations()`로 애니메이션을 찾아 `finish()`로 끝내고요.

피식에서도 메뉴 열기와 키보드 이동은 따로 검사했어요. 닫히던 메뉴가 클릭에 반응하는지 볼 때는 애니메이션을 멈추고 클릭하는 과정을 한 테스트에 뒀고요.

## 무한 스크롤 테스트

피식 갤러리는 게시물을 24개씩 불러와요. 목록 끝이 보이면 서버가 준 `nextOffset`으로 다음 페이지를 요청해 목록 뒤에 붙여요. `nextOffset`이 `null`이면 마지막 페이지예요.

### 응답 시점을 제어해 상태 만들기

테스트 페이지에는 피식의 최신 게시물 목록과 카드, 더보기 메뉴를 띄워요. 목록 끝을 감지하는 `IntersectionObserver`와 다음 페이지를 붙이는 Apollo 캐시는 그대로 써요. GraphQL 응답은 Playwright의 [`page.route`](https://playwright.dev/docs/mock)로 늦추거나 실패시켜요.

첫 페이지에는 카드 24개, 마지막 페이지에는 기본 2개를 준비하고 요청마다 offset을 기록해요. 첫 조회도 브라우저에서 시작해요. 서버가 미리 불러온 게시물이 HTML에 들어 있는지는 [별도의 E2E 테스트](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/access-layout.spec.ts#L32)에서 확인해요.

| 시점 | 화면에서 확인한 것 | 요청에서 확인한 것 |
| --- | --- | --- |
| 첫 응답을 기다릴 때 | 카드가 나오기 전 스켈레톤이 보이고, 응답 뒤 첫 24개가 나타나요 | `offset: 0` 한 번 |
| 스크롤 중 추가 응답을 기다릴 때 | 기존 카드와 목록 아래 스피너가 함께 보여요 | 끝을 다시 지나도 `offset: 24` 한 번 |
| 마지막 응답 뒤 | 마지막 페이지를 24개로 채운 테스트에서 총 48개가 보여요 | 문서 끝을 지나도록 스크롤해도 `[0, 24]` |
| 첫 조회가 실패했을 때 | 오류와 다시 시도 버튼이 보이고, 다시 시도하면 첫 페이지가 나타나요 | `[0, 0]` |
| 추가 조회가 실패했을 때 | 보던 카드 대신 목록 영역에 오류가 표시되고, 다시 시도하면 첫 페이지부터 읽어요 | 복구한 뒤 다시 내리면 `[0, 24, 0, 24]` |

테스트마다 새 페이지와 Apollo 클라이언트를 쓰고, 응답을 보류할 Promise와 요청 기록도 새로 만들어요. [`openGallery`](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/test/browser/gallery.fixture.ts)는 페이지를 열기 전에 핸들러를 등록해요. 지정한 offset의 첫 요청은 Promise가 풀릴 때까지 기다려요.

처음에는 로딩 중에 목록이 유지되는지와 같은 페이지를 두 번 요청하는지를 한 테스트에서 검사했어요. 지금은 둘을 나눠요. 첫 번째 테스트는 응답을 기다릴 때 첫 카드가 그대로 보이고, 응답 뒤에는 새 카드가 붙는지 봐요.

```typescript
test('추가 조회 중에는 기존 목록을 유지하고 응답 뒤 새 카드를 붙인다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards } = await openGallery(page, {
    responses: { 24: response.promise },
  });
  const loading = feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(loading).toBeVisible();
    await expect(cards.first()).toHaveAccessibleName('테스트 사진 1');
    await expect(cards).toHaveCount(24);
  } finally {
    response.resolve('success');
  }

  await expect(cards).toHaveCount(26);
  await expect(cards.last()).toHaveAccessibleName('테스트 사진 26');
  await expect(loading).toBeHidden();
});
```

중복 요청 테스트에서는 응답을 보류한 채 첫 카드까지 올라갔다가 다시 끝까지 내려요.

```typescript
test('추가 조회가 끝나기 전 다시 내려도 같은 offset을 요청하지 않는다', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards, offsets } = await openGallery(page, {
    responses: { 24: response.promise },
  });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(
      feed.getByRole('status').filter({ hasText: '게시물을 더 불러오는 중' }),
    ).toBeVisible();
    await cards.first().scrollIntoViewIfNeeded();

    const noRequest = expectNoGalleryRequest(page);
    await Promise.all([noRequest, scrollPastEnd(page)]);
    expect(offsets).toEqual([0, 24]);
  } finally {
    response.resolve('success');
  }
});
```

두 번째 스크롤 직전에 `expectNoGalleryRequest`를 호출해 1초 동안 요청을 감시해요. 스크롤부터 하면 그 순간 나간 요청을 놓칠 수 있거든요. 검사가 실패해도 보류한 응답은 `finally`에서 보내요. 첫 조회에서도 스켈레톤이 뜨는지와 그때 스크롤해도 요청이 한 번뿐인지는 따로 검사해요.

### 마지막 페이지까지 갔을 때

다음 페이지가 있는지 카드 수로 판단하도록 코드를 잠깐 바꿨는데, 기존 테스트 네 개가 모두 통과했어요. 마지막 페이지에 카드가 2개뿐이라 카드 수를 보든 서버의 `nextOffset`을 보든 26개에서 멈췄거든요.

마지막 페이지도 24개로 채우고 `nextOffset: null`을 보냈어요. 48개가 뜬 뒤 [요청 감시](https://playwright.dev/docs/api/class-page#page-wait-for-request)를 걸고 문서 높이보다 큰 값으로 스크롤한 다음 휠을 한 번 더 굴렸어요. 1초 동안 새 요청은 없었고 offset 기록은 `[0, 24]`였어요. 카드 수로 판단하는 코드는 이때 `offset: 48`을 요청해서 실패했어요.

마지막 응답이 오기 전에 스크롤하면 로딩 때문에 새 요청이 막혀도 통과해요. 훅 테스트에서도 응답을 받은 뒤 `nextOffset`이 `null`이면 요청을 멈추는지 검사해요.

### 요청이 실패했을 때

첫 조회는 카드가 없는 상태에서 `offset: 0`에 오류를 돌려줬어요. 오류 화면에서 ‘다시 시도’를 누르면 첫 24개가 돌아와요. 추가 조회는 카드 24개를 띄운 뒤 스크롤해 `offset: 24`에서 실패시켰어요. 이 경우에는 재시도로 첫 페이지를 되찾은 뒤, 다시 스크롤해 다음 페이지까지 읽었어요.

TanStack Query는 추가 조회에 실패해도 기존 페이지가 남아요. 피식에서는 `fetchMore`가 실패하면 Apollo의 `QueryRef`가 오류 상태가 돼서, 목록을 감싼 오류 경계가 카드 24개를 오류 화면으로 바꿔요. 보던 카드를 남기려면 추가 조회 오류를 따로 처리해 목록 아래에서 다시 시도할 수 있게 바꿔야 해요.

재시도마저 실패하는 경우도 검사할 수 있어요. 응답을 두 번 연속 실패시킨 뒤에도 오류와 다시 시도 버튼이 남는지 보는 거예요.

### 새로고침과 추가 조회가 겹칠 때

훅 테스트에서 다음 페이지 응답을 붙잡아 두고 새로고침을 먼저 끝냈더니 버그가 드러났어요. 훅은 진행 중인 요청을 하나만 저장하고 새로고침이 끝날 때 그 값을 비웠어요. 이때 추가 조회를 다시 호출하니 같은 offset을 두 번 요청했고, 페이지를 받았을 때 실행하는 콜백도 두 번 호출됐어요. 최신 게시물 목록은 이 콜백에서 분석 이벤트를 보내므로 이벤트까지 중복될 수 있었어요.

추가 조회 중에는 목록 끝을 감시하지 않아서 스크롤만으로는 이 버그가 잘 드러나지 않았어요. 사진 수가 바뀔 때 자동으로 새로고침하는 콘테스트 피드에서는 두 요청이 겹칠 수 있고요. 처음에는 [진행 중인 요청을 모두 기록했어요](https://github.com/jingeon27/side-project/commit/4830f074859ade4126f7d0a93c7bad9148bc9e92). 지금은 [Apollo의 ObservableQuery에서 조회 상태를 읽고](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/src/shared/api/infinite-query.hook.ts) 앞선 조회가 끝나야 다음 페이지를 요청해요.

훅 테스트에서는 Apollo의 `queryDeduplication`을 꺼요. Apollo가 요청을 합치면 훅이 두 번 호출해도 네트워크에는 한 번만 찍히거든요. 요청한 offset과 콜백 호출 횟수를 함께 보는 이유예요.

### 같은 응답을 MSW로 만들기

[MSW 3의 GraphQL 핸들러](https://mswjs.io/api/graphql/)로도 같은 상황을 만들 수 있어요. 카드 48개를 두 페이지로 나누고, 응답을 늦추거나 실패시킬 offset에만 Promise를 넘겨요.

```typescript
import { graphql } from 'msw/graphql';
import { HttpResponse } from 'msw/http';

import { GalleryPostsDocument, type GalleryPostsQuery } from '@/shared/api/generated';

type TResponse = 'success' | 'error';

function galleryHandler(
  endpoint: string,
  posts: GalleryPostsQuery['galleryPostsPage']['items'],
  responses: Partial<Record<number, Promise<TResponse>>> = {},
) {
  const pageSize = 24;

  return graphql.link(endpoint).query(GalleryPostsDocument, async ({ variables: { offset, limit } }) => {
    if ((offset !== 0 && offset !== pageSize) || limit !== pageSize) {
      return HttpResponse.json({ errors: [{ message: 'Unexpected pagination variables' }] });
    }

    if ((await responses[offset]) === 'error') {
      return HttpResponse.json({ errors: [{ message: 'Gallery request failed' }] });
    }

    return HttpResponse.json({
      data: {
        galleryPostsPage: {
          __typename: 'GalleryPostPage',
          items: posts.slice(offset, offset + pageSize),
          nextOffset: offset === 0 ? pageSize : null,
        },
      },
    });
  });
}
```

브라우저에서 [워커를 시작한 뒤](https://mswjs.io/api/setup-worker/) 목록을 띄우기 전에 `offset: 24`의 응답을 보류해요.

```typescript
import { setupWorker } from 'msw/browser';

const endpoint = new URL('/__test__/gallery', window.location.origin).href;
const worker = setupWorker(galleryHandler(endpoint, posts));
await worker.start();

const nextPage = Promise.withResolvers<'success'>();
worker.use(galleryHandler(endpoint, posts, { 24: nextPage.promise }));
```

스크롤한 뒤 카드 24개와 스피너가 함께 보일 때 `nextPage.resolve('success')`를 호출해요. 이제 카드는 48개여야 해요. 첫 로딩은 `offset: 0`에 새 Promise를 걸고 스켈레톤이 보인 뒤 응답을 보내요.

추가 조회를 실패시키려면 `24`에 오류 응답을 지정해요.

```typescript
worker.use(galleryHandler(endpoint, posts, { 24: Promise.resolve('error') }));
```

`24`를 `0`으로 바꾸면 첫 조회가 실패해요. 핸들러는 해당 offset을 요청할 때마다 오류를 돌려줘요. 오류 화면이 뜨면 [`worker.resetHandlers()`](https://mswjs.io/api/setup-worker/reset-handlers/)로 성공 핸들러를 복원하고 다시 시도를 눌러 첫 페이지가 돌아오는지 봐요.

재시도할 때는 실패했던 Apollo 클라이언트를 그대로 써요. `resetHandlers()` 뒤에도 캐시와 보류한 Promise는 남으니, 테스트가 끝나면 컴포넌트를 언마운트하고 남은 응답을 보내요. 다음 테스트는 새 클라이언트와 Promise로 시작해요.

## 드롭다운 테스트

체크박스 항목을 누르면 Base UI는 메뉴를 열어 두고(`closeOnClick` 기본값 `false`), Radix는 닫아요.

흔히 드롭다운이라고 부르는 UI도 용도에 따라 키보드 동작과 ARIA 속성이 달라요. [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/)에서는 작업을 고르는 메뉴 버튼, 값을 고르는 리스트박스, 글자를 입력해 선택지를 좁힐 수 있는 콤보박스를 구분해요.

피식 카드의 더보기 버튼은 Base UI의 Menu로 만들었어요. 메뉴를 열면 페이지 스크롤이 잠기고, 항목을 고르면 메뉴가 닫혀요. 수정을 고르면 편집 시트가 열리고 숨기기와 삭제는 확인 대화상자를 거쳐요.

### 스크롤한 위치에서 드롭다운 열기

여덟 번째 카드까지 스크롤해 더보기 아이콘 아래에 남는 공간을 바꿔 봤어요. [300px이면 메뉴가 아래로 열리고](https://base-ui.com/react/components/menu), 20px이면 위로 열려야 해요. 두 경우 모두 열기 전후의 `scrollY`를 비교해 목록이 밀리지 않았는지도 봤어요.

위로 열릴 때는 팝업 아래쪽이 아이콘보다 위에 있고 양옆이 화면 안에 들어오는지 좌표로 검사했어요. 수정과 삭제 항목에는 Playwright의 [`toBeInViewport`](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport)를 썼어요. 항목이 다 보이는데도 브라우저가 계산한 비율이 `0.99999988`이라 실패한 적이 있어요. 그래서 `1` 대신 `0.99` 이상이면 통과하게 했어요.

카드를 준비하고 스크롤 위치를 맞추는 코드는 두 테스트가 공유하고, 좌표 비교는 각 테스트에 뒀어요. Base UI의 `it.each`처럼 남은 공간과 예상 방향을 짝지어 검사하는 방법도 있어요.

### 메뉴를 연 뒤 어디를 누르는지 나누기

각 테스트는 `테스트 사진 8 더보기`라는 접근성 이름으로 버튼과 메뉴를 찾아요. 같은 카드에서 시작해 누르는 곳만 바꿔요.

| 누르는 곳 | 확인한 결과 |
| --- | --- |
| 메뉴 바깥 배경 | 메뉴가 닫히고 `aria-expanded`가 `false`로 바뀌어요. 대화상자는 뜨지 않고 목록 조회도 늘지 않아요 |
| 삭제 항목 | 메뉴가 닫히고 삭제 확인 대화상자가 열려요. 취소하면 대화상자가 닫히고 게시물은 남아요 |
| 더보기 아이콘 | 다시 누르면 메뉴가 닫히고, 한 번 더 누르면 열려요 |

offset 기록에는 목록 조회만 남아요. 취소할 때 삭제 요청이 없었는지까지 보려면 클릭 전에 삭제 mutation을 감시해야 해요. 삭제를 확정하는 경우라면 그 게시물의 id가 한 번만 전달되는지도 볼 수 있고요.

### 키보드 조작과 포커스 확인하기

키보드 테스트는 조작마다 새 페이지에서 시작해요. Desktop Safari에서도 같은 테스트를 실행해요.

| 조작 | 시작 상태 | 기대하는 결과 |
| --- | --- | --- |
| Enter | 더보기 아이콘에 포커스 | 메뉴가 열리고 수정 항목에 포커스가 가요 |
| 아래 화살표 | 수정 항목에 포커스 | 구분선을 건너 삭제 항목으로 가요 |
| Escape | 메뉴 항목에 포커스 | 메뉴가 닫히고 포커스가 더보기 아이콘으로 돌아와요 |
| Escape로 삭제 취소 | 삭제 확인 대화상자가 열린 상태 | 게시물이 남고 포커스가 더보기 아이콘으로 돌아와요 |

더보기 버튼의 `aria-controls`는 메뉴가 열려 있을 때만 그 메뉴의 id를 가리켜야 해요. 열기 전과 닫은 뒤에는 속성이 없는지도 검사해요.

### 메뉴가 닫히는 동안의 입력 확인하기

Escape를 눌러도 애니메이션이 끝날 때까지 메뉴는 DOM에 남아요. 그사이에 삭제를 눌러 보려고 전환 시간을 10초로 늘렸어요. Escape를 누르면 `data-ending-style`이 붙고 `getAnimations()`에 애니메이션이 잡힐 때까지 기다려요. 시작 전에는 빈 배열이 돌아올 수 있거든요.

`pause()`로 애니메이션을 멈추고 삭제 항목 위로 포인터를 옮겨 클릭해요. 메뉴는 남아 있되 항목이 강조되거나 삭제 확인 대화상자가 뜨면 실패예요. 마지막에 `finish()`를 호출하면 메뉴가 DOM에서 사라져야 해요. 닫히는 메뉴가 클릭을 받도록 바꿔 보니 이 테스트가 실패했어요.

## 무한 스크롤과 드롭다운이 겹칠 때

다음 페이지가 붙으면 보던 카드의 위치와 `scrollY`가 그대로인지 봤어요. [마지막 카드의 메뉴를 열어 둔 테스트](https://github.com/jingeon27/side-project/commit/49294bdff9abf8120bb67cfc06c6e61ef4d7188b)에서는 응답 전후에 메뉴 좌표도 비교했어요.

다음 페이지 요청을 실패시키면 목록이 오류 화면으로 바뀌면서 메뉴도 사라져요. 메뉴가 걸어 둔 `body`의 스크롤 잠금이 풀리고, 다시 시도를 누르면 첫 24개가 돌아오는 것까지 확인했어요.
