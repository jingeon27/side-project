<Summary>

I revisited the component tests I had given too little thought to. Reading library tests helped me find missing cases in Photo Contest's infinite scroll and dropdown menus, and reconsider how to divide those tests.

</Summary>

![A spinner beneath the existing cards while the next page loads, alongside a dropdown that opens above its trigger near the bottom of the viewport.](/images/covers/scroll-and-dropdown-states.avif)

At work, I wrote unit tests mainly for logic and checked screens through integration and E2E tests. I built those screens with Radix, Base UI, and shadcn/ui, which I trusted for their popularity, high download counts, and quick fixes for reported issues. I had given little thought to how their components were tested.

When reading library code, I usually started with the implementation and type definitions. Tests were useful as examples of inputs and usage.

I also revisited my [test file convention at work](/en/blog/testing-standards). New feature specifications went in `*.spec.*` files, while `*.test.*` files reproduced unexpected failures to prevent regressions. I knew my test design had gaps and wanted to keep filling them as problems surfaced. Looking back, I should have spent more thought on which situations to cover in the initial specification.

Infinite scrolling and dropdowns have plenty of cases that are easy to miss. A test that only checks for new cards after scrolling to the end can pass even if the existing list disappears while the request is pending. Checking only that a menu opens can miss an item clipped by the bottom of the screen.

Photo Contest already had a [gallery E2E test](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/gallery-pagination.spec.ts) that started with 24 posts and scrolled to the next page. I added cases for delayed and failed responses and for opening a post's menu farther down the list.

## Library tests as an answer key

This time, I read tests in TanStack Query, Radix, and Base UI by following their starting conditions, actions, and expected results. I used them as an answer key to find cases I had not thought of.

Reading tests also gave me a glimpse of how the libraries had resolved issues. The reproduction code and assertions showed which input or interaction had caused a problem and what behavior the fix was meant to preserve.

The TanStack Query [`useInfiniteQuery` tests](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx) collect the hook's state on every render and check the order in which the first fetch and next-page fetches change it. They separately check that pages already fetched stay when a next-page request fails, with `isFetchNextPageError` set, and that `hasNextPage` becomes `false` when `getNextPageParam` returns `undefined`.

I also looked at shadcn/ui, which I had been using regularly. It offers dropdown implementations based on Radix, Base UI, and React Aria. The [Base UI version](https://github.com/shadcn-ui/ui/blob/8ab27715521cbd4f87ae6886cd989cbb678f6de7/apps/v4/registry/bases/base/ui/dropdown-menu.tsx) composes Base UI components and adds styles. I followed opening, closing, and focus behavior to the tests in the underlying Radix and Base UI libraries.

The Radix [DropdownMenu tests](https://github.com/radix-ui/primitives/blob/fe02008f49834d7421427fe532e5b11f13c7bcac/packages/react/dropdown-menu/src/dropdown-menu.test.tsx) cover details that are easy to overlook when opening and closing a menu. They check that `aria-controls` does not point to a missing element, that submenus close when the window loses focus, and that items cannot take focus from a passing pointer during dismissal.

Photo Contest uses Base UI for its post menus. In its [menu tests](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/root/MenuRoot.test.tsx), I noticed how small the individual cases were. Suites group keyboard navigation and focus management, then separate tests check each behavior: Enter focuses the first item, ArrowUp focuses the last, and closing returns focus to the trigger. A failed interaction does not prevent the other tests from running.

The [popup transition state test](https://github.com/mui/base-ui/blob/5aacdbb7852487518b982ea397885c8322a3ebc6/packages/react/src/menu/popup/MenuPopupTransitionState.test.tsx) records opening, closing, and reopening during dismissal in sequence. Those steps belong together because an earlier transition can affect the next one. It repeats the checks with `it.each` across controlled state, `keepMounted`, initially open state, and portal container options. This file runs in a real browser and is skipped in jsdom.

I revisited the Photo Contest tests with this distinction in mind. I split independent interactions into separate cases and kept sequences together where the transitions mattered. The following sections cover those changes and the cases I could still add.

## Control responses to create each state

Photo Contest has a dedicated browser test page that renders the real latest-posts feed, post cards, and menus. Playwright's [`page.route`](https://playwright.dev/docs/mock) controls when GraphQL responses arrive. The feed still uses its actual `IntersectionObserver` and Apollo cache to detect the end and append pages.

The default responses contain 24 cards on the first page and two on the last. Recording each request's offset produces `0` for the initial query and `24` for the next one. This page starts its first query in the browser. A [separate E2E test](https://github.com/jingeon27/side-project/blob/ba263cb1f9a1b09ae2d77a4e1a99229d9b1c2ff6/projects/photo-contest/apps/web/e2e/access-layout.spec.ts#L32) checks that server-preloaded content appears in the HTML.

Holding or failing a response lets the tests check these situations.

| State | What the browser shows | Request check |
| --- | --- | --- |
| First response pending | A skeleton before any cards, then the first 24 cards when the response arrives | One request at `offset: 0` |
| Next response pending | The existing cards and a spinner below the list | One request at `offset: 24` even after scrolling to the end again |
| Final response received | In the test with a full last page, 48 cards in total | `[0, 24]` after scrolling past the end |
| First request fails | An error with Retry, followed by the first page after retry | `[0, 0]` |
| Next request fails | An error replaces the cards already on screen, and retry starts again from the first page | `[0, 24, 0, 24]` after scrolling again |

TanStack Query [creates a new QueryClient before each test and clears it afterward](https://github.com/TanStack/query/blob/d7c0418f871052e45afc866f4520c062ebd5561a/packages/react-query/src/__tests__/useInfiniteQuery.test.tsx#L31-L46). Reusing cached data could skip initial loading and change the starting condition. In Photo Contest, each Playwright test starts the app and its Apollo client on a fresh page, with routes installed for that page. Each test also creates its own response promises and request log.

Holding the first response exposes the skeleton. Holding the next one exposes a spinner below the existing cards. The next-page test originally checked list retention, duplicate requests, and appending cards together. I split the loading lifecycle from duplicate-request prevention. Initial loading and preventing requests during that loading now have separate tests too.

These examples show shortened versions of the split tests. [`openGallery`](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/test/browser/gallery.fixture.ts) installs routes before navigation and holds the first response at the specified offset until its promise resolves.

```typescript
test('keeps the list during loading and appends the next page', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards } = await openGallery(page, {
    responses: { 24: response.promise },
  });
  const loading = feed.getByRole('status');

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(loading).toBeVisible();
    await expect(cards.first()).toBeVisible();
    await expect(cards).toHaveCount(24);
  } finally {
    response.resolve('success');
  }

  await expect(cards).toHaveCount(26);
  await expect(cards.last()).toBeVisible();
  await expect(loading).toBeHidden();
});
```

Check that loading is visible before releasing the response, so the test cannot pass by inspecting only the completed screen. The card count, first card's visibility, and spinner all establish that the list remains usable during loading. These assertions describe the same behavior and can stay together.

The duplicate-request case also holds the next response, then scrolls up and returns to the end. The existing `expectNoGalleryRequest` helper waits one second for a gallery request and passes if none arrives.

```typescript
test('does not request the same offset again while the next page is pending', async ({ page }) => {
  const response = Promise.withResolvers<'success'>();
  const { feed, cards, offsets } = await openGallery(page, {
    responses: { 24: response.promise },
  });

  try {
    await expect(cards).toHaveCount(24);
    await scrollPastEnd(page);
    await expect(
      feed.getByRole('status'),
    ).toBeVisible();
    await cards.first().scrollIntoViewIfNeeded();

    const noRequest = expectNoGalleryRequest(page);
    await Promise.all([noRequest, scrollPastEnd(page)]);
    expect(offsets).toEqual([0, 24]);
  } finally {
    response.resolve('success');
  }
});
```

Start watching before the second scroll to catch an immediate request. The `finally` block releases the response whether the test passes or fails. With separate cases, a failure to retain the list does not prevent the duplicate-request behavior from being checked.

## Reach the final page

With the default data, fetching stopped after 26 cards. I temporarily changed the feed to infer the next offset from the card count instead of the server's `nextOffset`, but all four tests that existed then still passed. With only two cards on the last page, both implementations stopped at the same point.

So I added a separate test that fills the last page with 24 cards and returns `nextOffset: null`. Once 48 cards appear, the test starts [watching for requests](https://playwright.dev/docs/api/class-page#page-wait-for-request), scrolls beyond the document's height, and sends another wheel input. No request arrives within the one-second watch window, so the sequence stays at `[0, 24]`. With the same data, the card-count implementation fails by requesting `offset: 48`.

The test waits for the final response before scrolling to the end again. An absence of requests during loading, or halfway down the list, would not establish that pagination had ended. The browser test observes a one-second window. Separate hook tests check that fetching follows the server's end condition.

## Recover from failed requests

I tested initial-query and next-page failures separately. Both recover by fetching the first page again, so the final card count alone cannot distinguish them. The tests record which offset failed, then check that scrolling can fetch the next page after retry.

When a next-page request fails, the 24 cards already displayed are replaced by the error screen. The list reads from an Apollo `QueryRef`. A failed `fetchMore` puts that reference into an error state, which activates the list's error boundary.

The TanStack Query test checks that existing pages remain after a next-page failure. Keeping them in Photo Contest would require handling that error separately from failure of the whole list and offering retry below it. The expected result still needs to match the product's intended behavior.

The preparation differs too. The initial-error case starts without cards, while the next-page case first loads 24 cards and then scrolls. Both establish that the error is visible before retrying. Error and retry belong together here because the test checks recovery from that specific failed query.

A retry that also fails could have its own test. Two consecutive failure responses would let it check that the error and Retry button remain available.

## When refresh and next-page requests overlap

I also examined the query states behind the screen. Following TanStack Query's tests, I recorded the states committed to the UI in order. A next-page request should keep the list visible with a loading state, then append the page and end loading. The record exposes any intermediate state that replaces the whole list with a loading screen.

Testing an overlap between refresh and next-page requests revealed a bug. If refresh finished first, a later call to fetch more requested the pending offset again and ran the page-loaded callback twice. The latest-posts feed uses that callback to send analytics events, so those could be duplicated too.

The hook remembered only one pending request. Refresh completion cleared that record, making the hook accept another request while the next page was still loading.

The screen did not reveal this immediately because it stops observing the end during next-page loading. But the contest feed refreshes when its photo count changes, so the requests can overlap. The [first fix](https://github.com/jingeon27/side-project/commit/4830f074859ade4126f7d0a93c7bad9148bc9e92) tracked every pending request. The hook [now reads Apollo ObservableQuery's current state](https://github.com/jingeon27/side-project/blob/d5f35d7b06857ee519f3868d70f530980c66b3a2/projects/photo-contest/apps/web/src/shared/api/infinite-query.hook.ts) to decide whether it can fetch the next page, without maintaining a separate request log.

The hook tests disable Apollo's `queryDeduplication`. Otherwise, several calls could be combined into one network request and escape detection. That is why the tests check both requested offsets and the page-loaded callback count. Browser tests cover actual scrolling, while hook tests cover request control when operations overlap.

## Serve the same responses with MSW

So far, the tests have controlled responses with `page.route`. [MSW 3 GraphQL handlers](https://mswjs.io/api/graphql/) can create the same situations. This example splits 48 cards into two pages. Offset `0` returns 24 cards and `nextOffset: 24`. Offset `24` returns the rest and `nextOffset: null`. A promise at a specific offset can hold that response or make it fail.

```typescript
import { graphql } from 'msw/graphql';
import { HttpResponse } from 'msw/http';

import { GalleryPostsDocument, type GalleryPostsQuery } from '@/shared/api/generated';

type TResponse = 'success' | 'error';

function galleryHandler(
  endpoint: string,
  posts: GalleryPostsQuery['galleryPostsPage']['items'],
  responses: Partial<Record<number, Promise<TResponse>>> = {},
) {
  const pageSize = 24;

  return graphql.link(endpoint).query(GalleryPostsDocument, async ({ variables: { offset, limit } }) => {
    if ((offset !== 0 && offset !== pageSize) || limit !== pageSize) {
      return HttpResponse.json({ errors: [{ message: 'Unexpected pagination variables' }] });
    }

    if ((await responses[offset]) === 'error') {
      return HttpResponse.json({ errors: [{ message: 'Gallery request failed' }] });
    }

    return HttpResponse.json({
      data: {
        galleryPostsPage: {
          __typename: 'GalleryPostPage',
          items: posts.slice(offset, offset + pageSize),
          nextOffset: offset === 0 ? pageSize : null,
        },
      },
    });
  });
}
```

Put 48 distinct fixture cards in `posts`. [Start the worker](https://mswjs.io/api/setup-worker/) on the browser test page, then register the handler that holds the next response before mounting the feed.

```typescript
import { setupWorker } from 'msw/browser';

const endpoint = new URL('/__test__/gallery', window.location.origin).href;
const worker = setupWorker(galleryHandler(endpoint, posts));
await worker.start();

const nextPage = Promise.withResolvers<'success'>();
worker.use(galleryHandler(endpoint, posts, { 24: nextPage.promise }));
```

Scroll to the end, check that the 24 cards and the spinner are both visible, then call `nextPage.resolve('success')` and check that the list grows to 48 cards. To test initial loading, use a fresh promise at `offset: 0` and release the response after checking for the skeleton.

To make a request fail, resolve its response to `'error'`. This example fails the next-page request.

```typescript
worker.use(galleryHandler(endpoint, posts, { 24: Promise.resolve('error') }));
```

Use `0` to fail the first request. In either case, once the error is visible, call [`worker.resetHandlers()`](https://mswjs.io/api/setup-worker/reset-handlers/) to restore the initial success handler. You can then click Retry and check that the first page returns.

Prepare handlers and client state separately for each test. `resetHandlers()` clears neither Apollo's cache nor pending promises. Unmount the component and release pending responses during cleanup, then use fresh promises and a new Apollo client in the next test. Keep the existing client when retrying within one test to exercise recovery from its failure.

The error handler above keeps failing until replaced. Restore the success handler after checking the error, then click Retry.

MSW changes how the response is prepared. The UI assertions still need to check whether the existing cards remain and when the spinner or error appears.

## Open the dropdown from a scrolled position

I scrolled to the eighth post, which starts below the visible part of the page. With its trigger on screen, I compared [where the menu opens](https://base-ui.com/react/components/menu) with two amounts of space below the trigger. With 300 pixels, the menu opens beneath it. With 20 pixels, it opens above the trigger and both Edit and Delete remain reachable. The test compares `scrollY` before and after opening so it also catches a jump in the list.

For a menu opening upward, the test checks that its bottom edge sits above the trigger and that its horizontal edges fit within the viewport. Playwright's [viewport assertion](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport) checks item visibility.

Requiring an exact visible ratio of `1` failed when the browser returned `0.99999988`. This was a small rounding difference, so the tests allow a little tolerance for visibility and use coordinates to verify the opening direction.

The two placement cases could use pairs of available space and expected direction, much like Base UI's `it.each`. Each pair should generate its own test so a failure in one does not prevent the other from running. A helper can prepare the card and scroll position, while each test keeps its coordinate comparisons visible.

## Click the background, a menu item, or the trigger

Checking only that the menu closed would pass for both the background and Delete. Choosing Delete must also open the confirmation dialog, while clicking the background must leave the page without it. So each click target has its own test.

Each test scrolls to the same card before opening its menu. The trigger and menu share an accessible name that includes the card title. Looking up that named menu before choosing an item makes it clear which card the test operates on.

| Click target | What the test checks |
| --- | --- |
| Background outside the menu | The popup closes and `aria-expanded` becomes `false`. No confirmation appears, and the list-query log stays unchanged |
| Delete item | The menu closes and a confirmation dialog opens. Cancelling closes the dialog and leaves that post present |
| The trigger that opened the menu | A second click closes it. A third click opens it again |

The offset log covers list queries only. Checking that cancellation sends no deletion request would require watching the delete mutation before clicking. A confirmation test could also check that the correct post id is sent exactly once. A card that remains on screen does not prove that no deletion request was sent.

## Keyboard interaction and focus

Opening with Enter, moving with ArrowDown, and closing with Escape now have separate tests. Each prepares the menu on a fresh page, so failure in one interaction does not prevent the others from being checked. These tests also run in Desktop Safari.

Alongside focus, the tests check `aria-controls`. The trigger has no such attribute while closed and points to the menu's id while open. Closing must remove it again so it cannot reference an unmounted menu.

| Test | Starting condition | Expected result |
| --- | --- | --- |
| Open with Enter | Trigger focused | Edit receives focus |
| Move with ArrowDown | Menu open, Edit focused | Focus skips the separator and moves to Delete |
| Close with Escape | Menu open, an item focused | Menu disappears and focus returns to the trigger |
| Cancel deletion | Delete confirmation open | Post remains and focus returns to the trigger |

An Escape test still needs to prepare an open menu with focus on an item. Testing focus after cancelling deletion also requires selecting Delete first. Keep that preparation with its expected result, while testing unrelated conditions such as placement and page arrival separately. This makes a failure easier to locate.

## Input while the menu is closing

A menu can remain visible briefly while closing. Moving or clicking the pointer over it must not activate an item. Checking only after the transition ends would miss this interval.

Base UI's popup transition test also controls when the animation ends. It stretches the transition to ten seconds to leave time for intermediate checks, then calls `finish()` on the animations returned by `getAnimations()`.

I changed the Photo Contest test to control completion too. It stretches the exit transition to ten seconds, presses Escape, and checks both `data-ending-style` and the presence of actual animations. It then calls `pause()` before moving the pointer over Delete and clicking. An empty animation list can also mean the transition has not started, so the start check comes first.

During those interactions, the menu must remain in the DOM, the item must stay unhighlighted, and no deletion confirmation should open. Afterward, `finish()` ends the transition and the test checks that the menu is removed. Deliberately allowing pointer input during dismissal makes this test fail.

## What happens to an open menu when the list changes?

Finally, I checked what happens when [list updates and menu interactions overlap](https://github.com/jingeon27/side-project/commit/49294bdff9abf8120bb67cfc06c6e61ef4d7188b). Appending a page should preserve the card's position and `scrollY`. With the last card's menu open, it should also leave the menu at the same coordinates.

A failed next-page request replaces the list with the error screen and removes the open menu. The test checks that the menu's scroll lock on `body` is released as well. Retrying brings back the first page so the list can be read again.
