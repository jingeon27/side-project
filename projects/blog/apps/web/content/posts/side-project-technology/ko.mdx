사진 커뮤니티와 Game Mate를 같은 저장소에서 만들지만 API와 캐시까지 맞추지는 않았어요. 웹은 Next.js와 React, 서버는 NestJS, DB는 PostgreSQL을 쓰고, 사진 서비스에는 GraphQL과 Apollo를, Game Mate에는 REST와 TanStack Query를 골랐어요.

여러 목록에 나타나는 같은 게시물을 Apollo의 정규화 캐시로 다뤄 보고 싶었어요. Game Mate에서는 글을 바꾼 뒤 어떤 목록과 상세를 다시 읽을지 쿼리 키로 직접 정해 보고 싶었고요. 같은 설정을 재사용하는 편리함보다 서로 다른 갱신 방식을 다뤄 보는 쪽을 택했어요.

그런데 글 하나를 저장하는 기능만 봐도 라이브러리 선택으로 끝나지는 않았어요. 웹과 앱에서 같은 입력 화면을 쓸지, API 응답이 예상과 다르면 어디서 멈출지, 요청을 두 번 받아도 한 번만 저장할지 정해야 했어요. 저장한 내용이 브라우저와 서버 캐시에 언제 반영되는지도 별개의 일이었어요.

이 과정에서 계속 신경 쓴 건 기능을 고칠 때 수정할 곳을 찾을 수 있는지, 실패한 요청이 어디까지 처리됐는지 설명할 수 있는지였어요. 입력 중인 값은 폼에, 서버에서 읽은 값은 캐시에 두었고, 저장 여부는 DB에서 결정하게 했어요. 테스트와 ESLint도 그 구분이 코드에 남아 있는지 확인하는 쪽으로 붙였어요.

[기획과 화면을 바꾼 이야기](/ko/blog/사이드-프로젝트를-설계하면서-계속-바꾼-것들)에서 익명 기록과 투표, 메시지 재전송을 다뤘어요. 그런 동작을 실제로 만들다 보니 화면뿐 아니라 API 응답과 DB 저장, 캐시 갱신에도 정할 게 생겼어요.

## 웹 화면을 먼저 만들고 앱에서도 같이 쓰기로 했어요

두 서비스의 웹은 Next.js App Router와 React로 만들었어요. 공개 글과 그룹에는 검색에 필요한 서버 HTML을 만들고, 댓글이나 입력 폼처럼 조작이 필요한 부분은 클라이언트 컴포넌트로 두었어요.

공개 글은 브라우저가 데이터를 다시 받을 때까지 빈 화면으로 기다리게 하고 싶지 않았어요. 그래서 첫 본문과 검색 메타데이터를 서버에서 만들어요. 이때 개인의 세션이나 권한이 섞인 결과를 공용 캐시에 넣지 않도록 공개 조회와 개인화 조회를 나눴어요.

사진 서비스의 공개 조회는 쿠키를 전달하지 않아요. 세션이 필요한 서버 조회는 요청마다 만든 Apollo Client로 처리하고 공용 HTTP 캐시를 쓰지 않아요. Game Mate에서도 공개 게시물 상세를 조회하는 요청과 로그인한 사람의 차단 목록을 읽는 요청을 나눴어요. 공개 본문을 캐시하더라도 누가 어떤 내용을 볼 수 있는지까지 같은 결과로 취급하지 않으려는 구성이에요.

모바일은 Expo 안에 WebView를 두고 웹 화면을 공유해요. 화면을 두 벌 만들기보다 웹에서 글을 쓰고 답변을 읽는 흐름부터 다듬으려고 했어요. 푸시 알림과 시스템 브라우저 열기, 공유 같은 기능은 웹과 앱 사이의 메시지 계약으로 연결했어요.

WebView를 쓰면서 화면을 다시 만드는 일은 줄었지만, 뒤로 가기와 키보드, 안전 영역은 앱에서 따로 다뤄야 했어요. 사진 서비스는 아이디와 비밀번호 또는 익명 세션으로 로그인하고, WebView도 웹과 같은 HttpOnly 세션 쿠키를 써요. 로그인 토큰을 네이티브로 꺼내 전달하지 않아요. 앱스토어 배포와 실제 기기에서의 최종 확인은 아직 남아 있어요.

Game Mate의 푸시 권한 요청처럼 응답이 늦게 돌아오는 기능도 있어요. 권한 요청 도중 웹 페이지가 다시 로드되면 이전 페이지에 보낼 결과를 새 페이지에 주지 않도록 브리지의 세대를 구분해요. 허용한 웹 출처에서 온 메시지인지, 현재 페이지가 보낸 요청인지 확인하는 처리도 화면 공유에 따라 추가된 일이에요.

입력 폼은 React Hook Form과 Zod로 관리해요. 필드 검증과 제출 상태를 폼에 모으고, 버튼과 입력의 색과 간격은 공통 디자인 시스템에서 맞췄어요. 메뉴와 대화상자는 Base UI를 기반으로 조합해요. 그래도 포커스 복귀와 닫힘 애니메이션, 뒤로 가기까지 서비스에 맞게 연결하고 확인하는 작업은 남았어요.

## 브라우저 캐시는 서로 다르게 골랐어요

사진 게시물 하나가 홈 피드와 그룹 목록, 인기 목록에 같이 나와요. 이때 같은 엔티티를 여러 화면에서 읽고 바꾸는 방식을 다뤄 보려고 Apollo Client를 썼어요.

그렇다고 Apollo를 넣으면 모든 목록이 알아서 맞춰지는 건 아니었어요. 글 하나의 제목을 바꾸는 일과 목록에서 그 글을 빼는 일은 달라요. 페이지를 이어 붙이는 규칙이 있으면 삭제한 항목이 다시 섞여 들어올 수도 있었어요. 도메인별 type policy와 캐시 갱신 함수를 두고, 정렬과 그룹, 댓글의 부모 ID를 기준으로 목록을 구분했어요. 필요한 경우에는 활성 쿼리를 다시 받도록 했고요.

게시물 목록은 그룹과 대회, 카테고리, 정렬 조건으로 구분하고, 댓글은 게시물과 부모 댓글 ID로 구분해요. 목록 구성이 바뀌는 경우에는 피드 캐시를 비우고 다시 조회해요. 인기순은 서버에서 순위를 다시 받고, 더 읽은 최신순 목록은 유지하는 처리도 따로 있어요. [게시물 캐시 테스트](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/photo-contest/apps/web/src/features/post/model/post.cache.spec.ts)에는 다른 조건의 목록이 섞이지 않는지, 초기화 뒤 예전 뒷페이지가 살아나지 않는지를 넣었어요.

Game Mate에서는 REST와 TanStack Query를 골랐어요. 글 목록과 상세, 답변을 수정한 뒤 어떤 조회를 갱신할지 직접 정해 보고 싶었어요. 이쪽은 쿼리 키와 `queryOptions`를 함께 관리하고, 변경한 기능에서 관련 조회를 무효화해요.

예를 들어 답변을 쓰면 글 상세만 달라지는 게 아니에요. 목록의 답변 수와 알림 목록도 바뀔 수 있어서 세 조회를 함께 무효화해요. 목록 쿼리 키는 공통 접두사 아래 조회 조건을 넣고, 상세는 별도의 키를 써요. [쿼리 키 테스트](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/apps/web/src/features/post/model/post.options.spec.ts)에서는 목록 접두사를 무효화할 때 여러 필터의 목록이 함께 무효화되고 상세 캐시는 그대로 남는지 확인해요. 상세도 갱신해야 하는 변경이라면 그 키를 별도로 지정해야 해요.

이것은 GraphQL이면 정규화 캐시를 써야 하고 REST면 쿼리 키만 써야 한다는 기준은 아니에요. 제가 고른 두 조합에서 캐시가 어떤 단위로 갱신되는지 확인하며 구현한 결과예요. Apollo도 목록 정책과 재조회를 정해야 하고, TanStack Query도 변경과 조회의 관계를 빠뜨리지 않게 관리해야 했어요.

그래서 두 서비스의 서버 상태를 별도의 `useState`로 다시 복사하지 않도록 했어요. 입력 중인 값은 폼이, 서버에서 받은 값은 Apollo나 TanStack Query가 맡아요. 같은 값을 여러 곳에서 수정할 수 있게 만들면 저장 뒤 어느 값이 최신인지부터 다시 찾아야 했어요.

사진 서비스에서 목록을 고칠 때는 Apollo의 도메인별 갱신 함수를 보고, Game Mate에서는 쿼리 키와 무효화 옵션을 봐요. 두 방식을 같은 API 훅으로 감추면 무엇을 다시 읽는지 찾기 어려울 것 같아 각각의 형태를 남겼어요.

## 권한 확인과 데이터 처리는 NestJS에서 맡았어요

두 서비스의 서버는 NestJS와 Express, Prisma, PostgreSQL을 써요. Next.js는 화면을 그리고 서버에서 렌더링하거나 같은 출처로 API 요청을 전달해요. 누가 그룹에 가입할 수 있는지, 게시물을 지울 수 있는지, 언제 투표할 수 있는지는 NestJS에서 확인해요.

화면에서 버튼을 숨겨도 API로 직접 요청을 보낼 수 있어요. 그래서 비공개 그룹의 글을 볼 수 있는지, 관리자가 멤버를 내보낼 수 있는지도 API에서 확인하게 했어요.

요청은 REST 컨트롤러나 GraphQL 리졸버가 받고, 서비스에서 권한을 확인하고 데이터를 저장해요. 모듈은 그 기능이 사용할 서비스와 외부 연결을 등록해요. OAuth와 게임 API 호출은 따로 두었어요. 서버 로직을 시험할 때 실제 외부 서비스 응답을 기다리는 대신 준비한 응답으로 연결할 수 있어요.

모듈은 인증, 그룹, 게시물, 채팅처럼 기능별로 나눴어요. 한꺼번에 저장돼야 하는 데이터는 트랜잭션으로 묶었고요. 두 서비스는 서버와 DB를 각각 두었고 계정도 공유하지 않아요. 같은 NestJS를 쓴다는 이유로 두 서비스의 사용자 모델까지 하나로 합칠 필요는 없었어요.

Prisma가 조회 타입을 맞춰 줘도 동시에 온 요청 두 개를 한 번만 저장해 주는 건 아니에요. 그 부분은 DB 제약과 잠금으로 막고, 실제 PostgreSQL에 요청을 겹쳐 보내는 테스트를 두었어요.

## API 타입은 한곳에서 만들고 실제 응답도 검사해요

Game Mate의 API 계약은 서버가 사용하는 Zod 스키마에서 시작해요. 여기서 OpenAPI를 만들고 Orval로 SDK를 생성해요. 응답 필드를 바꿀 때 서버 타입과 프런트 타입을 따로 고치는 일을 줄이려고 했어요.

```text
Zod 계약
  → OpenAPI
  → 생성 SDK와 응답 스키마
  → 웹·관리자에서 사용
```

API와 웹의 배포 시점이 다르거나 서버가 예상하지 않은 값을 보내면 생성된 타입과 실제 응답이 달라질 수 있어요. 그래서 SDK 전송 함수가 응답 스키마를 적용해요. 생성된 요청도 이 검증을 빠뜨리지 않는지 테스트해요.

SDK의 공통 전송 함수는 응답 스키마가 없으면 요청하지 않아요. 성공 응답이라도 스키마를 통과해야 호출한 쪽에 돌려줘요. 계약을 바꾼 뒤에는 SDK를 다시 생성해야 하고, CI에서도 커밋된 생성 코드와 차이가 있는지 확인해요. 타입을 손으로 두 벌 쓰는 일은 줄었지만 생성 과정을 유지하는 비용은 있어요.

예상하지 못한 응답을 모두 기본값으로 채우는 방식은 피했어요. 일부 표시용 필드에는 명시적인 보완 정책을 두되, ID나 권한, 세션, 본문과 목록이 잘못된 경우에는 오류로 드러나게 했어요. 화면을 계속 그리기 위해 중요한 값까지 조용히 바꾸고 싶지는 않았어요. [SDK의 응답 처리](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/packages/sdk/src/http.ts)에 이 경계를 뒀어요.

사진 서비스는 API의 GraphQL 스키마와 웹의 쿼리, 뮤테이션 문서로 타입과 Document를 생성하고 CI에서도 코드 생성을 실행해요. 스키마와 요청 문서를 연결하는 이 코드 생성은 Game Mate SDK의 Zod 기반 응답 검증과는 달라요. 사진 서비스의 브라우저에서 같은 검증을 수행한다고 볼 수는 없어요.

API 타입이 맞아도 그룹 가입 권한이나 투표 가능한 시간까지 확인해 주지는 않아요. 형식이 올바른 요청과 허용할 수 있는 요청은 다른 문제라서 입력 검증과 권한 검사는 서버에 남겼어요.

## 두 번 들어온 요청은 DB에서도 막아야 했어요

투표 버튼을 누른 뒤 비활성화하면 중복 클릭은 줄일 수 있어요. 하지만 다른 탭에서 누르거나 요청을 직접 두 번 보내는 경우까지 막을 수는 없어요.

사진 서비스의 대회 투표는 대회와 투표자 조합에 unique 제약을 두었어요. 먼저 조회해서 투표가 없다는 사실을 확인하더라도, 두 요청이 동시에 그 확인을 통과할 수 있어요. 마지막 저장 단계에서도 한 표만 들어가도록 한 거예요. 투표 기간과 그룹 멤버 여부, 자신의 게시물인지도 트랜잭션 안에서 확인해요. [그룹 대회 투표 구현](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/photo-contest/apps/api/src/contest/group-contest/group-contest.service.ts)에서 볼 수 있어요.

Game Mate의 채팅에는 클라이언트가 만든 메시지 ID를 보내요. 같은 사람이 접근할 수 있는 같은 대화에서 ID와 본문, 첨부파일을 그대로 다시 보내면 이미 저장한 메시지를 돌려줘요. 같은 ID를 다른 내용이나 다른 대화에 쓰면 충돌로 처리하고, 비운 대화 이력에 있던 메시지는 재전송으로 복구하지 못하게 했어요. 응답을 못 받았다는 이유로 재시도했을 때 메시지가 두 개 생기지 않도록 한 거예요.

메시지 저장에서는 대화 행을 잠그고 접근 권한과 첨부파일을 다시 확인해요. 메시지와 알림, 푸시 대기 기록을 같은 트랜잭션에 넣고, 실시간 이벤트는 커밋 후에 보내요. 이 잠금은 같은 대화의 전송을 순서대로 처리하는 만큼 병렬 처리의 제약도 있어요. 현재는 읽음 경계와 메시지 순서를 일관되게 다루는 쪽을 택했어요. [채팅 전송 구현](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/apps/api/src/chat/message/chat-message.service.ts)에 그 순서를 남겼어요.

두 기능 모두 중복 요청을 다루지만 결과는 달라요. 투표는 한 표만 허용하고, 같은 채팅 재전송은 같은 메시지를 반환해요. unique 제약이나 잠금을 넣기 전에 요청이 겹쳤을 때 어떤 응답을 줄지부터 정해야 했어요. 같은 대화의 잠금은 전송이 몰릴 때 대기가 생길 수 있다는 비용도 있어요.

중복만 막는다고 데이터의 연결까지 올바른 건 아니에요. 사진 서비스에서는 게시물과 참여 대회가 같은 그룹에 속하는지, Game Mate에서는 알림의 답변이나 댓글이 해당 게시물에 속하는지도 DB의 복합 외래 키로 묶었어요. 각각의 ID가 존재해도 서로 다른 게시물이나 그룹을 가리킬 수 있기 때문이에요. API의 확인을 거치지 않는 저장 경로에서도 이 관계를 어기지 않게 [그룹 데이터 제약](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/photo-contest/apps/api/prisma/migrations/20261030000000_group_integrity/migration.sql)과 [리소스 관계 제약](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/apps/api/prisma/migrations/20261030000000_resource_relations/migration.sql)을 추가했어요.

이런 부분은 DB를 흉내 낸 테스트만으로 확인하기 어려워요. 실제 PostgreSQL에 동시에 요청을 보내고 저장된 행과 응답을 함께 보는 검사, 관계가 맞지 않는 저장을 DB가 거부하는 검사가 필요했어요.

## 저장 성공과 캐시 전달 실패를 나눴어요

Game Mate에 공개 서버 캐시를 붙인 뒤에는 브라우저 캐시만 갱신해서는 부족했어요. 새로 조회해도 Next.js가 예전 글을 돌려주면 방금 수정한 내용이 되돌아간 것처럼 보일 수 있었어요.

그래서 DB를 바꾸는 트랜잭션 안에 무효화할 캐시 태그도 기록해요. 커밋 뒤에 Next.js Route Handler로 전달하고, 실패하면 대기 기록을 남겨 다시 시도해요. 저장은 끝났는데 캐시 전달이 실패했다고 글쓰기 오류를 돌려주면 사용자가 같은 글을 다시 등록할 수 있기 때문이에요.

같은 태그에 새 변경이 생기는 경우도 생각해야 했어요. 첫 번째 수정의 전달이 진행되는 동안 두 번째 수정이 저장될 수 있어요. 첫 요청이 늦게 성공했다고 태그 이름만 보고 기록을 지우면 두 번째 수정의 전달까지 끝난 것으로 처리하게 돼요. 태그마다 revision을 함께 저장하고, 전달한 revision과 일치하는 기록만 지우도록 했어요. 재시작 뒤 재전달과 이전 요청이 늦게 끝나는 경우를 [통합 테스트](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/apps/api/src/cache-invalidation/cache-invalidation.integration.spec.ts)에 넣었어요.

캐시 태그 전달이 끝나기 전에는 예전 글을 읽을 수 있어요. 이 처리는 즉시 최신 결과를 보장하려는 것보다, 이미 저장한 글을 실패로 알리지 않고 캐시 전달만 다시 시도하려는 구성이에요.

## 오류와 속도, 이용 흐름은 다른 정보로 봐요

테스트에서 조건을 확인하는 것과 실행 중인 서비스에서 무슨 일이 생겼는지 아는 것은 달라요. 두 서비스의 API와 Next 서버, 브라우저에는 Sentry를 붙였어요. 권한이 없거나 투표 기간이 지난 요청까지 오류 알림으로 쌓지 않고, 예상하지 못한 내부 오류를 보고해요. 오류 원문에는 Prisma 쿼리 인자나 입력값이 섞일 수 있어서 종류와 코드, 호출 위치를 남기고 메시지 원문과 요청, 사용자, 쿠키는 제거해요.

느린 요청은 오류 이벤트만으로 찾기 어려워서 성능 추적도 넣었어요. 두 API의 trace는 10%를 샘플링해요. 자동 HTTP와 SQL 계측을 켜는 대신 사진 서비스는 HTTP와 최상위 GraphQL 필드, Game Mate는 HTTP와 채팅의 잠금, 저장, 커밋 뒤 전달을 수동 span으로 나눴어요. `chat.lock`은 DB 왕복을 포함한 행 잠금 호출 시간이고, `chat.publish`는 서버 구독자에게 넘기는 구간이에요. 잠금 대기만의 시간이나 상대 기기에 표시된 시간으로 읽지 않도록 범위를 정했어요.

샘플링된 trace 수를 전체 요청 수로 쓰지는 않아요. Sentry Application Metrics는 trace 샘플링과 별개로 계측한 요청 수와 지연 분포를 기록해요. Game Mate는 신규 메시지 저장과 같은 요청의 재전송을 `created`, `duplicate`로 나누고, 사진 서비스는 HTTP 200으로 응답한 GraphQL 요청에서도 필드의 정상 처리와 업무상 거절, 내부 실패를 나눠요. 느린 요청의 흐름을 따라갈 trace와 계측한 전체 요청에서 결과를 집계할 metric을 따로 둔 거예요.

브라우저의 LCP, CLS, INP 같은 Web Vitals는 화면을 읽고 조작할 때의 상태를 보려고 Sentry로 보내요. Amplitude에는 페이지 방문을 보내고, Game Mate는 글쓰기 성공 같은 제품 이벤트도 보내요. 사진 서비스의 투표 같은 API 도메인 이벤트는 DB에 남겨요. 서비스와 `api`, `next-server`, `browser`를 태그로 구분하고 웹과 WebView도 나눠요. 운영 빌드의 release에는 커밋 SHA를 연결해 어느 코드의 기록인지 찾을 수 있게 했어요. SDK 키가 없으면 전송하지 않도록 두었어요.

오류에서 지웠다고 성능 정보에서도 사라지는 건 아니었어요. `beforeSend`와 별도로 `beforeSendSpan`, `beforeSendMetric`에서 작업명과 라우트 템플릿, 허용한 수치와 결과만 남겨요. 원본 URL과 쿼리, GraphQL 문서와 변수, 메시지 본문과 사용자 ID는 수집 차원에 넣지 않아요. SDK가 metric 처리 뒤 scope 속성을 합치는 경로도 있어서 최종 전송 묶음인 envelope에서 한 번 더 정리해요. 사진 서비스의 [성능 전송 정책](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/photo-contest/apps/api/src/monitoring/performance.ts)과 Game Mate의 [채팅 지표 전송 정책](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/apps/api/src/monitoring/chat-metrics.ts)에 이 처리가 있어요.

검사는 SDK의 메모리 transport가 받은 최종 전송 내용을 보도록 만들었어요. trace 샘플링을 0으로 둬도 metric이 남는지, scope에 넣은 확인용 입력이 전송에서 빠지는지, 실제 DB와 HTTP 요청의 span이 같은 trace로 이어지는지를 테스트해요. 이 검사는 실제 Sentry 수신 확인과는 달라서 수집 응답과 event ID를 확인하는 실행기를 따로 두었어요. 전송 정책과 각 검사 범위는 두 프로젝트의 [관측 안내](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/projects/game-feedback/docs/observability.md)에 남겨 두었어요.

## 테스트는 각 앱에서 필요한 경계를 확인해요

정렬이나 검증 규칙은 Vitest로 빠르게 확인해요. DB 제약과 트랜잭션, HTTP 요청은 실제 PostgreSQL과 API를 쓰는 통합 테스트로 확인하고, 화면이 있는 웹은 Playwright로 조작해요. API 테스트를 위해 브라우저를 띄우지는 않아요.

투표를 검사할 때는 API 응답 하나가 성공했는지만 보면 부족해요. 겹쳐 보낸 요청 중 성공한 응답 수와 DB에 남은 투표 수가 모두 하나인지 봐요. 채팅 재전송은 두 응답의 메시지 ID가 같은지, 다시 읽은 대화에 메시지가 하나만 있는지 함께 확인해요. DB를 흉내 낸 대역이 요청 순서를 그대로 처리하면 실제 잠금이나 unique 충돌은 드러나지 않을 수 있어서 이 검사는 PostgreSQL에 맡겼어요.

두 API에는 `*.database.integration.spec.ts`와 `*.database.integration.test.ts`를 모으는 `database` 레인도 두었어요. 관계 제약과 계측처럼 실제 DB가 필요하지만 S3나 브라우저까지 켤 필요는 없는 검사를 따로 실행할 수 있어요. 단위 검사에서 제외한 통합 테스트를 필요한 환경에 맞춰 호출하고, 마이그레이션을 적용한 DB에서 제약이 동작하는지 봐요.

테스트 설정과 러너는 각 앱 안에 두었어요. 저장소 루트는 필요한 검사를 호출하는 역할만 해요. 테스트용 포트와 임시 DB 스키마도 개발 환경과 나누어서, 검사를 돌리다가 쓰고 있던 서버의 데이터를 건드리지 않게 했어요.

OAuth와 게임 API는 외부 제공자의 응답을 대역으로 바꿔요. 미디어 통합 테스트는 실제 S3에 실행마다 다른 객체 경로를 써요. 폼 로직이 통과하는 것과 S3 권한, 서명, 업로드가 맞는 것은 실패하는 지점이 달라서 따로 보게 됐어요.

브라우저에서는 기다릴 시점도 구체적으로 잡아야 해요. 서버 HTML에 버튼이 있어도 이벤트가 아직 연결되지 않을 수 있고, 삭제가 끝나도 확인창의 닫힘 애니메이션은 진행 중일 수 있어요. 단순히 대기 시간을 늘리는 대신 클릭할 수 있는 상태와 닫힘이 끝난 상태를 나눠 봐야 했어요.

중복 투표나 채팅 재전송은 한 번의 정상 요청만 보는 테스트에서 빠지기 쉬워요. 비공개 글을 읽으려는 요청과 저장 뒤 캐시 전달이 실패하는 경우도 그렇고요. 화면과 DB, 외부 연결을 나눈 테스트가 필요한 이유가 이런 경우에 있었어요.

## 리뷰에서 반복한 지적은 ESLint로 옮겼어요

화면을 나눠 놓아도 다른 기능의 내부 파일을 바로 가져오면 금방 다시 엉켜요. 리뷰에서 import를 고치고 다음 작업에서 같은 코드를 또 고치는 일이 번거로웠어요. 폴더 배치와 import 규칙은 ESLint로 검사하도록 옮겼어요.

설정은 `packages/config/eslint`에 두었어요. 공통 TypeScript 규칙에서 시작해 React, DOM 접근성, Next.js, Expo 설정을 나눴어요. 웹의 label 규칙을 React Native까지 적용하지 않도록 하고, 각 앱은 필요한 preset과 자신의 경로를 조합해요.

규칙 구현도 설정 파일 한곳에 몰아넣지 않았어요. `rules/fsd`, `rules/web`, `rules/common`처럼 나누고, 각 규칙 옆에 테스트와 fixture를 두었어요. [ESLint 패키지](https://github.com/jingeon27/side-project/tree/225edfe3c1f564d55b69373906d1a29561b8ef6e/packages/config/eslint/src)에서 설정과 규칙을 함께 볼 수 있어요.

FSD 검사는 세 규칙으로 나눴어요.

- `layer-imports`: 아래 레이어에서 위 레이어를 가져오는지 검사해요.
- `slice-public-api`: 다른 slice의 내부 파일을 직접 가져오거나 자기 배럴을 다시 가져오는지 검사해요.
- `no-cross-page`: 화면 slice끼리 의존하는지 검사해요.

경로 해석은 `fsd.helper.ts`에서 함께 써요. `@/` 별칭과 상대 경로를 실제 위치로 바꾸고, import한 파일과 대상 파일의 레이어와 slice를 비교해요. `types`, `mocks`, schema와 server 파일처럼 허용한 경로도 이곳에서 구분해요.

규칙을 붙이고도 검사할 파일을 못 찾으면 통과할 수 있었어요. srcDir을 잘못 넘긴 경우였어요. 경로가 없거나 인식할 레이어 폴더가 없으면 설정 오류를 내도록 바꿔, 아무것도 검사하지 않은 lint를 성공으로 보지 않게 했어요.

RuleTester에는 허용할 import와 막을 import를 fixture로 넣었어요. 별칭으로 가져올 때만 막히고 상대 경로로 돌아가면 통과하는 식의 구멍이 없는지 확인해요. [배럴 경계 테스트](https://github.com/jingeon27/side-project/blob/225edfe3c1f564d55b69373906d1a29561b8ef6e/packages/config/eslint/src/rules/fsd/slice-public-api/slice-public-api.spec.ts)에도 두 경우가 함께 있어요.

컴포넌트에서 직접 fetch를 호출하거나 오버레이의 열림 상태를 다시 복제하는 코드도 규칙으로 검사해요. preset을 공유할 때는 ESLint flat config의 플러그인 등록이 문제였어요. 같은 이름에 서로 다른 객체를 등록할 수 없어서, 공통 규칙과 웹 규칙을 sidePlugin 하나에 넣고 preset마다 쓸 규칙을 켜게 했어요.

이렇게 검사할 수 있는 import와 구현 패턴은 CI가 먼저 잡게 했어요. 권한 확인이 적절한 위치에 있는지, 트랜잭션을 어디까지 묶을지는 계속 코드를 읽고 테스트로 확인해요.

인프라는 초기 비용을 보고 두 서비스와 PostgreSQL을 EC2 한 대에 넣는 쪽으로 정했어요. 대신 장애 범위가 커지고 백업과 복구를 직접 챙겨야 해요. 파일은 S3에 직접 올려 API가 대용량 파일을 받아 처리하는 경로를 줄였고요. 이 비용과 운영 판단은 [인프라 글](/ko/blog/사이드-프로젝트-인프라를-ec2-한-대로-시작하기로-한-이유)에 따로 적었어요.
