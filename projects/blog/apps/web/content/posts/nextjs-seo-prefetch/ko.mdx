<Summary>

예약 상세 페이지는 브라우저에서 멀쩡했지만, 서버가 처음 보낸 HTML에는 병원 정보가 없었어요. 검색엔진 크롤러가 먼저 받는 것도 그 HTML이에요. 원인은 서버에서 조회를 시작만 하고 기다리지 않은 데 있었어요. prefetch를 시작한 것과 서버가 데이터를 넘길 준비가 된 것은 달랐어요.

</Summary>

서버가 처음 보낸 HTML을 열어 보니 병원 정보가 없었어요. 브라우저에서 예약 상세를 열면 잘 보여서 조회가 잘된 줄 알았던 화면이에요.

브라우저 화면만 봐서는 이 차이가 보이지 않아요. 눈에 보이는 건 JavaScript까지 실행된 결과이고, 크롤러가 주소를 요청해 먼저 받는 건 서버의 첫 HTML이에요. Google은 크롤링 뒤 별도 단계에서 JavaScript를 렌더링하지만, [Google 문서](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)도 모든 봇이 JavaScript를 실행하지는 못한다고 적어요. 검색 결과에 나와야 할 내용은 첫 HTML에 들어 있는 편이 안전해요.

이 페이지는 Next.js 서버 컴포넌트에서 TanStack Query로 병원 정보를 미리 조회하고 있었어요. 서버 컴포넌트가 `prefetchQuery`를 부른 다음 언제 `dehydrate`하는지 확인했어요.

```tsx
void queryClient.prefetchQuery(hospitalOptions(hospitalId));

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <ReservationPageView />
  </HydrationBoundary>
);
```

순서를 풀면 이래요. `prefetchQuery`는 서버의 `QueryClient` 캐시에 조회 결과를 미리 넣어요. `dehydrate`는 그 캐시를 브라우저로 보낼 수 있는 값으로 꺼내고, `HydrationBoundary`는 그 값을 아래 화면이 쓰는 캐시에 채워요. 아래 화면은 서버에서 HTML을 만들 때 한 번 렌더되고, 브라우저에서 다시 실행되며 그 HTML을 이어받아요. 이 이어받기가 hydration이에요. 서버에서 렌더될 때 캐시에 데이터가 있어야 HTML에 병원 정보가 실려요.

그런데 이 코드는 `prefetchQuery`를 시작만 하고 결과를 기다리지 않아요. `void`는 이 Promise를 기다리지 않겠다고 표시한 거예요. 조회가 끝나기 전에 `dehydrate`하면 기본 설정상 아직 pending인 쿼리는 빠져요. 기본 규칙이 성공한 쿼리만 고르거든요. 화면이 정상처럼 보인 건 브라우저가 다시 조회한 덕분이고, 처음 HTML에 데이터가 실린 것은 아니었어요.

## `await` 뒤에 dehydrate

초기 HTML에 필요한 조회는 `await`로 기다렸어요. Next.js 15에서는 주소의 쿼리 문자열을 담은 `searchParams`도 Promise라 먼저 읽어 조회 옵션을 만들어요.

```tsx
interface Props {
  searchParams: Promise<{
    hospitalId?: string;
  }>;
}

export default async function ReservationPage({ searchParams }: Props) {
  const { hospitalId } = await searchParams;

  if (!hospitalId) notFound();

  const queryClient = getQueryClient();
  await queryClient.prefetchQuery(
    hospitalOptions(Number(hospitalId)),
  );

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ReservationPageView />
    </HydrationBoundary>
  );
}
```

조회가 성공하면 `await` 뒤의 `dehydrate`가 결과를 포함해요. 서버 렌더가 그 캐시를 읽으니 HTML에도 병원 정보가 들어갈 수 있어요. 대신 이 조회가 느리면 페이지의 HTML도 그만큼 늦어져요.

실패는 따로 봐야 해요. `prefetchQuery`는 실패를 호출부로 던지지 않아서, 서버에서 `notFound`나 오류 응답을 결정할 조회라면 `fetchQuery`의 결과와 실패를 직접 처리해야 해요. 검색 결과에 쓰일 제목과 설명을 만드는 `generateMetadata`도 page의 `QueryClient`를 자동으로 공유하지 않아, 두 곳의 조회를 묶으려면 따로 구성해야 해요.

## `void`로 둬도 되는 조회

그렇다고 `void`가 보이면 무조건 `await`를 빠뜨린 것은 아니에요. 모든 데이터를 같은 시점까지 기다릴 필요는 없거든요. 스트리밍은 서버가 HTML을 한 번에 보내지 않고 준비된 부분부터 이어서 보내는 방식이에요. TanStack Query가 pending인 쿼리도 직렬화하게 하면, 조회가 진행 중인 상태를 넘기고 스트리밍할 수 있어요.

```typescript
const queryClient = new QueryClient({
  defaultOptions: {
    dehydrate: {
      shouldDehydrateQuery: (query) =>
        defaultShouldDehydrateQuery(query) ||
        query.state.status === 'pending',
    },
  },
});
```

이때는 화면에서도 같은 쿼리를 `useSuspenseQuery`로 구독해요. 아직 준비되지 않은 영역은 Suspense가 대체 화면으로 처리하므로 서버에서 prefetch 완료를 먼저 기다리지 않아도 돼요.

```tsx
void queryClient.prefetchQuery(hospitalOptions(hospitalId));

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <Suspense fallback={<ReservationSkeleton />}>
      <ReservationPageView />
    </Suspense>
  </HydrationBoundary>
);
```

첫 줄은 맨 처음 코드와 똑같아요. 그래서 `void` 한 줄로 판단하지 않고, 이 화면에서 데이터가 필요한 시점과 dehydration 설정, 소비하는 컴포넌트를 함께 봐요.

| 상황 | 선택 |
| --- | --- |
| 초기 HTML에 반드시 필요한 핵심 데이터 | `await prefetchQuery` |
| 서버에서 not-found나 오류를 결정해야 하는 데이터 | `fetchQuery` 결과와 실패를 서버에서 처리 |
| 화면 일부를 Suspense로 늦게 보여줘도 되는 데이터 | pending dehydration + streaming |
| interaction 뒤에만 필요한 데이터 | client query |

캐시를 전달하는 `HydrationBoundary`도 무조건 한곳으로 모으지는 않아요. 여러 서버 컴포넌트가 각자 조회한 데이터를 가까운 클라이언트 화면에 넘길 수 있어요. 같은 쿼리와 state를 반복해서 전달하는 경우인지 보고 합칠지를 정해요.

## sitemap에 주소가 있어도

sitemap은 검색엔진에 페이지 주소를 알려 줘요. 크롤러는 그 주소를 다시 요청해서 HTML을 읽어요. 그 주소에서 받은 HTML에 병원 정보가 있는지는 페이지 쪽에서 확인해야 했어요. 이 문제에서 바꿀 곳도 sitemap이 아니라 서버의 조회와 `dehydrate` 순서였어요.
