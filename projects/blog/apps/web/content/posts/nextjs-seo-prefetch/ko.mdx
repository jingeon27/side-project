<Summary>

브라우저에는 보이지만 초기 HTML에는 없던 데이터를 확인했어요. 서버에서 조회를 기다릴 때와 pending query를 스트리밍할 때를 나눴어요.

</Summary>

예약 상세를 브라우저로 열면 병원 정보가 보였는데 초기 HTML에는 없었어요. 서버 컴포넌트의 prefetchQuery 호출과 dehydrate가 실행되는 시점을 따라가 봤어요.

```tsx
void queryClient.prefetchQuery(hospitalOptions(hospitalId));

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <ReservationPageView />
  </HydrationBoundary>
);
```

이 코드에서는 prefetch가 끝나기 전에 dehydrate가 실행될 수 있어요. 기본 설정은 성공한 쿼리만 직렬화하므로 pending인 쿼리는 빠져요. 브라우저가 다시 조회하면 화면은 보이지만, 처음 받은 HTML에는 데이터가 없는 상태가 될 수 있어요.

## 초기 HTML에 필요한 데이터는 기다려요

Next.js 15의 page에서는 searchParams도 Promise로 받아요.

```tsx
interface Props {
  searchParams: Promise<{
    hospitalId?: string;
  }>;
}

export default async function ReservationPage({ searchParams }: Props) {
  const { hospitalId } = await searchParams;

  if (!hospitalId) notFound();

  const queryClient = getQueryClient();
  await queryClient.prefetchQuery(
    hospitalOptions(Number(hospitalId)),
  );

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ReservationPageView />
    </HydrationBoundary>
  );
}
```

조회가 성공하면 await 다음의 dehydrate에 결과가 포함돼요. 다만 TanStack Query v5의 prefetchQuery는 실패를 호출부로 던지지 않아요. 서버에서 notFound나 오류를 직접 결정해야 한다면 fetchQuery로 결과와 실패를 받아 처리해야 해요. generateMetadata도 page의 QueryClient를 자동으로 공유하지 않으므로, 두 조회를 공유하려면 별도 구성이 필요해요.

## pending query를 스트리밍할 수도 있어요

TanStack Query는 pending query도 직렬화하도록 설정해 스트리밍할 수 있어요.

```typescript
const queryClient = new QueryClient({
  defaultOptions: {
    dehydrate: {
      shouldDehydrateQuery: (query) =>
        defaultShouldDehydrateQuery(query) ||
        query.state.status === 'pending',
    },
  },
});
```

이 설정과 함께 소비하는 컴포넌트가 useSuspenseQuery로 같은 쿼리를 구독한다면, 서버에서 완료를 기다리지 않고 Suspense로 넘길 수 있어요.

```tsx
void queryClient.prefetchQuery(hospitalOptions(hospitalId));

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <Suspense fallback={<ReservationSkeleton />}>
      <ReservationPageView />
    </Suspense>
  </HydrationBoundary>
);
```

호출에 void가 붙었는지만으로 판단하지 않고, 서버가 어느 시점까지 데이터를 준비해야 하는지 봐요.

| 상황 | 선택 |
| --- | --- |
| 초기 HTML에 반드시 필요한 핵심 데이터 | await prefetchQuery |
| 서버에서 not-found나 오류를 결정해야 하는 데이터 | fetchQuery 결과와 실패를 서버에서 처리 |
| 화면 일부를 Suspense로 늦게 보여줘도 되는 데이터 | pending dehydration + streaming |
| interaction 뒤에만 필요한 데이터 | client query |

## sitemap과 페이지 HTML은 따로 확인해요

sitemap은 검색엔진에 URL을 알려 줘요. 크롤러가 그 주소를 요청해 받은 HTML에 필요한 콘텐츠가 있는지는 별도로 확인해야 해요. 이번에 확인한 문제도 sitemap 자체가 아니라 페이지의 초기 HTML에 있었어요.

서로 다른 서버 컴포넌트가 각자 준비한 캐시를 가까운 클라이언트 화면에 전달하면 HydrationBoundary도 여러 개일 수 있어요. 같은 쿼리와 state를 반복해서 전달하는지 확인한 뒤 경계를 합칠지 결정해요.

처음 HTML에 필요한 데이터만 기다리고, 늦게 보여 줘도 되는 영역은 스트리밍하도록 나눴어요. 서버가 실패까지 처리해야 하는 조회는 prefetch와 구분해서 사용하고요.
