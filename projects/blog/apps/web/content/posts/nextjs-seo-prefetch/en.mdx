I opened the HTML the server sent first, and the hospital information wasn't in it. The reservation detail page showed it fine in the browser, so the query had seemed to work.

The browser hides this difference. What you see on screen is the result after JavaScript has run, while a crawler requesting the address first receives the server's initial HTML. Google renders JavaScript in a separate step after crawling, and [its documentation](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) also notes that not all bots can run JavaScript. Content that should appear in search results is safer in that first HTML.

This page used TanStack Query in a Next.js Server Component to fetch hospital information ahead of time. I checked when the Server Component called `dehydrate` after starting `prefetchQuery`.

```tsx
void queryClient.prefetchQuery(hospitalOptions(hospitalId));

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <ReservationPageView />
  </HydrationBoundary>
);
```

Here is the intended order. `prefetchQuery` puts a result into the server's `QueryClient` cache ahead of time. `dehydrate` extracts that cache as a value that can travel to the browser, and `HydrationBoundary` fills the cache used by the screen below it with that value. That screen renders once on the server to produce HTML, then runs again in the browser and takes the HTML over. That takeover is hydration. The hospital information reaches the HTML only if the cache has data during the server render.

But this code starts `prefetchQuery` without waiting for the result. The `void` marks the Promise as deliberately not awaited. If `dehydrate` runs before it finishes, the default policy leaves the pending query out, since it selects only successful queries. The screen looked right because the browser fetched again, and that doesn't mean the data was in the initial HTML.

## `await`, then dehydrate

I awaited the query the initial HTML needed. In Next.js 15, `searchParams`, which holds the address's query string, is also a Promise and has to be read before building the query options.

```tsx
interface Props {
  searchParams: Promise<{
    hospitalId?: string;
  }>;
}

export default async function ReservationPage({ searchParams }: Props) {
  const { hospitalId } = await searchParams;

  if (!hospitalId) notFound();

  const queryClient = getQueryClient();
  await queryClient.prefetchQuery(
    hospitalOptions(Number(hospitalId)),
  );

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ReservationPageView />
    </HydrationBoundary>
  );
}
```

On success, `dehydrate` after the `await` includes the result. The server render reads that cache, so the hospital information can reach the HTML. The cost is that a slow query delays the page's HTML by as much.

Failure is a separate matter. `prefetchQuery` does not throw to its caller, so when the server has to decide on `notFound` or an error response, it needs `fetchQuery` and direct handling of the result and the failure. `generateMetadata`, which produces the title and description search results can use, does not automatically share the page's `QueryClient` either, and tying those reads together takes separate configuration.

## Queries that can stay `void`

A `void` doesn't automatically mean a missing `await`, because not every piece of data has to be ready at the same point. Streaming means the server sends HTML in parts as they become ready instead of all at once. If TanStack Query also serializes pending queries, an in-progress query can be passed along and streamed.

```typescript
const queryClient = new QueryClient({
  defaultOptions: {
    dehydrate: {
      shouldDehydrateQuery: (query) =>
        defaultShouldDehydrateQuery(query) ||
        query.state.status === 'pending',
    },
  },
});
```

The screen then subscribes to the same query with `useSuspenseQuery`. Suspense shows a fallback for the region that isn't ready, so the server doesn't have to wait for prefetch to finish first.

```tsx
void queryClient.prefetchQuery(hospitalOptions(hospitalId));

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <Suspense fallback={<ReservationSkeleton />}>
      <ReservationPageView />
    </Suspense>
  </HydrationBoundary>
);
```

The first line is identical to the code I started with. So I don't judge by the `void` alone. I read it together with when this screen needs the data, the dehydration settings, and the consuming component.

| Situation | Choice |
| --- | --- |
| Essential data that must be in the initial HTML | `await prefetchQuery` |
| Data used to decide not-found or an error on the server | Handle `fetchQuery` results and failures on the server |
| Data that can appear later within Suspense | pending dehydration + streaming |
| Data needed only after an interaction | client query |

`HydrationBoundary` doesn't have to be gathered into one place either. Several Server Components can fetch their own data and pass it to nearby client screens. I check whether the same query and state are being passed repeatedly before combining them.

## A URL in the sitemap

The sitemap tells search engines where a page is. The crawler then requests that address and reads the HTML. Whether the HTML at that address contains hospital information had to be checked on the page itself. The change here belonged in the server's query and `dehydrate` order, rather than the sitemap.
