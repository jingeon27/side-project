I introduced tests to the services I maintain so that features and structural changes could be checked against existing behavior.

The criteria developed through mistakes. Integration tests bypassed real submission code, and mocks accepted requests the server rejected. I wanted to read a passing test and understand what behavior it had actually checked.

I now use unit tests for functions and schemas, actual product code plus MSW for form submission, the dev server for API contracts, and browsers for URL entry and back navigation. Those distinctions came from bugs the tests missed.

## Keep tests beside their subject

I adopted colocated tests from the start.

```text
program-form.tsx
program-form.spec.tsx
program-form.test.tsx
```

Feature requirements go in spec files; production and QA bugs go in test files. Moving or deleting a subject makes its tests visible in the same diff, and changing a feature exposes the behavior to check nearby.

## Integration tests must use real submission code

The first global CMS integration tests rendered form fields but let a Harness perform submission. This example is shortened and renamed for publication.

```tsx
function CreateHarness({ onCreated }: { onCreated: (id: number) => void }) {
  // 등록 Drawer가 하는 변환·요청을 테스트가 다시 쓰고 있었다
  const handleFinish = async (values: PartnerFormValues) => {
    const { id } = await createPartner(toRequest(values));
    onCreated(id);
  };

  return <PartnerFormFields initialValues={initialValues} onFinish={handleFinish} />;
}
```

That duplicated production submission logic. The real creation Drawer could break while the Harness kept passing. I changed the test to render that Drawer and exercise product code from input through submission.

I shared setup such as providers and routers, but left submission decisions in the actual product code. If the test duplicates that logic, one implementation can change while the other still passes.

## A permissive mock was mistaken for the server contract

We developed the global service with MSW before its backend was ready. Handlers returned 200 without inspecting bodies. Connecting global CMS to real APIs revealed rejected creation requests across several domains despite passing integration tests. Partner creation omitted an ordering value with no input UI and failed a business-hours rule requiring all seven days. Program creation omitted a required code the frontend assumed the server generated. Price-policy enum values also differed.

Mock seeds diverged from initial server data. In the global user-facing service, a separate repository from CMS, the All category existed only in mock seeds. E2E passed on the false assumption that the backend supplied it.

I copied only constraints confirmed in backend DTOs and validation into mocks, making them reject with 400 what the server rejected. This reduced example uses `partnerId` as an alias.

```typescript
// 서버 DTO가 거절하는 조건만 옮긴다
function programViolations(body: ProgramSaveRequest): Violation[] {
  const violations: Violation[] = [];
  const required = (field: keyof ProgramSaveRequest, isValid: boolean) => {
    if (!isValid) violations.push({ field, code: 'VALIDATION.REQUIRED' });
  };

  required('partnerId', Boolean(body.partnerId));
  required('programCode', Boolean(body.programCode?.trim()));

  if (body.listPrice < body.salePrice) {
    violations.push({ field: 'validPrice', code: 'VALIDATION.INVALID' });
  }

  return violations;
}

http.post('/programs', async ({ request }) => {
  const body = (await request.json()) as ProgramSaveRequest;
  const violations = programViolations(body);

  if (violations.length > 0) {
    return errorJson(400, 'COMMON.VALIDATION_FAILED', violations);
  }

  return ok({ id: programStore.create(body) });
});
```

`onUnhandledRequest: 'error'` exposes unregistered requests immediately, including new calls from child components. Mocks became a record of the frontend's current understanding of the contract rather than a convenient fake backend.

I then removed the required code from a request and confirmed the existing integration test failed. Live tests against dev APIs passed both fully populated and minimal inputs for each domain. Six days later, I aligned global CMS department, category, language, and region seeds with server initial data. Not one medical-department code had previously overlapped.

Mocks are still not the authoritative contract. New constraints discovered on the dev server feed back into form validation, handlers, and integration tests so subsequent work fails locally first.

## Some passing assertions checked nothing

Colocation alone did not prevent another mistake. Tabs, creation, and Drawer responsibilities moved from a global CMS list View to page.tsx, but tests still rendered the old View alone. Eight tests remained broken because the expected DOM was gone. The assertion that a Drawer was closed without an ID always passed because no Drawer was rendered at all. Five days later, I restored tests beside page.tsx and added an admin AGENTS.md rule to move tests with their responsibility.

A Back-Office banner E2E waited for “Uploading...” to disappear, but the text existed nowhere in the repository. Playwright passed immediately, potentially advancing before the image entered the form. Code review caught it, and I changed the wait to the actual upload-progress entry disappearing.

## Give each test layer a scope

More test types do not inherently mean more safety. Repeating behavior at every layer increases cost, and ignoring each layer's limits encourages overconfidence.

The responsibilities are:

- Unit tests: pure functions, Zod schemas, state transitions, and boundary values.
- Component/integration tests: connections among actual UI, Query, forms, and MSW contracts.
- `.live.test.ts(x)`: request/response compatibility with dev API contracts.
- Playwright E2E: browser-specific URL entry, refresh, back navigation, cookies, and server gates.

I do not force Server Components or heavily provider-dependent screens into jsdom. I extract pure calculations for unit tests or use E2E when the browser is essential.

## Prefer dev APIs and mock difficult states

When a feature can be checked against dev APIs, I start there to see actual contracts and data connected. Mocks fix conditions that are difficult to create safely and repeatedly there, such as authentication stages, particular errors, and empty lists.

The portal signup E2E does not mock everything. MSW controls user state and authentication requests that the test needs to own; other requests reach the dev server.

The admin monorepo runs `*.live.test.ts(x)` through a separate configuration from ordinary Vitest. Running them with MSW enabled could masquerade as real-server verification. Dev accounts and data are shared, so files run serially and automation does not arbitrarily modify other people's data.

Discovering a contract difference does not mean adding only live tests. Confirmed constraints return to local mocks and existing tests. Live tests discover differences; they are not the layer carrying the largest scenario count.

Global CMS is an exception. When its dev-API runner was removed later, I deleted live files that could no longer run. Leaving them would imply ongoing verification. It now checks server rules through the updated mocks only.

## Confirm that a new test can fail

For a new testing pattern, I deliberately broke the behavior it was intended to protect. A payment calculation might look like this.

```typescript
// 정상
const finalAmount = paymentAmount - couponDiscount;

// 테스트 확인을 위해 잠시 변경
const finalAmount = paymentAmount + couponDiscount;
```

After observing failure, I restored product code. Removing the required API code earlier was the same check. I distinguish adding a test from confirming it catches a regression, and documented this mutation-check principle in admin AGENTS.md.

Refactoring order matters too: preserve current behavior in tests before changing structure. Writing tests afterward can simply declare the new behavior correct.

## Put browser boundaries in E2E

The portal signup funnel combines direct URL entry, refresh, back navigation, and authentication. Function tests cannot easily cover that combination. Playwright checks ordinary progression, direct entry midway, returning after logout, and blocked popups.

The right URL alone is insufficient. Logout can navigate to login while displaying an error page.

```typescript
await page.getByRole('button', { name: '로그아웃' }).click();

await expect(page).toHaveURL(/\/sign(\?|$)/);
await expect(page.getByRole('button', { name: '카카오로 계속하기' })).toBeVisible();
```

Checking both destination and visible screen makes broken guards or rendering fail. The value comes from asserting what users see.

Cross-app flows get cross-app E2E. Program registration/review requests in hospital admin and Back-Office review initially had no tests. After introducing the framework, I added registration through under-review status, rejection, and approval, running both apps against dev APIs. [The AI workflow article describes this work.](/en/blog/plan-gated-ai-workflow)

I choose the environment around the problem. Storefront E2E defaults to the Next development server. A build-then-start path also exists, but concurrent requests to cookie-reading statically generated routes kept it from becoming the default. The Back-Office search error did not appear under dev and needed build followed by start to reproduce, as [described here](/en/blog/nextjs-server-client-issues).

## Leave repetition when it exposes the important behavior

In tests, I prioritize readable scenarios over sharing every repeated action. This portal search E2E is shortened; the real test also checks event delivery, and helper names are changed.

```typescript
await gotoSearchPage(page);

await page.getByRole('button', { name: '특가전', exact: true }).click();

await expect(page).toHaveURL(/hasEvent=true/);
```

Clicking filters and checking URLs repeats elsewhere, but I do not hide those core actions in a generic `expectFilterScenario()`. Only unrelated preparation such as navigation and login is hidden. Reading inputs, actions, and expected results directly helps me assess the meaning of an AI-reported success.

## Distinguish specifications from bug reproduction

New requirements use BDD-style `*.spec.ts` or `*.spec.tsx`, showing conditions, actions, and visible results. I check each component's requirements for omissions. Production/QA errors and console warnings are reproduced in `*.test.ts` or `*.test.tsx` to prevent recurrence.

I read agent-written product code and tests: does setup replace submission behavior, or does an assertion pass without its subject? Missing specification conditions go back to the agent, and I recheck both code and tests.

Custom lint rules also get RuleTester, `__fixture__`, and mock environments. A rule enforcing repository conventions can reject valid code or miss violations itself.

## Avoid repeating full verification across parallel worktrees

Running full lint, typecheck, and tests in several worktrees caused CPU contention. One admin lint run spans many packages, and each linked worktree creates its own Turbo and TypeScript caches. Overlapping runs were killed, leaving neither a pass nor a failure to interpret.

During work I verify affected changes first, then inspect full CI. The current sequence is:

Ticket/plan review → tests → agent implementation/review → affected tests/lint/typecheck → my diff review → actual screen checks → full CI (tests, Knip, lint) → QA double check

Failures return to the relevant earlier stage. Tests can define when an agent stops editing, but I consider the work finished only after code and screen review too.

Local scope differs by tool. ESLint checks changed files, tests cover affected files, and Knip checks the full reference graph in both repositories. Typechecking covers the whole portal app, but changed packages in admin; changing a shared package API also checks consuming apps. Calling that “typecheck changed files” would miss dependencies.

This reduces simultaneous full checks across sessions. Narrow local checks still receive final CI and screen verification.

## CI scope follows its environment

Admin PR Vitest initially ran all MSW tests, but the runner shared an instance with dev, and those runs stopped the dev environment too. MSW integration tests moved to affected pre-push checks.

Admin CI now runs lint, typecheck, Knip, and tests without MSW. Dev-API live tests run separately without blocking PRs because server deployments and data changes can cause failures; I inspect results for contract differences. Portal CI runs lint, typecheck, and Knip. Both repositories check E2E outside CI.

The criteria continue to change. New features add conditions, missed bugs add regression tests, and code changes prompt a check that tests still exercise their subjects. Each task leaves more precise things to verify next time.
