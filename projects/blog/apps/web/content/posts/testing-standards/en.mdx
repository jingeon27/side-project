We built the global service with MSW before its backend was ready. MSW is a library that intercepts HTTP requests from an app at the network level and returns responses you wrote in advance, and the functions that decide those responses are called handlers. Our handlers returned 200 without inspecting the body. Integration tests passed, and once connected to the real API, those requests were rejected.

An integration test runs forms, data fetching, and request code connected for real, with MSW standing in only for the server. When that server accepts anything, a wrong request body gives the test no reason to fail.

I introduced tests to the services I maintain because checking every existing behavior by hand became difficult as I added features and changed structure. But passing tests still accompanied requests rejected by the server, and assertions kept succeeding after their subject had disappeared from the screen. Before adding more tests, I began rereading what they actually ran, and the criteria I use now came from repairing those gaps.

The apps in this article split like this. The benefits portal is the service where users find and book hospital programs. Hospital admin, the operations team's Back-Office, and global CMS, the global service's admin screen, live together in the admin monorepo.

## Mocks reject what the server rejects

A mock is any fake used in place of the real thing. Swapping out a function or module is a mock, and MSW standing in for a server is a mock too. With MSW, the app's request code still runs as it is. In this article, a mock mostly means an MSW handler.

When global CMS was connected to the real API, registration requests that had passed every integration test were rejected across several domains. Shortened, the handlers looked like this.

```typescript
// A shortened example. It never reads the body and answers success to anything.
http.post('/programs', () => ok({ id: 1 }));
```

The rejections came from constraints the mock did not know about. Partner creation required an ordering value with no input in the UI and business hours for all seven days. Program creation required a code the frontend thought the server generated and so never sent, and the price-policy enum names differed too. A mock returning only success could not expose those differences.

Mock seeds, the initial data a mock answers with, had also grown apart from the server's initial data. In the global user-facing service, a separate repository from CMS, the All category tab existed only in mock seeds. E2E was passing on the false assumption that the tab came from the server. E2E tests open the app in a real browser and operate it as a user would, and we use Playwright for them.

So I copied only constraints confirmed in backend DTOs (code defining the request shape the server accepts) and validation into the mocks, making them answer 400 to whatever the server rejects. This example is shortened for publication, and `partnerId` is an alias.

```typescript
// Include only the conditions rejected by the server DTO
function programViolations(body: ProgramSaveRequest): Violation[] {
  const violations: Violation[] = [];
  const required = (field: keyof ProgramSaveRequest, isValid: boolean) => {
    if (!isValid) violations.push({ field, code: 'VALIDATION.REQUIRED' });
  };

  required('partnerId', Boolean(body.partnerId));
  required('programCode', Boolean(body.programCode?.trim()));

  if (body.listPrice < body.salePrice) {
    violations.push({ field: 'validPrice', code: 'VALIDATION.INVALID' });
  }

  return violations;
}

http.post('/programs', async ({ request }) => {
  const body = (await request.json()) as ProgramSaveRequest;
  const violations = programViolations(body);

  if (violations.length > 0) {
    return errorJson(400, 'COMMON.VALIDATION_FAILED', violations);
  }

  return ok({ id: programStore.create(body) });
});
```

The agreement on what a server accepts and what it answers is called a contract. After this change, the mock became the place that records the contract as the frontend currently understands it.

I also set `onUnhandledRequest: 'error'` so a request without a handler does not slip through quietly. If a child component starts calling a new API as the screen opens, the test fails right there, which exposes calls outside the contract written into the mock.

After changing the mock, I removed the program code from a request and the existing integration test failed. I also sent fully populated and minimal inputs to the dev API, the real backend in the development environment, to check the contract. Later I aligned department, category, language, and region seeds with the server's initial data, and found that the old department codes had not matched any server code.

Mocks are still not the authoritative contract. New constraints found on the dev API server go back into form validation, handlers, and integration tests so that later work fails locally first.

## Submission belongs to the product code

The first global CMS integration tests had another gap. They rendered form fields but let a Harness perform the submission. A Harness is a helper component built on the test side to run the subject. This example is shortened and renamed for publication.

```tsx
function CreateHarness({ onCreated }: { onCreated: (id: number) => void }) {
  // The test duplicated the registration drawer's conversion and request logic
  const handleFinish = async (values: PartnerFormValues) => {
    const { id } = await createPartner(toRequest(values));
    onCreated(id);
  };

  return <PartnerFormFields initialValues={initialValues} onFinish={handleFinish} />;
}
```

It looked convenient, but the successful submission belonged to the Harness. The real creation Drawer never ran. Product conversion or request code could break while the copied test implementation stayed correct and passing. I changed the test to render the real Drawer so input through submission follows the same code. Here is the structure in reduced form.

```tsx
// A shortened example. Render the real Drawer, then type and submit as a user would.
render(<PartnerCreateDrawer open onCreated={onCreated} />, { wrapper: TestProviders });

await user.type(screen.getByLabelText('Partner name'), 'Test partner');
await user.click(screen.getByRole('button', { name: 'Create' }));

await waitFor(() => expect(onCreated).toHaveBeenCalled());
```

I shared setup such as providers and routers. What gets sent to the server, and when, had to stay with the actual product code. If a test rewrites submission, changing either implementation alone can leave the test passing.

## Assertions that checked nothing

Tests live beside their subject, so the tests describing a behavior are right there to read when the file changes.

```text
program-form.tsx
program-form.spec.tsx
program-form.test.tsx
```

Requirements for a new feature go in BDD style in `*.spec.ts` or `*.spec.tsx`, showing what should appear when someone takes a given action under a given condition, and I check that each component's needed behavior is covered. Functional errors and console warnings found in production or QA are reproduced in `*.test.ts` or `*.test.tsx` so the same problem does not come back. Moving or deleting a file makes its tests visible in the same diff.

Sitting next to the code did not make tests follow a moved responsibility, though. Tabs, creation, and the Drawer moved from the global CMS list View up to `page.tsx`, while the tests still rendered only the View. Tests expecting the old DOM broke, but the check that the Drawer stays closed without an ID kept passing. No Drawer existed at all, so "closed" was trivially true. Shortened, such an assertion looks like this.

```tsx
// A shortened example. queryByRole returns null when nothing matches, so this always passes.
render(<PartnerListView />);

expect(screen.queryByRole('dialog')).not.toBeInTheDocument();
```

I moved the behaviors the page had taken on into tests beside `page.tsx`. Moving code now also means checking that its tests render the actual component in its new location. I wrote "when a responsibility moves, its tests move with it" into the admin service's AGENTS.md, the repository guidance coding agents read, as a working principle.

E2E had a line like this too. A Back-Office banner E2E waited for "Uploading..." to disappear, but the text existed nowhere in the repository, so Playwright passed immediately. Playwright's hidden assertion counts a missing element as success. A reduced example follows.

```typescript
// A shortened example. Text that does not exist counts as hidden, so this passes at once.
await expect(page.getByText('Uploading...')).toBeHidden();
```

The test could advance before the image value reached the form. Code review caught it, and I changed the wait to the actual upload-progress entry disappearing.

## Break a new pattern on purpose once

For a new testing pattern, I deliberately broke the product code behind the behavior it was meant to protect. A payment calculation might look like this.

```typescript
// Original behavior
const finalAmount = paymentAmount - couponDiscount;

// Temporary change used to verify the test
const finalAmount = paymentAmount + couponDiscount;
```

After seeing the failure, I restored the product code. Removing the program code earlier was the same kind of check. I apply this mutation check to new patterns to avoid a test staying green when it shares the implementation's mistake. It separates "I added a test" from "I confirmed the test catches a regression." This check also went into AGENTS.md as a principle.

In refactoring, order mattered too. I pinned current behavior in tests first and changed the structure after. Tests written after the change can simply declare the new behavior correct.

## The URL can be right while the screen is broken

After logout, the address can change to the login page while the screen shows an error page. So the right URL alone did not count as success.

```typescript
await page.getByRole('button', { name: 'Sign out' }).click();

await expect(page).toHaveURL(/\/sign(\?|$)/);
await expect(page.getByRole('button', { name: 'Continue with Kakao' })).toBeVisible();
```

The test checks both that the address changes to login and that the Kakao button is visible. That separates a redirect that succeeded from one followed by a broken guard or screen render.

Boundaries like this only show in a browser. The portal signup funnel combines direct URL entry, refresh, back navigation, and authentication state, and function tests alone could not easily cover that combination. Along with ordinary progression, Playwright checks entering a midway URL directly, coming back after logout, and blocked popups.

Flows that do not end in one app get E2E across both apps. Program registration and review requests in hospital admin and the Back-Office review screen had no tests when first built. After bringing in the test setup, I added E2E from registration through under-review status, rejection, and approval, running both apps against the dev API server. [The AI workflow article describes the process.](/en/blog/plan-gated-ai-workflow)

I also chose the environment to fit the problem. Portal E2E starts the Next development server by default. A build-then-start path exists too, but a concurrent request problem on cookie-reading statically generated routes kept it from becoming the default. The Back-Office search error did not appear under dev, so I confirmed it with build followed by start, as [recorded here](/en/blog/nextjs-server-client-issues).

## What each test actually runs

Correct calculations that break on browser back navigation, and a mock accepting what the server contract forbids, are not caught by the same test. Repeating one behavior in several places only adds run time, so I divided the scopes by what each test actually executes.

- Unit tests check pure functions, Zod schemas, state transitions, and boundary values.
- Component and integration tests check that actual UI, Query, forms, and MSW contracts connect. They run in jsdom, which imitates the DOM on Node, in place of a browser, and MSW takes the server's place.
- `.live.test.ts(x)` checks that requests and responses match the dev API server's contract. These are contract tests that send requests to a real server.
- Playwright E2E handles flows that appear only in a browser, such as direct URL entry, refresh, back navigation, cookies, and server gates.

I do not force Server Components or heavily provider-dependent screens into jsdom. I extract the calculation into a pure function for unit tests, or move the problem to E2E when it needs a real browser.

When a feature can be checked on the dev API server, I start there, because it shows the API contract and data actually connected. Mocks pin conditions that are hard to create safely and repeatedly there, such as login stages, particular error responses, and empty lists. The portal signup E2E does not mock every request either. MSW handles only what the test has to control directly, such as user state and authentication flows, and other requests go to the dev API server.

The admin monorepo separates tests that need the dev API server from ordinary Vitest runs, using `*.live.test.ts(x)` and a separate configuration. Running live tests with MSW on, like ordinary tests, could make it look as if the server had been verified. Accounts and data on the dev API server are shared, so files run serially and flows that arbitrarily change other people's data are not automated.

A constraint found through the dev API does not stay only in a live test. It goes back into local form validation, mocks, and integration tests, so the next change can catch the same bad request without reaching the dev server. Live tests are for finding contract differences, and I did not make them the place that runs the most scenarios.

There is an exception. When global CMS later removed its dev API test runner, I deleted the live test files that could no longer run. Leaving them would suggest that contract was still being checked. It now relies only on mocks carrying the server's rules.

## Keep the core action out of helpers

Product code often gets reviewed for shared helpers, but in tests I put reading a scenario at a glance first. So I sometimes leave repeated clicks visible. This part of the portal search E2E presses a filter and checks the URL. The helper is renamed here, and the real test also checks event delivery.

```typescript
await gotoSearchPage(page);

await page.getByRole('button', { name: 'Special offers', exact: true }).click();

await expect(page).toHaveURL(/hasEvent=true/);
```

Pressing filters and checking URLs repeats in other tests, but I do not hide the core action in a generic helper like `expectFilterScenario()`. Only preparation outside the test's concern, such as navigation and login, gets hidden. Reading input, action, and expected result directly from the test name and body is what lets me quickly check what an AI-reported "success" means.

When an agent writes both product code and tests, I read them myself and look again for setup that replaces submission and assertions that pass without a subject. Those are the two cases I already missed, so I compare against the actual code instead of accepting only the test result. If the specification is missing a condition, I add it and check again.

Custom lint rules also get verified through RuleTester, `__fixture__`, and mocks that build a test environment. Code that enforces repository conventions can wrongly block valid code or miss violations too.

## Running full checks across several worktrees

A worktree is a git feature that checks out one repository into several folders at once. Running full lint, type checks, and tests in several worktrees at once caused heavy CPU contention. In the admin monorepo, one full lint run spans many packages, and each linked worktree rebuilds its own Turbo and TypeScript caches. Overlapping checks actually got processes killed, leaving no way to tell whether something had passed or failed.

So I changed the order. During work, I check what changed first so agent fixes and review can continue. I read the result in the diff and try the screen myself before moving to full CI and QA. That keeps several sessions from starting full checks at the same time at every step.

```text
Ticket and plan review
  → Write tests
  → Agent implementation and agent code review
  → Tests, lint, and typecheck on what changed
  → My diff review
  → Open the screen and check behavior
  → Full CI (tests, Knip, lint)
  → Request a QA double check
```

When a problem appears at any stage, the work goes back to the earlier stage that fits the cause. Tests also serve as the condition for an agent to finish a fix, but I count the work as done only after code review and checking the real screen.

Local verification scope also differs by tool. ESLint looks only at changed files, tests only at those tied to changed files, and Knip, which finds unused code, at the full reference graph in both repositories. Type checking covers the whole app in the portal and the package holding the changed file in the admin service, and changing a shared package's API also checks the apps using it. Describing type checks as "changed files only" would miss those dependencies.

## What stayed in CI and what stayed out

I adjusted what runs automatically to fit the operating environment as well. I added Vitest PR checks to the admin service, but the CI runner shared an instance with the dev environment, and MSW tests across all packages brought the dev environment to a halt too. So MSW integration tests moved to the affected-change checks before push.

Admin CI now runs lint, type checks, Knip, and tests that do not use MSW. Dev API live tests run separately. Server deployments or data changes can also break them, so they do not block PRs, and I read their results for contract differences. Portal CI runs lint, type checks, and Knip. E2E for both repositories is checked outside CI.
