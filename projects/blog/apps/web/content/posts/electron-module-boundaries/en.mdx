A month into the job I picked up a new recruiting platform, and my first move was to copy an existing file. That was how the Electron app was growing at the time: copy a file, change the selectors and exception handling.

The app collects applicants from several recruiting platforms, using data the company is authorized to access through its corporate accounts. It logs in to a platform, reads the applicant list, filters out people already saved, then registers the new applicants and uploads their resume files.

Electron builds desktop apps with web technology and splits them into two kinds of process. The main process is the entry point and runs in Node.js. Each window gets a renderer process that draws a web page, and by default a renderer cannot reach Node.js APIs directly. So when the screen asks for a collection run, it sends a message to main over IPC (inter-process communication), and main does the work.

That work goes through Puppeteer, a Node.js library that drives a browser from code: opening pages, filling inputs, and finding DOM elements with CSS selectors. Every site has its own login screen and DOM structure, so the selectors differ from site to site.

The function I was about to copy held this whole sequence from start to finish.

```text
Login
  -> Collect the list
  -> Check for duplicates
  -> Register applicants
  -> Download and upload files
```

Reduced to its shape, each platform file had a function like the one below. I rewrote it to show the structure only, so the names and selectors differ from the real code.

```typescript
export async function collectPlatformA(page: Page) {
  // Differs per site
  await page.goto(PLATFORM_A_LOGIN_URL);
  await page.type('#login-id', account.id);
  await page.type('#login-password', account.password);
  await page.click('#login-button');
  const candidates = await page.$$eval('.candidate-row', readCandidateRows);

  // Same on every site
  const newCandidates = await removeDuplicates(candidates);
  await saveCandidates(newCandidates);
  await uploadResumes(newCandidates);
}
```

Login and DOM structure differed from site to site, but the order did not: log in, check duplicates, save applicants, upload resumes. Site-specific code and code common to every site sat in the same function, and changing the order meant editing every platform file together. Copying it again would bring a fourth platform and a fourth copy of the post-login workflow.

## Requests, collection order, and site handling

I happened to be reading the backend team's NestJS code at the time, looking at what Controllers and Services did. NestJS is a Node.js server framework that puts receiving HTTP requests in a Controller and the actual processing in a Service. I borrowed that split for the collector: one place receives IPC requests, one runs the collection order, and one holds whatever differs per site. The files were divided by what has to change when something changes.

- Change the Controller when the IPC request changes.
- Change `CrawlingService` when the overall processing order changes.
- Change a platform's adapter when its DOM or login method changes.

## NestJS lasted five days

I initially introduced NestJS itself. In NestJS you mark a class with a decorator such as `@Injectable()`, and the framework's DI container finds the dependencies listed in a constructor, creates the instances, and passes them in. The CTO rejected it as too much framework to add to Electron's main process. I removed the dependency five days after adding it, and neither decorators nor a DI container stayed behind.

Removing the framework did not send the files back together, because separating requests, collection order, and site handling never required a container. Passing `PuppeteerService` through a constructor and assembling it in a Factory (a function that builds and returns an instance) was enough. I now write the instance assembly a container would have done, and the main process carries no framework.

## What the split looks like in code

An `ipcMain` handler receives the app's requests. A request the renderer sends with `ipcRenderer.invoke` arrives at the function registered with `ipcMain.handle`, and that function's return value becomes the result of the renderer's Promise. I treat this handler as an entry point much like an HTTP Controller. The platform names and some identifiers below are illustrative replacements.

```typescript
const createCrawlingService =
  (puppeteer: PuppeteerService) =>
  (platform: Platform) =>
    new CrawlingService(puppeteer, platform);

export function createCrawlingController(puppeteer: PuppeteerService) {
  const createService = createCrawlingService(puppeteer);

  return {
    collect({ platform }: { platform: Platform }) {
      return createService(platform).collect();
    },
  };
}

const controller = createCrawlingController(puppeteer);
ipcMain.handle('crawl', (_event, req) => controller.collect(req));
```

`createCrawlingService` is a function called twice. It takes `puppeteer` once up front, then takes a platform on each request and builds a `CrawlingService`. This is the assembly code mentioned above.

The Controller obtains the Service for the requested platform and runs it. Login functions and DOM selectors are not here, and the platform list lives elsewhere, so registering another platform does not touch this code. The Service keeps only the processing order.

```typescript
export class CrawlingService {
  constructor(
    private readonly puppeteer: PuppeteerService,
    private readonly platform: Platform,) {}

  async collect() {
    // Exception handling and page cleanup omitted
    const config = CRAWLING_HANDLERS[this.platform];
    const page = await this.puppeteer.open(config.pages.recruit);

    await config.login(page);

    const processor = new config.Processor({ page });
    await processor.collectCandidates();
    await processor.removeDuplicates();
    await processor.saveCandidates();
    await processor.uploadResumes();
  }
}
```

`CrawlingService` uses the `PuppeteerService` it receives to run the shared order. The sequence each platform file used to carry now lives here, in one place. NestJS inspired the constructor injection, but the Factory above creates the actual instance. The per-platform functions come from `CRAWLING_HANDLERS`.

```tsx
abstract class CandidateProcessor {
  abstract collectCandidates(): Promise<void>;
  abstract removeDuplicates(): Promise<void>;
  abstract saveCandidates(): Promise<void>;
  abstract uploadResumes(): Promise<void>;
}

interface CrawlingHandler {
  pages: { recruit: string };
  login: (page: Page) => Promise<void>;
  Processor: new (args: { page: Page }) => CandidateProcessor;
}

const CRAWLING_HANDLERS = {
  platformA: {
    pages: PLATFORM_A_PAGES,
    login: loginPlatformA,
    Processor: PlatformAProcessor,
  },
  platformB: {
    pages: PLATFORM_B_PAGES,
    login: loginPlatformB,
    Processor: PlatformBProcessor,
  },
  platformC: {
    pages: PLATFORM_C_PAGES,
    login: loginPlatformC,
    Processor: PlatformCProcessor,
  },
} as const satisfies Record<Platform, CrawlingHandler>;
```

An abstract class cannot be instantiated on its own. It sets the methods a subclass must implement, and a platform implementation missing one of them fails to compile. `CrawlingService` decides when to call those methods, and the configuration object connects each platform's class and helpers. The trailing `satisfies Record<Platform, CrawlingHandler>` produces a compile error if a platform is left out of the configuration. The shape borrows from a NestJS Module, without runtime DI or decorators.

The example gives `Processor`'s constructor a specific type. In the code at the time, that position was `any`.

## Adding login and parsing for the next platforms

For later platforms, I no longer copied the collection function. The shared order stayed in `CrawlingService`, and I implemented each site's login and parsing and registered them in the configuration.

Two platforms went in this way. One delivered encrypted ZIP resumes. The other needed two-factor authentication and pagination, and handled education, work history, and duplicate applicants in its own way. Those differences went into each platform's implementation. Errors are caught per applicant, so one failure does not stop the rest of the collection.

IPC changes, collection-order changes, and DOM fixes no longer start in the same file. NestJS was gone, but adding a platform stopped meaning a copy of the common sequence.

## Platform functions are still tied to the configuration

This refactor left no automated tests or performance measurements behind. Structurally, Puppeteer arrives through the constructor, so a stand-in can replace it. `CrawlingService` still reads `CRAWLING_HANDLERS` directly from a module, though, so login functions and `Processor` classes cannot be swapped from outside.
