여러 채용 플랫폼에서 지원자 정보를 모으는 Electron 앱에 새 플랫폼을 붙이려고 기존 파일을 복사하려다 멈췄어요. 로그인 뒤의 같은 흐름이 한 벌 더 생기겠더라고요. NestJS를 넣었다가 5일 만에 뺐지만, 요청을 받는 코드와 수집 순서, 사이트별 처리를 나눈 구분은 남았어요.

</Summary>

입사 한 달째, 새 채용 플랫폼을 붙이는 일을 맡아 저도 먼저 기존 파일을 복사하려 했어요. 당시 Electron 앱은 플랫폼을 그렇게 늘리고 있었어요. 파일을 복사하고 selector와 예외 처리를 바꿨어요.

이 앱은 여러 채용 플랫폼에서 지원자 정보를 모아요. 대상은 자사가 각 플랫폼의 기업회원으로서 접근 권한을 가진 지원자 데이터예요. 플랫폼에 로그인해 지원자 목록을 읽고, 이미 저장한 사람을 걸러 낸 뒤 새 지원자를 등록하고 이력서 파일을 올려요.

Electron은 웹 기술로 데스크톱 앱을 만드는 도구이고, 앱을 main 프로세스와 renderer 프로세스로 나눠요. main은 앱의 시작점으로 Node.js에서 돌고, renderer는 창마다 하나씩 떠서 웹 화면을 그려요. renderer는 기본적으로 Node.js API에 바로 닿지 못해서, 화면에서 수집을 요청하면 IPC(프로세스 사이의 메시지 통신)로 main에 보내고 main이 실제 작업을 해요.

그 작업에 쓰는 도구가 Puppeteer예요. 코드로 브라우저를 열고 입력창을 채우고, CSS selector로 페이지의 요소(DOM)를 찾아 읽는 Node.js 라이브러리예요. 사이트마다 로그인 화면과 DOM 구조가 다르니 selector도 사이트마다 달라요.

복사하려던 함수 안에는 이 흐름이 처음부터 끝까지 들어 있었어요.

```text
로그인
  -> 목록 수집
  -> 중복 확인
  -> 지원자 등록
  -> 파일 다운로드 및 업로드
```

줄이면 이런 함수가 플랫폼 파일마다 한 벌씩 있었어요. 구조만 보여 주려고 다시 쓴 예시라 이름과 selector는 실제 코드와 달라요.

```typescript
export async function collectPlatformA(page: Page) {
  // 사이트마다 달라지는 부분
  await page.goto(PLATFORM_A_LOGIN_URL);
  await page.type('#login-id', account.id);
  await page.type('#login-password', account.password);
  await page.click('#login-button');
  const candidates = await page.$$eval('.candidate-row', readCandidateRows);

  // 모든 사이트에 같은 부분
  const newCandidates = await removeDuplicates(candidates);
  await saveCandidates(newCandidates);
  await uploadResumes(newCandidates);
}
```

사이트마다 로그인과 DOM은 달랐지만, 로그인한 뒤 중복을 확인하고 지원자를 저장해 이력서를 올리는 순서는 같았어요. 사이트 때문에 달라지는 코드와 모든 사이트에 같은 코드가 한 함수에 남아 있었고, 순서를 고치면 각 파일을 같이 수정해야 했어요. 여기서 또 복사하면 네 번째 플랫폼과 함께 로그인 뒤의 같은 흐름도 네 벌이 되겠더라고요.

## 요청, 수집 순서, 사이트별 처리

마침 백엔드 팀의 NestJS 코드를 읽으며 Controller와 Service가 하는 일을 보던 때였어요. NestJS는 Node.js 서버 프레임워크인데, HTTP 요청을 받는 일은 Controller에 두고 실제 처리는 Service에 둬요. 그 구분을 수집 앱에 가져와서, IPC 요청을 받는 곳과 수집 순서를 실행하는 곳, 사이트마다 달라지는 곳을 따로 두기로 했어요. 파일을 나눈 기준은 무엇이 바뀌면 어디를 고치느냐였어요.

- IPC 요청이 바뀌면 Controller만 고쳐요.
- 전체 처리 순서가 바뀌면 `CrawlingService`만 고쳐요.
- 특정 사이트의 DOM이나 로그인 방식이 바뀌면 해당 플랫폼 구현(adapter)만 고쳐요.

## 5일 만에 뺀 NestJS

처음에는 NestJS 자체도 넣어 봤어요. NestJS에서는 클래스에 `@Injectable()` 같은 decorator를 붙이면, 프레임워크의 DI container가 생성자에 적힌 의존성을 찾아 인스턴스를 만들어 넣어 줘요. CTO는 Electron main 프로세스에 그 프레임워크까지 올리는 것은 무겁다고 반려했어요. 도입한 지 5일 만에 의존성을 뺐고, decorator와 DI container도 남기지 않았어요.

프레임워크를 뺐다고 파일을 다시 합치지는 않았어요. 요청과 수집 순서, 사이트 처리를 나누는 데 컨테이너가 꼭 필요하지는 않았어요. `PuppeteerService`를 생성자로 받고 Factory(인스턴스를 만들어 돌려주는 함수)에서 직접 조립하면 됐어요. 컨테이너가 하던 인스턴스 조립을 제가 코드로 적어야 하지만, main 프로세스에 프레임워크는 올라가지 않아요.

## 남은 구분을 코드로 보면

앱에서 받은 요청은 `ipcMain` handler가 처리해요. renderer가 `ipcRenderer.invoke`로 보낸 요청이 `ipcMain.handle`에 등록한 함수로 들어오고, 이 함수가 돌려준 값은 renderer 쪽 Promise의 결과가 돼요. 이곳을 HTTP Controller처럼 진입점으로 두었어요. 아래 플랫폼 이름과 일부 식별자는 예시용으로 바꿨어요.

```typescript
const createCrawlingService =
  (puppeteer: PuppeteerService) =>
  (platform: Platform) =>
    new CrawlingService(puppeteer, platform);

export function createCrawlingController(puppeteer: PuppeteerService) {
  const createService = createCrawlingService(puppeteer);

  return {
    collect({ platform }: { platform: Platform }) {
      return createService(platform).collect();
    },
  };
}

const controller = createCrawlingController(puppeteer);
ipcMain.handle('crawl', (_event, req) => controller.collect(req));
```

`createCrawlingService`는 함수를 두 번 불러요. `puppeteer`를 먼저 받아 두고, 요청마다 플랫폼을 넘겨 `CrawlingService`를 만들어요. 앞에서 말한 조립 코드가 이 부분이에요.

Controller는 요청받은 플랫폼에 맞는 Service를 얻어 실행해요. 로그인 함수와 DOM selector는 여기에 없어요. 플랫폼 목록도 다른 곳에 있으니, 새 플랫폼을 등록할 때 Controller를 고치지 않아도 돼요. Service에는 처리 순서만 남겼어요.

```typescript
export class CrawlingService {
  constructor(
    private readonly puppeteer: PuppeteerService,
    private readonly platform: Platform,) {}

  async collect() {
    // 예외 처리와 page 정리는 생략
    const config = CRAWLING_HANDLERS[this.platform];
    const page = await this.puppeteer.open(config.pages.recruit);

    await config.login(page);

    const processor = new config.Processor({ page });
    await processor.collectCandidates();
    await processor.removeDuplicates();
    await processor.saveCandidates();
    await processor.uploadResumes();
  }
}
```

`CrawlingService`는 받은 `PuppeteerService`를 써서 같은 순서를 실행해요. 플랫폼 파일마다 있던 순서가 여기 한곳으로 옮겨 왔어요. 생성자 주입은 NestJS에서 참고했지만, 실제 인스턴스는 앞의 Factory가 만들어요. 플랫폼별 함수는 `CRAWLING_HANDLERS`에서 가져와요.

```tsx
abstract class CandidateProcessor {
  abstract collectCandidates(): Promise<void>;
  abstract removeDuplicates(): Promise<void>;
  abstract saveCandidates(): Promise<void>;
  abstract uploadResumes(): Promise<void>;
}

interface CrawlingHandler {
  pages: { recruit: string };
  login: (page: Page) => Promise<void>;
  Processor: new (args: { page: Page }) => CandidateProcessor;
}

const CRAWLING_HANDLERS = {
  platformA: {
    pages: PLATFORM_A_PAGES,
    login: loginPlatformA,
    Processor: PlatformAProcessor,
  },
  platformB: {
    pages: PLATFORM_B_PAGES,
    login: loginPlatformB,
    Processor: PlatformBProcessor,
  },
  platformC: {
    pages: PLATFORM_C_PAGES,
    login: loginPlatformC,
    Processor: PlatformCProcessor,
  },
} as const satisfies Record<Platform, CrawlingHandler>;
```

추상 클래스는 직접 인스턴스를 만들 수 없고, 상속하는 클래스가 구현할 메서드를 정해 주는 클래스예요. 플랫폼 구현이 이 메서드 중 하나를 빠뜨리면 컴파일 오류가 나요. 언제 어떤 메서드를 부를지는 `CrawlingService`에 있고, 설정 객체에는 각 플랫폼의 클래스와 보조 함수를 연결했어요. 끝에 붙은 `satisfies Record<Platform, CrawlingHandler>`는 플랫폼 하나를 설정에서 빠뜨리면 컴파일 오류를 내요. NestJS Module을 참고한 모양이지만 런타임 DI나 데코레이터를 쓰는 것은 아니에요.

`Processor` 생성자의 타입은 예제에서 구체적으로 적었어요. 당시 코드에서는 `any`였던 자리예요.

## 다음 플랫폼에는 로그인과 파싱을 새로 붙였어요

이후 플랫폼을 더 붙일 때는 기존 수집 함수를 복사하지 않았어요. 공통 순서는 `CrawlingService`에 두고, 사이트가 요구하는 로그인과 파싱을 구현해 설정에 등록했어요.

두 플랫폼을 이렇게 붙였어요. 한 곳은 이력서를 암호화된 ZIP으로 줬어요. 다른 한 곳은 2차 인증과 페이지네이션이 있었고 학력과 경력, 중복 지원자를 처리하는 방식도 달랐어요. 그 차이는 각 플랫폼 구현에 넣었어요. 지원자 한 명을 수집하다 실패해도 나머지는 이어 가도록, 에러는 지원자 단위로 잡았어요.

이제 IPC 요청을 바꾸는 일과 수집 순서를 바꾸는 일, 사이트 DOM을 고치는 일이 같은 파일에서 시작하지는 않아요. NestJS는 빠졌지만 플랫폼을 붙일 때 공통 순서까지 복사하던 방식은 바뀌었어요.

## 플랫폼 함수는 아직 설정에 묶여 있어요

이 리팩터링에 자동화 테스트와 성능 측정은 남기지 못했어요. 구조를 보면 Puppeteer는 생성자로 받으니 대체 객체를 넣을 수 있어요. 다만 `CrawlingService`가 `CRAWLING_HANDLERS`를 모듈에서 직접 읽어서, 로그인 함수와 `Processor`까지 외부에서 바꿔 끼울 수 있는 구조는 아니에요.
