입사 당시 Electron 수집 앱은 여러 채용 플랫폼에서 지원자 정보를 수집하고 있었어요. 수집 대상은 자사가 각 플랫폼의 기업회원으로서 정당한 접근 권한을 가진 지원자 데이터였어요. 플랫폼마다 로그인 방식과 DOM 구조는 달랐지만, 로그인, 중복 확인, 지원자 저장, 이력서 업로드라는 큰 흐름은 같았어요. 그런데 각 플랫폼 파일이 이 흐름을 모두 들고 있어서, 공통 동작 하나를 바꾸려면 여러 파일을 함께 고쳐야 했어요.

## 플랫폼 파일마다 같은 흐름이 한 벌씩 있었어요

기존 구조에서는 플랫폼별 함수 하나가 다음 작업을 모두 수행했어요.

```text
로그인
  -> 목록 수집
  -> 중복 확인
  -> 지원자 등록
  -> 파일 다운로드 및 업로드
```

플랫폼이 추가될 때 기존 파일을 복사한 뒤 selector와 예외 처리를 바꾸는 방식이어서, 공통 로직과 플랫폼별 로직의 경계가 계속 흐려졌어요.

저도 처음에는 기존 플랫폼 파일을 복사하려 했어요. 그렇게 네 번째 플랫폼을 추가하면 로그인 이후의 공통 흐름도 네 벌이 되겠더라고요.

## 무엇이 바뀌면 어디를 고칠지부터 정했어요

마침 백엔드 팀의 NestJS 코드를 보며 Controller와 Service가 나뉜 이유를 이해하던 때였어요. 그 구분을 빌려 파일을 나누는 기준을 세웠어요. 목표는 계층을 늘리는 게 아니라 변경 이유를 세 가지로 나누는 것이었어요.

- IPC 요청이 바뀌면 Controller만 고쳐요.
- 전체 처리 순서가 바뀌면 CrawlingService만 고쳐요.
- 특정 사이트의 DOM이나 로그인 방식이 바뀌면 해당 플랫폼 구현(adapter)만 고쳐요.

## NestJS는 걷어내고 경계만 남겼어요

이 경계 위에 NestJS를 그대로 올려 보려 했지만, CTO가 Electron main 프로세스에 프레임워크까지 얹기에는 무겁다고 반려했어요. 그래서 NestJS를 넣은 지 5일 만에 의존성을 걷어내고 경계만 남겼어요. 최종 구조에는 decorator도 DI container도 없어요.

파일은 "무엇이 바뀌면 어디만 고치는가"로 나눴어요. 프레임워크가 빠져도 이 경계는 그대로 두고, 모듈 경계와 생성자 주입이라는 생각만 남겨 Factory가 의존성을 직접 조립하게 했어요.

아래에서 각 역할을 하나씩 볼게요.

## IPC 요청은 Controller에서 받아요

Electron의 ipcMain handler를 HTTP Controller와 비슷한 진입점으로 봤어요. 예시 코드의 플랫폼 이름과 일부 식별자는 바꿨어요.

```typescript
const createCrawlingService =
  (puppeteer: PuppeteerService) =>
  (platform: Platform) =>
    new CrawlingService(puppeteer, platform);

export function createCrawlingController(puppeteer: PuppeteerService) {
  const createService = createCrawlingService(puppeteer);

  return {
    collect({ platform }: { platform: Platform }) {
      return createService(platform).collect();
    },
  };
}

const controller = createCrawlingController(puppeteer);
ipcMain.handle('crawl', (_event, req) => controller.collect(req));
```

Controller는 요청받은 플랫폼의 Service를 만들어 실행을 넘겨요. 로그인이나 DOM 파싱 규칙은 몰라도 되고, 플랫폼 목록도 들고 있지 않아서 플랫폼이 늘어도 Controller는 바뀌지 않아요.

## Service에는 처리 순서만 남겼어요

```typescript
export class CrawlingService {
  constructor(
    private readonly puppeteer: PuppeteerService,
    private readonly platform: Platform,) {}

  async collect() {
    // 예외 처리와 page 정리는 생략
    const config = CRAWLING_HANDLERS[this.platform];
    const page = await this.puppeteer.open(config.pages.recruit);

    await config.login(page);

    const processor = new config.Processor({ page });
    await processor.collectCandidates();
    await processor.removeDuplicates();
    await processor.saveCandidates();
    await processor.uploadResumes();
  }
}
```

PuppeteerService를 생성자에서 받도록 한 부분은 NestJS의 constructor injection에서 참고했어요. 다만 컨테이너가 자동으로 주입하지 않고, 앞에서 본 Factory가 직접 인스턴스를 만들어요. CRAWLING\_HANDLERS는 다음 절에서 정의해요.

## 플랫폼마다 다른 부분은 추상 클래스와 설정으로 나눴어요

```tsx
abstract class CandidateProcessor {
  abstract collectCandidates(): Promise<void>;
  abstract removeDuplicates(): Promise<void>;
  abstract saveCandidates(): Promise<void>;
  abstract uploadResumes(): Promise<void>;
}

interface CrawlingHandler {
  pages: { recruit: string };
  login: (page: Page) => Promise<void>;
  Processor: new (args: { page: Page }) => CandidateProcessor;
}

const CRAWLING_HANDLERS = {
  platformA: {
    pages: PLATFORM_A_PAGES,
    login: loginPlatformA,
    Processor: PlatformAProcessor,
  },
  platformB: {
    pages: PLATFORM_B_PAGES,
    login: loginPlatformB,
    Processor: PlatformBProcessor,
  },
  platformC: {
    pages: PLATFORM_C_PAGES,
    login: loginPlatformC,
    Processor: PlatformCProcessor,
  },
} as const satisfies Record<Platform, CrawlingHandler>;
```

추상 클래스는 플랫폼 구현이 갖춰야 할 메서드 집합을 컴파일 단계에서 강제해요. 그 메서드를 어떤 순서로 부를지는 CrawlingService가 정해요. 설정 객체는 NestJS Module처럼 구현 클래스와 보조 함수를 한곳에서 연결하지만, 런타임 DI나 데코레이터는 쓰지 않아요.

예시의 Processor 생성자 타입은 지금 다시 쓴 형태예요. 당시 제 구현에서는 이 자리가 any였어요.

## 두 플랫폼을 복사 없이 더 붙였어요

나눈 뒤에는 공통 처리 순서가 CrawlingService 한곳에 모였고, 플랫폼별 selector와 예외 처리는 각 구현 안으로 좁혀졌어요. 이 구조를 실제로 써 본 건 이후 플랫폼을 붙일 때였어요.

- 한 곳은 이력서를 암호화된 ZIP으로 내려줬어요. 다른 한 곳은 2차 인증과 페이지네이션이 있었고, 학력, 경력 추출과 중복 지원자 처리도 따로 필요했어요. 두 곳 모두 기존 플랫폼 파일을 복사하지 않고, 플랫폼별 구현을 새로 만들어 설정 객체에 등록하는 방식으로 붙였어요.
- 지원자 한 명의 수집이 실패해도 나머지 수집은 이어지도록 지원자 단위로 에러를 잡았어요.

최종 구조에 남은 것은 IPC 변경, 공통 수집 순서 변경, 사이트 DOM 변경이 서로 다른 파일에서 끝나는 구조예요. 두 플랫폼을 기존 파일 복사 없이 붙일 수 있었다는 점에서 방향은 맞았다고 봐요.

## 테스트할 수 있는 구조까지만 만들었어요

이 리팩터링에는 자동화 테스트와 성능 측정을 남기지 못했어요.

여기서 구분할 점도 있어요. **테스트 가능한 구조와 테스트가 있는 구조는 달라요.** Puppeteer 의존성은 생성자 경계로 옮겨 대체 객체를 넣을 수 있게 됐지만, CrawlingService가 CRAWLING\_HANDLERS를 모듈에서 직접 읽기 때문에 플랫폼별 로그인 함수와 Processor는 여전히 정적으로 묶여 있어요.
