# API 감사 후속 결정 (2026-10-28)

[API 감사 #112](https://github.com/jingeon27/side-project/pull/112)의 제한은 초기 운영값으로 유지한다. 실제 트래픽과 저장 비용을 측정한 결과는 아니므로 정상 사용자의 429와 업로드 거부 사유를 보고 조정한다. UI의 MB/GB 표기와 달리 코드의 계산 단위는 MiB/GiB다.

| 항목                    | 유지할 값               | 판단과 조정 기준                                                                                                                                                                                                           |
| ----------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 회원 저장 용량          | 5GiB                    | 보관 중인 원본의 합이며 100MiB 영상 약 51개 분량이다. 삭제 중인 파일과 대기 업로드도 계산한다.                                                                                                                             |
| 익명 저장 용량          | 500MiB                  | 최대 크기 영상 5개 분량이다. 계정 재생성 우회는 주소별 예산으로 함께 제한한다.                                                                                                                                             |
| 주소별 업로드 발급 예산 | UTC 하루 10GiB          | 최대 크기 영상 약 102개 분량이다. 실제 S3 전송 성공량이 아니라 발급 크기를 누적하므로 포기·만료·재발급도 예산을 쓴다. UTC 자정은 한국 시각 오전 9시다. 같은 NAT의 이용자가 공유하며 서비스 전체 저장 비용의 상한은 아니다. |
| 미디어 경로             | 주소당 분당 1200회      | 초당 평균 20회이며 사진·대표 사진의 요청이 많은 피드에 맞춘 초기값이다. GraphQL 예산과 별개이고 여러 API 인스턴스에서 합산하지 않는다. 같은 NAT의 정상 사용이 제한되면 사용자별 제한과 함께 재설계한다.                    |
| 그룹 멤버 목록          | 페이지당 기본·최대 48명 | API의 `offset`·`limit`는 유지한다. 현재 웹에 다음 페이지 UI가 없어 49번째 이후 멤버를 관리할 수 없는 문제는 별도로 해결해야 한다. 전체 멤버 수는 `memberCount`를 사용하며 48명을 그룹 인원 제한으로 해석하지 않는다.       |

`auth/password.ts`의 동시 실행 수는 상태를 소유하는 클래스에, `cookie-header.ts`의 따옴표 처리는 단계별 `const` 변환에, `media-upload.service.ts`의 HEAD 실패 처리는 Promise 반환값에 둔다. 동시 실행·대기 한도, 쿠키 파싱 결과, 업로드 검증 오류는 유지한다.

## 다음 릴리스의 DB 정리

삭제 대상은 `OAuthAttempt`, `AppLoginTicket`, `PostUploadAttempt` 테이블과 `PostUpload.completionKey`·`completionStartedAt` 컬럼이다. 현재 런타임 소스에는 사용처가 없지만 Prisma 모델에는 남아 있다. 이번 후속 변경은 운영 DB나 Prisma 스키마를 삭제하지 않는다.

1. #112 이후 버전이 API와 정리 작업을 실행하는 모든 컨테이너에 배포됐는지 확인한다. 아직 실행 중인 구버전은 해당 테이블을 정리할 수 있으므로 PR 병합만으로 삭제 조건이 충족되지는 않는다.
2. 컬럼은 명시적 참조가 없어도 이전 Prisma Client의 기본 조회에 포함된다. 먼저 삭제 대상 필드를 조회하지 않는 Client를 배포한다. 모델·필드의 `@@ignore`/`@ignore`를 이용하면 이 단계에서 실제 DB 구조를 유지할 수 있다. 사용하지 않는 관계 필드도 함께 처리하고 Client를 재생성한다.
3. 해당 호환 버전을 가장 오래된 롤백 대상으로 정하고, 이전 API·ops 컨테이너를 더 이상 실행하지 않는 시점에 별도 contract migration으로 테이블·컬럼을 삭제한다. `schema.prisma`·관계·생성 Client를 함께 갱신하고 격리 스키마에서 `migrate deploy`와 업로드·정리 작업을 검증한다. 배포 전 백업과 기존 배포 도구의 순서를 따른다.

`PostUpload.tokenHash`는 현재 생성 경로가 값을 채우는 별도 호환 필드이므로 이 삭제 목록에 추가하지 않는다. 데이터나 DB를 자동으로 되돌리는 절차는 두지 않는다.
