# 사이드 프로젝트: 짤림픽(가칭) 계획

> 친구들과 만드는 프라이빗 사진 콘테스트 플랫폼. '그룹별 이달의 웃긴 사진 대회' 아이디어를 바탕으로, 실제 서비스 출시와 이직 포트폴리오까지 고려한 기획서다.
> 목표: 단순 CRUD 프로젝트보다 제품 가설 검증 → MVP 출시 → 사용자 행동 분석 → 개선을 경험한다.
> 주요 기술: Next.js · Apollo Client · GraphQL · PostgreSQL

## 1. 프로젝트 개요

### 한 줄 소개

친구들과 비공개 그룹을 만들고, 각자 재미있는 사진을 업로드해 투표로 우승자를 선정하는 소셜 콘테스트 플랫폼.

### 프로젝트 목표

- 실제 사용자가 지속적으로 사용하는 서비스 출시
- 작은 규모에서 제품 가설을 검증하고 사용자 피드백을 기반으로 개선
- Next.js, Apollo Client, GraphQL, PostgreSQL 기반 풀스택 개발
- 실사용 데이터를 통해 성능, 안정성, UX를 개선한 사례 확보
- 기술적 의사결정과 제품 성과를 함께 설명할 수 있는 포트폴리오 제작

예상 개발 기간: 6주 MVP + 2~4주 검증 및 개선
개발 인원: 1명

## 2. 문제 정의 및 가설

### 문제 정의

친구들은 카카오톡이나 SNS에서 재미있는 사진을 공유하지만, 이러한 콘텐츠는 대화 속에 묻히고 일회성 소비로 끝나는 경우가 많다.

친구들끼리 재미있는 사진을 모아 경쟁하고, 우승자를 선정하며, 이전 기록을 추억하는 경험을 하나의 서비스로 제공할 수 있을까?

이 문제 자체가 실제로 존재하는지는 아직 검증되지 않았다.

### 핵심 가설

- **H1 — 참여:** 친밀한 관계로 형성된 소규모 그룹에서는 재미있는 사진 대회에 자발적으로 참여할 것이다.
- **H2 — 재방문:** 우승자를 선정하고 이전 대회의 결과를 기록하면 사용자는 다음 대회에도 다시 참여할 것이다.
- **H3 — 자연스러운 확산:** 친구 초대와 결과 공유를 통해 별도의 광고 없이 새로운 그룹이 생성될 것이다.

### 검증 방식

초기에는 5개 그룹, 그룹당 4~10명을 대상으로 최소 2회의 대회를 운영해 본다.

한 달에 한 번 진행하면 검증 속도가 너무 느리므로 초기 베타에서는 주간 대회를 사용하고, 이후 월간 대회로 전환한다.

## 3. 핵심 사용자 경험

### Core Loop

1. 사용자가 새로운 그룹을 생성한다.
2. 친구들에게 초대 링크를 공유한다.
3. 그룹의 대회가 시작된다.
4. 멤버들이 재미있는 사진을 업로드한다.
5. 업로드가 마감되면 투표를 진행한다.
6. 투표가 끝나면 우승자가 선정된다.
7. 우승 기록을 공유하고 다음 대회에 참여한다.

핵심은 사진 업로드 자체가 아니라 친구들과의 반복적인 상호작용이다.

## 4. MVP 기능 정의

### P0 — 필수 기능

| 영역 | 기능                            |
| ---- | ------------------------------- |
| 인증 | 소셜 로그인, 로그아웃           |
| 그룹 | 그룹 생성, 초대 링크, 그룹 가입 |
| 멤버 | 그룹 멤버 조회, 기본 권한 관리  |
| 대회 | 대회 생성, 진행 상태, 마감 시각 |
| 사진 | 사진 업로드, 목록·상세 조회     |
| 투표 | 사진 선택, 중복 투표 차단       |
| 결과 | 우승자 선정, 결과 확인          |
| 기록 | 이전 대회 우승 기록 조회        |
| 운영 | 사진 신고, 콘텐츠 숨김 및 삭제  |

### P1 — MVP 출시 이후

- 투표 종료 후 결과 공유 카드
- 그룹별 역대 우승 순위
- 대회 주제와 기간 설정
- 푸시·이메일 알림
- 사진 댓글과 반응
- 그룹 활동 통계

### P2 — 성장 이후

- 공개 그룹과 그룹 탐색
- 그룹 간 대항전
- 시즌별 랭킹 및 배지
- 실시간 결과 업데이트
- 사용자 프로필 커스터마이징

### MVP 제외 사항

채팅, 팔로우, 복잡한 추천 알고리즘, AI 이미지 평가, 고급 관리자 CMS는 구현하지 않는다.

## 5. 기본 서비스 정책

초기에는 정책을 단순하게 유지한다.

- 그룹은 비공개이며 초대된 멤버만 참여한다.
- 한 사용자는 한 대회에 사진을 최대 1장 제출한다.
- 제출 기간이 종료된 후 투표를 시작한다.
- 투표권은 멤버당 1표이며 본인 사진에는 투표할 수 없다.
- 투표 현황은 종료 전까지 비공개로 유지한다.
- 동점일 경우 공동 우승으로 처리한다.
- 대회 시작·종료 시각은 서버에서 판단한다.
- 그룹 관리자에게 신고 콘텐츠를 숨길 수 있는 권한을 부여한다.

사진 업로드 시 권리와 동의 여부를 안내하고, 비공개 그룹의 사진은 그룹 외부에 공개되지 않도록 설계한다.

## 7. GraphQL API 설계

### 주요 도메인

| Entity      | 주요 필드                             |
| ----------- | ------------------------------------- |
| User        | id, nickname, avatar                  |
| Group       | id, name, ownerId                     |
| GroupMember | groupId, userId, role                 |
| Contest     | id, groupId, status, startsAt, endsAt |
| Submission  | id, contestId, authorId, imageKey     |
| Vote        | id, contestId, submissionId, voterId  |
| Report      | id, reporterId, submissionId, reason  |

### 핵심 Query

- `me` — 현재 사용자
- `group(id)` — 그룹 상세
- `myGroups` — 참여 그룹 목록
- `contest(id)` — 대회 상세
- `submissions(contestId)` — 제출 사진 목록
- `contestResults(contestId)` — 종료된 대회 결과

### 핵심 Mutation

- `createGroup`
- `joinGroup`
- `createContest`
- `requestUploadUrl`
- `createSubmission`
- `castVote`
- `reportSubmission`

비즈니스 규칙은 GraphQL Resolver에만 의존하지 않고 서비스 계층과 DB 제약조건에서도 검증한다. 예를 들어 대회당 1회 투표 정책은 `Vote(contestId, voterId)`에 Unique Constraint를 적용한다.

## 8. 핵심 기술 도전 과제

### A. Apollo Normalized Cache

- **문제:** 동일한 사진이 대회 목록, 상세 화면, 결과 화면에 동시에 표시된다.
- **학습 및 구현**
  - `typePolicies`, `keyFields`로 엔티티 식별
  - Fragment를 활용한 데이터 재사용
  - `cache.modify`를 통한 캐시 갱신
  - Mutation 이후 refetch와 직접 캐시 갱신의 차이 분석
  - 정렬된 목록과 페이지네이션 캐시 관리
- **검증:** Mutation 이후 불필요한 네트워크 요청 및 UI 재렌더링을 측정한다.

### B. Optimistic UI

- **문제:** 사용자가 투표했을 때 서버 응답을 기다리면 인터랙션이 느리게 느껴진다.
- **학습 및 구현**
  - `optimisticResponse` 적용
  - 중복 요청 처리
  - 실패 시 자동 롤백
  - 서버 결과와 클라이언트 캐시 일치 여부 검증
- **검증:** 인위적으로 네트워크 지연과 오류를 발생시켜 UI 일관성을 테스트한다.

### C. 동시성 및 데이터 무결성

- **문제:** 사용자가 여러 브라우저 탭에서 동시에 투표할 수 있다.
- **학습 및 구현**
  - Database Unique Constraint
  - 트랜잭션 적용
  - 서버 시간 기준으로 투표 종료 처리
  - 동시 요청에 대한 Integration Test
  - 중복 요청에 대한 일관된 오류 응답
- **검증:** 동일 사용자가 투표 요청을 동시에 전송해도 정확히 하나만 성공하도록 한다.

### D. Next.js SSR / RSC / Streaming

- **학습 및 구현**
  - Server Component와 Client Component 경계 설계
  - Apollo SSR과 Hydration
  - Suspense 기반 로딩 UI
  - 인증된 사용자 데이터의 캐싱 정책
  - Apollo 캐시와 Next.js 서버 캐시의 역할 구분
- **검증:** 초기 렌더링, 네트워크 요청 수, Hydration 오류와 Web Vitals를 비교한다.

### E. 이미지 처리 및 성능

- Presigned URL 기반 직접 업로드
- 이미지 파일 형식 및 크기 제한
- 썸네일 생성과 최적화
- 페이지네이션
- 이미지 Lazy Loading
- 접근 권한에 따른 이미지 조회 제한

## 9. 제품 분석 (Amplitude)

### 이벤트 설계

| Event                 | 의미              |
| --------------------- | ----------------- |
| `group_created`       | 그룹 생성         |
| `group_joined`        | 초대 수락 및 가입 |
| `contest_created`     | 대회 생성         |
| `submission_created`  | 사진 제출 완료    |
| `vote_cast`           | 투표 성공         |
| `contest_completed`   | 대회 종료         |
| `result_viewed`       | 결과 조회         |
| `next_contest_joined` | 다음 대회 재참여  |

### 핵심 퍼널

그룹 생성 → 친구 가입 → 사진 제출 → 투표 → 결과 조회

이 과정에서 가장 큰 이탈이 발생하는 구간을 분석한다.

### 핵심 지표

- **North Star Metric:** 주간 활성 대회 수 — 3명 이상이 실제로 참여해 종료된 대회 수
- **보조 지표**
  - 그룹 생성 후 첫 대회 활성화율
  - 그룹당 평균 참여 인원
  - 사진 제출률
  - 투표 참여율
  - 결과 조회율
  - 다음 대회 재참여율

### 초기 POC 성공 기준(가설)

- 5개 그룹에서 최소 2회의 대회 진행
- 그룹당 4명 이상의 가입자 확보
- 참여 가능 멤버 중 60% 이상이 투표
- 첫 대회 참여자 중 50% 이상이 두 번째 대회에 재참여
- 사용자 인터뷰에서 재사용 의향과 구체적 개선점을 확인

수치는 초기 목표이며 실제 사용자 규모와 사용 패턴을 보고 조정한다.

## 11. 포트폴리오 산출물

최종적으로 아래 사례를 문서화한다.

1. 제품 설계: 어떤 사용자 문제를 가정했고, 무엇을 검증했는가?
2. 기술 선택: GraphQL과 Apollo를 사용한 이유와 REST/TanStack Query 대비 트레이드오프
3. 캐시 전략: Apollo Normalized Cache를 활용한 데이터 동기화
4. 안정성: 중복 투표와 동시성 문제 해결
5. 성능: 네트워크 요청 수, 렌더링 및 로딩 성능 개선
6. 제품 지표: 실제 퍼널 데이터로 문제를 발견하고 개선한 경험

기술 선택이 실제 문제 해결에 어떤 영향을 미쳤는지를 중심으로 기록한다.

## 12. 최종 목표

- **1차 목표:** 친구들이 실제로 대회를 진행할 수 있는 MVP 출시
- **2차 목표:** 5개 이상의 실제 그룹을 확보하고 반복 참여를 검증
- **3차 목표:** 사용자 데이터에 기반한 개선과 기술적 트레이드오프를 문서화
- **장기 목표:** 특정 커뮤니티 안에서 반복적으로 사용되는 소셜 놀이 서비스로 성장할 가능성 검증

프로젝트 성공은 코드의 양이나 기술 스택의 수가 아니라 사용자가 다시 돌아오는 경험을 만들었는지로 판단한다.

## 추천 개발 전략

위 계획을 진행한다면 세 가지를 우선한다.

1. **6주 안에 MVP를 출시한다.** React 컴포넌트 설계나 프론트엔드 리팩터링 경험은 충분히 쌓았으니, 이번에는 기존에 잘하는 부분을 반복하기보다 서버·데이터베이스·제품 검증 경험을 확보한다.
2. **Apollo를 선택한 기술적 이유를 실험으로 증명한다.** 예를 들어 투표 기능에서 Apollo의 정규화 캐시와 낙관적 업데이트를 사용한 전후 네트워크 요청, 캐시 일관성, 실패 복구를 비교한다. 공식 Next.js 통합은 RSC와 Client Component를 모두 지원하고, GraphQL Code Generator를 통한 타입 생성도 활용할 수 있다(Apollo GraphQL Docs).
3. **사용자 20~50명 확보를 기능 추가보다 우선한다.** 프로젝트가 실제로 사용된다면 Apollo나 GraphQL을 사용해 봤다는 사실보다 더 설득력 있는 이야기가 생긴다.

이 프로젝트에서 가장 가치 있는 결과는 단순히 '사진 대회 서비스를 만들었다'가 아니라, **'사용자의 재참여를 높이기 위해 어떤 가설을 세우고, 기능을 설계하고, 데이터를 분석해서 개선했는가'**를 설명할 수 있게 되는 것이다.
