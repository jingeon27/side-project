# MVP 구현 기록

기획: `product-plan.md`.
2026-10-13 기준으로 친구들과 비공개 대회를 진행하는 P0 흐름을 구현했다.
실제 베타 사용자 모집과 제품 가설 검증은 코드 검증 이후 수행한다.

## 정책과 기술 결정

| 항목        | 구현과 이유                                                                                                                                                                       |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 패키지/UI   | 기존 저장소 규칙의 Yarn 4 / Base UI를 유지했다.                                                                                                                                   |
| 대회 단계   | DB에 phase를 저장하지 않고 startsAt, submissionEndsAt, endsAt을 서버 시각과 비교한다. 별도 종료 작업이 늦어도 API 정책이 바뀐다.                                                  |
| 경계 시각   | 제출 마감부터 투표, 투표 마감부터 결과 공개. 시작보다 앞서면 예정 상태.                                                                                                           |
| 무투표 대회 | 유효한 득표가 모두 0이면 우승자가 없다. 참여 사진은 결과에서 볼 수 있다.                                                                                                          |
| 공동 우승   | 숨기지 않은 사진 중 최대 득표를 모두 우승자로 반환한다.                                                                                                                           |
| 무결성      | Submission(contestId, authorId), Vote(contestId, voterId)의 unique와 Serializable 재시도를 적용한다. UI 상태는 권한이나 중복 방지 수단이 아니다.                                  |
| 비공개 사진 | 매 파일 요청에서 세션과 그룹 멤버십을 검사하고 no-store로 응답한다. 숨긴 사진은 관리자만 볼 수 있다.                                                                              |
| 업로드      | 5분 유효한 일회용 ticket으로 API에 직접 전송한다. JPEG/PNG/WebP 실제 디코딩, 최대 40MP/10MB, 1600px WebP로 변환하며 메타데이터를 제거한다.                                        |
| 스토리지    | 로컬 private 디렉터리와 S3 호환 private 버킷 어댑터. 원본의 S3 presigned 직접 업로드는 변환 파이프라인 복잡도를 줄이기 위해 베타 범위에서 선택하지 않았다.                        |
| 캐시        | User/Group/Contest/Submission을 ID로 정규화한다. 투표는 cache.modify와 optimisticResponse를 사용한다. 사진 제출/운영 작업은 영향을 받는 활성 목록·결과 쿼리를 refetch한다.        |
| SSR         | Me는 Apollo RSC PreloadQuery로 요청별 Cookie를 전달한다. Cookie 원문은 Client Component props로 전달하지 않는다. 그 밖의 변경이 잦은 화면은 브라우저 쿼리와 polling으로 갱신한다. |
| 기록        | 그룹 화면에서 최근 50개 대회를 조회한다. 사진 목록은 24장 단위, 최대 요청 크기 48장. 결과는 종료한 대회의 전체 사진을 순위로 보여준다.                                            |
| 관측        | 제품 이벤트를 변경과 함께 DB outbox에 기록한다. Amplitude insert_id로 재시도를 식별한다. 종료 이벤트는 백그라운드 작업으로 기록하며 phase 판단은 해당 작업에 의존하지 않는다.     |
| 재참여 정의 | 같은 그룹의 이전 종료 대회에 사진을 제출한 사용자가 이후 대회에도 제출하면 next_contest_joined. 결과 조회는 계정·대회당 최초 1회.                                                 |
| 운영        | 신고는 계정·사진당 1건, 내용은 관리자만 조회. 숨김은 보존, 삭제는 투표·신고도 제거. 미제출/삭제 파일과 만료 인증 요청은 주기적으로 정리한다.                                      |

## 확인한 내용

- 실제 PostgreSQL에서 API 권한·사진 변환·중복 제출·마감 정책·공동 우승을 검증했다.
- 같은 계정의 투표 8건을 동시에 요청하여 정확히 1건의 Vote와 vote_cast 이벤트만 생성됨을 확인했다.
- OAuth 외부 응답만 경계에서 대체하여 PKCE verifier 전달, state/만료/재사용 거부, session hash 저장을 검증했다.
- 실제 RHF/Base UI 폼과 키보드 focus 복귀를 UI 테스트로 검증했다.
- 두 서버와 두 브라우저 계정으로 그룹 생성 → 초대 가입 → 사진 제출 → 투표 → 공동 우승까지 실행했다.
- 브라우저에서 실패 응답을 주입하여 낙관적 투표가 롤백되고 다시 투표할 수 있음을 확인했다.
- 데스크톱/390px 화면 캡처와 가로 overflow, SSR HTML에 세션 원문이 없는 것을 확인했다.

## 외부 환경에서 확인할 내용

- 실제 Google·카카오 OAuth 앱의 consent/redirect/client-secret 설정과 인증
- private S3/R2/MinIO 버킷 접근·권한·삭제 및 API 볼륨/네트워크 구성
- Amplitude 프로젝트에서 이벤트 수신·퍼널·재참여율, Sentry 오류 수신
- 실제 서비스 배포와 최초 5개 그룹의 2회 대회 운영
- 네트워크 요청 수, Apollo 캐시 효과, Web Vitals의 정량 비교 및 사용자 인터뷰

현재 수치로 사용자 재참여율이나 성능 개선 효과를 주장하지 않는다.
