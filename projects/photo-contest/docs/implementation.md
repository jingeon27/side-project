# 웃긴순간 구현 기록

2026-10-15 기준 코드와 검증 기록입니다. 친구 그룹 모집·실사용·재방문 가설과 전환율은 아직 측정하지 않았습니다.

## 제품과 구조

홈·MY·그룹·초대·대회 화면을 `_pages/<화면>`에서 조립하고 라우트는 배럴을 통해 연결했습니다. 최초 사용자·그룹·대회·초대·사진 조회는 RSC `PreloadQuery`가 준비하고, 브라우저는 같은 Apollo 문서와 변수로 읽습니다. Cookie 원문은 서버의 API 요청에만 전달합니다.

비공개 그룹, 관리자/일반 멤버 구분, 1인 1장·1인 1표, 좋아요·정렬·공동 우승·무투표·지난 대회·그룹 순위·신고/숨김/삭제를 구현했습니다. 사진은 실제 포맷을 검증해 WebP로 변환하고 모든 파일 조회에 그룹 권한을 검사합니다.

대회 단계는 저장하지 않고 서버 시각과 세 마감으로 계산합니다. 종료 기록 작업이 늦어도 제출·투표·결과 정책은 바뀝니다. 중복 요청은 DB unique와 Serializable 재시도로 제한합니다.

## 캐시와 실패 처리

Apollo 정규화 캐시가 서버 상태를 소유합니다. 좋아요·투표는 낙관적 응답 후 실패 시 Apollo가 되돌립니다. 폼은 실제 RHF·Base UI로 제출하고 실패 후 입력을 유지합니다. 오버레이는 overlay-kit, mutation 진행·오류는 Apollo와 공통 토스트로 처리합니다.

사진 목록은 `offsetLimitPagination(['contestId', 'sort'])`으로 정렬별 24장씩 받습니다. 리뷰에서 숨김 이후 offset과 기존 목록이 어긋날 수 있음을 확인해 목록을 비우고 첫 페이지를 다시 받도록 바꿨습니다. 공개 피드는 숨긴 사진을 빼고 관리자 목록에서만 보여줍니다. 피드는 polling하지 않으며 새로고침·앱 복귀·변경 후 다시 조회합니다.

진행 중인 대회 정보는 로그인한 사용자에게 30초마다 갱신해 마감 이후 투표·결과 화면으로 전환합니다. 종료되거나 로그인이 풀리면 갱신을 멈춥니다. 단계 이동 뒤 새로고침 없이 화면이 바뀌는 동작을 브라우저 테스트로 확인했습니다.

화면과 각 조회에는 로딩·빈 결과·권한/로그인·실패 상태를 넣었습니다. 그룹 순위는 별도 조회해 실패해도 그룹의 다른 기능은 사용할 수 있습니다.

조회 부모의 `useBackgroundQuery`와 섹션 자식의 `useReadQuery`를 나누고 `QueryRef`로 연결했습니다. 인증·그룹 목록·순위·피드·결과는 각각 Suspense·오류·재시도 경계를 가집니다. 인증·대회 단계·조회 실패는 ts-pattern으로 분기하고, 대회 헤더·안내·제출·관리·주기 갱신도 각 책임에 맞게 분리했습니다. 추가 조회와 새로고침은 transition으로 기존 사진을 유지합니다. 첫 페이지 갱신 시 과거 페이지를 덮어쓰고, 관리자가 받는 숨긴 사진도 offset 계산에 포함합니다.

## 인증·앱·모니터링

세션은 HttpOnly 쿠키이며 DB에는 해시만 저장합니다. Origin 검사·OAuth state/PKCE·일회용 앱 로그인 티켓 교환을 적용했습니다. 앱은 시스템 브라우저에서 인증하고 웹이 코드를 교환해 WebView 쿠키를 받습니다.

Expo 셸은 네이티브 공유·클립보드·햅틱·외부 링크, 딥링크·Android 뒤로 가기·최소 버전·오프라인/프로세스 종료 복구를 담당합니다. 네이티브가 안전 영역을 처리하고 웹은 540px 앱 열을 유지합니다.

API는 예상하지 못한 오류만 정리해 Sentry에 보내고 도메인 이벤트는 DB에 기록합니다. 웹·앱은 Sentry와 Amplitude를 사용하며 키 없는 실행과 테스트는 외부로 전송하지 않습니다.

## 확인한 내용

- API: 실제 PostgreSQL·supertest로 권한, 업로드/변환, 마감, 순위, 중복·동시 요청, 세션·PKCE·재사용 방지, 오류 응답을 검사했습니다. 기동한 스키마의 모든 Query·Mutation 필드가 resolver에 연결되는지도 확인했습니다.
- 웹 계약: 생성 GraphQL 문서를 격리 API에 실행해 그룹·초대·사진·좋아요·투표·결과·순위·신고·숨김·삭제와 비회원/신고 내용 보호를 확인했습니다.
- 브라우저: Chrome·WebKit에서 그룹 생성→초대 가입→두 사용자 사진 제출→좋아요→투표→숨김→결과→그룹 순위를 실행했습니다. 로그인 게이트, 만료 쿠키, 잘못된 초대, MY/로그아웃, 가로 넘침·앱 열도 검사했습니다. 홈·MY의 사용자 정보가 JS 실행 전 서버 HTML에 있고 서버 오류 fallback이 없음을 확인했습니다. 열어둔 대회가 투표와 종료 결과로 전환되는 동작도 검사했습니다.
- 앱: 실제 웹을 모바일의 라우터·기능 로직에 붙여 딥링크·복귀·뒤로 가기·공유·복사·햅틱·로그인 성공/취소/실패를 확인했습니다. OS와 OAuth provider 경계만 대체합니다.
- 웹 codegen·타입 검사·lint·프로덕션 빌드를 확인했습니다. 테스트는 독립 DB의 임시 스키마를 만들고 종료 뒤 남은 스키마가 없는지 검사합니다.

Vitest 674개(API unit 54·실제 DB 172, 웹 unit/UI 263·API 계약 4, 모바일 unit/UI 137·API 계약 9, bridge 35), Playwright 36개(웹 12·모바일 24)가 통과했습니다. 모바일의 Android 하드웨어 뒤로 가기 두 항목은 iOS 프로젝트에서만 제외합니다. 웹 프로덕션 빌드와 모바일 JS 번들 검사도 통과했으며, 마지막 검사에서 남은 테스트 스키마는 0개였습니다. 웹의 추가 5개는 섹션별 로딩·실패·재시도·대상 변경과 사진 추가 조회·첫 페이지 갱신을 검증합니다. 이번 웹 리팩터링에서는 웹 unit/UI·API 계약·브라우저와 모바일 브라우저 레인을 다시 실행했습니다.

테스트용 사용자·세션·단계·외부 로그인 콜백 티켓은 `/testing/*`로 준비합니다. 테스트 환경과 활성화 플래그를 모두 요구하고 개발·운영에서 활성화하면 시작을 거부합니다. 앱별 테스트 레인은 전용 DB의 임시 스키마와 별도 포트의 서버에서 실행했습니다.

## 로컬 실행 환경

개발 DB에 `20261013130000_likes_and_app_login`을 적용하고 API·웹을 다시 시작했습니다. 개발 주소에서 기존 계정의 로그인·그룹 조회·MY·로그아웃과 웹 프록시의 헬스를 확인했고, 브라우저 오류는 없었습니다. 개발 서버의 `/testing/users`는 404를 반환합니다. 이 확인에서는 그룹·대회·사진을 추가하지 않았습니다.

`db:test:local`은 개발 DB와 다른 `.data/test-postgres`·55434·`photo_contest_test`를 사용합니다. `.env`의 `TEST_DATABASE_URL`을 이 DB로 설정한 뒤 API e2e 172개와 스키마 정리 검사를 실행해 통과했습니다. 테스트 DB는 별도 터미널에서 같은 명령으로 다시 시작할 수 있습니다.

GitHub Actions에서도 API·계약·빌드 검증과 웹·모바일 브라우저 레인이 모두 통과했습니다. 로컬 결과와 원격 CI 결과는 별도로 확인했습니다.
